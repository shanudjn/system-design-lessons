**Curriculum spine item:** #47 (Storage engines: LSM-trees vs B-trees)
**Worked example:** Lesson 44's metrics ingest — 1,000,000 writes/second, each a 16 B sample (timestamp+value), randomly interleaved series keys → only 16 MB/s of DATA but the hardest possible *shape* of write.

## What this lesson covered

The framing: for 46 lessons a "database" was a black box; Lesson 12 opened it for READS (the B-tree). This lesson opens it the rest of the way for WRITES — how a **storage engine** turns a stream of writes into bytes on a disk that is fast at SEQUENTIAL and slow at RANDOM access. That one gap decides everything. Followed the four-move spine:

- **Estimate** — the B-tree (Postgres/InnoDB default, read-optimized: any of 100M rows in ~3 hops, L12) collapses under the firehose because it keeps keys **sorted in place** on disk. Each 16 B insert = read-modify-write of a whole **8 KB page** → 8,192 ÷ 16 = **512× write amplification** for an isolated insert. Random keys defeat the one escape (page-batching: 512 sorted inserts to one page → ~1×), so each write hits a scattered page, evicted before the next write for it arrives, and it's a read-modify-write (random read + random write). Two views of the wall: bandwidth = 16 MB/s × 512 = **8 GB/s ≈ 16×** the disk's entire sequential bandwidth (and not sequential); ops = ~1,000,000 random writes/s vs a disk's ~100 (HDD, 10,000× short) to ~50,000 (SSD, 20× short) random IOPS. No same-class faster disk closes an orders-of-magnitude gap. NAMED trade: sorted-in-place (B-tree) vs log-structured (LSM) — "always sorted on disk" and "never random-write" cannot both hold; the B-tree chose sorted-in-place and pays on writes.
- **Model** — the **LSM-tree** (RocksDB, Cassandra, LevelDB, ScyllaDB): if random writes are expensive, never do them. Four parts:
  - **Write path**: append to a sequential **WAL** (crash recovery) + insert into the RAM **memtable** (sorted skip-list/tree), ack. 16 MB/s WAL = 3.2% of 500 MB/s (vs the B-tree's 1,600%).
  - **Flush**: full memtable (64 MB) → one immutable sorted **SSTable** in one sequential pass. 64 MB fills every 64÷16 = 4 s, flushes in 64÷500 = 0.13 s. WAL segment then discarded.
  - **Immutability**: updates = a new write that shadows the old (newest wins); deletes = a **tombstone** (L15/20 delete-by-marker). A key can have several versions across SSTables.
  - **Compaction**: background merge-sort of SSTables (sequential), keep newest per key, drop shadowed values + tombstones. **Size-tiered** (merge similar sizes → low write amp, high read/space amp) vs **leveled** (sorted non-overlapping files per size level → high write amp, low read/space amp).
  - NAMED trade — the **amplification triangle** (can't minimize all three): write amp (~10–30× leveled, all SEQUENTIAL, vs B-tree's random 512×), read amp (probe memtable + several SSTables), space amp (dead versions/tombstones until compacted).
- **Trace** — (A) write: WAL append (only durable step, ~µs) + memtable insert, ack; later flush; later compact — never a random page. (B) point read: newest→oldest, would probe ~7 levels of SSTables (read amp) vs a B-tree's deterministic ~3–4 hops → per-SSTable **Bloom filter** (L21) answers "definitely NOT here" with no false negatives → skip the file's disk read; 10 bits/key → 0.6185^10 ≈ **0.8% (~1%)** FP → read touches ~1 real file + negligible false probes (~7→~1). (C) range read: Bloom CANNOT help — it's exact-key membership, not "any key in [a,b]" and you don't know the keys in advance → merge every overlapping SSTable = full read amp (the LSM's honest weakness; leveled compaction exists to keep this small; B-tree's sorted-in-place scan is its home turf, L12/18). (D) delete: write a tombstone → shadows older values → space TEMPORARILY increases until a compaction sees both tombstone and values and drops them; tombstone-heavy files slow scans.
- **First bottleneck** — compaction is a SECOND write workload on the same disk. The WAL's 3.2% makes ingest look free, but every byte is rewritten ~10–30× by compaction sharing one 500 MB/s disk → sustainable ingest ceiling = **bandwidth ÷ write-amp** ≈ 500 ÷ 20 = **25 MB/s** (only ~1.5× headroom over our 16 MB/s; at WA 30× → 16.7 MB/s, right on our load). Cross it → SSTables pile at the top level faster than merged → read amp climbs, space balloons → engine **throttles/stalls writes** ("write stall" / "compaction debt"). This is L27's utilization knee + L28's backpressure INSIDE one database. NAMED trade: foreground latency vs background work — one disk's bandwidth split between "serve now" and "clean up so we can serve later."

Scoreboard table: B-tree wins random-write? no; point read deterministic; range scan cheap (contiguous); write amp high & random (~512×); space ~1.3–1.5× (half-full pages); best for read/range-heavy OLTP. LSM: high write throughput; point read ~1 Bloom-gated file; range scan merges files; write amp ~10–30× sequential; space ~1.1× leveled; best for write-heavy logs/metrics/ledgers/KV.

Four traps: (1) B-tree because it's the default, under a write-heavy random-key load; (2) assuming the LSM made writes free (real ceiling = BW ÷ WA, not the WAL); (3) expecting Bloom filters to speed range scans (point-membership only); (4) ignoring tombstones & space amplification (deletes don't shrink immediately).

Arithmetic double-checked: 1,000,000 × 16 B = 16 MB/s; 8,192 ÷ 16 = 512; 16 MB/s × 512 = 8,192 MB/s = 8 GB/s; 8,192 ÷ 500 = 16.4×; 1,000,000 ÷ 100 = 10,000; 1,000,000 ÷ 50,000 = 20; 16 ÷ 500 = 3.2%; 64 ÷ 16 = 4 s; 64 ÷ 500 = 0.128 s; 0.6185^10 = e^(10·ln0.6185) = e^(−4.805) = 0.0082 ≈ 0.8%; 500 ÷ 20 = 25 MB/s; 500 ÷ 30 = 16.7 MB/s.
