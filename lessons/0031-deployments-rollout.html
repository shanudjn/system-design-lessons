Deployments & Progressive Rollout: Shipping New Code to a Live Fleet Without Making Every User Your Test Subject

For thirty lessons we built a system. Now we have to change it — ship a new version of the code to Lesson 27's live fleet (286 servers, 40,000 req/s) while real users are mid-request. The tempting move is the simplest one: swap every server to the new build at once. That is a big-bang deploy, and it hides the exact failure Lesson 30 spent its whole length shrinking — a blast radius of everything, now in release form. If the new build has a bug, 100% of traffic hits it the instant it lands, and you find out from users, not tests. This lesson takes that one fleet and traces how to push new code so a bad version burns a fraction of users for a few seconds, not all of them for minutes. We'll estimate the blast radius of big-bang versus a canary, model the three rollout strategies (rolling, blue-green, canary) plus the feature flag that decouples deploy from release, trace a healthy rollout and a poisoned one through health-gated promotion, and hit the wall that defines the domain: old and new versions run at the same time over one shared database that can't be rolled back in seconds — so a rollout is only as safe as the compatibility of the state underneath it. The trade shifts from Lesson 30's blast-radius-vs-friction to release velocity vs blast radius.

The one system we'll design

Take Lesson 27's API tier: 286 servers behind a load balancer, serving 40,000 requests/second at a target utilization safely below the knee. Version v2 is built and passed its tests — but tests never cover the exact mix of live traffic, real data, and production load. The job: get every server running v2 without an outage, and with a fast, safe way back to v1 if v2 misbehaves. First, one distinction the whole lesson rests on.

Deploy = the new code is present and running on the servers. Release = the new behavior is reaching users. They sound identical and are usually done together — which is the mistake. Keeping them separate is the single most powerful lever in this lesson: you can deploy code that is switched off (safe — it's just sitting there), then turn it on for 1% of users, then 100%, then off again — all without touching a server. Hold that distinction; Move 2 turns it into feature flags.

  THREE WAYS TO REPLACE v1 WITH v2 ON A 286-SERVER FLEET

  BIG-BANG                ROLLING (batch 10%)        BLUE-GREEN
   all 286 -> v2 at once   29 at a time, 10 waves     two full fleets, flip the LB
   [v2 v2 v2 v2 v2]        [v2 v2 v1 v1 v1]  wave 3    BLUE(v1) 286   GREEN(v2) 286
   100% exposed instantly  mixed versions live         LB ---> BLUE      (warm, 0%)
   rollback = redeploy     rollback = roll back        flip: LB ---> GREEN  (instant)
   (~minutes)              through the waves (slow)     rollback = flip back (~seconds)

  CANARY (the small-blast-radius one)          FEATURE FLAG (deploy != release)
   route a SLICE to v2, watch, then ramp        v2 shipped to 100% of fleet, code OFF
     1%  -> watch health -> 5% -> 25% -> 100%    flag on for 1% of USERS -> 100%
   a bug shows at 1%, never reaches the rest     rollback = flip the flag (no redeploy)

  blast radius:  big-bang = 100%   >   rolling = grows per wave   >   canary/flag = the slice

Every strategy here is one idea applied two ways: shrink how many users a bad version can reach (canary, feature flag → expose a slice), or shrink how long it takes to undo it (blue-green → instant flip back). Big-bang does neither: 100% exposed, and rollback means a full redeploy. The rest of this lesson is choosing which of those two dials you turn, and paying for it in fleet cost, deploy speed, or operational machinery.

Words we'll earn before we lean on them

  • Deploy vs release — code running on servers vs behavior reaching users. Decoupling them is the core move.
  • Big-bang deploy — replace the whole fleet at once. Simplest, largest blast radius.
  • Rolling deploy — replace the fleet in batches, so old and new run side by side during the roll. No extra fleet, but slow rollback and mixed versions.
  • Blue-green — run two full fleets (blue = old, green = new); shift the load balancer from one to the other. Instant rollback, but 2× fleet during the swap.
  • Canary — route a small slice of traffic to the new version, watch its health, then ramp up in stages. Named for the canary in a coal mine: a small sacrifice that warns before the whole is harmed.
  • Feature flag — a runtime switch that turns a code path on/off (per user, per %, per region) without a redeploy. The mechanism that decouples deploy from release. A dark launch ships the code with the flag off.
  • Health-gated promotion / automated canary analysis — promote to the next stage only if the new version's error rate and latency (Lesson 17's p99) stay within a threshold of the old; otherwise auto-roll-back.
  • Bake time — how long you hold a stage to gather enough signal before promoting.
  • Rollback — return to the last known-good version. TTR (time to recover) = detect + decide + revert.
  • Blast radius — how many users a bad release harms before you stop it. Backward/forward compatibility — whether a version works with the data and neighbors written by the other version.

Move 1 — Estimate: what a big-bang deploy actually costs

Before choosing a strategy, price the naive big-bang on the axis that matters for a release: how many requests hit the bug before you can stop it. That number is rate × time-to-recover, and both factors are large.

Worked: big-bang blast radius. Say v2 has a bug that breaks a request. You don't know instantly — an alarm needs a minute or so of sustained errors to fire (Lesson 17), then a human or automation decides and triggers a rollback, and re-deploying v1 across 286 servers takes a few minutes. Call the whole time-to-recover ≈ 5 minutes = 300 s (optimistic). With the fleet at 100% on v2:

• failed requests = 40,000 req/s × 300 s = 12,000,000. Twelve million requests hit the bug — every user at once — before the fix lands.

That is the release-form of Lesson 30's one-key blast radius: a single change, 100% exposed.

Worked: the same bug, shipped as a canary. Route just 1% of traffic to v2 and hold there while you watch. Exposure = 1% × 40,000 = 400 req/s. Over the same 300 s detection window that's 400 × 300 = 120,000 failed requests — a 100× smaller blast radius — and because the canary is explicitly watched, its error spike is caught and the ramp is stopped, so the bug never reaches the other 99%. In practice automated canary analysis reacts in ~60 s, not 300 s: 400 × 60 = 24,000 — a 500× cut. The bug still shipped; it just met 24,000 requests instead of 12,000,000.

Name the trade-off — release velocity vs blast radius. A big-bang deploy is the fastest and cheapest way to ship: one step, no extra fleet, done in minutes. Every safer strategy below slows the release down (stages, bake times, ramps) or spends more (a second fleet, a metrics-and-automation pipeline) to buy a smaller blast radius. You are not choosing between "safe" and "unsafe" — you're choosing how much deploy speed and machinery you'll trade to cap how many users a bad version can burn. Every strategy in Move 2 sits somewhere on that one line.

Move 2 — Model: three strategies and the flag that changes the game

The estimate says: shrink the exposed slice, shrink the time to undo, or both. Three deployment strategies and one orthogonal technique cover the space.

Rolling — cheap, gradual, but slow to undo

Replace the fleet in batches: take 10% (≈ 29 servers) out, put v2 on them, return them, repeat 10 times. No extra hardware — the same 286 boxes end up on v2. The costs: (1) while a batch is out, 257 servers carry 40,000 req/s, so per-server load rises 286/257 ≈ 1.11× — you need Lesson 27's headroom (or add surge capacity before removing) or utilization creeps toward the knee. (2) Exposure grows wave by wave — after wave 3, 30% of traffic is on v2 — with no explicit "hold and watch" gate. (3) Rollback means rolling the waves backward: minutes, not seconds. And throughout, both versions serve live traffic — remember that; it's the wall.

Blue-green — instant rollback, at the price of a second fleet

Stand up a whole second fleet of 286 servers running v2 (green) next to the live one running v1 (blue), warm it, then point the load balancer at green. If green is bad, point back at blue — rollback in seconds, because v1 was never torn down. The cost is the transient double fleet: 286 extra servers for the deploy window. At Lesson 27's ~$4,384/server-year (≈ $0.50/server-hour), a one-hour cutover of doubled capacity is 286 × $0.50 ≈ $143 — modest. The subtler cost: the flip itself is all-at-once. Unless you shift the load balancer gradually (which is just canary by another name), blue-green optimizes rollback speed, not blast radius — at the flip, 100% moves to green together.

Canary — the smallest blast radius, at the price of machinery and time

Route a small, fixed slice (1%) to v2, hold and watch (the bake time), and promote through stages — 1% → 5% → 25% → 50% → 100% — only while health holds. This is the strategy that directly buys the Move 1 estimate: a bug is caught at 1% and never promoted. The price is real: you need the metrics to judge health (Lesson 17), enough traffic and bake time at each stage to get a signal, and automation to promote or roll back — and the full ramp takes longer than any other strategy.

Feature flags — decouple deploy from release (the orthogonal lever)

All three above move servers. A feature flag moves the decision into the running code: deploy v2 to 100% of the fleet with the new path switched off (a dark launch — low risk, the code is just present), then flip the flag on for 1% of users, ramp to 100%, and — critically — roll back by flipping the flag off, in milliseconds, no redeploy. Flags give canary-style exposure control at the user level and work for changes you can't route around (logic buried deep in shared code). They compose with the others: deploy via rolling, release via flag.

Name the trade-off — where the "undo" lives. Blue-green puts undo in the load balancer (flip the fleet). A feature flag puts undo in a config value (flip the switch). A rolling deploy has no cheap undo at all — you must re-run the process backward. The faster and cheaper the undo, the less a bad release costs you, which is why the best real rollouts stack them: ship code dark (deploy), release behind a flag to a canary slice (small blast radius), keep the old fleet a flip away (fast undo). Each layer is buying down either the size of the blast or the time to stop it — the two dials from the diagram.

Move 3 — Trace the paths

Run one healthy version and one poisoned version through the same canary pipeline and watch the gate do its job.

Path A — a good version rides the ramp to 100%

  1. DEPLOY    v2 to a canary slice; load balancer sends 1% (400 req/s) to it
  2. BAKE      hold 10 min; compare canary error rate & p99 to the v1 baseline
  3. GATE      within threshold -> PROMOTE
  4. RAMP      5% -> bake -> 25% -> bake -> 50% -> bake -> 100%
  5. RETIRE    v1 fleet drained and removed; v2 is the new baseline
  -> users saw a gradual, watched, reversible change; at no point was 100% at risk

The slow part is the point. Each stage is a checkpoint where a problem is still cheap: the worst case at the 1% stage is 400 req/s, at 25% it's 10,000 req/s — but by 25% the version has already survived two earlier gates on real traffic. Draining in step 5 matters: an old instance is removed only after its in-flight requests finish and its connections close gracefully (Lesson 26), so retiring v1 doesn't drop live work.

Path B — a poisoned version is caught at 1% (and where the wall appears)

  1. DEPLOY    v2 (has a bug) to the 1% canary slice — 400 req/s
  2. OBSERVE   canary error rate jumps 0.1% -> 4%; p99 doubles vs baseline
  3. GATE      threshold breached -> AUTO-ROLLBACK: canary slice back to 0%, page on-call
  4. RESULT    blast radius = the ~24,000 requests that hit the 1% before the gate fired
                 (500x smaller than big-bang's 12,000,000) — the other 99% never saw v2
  5. ...BUT    while v2 ran, it WROTE to the shared database in its new format.
               Rolling the CODE back to v1 does NOT un-write those rows.  <-- the wall

Steps 1–4 are the whole promise of progressive delivery: a bug meets a fraction of users for a moment, the gate fires, and you're back on v1. Step 5 is the catch that Move 4 exists for. The load balancer flipped in seconds, but the database did not flip with it — any state v2 wrote in its new shape is still there, and now v1 has to read it. Rollback is only as fast as your slowest-to-reverse layer, and the database is never as fast as the load balancer.

Move 4 — Find the first bottleneck: two versions, one shared state

Every progressive strategy has the same structural fact at its core: during the rollout, old and new run at the same time, and they share things that are not versioned with the deploy — the database schema, cache entries, message formats on the queue (Lesson 9), the API contract (Lesson 18). The fast rollback you designed is an illusion if a version change underneath it can't be undone as fast. Two hazards make this concrete.

Hazard 1 — mixed versions must interoperate. Canary and rolling both mean v1 and v2 serve simultaneously and touch the same rows and messages. If v2 writes a new column or a new message field that v1 can't parse, v1 throws the instant it reads that row — so your "1% canary" just broke the 99% still on v1. This is Lesson 18's rule (additive changes safe; removals/renames break clients) and Lesson 24's expand/contract, now applied between two live versions of your own service.

Hazard 2 — the database is not in the deploy. You can flip code from v2 to v1 in seconds (blue-green, or a flag). You cannot un-migrate a schema or un-write data in seconds — a schema change is Lesson 24's careful, batched, throttled migration, and a DROP is a one-way door (Lesson 30's irreversible step). So a safe rollback requires that v2's code also works against the old schema, and that v1 tolerates anything v2 wrote — i.e. every neighbor pair is backward- and forward-compatible.

Name the core trade-off — a fast release needs a compatible past. Progressive rollout hands you a fast undo button for code. But the button only works if the state changes underneath are themselves reversible or compatible. That's why you never ship a destructive migration with the code that needs it: you expand the schema first (add nullable columns, dual-write — Lesson 24), deploy code that works against both shapes, and only contract (drop the old shape) long after the new code has baked and rollback is no longer needed. The release can move fast precisely because the schema moved slow and compatibly — deploy velocity is bought by decoupling the code rollout from the data migration, never by fusing them.

The four traps

  • Trap 1 — coupling the migration to the deploy. Ship a RENAME/DROP in the same release as the code that depends on it, and a code rollback leaves you stranded: the new code is gone but the schema already changed, so v1 is now broken against a shape it never knew. Decouple them (expand → deploy → bake → contract, Lesson 24). The migration and the deploy are two separate, separately-reversible steps.
  • Trap 2 — a green canary that proves nothing. 1% for two minutes may never exercise the bug — the broken path is rare, region-specific, or only fires on a cache-cold request. A canary needs enough traffic × enough bake time × a representative slice to give a real signal; a green light on a thin, brief, unrepresentative sample is weak evidence, not proof. Route real (not synthetic-only) traffic, and hold long enough for the p99 tail and the rare paths to show up.
  • Trap 3 — dropping in-flight work at cutover. Killing an old instance the moment you promote severs its open connections (Lesson 26's sockets) and abandons requests mid-flight. Every safe rollout drains: stop sending new requests, let in-progress ones finish (or hand them off), close connections gracefully, then remove the instance. No graceful shutdown = a burst of user-visible errors on every otherwise-healthy deploy.
  • Trap 4 — feature flags as permanent debt. A flag is powerful because it's config you can flip live — but every long-lived flag doubles the code paths you must test (N independent flags → up to 2^N combinations), and a flag flip is itself a change with its own blast radius (a bad flip is an incident, with no deploy to point at). Treat flags as temporary: give each an owner and an expiry, and delete it once the rollout is done. A flag that outlives its rollout is untested config debt.

Where we landed

We took one live fleet — Lesson 27's 286 servers at 40,000 req/s — and traced how to ship a new version without making every user its test subject. Estimate priced the naive big-bang: a bug meets 40,000 × 300 s = 12,000,000 requests — 100% of users at once — before a ~5-minute rollback lands, while the same bug shipped as a 1% canary meets ~120,000 (100×) or ~24,000 (500×) with automated analysis, and never reaches the rest. Model laid out the space as two dials — shrink the exposed slice or shrink the time to undo: rolling (cheap, gradual, slow rollback, capacity dip), blue-green (instant flip-back, 2× transient fleet, all-at-once at the flip), canary + health-gated promotion (smallest blast radius, at the cost of metrics, bake time, and machinery), and the orthogonal feature flag that decouples deploy (code running) from release (behavior reaching users) so rollback is a millisecond config flip. Tracing a healthy ramp (1% → 5% → 25% → 100%, each stage a cheap checkpoint, drain before retiring v1) against a poisoned one (error spike at 1% → gate fires → auto-rollback, ~24,000 requests burned, 99% untouched) exposed the first bottleneck: old and new run simultaneously over one shared database that the load balancer's fast flip can't reverse. The fix isn't in the deploy tool — it's compatibility: expand the schema first, deploy code that works against both shapes, contract only after the new version has baked (Lesson 24), so every neighbor pair is backward- and forward-compatible. Four traps guard the build: coupling the migration to the deploy, a thin canary that proves nothing, dropping in-flight work instead of draining, and feature flags left to rot into test debt. The real lesson: a fast, safe release is bought by making the blast small and the undo cheap — but the undo is only as fast as your slowest-to-reverse layer, so the code can move fast precisely because the data underneath was changed slowly and compatibly. Release velocity vs blast radius, and the database is where that trade is really paid.
