Geo & Proximity: Finding the Drivers Near You Without Scanning a Million

Lesson 18 ended on a hint: a cursor's 1-D sort key names "next in a list," but proximity means "nearest in 2-D space" — and one sorted column can't answer it. This lesson takes one concrete screen: a rider taps "find a ride," and the server must return the drivers within 2 km — out of a million moving cars — in a few milliseconds. We'll estimate why the obvious answers (check every driver / index one coordinate) fall over, model the trick that saves us — turning a 2-D point into a 1-D string so nearby points share a prefix (geohash), then quadtrees and S2 cells — trace the write path (drivers pinging their location) and the read path (a rider's search), and hit the wall every gridded map hits: a stadium empties and one cell holds 50,000 cars. The trade-off underneath: a simple uniform grid vs load that follows where people actually are.

The one screen we'll design

A rider stands on a corner and opens the app. The server knows the live location of every active driver — a million cars, each moving, each reporting where it is every few seconds. The rider's phone sends one point (its own latitude and longitude) and asks: which drivers are within 2 km of me, nearest first? The answer must come back before the map finishes its little loading spin — call it under ~50 ms. The whole tension is on one screen: a point, a radius, and a haystack of a million moving needles.

Proximity is a 2-D question, and a 2-D question does not collapse into one sorted column. That single fact is why "find nearby" needs its own machinery — everything below earns that machinery with numbers.

Words we'll earn before we lean on them

  • Latitude / longitude — the two numbers that name a point on Earth: latitude is north–south (−90°…+90°), longitude east–west (−180°…+180°). A location is the pair.
  • Proximity / radius query — "give me everything within distance r of point P." The core operation of this lesson.
  • Great-circle distance (haversine) — the true distance between two lat/lng points across the curved Earth. It's exact but costs real arithmetic, so we only want to run it on a short list.
  • Spatial index — a data structure that answers "what's near here?" without scanning everything, the 2-D cousin of Lesson 12's B-tree.
  • Cell — a small square patch of the map that we treat as one bucket. Every point falls in exactly one cell.
  • Geohash — a scheme that turns a lat/lng point into a short string, built so that nearby points share a leading prefix.
  • Space-filling curve — a single 1-D line threaded through 2-D space so that "close on the line" usually means "close on the map." Geohash uses a Z-order curve; S2 uses a Hilbert curve.
  • Quadtree — a tree that recursively splits a region into 4 quadrants, but only where it's crowded, so cell size follows density.
  • S2 cell — Google's scheme: it wraps the sphere onto a cube and threads a Hilbert curve through each face, giving each cell a 64-bit id with better shape and locality than a geohash.
  • Hot cell — one cell holding wildly more points than the rest (a stadium, an airport). This lesson's final bottleneck, and the same hotspot from L03/L08/L09 wearing a map.

Move 1 — Estimate: why the two obvious designs fall over

Before reaching for a clever structure, price the two things a beginner would try first, so the cleverness is earned.

Worked: the load, and design #1 — check every driver.

• Active drivers: 1,000,000. Each pings its location every 4 s → 1,000,000 / 4 = 250,000 location writes/sec.
• Rider searches: say 50,000/sec at peak.
• Naïve read: for one search, compute the distance from the rider to every driver and keep those under 2 km. That's 1,000,000 haversine calculations per search.
• Across all searches: 1,000,000 × 50,000 = 5 × 10¹⁰ distance calculations per second.

Fifty billion trig calls a second is not a tuning problem; it's the wrong shape. A single search touching all million cars is O(N) when we need something closer to O(handful).

Design #2 — index one coordinate (and why 2-D won't fold into 1-D). We know B-trees (Lesson 12) make range queries fast, so index latitude. A 2 km search means latitude within about 2 / 111 ≈ 0.018° (one degree of latitude ≈ 111 km). The index instantly returns everyone in the band lat ∈ [me − 0.018°, me + 0.018°].

But that band is a strip 4 km tall that wraps the entire planet — ~40,000 km around. Every driver at your latitude, in any city on Earth, is a candidate. You then have to filter that huge set by longitude one row at a time. Indexing longitude instead has the same disease in the other direction. Two separate 1-D indexes cannot be intersected cheaply into one 2-D box — the database can use only one of them, and the other coordinate becomes a linear filter.

Name the first trade-off — dimensionality. A B-tree is a line; a map is a plane. The whole job of a spatial index is to reduce 2 dimensions to 1 in a way that keeps near-in-2-D mostly near-in-1-D, so that a single ordinary index (the tool we already have) can answer a proximity query. That reduction is a space-filling curve, and geohash is the simplest one.

Move 2 — Model: turn a point into a prefix (geohash), then quadtree & S2

The idea is to chop the world into a grid of cells and give each cell a name, chosen so that adjacent cells have similar names. Then "near me" becomes "same or neighbouring cell name" — a string prefix query on the index we already know how to build.

Model A — geohash: interleave the bits

Geohash builds the cell name by repeatedly halving the world. Ask of the longitude: is it in the left half or the right half? That's one bit. Ask the same of latitude: top or bottom half? Another bit. Keep alternating, each answer halving the remaining box, and interleave the two streams of bits. Group the bits 5 at a time and map each group to one character (base-32). More characters = more halvings = a smaller, more precise cell.

  2-D POINT  ->  1-D STRING        (why nearby points share a prefix)

  point:  lng = -122.4   lat = 37.8

  longitude, halving [-180,180]:      latitude, halving [-90,90]:
    -122.4 < 0     -> 0                 37.8 > 0     -> 1
    -122.4 < -90   -> 0                 37.8 < 45    -> 0
    -122.4 > -135  -> 1                 37.8 > 22.5  -> 1
    -122.4 < -112.5-> 0                 37.8 > 33.75 -> 1
    -122.4 > -123.7-> 1                 37.8 < 39.37 -> 0
     lng bits: 0 0 1 0 1                 lat bits: 1 0 1 1 0

  interleave  lng,lat,lng,lat,... :
       0 1 0 0 1 1 0 1 1 0
       └──5 bits──┘└─5 bits─┘
         01001        10110
        = 9 (idx 9)  = 22 (idx 22 = 'q')      ->  geohash "9q..."

  Two points in the same 5-char cell agree on the first 25 bits,
  so they share the first 5 characters. A plain B-tree string
  prefix range (L12) now answers a 2-D "who is near here?"

Worked: reading that base-32 step. The base-32 alphabet is 0123456789bcdefghjkmnpqrstuvwxyz (the letters a i l o are dropped so nothing looks like a digit). The first five interleaved bits are 01001 = 8+1 = 9 → the character at index 9 is '9'. The next five, 10110 = 16+4+2 = 22 → index 22 is 'q'. So the point encodes to a geohash beginning 9q…, and any other point in that same box shares that prefix. Precision by length, in the real world:

Geohash lengthCell size (≈)Good for
4 chars39 km × 20 kma metro region
5 chars4.9 km × 4.9 kma 2 km search ✔

For a 2 km radius we pick 5 characters (~4.9 km cells): big enough that the search circle fits within a small patch of cells, small enough that each cell holds few drivers.

Now the read is trivial to state: the rider's point encodes to, say, 9q8yy, and we ask the index WHERE geohash LIKE '9q8yy%' — a prefix range, exactly the B-tree seek from Lesson 12. That returns the drivers in one ~5 km cell instead of a million. But it has a bug, and it's the one in the opening diagram.

The cell-boundary problem — and the 3×3 fix

The rider sits near the top edge of cell 9q8yy. A driver 100 m away, just across that edge, is in cell 9q8yv — a different prefix. Querying only 9q8yy% misses a car that is almost close enough to touch. Worse, the 2 km circle physically spills into as many as 4 neighbouring cells at a corner. "Same cell" is not the same as "within radius": cells have hard edges, distance does not.

The fix: compute the rider's cell and its 8 neighbours (the 3×3 box of cell names), query all 9 prefixes, gather the candidates, then run the exact haversine distance on that short list and keep only the ones truly within 2 km. With 5-char (~5 km) cells, a 3×3 box covers ~15 km × 15 km — comfortably larger than the 2 km circle, so no nearby driver can hide.

Worked: how much this saved. Put 1,000,000 drivers across a big metro of ~500 km × 500 km. At ~24 km² per 5-char cell that's 250,000 / 24 ≈ 10,400 cells, so 1,000,000 / 10,400 ≈ 96 drivers per cell on average. The 9-cell query gathers 9 × 96 ≈ 865 candidates; we run exact haversine on those ~900 and return the survivors.

1,000,000 candidates → ~900 is a 1,000,000 / 900 ≈ 1,100× cut in the per-search work — and that's what turns "scan the planet" into "a few milliseconds." The exact-distance step still runs, but on 900 rows, not a million.

Name the trade-off — cell size is recall vs work. Bigger cells → the 3×3 box covers more ground, so you're sure to catch every nearby driver (high recall), but each cell holds more candidates to distance-filter (more work). Smaller cells → fewer candidates per cell, but the 2 km circle now spans many cells, so you must query a larger neighbourhood (a 5×5 or 7×7 box). You tune cell size to the search radius: roughly, pick cells about the size of the radius so a 3×3 box always contains the circle.

Model B — quadtree: let cell size follow the crowd

Geohash lays down a uniform grid: every 5-char cell is the same size, whether it covers a packed downtown or empty ocean. A quadtree instead starts with one big square and splits a square into 4 smaller squares only when it holds too many points. A dense city centre keeps subdividing into tiny cells; the countryside stays one big cell. The result: every leaf cell holds roughly the same number of points, not the same area.

Name the trade-off — statelessness vs adaptivity. A geohash is stateless: you compute a point's cell from its coordinates alone, with no shared structure to consult, which makes it trivial to shard and to store in a plain database index. A quadtree adapts to density so no single leaf gets overloaded — but it's a mutable tree that must be built, balanced, and kept in memory, and it's harder to split across machines. You trade the simplicity of a fixed grid for load that follows where people actually are.

Model C — S2: a better curve on a cube

Geohash has two rough edges. Its cells distort the further you get from the equator (a degree of longitude shrinks toward the poles), and its Z-order curve occasionally jumps — two cells adjacent on the map can be far apart in the string ordering, which is the boundary problem in another guise. S2 fixes both: it projects the sphere onto the 6 faces of a cube (keeping cells close to equal-area) and threads a Hilbert curve through each face. A Hilbert curve never jumps — consecutive cells along it are always physically adjacent — so a nearby region maps to a small number of contiguous id-ranges, and each cell is a compact 64-bit integer.

Name the trade-off — simplicity vs quality of locality. Geohash is a few lines of bit-twiddling and stores as a plain string; S2 needs a real library, but its cells are more uniform and its Hilbert ordering keeps "near on the map" and "near in the index" tighter, so region queries touch fewer, cleaner ranges. Reach for geohash when simple is enough; reach for S2/quadtree when uniformity and locality start to bite.

Move 3 — Trace the two paths

Two flows meet at the spatial index: drivers writing their positions, and riders reading nearby drivers.

  WRITE PATH  (a driver moves)                READ PATH  (a rider searches)

  driver GPS every 4 s                         rider point P, radius 2 km
        │  (lat, lng)                                │
        ▼                                            ▼
  encode -> geohash5  e.g. "9q8yy"             encode P -> "9q8yy"
        │                                            │
        ▼                                            ▼
  update index:                                compute 3x3 neighbour cells:
    driver_id -> "9q8yy"                         9q8yv 9q8yy 9q8yz
    (or: cell "9q8yy" -> {set of drivers})       9q8yt 9q8y? 9q8y?  ...
        │                                            │
        ▼                                            ▼
  250,000 writes/sec, each a small             fetch drivers in those 9 cells
  key update (cheap, O(1))                      -> ~900 candidates
                                                     │
                                                     ▼
                                              exact haversine <= 2 km,
                                              sort by distance, take top N

Write path. Each ping recomputes the driver's geohash and updates one small entry — either "driver → cell" (and a per-cell index) or the cell's set of drivers. It's an O(1) key update, so 250,000/sec is comfortable; positions are hot and short-lived, so this usually lives in memory (a Redis-style store), not on spinning disk. Read path. Encode the rider, expand to the 3×3 (or 5×5) neighbourhood, gather ~900 candidates, run exact distance, sort, return the nearest N. Every expensive step (the haversine, the sort) runs on the short candidate list, never the million.

Name the trade-off — precompute the cell vs compute distance at read. We do the cheap, coarse filter (which cell?) at write time and on the index, and pay for the exact, expensive filter (haversine, ranking) at read time on a tiny set. It's the same "narrow cheap, then refine expensive" funnel as L12's covering index, L14's CDN, and L16's two-phase ranking — the grid narrows a million to ~900, exact distance perfects those 900.

Move 4 — Find the first bottleneck: the hot cell

A concert ends. Thirty thousand people open the app in the same two minutes, standing in the same few blocks — one cell. Meanwhile a rural cell holds 3 drivers. The uniform grid gave every cell the same area, but people are not spread by area, so it gave them wildly different load.

Worked: the stadium cell. Suppose that one 5-char cell now holds 50,000 drivers and riders instead of the ~96 average. Every search there is served from that single cell's entry — a read hotspot ~500× the normal cell — and the "short" candidate list is now 50,000 long, so the exact-distance step is back to being expensive for everyone in that cell. A cell is a shard, and a hot cell is a hot shard — the very same wall as L03's hot partition key, L08's hot rate-limit key, and L09's hot queue partition, now drawn on a map.

Three fixes, each a familiar trade:

  • Adaptive precision. Use finer cells where it's dense — a 7-char (~150 m) cell downtown, a 4-char (~30 km) cell in the countryside — so each cell holds a bounded number of points. This is exactly what a quadtree does automatically, and why S2 lets a region mix cell levels. Trade: uniform-and-simple vs balanced-and-stateful (Model B's trade, now forced on us).
  • Cap and sample. A rider doesn't need all 50,000 nearby cars, just the closest handful. Keep or return only the nearest few hundred and stop. Trade: exactness vs work — the L06/L08 "approximate to stay scalable" move.
  • Replicate the hot cell for reads. If the pain is read throughput on one cell's entry, copy that entry across replicas so reads spread out (L02/L06). Trade: read scale vs the staleness/consistency of the extra copies.

Name the last trade-off — uniform grid vs load-following structure. The uniform geohash grid is simple, stateless, and shards trivially, but it distributes space evenly while the world distributes people unevenly, so it manufactures hot cells wherever crowds gather. Making cell size follow density (quadtree / mixed-level S2) removes the hotspot but buys a mutable, harder-to-distribute structure. There is no grid that is both perfectly uniform to operate and perfectly balanced under a crowd — you choose which one the crowd is allowed to break.

Where we landed

We designed one screen — "find drivers within 2 km" — and made every choice pay for itself. Estimate killed the two obvious designs: checking every driver is 1,000,000 × 50,000 = 5 × 10¹⁰ distance calls/sec, and indexing one coordinate returns a 4 km strip that wraps the planet, because two 1-D indexes don't intersect into a 2-D box. Model fixed it by folding 2-D into 1-D: geohash interleaves the bits of lat and lng (our point → 01001 10110 → 9q…) so nearby points share a prefix and a plain B-tree prefix range answers "who's near here?" — with the boundary problem (a car 100 m away in a different cell) fixed by querying the 3×3 neighbourhood and running exact haversine on the ~900 candidates, a 1,100× cut. Quadtree makes cell size follow density (adaptive but stateful); S2 puts a Hilbert curve on a cube for better locality and shape. Tracing the write path (250k cheap O(1) cell updates/sec) and read path (encode → 3×3 → candidates → exact distance → top N) showed the coarse-then-exact funnel again. The next bottleneck was the hot cell: a stadium jams 50,000 into one cell — a hot shard, the L03/L08/L09 wall on a map — fixed by adaptive precision, capping, or replication. The thread: a proximity system is a curve that threads 2-D space into 1-D so an ordinary index can find "near"; you keep near-in-space near-in-index, query a neighbourhood not a single cell, refine with exact distance, and bend the grid where crowds gather.
