Vector Databases & Semantic Search: Finding Things by Meaning

Lesson 16 built a keyword search engine: an inverted index that maps the word "shoes" to every document containing the literal token "shoes." It is fast and exact — and it is blind to meaning. Type "comfortable footwear for marathon training" and it will miss a product titled "cushioned long-distance running sneakers," because the two share almost no words. This lesson builds the engine that can match them: a semantic search over a 10-million-product catalog that finds items by what they mean, not which tokens they happen to contain. The trick is to turn every product and every query into a point in a high-dimensional space where closeness = similarity of meaning, then answer "find things like this" as "find the nearest points." We'll estimate the index and discover that the honest, exact answer costs about a second per query; model the embedding, the distance metric, why ordinary tree indexes collapse in high dimensions, and the two approximate-nearest-neighbor families (HNSW and IVF) that rescue us; trace a query end to end, a graph walk that visits 2,000 of 10 million vectors, and the recall knob being turned; and find the first bottleneck, which is not storage or throughput but the three-way tension between recall, latency, and memory — and the day someone upgrades the embedding model and the whole index must be rebuilt. The trade under every knob: recall & quality vs query latency & index cost.

The one system we'll build

A semantic product search. We have the 10-million-item catalog from Lesson 48. A shopper types a phrase — "comfortable shoes for marathon training" — and we must return the ten products whose meaning is closest, even when they share no keywords with the query. The keyword engine of Lesson 16 can't do this: its inverted index matches tokens, so "marathon" finds only documents literally containing "marathon," and a great result titled "cushioned long-distance running sneaker" is invisible. We want an engine that understands "marathon training" and "long-distance running" are the same idea. That single requirement — match by meaning, not by shared words — is the seed of the whole design, and it forces a completely different data structure from the inverted index: instead of "which documents contain this word," we ask "which points are nearest this point."

A vector database answers a different question than every database before it in this course. Lesson 12's B-tree answers "find the row where id = 8842" — an exact match on a value. Lesson 16's inverted index answers "find documents containing this word" — an exact match on a token. A vector index answers "find the items most similar to this one" — a nearest-neighbor query with no exact key at all. That shift, from lookup-by-equality to search-by-proximity, is why none of our earlier indexes work here and why we need a new machine.

Words we'll earn before we lean on them

  • Embedding — a fixed-length list of numbers (a vector) that a machine-learning model produces from a piece of content (text, image, audio). The model is trained so that similar meanings produce nearby vectors. "running shoes" and "sneakers for jogging" land close together; "running shoes" and "kitchen blender" land far apart.
  • Dimension — how many numbers are in each vector. Common sizes are 384, 768, or 1536. Our catalog uses 768 dimensions. Each number is a coordinate; a vector is one point in 768-dimensional space.
  • Distance / similarity metric — the rule for "how close are two vectors." Cosine similarity measures the angle between them (are they pointing the same way?); Euclidean distance measures straight-line gap. Smaller distance = more similar. We'll use cosine, the usual choice for text embeddings.
  • Nearest-neighbor search (kNN) — given a query point, return the k catalog points closest to it. "Find 10 products like this" is a k=10 nearest-neighbor query.
  • Exact vs approximate (ANN) — exact kNN compares the query to every vector and is always right but slow. Approximate nearest-neighbor (ANN) visits only a clever subset and returns almost the true nearest, far faster. Vector databases are ANN engines.
  • Recall — the quality measure for ANN: of the true top-k nearest neighbors, what fraction did we actually return? Recall@10 = 0.97 means we returned, on average, 9.7 of the true 10. It is the dial we trade against speed.
  • HNSW / IVF — the two dominant ANN index structures. HNSW is a navigable graph you walk toward the query. IVF clusters the vectors and searches only the nearest clusters. We'll build both and name their trade.
  • Quantization — compressing each vector (e.g. 3,072 bytes → 96 bytes) so the index fits in less memory, at some cost to recall. Product quantization (PQ) is the common scheme.

Move 1 — Estimate: the index, and why the exact answer is hopeless

Two numbers decide the shape of everything: how big is the index, and what does the honest (exact) query cost? The second number is the shock that forces approximation.

PieceValueWhere it comes from

Exact query latency~1 s30.72 GB ÷ 30 GB/s → ~1 QPS/box
Targetp99 < 20 ms, thousands QPSa search box a human waits on

The number that forces the whole design: the exact answer reads the entire 30 GB index on every query. Nearest-neighbor has no key to look up — to be sure you found the closest point, you must measure the distance to every point. That's 10 million dot products of 768 numbers each per query, and the real cost isn't the arithmetic — it's that you must stream all 30 GB of vectors through the CPU. At ~30 GB/s memory bandwidth that's 30.72 ÷ 30 ≈ 1.02 s per query, so one query saturates one machine for a second — about 1 query per second per box. Our target is thousands of queries per second at 20 ms each. The gap is roughly a thousandfold in latency and a thousandfold in throughput at once. No amount of sharding closes a 1,000× per-query cost cheaply; we have to stop looking at almost all the vectors.

Why can't we just index it like Lesson 12? A B-tree makes id = 8842 fast by sorting on one dimension and bisecting. A vector has 768 dimensions and no single one to sort by. You might think "build a tree that splits space" (a k-d tree) — and in 2 or 3 dimensions that works. But in high dimensions it collapses, for a reason worth naming: the curse of dimensionality. As dimensions grow, points spread out until almost every pair is roughly the same distance apart — the gap between the nearest and farthest point shrinks toward nothing. A space-splitting tree prunes by saying "everything on the far side of this split is too far to matter," but when far and near are nearly equal, no branch can be pruned, and the tree ends up visiting almost every point anyway. Past ~10–20 dimensions, exact tree indexes degrade to brute force. That is why nearest-neighbor at 768 dimensions is a genuinely different problem — and why the answer is to give up on exact and search approximately.

Move 2 — Model: meaning as geometry, and two ways to search it fast

The embedding: how meaning becomes distance

An embedding model is a trained function from content to a vector. You feed it "cushioned long-distance running sneaker" and it returns 768 numbers; you feed it "comfortable shoes for marathon training" and it returns 768 different numbers — but because the model was trained so that similar meanings map to nearby points, those two vectors point in almost the same direction, while "stainless steel blender" points somewhere else entirely. Similarity is measured by cosine: the cosine of the angle between two vectors, ranging from 1 (identical direction) to 0 (unrelated) to -1 (opposite). The magic is entirely in the model's training; our job as system designers starts after the vectors exist — store 10M of them and answer "nearest to q" in milliseconds. One rule we must never break: the query must be embedded by the exact same model that embedded the catalog, or the two live in incompatible coordinate systems and "nearness" is meaningless.

The escape from brute force: don't visit almost all the vectors

Every ANN index is one idea in two disguises: organize the 30 GB so a query can reach the neighborhood of the answer while touching a tiny fraction of the points. Two structures dominate.

HNSW — a navigable graph you walk toward the query. HNSW (Hierarchical Navigable Small World) builds a graph where each vector is a node linked to a few dozen of its nearest neighbors, plus a few long-range links, arranged in layers like a skip-list (Lesson 12): sparse express lanes on top, dense local roads at the bottom. To search, you start at an entry node and greedily hop to whichever neighbor is closer to q, dropping down layers as you home in, until no neighbor is closer — you've arrived. Because the graph is "small-world" (any point is a few hops from any other), a query reaches the answer's neighborhood in about log(N) hops — log₂(10M) ≈ 23 — visiting on the order of a couple thousand vectors instead of 10 million. A tunable knob, efSearch, controls how wide a frontier you keep as you walk: bigger = more candidates examined = higher recall and higher latency.

  HNSW greedy walk (one layer shown). Start far, hop closer, stop
  when no neighbor beats where you stand.

    entry --> n1 (closer) --> n2 (closer) --> n3 (closer) --> ANSWER

                   that are       measures        answer is closer to q
                   farther)       distance to q)  -> stop, return top-K

    Visited ~2,000 nodes of 10,000,000  = 0.02% of the catalog.
    ~23 hops (log2 of 10M) to cross the graph, times the frontier
    width efSearch. Read ~2,000 x 3 KB = ~6 MB, not 30 GB
    -> ~5,000x less data moved -> single-digit milliseconds.

The price of HNSW is memory and update cost. On top of the 30 GB of vectors it stores the graph — a few dozen neighbor links per node — which typically adds 15–30% more memory (a few GB of link ids). And inserting or deleting a vector means editing the graph's links, which is far more expensive than appending a row; high-churn catalogs pay for that (we'll hit it as the bottleneck).

IVF — cluster the space, search only the nearest clusters. IVF (Inverted File) borrows Lesson 16's idea. First, offline, run k-means to group the 10M vectors into nlist clusters — a good rule of thumb is √N ≈ √10,000,000 ≈ 3,162 clusters, each holding 10M / 3,162 ≈ 3,163 vectors, each cluster represented by its centroid (average point). To search, compare q to the 3,162 centroids (cheap), pick the nearest nprobe clusters, and search only those exhaustively. With nprobe = 16 you scan 16 × 3,163 ≈ 50,600 vectors — 0.5% of the catalog — reading ~150 MB instead of 30 GB. nprobe is IVF's recall knob: probe more clusters → catch more true neighbors that fell just over a cluster boundary → higher recall, higher latency.

Quantization — shrink each vector so the index fits. 30 GB fits in RAM on a big box, but replicate it across a fleet (Lesson 2/48) and memory becomes the bill. Product quantization (PQ) chops each 768-dim vector into, say, 96 short sub-vectors and replaces each with a 1-byte code from a learned codebook — turning a 3,072 B vector into 96 B, a 32× compression: 30 GB → under 1 GB. Distances are then computed on the compact codes. The cost is recall — the codes are lossy, so the neighbors come back slightly wrong. The standard fix is a two-stage search: use the tiny quantized index to fetch, say, the top 200 candidates fast, then re-rank those 200 with their full-precision vectors. You pay compression's recall loss only on the coarse pass and recover accuracy on a cheap re-score. That is the memory-vs-recall dial.

Neither engine alone is enough: hybrid keyword + vector

Vector search understands meaning but is bad at exactness. Search for the SKU "AJ1-2024" or the brand "Salomon" and the embedding may drift to "similar sneakers," burying the exact item. Keyword search (Lesson 16) is the mirror image: perfect on exact tokens, blind to synonyms. So production search runs both and fuses the results. A common fuser is reciprocal rank fusion: score each result by 1/(rank + k) in each list and add — an item ranked high by either engine floats up, without having to calibrate two different score scales. Keyword catches the exact brand and model number; vector catches "marathon" ≈ "long-distance running"; the fusion catches both. Naming the trade: hybrid buys quality across query types at the cost of running and maintaining two indexes.

The model in one line: embed every product with one model into a 768-dim vector; store the 10M vectors in an ANN index — a navigable HNSW graph you walk toward the query, or an IVF cluster-and-probe — so a query touches a fraction of a percent of the vectors; optionally quantize to fit memory and re-rank the survivors at full precision; and fuse with a keyword index so exact tokens and semantic meaning both win.

Move 3 — Trace the paths

Three scenarios: a query flowing end to end, the HNSW graph walk up close, and the recall knob being turned so you can see recall and latency move together.

Path A shows the payoff and the shape of a real query: the winning result shared no words with the query and was found purely by meaning — exactly what the keyword engine could never do — in 17 ms instead of a second. Path B makes the ANN bargain concrete: HNSW returned 97% of the true answer while reading 6 MB instead of 30 GB, a five-thousandfold cut in data moved for a 3% quality loss no shopper would notice. Path C is the one to remember: recall and latency are the same knob viewed from two ends, and the curve bends viciously near the top — buying the last few percent of recall drags you back toward the 1-second brute-force scan. That curve is the lesson's trade, drawn as a graph.

Move 4 — Find the first bottleneck: the recall–latency–memory triangle, and the day the model changes

Storage isn't the wall (30 GB is small), and neither is throughput once ANN cuts each query 1,000×. The wall is that ANN is only cheap because it is approximate — and the three things you want (high recall, low latency, low memory) pull against each other so that improving any one costs you another.

The bottleneck — you can pick any two of {recall, latency, memory}, and the third pays. Want higher recall? Turn efSearch/nprobe up → visit more vectors → higher latency (Path C). Want lower latency at the same recall? Keep more of the index in fast memory and use a richer graph → more memory. Want lower memory? Quantize → recall drops, or add a re-rank stage → more latency. There is no setting that is best at all three; every deployment picks a point on this triangle and names what it gave up. This is the concrete face of the whole lesson's trade: recall & quality vs query latency & index cost. The dangerous move is chasing 99.9% recall because "missing results looks broken" — that pushes you up the vicious end of Path C's curve, toward brute-force cost, for neighbors a human would never notice were missing. Decide the recall you actually need (often 95–98% is invisible to users) and stop.

The second wall — updates and freshness. Our earlier indexes append cheaply; an ANN graph does not. Inserting a vector into HNSW means finding its neighbors and rewiring links; deleting one means the graph now points at a tombstone that still costs a hop. A catalog with heavy churn — prices, new products, deletions — slowly degrades an HNSW index's recall and speed as tombstones accumulate and links go stale. The usual answer is the same as Lesson 12's B-tree fragmentation and Lesson 47's LSM compaction: don't mutate forever — periodically rebuild. Serve reads from the current index while building a fresh one offline from the latest catalog, then swap atomically (Lesson 31's blue-green, Lesson 24/57's shadow-build-then-cutover). Fresh writes land in a small, cheap "delta" index searched alongside the big one until the next rebuild folds them in — the same hot-delta-plus-cold-base shape as an LSM memtable.

The third wall — reindexing when the embedding model changes, and it will. Here is the cost unique to vector systems, and the one teams underestimate. An embedding is only meaningful relative to the model that produced it. Upgrade from model v1 to a better v2 and every existing vector is now written in a language the new query vectors don't speak — v1 and v2 coordinates are not comparable, and you cannot mix them in one index. A model upgrade is therefore not a config change; it is a full re-embedding of all 10M products and a full index rebuild — run every product back through the new model (a large batch/backfill job, Lesson 57), build a brand-new index, and cut over atomically, embedding queries with v2 only after the switch. During the migration you either run both indexes in parallel (double the memory) or accept a maintenance window. Plan for this from day one: version your vectors by model, keep the raw text so you can always re-embed, and treat "which model version is this index?" as a first-class piece of metadata (Lesson 24's schema-version discipline, applied to vectors).

So the honest design for our semantic search is: embed all 10M products with one versioned model into 768-dim vectors; store them in an HNSW index (choose HNSW over IVF when you want the lowest latency at a given recall and can afford the graph memory; choose IVF when memory is tight and build/update cost matters more); pick a recall target you can actually justify — ~97%, high on Path C but before the vicious tail — and set efSearch to hit it; quantize with PQ plus a full-precision re-rank if the index must fit a smaller memory budget; run a keyword index alongside and fuse so exact brands/SKUs and semantic meaning both win; absorb writes in a small delta index and rebuild-and-swap periodically so churn can't rot the graph; and treat an embedding-model upgrade as a planned full re-embed and rebuild, never an in-place change. Every choice names its price: ANN buys 1,000× speed at the cost of ~3% recall; a higher recall target buys quality at the cost of latency; quantization buys memory at the cost of recall (bought back by a re-rank); hybrid buys robustness at the cost of a second index; and the whole thing buys "search by meaning" at the cost of an index that must be rebuilt whenever the meaning-maker changes.

The deepest point: a vector database is the first index in this course that answers "what is similar?" instead of "what is equal?" — and similarity in high dimensions is expensive to compute exactly, so the entire discipline is the art of being approximately right cheaply. Embeddings turn meaning into geometry; ANN indexes turn "compare to everything" into "walk to the neighborhood"; recall is the dial that says how approximate you're willing to be; and the model version is the hidden coordinate system that, when it changes, invalidates everything at once. Get those four right and "find things like this one" stops being magic and becomes a point you choose on a triangle you can see. The four traps

  • Trap 1 — expecting an exact index (B-tree / k-d tree) to do nearest-neighbor. At 768 dimensions the curse of dimensionality makes near and far nearly equal, so space-splitting trees prune nothing and degrade to brute force. Use an approximate (ANN) index built for high dimensions.
  • Trap 2 — chasing 99.9% recall. Path C's curve bends viciously near the top: the last few percent of recall costs most of the latency and drags you back toward the 1-second exact scan, for neighbors no user would miss. Pick the recall you actually need (often 95–98%) and stop.
  • Trap 3 — embedding the query with a different model (or version) than the index. Vectors from two models live in incompatible coordinate systems; "nearness" between them is noise. The query model must exactly match the index model, and a model upgrade means re-embedding everything.
  • Trap 4 — relying on vector search alone for exact tokens. Brands, SKUs, model numbers, and rare terms embed poorly and get buried under "similar" items. Run a keyword index (Lesson 16) alongside and fuse the results so exactness and meaning both survive.

Where we landed

We built a semantic search over a 10-million-product catalog — one that finds "cushioned long-distance running sneaker" for the query "comfortable shoes for marathon training" though they share no words, the thing Lesson 16's keyword index could never do. Estimate exposed the shock: nearest-neighbor has no key, so the exact answer reads the whole ~30 GB index every query — ~1 s, ~1 QPS/box — a thousandfold short of the target, which is why we must approximate.
