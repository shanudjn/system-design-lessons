Feature Stores & ML Serving: Feeding a Model the Same Numbers It Trained On

Lesson 52's moderation funnel leaned on a classifier; Lesson 16's search leaned on a ranker; recommenders, fraud scorers, and churn predictors all lean on the same thing. A model is a function, and a function is only as good as its inputs. Those inputs are features — computed signals about a user, an item, a merchant: "how many times did this card pay in the last minute," "what's this user's average order over 30 days." The model itself is the glamorous part; the unglamorous part that decides whether it works in production is getting the right feature values to it, fast enough, and computed the exact same way they were in training. Get the plumbing wrong and the model that scored 99% in the lab quietly performs like a coin flip on real traffic — with no error in the code and no alert firing. We'll take one concrete model call — a fraud scorer deciding whether to approve a payment in ~50 ms — and estimate why you can't just compute features when the request arrives. We'll model the feature store: an online store for serving, an offline store for training, and one shared definition that keeps them honest. We'll trace a serving read, a feature update (batch vs streaming), and the training-set build. And we'll hit the wall the whole thing stands on: the number the model trained on and the number it's served must be identical, and three separate leaks pull them apart. The trade underneath: feature freshness vs serving latency & training-serving consistency.

The one system we'll design

A payments company runs a fraud model. Every time a card is charged, the model must score the transaction — fraud or legit — and return a decision fast enough to approve or decline before the customer is left waiting: a budget of about 50 ms end to end. The model doesn't look at the raw transaction alone; a single "$80 at a coffee shop" tells you almost nothing. It looks at features — precomputed signals that put this charge in context:

  • card_txn_count_1m — how many charges this card made in the last minute (a stolen card being tested fires dozens in seconds).
  • user_avg_amount_30d — the cardholder's average charge over 30 days (is $80 normal for them, or 40× their usual?).
  • merchant_fraud_rate_7d — how often charges at this merchant turned out fraudulent last week.
  • amount_vs_user_avg — this charge divided by the 30-day average. ...and ~200 more.

So the real question of this lesson is not "is the model good?" — assume it is. It's "how do we hand this model ~200 correct, current feature values in a few milliseconds, ten thousand times a second, computed the same way they were when the model learned from them?" That plumbing is the feature store, and it is where most real ML systems live or die.

A feature store is the system that computes named signals (features) once from a shared definition, keeps their full history in an offline store for building training sets and their latest value in a fast online store for serving, so a model is fed the same values at serving time that it learned from at training time — with a chosen freshness for each feature. It is not a database you query at request time. It's a precomputation pipeline plus two stores shaped for two jobs, held together by one definition whose entire purpose is to stop the training numbers and the serving numbers from drifting apart.

Words we'll earn before we lean on them

  • Feature — a named, computed number describing an entity, fed to a model as input (e.g. card_txn_count_1m).
  • Entity — the thing a feature is about, identified by a key: a user_id, merchant_id, card_id. Features are looked up by entity key.
  • Feature definition — the single piece of transformation code that computes a feature from raw data. The anti-drift mechanism: both paths run the same one.
  • Online store — a low-latency key-value store (Lesson 2/48's cache shape) holding only the latest value of each feature per entity. Read at serving time.
  • Offline store — a big columnar warehouse (Lesson 29) holding the full history of every feature value over time. Read to build training sets.
  • Serving / inference — running the model on a live request to get a score, under a tight latency budget.
  • Training — building the model from historical examples, each a set of feature values plus a known label (was it actually fraud?).
  • Label — the known-correct answer for a past example, used to train. For fraud it arrives late (a chargeback lands weeks after the charge).
  • Train-serve skew — when a feature is computed differently in training than in serving, so the model is fed one distribution in the lab and another in production. Silent accuracy loss.
  • Point-in-time correctness — building each training row from feature values as they were at that past moment, never as they are now — so training can't peek at the future (leakage).
  • Leakage — a training feature that secretly contains information from after the moment being predicted, making the model look great offline and fail in production.
  • Batch vs streaming — two ways to compute a feature: a periodic job over history (batch, Lesson 29) vs an incremental update off the live event stream (streaming, Lesson 29's kappa).
  • Freshness — how up-to-date a feature's serving value is: the lag between the event that should change it and the online store reflecting it.

Move 1 — Estimate: you can't compute features at request time, so you precompute and look them up

Two numbers rule the design: how much work "just compute the features when the charge arrives" would be, and how small the precomputed answers are once you stop recomputing them.

1. Why request-time computation is off the table — twice over. Peak load is 10,000 transactions/s, and each needs ~200 features. Suppose you compute each feature the honest way at request time — card_txn_count_1m is a COUNT(*) over the transactions table (Lesson 12), user_avg_amount_30d an AVG over 30 days, and so on. That's 10,000 × 200 = 2,000,000 aggregation queries per second against your OLTP database. A database that safely serves ~5,000 heavy queries/s (Lesson 27's knee, Lesson 48) is 2,000,000 ÷ 5,000 = 400× underwater — it melts, and takes checkout down with it. And even for one request, running 200 aggregations — say 5 ms each — is 200 × 5 ms = 1,000 ms, twenty times over the 50 ms budget. Request-time computation fails on throughput and on latency at the same time; there is no faster database that fixes a 400× and a 20× wall together. The work must be done ahead of the request.

2. What the precomputed answers cost to hold. Flip it around: compute each feature once, ahead of time, and store just the latest value per entity. For 100M active users × 200 features × 8 bytes each: 100M × 200 × 8 B = 160 GB. That fits comfortably in a modest in-memory key-value cluster (Lesson 48), sharded by entity key (Lesson 4). Now serving is one lookup — "give me all of user X's features" — returning ~200 values in ~2 ms, not 1,000. The 400× write-side firehose is gone too: a feature is recomputed only when its inputs change, not once per read. Precompute-and-look-up converts an impossible 2,000,000 reads/s of computation into a 160 GB table and a 2 ms point read — the exact "precompute the read" move from Lesson 15, now applied to model inputs.

Name the trade-off — feature freshness vs serving latency & training-serving consistency. Precomputing buys the 2 ms lookup, but it introduces a gap: the stored value is only as current as the last time you computed it. How hard you chase that gap (a nightly batch vs a second-by-second stream) is the freshness dial, and it costs money and pipeline complexity. Meanwhile splitting the work into "compute ahead, serve later" opens the door to the deeper hazard — the ahead-of-time computation and the training-time computation must produce the same number, or the model is quietly fed inputs it never learned from. The whole rest of the lesson is those two tensions.

Move 2 — Model: one definition, two stores, and the two correctness rules that keep them honest

Three ideas make the system: a two-store split shaped for two opposite jobs, a single feature definition that feeds both, and the two rules — train-serve consistency and point-in-time correctness — that are the only reasons this is hard rather than a cache with extra steps.

1. Two stores, because serving and training want opposite things

Serving wants one entity, latest values, in 2 ms — and it never cares what a feature was last Tuesday. Training wants the full history of every feature over years, so it can reconstruct what each value was at every past moment — and it doesn't care about latency, because it runs offline over hours. These are the read patterns of two different worlds (Lesson 29 already taught that serving and analytics have opposite shapes and must not share one store). So you keep two: an online store (a low-latency KV cache, Lesson 2/48, holding only the latest value per entity — small and fast) and an offline store (a columnar warehouse, Lesson 29, holding the whole time-series of values — huge, cheap, slow). Same features, two physical shapes, because "fast latest lookup" and "complete history scan" cannot be the same storage engine.

2. One definition, or you've already lost

Here is the discipline that separates a feature store from "two teams computing similar-looking numbers." A feature is defined once — one piece of transformation code, card_txn_count_1m = count(txns for this card in the last 60 s) — and both the offline history and the online latest value are produced by that same definition. The instant training computes a feature one way (a data scientist's SQL over the warehouse) and serving computes it another way (an engineer's hand-written stream aggregation), they will disagree — different window edges, different rounding, a bug in one but not the other — and the model, trained on one, is served the other. The single definition isn't tidiness; it's the mechanism that makes the next rule even possible to keep.

3. The two correctness rules — and why they're the whole difficulty

Train-serve consistency. The feature value the model sees at serving time must be computed identically to the one it saw at training time. Break it and you get train-serve skew: the model learned that "user_avg_amount_30d = 42.10" means one thing, but serving computes 41.80 for the same state (a different rounding, a timezone slip in the window) — a small, silent shift, repeated across 200 features, that moves every input off the distribution the model was fit on. Nothing errors. The model just gets worse, and no dashboard says why.

Point-in-time correctness. To build a training row for "was the charge at time t fraud?", you must gather each feature's value as it was at t — not its value now. Miss this and you get leakage: you join the label (fraud, confirmed by a chargeback 30 days later) against today's feature values, so merchant_fraud_rate_7d "now" already includes the very fraud you're trying to predict. The model looks brilliant offline (it's peeking at the answer) and is useless in production, where the future genuinely doesn't exist yet. This is exactly why the offline store keeps history and not just the latest value — a "latest value" store literally cannot answer "what was this on day 60," so it cannot build a leak-free training set.

The two rules are why you can't just cache features and call it done. A plain cache (Lesson 48) serves the latest value fast — that solves latency, and nothing else. It has no notion of "the same way training computed it" (train-serve skew) and no notion of "as it was at a past instant" (point-in-time). A feature store is a cache plus a shared definition plus a time-versioned history — and those two additions are the entire reason the discipline exists.

Move 3 — Trace the paths

Follow the same feature through the three journeys that matter: a serving read, the two ways a feature gets updated, and the training-set build where point-in-time correctness earns its keep.

Path A — a serving read (the 50 ms hot path)

  A $80 charge arrives on card C, user U, merchant M.

   t=0     the entity keys are already on the request: card_id=C, user_id=U,
           merchant_id=M. No lookup needed to KNOW who; only to fetch features.
   t~2ms   ONE batched read to the online store: GET features for {C, U, M}
           -> ~200 latest values come back in a single round trip (~2 ms).
           NOT 200 queries; the values were precomputed, this is a KV lookup.
   t~22ms  model inference on those 200 numbers -> fraud score 0.03 -> APPROVE.
   t~25ms  decision returned, well inside the 50 ms budget.

  The online store is NEVER asked to compute anything or scan history on this path.
  It hands back numbers someone else already computed. That's the whole point of
  Move 1: the expensive work happened ahead of time, off the request's critical path.

Path B — how a feature stays current: batch vs streaming, chosen per feature

  Two features, two completely different freshness needs.

  user_avg_amount_30d  (slow-moving)
   -> a BATCH job (L29) runs every 6 h: scan the warehouse, recompute the 30-day
      average for every user, write the latest value to the online store.
   -> Is 6 h of staleness ok? A 30-day average over ~100 txns moves ~1/100 = ~1%
      per new charge. Six hours stale barely changes it. BATCH is fine, and cheap.

  card_txn_count_1m  (fast-moving -- this IS the fraud signal)
   -> a stolen card gets TESTED: 50 tiny charges in 60 seconds. This feature must
      go 0 -> 50 within a second or it's worthless.
   -> a BATCH job at midnight would report whatever it was at midnight -> the entire
      attack finishes before the feature updates -> the model is blind exactly when
      it matters. So this feature is STREAMING: a stream processor consumes the txn
      event log (L09/L33), keeps a rolling 60 s count, writes to the online store
      within ~1-2 s. Costs a streaming pipeline; buys the freshness the signal needs.

  RULE: freshness is chosen PER FEATURE. Pay for streaming only where the signal
  moves fast; use cheap batch where staleness is harmless. (L29 lambda/kappa,
  L39 tier-by-need -- the same "spend freshness where it pays" shape.)

Path C — building the training set (where point-in-time correctness is life or death)

  Goal: teach the model from history. We have labels: txns from 60 days ago,
  each now KNOWN fraud/legit (the chargebacks have settled). For each past txn at
  time t we need its feature values AS THEY WERE AT t.

  WRONG (leakage):  join each old txn to the online store's CURRENT values.
     merchant_fraud_rate_7d "now" includes fraud that happened AFTER t --
     including this txn's own chargeback. The model learns to read the answer.
     -> offline AUC 0.99 (!). In production: no better than the old rules, because
        at decision time the future values it leaned on simply don't exist.

  RIGHT (point-in-time / "as-of" join):  for each txn at t, fetch each feature's
     value from the OFFLINE history as of the last update BEFORE t.
        txn at t=day60 12:00:00  ->  merchant_fraud_rate_7d as of day60 11:59:xx
     No future information enters any row. Offline score now reflects reality.

  This is ONLY possible because the offline store kept the full time-series. A
  latest-value-only store cannot answer "what was this at day 60" -> cannot train
  honestly. History in offline, latest in online: not duplication -- two jobs.

Path A is why the system is fast: the model-serving hot path is a single 2 ms key-value read of values computed earlier, never a computation. Path B is the freshness dial made concrete — the same machinery (one definition, written to the online store) fed by two engines, batch where staleness is harmless and streaming where the signal moves faster than a batch interval. Path C is the trap that sinks more ML projects than any modeling mistake: a training set built from today's feature values silently leaks the future, producing a model that dazzles in the notebook and flatlines in production — and the only defense is a time-versioned offline store and a point-in-time join that reconstructs the past exactly. Notice that Paths B and C are two views of one thing: the offline store records the history of every value the streaming/batch pipeline ever wrote, and the training join reads that history back.

Move 4 — Find the first bottleneck: the served number and the trained number must be identical

The online store makes serving fast and the offline store makes training honest — but the model is one function stretched across both, and it only works if the number it's fed in production equals the number it learned from. Train-serve skew is the wall, and even after you share one definition it sneaks back in through the gap between the two stores. Two forces press on it, and one clean fix cuts under both.

1. The skew that survives a shared definition — the two stores drift. You did the right thing: one definition computes card_txn_count_1m. But the streaming pipeline writes it to the online store at 12:00:03, while the batch materialization lands it in the offline history at a slightly different instant, with a slightly different window edge. Now training (reading offline) and serving (reading online) see values that agree almost always — and disagree exactly at the fast-moving moments that matter most for fraud. The model is trained on the offline version and served the online version; the skew is small, silent, and concentrated where the stakes are highest. Sharing the definition removed the code divergence but not the store divergence.

2. The honest fix — log what you actually served. Stop trying to reconstruct the training features from the offline store and hope they match serving. Instead, at serving time, write down the exact feature vector the model was given (Path A's 200 values) alongside the request id. Weeks later, when the label arrives, join the label to the logged features. Now the training row contains, by construction, the literal numbers serving used — skew is impossible because there's only one number, recorded once (Lesson 13's "decide once, record it" habit, applied to features). This also fixes point-in-time correctness for free: the logged vector is the state as of the request instant, so there's nothing to reconstruct and nothing to leak. Feature logging is the strongest anti-skew technique because it makes "the value trained on" and "the value served" the same physical fact.

There are two more walls behind that one, familiar from earlier lessons. The online store is a hot dependency on every model call: at 10,000 req/s it's a shared, latency-critical KV tier, so it inherits Lesson 48's whole toolkit — shard by entity key (Lesson 4), replicate for reads, and beware the hot entity (a giant merchant's features read on every one of its transactions is a Lesson 3 hot key, coalesce it). And freshness lag is never zero: even streaming has a second or two between the event and the online store reflecting it (Lesson 6's replication lag, Lesson 26's propagation window), so a feature is always slightly behind reality — you shrink that window where the signal is fast-moving and accept it where it isn't, which is just Path B's per-feature dial seen from the other side. The deepest point stands, though: a model in production is only as good as the promise that the numbers it's scored on are the numbers it learned from — and that promise is a systems problem, not a modeling one.

The four traps

  • Trap 1 — computing features at request time. Running the aggregations when the charge arrives is 400× over the database's safe throughput and 20× over the latency budget at once. Precompute each feature ahead of time and serve it as a single key-value lookup (Lesson 15's precompute-the-read, aimed at model inputs); the request path should fetch, never compute.
  • Trap 2 — training on current feature values (leakage). Joining old labels to today's feature values lets information from after the predicted moment leak in, so the model reads the answer and scores ~0.99 offline, then flatlines in production. Keep a time-versioned offline history and build every training row with a point-in-time (as-of) join — or better, train on the features you logged at serving time.
  • Trap 3 — two code paths for one feature (train-serve skew). A data scientist's SQL and an engineer's stream aggregation for "the same" feature will disagree at the edges, silently shifting every input off the trained distribution with no error and no alert. Compute each feature from one definition, and close the residual store-to-store gap by logging and training on the actually-served values.
  • Trap 4 — one freshness for everything. Streaming every feature is expensive overkill for a 30-day average; batching every feature blinds the model to a card being tested in real time. Choose freshness per feature: streaming where the signal moves faster than a batch interval, cheap batch where staleness is harmless (Lesson 29's lambda/kappa, Lesson 39's tier-by-need).

Where we landed

A model is only as good as the numbers it's fed, and feeding them is a systems problem. Estimate killed the obvious approach: computing ~200 features per request at 10,000 req/s is 2,000,000 aggregations/s (400× a database's safe rate) and ~1,000 ms of latency (20× the 50 ms budget) — impossible on both axes — while the precomputed answers are just 160 GB served as a 2 ms lookup. Model split the work into an online store (KV cache, latest-per-entity, fast) and an offline store (warehouse, full history, for training), fed by one shared definition, and named the two rules that make it hard: train-serve consistency (serve the number you trained on) and point-in-time correctness (build each training row from values as they were then, never now). Tracing walked the 2 ms serving read, the per-feature freshness choice (batch for a 30-day average, streaming for a 1-minute count that is the fraud signal), and the training-set build where a naive join to current values leaks the future and yields a model that scores 0.99 offline and fails live. The first bottleneck is skew between the two stores: even one definition can't stop the online and offline values from drifting at the fast-moving moments that matter, and the honest fix is to log the exact feature vector served and train on it — one number, recorded once, so "trained on" and "served" are the same fact — with the online store's hot-key/latency care (Lessons 3/4/48) and an irreducible freshness lag (Lessons 6/26) sitting behind it. The model is the last mile; the feature store is the road, and a model in production is exactly as trustworthy as the promise that the numbers scoring it are the numbers it learned from. The standing tension: feature freshness vs serving latency & training-serving consistency.
