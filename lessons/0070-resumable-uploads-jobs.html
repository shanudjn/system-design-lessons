Idempotent, Resumable Data APIs: A 2 GB Upload and a Long Job Over a Flaky Network

Every lesson so far assumed the request arrives. This one drops that assumption. A customer on a train is uploading a 2 GB dashcam video from their phone, and the mobile signal comes and goes — a tunnel here, a dead spot there, a handoff between cell towers. The same customer then taps "export my order history," a job that takes the server minutes to run. Two hard shapes hide here: a huge transfer that will not survive one unbroken connection, and a mutation that takes longer than any HTTP request should wait. Do the naïve thing — one giant POST for the file, one blocking request for the job — and the file restarts from byte zero on every hiccup (it may never finish), while the job's request times out and the client, seeing an error, retries and kicks off the same export twice. We'll estimate why a single connection can't carry either one; model the two patterns that fix them — chunked, resumable upload (split, checksum, commit-last) and async job + status polling (accept fast, work in the background, poll for the result) — bound together by one idea, the idempotency key (Lesson 13/18) that makes every retry safe; trace an upload surviving a dropped connection and a job survived across a client crash; and find the first bottleneck, which is that "resumable" means the server now holds state for every in-flight upload and job — state that must be found, expired, and cleaned up. The trade under all of it: robustness on bad networks vs protocol & server-state complexity.

The one system we'll build

A phone app talks to our API over a mobile network that disconnects, on average, every ~3 minutes. Two operations must work anyway. (1) Upload: a 2 GB video (a large binary blob, Lesson 20) must reach our object store intact. (2) Long job: "export my full order history to a CSV" runs on the server for ~4 minutes and produces a downloadable file. The naïve design treats both as ordinary requests — one POST /upload with the whole file in the body, one POST /export that blocks until the CSV is ready. On a perfect network that works. On this network, both fail in ways that waste enormous work and — worse — can happen twice. The fix is two protocols that share one backbone: make big transfers resumable, make slow work asynchronous, and make every retry idempotent so a flaky network costs a resume, never a restart or a duplicate.

The one idea the whole lesson turns on: a network that drops connections turns every operation into "did that actually happen?" You cannot prevent the drop, so you design so the drop is cheap and safe. Cheap means the unit of loss is small — a chunk, not a file; a poll, not a job. Safe means repeating any step changes nothing — a re-sent chunk overwrites itself, a re-submitted job is recognized as the same job. Both fall out of two moves: break the big thing into small, independently-committable pieces the server tracks, and give every piece a stable identity so a retry is a no-op, not a duplicate. Everything else — resume tokens, status polling, commit-last, TTL cleanup — is machinery around those two moves.

Words we'll earn before we lean on them

  • Chunk (part) — a fixed-size slice of a big file (we'll use 8 MB) uploaded as its own small request, so a failure loses only that slice.
  • Resumable upload — a multi-request upload where the server remembers which chunks it already has, so after a disconnect the client sends only what's missing.
  • Upload session / upload_id — a server-side record identifying one in-progress upload and tracking its received chunks. The resume token is how the client names it.
  • Checksum — a hash of the bytes (e.g. a CRC or SHA of a chunk) sent alongside them, so the server can detect a corrupted or truncated transfer and reject it.
  • Commit-last — the object becomes visible/usable only in a final step, after all chunks are present and verified (Lesson 20's "commit metadata last," Lesson 25's atomic commit).
  • Idempotent — an operation you can repeat and get the same result as doing it once (Lesson 13). A retry causes no extra effect.
  • Idempotency key — a client-chosen unique id attached to a mutation so the server recognizes a retry of the same request and doesn't do the work twice (Lesson 13/18).
  • Asynchronous (async) job — work the server does after answering the request. The request returns a handle immediately; the work finishes later (Lesson 5).
  • 202 Accepted — the HTTP status meaning "I took your request, I haven't finished it; here's where to check." The standard "async accepted" answer.
  • Status polling — the client repeatedly asks "is job X done yet?" via a status endpoint until it's finished (or failed).
  • Resume token / cursor — the opaque handle the client keeps so it can ask "what have you got, and where do I continue?" (Lesson 18's cursor idea, applied to transfers).
  • TTL (time-to-live) — how long the server keeps an abandoned upload session or finished job around before garbage-collecting it (Lesson 8/13/48).

Move 1 — Estimate: why one connection can't carry either operation

Put real numbers on "the network is bad," and the two failures become arithmetic, not bad luck.

The upload will not finish in one shot. Uploading 2 GB over a typical mobile uplink of 5 Mbps = 0.625 MB/s takes 2048 MB ÷ 0.625 ≈ 3,277 s ≈ 55 minutes. Now add the network: connections drop on average every ~180 s. A 55-minute upload therefore crosses about 3,277 ÷ 180 ≈ 18 disconnect windows. The probability the whole transfer survives with zero drops is astronomically small (roughly e^-18 ≈ 1 in 80 million). With the naïve single POST, every one of those ~18 drops throws away everything sent so far and restarts at byte 0 — so the upload doesn't just retry, it never converges. The unit of loss (the whole file, avg ~1 GB wasted per drop) is catastrophically too big.

Chunking shrinks the unit of loss by 256×. Split the 2 GB file into 8 MB chunks → 2048 ÷ 8 = 256 chunks, each taking 8 ÷ 0.625 ≈ 12.8 s to send. A disconnect now wastes at most the one chunk in flight — on average ~4 MB, versus ~1 GB for the naïve restart, a 1024 ÷ 4 = 256× reduction in wasted bytes per failure. And a single chunk transfer (12.8 s) has a e^-(12.8/180) ≈ 93% chance of surviving, so almost every chunk lands on the first try and the rest just retry cheaply. The upload now makes monotonic progress: after each disconnect the client resumes from where the server confirms it left off, and 55 minutes of good-signal-time gets you there no matter how many drops interrupt it.

The long job outlives the request — and the retry is the real danger. The CSV export scans the customer's full order history and takes the server ~4 minutes. But a phone's HTTP client typically times out an idle request in ~30–60 s, and mobile gateways cut long-held connections even sooner. So a blocking POST /export is guaranteed to time out: the client gets an error at ~60 s while the server is still working. What does an app do on an error? It retries. Now the same expensive export is running twice — and if the job has any side effect (charges a fee, emails a file, mutates a row, Lesson 13's $50 → $100), the timeout has manufactured a duplicate. Long work simply cannot live inside a request that something along the path will kill; it must be accepted quickly and run behind the request (Lesson 5's producer→queue→worker).

Why "just make the timeout longer / the connection more reliable" is the tempting wrong answer: you cannot buy your way out of physics on a shared mobile network — a tunnel drops the connection no matter how patient your client is, and raising the request timeout to 5 minutes just means a thread (and a load-balancer slot, Lesson 7's thread-pool) sits blocked for 5 minutes per user, collapsing your capacity. The fix is never "hold the fragile thing open longer." It's stop depending on one fragile hold: chop the transfer into pieces each short enough to usually succeed, and move the slow work off the request path entirely. Name the trade: one simple request vs a resilient multi-step protocol.

Move 2 — Model: two protocols, one backbone

Pattern A — the resumable, chunked upload

Three phases: create a session, upload chunks (retrying only the missing ones), complete with a commit that makes the file real only when every piece is present and verified.

Create. The client says "I want to upload a 2 GB file named drive.mp4." The server mints an upload_id (the resume token), records an upload session (upload_id → {size, chunk_size: 8 MB, received: {}}), and returns it. The session — not the connection — is now the durable thing that survives a drop. Upload. The client PUTs each chunk to /uploads/{upload_id}/parts/{index}, with a checksum of the chunk's bytes in a header. The server verifies the checksum (rejecting a truncated/corrupted transfer, which on a flaky link is common), stores the part, and records received[index] = true. Each chunk is idempotent by its index: re-PUTting chunk 7 just overwrites chunk 7 — sending it twice after an ambiguous timeout is harmless (Lesson 13's natural idempotency of an absolute PUT). Complete. The client POSTs /uploads/{upload_id}/complete. The server checks it has all 256 parts, optionally verifies a whole-file checksum, assembles them, and only then makes the object visible — the commit-last step (Lesson 20/25). Before complete, a half-uploaded file is never readable; after it, the file is atomically there.

The resume is the whole point, and it's just a status read. After any disconnect, the client reconnects and asks GET /uploads/{upload_id}: "which parts do you have?" The server answers "I have 0…N." The client resumes at N+1, skipping everything already confirmed. This is Lesson 18's cursor idea wearing a transfer's clothes: the resume token names a stable place in the work, and progress is measured by what the server confirms it received — never by what the client thinks it sent (the last chunk before a drop may or may not have landed; only the server knows). That "ask the server what it actually has" step is what makes progress monotonic across any number of failures.

Pattern B — the async job with status polling

Four phases: submit (accept fast), work (in the background), poll (client checks status), fetch (download the result).

Submit. The client POSTs /exports with an idempotency key (a UUID it generated, Lesson 13). The server does the minimum synchronously: create a job row (job_id, status: queued), enqueue the work (Lesson 5/9), and return 202 Accepted with the job_id — immediately, in milliseconds, long before the ~60 s timeout. Work. A background worker (Lesson 5) picks up the job, runs the ~4-minute export, writes the CSV to object storage, and updates the job row to status: done, result_url: … (or failed, error: …). Poll. The client periodically GETs /jobs/{job_id} and reads {status, progress, result_url?} — a cheap, fast, read-only request that a flaky network can retry freely. Fetch. When status flips to done, the client downloads the CSV from the returned URL (served via CDN, Lesson 14). The slow work has been lifted out of the request and put behind a handle the client can check as often as it likes.

Why the idempotency key on submit is not optional. The submit request itself can time out on this network: the server created the job and enqueued it, but the 202 got lost on the way back. The client, seeing no answer, re-submits. Without a key, that's a second export job — duplicated work, and if the job has any side effect, a Lesson 13 double-charge. With a client-chosen idempotency key, the server does an atomic "claim this key" (Lesson 13's unique-constraint check) before creating the job: the retry finds the key already claimed and returns the existing job_id instead of starting a new job. One logical submission, at most one job, no matter how many times a bad network makes the client re-ask. This is the same exactly-once effect on at-least-once delivery we've built since Lesson 13 — here guarding the "start the work" step.

Polling has its own dial: frequency vs freshness vs load (Lesson 2's cache dial, reborn). Poll every 1 s and a 4-minute job costs 240 status requests per client; poll every 10 s and it costs 24 — 10× less server load, but the client learns the job finished up to 10 s late. Two refinements tame it: exponential backoff on the poll interval (check often early, then ease off, Lesson 7) so a job that's clearly going to take minutes isn't hammered every second; and, at larger scale, replace polling with a push — a webhook (Lesson 45) or a WebSocket (Lesson 26) that tells the client "done" the instant it is, trading polling's simplicity for a live connection's complexity. Start with backed-off polling; reach for push when the poll traffic itself becomes the load.

Move 3 — Trace the paths

Three scenarios: an upload surviving a mid-flight disconnect, an ambiguous re-sent chunk absorbed harmlessly, and a long job surviving the client crashing and coming back.

Path A — upload survives a dropped connection

  2 GB file, 256 chunks of 8 MB. Signal dies after chunk 130.

    create   -> upload_id = U-9, chunk_size 8 MB, received {}
    PUT 0..129 (each +checksum, each verified & recorded)
    PUT 130   -> [TRAIN ENTERS TUNNEL — connection dropped]
                 (server may or may not have finished storing 130)

    --- 40 s later, signal back ---
    GET /uploads/U-9   -> server: "received = 0..129" (130 didn't commit)
    resume: PUT 130, 131, ... 255   (skip the 130 already-confirmed parts)
    POST /uploads/U-9/complete
      -> server checks all 256 present + whole-file checksum -> COMMIT
      -> 200, file is now visible in the object store (L20)

    Wasted by the drop: ONE chunk (<= 8 MB), not 130 chunks (~1 GB).
    Progress was monotonic: each reconnect resumed from server truth.

Path B — an ambiguous chunk, re-sent, absorbed

  The subtle case: the chunk arrived but the ACK was lost (L13/68).

    PUT chunk 77  -> server stores it, sends 200 -> [200 LOST in a dead spot]
    client sees a timeout, doesn't know if 77 landed
      -> SAFE MOVE: just PUT chunk 77 again
      -> server overwrites part 77 with identical bytes, received[77] still true
      -> 200

    Why harmless: a chunk PUT is idempotent by its INDEX (an absolute
    write, L13's natural idempotency). Re-sending is a no-op on state.
    The client never has to know "did it land?" -- it just re-sends and
    the server converges. No duplicate part, no corruption.

Path C — long job survives the client crashing

  Export ~4 min. Client submits, then the app is killed / phone dies.

    POST /exports  (idempotency-key = K-3)
      -> server: claim K-3 (atomic), create job J-5 queued, enqueue (L5)
      -> 202 Accepted, job_id = J-5           [work runs in background]
    [app crashes here — the connection is gone, but the JOB IS NOT]

    --- user reopens app 10 min later ---
    app still holds K-3 (saved locally) OR lists the user's recent jobs
    POST /exports (idempotency-key = K-3)   <- retry of the SAME submit
      -> server sees K-3 already claimed -> returns EXISTING J-5 (no 2nd job)
    GET /jobs/J-5  -> {status: done, result_url: .../export-J5.csv}
    download the CSV (L14).

    The work was decoupled from the connection: the job outlived the
    client. The idempotency key made the re-submit return the SAME job,
    not start a second ~4-min export (L13 exactly-once EFFECT).

Path A is the payoff of chunking: a drop costs one chunk and the server's confirmed state is the source of truth for resume. Path B is the payoff of idempotent-by-index chunks: the client never has to solve the impossible "did my last write land?" problem — it just re-sends and the server converges. Path C is the payoff of async + idempotency key together: the slow work survives the client entirely, and the retry that a flaky network guarantees lands on the same job instead of duplicating four minutes of work. In all three, the network still fails constantly — we just made each failure cost a cheap, safe retry. That resilience is bought with something, and the bill comes due next.

Move 4 — Find the first bottleneck: "resumable" means the server holds state

The moment an upload can pause and resume, the server must remember every in-flight upload between requests. The moment a job outlives its request, the server must store every job's status. That stored, in-flight state — not bandwidth, not CPU — is the real cost of this whole design.

The first bottleneck — orphaned state and its cleanup (the TTL dial). Every create that never reaches complete leaves an orphaned upload session: partial chunks sitting in storage, a session row in the index. On a flaky network, many uploads are abandoned — the user closes the app, gives up, or never comes back. Suppose 100,000 uploads/day start and 10% are abandoned mid-flight at an average of 1 GB already uploaded: that's 10,000 × 1 GB = 10 TB/day of orphaned bytes piling up, plus their part rows in your metadata store (Lesson 20's metadata plane). Without cleanup, you pay to store garbage forever. The fix is a TTL on every session (Lesson 8/13/48): if an upload sees no activity for, say, 24 hours, a background sweeper deletes its parts and its session row. The TTL is a two-sided dial — too short and you garbage-collect an upload the user meant to resume tomorrow (their progress is gone); too long and orphaned bytes accumulate and cost money. Finished jobs need the same treatment: keep the result and status for a bounded window (long enough for the client to poll and download, e.g. 7 days), then reap the CSV and the job row.

The second wall — where the in-flight state lives, and keeping it consistent with the bytes. The upload session (which parts received) and the job status (queued/running/done) are small but hot and shared: every chunk PUT updates a session, every poll reads a job row, and — critically — a load balancer may send the resume request to a different server than the one that took the earlier chunks. So this state cannot live in one server's memory; it must sit in a shared store (Lesson 26's connection-registry lesson: keep the truth off the disposable front-end). Two consistency traps follow. (1) The part bytes (in object storage) and the "I have this part" record (in the metadata store) are two writes — record the part as received only after its bytes are durably stored, or a resume will skip a part that isn't really there (Lesson 33's dual-write, in miniature). (2) The complete step must re-verify all parts are present at commit time, because a part could have been TTL-swept between upload and complete. The commit is the one linearization point (Lesson 25's atomic commit): before it, nothing is real; at it, everything is checked and made real at once.

The third wall — choosing the chunk size, and the resume-after-crash-mid-job problem. The chunk size is itself a trade: smaller chunks (say 1 MB) waste less per drop and resume faster, but multiply request overhead and metadata rows (2 GB = 2,048 parts to track); larger chunks (say 64 MB) mean fewer requests but a single drop wastes more and a slow link may not finish one chunk between disconnects. 8 MB is a common sweet spot for mobile: ~13 s per chunk (usually survives a 180 s-MTBF link) and only 256 rows to track. And jobs have their own resumability question: if a worker crashes 3 minutes into the 4-minute export, the job must not be lost or silently stuck — the queue's visibility timeout (Lesson 5/9) makes the message reappear so another worker retries, which means the job's own work must be idempotent or checkpointed (write the CSV to a temp path and atomically rename on completion, Lesson 20's commit-last again), so a retried job overwrites cleanly instead of producing a half-file or double side effect. Resumability is fractal: the upload resumes across drops, and the job must resume across worker crashes, by the same commit-last and idempotency moves.

So the honest design for our flaky-network customer is: for the big transfer, a resumable chunked upload — create a session with a durable upload_id (Lesson 18's cursor as a resume token), PUT fixed-size chunks that are idempotent by index and checksummed (Lesson 13/20), resume after any drop by asking the server what it actually has, and make the file real only at a commit-last step (Lesson 20/25); for the slow mutation, an async job — accept fast with 202 and a client-chosen idempotency key so a re-submit returns the same job (Lesson 13), run the work behind the request on a worker (Lesson 5/9), and let the client poll a status handle with backoff (Lesson 7) or get pushed the result (Lesson 26/45); and pay for all of it in server-held in-flight state that lives in a shared store (Lesson 26), stays consistent with the bytes (Lesson 33), and gets TTL-swept when abandoned (Lesson 8/13/48). Every choice names its price: resumability costs state; smaller chunks cost overhead; polling costs traffic; commit-last costs a two-phase protocol.

The deepest point: on an unreliable network you cannot make a step succeed, so you make repeating it free. The whole design is one instinct applied twice — shrink the unit of work until a failure is cheap, and give every unit a stable identity until a retry is safe. A chunk indexed 77 can be re-sent forever with no harm; a job keyed K-3 can be re-submitted forever and still run once. That's the same exactly-once-effect-on-at-least-once-delivery spine from Lesson 13, the same commit-last from Lesson 20/25, the same "keep the truth off the disposable connection" from Lesson 26, and the same cursor-names-a-stable-place from Lesson 18 — assembled into a protocol that treats a dropped connection as a routine event to resume past, not an error to fail on. The standing tension, from Lesson 2's first cache to here: robustness on bad networks vs protocol & server-state complexity.

The four traps

  • Trap 1 — trusting the client's idea of progress. Resuming from "the last chunk I think I sent" is wrong: the chunk before a drop may or may not have landed. Always resume from what the server confirms it received (GET the session) — the server's stored state is the only truth.
  • Trap 2 — a slow mutation inside a blocking request. Any request held open for minutes will be killed by a client, proxy, or gateway timeout, and the client's retry then duplicates the work (Lesson 13's double-charge). Accept fast with 202, run behind the request, and guard the submit with an idempotency key.
  • Trap 3 — no TTL on in-flight state. Every abandoned upload and finished job is state you keep paying for. Without a TTL sweeper, orphaned parts (10 TB/day in our estimate) and stale job rows accumulate forever. But tune it: too short and you delete an upload the user meant to resume.
  • Trap 4 — recording a part as received before its bytes are durable. If the "I have part 77" record commits before part 77's bytes are safely stored (or a part is swept between upload and complete), a resume skips a part that isn't there and the file is silently corrupt. Record after durability, and re-verify all parts at commit-last.

Where we landed

We dropped the hidden assumption behind every earlier lesson — that the request arrives — and designed for a mobile network that disconnects every ~3 minutes. Estimate showed the two failures as arithmetic: a 2 GB / 55-minute upload crosses ~18 disconnect windows so a single POST effectively never finishes, and a ~4-minute job is guaranteed to outlast the ~60 s request timeout, so the client's inevitable retry runs the expensive work twice. Model gave two protocols on one backbone: a resumable chunked upload (create a session → PUT 256 checksummed, index-idempotent 8 MB chunks → resume from server-confirmed state → commit-last), and an async job (202 + client-chosen idempotency key → background worker → poll-with-backoff or push → download), bound by the one idea that makes every retry safe. Tracing watched an upload survive a tunnel by wasting one chunk not a gigabyte, an ambiguous re-sent chunk absorbed as a no-op, and a job survive the client crashing by returning the same job_id on re-submit. The first bottleneck was that "resumable" means the server now holds in-flight state for every upload and job — orphaned sessions (~10 TB/day) demanding a TTL sweep, state that must live in a shared store and stay consistent with the actual bytes (record-after-durable, re-verify at commit), a chunk-size trade, and jobs that must themselves resume across worker crashes. Every dial named its trade. The standing tension, unbroken since Lesson 2's first cache: robustness on bad networks vs protocol & server-state complexity.
