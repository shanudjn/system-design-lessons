Storage Engines: LSM-Trees vs B-Trees — the Write Tax Under Every Database

For 46 lessons a "database" has been a black box we put rows into and read rows out of. Lesson 12 cracked it open just enough to explain fast reads: the B-tree, a fan-out-500 tree that finds any of 100M rows in ~3 disk hops. But every write-heavy system since then quietly paid a tax the B-tree never advertised — the ledger of Lesson 25 appending entries, the event log of Lesson 38 that only ever grows, the metrics store of Lesson 44 taking a million samples a second. A B-tree keeps its data in sorted order on disk, so inserting a key whose neighbors are scattered means a random write to a random spot — the one thing spinning and even solid-state disks do worst. This lesson opens the box the rest of the way and asks the question that decides which database you pick for a write-heavy workload: how does the storage engine turn a stream of writes into bytes on disk? We'll take Lesson 44's metrics ingest — 1,000,000 writes/second — and estimate why a B-tree needs ~16× the disk's entire bandwidth to keep up (and can't). We'll model the answer every write-optimized store reaches for — the log-structured merge-tree (LSM-tree): buffer writes in RAM, dump them to disk in big sequential batches as immutable SSTables, and clean up later with background compaction. We'll trace a write, a point read, a range read, and a delete through both engines. And we'll hit the wall the LSM trades into: reads now have to look in many places (read amplification), old versions pile up (space amplification), and compaction competes with your writes for the same disk — capped by a per-file Bloom filter (Lesson 21) that keeps reads cheap. The trade underneath every storage engine: write throughput vs read amplification & space.

The one system we'll design

We'll store the same firehose from Lesson 44: a fleet emits metrics at 1,000,000 data points per second, and (following Lesson 44) each point on disk is a lean 16 bytes — a timestamp and a value, with the label set stored once elsewhere. That is 1,000,000 × 16 B = 16,000,000 B/s = 16 MB/s of actual user data — a trickle. The catch is not the volume; it's the shape of the writes. Each point belongs to a different series, and a million series interleave, so at the storage layer the keys arrive in effectively random order. A storage engine — the layer of a database that decides how records are laid out on disk and how they're found again — has exactly one hard job here: absorb a million randomly-keyed writes a second onto a disk that is fast at sequential access and slow at random access. We'll measure our disk with the two numbers from Lessons 12/29: it streams ~500 MB/s sequentially, but a random seek-and-write costs on the order of milliseconds, so it manages only a few hundred to a few tens of thousands of random operations per second. Everything below follows from that one gap between sequential and random.

A storage engine turns a stream of writes into bytes on disk. A B-tree keeps those bytes sorted and updates them in place — great for reads, brutal for random-order writes. An LSM-tree refuses to ever write randomly: it batches writes in memory and flushes them sequentially, paying the cost back later in reads, space, and compaction work. Two terms up front: a write is sequential when it lands right after the previous one (the disk head never moves / the flash controller writes a clean block); it's random when it lands somewhere unrelated (a seek, or a read-modify-write of a scattered block). That single distinction is the whole lesson.

Words we'll earn before we lean on them

  • Storage engine — the layer of a database that lays records out on disk and finds them again (B-tree and LSM-tree are the two dominant designs).
  • Page — the fixed-size block (here 8 KB, from Lesson 12) a B-tree reads and writes as one unit; you can't update 16 bytes without rewriting the whole page.
  • Sequential vs random I/O — a write that lands next to the last one (fast, ~500 MB/s) vs one that lands somewhere scattered (slow, a seek per operation).
  • Write-ahead log (WAL) — an append-only file every committed write is first appended to, so a crash can't lose an acknowledged write (Lessons 33/38's durable log, here as a crash-recovery journal).
  • Memtable — the in-memory sorted buffer an LSM-tree accepts writes into before flushing them to disk.
  • SSTable (Sorted String Table) — an immutable file of key→value pairs kept in sorted order; once written, it is never modified.
  • Flush — writing a full memtable out to disk as one new SSTable, in a single sequential pass.
  • Compaction — the background job that merges several SSTables into fewer, dropping superseded values and deleted keys, keeping read cost and space bounded.
  • Tombstone — a marker written to record that a key was deleted (you can't erase it from an immutable file; you shadow it, and compaction removes it later — Lessons 15/20).
  • Write / read / space amplification — bytes actually written to disk per byte of user data; files touched per read; disk used per byte of live data. The three-way trade you can never zero out at once.
  • Bloom filter — a tiny probabilistic bitmap that answers "is this key definitely not here?" with no false negatives (Lesson 21), used per SSTable to skip files that can't hold the key.

Move 1 — Estimate: why a B-tree needs 16× the disk to ingest 16 MB/s

The B-tree from Lesson 12 is the default engine of most relational databases (Postgres, MySQL's InnoDB, and every classic SQL store) — and it earns that place on reads: it finds any key in ~log₅₀₀ rows ≈ 3 page hops. But its defining property is that keys live in sorted order across pages on disk, and that is exactly what makes our write workload detonate. Let's price it.

One insert = a full-page rewrite. A B-tree page is 8 KB = 8,192 bytes (Lesson 12); our record is 16 bytes. To store one new point, the engine must locate the leaf page whose key range covers it, read that 8 KB page, splice in the 16 bytes, and write the whole 8 KB page back — you cannot durably change 16 bytes of a page without rewriting the page. That's 8,192 ÷ 16 = 512× write amplification for a single isolated insert: 8 KB of disk writes to persist 16 B of data.

Random keys kill the one escape hatch. A B-tree can amortize that — if the next 511 inserts land in the same page (sorted, sequential keys), one page-write stores 512 records and amplification falls toward 1×. But our million series interleave, so consecutive writes land in different, scattered pages. Each insert touches a fresh page, which is then evicted from cache before the next write for it arrives — so the batching never happens. Worse, each is a read-modify-write of a random page: potentially a random read and a random write.

Now the two ways to see the wall. By bandwidth: 16 MB/s of data × 512 = 8,192 MB/s = 8 GB/s of page writes — 8,192 ÷ 500 ≈ 16× the disk's entire sequential bandwidth, and it isn't even sequential. By operations: 1,000,000 random page writes/second, when a hard disk does ~100 random I/O per second (1,000,000 ÷ 100 = 10,000× short) and even a fast SSD does maybe ~50,000 random writes/second (1,000,000 ÷ 50,000 = 20× short). The B-tree isn't slow here — it's off by one to four orders of magnitude, and no faster disk in the same class closes that gap.

Name the trade-off — sorted-in-place (B-tree) vs log-structured (LSM). Keeping data sorted on disk is what makes a B-tree's reads and range scans cheap and predictable (Lesson 12), and it is the exact same property that makes a random-order write expensive — you must go modify the one page where that key belongs. You cannot have "always sorted on disk" and "never do a random write" at once. The B-tree chose sorted-in-place and pays on writes; the LSM-tree, next, chooses never-random-write and pays on reads and space. Every storage engine is a position on that single trade.

Move 2 — Model: the LSM-tree turns random writes into sequential ones

The insight is Lesson 2's and Lesson 5's, applied to disk layout: if the expensive thing is a random write, don't do random writes — buffer them and write them out in big sequential batches. That is the whole of the log-structured merge-tree (the engine under RocksDB, Cassandra, LevelDB, ScyllaDB, and most write-heavy stores). Four parts.

1. The write path never touches a random page

Every incoming write does two cheap things and returns: it is appended to a write-ahead log (a pure sequential file, for crash recovery only) and inserted into the memtable — an in-memory sorted structure (a balanced tree or skip list). No disk seek, no page rewrite. At 16 MB/s, the WAL append is 16 ÷ 500 = 3.2% of the disk's sequential bandwidth — a rounding error, versus the B-tree's 1,600%.

2. Flush: memtable → one immutable SSTable, sequentially

When the memtable fills — say 64 MB — it is written to disk in one sequential pass as an immutable SSTable: a file of key→value pairs in sorted order, plus a small index and (below) a Bloom filter. Because the memtable is already sorted in RAM, the flush is a clean sequential write. A 64 MB memtable fills every 64 ÷ 16 = 4 s and flushes in 64 ÷ 500 = 0.13 s. The old WAL segment can then be discarded — its data is now safely in the SSTable. Random writes have become: a sequential WAL append, then a sequential bulk flush. The disk only ever does what it's good at.

3. SSTables are immutable — so an update is a new write, not an edit

An SSTable is never modified. To update a key you simply write the new value into the current memtable; it lands in a newer SSTable that shadows the older one. To delete a key you write a tombstone — a marker meaning "this key is gone" — which shadows every older value (Lessons 15/20's delete-by-marker). So over time a key can have several versions scattered across SSTables, newest wins. This is what makes writes cheap; it is also the seed of every cost in Move 4.

4. Compaction: merge files back down in the background

If SSTables only ever accumulated, reads would keep slowing and dead versions would waste space forever. Compaction is the background janitor: it reads several sorted SSTables, merge-sorts them into fewer (merging already-sorted files is sequential I/O), keeps only the newest value per key, and drops shadowed values and tombstones. Two common strategies set where you sit on the cost triangle: size-tiered (merge files of similar size; fewer rewrites → low write amplification, but more overlapping files → higher read & space amplification) and leveled (keep sorted, non-overlapping files in size levels; more rewrites → higher write amplification, but ~1 file per level to check → low read & space amplification).

Name the trade-off — the amplification triangle. An LSM-tree exposes three costs you trade against each other and can never minimize all at once: write amplification (each byte gets rewritten once per compaction it passes through — roughly 10–30× for leveled, still far below the B-tree's 512× and, crucially, all sequential), read amplification (a read may probe the memtable plus several SSTables), and space amplification (superseded versions and tombstones sit around until compaction reclaims them). Leveled compaction spends write amplification to buy low read & space; size-tiered does the reverse. Choosing a compaction strategy is choosing which corner of the triangle your workload can least afford.

Move 3 — Trace the paths

Follow one write, one point read, one range read, and one delete through the LSM engine — and contrast the read with the B-tree.

Path A — a write (the whole point)

  write  series=cpu.load{host=web-7}  ts=03:00:10  value=0.42   (16 B)

   1. APPEND to WAL (sequential, fsync) -- the only durable step. ~microseconds.
   2. INSERT into memtable (RAM, sorted). Ack the write. DONE.
        (no page found, no page read, no random write -- nothing like the B-tree)
   3. ...later, memtable hits 64 MB -> FLUSH as SSTable-9 (one sequential write),
        discard the WAL segment it covered.
   4. ...later still, compaction merges SSTable-9 with peers -> fewer, cleaner files.

  16 MB/s of writes = 3.2% of the disk sequentially. A million/s is comfortable.

Path B — a point read, and why it needs a Bloom filter

  read  latest value for cpu.load{host=web-7} at 03:00:10

   Newest wins, so search NEWEST -> OLDEST until found:
     1. memtable (RAM)                          -- miss
     2. SSTable-12 ? SSTable-11 ? ... SSTable-1  -- up to ~7 levels of files

   Naive: a key that ISN'T there forces probing EVERY SSTable = read amplification.
   B-tree comparison: a read is ~3-4 page hops, ALWAYS -- deterministic, no probing.

   FIX (L21): each SSTable carries a BLOOM FILTER -- a tiny bitmap answering
   "is this key DEFINITELY NOT in this file?" with NO false negatives.
     - Before touching a file's data, check its Bloom filter.
     - "definitely not" -> SKIP the file entirely (no disk read).
   At ~10 bits/key the false-positive rate is ~0.6185^10 = ~0.8% (~1%), so a read
   touches the ~1 file that truly has the key + a negligible ~1% wasted probe.
   Read amplification collapses from ~7 files to ~1.

Path C — a range read (where Bloom filters can't help)

  read  all cpu.load{host=web-7} samples from 03:00 to 03:05  (a scan, L44)

   A Bloom filter answers "is EXACT key X present?" -- it cannot answer "any key
   in [03:00, 03:05]?", because you don't know the exact keys in advance.
   So a range scan must MERGE the relevant key-range from the memtable AND every
   SSTable whose range overlaps [03:00, 03:05], newest-wins per key.

   This is the LSM's honest weakness: point reads are rescued by Bloom filters,
   but range scans pay full read amplification -> which is exactly what leveled
   compaction (few, non-overlapping files per level) exists to keep small.
   A B-tree, sorted in place, does a range scan as one contiguous walk -- its
   home turf (L12/L18 cursor pagination).

Path D — a delete is a write

  delete  series cpu.load{host=web-7}

   You cannot erase it from immutable SSTables. Instead WRITE a TOMBSTONE into
   the memtable -> it shadows every older value (newest wins). Reads that hit the
   tombstone first return "not found." The old values keep occupying disk until a
   COMPACTION that sees both the tombstone AND the values drops them together.
   => a delete temporarily INCREASES space (space amplification), and a stream of
      deletes can leave "tombstone-heavy" files that slow scans until compacted.

Path A is why you reach for an LSM at all — a million writes/second becomes a 3.2%-of-disk trickle. Path B is the tax you take in return (many places to look), bought back cheaply by the Bloom filter for point lookups. Path C is the tax the Bloom filter can't pay — range scans — and Path D shows deletes making it briefly worse before compaction cleans up. Every one of those "...later" and "until compacted" clauses points at the same background process, which is where the first real bottleneck lives.

Move 4 — Find the first bottleneck: compaction is a second write workload

The WAL makes it look like you can ingest at the disk's full sequential speed. You can't — because compaction is also writing, over the same disk, forever.

The real write ceiling is disk bandwidth ÷ write amplification. Foreground writes stream at 16 MB/s, but every byte gets rewritten by compaction ~10–30× on its way down the levels. Compaction and foreground flushes share one disk of ~500 MB/s. So the sustainable user-write rate isn't 500 MB/s — it's 500 ÷ WA. At a leveled WA of 20×: 500 ÷ 20 = 25 MB/s sustainable — comfortably above our 16 MB/s, but only ~1.5× headroom. Push WA to 30× and the ceiling drops to 500 ÷ 30 ≈ 16.7 MB/s — right on top of our load.

What happens when you cross it. If writes arrive faster than compaction can churn, new SSTables pile up at the top level faster than they're merged down. Read amplification climbs (more files to probe), space balloons (dead versions un-reclaimed), and the engine does the only safe thing: it throttles or stalls writes — the dreaded LSM "write stall" / "compaction debt." The LSM didn't remove the write cost; it moved it into the background, where it becomes a bandwidth budget you must not overspend. This is Lesson 27's utilization knee and Lesson 28's backpressure, living inside a single database.

Name the trade-off — foreground latency vs background work. More aggressive compaction (leveled) keeps reads and space tight but spends more of your disk on rewrites, lowering the sustainable write ceiling and stealing bandwidth from foreground writes. Lazier compaction (size-tiered) raises the write ceiling but lets read and space amplification grow. You are always dividing one disk's bandwidth between "serve now" and "clean up so we can serve later." There is no setting that is best at writes, reads, and space at once — you pick the two your workload needs and pay in the third.

The scoreboard: which engine for which workload

The four traps

  • Trap 1 — reaching for a B-tree because it's the default, under a write-heavy load. A B-tree's sorted-in-place layout turns each randomly-keyed insert into a full-page random rewrite (~512× amplification), and random-write IOPS is exactly what disks lack — so a metrics/log/ledger firehose (Lessons 25/38/44) can be 10–10,000× beyond what the engine can absorb. Match the engine to the workload: write-heavy + point/KV access → LSM; read/range-heavy OLTP → B-tree.
  • Trap 2 — assuming the LSM made writes free. The WAL's 3.2%-of-disk makes ingestion look effortless, but compaction rewrites every byte 10–30× over the same disk, so the sustainable ceiling is bandwidth ÷ write-amplification (~25 MB/s here), not the raw 500 MB/s. Exceed it and you get write stalls. Provision for the compaction bandwidth, not just the WAL.
  • Trap 3 — forgetting range scans can't use the Bloom filter. A Bloom filter rescues point reads by answering "definitely not here," but it can't answer "any key in this range," so range scans pay full read amplification across overlapping SSTables. If your workload is scan-heavy, choose leveled compaction (few, non-overlapping files) or reconsider a B-tree.
  • Trap 4 — ignoring tombstones and space amplification. Deletes and updates don't shrink an LSM immediately — they write markers that shadow old data, which lingers until compaction. A delete-heavy or churny workload can bloat space and slow scans with tombstone-heavy files. Size disk for the amplified footprint and tune compaction to reclaim on time.

Where we landed

The same "database" we've written to for 46 lessons is really a storage engine making one choice: how to turn a stream of writes into bytes on a disk that is fast at sequential and slow at random access. Estimate showed the B-tree of Lesson 12 — the read-optimized default — collapsing under Lesson 44's 1,000,000 writes/s: because it keeps data sorted in place, each 16-byte insert forces a read-modify-write of an 8 KB page (8,192 ÷ 16 = 512× write amplification), and random keys defeat the page-batching that could save it, so the engine needs 16 MB/s × 512 = 8 GB/s ≈ 16× the disk's whole bandwidth — or, in operations, 10,000× a hard disk's random-write budget. Model gave the write-optimized answer, the LSM-tree: append every write to a sequential WAL and a RAM memtable, flush the full memtable to disk as one immutable sorted SSTable, and let background compaction merge-sort files down, dropping shadowed values and tombstones — so a million random writes/second become a 3.2%-of-disk sequential trickle. Tracing showed the cheap write, the point read that would otherwise probe every SSTable (read amplification) rescued to ~1 file by a per-SSTable Bloom filter (Lesson 21, ~1% false positives at ~10 bits/key), the range read the Bloom filter can't help, and the delete that is itself a write. The first bottleneck is that compaction is a second write workload on the same disk: the sustainable ingest ceiling is bandwidth ÷ write-amplification ≈ 500 ÷ 20 = 25 MB/s, not the WAL's apparent 500 — cross it and the engine stalls writes (Lessons 27/28 inside one database). The real lesson: you cannot be best at writes, reads, and space at once. Sorted-in-place (B-tree) buys cheap reads and range scans with expensive random writes; log-structured (LSM) buys cheap sequential writes with read amplification, space amplification, and a compaction bandwidth budget you must respect. Picking a database is picking a corner of that triangle for your workload — the standing tension: write throughput vs read amplification & space.
