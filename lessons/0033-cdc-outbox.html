Change Data Capture & the Outbox: Getting Data Out of One Database Into Everyone Else's Without the Dual-Write Lie

Lesson 32 ended on a small, poisonous sentence: each saga step had to "commit locally and emit an event." Look closely at that "and." Committing to your database is one system; publishing to a message broker is another system — and Lesson 32 just spent a whole lesson proving there is no shared transaction across two systems. So "write the row and publish the event" is a dual write: two independent writes to two independent systems, and either one can succeed while the other fails. Pick write-then-publish and a crash in the gap leaves a real order that no one was ever told about. Pick publish-then-write and a crash leaves an announcement of an order that doesn't exist. There is no safe order — the same wall as Lesson 32, in miniature, and it sits under every "when an order is placed, update search / cache / the warehouse / notify the customer." This lesson takes one orders table and traces how to get its changes out to everyone else reliably. We'll estimate how often the dual write silently lies, model the transactional outbox (make the event a byproduct of the one commit) and change data capture (read the database's own commit log), trace a crash that the outbox survives and a dual write does not, and hit the wall that defines the domain: the whole world now flows through one relay. The trade shifts from Lesson 32's atomicity-vs-availability to freshness/consistency vs pipeline complexity.

The one system we'll design

Our orders service (Lessons 12, 24, 25) owns the source of truth for orders in its own database. It does 5,000 order writes/second at peak. But an order being placed is news that four other systems need:

  • the search index (Lesson 16) — so the order becomes findable;
  • the cache (Lesson 02) — so the read path serves it fast and stays fresh;
  • the data warehouse (Lesson 29) — so revenue dashboards count it;
  • the notification / next-saga-step (Lessons 26, 32) — so the customer hears "order confirmed."

None of those systems shares the orders database (Lesson 32's database-per-service rule). So the orders service has to tell them, and the obvious way is: write the order row, then publish an OrderPlaced event to a broker (Lesson 9) that all four consume. That "write, then publish" is the dual write. First, the words, then why it's a lie.

A dual write is two writes to two systems that can't share a transaction. Your database gives you BEGIN … COMMIT — atomic inside itself. The broker is a different system with its own success/failure. When you do "commit the row" and then "publish the event," you have two commits, no coordinator, and a gap between them where the process can crash, the broker can be down, or the network can drop. Whichever write lands second can fail after the first succeeded — and now two systems disagree about whether the order exists. This whole lesson is how to stop doing two writes and do one.

  There is no safe order to do two writes in. The gap between them is the bug.
  (This is Lesson 32's wall: atomicity across two systems must be BUILT, not assumed.)

The fix is not to pick a better order for the two writes — there isn't one. The fix is to stop having two writes. Make the announcement a byproduct of the one database commit you already trust, then ship it out separately from a durable log. That's the outbox, and change data capture is the same idea reading the database's own log instead of a table you add.

Words we'll earn before we lean on them

  • Dual write — writing the same fact to two independent systems (a database and a broker, or two databases) in two separate steps that can't be one atomic commit.
  • Transactional outbox — a plain table in the same database as your data. You insert the event row into it in the same transaction as the business row, so both commit together or neither does.
  • Relay / message relay — a separate process that reads unpublished outbox rows and publishes them to the broker, then marks them done. The only thing that talks to the broker.
  • Change data capture (CDC) — reading the database's own commit log (the write-ahead log / WAL in Postgres, the binlog in MySQL) and emitting an event for every committed row change — no outbox table, no app change.
  • Commit log / WAL — the append-only log a database writes before it acknowledges a commit; it's how the database itself guarantees the D in ACID (durability). Every committed change is already in it.
  • At-least-once — the relay may publish the same event more than once (it can crash after publishing but before recording that it did), so consumers see duplicates (Lesson 9).
  • Idempotent consumer — a consumer for which processing the same event twice has the same effect as once (Lesson 13) — the thing that makes at-least-once safe.
  • Replay — because every change is a durable, ordered log entry, you can re-read it from the start to rebuild a downstream system from scratch (Lesson 9's log, Lesson 29's kappa).

Move 1 — Estimate: how often does the dual write actually lie?

"It only breaks if we crash at the exact wrong instant" sounds rare. Price it and it isn't — at 5,000 writes/second even a tiny failure rate is a flood of silent divergence.

Worked: the steady drip. Say the publish step succeeds 99.9% of the time — a good broker on a good day. Then 0.1% of orders commit to the DB but their event never lands: 5,000/s × 0.001 = 5 lost events/second. Over a day that's 5 × 86,400 = 432,000 orders that exist in your database but were never announced — not searchable, not counted in revenue, no confirmation sent. Not an edge case. A constant, compounding leak of ~432k silently-invisible orders per day.

Worked: the burst. Now the broker has a brief blip — 30 seconds unreachable, once a day. If you write-DB-then-publish, every order in that window commits but can't be announced: 30 s × 5,000/s = 150,000 orders orphaned from one 30-second hiccup. If instead you publish-first, those same 150,000 announcements go out for orders that then fail to save — 150,000 phantoms. Either way one short blip = six figures of divergence.

Why "just add a retry" doesn't save it. Retrying the publish shrinks the drip but can't close it: the process can crash between the commit and any retry, and a retry loop that blocks the request holds the DB row's effects hostage to the broker's health (Lesson 7's cascade). The failure isn't "the publish was flaky"; it's "the commit and the publish are two separate facts, and something has to make them one." You cannot retry your way out of two systems disagreeing — you have to make there be only one write that matters.

Move 2 — Model: the outbox and change data capture

Both fixes share one move: collapse the two writes into one commit, then propagate from a durable log. They differ in where the log lives.

The transactional outbox — make the event part of the commit

Add an outbox table to the same database as orders. When an order is placed, insert the order row and an outbox row describing the event in one transaction:

  BEGIN                                    -- one local transaction, one database
    INSERT INTO orders     (id, ...);      -- the business fact
    INSERT INTO outbox     (event_id, type='OrderPlaced', payload, published=false);
  COMMIT                                    -- both land, or neither does (Lesson 13/25)

Now there is no dual write: the event and the order are one atomic commit, guaranteed by the database you already trust. A separate relay then does the risky part — talking to the broker — out of band:

  RELAY loop (a separate process):
    SELECT * FROM outbox WHERE published=false ORDER BY event_id LIMIT 500;  -- oldest first
    for each row:  publish to broker (Lesson 9)
    mark those rows published=true         -- (or delete them)

The relay is at-least-once (Lesson 9): if it crashes after publishing a batch but before marking those rows, it will re-read and republish them on restart → duplicates. That's fine, because we make consumers idempotent (Lesson 13) — the same event_id processed twice is a no-op. The outbox turns an unsolvable dual-write into two solved problems: one atomic local commit (the database's job) plus an at-least-once relay from a durable table (Lesson 9 + Lesson 13's job).

Change data capture — skip the table, read the database's own log

The outbox has you write the event down explicitly. But the database already writes down every committed change — that's the commit log (WAL / binlog), the append-only record it must fsync before acknowledging a commit (that's what makes commits durable). CDC puts a connector (e.g. Debezium) at the end of that log; it reads each committed change and emits an event. No outbox table, no application change at all — the event is the committed row change, read from the one log the database can't lie about.

  orders DB ──writes every commit──▶  COMMIT LOG (WAL / binlog)  ──tailed by──▶  CDC connector ──▶ broker
   (durable by definition; the DB's own source of truth)                          emits row-change events

  Outbox:  YOU write the event, the relay POLLS the table for it.
  CDC:     the DB ALREADY wrote the change, the connector TAILS the log for it.

Outbox vs CDC — the same idea, two costs.

Name the trade-off — clean events & portability vs zero app change & lowest latency. The outbox lets you emit exactly the event consumers should depend on, on any database, at the price of a table and a relay you build and clean. CDC gives you every change for free with the lowest lag, at the price of coupling consumers to your internal schema and needing privileged log access. And you can combine them: write to the outbox table in the transaction, then point CDC at just the outbox table — clean events, no polling load, log-driven propagation. Best of both.

Move 3 — Trace the paths

Run three scenarios through the outbox + relay design and watch the gap that killed the dual write simply not exist.

Path A — everything works

  1. BEGIN; INSERT order; INSERT outbox(OrderPlaced, published=false); COMMIT   -- one atomic commit
  2. relay: SELECT ... WHERE published=false  -> finds the row
  3. relay: publish OrderPlaced to broker      -> broker ACKs
  4. relay: UPDATE outbox SET published=true    -> row retired
  5. search / cache / warehouse / notify each consume OrderPlaced (Lessons 16/02/29/26)
  -> One write of record (the COMMIT). The broker never saw a half-order.

Path B — crash right after the commit (the dual write's death, survived)

  1. BEGIN; INSERT order; INSERT outbox(published=false); COMMIT   -- OK, both rows durable
        x  <-- CRASH here, or broker down for 30 s. The event was NOT published yet.
  ... process restarts (or broker recovers) ...
  2. relay: SELECT ... WHERE published=false   -> the outbox row is STILL THERE
  3. relay: publish it now                       -> order announced, just later
  -> No lost order. The dual write lost this event forever (nothing recorded the intent to
     publish). The outbox recorded that intent INSIDE the commit, so the crash only DELAYED it.

This is the whole point in one picture. In the dual write, the intent to publish lived only in the running process's next line of code — a crash erased it. In the outbox, the intent to publish is a committed row, as durable as the order itself. A crash can only make it late, never lost. Freshness bends; consistency holds.

Path C — the relay double-publishes (why consumers must be idempotent)

  2. relay: publish OrderPlaced (event_id=E) to broker  -> broker ACKs
        x  <-- CRASH before step 4's UPDATE published=true
  ... relay restarts ...
  2'. relay: SELECT ... WHERE published=false  -> row E is STILL false, republishes E
  -> broker now carries E TWICE. Consumers see a DUPLICATE.

  Safe because every consumer is IDEMPOTENT (Lesson 13):
    search:    upsert by order id        (indexing E twice = same document)
    warehouse: dedup on event_id         (second E ignored, revenue counted once)
    notify:    idempotency key on event_id (customer emailed once, not twice)

The relay guarantees at-least-once, not exactly-once — there is no exactly-once on the wire (Lessons 9, 13). You get exactly-once effect by making the receiving side idempotent, keyed on the stable event_id the outbox minted inside the commit. The same event id that made the commit atomic also makes the redelivery safe — one id doing double duty.

Move 4 — Find the first bottleneck: everything now flows through one relay

We removed the dual write, but we created a new load-bearing thing: a single pipe every downstream system depends on. Its health is now the freshness of search, cache, warehouse, and notifications all at once. Four pressures show up on it.

Pressure 1 — relay throughput & lag. The relay must keep up with 5,000 events/s. Poll every 100 ms in batches of 500 → 500 / 0.1 s = 5,000/s — it exactly keeps pace, and the batch/interval pair is the same latency-vs-throughput dial as Lesson 28 (bigger batches = higher throughput, more lag). If it falls behind, the backlog is consumer lag (Lesson 9) — the one number to alarm on, because it is how stale every downstream system is. Fall an hour behind and search is an hour stale.

Pressure 2 — polling load on the primary DB. A relay that SELECT ... WHERE published=false every 100 ms is 10 queries/second against your production orders database forever, plus the churn of updating/deleting retired rows. The fix is the combine-them move: point CDC at the outbox table so the log does the tailing — no polling query, lowest lag, and the primary is untouched.

Pressure 3 — the outbox table grows without bound. At 5,000 rows/s × 200 bytes, that's 5,000 × 86,400 × 200 B ≈ 86 GB/day of outbox rows if nothing removes published ones. Left alone it dwarfs the orders it describes and slows every relay scan. So published rows must be deleted or compacted — retire them after publish, or partition the outbox by time and drop old partitions (Lessons 20, 24). The outbox is a conveyor belt, not an archive: things ride it once and leave.

Pressure 4 — ordering. Consumers often need per-key order (all events for order 42 in the order they happened — placed before cancelled). One relay reading the outbox by event_id preserves global order but caps throughput; sharding the relay for scale means you must partition by key (Lesson 9) so a single order's events stay on one partition and stay ordered, even as different orders parallelize. Same partition-for-order-vs-parallelism trade as the log itself.

Name the core trade-off — you traded a silent lie for an eventually-consistent pipeline. The dual write was simple and wrong: it looked fine and silently diverged 432k times a day. The outbox/CDC pipeline is correct — nothing is ever lost — but it is eventually consistent: downstream systems lag the source by the relay's delay, you now run a relay/connector, size and clean an outbox, and make every consumer idempotent. You did not make the update instant everywhere; you made it guaranteed to arrive everywhere. Freshness/consistency vs pipeline complexity — and the log's hidden gift is replay: because every change is a durable ordered entry, a brand-new consumer (a fresh search cluster, a new warehouse) can be built by re-reading the log from the start (Lessons 9, 29). The propagation pipeline is also the rebuild button.

The four traps

  • Trap 1 — "just add a retry / a queue" to the dual write. A retry shrinks the drip but never closes the crash-in-the-gap window, and a synchronous retry loop couples your commit's success to the broker's health (Lesson 7 cascade). The only fix is one commit — outbox or CDC. Retrying two writes is still two writes.
  • Trap 2 — a non-idempotent consumer. The relay is at-least-once, so duplicates will arrive. A consumer that isn't idempotent double-counts revenue, double-charges, or double-emails on the very first relay restart. Key every consumer on the stable event_id (Lesson 13) — this is not optional, it's the price of at-least-once.
  • Trap 3 — never cleaning the outbox. An outbox that only grows becomes a 30 TB table in a year, slows every scan, and eventually takes the primary down. Retire published rows (delete, or partition-and-drop, Lessons 20/24). A conveyor belt that never unloads is a landfill.
  • Trap 4 — CDC leaking your physical schema. Raw row-change CDC ties every consumer to your exact table columns; a harmless rename or split (Lesson 24) then breaks four downstream systems at once. If consumers are external or many, emit a designed domain event (outbox, or an outbox-fed CDC) so your internal schema stays yours to change (Lesson 18's contract discipline).

Where we landed

We took one thing an orders service must do — save the order and tell everyone else (search, cache, warehouse, notify) — and named the trap hiding in the word "and": doing both is a dual write to two systems that can't share a transaction, so a crash in the gap loses the event (order exists, nobody told) or loses the row (everyone told about a ghost), with no safe order to do the two writes in — Lesson 32's wall, in miniature. Estimate showed it's not rare: at 5,000 writes/s a mere 99.9% publish rate drips 5/s = 432,000 silently-invisible orders a day, and one 30-second broker blip orphans 150,000 at once — and no retry closes the crash-in-the-gap window. Model gave the one move both fixes share — collapse two writes into one commit, propagate from a durable log: the transactional outbox writes an event row in the same transaction as the order (Lessons 13/25) so the announcement is a byproduct of the commit, shipped out-of-band by an at-least-once relay; and change data capture skips the table entirely by tailing the database's own commit log, emitting every committed change with no app change and the lowest lag — clean-events-and-portability vs zero-app-change-and-latency, and you can combine them by CDC-tailing the outbox. Tracing a clean run, a crash right after the commit (the outbox row survives → the event is only late, never lost, exactly where the dual write dies), and a relay that republishes (at-least-once → duplicate → made safe by idempotent consumers keyed on the same event_id the commit minted) showed the guarantee is real. The first bottleneck: everything now flows through one relay, whose lag is every downstream system's staleness (Lesson 9), whose polling loads the primary (→ CDC-tail it), whose outbox grows 86 GB/day unless cleaned (Lessons 20/24), and whose ordering needs partition-by-key to scale (Lesson 9). Four traps guard the build: retrying the dual write, a non-idempotent consumer, an un-cleaned outbox, and CDC leaking your schema. The real lesson: you can't atomically write to a database and a broker — so don't. Write once, to the log the database already keeps, and let a relay carry it everywhere at-least-once. Freshness/consistency vs pipeline complexity — and the log you built to propagate changes is the same log you replay to rebuild.
