Edge Computing: Running Code Milliseconds From the User

Lesson 14 pushed cached bytes out to hundreds of edge locations so a photo loaded from 20 km away instead of across an ocean; Lesson 50 steered each user to the nearest one. This lesson pushes the next thing outward — code. Instead of every request crossing the planet to a single origin to be authenticated, personalized, and routed, we run that logic at the edge: a small function executes at the PoP nearest the user, milliseconds away, and only the requests that genuinely need the authoritative database travel home. Done right, this cuts tail latency and takes load off the origin. Done wrong, it does something worse than nothing: a function that isn't already running nearby has to start first, and if starting costs more than the round trip you were trying to save, you have paid to be slower. We'll take one concrete system — a global app on 300 edge PoPs fronting a Virginia origin — and estimate both the latency it can win and the trap hiding inside "run it everywhere." We'll model what an edge function actually is, why the isolation mechanism (isolate vs container) decides whether the idea even works, and the hard rule for state. We'll trace a request the edge fully answers, a cold start that either wins or loses depending on one number, and a request that must go home because it touches authoritative data. Then the wall the whole thing leans on: you can push code to 300 places, but you cannot push a strongly-consistent database there — so the edge runs the decision, never the source of truth. The trade underneath: latency & offload vs consistency & operational reach.

The one system we'll design

A global web app serves users on every continent. Its authoritative systems — the database (Lesson 25's ledger, Lesson 12's orders table), the application services — live in one origin region, Virginia. In front of them sit 300 edge PoPs (Lesson 14/50): small points of presence in cities worldwide, each already terminating TLS and caching static bytes for the users nearest it. Global request rate is 40,000 req/s (Lesson 27's fleet).

Today every dynamic request — even one the origin will just reject or redirect — makes the full trip to Virginia and back. We want to move the cheap, near-the-user work onto the PoPs: verify the login token, pick the A/B test variant, choose which region to route to, rewrite the URL, block the obvious bot, serve a personalized-but-cacheable shell. Each of those is a small piece of code, and we want it to run at the PoP the user already reached — not an ocean away. The goal: answer at the edge everything that can be answered with only local or slightly-stale data, and send home only what truly needs the authoritative database.

Why bother? Two payoffs, and one trap that eats them if you're careless:

  • Latency — a request the edge can fully answer skips the ~200 ms round trip to Virginia. For a user in Sydney that's the difference between ~215 ms and ~15 ms.
  • Offload — every request the edge finishes is one the origin never sees, so the origin fleet shrinks and its tail calms (Lesson 27's knee).
  • The trap — spreading compute across 300 locations means each location runs each function rarely, so functions keep going cold. If starting a cold function costs more than the trip you avoided, edge compute is a net loss. This is the whole tension, and we'll size it exactly.

Edge computing runs short, stateless-or-eventually-consistent functions at the PoP nearest each user, so requests that need only local or slightly-stale data are answered milliseconds away and never reach the origin — while anything needing the authoritative, strongly-consistent database is forwarded home. It is not "move the app to the edge." The origin database does not move (it can't, and stay consistent — that's the whole lesson). What moves is the decision layer in front of it.

Words we'll earn before we lean on them

  • Edge / PoP (point of presence) — one of the hundreds of small datacenters near users (Lesson 14/50), close in network distance so a round trip is a few ms, not ~200.
  • Origin — the central region holding the authoritative services and database. The single source of truth.
  • Edge function — a small piece of code that runs at a PoP, triggered per request, short-lived, with a tight CPU and memory budget and no durable local disk.
  • Cold start — the time to get a function ready to run when nothing is already warm for it: load the code, build its sandbox, initialize. Paid on the request that finds it cold.
  • Isolate — a lightweight sandbox inside one already-running process (a V8 isolate is the common form). Starts in ~5 ms, costs ~3 MB. Many thousands share one process.
  • Container / micro-VM — a heavier sandbox with its own OS/runtime. Stronger isolation, but ~250 ms–seconds to cold-start and 100s of MB each.
  • Warm window — how long a runtime keeps a function loaded after its last request before evicting it to reclaim memory.
  • Edge KV — a key–value store replicated to every PoP: reads are local and fast, writes go to a center and propagate to the edges over seconds (eventually consistent, Lesson 11/23).
  • Offload — the fraction of requests the edge finishes so the origin never sees them.
  • Blast radius / operational reach — how far a bad change spreads, and how hard it is to deploy, observe, and debug code that now runs in 300 places (Lesson 17/31/36).

Move 1 — Estimate: the latency you win, and the cold start that can eat it

Three numbers decide whether edge compute helps: the round trip you save, the cost to start a cold function, and how often functions actually go cold when you spread them across 300 PoPs. Get the third wrong and the first two are a fantasy.

1. The round trip you win. Virginia to Sydney is ~15,500 km. Light in fiber travels at ~⅔ c ≈ 200,000 km/s, so one way is 15,500 ÷ 200,000 = 77.5 ms and a round trip is ~155 ms at the theoretical floor — call it ~200 ms in practice with routing (Lesson 14's speed-of-light tax). A request the edge fully answers pays ~5 ms to reach the Sydney PoP plus ~10 ms of work = ~15 ms, versus ~215 ms going home. That ~200 ms gap is the prize — and it is also the budget a cold start must stay under, or the edge is slower than the origin it replaced.

2. The cold-start budget. Here is the number that makes or breaks the design. An isolate starts in ~5 ms; a container starts in ~250 ms or more.
• Isolate cold start 5 ms « 200 ms saved → even a cold request is a big win.
• Container cold start 250 ms > 200 ms saved → a cold request is slower than just calling Virginia would have been.
Same idea, opposite outcome, decided entirely by the isolation mechanism. This is why edge platforms run isolates, not containers: at the edge, cold start is not an edge case — it's the common case.

3. Why functions go cold at the edge (the counter-intuitive part). At the origin, one function serving all 40,000 req/s is invoked constantly — it is permanently warm, and its cold start is amortized to zero. Spread that same traffic across 300 PoPs and each PoP sees 40,000 ÷ 300 ≈ 133 req/s. Now spread that across, say, 1,000 different tenant functions per PoP and each individual function sees 133 ÷ 1,000 ≈ 0.13 req/s — one request every ~7.5 s. If the warm window is 5 s, the function is evicted between requests, so nearly every request pays a cold start. The very thing that makes the edge fast — being in 300 places — is what makes each place cold, because it divides your traffic 300 ways. Locality and warmth pull against each other, and near-zero cold start (isolates) is the only thing that lets you have both.

Name the trade-off — latency & offload vs consistency & operational reach. Moving code to the edge buys latency (skip the round trip) and offload (spare the origin). You pay in two currencies. First, consistency: the edge can hold only local or eventually-consistent state, so anything authoritative still goes home. Second, operational reach: your code now runs in 300 places you must deploy to, observe, and debug — a bad change has a 300-PoP blast radius. The rest of the lesson is spending latency where the data allows it and keeping the truth where it must stay.

Move 2 — Model: what an edge function is, why isolates, and the one rule for state

An edge function is not a shrunken server. It is a deliberately constrained thing, and each constraint exists to make "run it in 300 places, cold most of the time" actually work.

1. The execution model — small, short, stateless-by-default

An edge function is triggered per request, runs for a tight CPU budget (tens of milliseconds), gets a small memory cap, and has no durable local disk. It is designed to be started cheaply, run briefly, and thrown away — because at 0.13 req/s per function per PoP, it will be started and thrown away constantly. Statelessness isn't a style choice here; anything it needs to remember has to live somewhere that survives the function's disposal, which is the whole state question below.

2. Isolate vs container — the choice that decides feasibility

To run thousands of tenants' functions across 300 PoPs, each PoP must pack many functions into limited hardware and start any of them almost instantly. That rules out one-container-per-function:

Container / micro-VM: own OS and runtime, ~250 ms+ cold start, ~100–170 MB each. Strong isolation, but a PoP can hold only hundreds of them and every cold request blows the latency budget. Isolate: a sandbox inside one already-running process (a V8 isolate), ~5 ms cold start, ~3 MB each. One process holds thousands of tenants; starting one more is cheap.

The memory math is as decisive as the latency math: at ~3 MB per isolate, a modest PoP node holds thousands of tenant functions resident; at ~150 MB per container, the same node holds ~50× fewer. Edge compute is only affordable because isolates make a cold start ~5 ms and a resident function ~3 MB. The trade you accept: isolates share a process, so isolation is weaker than a container's — you lean on the language sandbox (no arbitrary native code, tight syscall surface) instead of an OS boundary.

3. The one rule for state — the edge runs the decision, the origin owns the truth

You cannot put a strongly-consistent database in 300 places. This is not a limitation of today's tools; it is Lesson 11 and Lesson 23 restated: 300 replicas plus the speed of light means a write can't be seen everywhere at once, so you either accept eventual consistency or you coordinate back to a center — and coordinating is exactly the round trip the edge was meant to avoid. So edge state comes in three honest flavors, chosen by how stale the data is allowed to be:

  • No shared state — the function needs only what's in the request: verify a signed JWT with a cached public key, read a signed cookie, rewrite a URL. Perfectly edge-native, nothing to replicate.
  • Eventually-consistent edge KV / cache — config, feature flags, A/B assignments, the product catalog (Lesson 48). Reads are local and fast; writes go to a center and reach the edges in seconds. Fine when "seconds stale" is harmless.
  • Forward to origin — anything authoritative and strongly consistent: place an order, move money (Lesson 25), read a live balance before a charge, check inventory before overselling (Lesson 32). The edge does the cheap near-user part (TLS, auth, bot filter) and pays the round trip for the authoritative op.

The four properties that make edge compute work, named: near-zero cold start (isolates, so cold is cheap), bounded execution (small/short, so 300 PoPs stay affordable), local-or-eventual state (never strong consistency at the edge), and graceful fallback (forward home what can't be answered locally). Miss any one and edge compute turns into a slow, inconsistent, unmanageable second copy of your app.

Move 3 — Trace the paths

Follow three requests through the Sydney PoP: one the edge fully answers, one that hits a cold start (and wins or loses on a single number), and one that must go home.

Path A — a request the edge fully answers (the payoff)

  A logged-in user in Sydney requests their personalized home page.

  t=0     request reaches the Sydney PoP (~5 ms from the user).
  edge    isolate runs the function:
            - verify the signed JWT with the cached public key  (no origin)
            - pick the A/B variant from the signed cookie       (no origin)
            - read feature flags from edge KV                   (local, ~1 ms)
            - assemble the personalized shell from edge cache   (L14)
  respond ~15 ms total. Origin in Virginia is NEVER contacted.

  vs the old way: ~215 ms (5 ms to PoP + ~200 ms round trip to Virginia
  + work) for the SAME answer. ~14x faster, and one fewer request the
  origin fleet had to serve (offload).

Path B — a cold start that wins or loses on one number

  This tenant's function is rarely hit at THIS PoP (0.13 req/s = 1 per 7.5 s),
  and the warm window is 5 s -- so this request finds it COLD.

  ISOLATE runtime:   cold start ~5 ms + ~10 ms work = ~15 ms.
                     5 ms << 200 ms saved -> STILL A WIN, even cold.

  CONTAINER runtime: cold start ~250 ms + ~10 ms work = ~260 ms.
                     260 ms > 215 ms (just calling Virginia) -> A LOSS.
                     You paid MORE to run it "nearby" than to go home.

  Same code, same PoP, same request. The isolation mechanism is the
  whole difference. At the edge, most requests are cold (traffic split
  300 ways), so cold start isn't a corner case to tolerate -- it's the
  design center. Near-zero cold start is a REQUIREMENT, not a nicety.

Path C — a request that must go home (state at the edge)

  The user clicks "Buy" -- a write against the authoritative order/ledger.

  edge    does the cheap near-user work first:
            - terminate TLS, verify the JWT, filter the obvious bot,
            - rate-limit the abusive client (L08) -- all local, ~ms.
          then: this needs the AUTHORITATIVE DB. The edge does NOT hold it.
   -> forward to Virginia. Pay the ~200 ms round trip. The order is placed
      exactly once (L13/L25/L32) against the single source of truth.

  Contrast two READS to show the dial:
    catalog page (stale by seconds is fine)  -> edge KV, ~1 ms, no trip.
    live account balance before a charge      -> authoritative, must be
       current -> forward to origin, pay the trip. Staleness here = wrong money.

  The edge still HELPED even on the write: it did auth, filtering, and
  rate-limiting near the user, so only clean, authenticated writes reach
  the origin. It moved the DECISION outward; the TRUTH stayed home.

Path A is the win: local-only data, answered in ~15 ms, origin untouched. Path B is the knife-edge — at the edge, cold start is the common case, so the runtime must make it ~5 ms (isolate) or the whole idea inverts into "slower than the origin". Path C is the boundary everyone gets wrong at first: the edge is a decision layer, not a database. It authenticates, personalizes, filters, and routes near the user, and forwards anything authoritative home — because a strongly-consistent write in 300 places is a contradiction (Lesson 11/23), and pretending otherwise trades correct money for saved milliseconds.

Move 4 — Find the first bottleneck: you can push code to 300 places, not a consistent database

Cold start, the scary number in Move 1, is solved by isolates — ~5 ms is comfortably under the round trip. The wall that remains is the one that doesn't go away with a better runtime: state. The edge can run any decision, but it cannot own the truth, because a strongly-consistent database cannot exist in 300 places at once and stay both consistent and fast.

1. The consistency wall (Lesson 11/23, at the edge). Say you tried to keep the live inventory count at all 300 PoPs so "Buy" could be answered locally. A sale in Sydney must be seen in Frankfurt before Frankfurt sells the same last unit — that requires cross-PoP coordination on every write, and the speed of light makes that a global round trip (Lesson 23's ~90 ms+ per hop) on the hot path. You've re-imported the latency you left home to escape, times 300. So you don't: authoritative inventory and orders stay at the origin (or a small set of regions), and the edge forwards to them. Eventually-consistent data (flags, catalog, A/B buckets) rides edge KV and is allowed to be seconds stale; strongly-consistent data (balance, inventory, orders) goes home. The dial is exactly "how stale can this be?" — and it's the same dial as Lesson 2's cache TTL, Lesson 14's freshness-vs-speed, and Lesson 23's local-writes-vs-global-order, now applied to where compute is allowed to answer.

2. The operational-reach wall. Your code now runs in 300 places. A bad deploy isn't one region's problem — it's a 300-PoP, global blast radius (Lesson 31/36). So edge deploys need canary + health-gated promotion (Lesson 31): roll to a few PoPs, watch error rate and p99 (Lesson 17), then widen. Observability must aggregate across 300 PoPs (Lesson 17's trace/metric firehose, now geographically smeared). And there's a seductive trap: keep pushing "just one more thing" to the edge and you grow a thick edge — a distributed monolith copied 300 times, coupled to origin schemas, that you can't change in one place. The discipline is a thin edge: auth, routing, personalization, filtering, caching — the stateless decision layer — and nothing that wants the authoritative database.

Two smaller walls sit behind those, both familiar. Cold start still bites the long tail: even at ~5 ms it's non-zero, and for latency-critical paths you keep the hottest functions warm (pay idle memory to remove even the 5 ms — Lesson 27's warm-pool dial, shrunk). And edge KV writes are eventually consistent by construction: a flag flipped at the center reaches all 300 PoPs over seconds, so two users in two cities can briefly see different config — fine for a flag, a bug if you mistook it for a lock (it isn't one — Lesson 22 lives at the origin). The deepest point: edge computing does not move your system to the edge. It moves the decision to the edge and leaves the truth at the origin — because latency is cheap to spread and consistency is not.

The four traps

  • Trap 1 — running edge code in containers. A ~250 ms container cold start is larger than the ~200 ms round trip you were saving, and at the edge most requests are cold (traffic split 300 ways). The function is then slower than just calling the origin. Use isolates (~5 ms, ~3 MB) so a cold start stays far under the trip and a PoP can hold thousands of tenants.
  • Trap 2 — putting authoritative state at the edge. Trying to keep a strongly-consistent count (inventory, balance) at 300 PoPs re-imports global coordination onto the hot path (Lesson 11/23) — the exact latency you fled, times 300, or a correctness bug when you skip it. Keep the truth at the origin; put only local or eventually-consistent data at the edge, chosen by how stale it may be.
  • Trap 3 — the thick edge. Pushing "one more thing" to the edge until it's a distributed monolith copied 300 times, coupled to origin schemas and impossible to change in one place. Keep the edge thin: auth, routing, personalization, filtering, caching — the stateless decision layer — and leave data-heavy logic at the origin.
  • Trap 4 — ignoring the 300-PoP blast radius. Deploying edge code everywhere at once makes a bug a global outage, and running blind across 300 PoPs hides where latency lives. Canary + health-gate the rollout (Lesson 31/36) and aggregate traces/metrics across PoPs (Lesson 17).

Where we landed

Edge computing is Lesson 14's idea — put it near the user — applied to code instead of bytes, and it lives or dies on two numbers and one rule. Estimate sized the prize (a ~200 ms round trip skipped, ~215 ms → ~15 ms for a Sydney user) and the trap: spreading 40,000 req/s across 300 PoPs and 1,000 functions gives each function ~0.13 req/s — one request every ~7.5 s — so functions go cold constantly, and a cold start must stay under the round trip or the edge is slower than the origin. Model showed why that makes isolates (~5 ms, ~3 MB) non-negotiable where containers (~250 ms) invert the win, and gave the one rule for state: local-only, eventually-consistent edge KV, or forward home — chosen by how stale the data may be. Tracing walked a request the edge fully answered in ~15 ms (origin untouched), a cold start that won on an isolate and lost on a container from the very same code, and a "Buy" that the edge authenticated and filtered near the user but forwarded home because the truth isn't at the edge. The first bottleneck is exactly that: you can push code to 300 places but not a strongly-consistent database, so the edge runs the decision and the origin owns the truth — with a thin-edge discipline and canary rollouts to keep the 300-PoP blast radius survivable. Move the logic outward; keep the source of truth home. The standing tension: latency & offload vs consistency & operational reach.
