Data Lakes & the Lakehouse: Teaching a Pile of Files to Act Like a Table

Lesson 29 built a warehouse that answered "revenue by region by day" in half a second — a closed, proprietary system that owned its storage and its query engine together. But most of the world's analytics data doesn't live in a tidy warehouse; it lives as a pile of files on object storage (Lesson 20) — cheap, open, and readable by any engine you like: Spark, Trino, Flink, the warehouse itself. That openness is the dream. The catch is brutal and quiet: a directory of files is not a table. It has no transactions, so a reader can catch a writer mid-update and get a silently wrong answer; it has no atomic way to swap one set of files for another; and just finding which files make up "the table right now" means listing a bucket that can hold millions of them. This lesson builds the missing layer that turns that pile of files back into a real table — an open table format (Iceberg, Delta, Hudi) — and the machine it produces is the lakehouse: warehouse guarantees on lake storage. We'll estimate the cost of the "directory = table" lie and watch planning a single query take minutes; model the fix — a thin metadata layer that names exactly which immutable files are the table, committed by swapping one atomic pointer; trace a read that sees a consistent snapshot, a write that commits atomically or safely retries, and a bad batch rolled back in an instant by pointing at yesterday's snapshot; and find the first bottleneck, which is that we didn't remove the hard part — we moved it into the metadata, where the commit is one serialization point and the files still need compacting. The trade under every choice: openness & cheap shared storage vs query performance & metadata-management complexity.

The one system we'll build

Take the exact dataset from Lesson 29: the orders history — 11 billion rows, ~11 TB, three years deep, partitioned by day (that's 1,095 daily partitions). In Lesson 29 it lived inside a closed warehouse. Now we want it stored as plain Parquet files on object storage (Lesson 20's key→blob store) for two reasons: object storage is cheap (a fraction of warehouse-managed storage), and it is open — Spark can train a model on it, Trino can run ad-hoc SQL, Flink can stream from it, and the warehouse engine can still serve dashboards, all reading one copy, with no vendor owning the bytes (the anti-lock-in argument of Lesson 58). We keep the columnar layout, partition pruning, and star schema of Lesson 29 — nothing there changes. What changes is who guarantees the table is a table. In the warehouse, the engine did. On raw object storage, nobody does — and that is the whole problem this lesson solves.

  A directory of files is NOT a table. Add a metadata layer.

  RAW LAKE (a pile of files) -- cheap & open, but no guarantees:
     s3://orders/day=2026-08-01/  file0001.parquet

  LAKEHOUSE = the same files + a thin METADATA LAYER on top:

        catalog pointer  --->  "current table = metadata_042"   (ONE atomic pointer)
                                        |
                                        v
                              metadata_042  (a SNAPSHOT)
                                schema (by column-ID, L24)
                                list of manifests
                                        |
                                        v
                              manifest  (the file list + STATS)
                                file0001.parquet  rows, day, min/max(region,amount)
                                file0002.parquet  rows, day, min/max(region,amount)
                                        |
                                        v
                              Parquet DATA FILES  (immutable, L20)

  Read  = follow the pointer -> get an exact, frozen list of files.
  Write = add new files -> write new metadata -> CAS the pointer.
  Roll back = point the catalog at an OLDER metadata. (instant)

The one idea the whole lesson turns on: a change that touches many files (add 78 files, delete 1,440, rewrite a column) is made atomic by reducing it to a change of one tiny thing — the pointer that names the current metadata. Files are immutable; you never edit a table in place. You write new files, write a new metadata object that lists the new set, and then flip a single pointer from the old metadata to the new in one atomic operation (a compare-and-swap, Lesson 6). A reader holding the old pointer sees the old complete table; a reader who follows the new pointer sees the new complete table. Nobody ever sees a half-done mix. This is Lesson 14's "rename, don't mutate," Lesson 20's "commit the metadata last," and Lesson 33's outbox — the same move, applied to a table.

Words we'll earn before we lean on them

  • Data lake — raw files (usually Parquet, Lesson 29) sitting directly on object storage (Lesson 20). Cheap and open; not a table on its own.
  • Object storage — a flat key→blob store (Lesson 20). Immutable-friendly, durable, cheap, but its only "find things" primitive is LIST (enumerate keys under a prefix), which is slow and paginated (~1,000 keys per call).
  • Parquet — a columnar file format (Lesson 29): stores a column together, compresses hard, and carries a footer with per-column min/max stats for the rows inside that file.
  • Open table format — a specification (Iceberg / Delta Lake / Hudi) for a metadata layer over immutable data files that makes the pile behave like a transactional table. Open = many engines implement the same spec and read one copy.
  • Metadata layer — small files that record which data files currently make up the table, plus the schema and per-file stats. The metadata is tiny compared to the data.
  • Snapshot — the exact, frozen set of data files that is the table at one instant. Each commit produces a new snapshot; old ones are kept.
  • Commit / atomic pointer swap — publishing a new snapshot by atomically changing one pointer (a compare-and-swap, Lesson 6) from the old metadata to the new.
  • Snapshot isolation — a reader pins one snapshot for its whole query, so a concurrent writer's commit can't change the answer mid-flight (the "I" of ACID, Lesson 32).
  • Time travel — querying an old snapshot ("the table as of last Tuesday"), free because old snapshots and data files are immutable and kept.
  • Compaction — rewriting many small data files into fewer big ones as a new snapshot, to fix the small-file problem (Lesson 20/29) — now safe, because the swap is atomic.
  • Lakehouse — the result: warehouse guarantees (ACID, schema, time-travel) on lake storage (cheap object files, open to many engines).

Move 1 — Estimate: what "a directory is a table" actually costs

Two numbers decide this whole lesson. First, how many files does this table become? Second, what does it cost to plan a query — just to figure out which files to read — when all you have is a directory.

PieceValueWhere it comes from
Table size11 TB, 11B rowsL29's orders history
Partitions1,0953 years × 1 partition/day
Volume per day~10 GB/day11 TB ÷ 1,095 days
Streaming ingest1 file/minutea small file every minute (L20/29 small-file trap)
Files per day1,44060 × 24; each ~7 MB (10 GB ÷ 1,440)
Files total~1.58 million1,095 days × 1,440
Object-store LIST page1,000 keys/callobject storage's only "find" primitive
Read a Parquet footer~1 ms (optimistic)one small GET + parse, per file

The number that kills "just point a query at the directory": planning takes minutes before a single row is read. Ask "revenue for one region on one day." To answer it you must find which files hold that day's rows and which of those hold that region. On a raw directory the metadata to answer that lives only inside each file's footer, so the engine must LIST the bucket (1.58M keys ÷ 1,000 per page = 1,580 paginated LIST calls) and then open every file's footer to read its min/max stats. Even at an optimistic 1 ms per footer, 1,580,000 footers × 1 ms = 1,580 seconds ≈ 26 minutes of planning — before the scan Lesson 29 measured at 0.5 s even begins. The scan isn't the problem; finding the files is. And it's worse than slow: LIST on object storage has historically been eventually consistent, so a file written a moment ago might not appear — the directory doesn't even reliably tell you what it contains.

The second number: there is no atomic multi-file change, so readers see half-done tables. Suppose a nightly job compacts today's 1,440 small files into ~78 big ones (10 GB ÷ 128 MB). On a raw directory the only way to "replace" them is: write 78 new files, then delete 1,440 old ones — two steps, not one, with no atomic bracket around them. A dashboard query that runs in the gap sees a partition that is missing rows (old files deleted, new ones not yet counted, or counted twice if it saw both). The result isn't an error you'd catch — it's a revenue number that's silently wrong for a few seconds every night. A directory has no transaction, so every operation that touches more than one file is a race. This is the same dual-write hazard as Lesson 33, and the same "no atomicity across a boundary" as Lesson 32 — here the boundary is "a set of files."

Move 2 — Model: a thin metadata layer, committed by one atomic pointer

The table is a pointer to an immutable list of immutable files

Every problem in Move 1 comes from the same root: on a raw directory, "what is the table right now?" has no single, atomic, precomputed answer. So we add one. We keep the data files exactly as they are — immutable Parquet on object storage — and layer small metadata files on top that record, explicitly, which data files make up the table and what's in each one.

The metadata tree (Iceberg's shape, in plain words). A catalog holds one tiny pointer per table: "the current table is metadata_042." That pointer is the only thing that ever changes, and it changes atomically. metadata_042 is a snapshot: it records the schema (columns tracked by a stable column ID, not by position — that's what makes Lesson 24's add/rename/drop safe) and a list of manifest files. A manifest is the file list with stats: for each data file it stores the row count, the partition it belongs to, and the min/max of each column inside it. At the bottom sit the immutable Parquet data files. Crucially, the stats that took 26 minutes to gather by opening 1.58M footers are now precomputed and sitting in the manifest — the engine reads a few tens of megabytes of metadata once and prunes files in memory, never touching the bucket's LIST at all.

Why this instantly fixes planning: the query "region X, day D" reads the current metadata, keeps only manifest entries whose partition is day=D (that alone drops 1.58M files to ~1,440 — partition pruning, Lesson 29), then keeps only files whose min(region) ≤ X ≤ max(region) (file skipping by stats, Lesson 12's index idea applied to files). Planning goes from reading 1.58M footers to filtering one manifest — minutes to well under a second — and the answer is a precise list of the handful of files worth scanning. No LIST, no footer stampede.

The commit: turn a many-file change into a one-pointer swap

Writing is where the magic pays off. To append, compact, or edit, a writer (1) writes new immutable data files, (2) writes a new manifest + new metadata object that lists the resulting file set, and (3) performs a single compare-and-swap on the catalog pointer: "if the current metadata is still 042, make it 043." Steps 1 and 2 touch object storage but change nothing visible — the table is still whatever the pointer says. Only step 3 publishes, and it is one atomic operation on one tiny object (Lesson 6's compare-and-set, Lesson 22's fencing idea). A reader sees either the whole old snapshot or the whole new one; the half-done middle state is unobservable because it was never pointed to. That is ACID atomicity and snapshot isolation, bought with a single CAS instead of a distributed transaction across a directory.

What falls out for free, all from "immutable files + a swapped pointer": Snapshot isolation — a reader pins 042 and finishes there even if a writer commits 043 mid-query. Time travel & rollback — old snapshots are kept, so "the table as of last Tuesday" is just reading an old metadata pointer, and undoing a bad commit is pointing the catalog back one snapshot (Lesson 31's blue-green flip; the snapshot log is Lesson 38's event history for a table). Safe compaction — rewrite small files into big ones as a new snapshot and swap; readers never catch it mid-way, so the small-file fix that was a race in Move 1 is now routine. Schema evolution (Lesson 24) — the schema is metadata keyed by column ID, so adding or renaming a column is a metadata change over 11 TB, not a rewrite. Concurrent writers — two writers both CAS; one wins, the loser re-reads the winner's snapshot and retries its append on top (optimistic concurrency, Lesson 6). Crash safety — a writer that dies after step 1 leaves orphan data files that no snapshot points to: invisible, and swept later by garbage collection (Lesson 20's "unreferenced = harmless").

The trade you are buying into

A closed warehouse (Lesson 29) owns storage and compute together, so it can co-design them — proprietary file layouts, tightly-coupled indexes, no separate metadata to manage — and squeeze out peak query speed. The lakehouse deliberately gives that up. It puts data in open files on cheap object storage so any engine can read one copy (no lock-in, Lesson 58) and storage scales independently of compute. You pay for that openness in metadata-management complexity: manifests to keep small, snapshots to expire, files to compact — chores the closed warehouse hid inside itself. Name the trade plainly: openness & cheap shared storage & storage/compute separation vs peak query performance & the operational burden of managing metadata. The lakehouse is the bet that open + cheap + good-enough-fast beats closed + fast + locked-in — a bet that pays when many teams and engines share one large dataset.

The model in one line: keep data as immutable Parquet on cheap object storage; layer a metadata tree (catalog pointer → snapshot → manifest with per-file stats) that names the table exactly and precomputes pruning; commit any change — append, compact, schema edit — by writing new files and new metadata, then a single compare-and-swap on one pointer, which buys ACID atomicity, snapshot isolation, time travel, and safe compaction all at once; and pay for the openness in metadata upkeep.

Move 3 — Trace the paths

Three scenarios: a read that gets a consistent snapshot with fast pruning, a write that either commits atomically or safely loses a race, and a bad batch undone instantly by time travel.

Path A — a read: fast planning + snapshot isolation

  Query: "revenue for region=EU on day=2026-08-01."

    1. read catalog pointer  -> current table is metadata_042
    2. read metadata_042     -> schema + list of manifests   (PIN this snapshot)
    3. scan the manifest, in memory:
         keep entries where partition == day=2026-08-01
             1,580,000 files  ->  ~1,440 files   (partition pruning, L29)
         keep entries where min(region) <= EU <= max(region)
             ~1,440 files     ->  ~     60 files   (file skipping by stats, L12)
    4. read ONLY the `region` + `amount` columns of those ~60 Parquet files
       (columnar projection, L29), sum, done.

    Meanwhile a compaction job COMMITS metadata_043 at step 3.
       -> our query is pinned to 042 and finishes on a consistent set.
          It never sees a half-swapped table.  (snapshot isolation)

    Planning cost: read one manifest (~tens of MB) once.
       NOT 1,580 LIST calls + 1.58M footers (~26 min).  Sub-second.

Path B — a write: atomic commit, or a safe retry under a race

  Nightly compaction: replace day=2026-08-01's 1,440 small files
  (7 MB each) with ~78 big files (128 MB each).

    1. write 78 new Parquet files            (nothing visible yet)
    2. write manifest + metadata_043 listing
       {all other days' files} + {the 78 new} - {the 1,440 old}
    3. CAS the catalog:  if current == 042 -> set 043    ATOMIC
         success -> table is now 78 files for that day, readers switch cleanly
         the 1,440 old files are now unreferenced -> GC later (L20)

  Concurrent append races the compaction:
    an ingest writer also builds metadata_043' from base 042 and CASes.
       first CAS wins (say compaction -> 043).
       the loser's CAS fails (current is no longer 042).
       -> loser RE-READS 043, re-applies its append on top -> 044, CAS again.
          (optimistic concurrency, L06 -- no lock held, just retry)

  Crash after step 1 (files written, pointer never swapped):
    -> orphan files no snapshot references. Invisible. Swept by GC.
       The table is exactly what the last successful pointer says. (L20)

Path C — time travel: undo a bad batch in one move

  A buggy ETL job commits metadata_045 that double-counts a region.
  The dashboards are now wrong. In a raw directory this is a disaster
  (which of the millions of files are the bad ones?). Here:

    snapshots are immutable and kept:  ... 043  044  [045 BAD]
    ROLLBACK = CAS the catalog pointer back to 044.   (instant, no data moved)
       -> the table is correct again in one atomic step.

    AUDIT / compare = query "AS OF snapshot 044" vs "AS OF 045"
       to see exactly what the bad job changed. (L38 event history)

    The catch (L56): time travel KEEPS old data. A user's deleted row
    still lives in snapshot 043 until snapshots are EXPIRED and the
    unreferenced files GC'd. "Right to be forgotten" forces expiry,
    which is the same operation that reclaims storage.

Path A is the payoff for readers: the precomputed stats turn 26 minutes of planning into a sub-second manifest scan, and the pinned snapshot means a concurrent writer can't corrupt the answer. Path B is the payoff for writers: a many-file change becomes one CAS, so compaction and appends are atomic and crash-safe, and two writers racing just means one retries — no lock, no distributed transaction. Path C is the payoff for operators: because history is immutable and kept, undoing a bad commit is instant and auditing is free — with the honest Lesson 56 caveat that "keep everything" fights "delete on request," and expiring snapshots is where those two meet.

Move 4 — Find the first bottleneck: we moved the hard part into the metadata

The lakehouse didn't make the difficulty vanish; it relocated it. The bottleneck is no longer "LIST the bucket" — it's the metadata layer itself, and the single point where every commit lines up.

The first bottleneck — metadata grows, and reading it to plan a query gets slow. Before compaction, 1.58M files means a manifest with 1.58M entries. At even a few hundred bytes of stats per entry that's hundreds of megabytes of metadata the engine must read just to plan — you traded "26 minutes of footers" for "read a huge manifest," better but not free. And every commit writes a new metadata generation, so thousands of snapshots pile up too. The fix is the same tool that fixed the data: compaction, now applied to metadata and files together. Compact the 1,440 files/day down to ~78 → the file count drops ~18× (1.58M → ~86,000), and the manifest shrinks with it (hundreds of MB → tens of MB). Expire old snapshots so the history you keep is bounded. Cache the manifest so repeat queries skip re-reading it. The metadata is a table in its own right, and it needs the same partition-and-prune, compact-and-expire hygiene as the data (Lesson 20's small-file problem, Lesson 29's over-partitioning trap, both reborn one level up).

The second wall — the commit is one serialization point per table. Every writer must CAS the same pointer, so all writes to a table funnel through one logical spot (Lesson 66's "one logical counter everyone contends on," wearing a table-format costume). Low write rates: fine. But point a thousand streaming tasks at one table, each committing per-second, and their CASes collide — the loser retries, the retries collide again, and you get a commit-contention storm (Lesson 7's retry storm at the metadata layer). The fixes echo the whole course: batch writes into fewer, larger commits (commit once a minute, not once a row — Lesson 9/47's "amortize the expensive operation"), which also produces bigger files and less metadata at the same time; and where truly independent, partition the write path so different partitions commit more independently. There is a floor, though: a single table has a single current-snapshot pointer, so a table's commit throughput is bounded by how fast you can serialize CASes on it — the same single-writer ceiling as Lesson 3's counter and Lesson 66's shared limit.

The third wall — the freshness/cost dial, exactly as in Lesson 29. Commit often and you get fresh data and tiny latency, but many small files and heavy metadata churn (slow reads, contended commits). Commit rarely and you get big files and light metadata (fast reads, cheap commits), but stale data. This is Lesson 29's batch-vs-stream tension in a new place: the commit interval is the master dial between ingestion freshness and read/scan efficiency. The lakehouse doesn't escape it — it just makes both ends safe (frequent commits don't corrupt readers; compaction to fix the small files doesn't either), so you can choose your point on the dial and move it later without changing the data model. And the deeper freshness limit is honest: a lakehouse commit is a batch publish, so end-to-end latency is one commit interval — for true sub-second streaming you still pair it with a speed layer (Lesson 29's lambda/kappa, Lesson 64's stream processor), and the lake is the durable, replayable log both read from.

So the honest design for our lakehouse is: store data as immutable Parquet on cheap object storage, keeping Lesson 29's columnar layout, partitioning, and star schema; layer an open table format's metadata tree (catalog pointer → snapshot → manifest with per-file stats) so planning is a sub-second manifest scan with partition pruning and file skipping (Lesson 12/29), not a LIST-and-footer stampede; commit every change — append, compaction, schema edit — by writing new files and new metadata then a single compare-and-swap, buying ACID atomicity, snapshot isolation, time travel, and safe compaction from one atomic pointer (Lesson 6/14/20); handle concurrent writers with optimistic retry (Lesson 6) and batch commits to tame the single serialization point (Lesson 3/66); run compaction and snapshot expiry as ongoing hygiene so metadata and files stay small (Lesson 20/29), remembering that expiry is also what finally deletes time-travel history (Lesson 56); and pick the commit interval as the freshness-vs-cost dial (Lesson 29), pairing with a speed layer (Lesson 64) when sub-second freshness is required. Every choice names its price: openness costs metadata upkeep; the atomic pointer costs a single serialization point; frequent commits cost small files and contention; kept history costs storage and a deletion headache.

The deepest point: the lakehouse is nothing but the "rename, don't mutate" trick (Lesson 14) scaled up to an entire table. A warehouse gets its guarantees by owning everything; a lake gives up ownership for openness and cheapness and, in doing so, loses the guarantees. The open table format buys them back without re-closing the system, by adding one indirection — a pointer to an immutable, precomputed description of which immutable files are the table right now — and making every change a swap of that one pointer. Atomicity over N files reduced to atomicity over 1 pointer; that single reduction is the whole idea, and every feature (snapshots, time travel, safe compaction, schema evolution, optimistic concurrency) is a corollary of it. The standing tension, from Lesson 29's closed warehouse to here: openness & cheap shared storage vs query performance & metadata-management complexity.

The four traps

  • Trap 1 — treating a directory of files as a table. With no atomic multi-file swap, a reader can catch a writer mid-update and get a silently wrong answer, and just planning a query means LISTing the bucket and opening millions of footers (~26 min). You need a metadata layer that names the table exactly and commits atomically.
  • Trap 2 — committing too often (or per-row). Every commit writes a new metadata generation and tiny files; per-second commits from many writers create a small-file pile and a commit-contention storm (L7/66). Batch into fewer, larger commits; compact continuously.
  • Trap 3 — never compacting or expiring. Metadata and snapshots grow unbounded; planning slows (huge manifests), storage bloats, and old data lingers. Compaction and snapshot expiry are not optional chores — they're what keeps the lakehouse fast, and expiry is what actually honors a deletion request (L56).
  • Trap 4 — expecting a warehouse's peak speed and a lake's zero management. The lakehouse trades some peak performance and adds metadata upkeep in exchange for openness, cheap storage, and storage/compute separation. If one engine owns the data forever and speed is everything, a closed warehouse may still win; the lakehouse's bet is that openness across many engines and teams is worth the management.

Where we landed

We took Lesson 29's 11 TB orders warehouse and rebuilt it on open files on cheap object storage — readable by any engine, owned by no vendor — then fixed the quiet catastrophe that comes with it: a directory of files is not a table. Estimate showed the cost of pretending it is: planning one query means LISTing 1.58M keys and opening every footer (~26 minutes before the scan starts), and any change across files is a race that shows readers half-done, silently-wrong answers. Model added the fix — a thin metadata layer (catalog pointer → snapshot → manifest with per-file stats) that names the table exactly and precomputes pruning, committed by a single compare-and-swap on one pointer — and named the one idea it all rests on: reduce an atomic change over many immutable files to an atomic swap of one tiny pointer (Lesson 14's rename-don't-mutate, scaled to a table). Tracing showed a read pruned to sub-second under snapshot isolation, a write committed atomically or safely retried under a race, and a bad batch undone instantly by pointing at yesterday's snapshot. The first bottleneck was that the hard part didn't vanish, it moved: metadata grows and needs its own compaction and expiry; the commit is one serialization point per table (Lesson 66's shared counter again); and the commit interval is Lesson 29's freshness-vs-cost dial in a new place — all now safe to tune because the format made every change atomic. Every dial named its trade. The standing tension, straight from Lesson 29: openness & cheap shared storage vs query performance & metadata-management complexity.
