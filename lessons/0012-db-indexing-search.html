Indexing & Search: How a Database Finds One Row in 100 Million

Every lesson so far has decided where data lives — one counter, many shards, replicas across zones. This one is about finding it again. We take ONE concrete table: 100 million orders sitting on disk. We ask it three questions — "give me order #84,213,905", "give me this customer's orders", and "find me the blue running shoes" — and watch the same table answer the first in under a millisecond, the second with one extra hop, and the third only once we bolt on a completely different structure. Along the way we build a B-tree from page size and arithmetic, build an inverted index for text, and then turn the whole thing around: we find the exact query where adding an index makes things slower, and name the trade-off every index silently charges you.

The one system we'll trace

A table called orders. 100 million rows. Each row is about 200 bytes (an id, a customer id, a timestamp, an amount, a short text description of the product). The rows live on disk in the order they were inserted — we'll call that pile the heap. Here is the whole shape on one screen: the raw heap, plus the two helper structures this lesson builds.

  ONE orders TABLE (100,000,000 rows) — THREE WAYS TO FIND A ROW

  THE HEAP  (rows on disk, in insert order)          Q: find order #84,213,905
  ┌─────────────────────────────────────────────┐    └─ scan all 100M rows ...... 40 s   ✗
  │ row · row · row · row · row · row · ... 100M │
  └─────────────────────────────────────────────┘

  B-TREE INDEX on order_id  (sorted, fan-out ~500)     └─ 3 page hops ............ 0.4 ms  ✓
            [ root ]                                       point lookups AND ranges
          /    |    \
      [ ··· ][ ··· ][ ··· ]   ← internal nodes (separators only)
        / | \   ...
     [ leaf → row pointer ] ........... 125M slots reachable in 3 levels

  INVERTED INDEX on the product text                   Q: find "blue running shoes"
     "blue"  → [ 12, 88, 207, ... 200,000 docs ]        └─ intersect two postings
     "run"   → [ 88, 91, 207, ... 120,000 docs ]           lists, not 10M scans .. fast ✓
     "shoe"  → [ 88, 207, 404, ...  50,000 docs ]
              AND = ids in ALL THREE = { 88, 207, ... }

An index is a second, sorted copy of one column (plus a pointer back to the row), kept in a shape you can binary-search. The table answers "where is everything"; the index answers "where is this" without reading everything. That's the whole idea — the rest of this lesson is making "without reading everything" concrete enough to predict in milliseconds.

Words we'll earn before we lean on them

  • Heap — the rows themselves, stored on disk roughly in insert order. No search help on its own.
  • Full table scan — reading every row to find the ones you want. Always correct, often far too slow.
  • Page (block) — the fixed-size chunk a database reads from disk at once. We'll use 8 KB, a common default.
  • Index — a sorted auxiliary structure mapping a key to the location of its row(s). Speeds reads, costs writes + space.
  • B-tree — the balanced, high-fan-out tree almost every relational index uses. "Balanced" = every leaf is the same depth, so every lookup costs the same.
  • Fan-out — how many children one tree node points to. Big fan-out → shallow tree → few disk reads.
  • Selectivity — what fraction of the table a query keeps. A query that returns 5 rows is highly selective; one that returns half the table is not.
  • Inverted index — for text: a map from each word to the sorted list of documents that contain it (a postings list).
  • Write amplification — one logical write turning into many physical writes, because every index also has to be updated.

Move 1 — Estimate: the scan we can't afford

Before reaching for an index, prove we need one. The honest baseline for "find order #84,213,905" with no index is: read the whole heap and check each row. Let's price that.

Worked: the cost of a full table scan.

• Table size: 100,000,000 rows × 200 bytes = 20,000,000,000 bytes = 20 GB.
• A fast SSD streams sequential data at roughly 500 MB/s.
• Time to read it all: 20,000 MB ÷ 500 MB/s = 40 seconds.

Forty seconds, for one lookup, on every query that filters by something the heap isn't sorted on. At even 100 such queries per second you'd need 4,000 seconds of disk time per second — impossible by a factor of 4,000. The scan isn't slow because the disk is slow; it's slow because we're reading 100 million rows to return 1. The waste is the 99,999,999 we touched for nothing.

Now the same lookup with a B-tree index on order_id (we'll build the structure in Move 2). A lookup walks from the root down to a leaf — a handful of page reads — instead of scanning everything.

Worked: the cost with an index. A B-tree on order_id for 100M rows is 3 levels deep (proven next). Finding the row reads 3 pages to reach the leaf, then 1 page to fetch the row from the heap = 4 page reads. A random SSD read is about 0.1 ms. Total ≈ 4 × 0.1 ms = 0.4 ms — and the top two levels are tiny (a few MB) so they almost always sit in RAM, often making it just one real disk read. Either way: 40 s → ~0.4 ms, a ~100,000× speed-up, because we read 4 pages instead of 2.5 million.

Name the first trade-off: an index is not free speed — it's read speed bought with write cost and storage. The sorted copy has to be kept sorted on every insert, update, and delete, and it occupies real disk. We'll cash that bill in Move 4. The rule of the whole lesson: an index trades cheaper reads for more expensive writes — so it pays off exactly when you read a column far more often than you write it.

Move 2 — Model: build the B-tree from arithmetic

Why is a 100-million-row index only 3 levels deep? Because each node is a whole 8 KB page, and a page holds a lot of keys. "Few levels" falls straight out of the page size — let's compute the fan-out.

Worked: fan-out, then depth (the Base62-style walk-through).

• One node = one page = 8 KB = 8,192 bytes.
• One entry inside a node = a key + a pointer. For an 8-byte order_id plus a ~6–8 byte pointer, call it ~16 bytes per entry.
• Entries per node (the fan-out): 8,192 ÷ 16 ≈ 512. Round down to ~500 for overhead.

Now stack the levels, each multiplying reach by ~500:

Level 1 (root) ....... 500 children
Level 2 .............. 500 × 500  = 250,000
Level 3 (leaves) ..... 500³      = 125,000,000 slots

125 million > 100 million, so 3 levels index the whole table. Going from 100M rows to 1 billion rows? 500⁴ = 62,500,000,000 — still only 4 levels. That's the magic of high fan-out: the tree's depth barely moves as the table explodes, so lookup cost stays nearly flat. Formally the depth is log₅₀₀(rows), and a logarithm with base 500 grows very slowly.

Two properties make the B-tree the default index almost everywhere, and both are trade-offs worth naming:

  • It stays balanced. When a leaf fills up it splits in two and pushes a separator up; the tree grows at the root, never lopsided. Cost: that occasional split is extra write work (Move 4). Benefit: every lookup is the same 3–4 reads, no slow cases.
  • Its leaves are sorted and linked. Because keys sit in order, the B-tree answers not just "= this id" but "between these two dates" and "give me these in sorted order" — just find the start, then walk the linked leaves. This is the one thing to remember when choosing index type:
Index typeAnswersCan't doTrade-off
B-tree=, < >, ranges, ORDER BY, prefix LIKE 'abc%'nothing big — it's the safe default~3–4 reads; pays write cost on splits
Hash= only, in ~1 readany range or sort (hashing destroys order)fastest equality, useless for > / ORDER BY
Inverted"which docs contain this word"ranges, exact-row lookupsgreat for text; expensive to keep fresh

A hash index is tempting because = in one read beats = in three. But hashing throws away order — Lesson 03's hash-vs-range sharding trade-off, now inside a single table. The moment a query says BETWEEN or ORDER BY, the hash index is dead weight and the B-tree wins. That's why B-tree is the default and hash is the special case.

Move 3 — Trace the paths

Path A — point lookup by the primary key

SELECT * FROM orders WHERE order_id = 84213905. The primary-key index is a B-tree on order_id. Walk root → internal → leaf (3 reads); the leaf points at the row; fetch it (1 read). ~0.4 ms, exactly Move 1's number. Done.

Path B — a secondary index, and the extra hop

Now SELECT * FROM orders WHERE customer_id = 5567. The heap isn't sorted by customer, and neither is the primary-key tree. So we build a second B-tree, on customer_id — a "secondary index." But notice what its leaves can store: not the row, just a pointer to where the row lives (its primary key or heap location). So a secondary-index lookup is two lookups:

  SECONDARY-INDEX LOOKUP = TWO HOPS (the "bookmark lookup")

  WHERE customer_id = 5567
     │
     ├─ 1) walk the customer_id B-tree ......... 3 reads → finds order_ids [771, 9930, 84213905]
     │
     └─ 2) for EACH match, look up the row ..... 3 reads each in the primary tree (or 1 heap read)
                                                  └─ this second hop is the hidden cost

Worked: when the second hop bites — and the fix. If customer 5567 has 3 orders, that's 3 reads to find them + ~3 reads each to fetch them ≈ 12 reads, still ~1 ms. Fine. But say all you needed was the total: SELECT amount FROM orders WHERE customer_id = 5567. You still pay the second hop just to read one number that could have lived in the index. The fix is a covering index — include amount in the index itself: INDEX (customer_id, amount). Now the query is "index-only": the answer is in the leaf, the heap is never touched, and the second hop vanishes. Trade-off: a covering index is bigger (it duplicates the extra column) in exchange for skipping the row fetch. Storage for latency — the same shape as Lesson 02's cache.

Path C — a range query (where B-tree earns its keep)

SELECT * FROM orders WHERE created_at BETWEEN '2026-06-01' AND '2026-06-07'. With a B-tree on created_at: descend once to the first row on June 1 (3 reads), then walk the linked leaves in order until you pass June 7. You read only the matching range, in sorted order, for free. A hash index cannot do this at all — its entries are scattered by the hash, so "everything between two dates" would mean scanning the whole index. This is the concrete payoff of "B-tree keeps order," and the reason you almost never pick hash.

Path D — "blue running shoes" (where B-trees give up)

Last question: find products whose description contains "blue running shoes". A B-tree on the description column sorts whole strings. It can find descriptions that start with "blue" (a prefix), but it is useless for a word in the middle — LIKE '%shoes%' can't use it, because the tree is sorted by first letter, not by "contains." To search text by word, you need the structure built for it: the inverted index.

Worked: build and query an inverted index. Take 10 million product descriptions. Building the index:

1. Tokenize each description into words: "Blue Running Shoes" → ["blue","running","shoes"].
2. Normalize: lowercase, and stem to root forms so "running" and "runs" both become run, "shoes" → shoe.
3. For each word, append this product's id to that word's postings list (kept sorted).

Result: "blue" → [12, 88, 207, … 200,000 ids], "run" → [88, 91, … 120,000], "shoe" → [88, 207, … 50,000]. To answer "blue running shoes" you take the intersection (AND) of the three sorted lists — ids that appear in all three. Because the lists are sorted, you merge them like three sorted decks, walking the shortest (50,000) and checking the others — on the order of a few hundred thousand comparisons, never reading a product row. Compare to the naive way: scan all 10,000,000 descriptions and substring-match each. The inverted index turns a 10M-row scan into a small merge of pre-built lists — and, as a bonus, it knows how often each word appears, which is exactly what ranking ("which match is most relevant") is built from.

Name the trade-off: the inverted index makes word-search cheap by paying up front — it pre-computes a list for every distinct word, and every time a description changes it must add/remove that id from each affected list. So it's fast, rich text search bought with build cost and update cost, and it's usually kept in a separate system (Elasticsearch, Lucene, a search service) that trails the source database by a second or two. That staleness is deliberate: search trades perfect freshness for query power. You wouldn't compute an account balance from it — but "blue running shoes," ranked by relevance, is exactly what it's for.

Move 4 — Find the next bottleneck: when an index makes things worse

Indexes feel like pure win, so the instinct is to index every column. That instinct is the bottleneck. Two concrete ways an index hurts:

The write tax (write amplification)

Worked: every index multiplies your writes. Suppose orders has the primary key plus 5 secondary indexes (customer, date, status, product, region). A single INSERT of one order now writes the heap row + 5 index entries = 6 physical writes, and any of those 5 B-trees might have to split a full page, adding more. So your "one insert" costs roughly 6× the disk work, and your write throughput drops by about the same factor. Trade-off named: each index speeds the reads that use it and slows every write to the table. On a write-heavy table (Lesson 03's 40,000 writes/sec), a careless 6th index can be the thing that tips you over the throughput wall.

The selectivity trap (an index the planner refuses)

An index only helps if it lets you skip most of the table. Put one on a column that barely narrows anything and it can be slower than no index at all — because the random row-fetches cost more than a clean sequential scan.

Worked: the break-even point. A full scan of our table is 40 s (Move 1). A secondary-index lookup pays one random read (~0.1 ms) per matched row to fetch it from the heap. So index-with-fetches beats the scan only while:

matched_rows × 0.1 ms < 40 s  →  matched_rows < 400,000

That's 400,000 of 100,000,000 = ~0.4% of the table. Index a high-cardinality column like customer_id (each value matches a handful of rows, well under 0.4%) and the index wins enormously. Index a low-cardinality column like status where status='shipped' matches 50,000,000 rows — and using the index means 50M random reads ≈ 5,000 s, 125× slower than just scanning the heap in 40 s. A good query planner spots this from its statistics and ignores the index, scanning instead. So the index you built costs write tax and storage and is never even used. Trade-off: an index pays off in proportion to its selectivity — on a column with few distinct values it's all cost and no benefit.

So "find the first bottleneck" here flips the usual direction: the bottleneck isn't a missing index, it's the wrong ones. The discipline is to index the columns your real queries filter and sort on, make them cover when a hot query needs just a few columns, and delete indexes nothing uses — each one is a standing tax on every write.

Where we landed

We took one 100-million-row orders table and asked it three questions. Estimate priced the no-index baseline — a 20 GB heap scanned at 500 MB/s is 40 s per lookup, because we read 100M rows to return 1 — and an index cuts it to ~0.4 ms. Model built the B-tree straight from page size: 8 KB pages ÷ 16-byte entries ≈ 500 fan-out, so 500³ = 125M > 100M means just 3 levels, and a logarithm base 500 keeps depth nearly flat as the table grows — plus the leaves stay sorted, which is why B-tree (not hash) is the default. Tracing the paths walked a point lookup (~0.4 ms), a secondary index and its hidden second hop (fixed by a covering index — storage for latency), a range query where ordered leaves shine, and full-text search where B-trees give up and the inverted index turns a 10M-row scan into a small merge of postings lists. The next bottleneck reversed the lesson: indexes aren't free, so too many or the wrong ones hurt — a 6th index makes one insert 6 physical writes, and a low-selectivity index on status is 125× slower than a scan and gets ignored anyway. The thread: an index is a bet that a column will be read far more than written — right bets buy 100,000× reads, wrong bets are pure tax.
