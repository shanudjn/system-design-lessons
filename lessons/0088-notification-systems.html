Notification Systems End to End: One "Your Order Shipped" Across Four Channels

Lesson 87's experiment said "ship it," so now the system has something to tell a real person: your order shipped. That sounds like one line of code — call the SMS API. It isn't. The same event might reach Alice by push, email, SMS, or in-app, and each has a different cost, speed, and annoyance. She might have turned some of them off. The event might arrive twice (the upstream pipeline is at-least-once, L68). It might land at 3 a.m. her time. She might already have gotten five notifications this hour. And a sent notification, unlike a database row, can't be un-sent — you can't un-ring a phone. We take one concrete event ("order.shipped" for user U-8842, Alice) on one concrete marketplace (5M DAU, from L86/L87) and trace it end to end. We'll estimate the volume and — the number that reshapes the whole design — the cost per channel, where one SMS campaign costs 75× an email one. We'll model the pipeline: preference & eligibility, dedup (L73), inbox rate limiting (L08), quiet hours & digests, template rendering, and per-channel delivery with retries & a DLQ (L09/L68). We'll trace three paths — the happy send, a duplicate event, and a 3 a.m. promo that gets held and batched. And we'll find the first bottleneck, which is not throughput at all: it's the user's standing permission to be reached — their notifications-on setting and your sender reputation with the providers — both destroyed by over-sending and nearly impossible to win back. The trade under all of it: reach & timeliness vs user annoyance & cost.

The one system we'll build

The marketplace from L86/L87: 5 million daily active users. Many things want to tell a user something — an order update, a price drop, a security alert, a promo. One notification service owns all of it. We follow a single event:

  • The event: order.shipped for user U-8842 ("Alice") — emitted by the orders pipeline (L68) the moment a package leaves the warehouse.
  • The channels: push (a phone banner via APNs/FCM), email, SMS (a text), and in-app (a bell icon inside the app). Each differs in cost, speed, reach, and how much it annoys.
  • The job: get the right message to Alice on the right channel, exactly once, at a decent hour, without training her to turn notifications off.

Here is the whole pipeline on one page. One event fans out, but every stage can drop it (already sent, not wanted, over the limit, wrong hour) — a notification system spends most of its effort deciding not to send:

        order.shipped {user:U-8842, event_id:E-551}      (at-least-once, L68)
                          │
                          ▼
     ┌─────────────────────────────────────────────────┐
     │ 1. DEDUP (L73)   key = user+event+type+channel    │  seen before? drop
     │ 2. PREFERENCE    does Alice want this, this way?   │  opted out?  drop
     ├─────────────────────────────────────────────────┤
     │ 3. ROUTE         pick channel(s) + fallback ladder │  push→email→SMS
     │ 4. RATE LIMIT (L08)  per-user inbox token bucket   │  over cap?  digest
     │ 5. QUIET HOURS   is it night in Alice's timezone?  │  night?     hold
     ├─────────────────────────────────────────────────┤
     │ 6. RENDER        template + data → per-channel msg │  localize, trim
     │ 7. DELIVER (L09/68)  provider send + retry + DLQ    │  bounce? suppress
     └───────────────────┬───────────────────────────────┘
                         ▼
             delivery receipt · bounce · unsubscribe
                         │  feeds back into
                         ▼
             preferences · suppression list · sender reputation

The one idea the whole lesson turns on: a send is an irreversible side effect on a scarce, non-renewable resource — the user's attention and your permission to reach them. A database write can be corrected; a 3 a.m. text cannot be recalled, and the opt-out it triggers is close to permanent. So the system is not built to send fast — it's built to decide, carefully, whether to send at all, and every stage above is a filter that protects that permission.

Words we'll earn before we lean on them

  • Channel — a way to reach a user: push, email, SMS, in-app. Differs in cost, latency, reach, and intrusiveness.
  • Push token — an id from Apple (APNs) or Google (FCM) that lets you send a banner to one installed app. No token (app deleted / never installed) = no push.
  • Transactional vs marketing — transactional = a message the user's own action earned (order update, receipt, 2FA); marketing = something you want to send them (promos). Different consent rules and different urgency.
  • Preference / opt-out — the user's stored choice of what to receive on which channel. Legally binding for marketing.
  • Dedup (idempotency) — suppressing a second notification for the same logical event (L13/L73), because upstream delivery is at-least-once (L68).
  • Fan-out — one event turning into many sends (across channels and, for a campaign, across users).
  • Fallback ladder — try the cheap/preferred channel first; if it can't deliver, fall to the next (push → email → SMS).
  • Inbox rate limit — a per-user cap on how many notifications reach them in a window (L08 token bucket), so no single user is flooded.
  • Digest / batching — rolling several held notifications into one summary ("3 items back in stock") instead of sending each.
  • Quiet hours — a per-user window (their night) when non-urgent notifications are held, not sent.
  • Provider — the downstream service that actually delivers: APNs/FCM (push), SES/SendGrid (email), Twilio (SMS). Each has its own rate limits and its own view of your reputation.
  • Bounce (hard/soft) — a failed email: hard = address doesn't exist (suppress forever); soft = temporary (mailbox full → retry later).
  • Suppression list — addresses/tokens you must never send to again (unsubscribed, hard-bounced, complained).
  • Sender reputation — the providers' trust score in you, driven by your bounce and spam-complaint rates. Low reputation = your messages go to spam or get blocked, for every user.
  • DLQ (dead-letter queue) — where a message goes after retries are exhausted or the failure is permanent (L09/L68).

Move 1 — Estimate: the volume is easy; the cost is the whole story

Two numbers decide the design. The first — how many notifications per second — turns out to be modest and handled by a queue. The second — what each channel costs — is where the real design pressure comes from.

Volume. Transactional traffic is tied to orders, not to page views:

  2,000,000 orders/day × 3 lifecycle events (placed, shipped, delivered)
     = 6,000,000 transactional notifications/day
     = 6,000,000 / 86,400 s  ≈  70 per second average
     evening peak ~4×          ≈  300 per second

  a MARKETING campaign is a different beast — a burst, not a stream:
     one flash-sale blast to 4,000,000 eligible users, "send now"
     = 4,000,000 sends dropped into the queue in one instant

The steady stream is small (~300/s peak); the campaign burst (4M at once) is 13,000× larger for a few minutes. This is exactly L09's shape: a queue absorbs the burst and workers drain it at a controlled rate, with a priority lane so a marketing blast never delays a password-reset or an "order shipped." Trade: buffering adds a little latency to campaigns to protect the latency of the messages that matter.

Cost — the number that reshapes everything. The four channels are not interchangeable; they differ by ~100× in price and ~1000× in throughput:

  channel   $ / message   4M-user campaign      throughput / notes
  ───────   ───────────   ────────────────      ──────────────────
  push       ~$0          ~$0,  ~instant        free, needs an installed app + token
  email      ~$0.0001     4M×0.0001 = $400      ~5,000/s → drains in ~13 min
  SMS        ~$0.0075     4M×0.0075 = $30,000   ~100/s  → 4M/100 = 11 HOURS
  in-app     ~$0          ~$0                   only seen when app is opened

  same campaign, two channels:  email $400   vs   SMS $30,000   → 75×

SMS costs 75× email and delivers 50× slower, so it can never be your bulk channel — it is a scalpel for the few messages that must arrive. This is what forces the fallback ladder: prefer push (free, instant) → then email (cheap, rich) → and reach for SMS only for critical messages when there's no push token. Trade named for the first time: reach vs cost — SMS reaches almost anyone (no app needed) and is read within minutes, but at a price and a throughput ceiling that make it unusable at scale.

Why not just push everything to every channel and let the user sort it out? Because the fan-out multiplies the two things you're trying to conserve. Four channels means 4× the cost (and SMS's cost is real money), and — worse — it means Alice gets buzzed four times for one shipped package. Do that a few times and she turns notifications off. Now you've lost the free, instant channel (push) forever and are left paying for SMS or reaching no one. The abundance of channels is a trap: every extra send spends a resource that doesn't refill.

Move 2 — Model: the pipeline that mostly decides NOT to send

Stage 1 — dedup: the send you can't take back

The event comes off an at-least-once pipeline (L68), so "order.shipped E-551" can arrive twice. For a database write, a duplicate is harmless (L13 — write the same row twice). For a notification, a duplicate is a second buzz you can never recall. So dedup happens before the send, with an atomic claim (L13's unique-key trick):

  key = hash(user_id + ":" + event_id + ":" + type + ":" + channel)
        e.g. "U-8842:E-551:order.shipped:push"

  claim(key) in a dedup store with a TTL:      (atomic INSERT-if-absent)
     · first arrival  → row created → PROCEED to send
     · second arrival → key exists  → DROP (already handled)

  the claim must be ATOMIC (L06/L13 check-then-act race): two workers
  processing the duplicate at once must not BOTH see "absent" and send.

Because a send is irreversible, dedup is a correctness requirement, not an optimization — and the check must be atomic or a concurrent redelivery double-buzzes. This is L13's "exactly-once effect on at-least-once delivery" applied to a side effect that leaves the building. Trade: the dedup store needs a TTL long enough to outlive redelivery (hours) but not forever (storage) — the same TTL trap as L13: forget too soon and a late redelivery double-sends.

Stage 2 — preference & routing: does she want it, and how?

Before choosing a channel, check what Alice has allowed. Preferences are per-user, per-category, per-channel — and for marketing they're legally binding:

  Alice's prefs:   order updates → push ON, email ON,  SMS OFF
                   promotions    → push OFF, email ON,  SMS OFF
                   security      → all channels ON  (can't fully disable)

  route(order.shipped, Alice):
     category = "order updates"  → allowed on push + email
     fallback ladder: try PUSH first (free, instant, and she has a token)
        push fails / no token → fall to EMAIL
        (SMS is OFF for this category → never used here)

Routing is preference ∩ fallback ladder: send on the cheapest allowed channel that can actually deliver, and only climb the ladder on failure. Security messages are the exception — a fraud alert can't be silenced, because the user's safety outranks their annoyance. Trade: granular preferences (per-category, per-channel) respect the user and lift engagement, but every extra knob is one more thing to store, honor everywhere, and get right — silence where they asked for silence is a promise you can't break.

Stage 3 — inbox rate limiting & digests: protecting attention

Even wanted notifications, sent too often, become noise. A per-user token bucket (L08) caps the flow; overflow isn't dropped — it's batched into a digest:

  per-user bucket:  capacity = 3 (burst),  refill = 1 token / 4 h
     → sustained ceiling ~6 notifications/day for non-urgent traffic

  4 "back in stock" alerts fire for Alice in 10 minutes:
     alert 1,2,3 → take a token each → SENT   (bucket now empty)
     alert 4     → no token → HELD → rolled into tonight's digest:
                   "3 items you follow are back in stock"  (one message)

  PRIORITY bypasses the bucket:
     critical (2FA, fraud)      → always immediate, never batched
     transactional (shipped)    → bypass the cap (low frequency, earned)
     marketing / social         → fully subject to the bucket + digest

The scarce thing being rationed isn't bandwidth — it's the user's willingness to keep looking, so overflow is summarized, not discarded. A digest turns ten buzzes into one, preserving the information while spending one unit of attention. Trade: batching cuts annoyance and cost but adds delay and blurs individual events — right for "back in stock," wrong for "your driver is arriving," which is why priority tiers bypass the bucket.

Stage 4 — quiet hours & rendering: the right hour, the right words

A notification's value depends on when it lands. Quiet hours hold non-urgent messages through the user's night; rendering then turns the template + data into a per-channel message — where the SMS character budget hides a cost trap:

  QUIET HOURS (Alice is in IST, UTC+5:30; quiet 22:00–08:00 local):
     promo generated 02:00 local → HELD → released 08:00 (morning digest)
     order.shipped   02:00 local → transactional → sent (or held to 08:00
                     if not time-critical); a fraud alert → sent NOW.

  RENDER — SMS segment math (why words cost money):
     GSM-7 text:  160 chars / single segment, 153 / segment concatenated
     add ONE emoji → UCS-2:  70 / single, 67 / segment concatenated
     a 150-char message:  plain = 1 segment ;  with 1 emoji = ceil(150/67)
                          = 3 segments = 3× the per-message cost

Timezone-aware quiet hours convert a 3 a.m. intrusion into an 8 a.m. welcome — same message, opposite reception. And rendering isn't just string-fill: a single emoji can flip an SMS from one billable segment to three (1 → 3 = 3× cost), so the template that "looks nicer" can triple the bill on a 4M campaign. Trade: quiet hours and batching improve reception and cut cost but delay delivery; you tune the quiet window and the priority tiers to the message's real urgency.

Stage 5 — delivery: retries, bounces, and the DLQ

Finally the provider send (L09/L68). Failures split in two, and treating them the same is how you wreck your sender reputation:

  send to provider (APNs / SES / Twilio):
     accepted            → await delivery receipt
     TRANSIENT fail (429 rate-limited, 5xx, timeout)
                         → retry with backoff + jitter (L07), then DLQ
     PERMANENT fail (invalid token, hard bounce, unsubscribed)
                         → do NOT retry → suppress + DLQ

  bounce handling:
     HARD bounce (no such mailbox) → suppress address FOREVER
     SOFT bounce (mailbox full)    → retry later, give up after N

Retry the transient, suppress the permanent — retrying a hard bounce or a dead token just burns reputation and money for a message that can never arrive. The delivery receipts, bounces, and unsubscribes feed back into preferences and the suppression list, closing the loop. Trade: aggressive retries lift delivery of the recoverable few but, aimed at permanent failures, they raise your bounce rate — which the providers read as spam behavior and punish for all your users (next section).

Move 3 — Trace the paths: a clean send, a duplicate, a 3 a.m. promo

Path A — "your order shipped," the happy path

   order.shipped {U-8842, E-551} arrives
     │
     ▼  dedup: claim "U-8842:E-551:order.shipped:push" → new → PROCEED
     ▼  preference: order updates → push ON, she has a valid token
     ▼  route: PUSH first (free, instant)
     ▼  rate limit: transactional → bypasses the bucket
     ▼  quiet hours: 15:00 local → fine, send now
     ▼  render: "📦 Your order is on the way — arriving Thu. Track it →"
     ▼  deliver: APNs accepts → delivery receipt in ~1 s
   RESULT: one push, ~1 second, $0.  Email/SMS not used.

One event, one send. Every other channel was correctly not used — that restraint is the design working, not a gap in it. The whole path took no database of "who's online," just stateless preference and dedup checks.

Path B — the same event, delivered twice (dedup earns its keep)

   order.shipped {U-8842, E-551} arrives AGAIN  (at-least-once, L68)
     │
     ▼  dedup: claim "U-8842:E-551:order.shipped:push"
        → key already exists (from Path A) → DROP, do nothing
   RESULT: zero second buzz. Alice never knows the event doubled.

   contrast WITHOUT dedup:
     → a second identical push at, say, 15:00:04 → "why did it buzz twice?"
     → repeated across millions of events → the annoyance that ends in opt-out

The duplicate is invisible to the user precisely because dedup ran before the send — the one place you can still stop it. This is the exactly-once effect from L13, and it matters more here than for a DB write: a doubled row is a cleanup job, a doubled buzz is a withdrawal from the attention account you can't undo.

Path C — a 2 a.m. promo into a full inbox (hold, batch, ladder)

   promo "flash sale" targets Alice, generated 02:00 IST
     │
     ▼  dedup: new → proceed
     ▼  preference: promotions → push OFF, email ON  → channel = EMAIL
     ▼  rate limit: marketing → subject to bucket; bucket empty → HELD
     ▼  quiet hours: 02:00 local is inside 22:00–08:00 → HELD anyway
     │
     ▼  08:00 IST: release window opens; several held promos exist
     ▼  BATCH into one morning digest email:
        "Your flash sale + 2 items back in stock"   (one email, $0.0001)
     ▼  deliver: SES accepts; if it HARD-bounces → suppress, DLQ
   RESULT: zero night buzzes; one tidy morning email instead of four.

Non-urgent traffic is shaped by when and how much, not just whether — the same four messages become one well-timed digest. Two independent brakes both fired (quiet hours and the empty bucket), and the digest turned the overflow into a single spend of Alice's attention. Had this been a fraud alert, both brakes would have been bypassed — priority is what tells the pipeline which rules to skip.

Move 4 — Find the first bottleneck: the permission to be reached

The first bottleneck is not throughput — it's the standing permission to reach the user, held on two sides at once and non-renewable:

  the two scarce, coupled resources:

    USER SIDE          PROVIDER SIDE
    notifications ON   sender reputation (bounce + spam-complaint rate)
        │                   │
   over-send → annoy   over-send to unengaged → bounces + spam reports
        │                   │
        ▼                   ▼
   user disables push   Gmail routes you to SPAM / blocks you
   (free channel lost)  (for EVERY user, not just the annoyed one)

    both degrade with volume; both are slow or impossible to recover.

Every send is a withdrawal from two accounts that don't refill on demand — the user's tolerance and the providers' trust — and once either is overdrawn, no amount of throughput helps because you've lost the right to arrive. This reframes the system: it is not a delivery engine, it's a permission-conservation engine, which is why so much of it (preferences, dedup, rate limit, quiet hours, digests) exists to not send. Trade, stated plainly: reach & timeliness vs annoyance & cost — pushed too far toward reach, the channel dies and future reach goes to zero.

The second wall — out-of-order events tell a nonsense story. The pipeline is at-least-once and per-partition ordered at best (L09/L68), so lifecycle events can arrive out of order across partitions:

  intended:   placed → shipped → delivered
  arrives:    shipped (10:02)  then  placed (10:03, delayed retry)

  naive: send "shipped" then "your order was placed" → user confused
         ("it shipped before I placed it?")

  fix: make notifications STATE-AWARE, not event-blind:
     · carry a status version / sequence per order; a notification for an
       OLDER state than already-sent is suppressed (L35 logical order).
     · or collapse: only notify on the LATEST known state at send time.

A notification reflects a state, so send it against the newest known state, not blindly per event — or the user reads the story backwards. This is L35's causal-ordering problem wearing a UX hat. Trade: state-aware suppression needs you to track per-entity status (more state) but prevents the confusing, trust-eroding out-of-order buzz.

The third wall — the self-inflicted thundering herd. A campaign that fans out to millions "right now" hits your own app when everyone taps at once:

  send 4,000,000 pushes instantly → say 20% tap within 2 minutes:
     0.20 × 4,000,000 = 800,000 taps / 120 s  ≈ 6,700 req/s spike
     stacked on the steady 40k req/s fleet (L27) → toward the knee

  fix: STAGGER + JITTER the send (L02/L07 shape):
     spread 4M over 15 min → 4,000,000 / 900 s ≈ 4,400 sends/s
     → the tap spike flattens under the fleet's headroom

A notification is a request you send yourself later — fan it out all at once and you DDoS your own backend when the taps land. The fix is the familiar one: spread the sends over a window with jitter so the induced traffic is a plateau, not a spike (L27's latency knee, L28's goodput cliff, both reachable by a careless blast). Trade: staggering delays the last recipient by minutes but keeps the whole platform up for everyone — timeliness spent to protect availability.

So the honest picture: a notification system looks like "call the send API" and is really a machine for deciding not to send. Estimate showed the stream is small (~300/s peak, absorbed by a queue with a priority lane) but the cost is everything — SMS at 75× email and 50× slower forces a push → email → SMS fallback ladder. Model built the pipeline as a chain of filters: dedup before the irreversible send (L13/L73), preference-bound routing, an inbox token bucket with digest overflow (L08), timezone quiet hours, template rendering (where one emoji triples an SMS bill), and delivery with transient-retry / permanent-suppress and a DLQ (L09/L68). Tracing a clean push, an invisible duplicate, and a held-and-batched 2 a.m. promo showed the filters firing. The first bottleneck — the permission to be reached, held by both the user and the providers and refilled by neither — makes over-sending the cardinal sin; beneath it, out-of-order events demand state-aware sends (L35) and mass fan-out demands staggered, jittered delivery (L07/L27). The standing tension: reach & timeliness vs user annoyance & cost.

The deepest point: a sent notification is the rare system output you cannot roll back, spent on a resource that doesn't replenish — so the whole discipline is restraint. A queue can retry, a database can be corrected, a cache can be invalidated; a buzz at the wrong time, for the wrong reason, one time too many, is permanent, and it withdraws from an account (the user's attention, the providers' trust) that you cannot top up by trying harder. The genuinely new idea is small and sharp: most of a notification system's job is to decide, at every stage, that the right move is silence. The trade to carry: reach & timeliness vs user annoyance & cost.

The four traps

  • Trap 1 — send on every channel to be safe. Four buzzes for one event multiplies cost and annoyance and trains the user to disable notifications, losing the free channel forever. Pick the cheapest allowed channel that can deliver and climb the ladder only on failure.
  • Trap 2 — no dedup, "the queue is reliable." Upstream is at-least-once (L68), so events double; without an atomic dedup claim before the send, the duplicate becomes a second buzz you can never recall. Dedup is correctness, not optimization.
  • Trap 3 — retry every failure the same way. Retrying hard bounces and dead tokens raises your bounce rate, which providers read as spam and punish for all users. Retry only transient failures; suppress permanent ones immediately.
  • Trap 4 — blast the campaign all at once. A 4M instant fan-out spikes your own backend when the taps land and hammers provider rate limits. Stagger with jitter so the induced load is a plateau, not a cliff.

Where we landed

We asked how to deliver Lesson 87's shipped-it result to a real person — one "order shipped" across push, email, SMS, and in-app — without becoming noise. Estimate found the stream small (~300/s peak, queued with a priority lane, L09) but the cost decisive: SMS at 75× email and 50× slower forces the push → email → SMS fallback ladder. Model built the pipeline as filters that mostly say no: dedup before the irreversible send (L13/L73), preference-bound routing, an inbox token bucket with digest overflow (L08), timezone quiet hours, template rendering (one emoji → 3× SMS cost), and delivery with transient-retry/permanent-suppress + DLQ (L09/L68). Tracing a clean push, an invisible duplicate, and a held-and-batched 2 a.m. promo showed each filter fire.
