Design a URL Shortener

One small system, traced end to end. By the finish you'll own the four moves every system-design problem reuses: estimate, model, trace the paths, find the first bottleneck.

The whole system on one screen

A URL shortener does two things. It takes a long link and hands back a tiny one. And when someone visits the tiny one, it sends them to the long one. That's it. Here is the entire thing as a picture — keep it in your head for the rest of the lesson.

  WRITE PATH  (someone creates a short link)
  ┌────────┐   POST /shorten          ┌────────┐   INSERT row     ┌──────────┐
  │ Client │ ───────────────────────► │  App   │ ───────────────► │ Database │
  └────────┘   {long_url}             │ server │   get new id     │  (table) │
       ▲                              └────────┘ ◄─────────────── └──────────┘
       │   short.ly/15FTGg                 │  encode id → code
       └───────────────────────────────────┘

  READ PATH   (someone clicks the short link)   — happens ~100x more often
  ┌────────┐   GET /15FTGg            ┌────────┐   look up code    ┌──────────┐
  │ Client │ ───────────────────────► │  App   │ ───────────────► │ Database │
  └────────┘ ◄─────────────────────── │ server │ ◄─────────────── └──────────┘
              302 → long_url          └────────┘   return long_url

Two boxes (App, Database), two paths (write, read). Everything below is just making each arrow good enough to survive scale. The big idea of the lesson: the read path is ~100× hotter than the write path, and that imbalance decides the whole design.

Move 1 — Estimate before you design

Never design in a vacuum. Put rough numbers on it first. The numbers tell you what's hard. We'll invent a plausible scale and do back-of-the-envelope math — round, not exact.

Assume: 100 million new short links created per month.

Read:write ratio = 100:1 (links get clicked far more than created) → 10 billion redirects per month.

A month ≈ 30 × 24 × 3600 ≈ 2.6 million seconds.

Writes/sec ≈ 100M ÷ 2.6M ≈ ~38 writes/sec  tiny

Reads/sec ≈ 10B ÷ 2.6M ≈ ~3,800 reads/sec  this is the real load

Storage: ~100M/mo × 12 × 5 years ≈ 6 billion rows. At ~500 bytes/row ≈ ~3 TB over 5 years. One database can hold that.

Why this matters: the estimate already wrote half the design for you. Writes are trivial (38/sec — a laptop could do it). Storage is fine (3 TB fits). The only hard part is 3,800 reads/sec. So we'll spend our effort making the read path cheap, and barely think about writes.

Move 2 — The data model

What do we actually store? The smallest thing that works: a mapping from the short code to the long URL. One table.

ColumnTypeExampleNote
idbigint, auto-increment1000000000the primary key, counts up
short_codevarchar, unique15FTGgwhat appears in the URL
long_urltexthttps://example.com/very/long/path?x=1where we send the click
created_attimestamp2026-06-21for cleanup / analytics

Notice one quiet but load-bearing property: once a row is written, it never changes. A short code always points to the same long URL, forever. We say the mapping is immutable (write-once). Remember this — it's why caching will be almost free later.

Move 3 — How do we make the short code?

This is the one genuinely interesting design choice. We need a short, unique string. Two honest options:

Option A — Hash the URL

Run the long URL through a hash (e.g. MD5), take the first 6–7 characters.

Problem: two different URLs can hash to the same 6 characters — a collision. Now one code points to two links. You'd have to check the DB on every create and re-try on collision. Extra reads, ugly edge cases.

Option B — Counter + Base62 ✅

The database already gives every row a unique number: the auto-increment id. Just turn that number into a short string. No two rows share an id, so no collisions, ever.

This is the standard choice. Let's see exactly how the number becomes the code.

What is Base62, in one breath

Normal numbers are base 10: ten digits, 0–9. Base62 uses 62 symbols: 0–9, then a–z, then A–Z. More symbols per character means a big number squeezes into fewer characters. That's the whole trick — we're just writing the id in a denser alphabet.

The alphabet (index → symbol):

0–9 → '0'…'9'  ·  10–35 → 'a'…'z'  ·  36–61 → 'A'…'Z'

Worked example: encode id 1,000,000,000

We repeatedly divide by 62 and keep the remainders — same as how you'd convert to any base. Each remainder is one Base62 digit.

 1,000,000,000  ÷ 62  →  16,129,032  remainder  16   → symbol 'g'   (16 = a..g)
    16,129,032  ÷ 62  →     260,145   remainder  42   → symbol 'G'   (42-36=6 → G)
       260,145  ÷ 62  →       4,195   remainder  55   → symbol 'T'   (55-36=19 → T)
         4,195  ÷ 62  →          67   remainder  41   → symbol 'F'   (41-36=5 → F)
            67  ÷ 62  →           1   remainder   5   → symbol '5'
             1  ÷ 62  →           0   remainder   1   → symbol '1'

 Read the remainders bottom-to-top:   1  5  F  T  G  g   →   "15FTGg"

Check it (turn the code back into a number): 1·62⁵ + 5·62⁴ + 41·62³ + 55·62² + 42·62 + 16 = 1,000,000,000 ✓ — the encoding is reversible, so it's a clean 1-to-1 mapping. The billionth link gets a 6-character code.

How many links can 6 characters hold?

62⁶ = 56,800,235,584 ≈ 56.8 billion distinct codes. Our 5-year estimate was 6 billion rows. So 6 characters is comfortably enough — we'd still be on 6-char codes for decades. (7 chars = ~3.5 trillion, if we ever need it.)

The transferable lesson: when you need unique IDs, lean on a source that's already unique (the DB counter) and just re-encode it. Don't invent uniqueness with hashing when something upstream already guarantees it.

Move 4 — Trace the two paths

Write path: POST /shorten

1. Client sends   { long_url: "https://example.com/very/long/path?x=1" }
2. App inserts a row → DB assigns  id = 1,000,000,000
3. App encodes      base62(1,000,000,000) = "15FTGg"
4. App saves "15FTGg" into the row's short_code  (or computes it on read)
5. App returns      { short_url: "https://short.ly/15FTGg" }

~38 of these per second. One small database handles it without breaking a sweat. Done thinking about writes.

Read path: GET /15FTGg

1. Client requests   GET short.ly/15FTGg
2. App looks up       SELECT long_url WHERE short_code = '15FTGg'
3. App replies        302 Found,  Location: https://example.com/very/long/path?x=1
4. Browser follows the Location header → user lands on the real page

One sharp detail: 301 vs 302

RedirectWhat the browser doesTrade-off
301 PermanentCaches it. Future clicks skip your server entirely.Less load, but you lose per-click analytics and can't change the target.
302 Found (temp)Asks your server every time.More load, but you count every click and can change the destination later.

Most real shorteners pick 302 on purpose — counting clicks is the product. That's a choice to accept more load in exchange for data. Naming the trade-off out loud is what system design is.

Move 5 — Find the first bottleneck

Now turn up the load in your head. 3,800 redirects per second, each doing a database lookup. The database becomes the hot spot — every click pays for a disk-backed query, and reads dwarf writes 100:1. This is the first thing that breaks.

Fix: put a cache in front of the database — an in-memory key→value store (think Redis). On a read, check the cache first.

  READ PATH, with a cache in front
  ┌────────┐  GET /15FTGg   ┌────────┐   hit? ──► return from memory  (~microseconds)
  │ Client │ ─────────────► │  App   │ ──► CACHE
  └────────┘ ◄───302─────── └───┬────┘        │ miss
                                │             ▼
                                │        ┌──────────┐
                                └────────│ Database │  read once, then store in cache
                                         └──────────┘

Why a cache fits this problem so perfectly

Caches aren't free — they can serve stale data and they cost memory. But a URL shortener hits four green lights at once:

✅ Read-heavy — 100:1. Caching pays off exactly when reads dominate.

✅ Key→value shaped — short_code → long_url is literally what a cache stores.

✅ Immutable — the mapping never changes, so a cached value is never wrong. No cache-invalidation problem — the hardest part of caching simply doesn't exist here.

✅ Skewed access — a few links go viral. A small cache of the hottest codes serves the large majority of traffic (the 80/20 rule).

The transferable lesson: reach for a cache when data is read-heavy, key-shaped, and rarely-or-never changes. The immutability is the gift here — most real caching pain is deciding when to throw stale data away, and a write-once mapping means never.

Where we landed

From two boxes we reasoned our way to: estimate → one table → counter+Base62 codes → traced write/read paths → spotted the read bottleneck → added a cache, and justified it with four properties. You didn't memorize an answer; you derived it. Every future system reuses these same four moves.
