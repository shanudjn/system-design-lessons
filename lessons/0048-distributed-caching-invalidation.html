Distributed Caching & Invalidation: Keeping Many Caches Honest

Lesson 2 put a cache in front of one database and Lesson 14 pushed copies out to the world's edges. Both times the cache was easy in one specific way: we mostly worried about hits — how to hold the hot data so the slow origin is touched less. This lesson takes the same idea to the shape of a real backend — many app servers sharing one cache tier in front of a database whose data keeps changing — and there the hard problem is no longer the hit. It's coherence: a cache is a copy, and the instant the source of truth changes, every copy is a small lie. We'll take a product-catalog read path — 50,000 reads/second over 10 million products against a database that can safely serve only ~5,000 reads/second — and estimate why a single shared cache tier beats a private cache on every server (it deduplicates both the RAM and the thing you have to invalidate). We'll model the choices that decide freshness: cache-aside vs write-through vs write-behind, and the sharper fork inside each — on a write, do you delete the key or overwrite it? We'll trace a hit, a miss, a write, and the famous stale-repopulation race where a slow reader writes an old value back after a newer write. And we'll hit the wall that makes distributed caching hard: the moment you add a per-server near cache to cut latency, you have N copies again and a write must invalidate all of them — an invalidation fan-out that is best-effort, bounded by a TTL, and which turns a single hot key's invalidation into a stampede (Lesson 2's thundering herd, back again). The trade underneath all of it: freshness vs cache hit rate & load.

The one system we'll design

We run a product catalog. There are 10,000,000 products, each rendered blob is about 2 KB (name, price, stock, ratings summary), so the full working set is 10,000,000 × 2 KB ≈ 20 GB. The read path serves 50,000 reads/second at peak — product pages, search result hydration, "you might also like" panels. Behind it is one relational database (the orders/catalog store of Lessons 12/37) that, kept safely below its utilization knee (Lesson 27), can serve about 5,000 reads/second before latency climbs. And the catalog changes: prices, stock counts, and descriptions get edited at roughly 500 writes/second (a 100:1 read:write ratio). The read fleet is Lesson 27's 286 app servers. Every one of them needs the same product data, the data is 10× too much read traffic for the database, and it is mutable. That combination — shared, hot, and changing — is exactly where a cache stops being a speed trick and becomes a correctness problem.

A cache is a copy of the truth that lives closer and answers faster. In a single-server world that copy is easy to keep honest — one writer, one copy. At scale you have many readers, one shared copy (or worse, many private copies), and a source of truth that keeps moving underneath them. The whole discipline of distributed caching is deciding, on every write, how each copy learns it is now wrong — and living with the fact that it learns a little late. The source of truth is the database (Lessons 6/25): the one place a value is authoritative. Everything cached is derived from it and therefore, for some window, potentially stale.

Words we'll earn before we lean on them

  • Cache tier — a fleet of dedicated cache nodes (Redis/Memcached) sitting between the app servers and the database, holding hot values in RAM.
  • Source of truth — the authoritative store (the database) that a cache merely copies; when the two disagree, the source of truth is right by definition.
  • Cache coherence — the property that a read from any cache reflects the latest committed write (or is at least no more than a bounded amount of time stale).
  • Cache-aside (lazy loading) — the app checks the cache first; on a miss it reads the DB and populates the cache. On a write it changes the DB and invalidates the key. The default pattern (Lesson 2).
  • Write-through — a write updates the cache and the DB together, synchronously, so the cache is never behind the DB.
  • Write-behind (write-back) — a write updates the cache, acks immediately, and flushes to the DB asynchronously later.
  • Invalidation — telling a cache a key is now wrong, either by deleting it (next read recomputes) or overwriting it with the new value.
  • TTL (time to live) — an expiry stamped on a cached entry so it self-evicts after N seconds, capping how stale any copy can get even if nothing invalidates it (Lesson 14).
  • Near cache (L1) — a small cache inside each app server's process, in front of the shared tier (which becomes the L2), trading coherence for latency.
  • Stampede / thundering herd — many readers missing the same key at the same instant and all hammering the source of truth at once (Lesson 2).
  • Single-flight (request coalescing) — letting exactly one reader recompute a missing key while the others wait for and share its result.
  • Stale-while-revalidate (SWR) — serving the old value immediately while refreshing it in the background, so an expiry never becomes a miss (Lesson 2).

Move 1 — Estimate: one shared copy beats 286 private ones

The first design question is not which cache pattern but where the copies live. Two layouts fit our 286 servers: give every server its own private in-process cache, or stand up one shared cache tier they all talk to. Estimating both exposes why "shared" is the load-bearing word.

Private caches multiply the RAM. If each of the 286 app servers cached the whole catalog locally, that's 286 × 20 GB = 5,720 GB ≈ 5.72 TB of RAM to hold the same 20 GB catalog 286 times over. In practice a private cache only holds each server's hot subset — say the top 10,000 products (Zipf skew, Lesson 2), 10,000 × 2 KB = 20 MB per server — so the RAM is fine. But the copies are the problem, not the bytes.

Private caches multiply the thing you must invalidate. When one product's price changes, there are now up to 286 stale copies, one per server, each with its own independent lifetime. To make them coherent you must reach all 286 — and a server the write never reaches keeps serving the old price until its entry expires. A shared tier holds exactly one copy per key (any server routes key product:42 to the same cache node via consistent hashing, Lesson 4), so invalidating it is a single delete at one place. The shared tier deduplicates both the RAM (20 GB once, not 5.72 TB) and the invalidation surface (1 copy, not 286).

And the offload has to be near-total. The DB serves ~5,000 reads/s; peak is 50,000/s. To keep the DB below its ceiling the cache must absorb at least 1 - 5,000/50,000 = 90% of reads — and 90% leaves zero headroom, so we aim for a 99% hit ratio: misses = 1% × 50,000 = 500/s, a tenth of the DB's budget. A 20 GB working set in a RAM tier hits that easily. The cache isn't an optimization here; at 99% it's load-bearing — the DB physically cannot serve peak without it.

Name the trade-off — private near-cache latency vs shared-tier coherence. A private in-process cache is the fastest possible read (nanoseconds, no network hop) and it can't take the whole tier down, but every private copy is a separate thing to keep honest. A shared tier costs a ~0.2 ms network round trip per read and is a dependency all 286 servers lean on, but it collapses N copies to one — one place to invalidate, one place to size. Fewer copies is more coherent and less fresh-to-read; more copies is faster to read and harder to keep true. We'll start with the shared tier (one copy, tractable) and only add private near-caches in Move 4, where their coherence cost becomes the bottleneck.

Move 2 — Model: the write is where caching gets hard

Reads are the easy half: check the cache, return on hit, fall through to the DB on miss and populate. Every hard decision in distributed caching is about the write — because a write is the moment a cached copy becomes a lie, and the pattern you choose decides how fast, and how safely, the copy learns it.

1. Three write policies, three points on the freshness/latency curve

PolicyA write does…FreshnessWrite latencyMain risk
Cache-asidewrite DB, then invalidate the keyfresh on next readDB onlystale-repopulation race; a miss right after each write
Write-throughwrite cache and DB synchronouslyalways freshDB + cachewrite amplification; caches data never read
Write-behindwrite cache, ack, flush DB laterDB temporarily behindcache only (fast)data loss if cache dies before flush; ordering

Cache-aside is the default because it is lazy and honest: the cache only ever holds data someone actually read, and the source of truth is always written first, so a crash between the two steps leaves a stale cache (self-heals on invalidate/TTL), never a stale database. Write-through buys guaranteed freshness by paying the cache write on the critical path of every DB write — worth it when reads must never see stale data, wasteful when you cache things that are rarely read. Write-behind is the fast-write extreme: acknowledge from RAM and flush to disk later (Lesson 47's memtable idea, applied across the cache/DB boundary) — great for absorbing write bursts, but the ack now precedes durability, so a cache node dying before the flush loses acknowledged writes. For a read-heavy catalog whose truth must survive, cache-aside is the fit; we'll build on it.

2. The sharper fork: on a write, delete the key or overwrite it?

Inside cache-aside sits the decision that trips up more systems than the policy choice: when the underlying value changes, do you delete the cache key (so the next read misses and repopulates from the DB) or overwrite it in place with the new value?

  • Delete / invalidate — simple and race-resistant. Deletes are idempotent and commutative: two concurrent writers both deleting a key can't leave it holding a wrong value — they leave it empty, and the next read fetches the current truth. The cost is a guaranteed miss after every write (and, on a hot key, a stampede — Move 4).
  • Overwrite / update-in-place — no miss, the new value is served immediately. But two concurrent writers race: if writer A (value v1) and writer B (value v2) interleave, the cache can end up holding v1 while the DB holds v2 — a lost update inside the cache (Lesson 6), and it persists until TTL. Safe only with a version stamp (write the value and its version; overwrite only if your version is newer, a compare-and-set — Lesson 6).

Name the trade-off — invalidate (correctness) vs overwrite (fewer misses). Deleting keeps the cache trivially correct by making the DB re-answer, at the price of a miss and a possible herd. Overwriting avoids the miss but reintroduces every concurrency hazard the delete sidestepped, so it demands versioning to be safe. Default to delete; reach for versioned overwrite only for keys so hot that the post-write miss is itself the problem. This is the same "recompute vs carry the value" tension as Lesson 33's invalidate-vs-update — here on a cache instead of a read model.

Move 3 — Trace the paths

Follow a read hit, a read miss, a clean write, and the write's dangerous cousin — the stale-repopulation race — through the shared cache-aside tier.

Path A — a read hit (the 99%)

  read  product:42

   1. app server -> GET product:42 from the shared tier (routed by hash, L04)
   2. HIT -> return the 2 KB blob. ~0.2 ms network round trip. DB untouched.

  At 99% hit ratio this is 49,500 of every 50,000 reads/s. The DB never sees them.

Path B — a read miss (populate)

  read  product:99  (not cached, or expired)

   1. GET product:99 -> MISS
   2. read product 99 from the DB (source of truth) -> value v_now
   3. SET product:99 = v_now  with a TTL (say 300 s)   [populate for next time]
   4. return v_now

  ~500 misses/s reach the DB -- a tenth of its 5,000/s budget. The TTL is a
  BACKSTOP: even if no write ever invalidates this key, it can't stay stale
  longer than 300 s (L14). Shorter TTL = fresher but more misses; longer TTL =
  fewer misses but staler. That dial is the freshness-vs-load knob.

Path C — a clean write (invalidate)

  write  product:42  price 19.99 -> 17.99

   1. UPDATE product 42 in the DB   -- source of truth first, always
   2. DELETE product:42 from the cache   -- invalidate the one shared copy
   3. next reader misses -> reads the DB (17.99) -> repopulates. Fresh.

  DB-first, then invalidate: a crash after step 1 leaves a STALE CACHE entry that
  the TTL will clear -- recoverable. Invalidate-first-then-write would leave a
  window where a reader repopulates the OLD value from the not-yet-updated DB.

Path D — the stale-repopulation race (why TTL alone isn't enough)

  A slow READER and a WRITER interleave on product:42:

   t0  reader R: GET product:42 -> MISS
   t1  reader R: read DB -> gets OLD value v1 = 19.99
   t2  (R stalls -- GC pause / slow network, L07/L22)
   t3  writer  W: UPDATE DB -> v2 = 17.99
   t4  writer  W: DELETE product:42        (cache now empty)
   t5  reader R: wakes, SET product:42 = v1 = 19.99   <-- writes STALE back!
   -------------------------------------------------------------------
   Cache now holds 19.99 though the DB says 17.99 -- and STAYS wrong until TTL,
   because no further write is coming to re-invalidate it.

  FIXES (pick by how much staleness you can tolerate):
   * TTL backstop      -- bounds the damage to <= TTL (300 s). Pragmatic default.
   * version stamp     -- store (value, version); on populate, SET only if the
                          fetched version >= the cached one (compare-and-set, L06).
   * delete-after-delay-- writer deletes on write, then deletes AGAIN a few ms
                          later, evicting any stale value a racing reader wrote.

Path A is why the cache exists; Path B is the tax you pay to fill it, dialed by the TTL. Path C is the write done right — source of truth first, then invalidate the copy — and Path D is the subtle bug the ordering alone doesn't fix: a reader that read the DB before the write can still populate the cache after the invalidate, and no amount of "delete instead of overwrite" prevents it, because the stale write comes from a reader, not a writer. A version stamp (or the humble TTL) is what finally bounds it. Every one of these paths assumed one shared copy. The moment we want reads faster than a network hop, we add a copy per server — and that is where coherence stops being a delete and becomes a broadcast.

Move 4 — Find the first bottleneck: the near cache brings back N copies

The shared tier answers in ~0.2 ms, but at 50,000 reads/s that round trip and that one tier are still a load and a dependency. The obvious win is a tiny near cache (L1) inside each app server — hold the top 10,000 products locally (20 MB/server), and the hottest reads never leave the process. It works beautifully for latency and instantly recreates the exact problem the shared tier solved: now there are up to 286 copies of every hot key again, and a write must reach all of them.

You can't delete a copy you can't address synchronously. The shared tier had one copy at a known node — a targeted DELETE. The 286 near-caches are spread across the fleet, changing as servers autoscale (Lesson 27). You can't synchronously reach every one on the write path. So invalidation becomes a broadcast: on a write, publish "drop key product:42" to a pub/sub channel (Lesson 9) that every app server subscribes to, and each drops its local copy. At 500 writes/s fanned out to 286 subscribers that's 500 × 286 = 143,000 invalidation deliveries/s — cheap (they're tiny keys, not values), but now a moving part on the write path.

And the broadcast is best-effort, so the TTL becomes the safety net, not a nicety. A subscriber that was briefly disconnected, restarting, or lagging misses the message and keeps serving the old price. There is no acknowledgement that all 286 dropped it. The only hard guarantee left is the near-cache TTL: set it short — say 10 seconds — and the worst-case staleness of a missed invalidation is bounded to 10 s, at the cost of every near-cache entry reloading from the shared tier every 10 s. In a multi-copy cache, invalidation is an optimization that makes staleness usually-tiny; the TTL is the contract that makes it never-unbounded.

The stampede: invalidating one hot key melts the layer below it

There is a second, sharper bottleneck hiding in the invalidate. Suppose product:42 is the front-page item taking 10,000 reads/s by itself. You invalidate it (a price change, or its TTL fires). Now every reader misses the same key at the same instant and rushes to recompute it. For the ~10 ms it takes to read the DB and repopulate, the number of in-flight duplicate misses is (Little's Law, Lesson 13) 10,000/s × 0.010 s = 100 simultaneous DB reads for one key — a thundering herd (Lesson 2), and on a hotter key or a slower recompute it is far worse. Multiply by the shared tier's own hot-shard problem (that key hashes to one cache node, Lesson 3) and a single popular product can overload both layers at once.

  hot key product:42 @ 10,000 reads/s is invalidated at t0:

  NAIVE:  all readers miss -> ~100 concurrent identical DB reads (L13 L=R*T)
          -> DB hot-spot / herd (L02). Worse on hotter keys.

  FIX 1  SINGLE-FLIGHT (request coalescing): the first miss takes a short lock,
         recomputes once, populates; the other ~99 WAIT and share that result.
         100 DB reads -> 1. (L02's single-flight, now across the shared tier.)

  FIX 2  SERVE-STALE / SWR (L02): don't delete on expiry -- serve the slightly
         old value and refresh in the BACKGROUND, so an expiry is never a miss.
         (Use only where a few seconds stale is acceptable -- not a price you
          just legally changed; fine for a ratings summary.)

  FIX 3  DON'T INVALIDATE HOT KEYS -- versioned OVERWRITE (Move 2): a write
         replaces the value in place (with a version stamp), so the hottest keys
         never go absent and never herd. Pay for it with the versioning machinery.

Name the trade-off — freshness vs hit rate & load, made concrete. Every lever in Move 4 is the same dial. A shorter near-cache TTL and eager invalidation buy freshness but cost hit rate (more reloads) and load (more misses, more herd risk). A longer TTL and serve-stale buy hit rate and shield the source of truth but let readers see older data. Single-flight and versioned overwrite let you push toward freshness without paying the herd — they're how you cheat the dial, at the cost of more moving parts. There is no "just make it fresh and fast and cheap": you're always trading how current the copy is against how often you hit it and how hard the layer beneath it works. This is Lesson 14's freshness-vs-speed and Lesson 2's herd, now spread across a fleet of caches instead of one.

The four traps

  • Trap 1 — invalidating the cache before writing the DB. If you delete (or overwrite) the cache first and then write the DB, a reader can slip into the gap, miss, read the not-yet-updated DB, and repopulate the old value — permanently stale until TTL. Always write the source of truth first, then invalidate the copy (Path C). A crash then leaves a stale cache (self-healing), never a stale database.
  • Trap 2 — overwriting the cache in place without a version. Update-in-place avoids a miss but lets two concurrent writers leave the cache holding the older value (a lost update inside the cache, Lesson 6), stuck until TTL. Either delete-to-invalidate (idempotent, race-free) or carry a version and overwrite only if newer (compare-and-set).
  • Trap 3 — trusting invalidation fan-out to be reliable. A pub/sub broadcast to N near-caches is best-effort: a disconnected or lagging server never gets the message and serves stale indefinitely. The near-cache TTL is not optional decoration — it is the only bound on how wrong a missed invalidation can get. Keep it short.
  • Trap 4 — deleting a hot key and expecting the DB to absorb the miss. Invalidating a key taking thousands of reads/s makes every reader miss at once and herd the source of truth (Lesson 2), and it lands on one hot cache shard (Lesson 3). Guard hot keys with single-flight, serve-stale, or versioned overwrite — never a bare delete.

Where we landed

Lessons 2 and 14 taught the cache as a speed trick in front of one origin. This lesson took it to the real shape — many app servers, one changing source of truth — where the cache becomes a copy-management problem and the hard word is coherence. Estimate showed why the copies, not the bytes, are the issue: 286 private caches mean up to 286 stale copies to chase on every write (and 5.72 TB to hold the catalog 286 times), while one shared tier holds one copy per key — 20 GB once, one delete to invalidate — and has to run at a 99% hit ratio because the DB (5,000 reads/s) physically cannot serve peak (50,000/s) without it. Model put the hard decisions on the write: cache-aside (write DB, invalidate — the honest default) vs write-through (always fresh, slow write) vs write-behind (fast, durability risk), and the sharper fork of delete (idempotent, race-free, but a miss) vs versioned overwrite (no miss, but demands compare-and-set, Lesson 6). Tracing walked the hit (the 99%), the miss (populate with a TTL backstop), the clean write (source of truth first, then invalidate), and the stale-repopulation race where a slow reader writes an old value back after a newer write — bounded only by a version stamp or a TTL. The first bottleneck arrived the instant we added a per-server near cache to beat the network hop: N copies returned, invalidation became a best-effort pub/sub fan-out (500 × 286 = 143,000 drops/s) whose only hard guarantee is a short TTL, and invalidating one hot key (10,000/s × 0.010 s = 100 simultaneous misses, Lesson 13) reignited Lesson 2's thundering herd — tamed by single-flight, serve-stale, or versioned overwrite. The real lesson: a cache is a copy, and every copy is a bet that the truth hasn't moved. Distributed caching is the discipline of deciding how each copy learns it lost that bet — and the cost of learning fast (eager invalidation, short TTLs, more copies to broadcast to) is exactly the cost you pay in hit rate and load. The standing tension: freshness vs cache hit rate & load.
