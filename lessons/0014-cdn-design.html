CDN Design: Serving a Photo to Sydney in 20 ms Instead of 800

Lesson 02 ended on a promise: a cache in front of your data can serve most reads, and a cache near the user beats the speed of light. This lesson cashes that promise. We take one concrete file — a 200 KB product photo stored on a server in Virginia — and follow a shopper in Sydney asking for it. First we'll measure why the raw trip takes the better part of a second. Then we'll build the CDN (Content Delivery Network) that cuts it to a few dozen milliseconds, size the bandwidth and money it saves, and trace the two paths that decide everything: the cache hit at the edge and the cache miss that falls back to origin. We finish on the problem that has haunted caching since the beginning — invalidation: getting a changed file to replace a stale one across a few hundred edge servers without knocking your origin over.

The one system we'll trace

A shopping site. Its origin — the one authoritative server (really a cluster, but think of it as one place) — lives in a data center in Virginia, USA. It stores static assets: product photos, the CSS and JavaScript bundles, thumbnails. A shopper opens a product page in Sydney, Australia and her browser needs /img/shoe-882.jpg, a 200 KB photo. The site serves 10 billion such asset requests a day to users on every continent. Two things are wrong with fetching every one from Virginia: it is slow for anyone far away, and it is expensive because every byte leaves the origin. A CDN fixes both by keeping copies of the file close to the user. Here is the whole idea on one screen.

  ONE PHOTO, TWO WORLDS — WITHOUT A CDN vs WITH ONE

  WITHOUT (every request crosses the ocean)      WITH a CDN (a copy waits nearby)
  ───────────────────────────────────────       ─────────────────────────────────
   Sydney browser                                 Sydney browser
        │  ~15,500 km each way                         │  ~50 km
        ▼                                              ▼
   [ ORIGIN, Virginia ]  ← every byte, every user  [ EDGE PoP, Sydney ]  cache HIT → serve in ~20 ms
        every request pays ~800 ms + full egress        │ (only on a MISS, once per TTL)
                                                         ▼
                                              [ SHIELD ] ─▶ [ ORIGIN, Virginia ]
                                                 one miss refills the edge; the next
                                                 million Sydney requests are local

A CDN is a fleet of caching servers spread across the world, sitting in front of your origin. Each location is a PoP (Point of Presence) or edge. When a user asks for a file, they're routed to the nearest PoP; if that PoP already has the file (a cache hit) it answers immediately, and the request never touches your origin. The CDN is Lesson 02's cache, but distributed by geography and run by someone else.

Words we'll earn before we lean on them

  • Origin — the one authoritative server that holds the real file. Everything a CDN serves is ultimately a copy of what the origin has.
  • Edge / PoP — a CDN caching server physically close to users. "Edge" = the edge of the network, near people; "PoP" = one such site. A big CDN has a few hundred PoPs.
  • Cache hit / miss — a hit: the edge already has the file and serves it. A miss: it doesn't, so it fetches from origin (or a shield), stores a copy, then serves.
  • Hit ratio (offload) — the fraction of requests served from the edge. 95% hit ratio = only 5% ever reach origin. This one number decides your latency and your bill.
  • TTL — time-to-live: how long an edge may serve a cached copy before it must recheck with origin. Set by Cache-Control headers.
  • Cache key — the string the edge uses to decide "is this the same file?" Usually host + path + query string. Two requests with the same key share one cached copy.
  • Origin shield — one designated PoP that all other PoPs miss through, so origin sees one refill request instead of hundreds. Also called a tiered cache.
  • Invalidation / purge — telling the CDN "forget this file, it changed," so edges stop serving the stale copy.
  • Speed of light in fiber — light in glass travels ~200,000 km/s (about ⅔ of its vacuum speed). This is a hard floor on how fast a far-away byte can arrive; no money removes it.

Move 1 — Estimate: why Virginia→Sydney is slow, and what it costs

The latency floor (why "just make the server faster" can't help)

Worked: the speed-of-light tax. Sydney to Virginia is about 15,500 km. Light in fiber goes ~200,000 km/s. One way: 15,500 ÷ 200,000 = 0.0775 s ≈ 78 ms. A round trip (RTT) is therefore ~155 ms at the theoretical best; real routes bend and pass through routers, so measured RTT is ~200 ms. Now count the round trips before the first byte of the photo arrives over a fresh HTTPS connection:

• TCP handshake: 1 RTT
• TLS handshake (1.2): 2 RTTs
• HTTP request → first byte: 1 RTT
• ≈ 4 RTTs × 200 ms = ~800 ms before the image even starts loading.

Route the same request to a PoP in Sydney at ~5 ms RTT: 4 × 5 = ~20 ms. The photo didn't get smaller and the origin didn't get faster — the bytes just have less distance to cross. A faster CPU in Virginia cannot beat physics; only moving the copy closer can.

The bandwidth and the bill

Worked: how much data, and what origin egress costs.

• Volume: 10,000,000,000 requests/day × 200 KB = 2×1015 bytes = 2 PB/day.
• Per second: 2 PB ÷ 86,400 s ≈ 23 GB/s ≈ 185 Gbps of egress if it all came from origin.
• Egress price (typical cloud): ~$0.08/GB. Daily bytes = 2,000,000 GB.
• Without a CDN: 2,000,000 × $0.08 = $160,000/day just to push the bytes out of Virginia — before you've paid for the servers to survive 185 Gbps.

Now put a CDN in front at a 95% hit ratio (realistic for static assets). Only 5% of bytes reach origin:

• Origin egress: 5% × 2,000,000 GB = 100,000 GB/day × $0.08 = $8,000/day — a 20× cut.
• Origin bandwidth drops from 185 Gbps to ~9 Gbps. The edges absorb the other 176 Gbps, spread across hundreds of PoPs and priced lower per GB.

The hit ratio is the whole game: at 95% offload the origin does 1/20th of the work; at 99% it does 1/100th. Push it up and both your bill and your origin load fall with it.

Name the trade-off up front: a CDN buys you low latency and origin offload, and the price is a second copy of the truth. The moment a file is cached at 300 edges, you have 300 places that can be wrong — serving yesterday's price, last week's photo. Everything hard about CDNs (TTLs, invalidation, cache keys) is the cost of keeping those copies honest. You trade freshness for speed, and the design job is choosing exactly how much staleness each file can tolerate.

Move 2 — Model: cache key, TTL, and how the edge decides

An edge server is a lookup table plus a rule. The table maps a cache key to a stored response. The rule, on every request, is: build the key, look it up, and check whether the copy is still fresh.

The cache key — "is this the same file?"

By default the key is scheme + host + path + query string. So /img/shoe-882.jpg and /img/shoe-883.jpg are different keys (good — different photos), and two shoppers both asking for /img/shoe-882.jpg hit the same key (good — they share one copy). The danger is in the query string, and it's worth a worked example.

Worked: how a tracking parameter destroys your hit ratio. Marketing appends a per-click id: shopper A requests /img/shoe-882.jpg?utm=fb&sid=a1, shopper B requests /img/shoe-882.jpg?utm=fb&sid=b2. If the cache key includes the full query string, these are two different keys for the identical photo — every shopper mints a brand-new key, every request is a miss, and your hit ratio collapses toward 0%. The image bytes don't depend on sid at all. Fix: tell the CDN to ignore (or whitelist only) query parameters that don't change the bytes. Now all those requests collapse to one key /img/shoe-882.jpg and the hit ratio climbs back to ~99%.

Name the trade-off: the cache key sets the precision-vs-hit-rate dial. A broader key (strip params, normalize) merges more requests onto one copy → higher hit ratio, but if you strip a parameter that does change the content you serve the wrong bytes. A narrower key is always correct but shatters the cache into many rarely-reused entries. Include exactly the inputs that change the response — no more (wasted misses), no less (wrong answers). The header Vary is the standard way to say "this response also depends on Accept-Encoding" so gzip and Brotli copies don't collide.

TTL — how long a copy may be served

Origin stamps each response with Cache-Control. Two fields matter: max-age (how long browsers may reuse it) and s-maxage (how long shared caches like the CDN may). While the copy is younger than its TTL, the edge serves it with zero contact with origin. When it expires, the next request becomes a miss and refills.

Worked: why popularity, not TTL alone, sets the hit ratio. In steady state an object costs one miss per TTL window (to refetch), and every other request in that window is a hit. If an object is requested R times per window, hit ratio for it ≈ 1 − 1/R.

• A hot photo: 100 requests/minute, TTL 10 min → R = 1,000 per window → hit ratio 1 − 1/1000 = 99.9%.
• A cold photo: 1 request/hour, TTL 10 min → it usually expires before it's asked for again → nearly every request is a miss → hit ratio ≈ 0%.

So your 95% overall hit ratio comes almost entirely from the popular head of the catalog (Lesson 02's skew / Zipf) — the long tail barely caches. Two levers raise it: a longer TTL (more requests fall inside one window) and a shield (Move 3) that lets cold objects share one origin fetch instead of many.

Name the trade-off: TTL is freshness vs offload. A long TTL means more hits and a quieter origin, but a change takes up to one TTL to appear; a short TTL keeps content fresh but hammers origin with refills. Set it per content type: immutable bundles get a year, a product photo gets hours, a price or stock count gets seconds — or isn't cached at all.

Move 3 — Trace the paths

Path A — the cache hit (the common case)

The Sydney shopper's browser resolves the asset hostname; the CDN's routing (anycast or DNS) points it at the Sydney PoP. The edge builds the key /img/shoe-882.jpg, finds a fresh copy, and returns it in ~20 ms. Origin is never contacted. This is 95% of traffic and it's why the origin only needs to survive 9 Gbps instead of 185. The response carries a header like X-Cache: HIT so you can measure your hit ratio.

Path B — the cache miss (first request, or after expiry)

Nobody in Sydney has asked for this photo since it expired. The edge has no fresh copy, so it fetches from origin, stores the copy with its TTL, and serves it. This one shopper pays the ~800 ms transatlantic cost; everyone after her, until the TTL expires, pays ~20 ms. A miss is a one-time tax that a whole region shares.

  EDGE LOGIC ON EVERY REQUEST:

  build cache key (host + path + chosen query params)
      │
  fresh copy for this key?
    ├─ yes ─▶ serve from edge  (HIT, ~20 ms, origin untouched)
    └─ no  ─▶ fetch from SHIELD → origin ─▶ store copy + TTL ─▶ serve  (MISS, ~800 ms, once per region per TTL)

Path C — the miss storm, and the origin shield

Here's the trap. Suppose a popular file expires (or is purged) everywhere at once. Now hundreds of PoPs miss simultaneously and all stampede origin for the same file — Lesson 02's thundering herd, but multiplied by every PoP on Earth. Origin, sized for 9 Gbps, suddenly takes a spike it can't serve, and slows for everyone.

Worked: what the shield saves. Say the CDN has 300 PoPs. Without a shield, one expiry can send 300 concurrent misses to origin for the same object. With an origin shield — one PoP (per region) that every other PoP misses through — the 300 edge misses collapse into 1 request to origin: the shield fetches once, and the other 299 PoPs get their copy from the shield. The shield turns "300 misses hit origin" into "1 miss hits origin, 299 hit the shield." Combined with request coalescing (Lesson 02's single-flight: many misses for the same key at one node wait on one fetch), origin sees one refill per object, not thousands.

Name the trade-off: the shield is an extra hop for protection. On a shield-miss the request now travels edge → shield → origin instead of edge → origin, adding a few milliseconds; in return origin's worst-case load drops by a factor of the PoP count. You pay a little latency on the rare miss to make the origin survivable. This is the same shape as Lesson 05's queue absorbing a spike: put something in front that flattens the burst.

Move 4 — Find the next bottleneck: invalidation

Caching reads was the easy half. The hard half is what happens when the truth changes — a photo is reshot, a price drops, a legal takedown lands. Now up to 300 edges hold a copy that must die. There are two honest strategies, and choosing between them is the core CDN design decision.

Strategy 1 — Purge (evict the stale copy)

You call the CDN's API: "purge /img/shoe-882.jpg." The CDN tells every PoP to drop that key; the next request re-fetches the new version. It's direct, but it has teeth:

  • It's not instant. The purge must reach hundreds of PoPs; propagation takes seconds. For those seconds, different users see different versions.
  • A mass purge is a self-inflicted stampede. "Purge everything" expires the whole cache at once → every object misses → the herd hits origin (why the shield in Move 3 exists).

Strategy 2 — Versioned (immutable) URLs (never invalidate at all)

Instead of changing a file in place, change its name. Build tooling renames app.js to app.9f3a2c.js where the suffix is a hash of the contents. That URL is stamped Cache-Control: max-age=31536000, immutable — cache it for a year, and never recheck. To ship a new version you produce a new filename app.7b21e0.js; the HTML that references it now points at the new URL, so edges serve the new file immediately and the old copies simply age out, never requested again.

Worked: why versioning beats purging for assets. With immutable URLs there is nothing to invalidate — a changed file is a different URL, so there's no stale copy to chase across 300 PoPs and no purge storm. The only file you can't version is the HTML that names the others (its URL is fixed), so you cache it for a short TTL (say 60 s) or not at all. The pattern: cache the things that name other things briefly, and cache the named, content-addressed things forever. Purge is the escape hatch for the one URL you can't rename and for emergencies (a takedown); versioning is the default for everything you deploy.

The other wall — the long tail and the un-cacheable

A CDN shines on shared, static bytes. It struggles on two things. First, the cold long tail: files asked for less often than their TTL expire between requests, so they barely cache (the 0%-hit photo from Move 2) — a longer TTL and a shield help, but you can't cache your way out of "nobody asks for it twice." Second, personalized or dynamic content: a logged-in user's cart or a per-user price can't share one cached copy without leaking one user's data to another. The move there is to split the response: cache the shared shell (layout, images, JS) at the edge and fetch only the tiny personalized slice from origin — or run logic at the edge itself. Cache what's shared; personalize what isn't.

Name the trade-off: purge is universal but eventually-consistent and stampede-prone; versioned URLs are instant and stampede-free but only work for files you can rename. Reach for immutable versioned URLs by default; keep purge for the un-renameable HTML and for "take it down now." Both are answers to the one question a CDN can never dodge — which copy is the truth, and how fast can a change reach 300 of them?

Where we landed

We took one 200 KB photo and a shopper 15,500 km from it. Estimate showed the two problems: the speed of light makes a fresh transatlantic HTTPS fetch cost ~800 ms (4 round trips × ~200 ms), and serving all 2 PB/day from origin costs ~$160,000/day in egress. Model built the CDN: edges keyed by host+path+query (with a warning that a stray tracking param can crater the hit ratio), and a per-content TTL whose payoff depends on popularity (a hot object hits 99.9%, a cold one ~0%). Tracing the paths walked the hit (~20 ms, origin untouched, ~95% of traffic → a 20× bill cut), the miss (a one-time regional tax), and the miss storm that an origin shield collapses from 300 origin requests down to 1. The next bottleneck was invalidation: purge (direct but eventually-consistent and stampede-prone) versus versioned immutable URLs (instant and storm-free, the default for anything you can rename), plus the long tail and personalized content a CDN can't cache. The thread of the whole lesson: a CDN trades a single source of truth for many nearby copies — fast and cheap to read, and the entire craft is keeping those copies honest.
