Async Work: Queues, Workers, and the 2-Million-Link Job

Lesson 03's villain is back: an enterprise customer uploads a CSV and asks our shortener to mint 2 million links in one API call. Do it inline and the request runs for ~2.8 hours — long past any timeout. This lesson takes that one job and traces it through a queue and a pool of workers: same four moves, and we name every trade-off (at-least-once vs exactly-once, ordered vs fast, retry vs dead-letter).

The one job we'll trace

A customer calls POST /bulk with a CSV of 2,000,000 long URLs. Each row must become a short code (counter + Base62 from Lesson 01, written to its shard from Lessons 03–04). The naive design does all 2M creates inside the HTTP request, then returns. That is the whole bug. Here is the bug and the fix on one screen.

  SYNCHRONOUS (inline)                      ASYNCHRONOUS (queue + workers)

  client ──POST /bulk──► API                client ──POST /bulk──► API
                          │                                          │ writes job row
                          │ creates 2,000,000                        │ enqueues messages
                          │ links one by one                         ▼
                          │ ...2.8 HOURS...               ┌──────── QUEUE ────────┐
                          │ (connection long dead)        │ msg msg msg msg ...   │
                          ▼                                └───────────────────────┘
                       times out                            │      │      │      │
                       at ~60 s                            W1     W2     W3 ... W20   (workers)
                                                            └─ each: pull → create → ACK
  API returns 202 + job_id in ~5 ms; client polls GET /jobs/{id} for progress

A queue turns "do it now, caller waits" into "promise to do it, caller leaves." The API's job shrinks to two fast steps — record the job and drop messages on the queue — then it answers 202 Accepted immediately. The slow part runs later, on machines the caller never sees.

Words we'll earn before we lean on them

  • Producer — code that puts a message on the queue (here, the API).
  • Message — one unit of work to do later (here, one CSV row → one link).
  • Queue — a durable buffer that holds messages until someone takes them.
  • Consumer / worker — a process that pulls a message, does the work, and acks (acknowledges) it so the queue can delete it.

Move 1 — Estimate: why inline is impossible, and how many workers we need

First price the work. Creating one link is one sharded DB write plus an ID-block bump (Lesson 03). Call it 5 ms of real work per row. That single number decides everything.

One worker. 5 ms/row → 200 rows/sec. For 2,000,000 rows: 2,000,000 ÷ 200 = 10,000 s ≈ 2.78 hours.

Inline is dead on arrival. A load balancer or proxy drops an idle HTTP connection after roughly 60 s. 2.78 hours ≫ 60 s, so the client times out, retries, and now you have two 2.8-hour jobs fighting over the same DB. Synchronous bulk work is not "slow" — it is structurally impossible past the timeout.

20 workers. Work is independent, so it parallelizes: 20 × 200 = 4,000 rows/sec. 2,000,000 ÷ 4,000 = 500 s ≈ 8 min 20 s. The customer's HTTP call still returns in ~5 ms; the 8 minutes happen behind the queue.

Queue cost. One message ≈ a CSV row (URL + metadata) ≈ 200 bytes. 2,000,000 × 200 B = 400 MB sitting in the queue at peak — trivial for a real broker. The messages drain to zero as workers chew through them.

Name the trade-off up front: the queue buys you decoupling and elastic throughput, but you pay in latency and complexity. The result is no longer ready when the call returns — the client must poll GET /jobs/{id} or get a webhook later. You've added a moving part (the broker) and a new failure mode (messages that get stuck). You trade "answer is ready immediately, but only for tiny jobs" for "answer is eventual, but any size job survives."

Move 2 — Model: producer → queue → workers

The shape is three boxes. The producer (API) writes a job row (status=running, done=0, total=2,000,000) and enqueues the messages. The queue holds them durably. A pool of workers pulls messages, creates links, updates the counter, and acks. Nothing in the request path waits for the work.

  PRODUCER (API)            QUEUE (durable buffer)         WORKERS (pool, scale freely)
  ───────────────          ──────────────────────         ────────────────────────────
  POST /bulk         ┌───────────────────────────┐         loop:
    write job row    │ [m1][m2][m3][m4] ... [mN]  │  pull →   m = receive()        (msg hidden)
    enqueue N msgs ─►│  oldest ───────► newest    │           create_link(m)
    return 202+id    └───────────────────────────┘   ack ◄──  ack(m)               (msg deleted)
                                  │                            on crash: no ack →
  client later:                   └─ "in flight" copy hidden    msg reappears, retried
    GET /jobs/{id} → {done: 1.31M / 2.00M, status: running}

The one mechanism that makes this safe is the visibility timeout. When a worker receives a message, the queue does not delete it — it hides it for, say, 30 seconds. If the worker acks within 30 s, the message is deleted for good. If the worker crashes and never acks, the 30 s elapses and the message becomes visible again for another worker to retry. No work is silently lost.

Worked: a worker dies mid-job. Worker W7 receives message m_948213 (hidden for 30 s), creates the link in the DB, then crashes before sending the ack. After 30 s the queue re-shows m_948213; worker W3 picks it up and creates the link again. Net result: the row was processed twice. The queue guarantees at least one delivery, never exactly one. We must design for the duplicate, not wish it away.

Move 3 — Trace the paths: delivery, duplicates, and poison

Path A — the duplicate (at-least-once delivery)

At-least-once means every message is delivered one or more times. The retry that saves you from crashes is the same retry that creates duplicates. The naive instinct — "just switch the queue to exactly-once" — is a trap: true exactly-once across a network is extremely expensive (it needs distributed transactions between broker and DB) and most "exactly-once" features are really at-least-once plus dedup under the hood. The cheap, standard fix lives in your code: make the work idempotent.

Idempotent = running it twice has the same effect as running it once. Give every row a stable idempotency key — e.g. (customer_id, csv_row_number) — and write with it:

  NOT idempotent:                          IDEMPOTENT:
    INSERT link (url) ...                     INSERT link (idem_key, url) ...
    -> retry makes a 2nd row, 2nd code        ON CONFLICT (idem_key) DO NOTHING
    -> customer billed twice                  -> retry is a no-op; one row, one code

  redeliver m_948213  ──►  worker does INSERT ... ON CONFLICT (cust42, row#948213)
                           first time: inserts.   second time: conflict → skipped.
                           SAME end state either way.

Idempotency converts "at-least-once" into "effectively exactly-once" for free. You stop fighting the queue's redelivery and instead make redelivery harmless. This is the load-bearing idea behind every reliable worker — we give it its own lesson later, but the shortener needs it now.

Path B — the poison message (retry that never ends)

Row #1,500,002 is malformed: its URL is 9 KB of garbage that violates a DB constraint. The worker pulls it, throws, never acks. After 30 s it reappears, another worker throws, never acks… forever. One bad row now loops endlessly, burning a worker slot and never finishing the job. This is a poison message.

The fix is a retry limit plus a dead-letter queue (DLQ) — a separate queue where messages go to die after, say, 5 failed attempts. They stop blocking live workers and wait for a human (or a repair job) to inspect them.

Worked: 50 poison rows out of 2,000,000. Each bad row is retried 5 times then parked in the DLQ. Workers spend 50 × 5 = 250 wasted attempts total — negligible against 2M good rows. The job finishes: 1,999,950 links created, 50 in the DLQ for review. Without a DLQ those 50 messages loop forever, the job's done counter sticks below total, and it never reports complete.

Name the trade-off: the retry limit balances two failures. Set it too low and a transient blip (a 1-second DB hiccup) sends good work to the DLQ. Set it too high and real poison wastes capacity longer before it's quarantined. ~3–5 attempts with exponential backoff (wait 1s, 2s, 4s… between tries) is the usual middle: it survives blips but quarantines true poison quickly.

Path C — fan-out and ordering (the second async job)

Bulk creation isn't the only async work. When each link is created we also fan out notifications: update the customer's dashboard, fire their webhook, maybe email a receipt. One event, many side-effects — perfect for a queue. But fan-out raises ordering. If a customer creates then immediately deletes a link, the "deleted" event must not be processed before "created", or their webhook ends up in a wrong state.

Global ordering (every message strictly in order) would force a single consumer and kill our parallelism. The standard answer is per-key ordering via partitions: pick a partition key = customer_id, so all of one customer's events land on the same partition and stay ordered, while different customers run on different partitions in parallel.

  GLOBAL ORDER (1 consumer)            PER-KEY ORDER (partition by customer_id)
  ─────────────────────────           ─────────────────────────────────────────
  all events ─► 1 worker               cust42's events ─► partition 0 ─► worker A  (ordered)
  strict order, NO parallelism         cust77's events ─► partition 1 ─► worker B  (ordered)
  throughput capped at 1 worker        cross-customer order: NOT guaranteed (don't need it)

Name the trade-off: ordering and throughput pull against each other. Total order costs parallelism; no order maximizes it. Per-key order is the pragmatic middle — you keep the ordering that actually matters (within one customer / one entity) and pay nothing for the ordering you don't care about (between unrelated customers).

Move 4 — Find the next bottleneck: consumer lag & backpressure

Workers now scale horizontally, but a new wall appears the moment arrival rate > drain rate. The queue depth grows, and the time between a message being enqueued and processed — the consumer lag — climbs. Trace it.

Drain rate with 20 workers = 4,000 msg/s. Customer A enqueues 2,000,000 at t=0: depth spikes to 2M, then falls linearly, hitting 0 at 2,000,000 ÷ 4,000 = 500 s.

Now customer B enqueues 1,000,000 more at t=100 s. At t=100 s the backlog is 2,000,000 − 4,000×100 = 1,600,000; add B's 1M → 2,600,000. Remaining drain = 2,600,000 ÷ 4,000 = 650 s, finishing at t=750 s. The oldest waiting message is now ~hundreds of seconds behind real time — that is the lag, and it's what an SLA actually feels.

The fix: watch queue depth, not CPU. If depth ÷ drain_rate (age of the oldest message) exceeds your target, autoscale workers. Doubling to 40 workers → 8,000 msg/s → the 2.6M backlog clears in ~325 s instead of 650 s. The queue's depth is the single best signal for "add capacity."

Backpressure is the honest limit. If producers can enqueue faster than any worker pool can drain forever, the queue grows without bound and eventually the broker runs out of disk. A queue is a shock absorber for bursts, not a bottomless pit for a permanent overload. The real fixes: autoscale workers to meet sustained load, or shed load at the producer (reject/throttle new bulk jobs when depth is dangerous — the rate-limiting topic coming up). A queue smooths spikes; it cannot create throughput that the workers don't have.

Where we landed

We took the 2-million-link bulk job that can't fit in one request and made it routine. Estimate showed inline = 2.78 hours (impossible past a 60 s timeout) and sized the fix at 20 workers → ~8 min, returning 202 in ~5 ms. Model set up producer → queue → workers with a visibility timeout so a crashed worker's message reappears instead of vanishing. Tracing the paths exposed three truths: at-least-once delivery means duplicates (fix: idempotency keys, not "exactly-once"), poison messages loop forever (fix: retry limit + DLQ), and fan-out needs per-key ordering via partitions (total order would kill parallelism). The next bottleneck — consumer lag and backpressure — says a queue absorbs bursts but can't invent throughput, pointing at autoscaling and rate limiting.
