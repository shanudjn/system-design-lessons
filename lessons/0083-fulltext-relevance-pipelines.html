Full-Text & Relevance Pipelines End to End: One Query and One Document, Traced Through the Whole Machine

Two lessons ago we said search was solved: Lesson 12 built the inverted index (tokenize text, keep a postings list per term, intersect the lists), and Lesson 16 ranked the matches (IDF, BM25, top-K). But between "raw product text sitting in a database" and "a ranked, filterable results page" sits an entire machine we skipped — and it's the part that decides whether a shopper who types runing shose at 11 p.m. finds anything at all. This lesson assembles that machine end to end. We take one document — a product listing — and one messy query, and trace both all the way through: through the analyzer (the pipeline that turns text into searchable terms), into the inverted index, and back out as a scored, faceted result page. We'll estimate the index size and the sharp asymmetry between building the index and querying it. We'll model the analyzer, the one iron rule that index-time and query-time must obey together, and how typos and synonyms are handled. We'll trace three paths — indexing a document, running a clean query, and running a query with a typo. And we'll find the first bottleneck: keeping the index fresh — why an inverted index can't be updated in place, and the segment-and-merge design that makes near-real-time search possible. The trade under all of it: index richness & freshness vs build cost & query latency.

The one system we'll build

Keep the product catalog from L12/L16: 10 million products, each with a title and a short description. Shoppers search it at 5,000 queries/second at peak, and they expect a results page in well under 100 ms. Two very specific things travel through the system in this lesson, and we'll follow each one byte by byte:

  • One document being indexed: a product titled Men's Running Shoes — Blue Runner (Waterproof), in category Shoes.
  • One query being run: a shopper types runing shose — two typos — and still expects to see that shoe.

Here is the whole machine on one page. The left column is done once per document, at index time; the right column is done on every query, at read time; the boxed rule in the middle is why the system works at all:

  INDEX TIME (once per document)            QUERY TIME (once per query)
  ------------------------------            ---------------------------
  "Men's Running Shoes -                    "runing shose"
   Blue Runner (Waterproof)"                      │
        │                                         │
        ▼                                         ▼
  ┌───────────────┐                        ┌───────────────┐
  │   ANALYZER    │  <=== MUST BE THE ===> │   ANALYZER    │
  │ char filter   │      SAME  PIPELINE    │ char filter   │
  │ tokenizer     │                        │ tokenizer     │
  │ lowercase     │                        │ lowercase     │
  │ stopwords     │                        │ stopwords     │
  │ stemming      │                        │ stemming      │
  │ synonyms      │                        │ + typo fix    │

         │ terms: [men, run, shoe,                │ terms: [run, shoe]

The one idea the whole lesson turns on: full-text search is a machine with two halves that must be built to match. At index time you do the heavy work once — run every document's text through an analyzer that turns messy prose into clean, normalized terms, and store those terms in an inverted index. At query time you run the same analyzer over the short query, look up the resulting terms, and rank what comes back. If the two halves disagree about how to turn text into terms — even slightly — the shopper's words never line up with the document's words, and a product that perfectly matches returns nothing. Everything else (typo tolerance, synonyms, facets, freshness) is a feature bolted onto that spine.

Words we'll earn before we lean on them

  • Term — the atomic unit the index is keyed on: a normalized token, e.g. run. Not the same as a word — the analyzer turns "Running" into the term run.
  • Analyzer — the pipeline that turns a blob of text into a list of terms. It runs at index time and at query time, and the two must be identical.
  • Char filter — the first analyzer stage: cleans the raw characters (strip HTML, normalize punctuation and accents) before anything is split.
  • Tokenizer — splits the cleaned text into tokens (usually on whitespace and punctuation): "Blue Runner" → [Blue, Runner].
  • Token filter — a stage that transforms the token stream: lowercase, remove stopwords, stem, expand synonyms. Analyzers are a char filter + a tokenizer + a chain of token filters.
  • Stopword — a term so common it carries almost no meaning (the, a, of); often dropped to shrink the index and speed queries (L16's near-zero IDF made concrete).
  • Stemming — reducing a word to a root form so variants collapse to one term: running, runs, ran → run. Makes a query for one variant match all of them.
  • Synonym expansion — mapping different words for the same thing to a shared term or term set: sneaker ↔ shoe.
  • Inverted index — the map term → list of documents containing it (the postings list). Built in L12; the thing the analyzer feeds.
  • Edit distance (Levenshtein) — the number of single-character insert/delete/substitute edits to turn one string into another. runing → running is distance 1 (one insert).
  • Segment — a small, immutable, self-contained inverted index. A search engine's index is a set of segments searched together; new documents go into new segments.
  • Refresh — the act of making newly-written documents visible to search by exposing a new segment. The interval between refreshes is the freshness dial.
  • Merge — the background job that combines many small segments into fewer big ones to keep query fan-out and file counts bounded (the LSM-tree shape from L47).
  • Facet — a count of matching documents grouped by a field, shown as filters: "Shoes (1,240) · Boots (89) · Sandals (12)".
  • Recall vs precision (from L16) — recall = did we retrieve the good matches at all; precision = are the retrieved ones actually good. Retrieve broadly, then rank to restore precision.

Move 1 — Estimate: the index size, and the build-vs-query asymmetry

Three numbers set up every decision in this lesson: how big the index is, how lopsided the cost of building it is versus querying it, and how expensive typo tolerance gets if you do it naively.

How big is the inverted index? Each product's title + description is ~500 characters, which the analyzer turns into roughly 50 distinct terms after stopword removal and stemming. The index is one posting per (term, document) pair:

  postings = 10,000,000 docs × 50 distinct terms/doc = 500,000,000 postings

  raw posting = doc_id (4 B) + term positions (~4 B) ≈ 8 B
     500,000,000 × 8 B = 4 GB raw

  but postings are SORTED by doc_id, so delta-encode the gaps and
  variable-length compress them (L80 wire encoding, L29 columnar) → ~3-4× smaller
     ≈ 1-1.5 GB compressed

  vocabulary (distinct terms) ≈ 1-2 million entries → a small term dictionary

~1 GB, held in RAM across a few nodes. That's the payoff of the inverted layout: the entire searchable form of a 10M-product catalog is small enough to serve from memory, because the analyzer threw away everything a search doesn't need (punctuation, casing, stopwords, word endings) before storing it. The trade named already: we shrank and sped the index by discarding information — the original text is no longer reconstructable from the terms, so the index is a derived copy (L82), not the source of truth.

The asymmetry: building the index is heavy, querying it is light. This is the single fact that shapes the architecture.

  INDEX a document: char-filter + tokenize + lowercase + stopword +
     stem + synonym, then write postings. ~0.2 ms of CPU per doc.
     Full rebuild of 10M docs = 10,000,000 × 0.2 ms = 2,000 s single-core
       ≈ 33 min on one core; parallelize across 32 cores → ~1 min.
     ==> heavy, done ONCE per document (or once per re-index).

  QUERY "runing shose": analyze a 2-word string (~microseconds),
     look up 2 postings lists, intersect/union, BM25-score the
     candidates, keep top 10.  Target: < 20 ms.
     ==> light, done on EVERY one of 5,000 queries/second.

This is L15's precompute-the-read, in its purest form. All the linguistic work — splitting, normalizing, stemming — is paid once at index time and baked into the terms. The query only has to analyze a handful of words and walk a few short lists. If you moved any of that work to query time (say, stemming every document's text while the query runs) you'd multiply a 20 ms query by millions of documents and melt the cluster. The design principle: do the expensive language processing once, at write time; keep the read a lookup.

The price of typo tolerance, done wrong. The shopper typed runing. To find that running (→ run) is one edit away, the naive approach compares the typo against every term in the dictionary:

  naive fuzzy match: 1 typo × 1,500,000 dictionary terms
     = 1,500,000 edit-distance computations, per query term, per query
     at 5,000 q/s × 2 terms → 15,000,000,000 comparisons/s  ==> impossible

  smart: a Levenshtein automaton / FST walk over the term dictionary
     enumerates only the terms within edit distance 1 of "runing"
     (a trie/finite-state walk prunes the other ~1,499,99x) → a handful
     of candidates in microseconds.

The lesson buried in the arithmetic: every "nice" search feature — typos, synonyms, wildcards — expands one query term into many, and the cost is in that expansion. Typo tolerance widens recall (you match more), but if you expand carelessly you either blow the latency budget or blow up precision (matching too much). The trade named: richer matching vs query latency and precision.

Why the whole design is "heavy once, light forever": a query is a tiny amount of text (2–4 words) read against a huge amount of data (10M docs), millions of times a second. So you spend lavishly, once, to pre-shape the data into a form where the query is a cheap lookup — and you refuse to do anything per-document at query time. Every hard part of this lesson (freshness, faceting, typo tolerance) is really the question "how do I add this feature without breaking the light-query rule?"

Move 2 — Model: the analyzer, the symmetry rule, and how matching gets smart

The analyzer, stage by stage, on our one document

Watch the product title become terms. Each stage does one job, in order:

  raw:         "Men's Running Shoes — Blue Runner (Waterproof)"
    │
  char filter  strip punctuation/accents, normalize the em-dash & parens
    ▼          "Men's Running Shoes Blue Runner Waterproof"
  tokenizer    split on whitespace/punctuation
    ▼          [Men's] [Running] [Shoes] [Blue] [Runner] [Waterproof]
  lowercase    fold case so "Running" and "running" are one term
    ▼          [men's] [running] [shoes] [blue] [runner] [waterproof]
  possessive/  strip 's ; drop stopwords (none here; "the/a/of" would go)
  stopword ▼   [men] [running] [shoes] [blue] [runner] [waterproof]
  stemming     collapse word endings to a root (Porter-style)
    ▼          [men] [run] [shoe] [blue] [runner] [waterproof]
  synonyms     (optional, index-time) sneaker->shoe, h2o->waterproof ...
    ▼          [men] [run] [shoe] [blue] [runner] [waterproof]

  FINAL TERMS stored in the index for this doc:
     men, run, shoe, blue, runner, waterproof

Notice what happened to running and shoes: they became run and shoe. The document no longer contains the word "running" anywhere in the index — only the stem run. This is the crucial setup for the next rule.

The one iron rule: index-time and query-time analysis must match

The document is stored under the term run, not running. So when a query arrives, it must be run through the same stemmer, or it will look up the wrong term and find nothing:

  Query "running shoes":
    SAME analyzer  -> [run, shoe]   -> looks up "run", "shoe" -> HIT ✓

  Query "running shoes" analyzed DIFFERENTLY (no stemmer at query time):
                   -> [running, shoes] -> looks up "running", "shoes"
                   -> the index has no term "running" (only "run") -> MISS ✗

This is the number-one cause of "search is broken and I can't tell why." Both sides analyze text; if they don't use the identical pipeline, a perfect match silently returns zero results — no error, no crash, just nothing. The rule: the query and the document must be turned into terms the same way. (There are deliberate exceptions — you might add synonyms only at query time — but they are decisions made knowing the two sides differ, never accidents.) The deeper point tying back to L82: the inverted index is a derived copy of the text under a specific analyzer. Change the analyzer and the copy is now built two different ways — which is exactly the freshness/consistency problem we hit in Move 4.

Recall first, then precision: retrieve broad, rank narrow

From L16: a search has two jobs, and it does them in two phases. First retrieve a broad candidate set (favor recall — don't miss good matches); then rank to pull the best to the top (restore precision). Our query [run, shoe]:

  RETRIEVE (cheap, broad):  docs containing run OR shoe
     -> ~600,000 candidate products (L16's broad OR-match)
  RANK (moderate, on candidates only):  BM25 score each candidate (L16)
     -> saturating term frequency + length normalization + IDF
     -> keep the top 10 in a heap  (N log 10, not N log N — L16)
  RE-RANK (expensive, optional, top ~1,000 only):  ML / business signals
     -> popularity, margin, in-stock, personalization (L16 two-phase funnel)

The funnel is the recall/precision trade made physical (L12/L14/L16). Match broadly with a cheap operation over the whole index, then spend the expensive scoring only on the survivors. You never run the costly ranker over 10M documents — you run it over the ~1,000 that already passed the cheap gate. Trade named: broader retrieval catches more true matches (recall) but hands more noise to the ranker to clean up (precision) — and more candidates means a slower query.

Typos and synonyms: widening recall on purpose

Two features live in the analyzer/retrieval boundary and both work by expanding one term into several:

  TYPO TOLERANCE (query-time, via edit distance):
     "runing" --edit distance 1 (insert 'n')--> {running} --stem--> run
     "shose"  --1 transposition (swap s,e)---> {shoes} --stem--> shoe
                (engines use Damerau-Levenshtein, which counts a swap of
                 two adjacent letters as ONE edit; keep only dictionary
                 terms that exist & are common)
     => query [run, shoe] now matches our document.

  SYNONYMS (index-time OR query-time expansion):
     index-time:  store "shoe" AND "sneaker" for the doc (bigger index,
                  no query-time cost, but re-index to change the list)
     query-time:  expand "sneaker" -> (shoe OR sneaker) at search
                  (smaller index, flexible, but every query pays to expand)

The synonym placement decision is the index-richness-vs-flexibility trade in miniature. Expand at index time and queries stay fast but the index is fatter and changing the synonym list means re-indexing (Move 4's wall). Expand at query time and the index stays lean and the list is editable instantly, but every query pays the expansion cost. Same pattern as L15 push-vs-pull and L82 precompute-vs-compute: pay early for speed, or pay late for flexibility.

Move 3 — Trace the paths: index a doc, run a clean query, run a typo query

Path A — index the product (heavy, once)

   product written to the catalog DB (the SOURCE OF TRUTH, L82)
     │  (via CDC/outbox, L33 — the index is a derived read model)
     ▼
   analyzer: "Men's Running Shoes — Blue Runner (Waterproof)"
     -> terms [men, run, shoe, blue, runner, waterproof]
     ▼
   append doc → a NEW in-memory segment; for each term, add this
     doc_id to that term's postings list within the segment
     ▼
   on REFRESH (say every 1 s), the segment becomes searchable
     -> the product is now findable ~1 s after it was written (near-real-time)

The document is not edited into the big index in place — it lands in a fresh little segment that becomes visible at the next refresh. Why it must work that way is Move 4.

Path B — a clean query, "running shoes" (light, on every request)

   "running shoes"
     -> SAME analyzer -> [run, shoe]
     -> fetch postings("run"), postings("shoe") from every segment
     -> union candidates (~600k), BM25-score them (L16), top-10 heap
     -> compute FACETS over the matching set: count by category
          Shoes (1,240) · Boots (89) · Sandals (12)
     -> return page in ~15 ms

The heavy lifting was all done at index time; the query walked two short posting lists and scored the survivors. This is the light-read the whole design protects.

Path C — the typo query, "runing shose" (the shopper's real input)

   "runing shose"
     -> analyze -> [runing, shose]  (still misspelled)
     -> typo tolerance: Levenshtein automaton over the term dictionary
          runing -> running -> stem -> run
          shose  -> shoes   -> stem -> shoe
     -> query becomes [run, shoe]  == exactly Path B from here on
     -> same postings, same BM25, same facets -> the shoe is found ✓

Paths B and C converge. The entire job of typo tolerance is to repair the query into the terms the index actually holds — after that repair, a misspelled query is identical to a clean one. And note the symmetry rule at work again: the repaired words still pass through the same stemmer (running→run) as the documents did, or the repair would fix the spelling and then miss anyway. Every smart feature funnels back onto the one spine: turn the query into the terms the documents were stored under.

Move 4 — Find the first bottleneck: keeping the index fresh

The first bottleneck — you can't update an inverted index in place. A postings list is stored sorted and compressed so it can be walked fast. Inserting one new document into the middle of a term's sorted, delta-encoded list means rewriting the list:

  term "run" -> [12, 47, 88, 210, ...]  (sorted, delta-encoded, packed)
  new doc 63 contains "run" -> must splice 63 between 47 and 88
     -> re-encode the deltas, rewrite the block on disk
  a single new product touches ~50 terms -> 50 packed lists rewritten
  10M-doc catalog updating live -> constant rewrites of huge lists
     ==> in-place update is O(rewrite), and it fights every concurrent read

So live full-text indexes almost never mutate the index. Instead they borrow the LSM-tree idea from L47:

   WRITE PATH: new/changed docs -> a small NEW immutable SEGMENT
      (a segment = a complete mini inverted index, write-once)
   REFRESH: expose the new segment to searchers (the freshness event)
   SEARCH: query ALL segments in parallel, merge their results (L21/L79)
   DELETE/UPDATE: mark the old doc_id in a "deleted" bitset; the term
      isn't removed — it's filtered out at read (a tombstone, L15/L20)
   MERGE (background): combine many small segments into fewer big ones,
      dropping tombstoned docs, to bound query fan-out & file count (L47)

This is what "near-real-time" means, and why it's near and not real. A document isn't searchable the instant it's written — it's searchable at the next refresh. The refresh interval is a direct dial: refresh every 1 second and a new product is findable ~1 second after it's written, but you mint a new tiny segment every second (more segments = more lists to merge on every query = slower reads and more merging work). Refresh less often and queries stay fast and segments stay few, but new products take longer to appear. Trade named: freshness vs query speed and merge cost — exactly L16's near-real-time indexing question and L29's batch-vs-stream freshness dial, now concrete.

The second wall — faceted search over a sharded index. At 10M products the index is sharded (L79): each shard holds a slice of the catalog and searches it independently, a coordinator scatters the query and gathers the results (L19/L21 scatter-gather). Ranking merges cleanly (each shard returns its top-K, coordinator merges into a global top-K). Facets are trickier:

   query hits 600k matches spread across, say, 12 shards
   each shard: count its matches by category -> partial facet counts
   coordinator: SUM the per-category counts across shards (L21 mergeable)
      Shoes: 110+95+... = 1,240   Boots: 8+11+... = 89   ...

   the deep-pagination / top-facet trap:
   if a shard returns only its LOCAL top-20 categories, a category
   ranked #21 on every shard could be #1 globally but never reported
   -> same top-K-from-shards accuracy problem as deep pagination (L18)
   -> fix: return more per shard than you display, or a second round

Facet counts merge by addition (L21's mergeable counters), but facet rankings ("show the top 20 brands") have the same shard-truncation hazard as deep pagination (L18): a global winner can hide just below every shard's local cutoff. The trade named: cheap, approximate facets (trust each shard's local top-N) vs exact facets (fetch more per shard or do a second round) — accuracy vs query cost, the L21 sketch trade wearing a search hat.

The third wall — changing the analyzer means reindexing everything. Suppose you add a stemmer, or swap the synonym list, or start folding accents. Every document already in the index was analyzed the old way — its terms are running, not run. New documents get the new terms. Now the index is half one language and half another, and the symmetry rule breaks for exactly half your catalog.

   old docs indexed as: [running, shoes]      (pre-stemmer)
   new docs indexed as: [run, shoe]           (post-stemmer)
   query analyzed new way: [run, shoe]
      -> matches new docs, MISSES every old doc  ✗
   the only fix: REINDEX the whole corpus under the new analyzer
      -> rebuild 10M docs (Move 1: ~1 min on 32 cores) into a NEW index,
         then atomically swap (blue-green, L31) so search never sees the seam

An analyzer change is a schema migration on the index (L24). Because the index is a derived copy of the text under a fixed analyzer (L82), changing the analyzer is changing the derivation — and the only way to make old and new agree is to re-derive everything and swap it in atomically (L31 blue-green, so no query straddles the two). This is why the index being rebuildable from a source of truth (L82) is not a nicety but the thing that makes the system evolvable at all: you can always throw the whole index away and rebuild it from the catalog.

The fourth wall — the index is stale by construction, so it needs a freshness pipeline. The catalog DB is the source of truth (L82); the search index is a derived read model. Keeping it current is the CDC/outbox pipeline from L33: every product write emits an event, an indexer consumes it, analyzes the doc, and writes a new segment. That pipeline has lag (L06), and its lag is your search staleness. The trade named: a fresher index needs a faster, more expensive propagation pipeline and more frequent refreshes/merges; a cheaper pipeline means shoppers see stale prices and missing new products for longer. Freshness is bought, never free.

So the honest picture: full-text search is a two-halved machine joined by one rule. At index time an analyzer (char filter → tokenizer → lowercase → stopword → stemming → synonyms) turns each document's prose into clean terms and stores them in an inverted index — heavy work done once (L15 precompute). At query time the same analyzer turns the short query into terms, retrieves a broad candidate set, and ranks it with BM25 (L16) — a light lookup done millions of times. Estimate sized the index (~1 GB compressed, RAM-resident) and named the build-vs-query asymmetry that forces "heavy once, light forever." Model walked the analyzer on one document, stated the iron symmetry rule (index and query must analyze text identically or a perfect match returns nothing), and showed typos and synonyms as deliberate recall-widening term expansions. Tracing a clean query and a typo query showed them converge onto the same terms. The first bottleneck — an inverted index can't be updated in place — is solved by immutable segments + refresh + background merge (L47's LSM shape), whose refresh interval is the freshness-vs-speed dial. Around it: sharded facets merge by addition but risk the top-K-from-shards trap (L18/L21/L79), an analyzer change is a full reindex-and-swap (L24/L31), and the index is a derived copy kept current by a CDC/outbox pipeline whose lag is your staleness (L33/L06/L82). The standing tension: index richness & freshness vs build cost & query latency.

The deepest point: the search index is a derived, disposable copy of your text, pre-shaped by an analyzer so that queries are cheap lookups — and everything hard about search is the cost of keeping that copy rich, fresh, and in sync with the terms a query will actually ask for. Once you see the index as a read model (L82) built by precomputation (L15), fed by a change pipeline (L33), searched by scatter-gather (L79), and rebuilt by migration-and-swap (L24/L31), full-text search stops being a black box and becomes an assembly of pieces you already own. The genuinely new idea is small: text isn't searchable — terms are, and the analyzer is the machine that turns one into the other, on both sides, the same way. The trade to carry: index richness & freshness vs build cost & query latency.

The four traps

  • Trap 1 — mismatched analyzers. Indexing with a stemmer but querying without it (or vice versa) makes perfect matches return zero results, silently. Always run the query through the identical pipeline the documents used; any deliberate difference (query-only synonyms) must be a known decision, not an accident.
  • Trap 2 — doing language work at query time. Stemming, synonym expansion, or fuzzy matching applied per-document while the query runs multiplies a cheap lookup by millions of documents. Pre-shape everything you can at index time; keep the read a lookup over a broad-then-narrow funnel.
  • Trap 3 — treating the index as the source of truth. The index is a derived, lossy copy of the text (the original prose can't be rebuilt from stems). Keep the catalog DB as the source of truth (L82), feed the index by a change pipeline (L33), and be ready to rebuild-and-swap the whole index whenever the analyzer changes (L24/L31).
  • Trap 4 — expecting real-time and exact facets for free. Near-real-time search is bounded by the refresh interval (a freshness-vs-speed dial), and top-N facets over shards can silently truncate a global winner below each shard's local cutoff. Choose the refresh cadence and the facet accuracy deliberately; both trade cost for correctness.

The first bottleneck — you can't update an inverted index in place — is solved by immutable segments + refresh + background merge (L47's LSM shape), whose refresh interval is the freshness-vs-query-speed dial. Around it: sharded facet counts merge by addition but top-N facets risk the shard-truncation trap (L18/L21/L79); changing the analyzer is a full reindex-and-atomic-swap (L24/L31); and the index is a derived read model kept fresh by a CDC/outbox pipeline whose lag is your search staleness (L33/L06/L82). The deepest point: the index is a disposable, lossy, pre-shaped copy of your text, and every hard part of search is the cost of keeping that copy rich, fresh, and aligned with the terms a query will ask for. The standing tension: index richness & freshness vs build cost & query latency.
