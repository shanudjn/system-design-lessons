Consensus Internals (Raft): How Five Servers Agree on One Log

Since Lesson 10 we've hidden the hardest part of distributed systems behind three innocent words: "a consensus cluster." Leader election (Lesson 10), distributed locks (Lesson 22), service discovery (Lesson 34), and anti-entropy coordination (Lesson 43) all said "store the truth in etcd / ZooKeeper / Consul" and moved on. This lesson opens that black box. The problem inside is exact: make five servers agree on one ordered list of commands — even though servers crash and the network delays, drops, and reorders messages — such that they never, ever disagree about what was decided. We'll take one concrete cluster — five nodes holding a tiny replicated config store (the exact thing that backs the lock and the leader lease from earlier lessons) — and design it end to end with Raft, the algorithm built to make this understandable. We'll estimate why you need a majority and what agreement costs in latency and fault tolerance; model Raft's three pieces (leader election, log replication, safety); trace a normal commit, a leader crash, and the one scenario that decides everything — why a committed entry can never be lost. The first bottleneck is built into correctness itself: every decision must be durably stored on a majority before it counts, so consensus costs a round trip and a disk flush that you cannot optimize away — you can only pay it less often. The trade underneath: understandability & correctness vs the latency of agreement.

The one problem we'll design

Five servers each hold a copy of a small, critical table — who currently holds the billing lock (Lesson 22), which node is the current leader (Lesson 10), where each service instance lives (Lesson 34). Clients send it commands like SET lock:billing = node1, token=42 or SET leader = node3. The whole point of running five copies instead of one is to survive a crash: if any one server dies, the truth is still there. But that creates the problem. If two clients send conflicting commands, and different servers apply them in different orders, the five copies disagree — and now there is no truth at all, just five opinions. One server holding the truth alone can't be the answer (it crashes, and it can also be stale — the network might have hidden a newer write from it). So the servers must agree: settle on one single ordered log of commands that every server applies identically, so that all five copies are always the same, and stay the same across any crash. That agreement, reached despite crashes and an unreliable network, is consensus, and it is the foundation every coordination service is built on.

  Five servers must agree on ONE ordered log of commands.

    clients' commands  (may arrive in any order, from anywhere)

        state machine: same commands + same order = same result)

Consensus is not "pick a value." It's "agree on an ever-growing ordered log of values, and never disagree, even as servers die and the network misbehaves." Agree on the log and you've agreed on everything: replay the same commands in the same order on every node and every node reaches the same state. Raft breaks this into three problems it solves one at a time: elect one leader, replicate the log through that leader, and guarantee that nothing committed is ever lost.

Words we'll earn before we lean on them

  • Consensus — getting a group of nodes to agree on one value (here, one ordered sequence of commands), such that they never disagree, even when some crash and the network delays/drops/reorders messages.
  • Replicated state machine (RSM) — the trick that turns consensus into a database: if every node starts identical and applies the same commands in the same order, every node ends identical. So agreeing on the command log is enough.
  • Replicated log — the ordered list of commands. Each entry is (index, term, command). Index = its position; term = which leadership era created it.
  • Leader / follower / candidate — Raft has one leader at a time that takes all writes and imposes the order; the rest are followers; a node that times out waiting for a leader becomes a candidate and stands for election.
  • Term — a monotonically increasing number, one leader per term. It is a logical clock (Lesson 35) and a fencing epoch (Lesson 10/22): a message from an older term is stale and rejected.
  • Majority / quorum — more than half the nodes: ⌊N/2⌋+1. For N=5 that's 3. Every decision needs a majority; this is Lesson 11's quorum, and its overlap property is the whole safety argument.
  • Committed — an entry is committed once it is durably stored on a majority of nodes. Only then is it safe, applied, and acknowledged to the client. An entry on fewer than a majority is not committed and may still be discarded.
  • AppendEntries / RequestVote — the two messages. The leader sends AppendEntries to replicate log entries (an empty one is a heartbeat); a candidate sends RequestVote to ask for votes.
  • Election timeout / heartbeat — followers expect a heartbeat regularly; if none arrives within a randomized election timeout, a follower assumes the leader died and starts an election.
  • Paxos — the original consensus algorithm (1998), famous for correctness and for being very hard to understand. Raft (2014) targets the same guarantees with an emphasis on being teachable; both are widely used.

Move 1 — Estimate: why a majority, and what does agreement cost?

Two questions size the whole design: how many failures does five nodes survive, and what does each committed decision cost in time?

PieceValueWhere it comes from
Cluster size N5the odd number that tolerates 2 failures
Majority (quorum)3⌊5/2⌋+1 = 3
Failures tolerated f2N = 2f+1 → f = 2
Heartbeat interval~50 msleader→followers, keeps them from timing out
Election timeout (randomized)150–300 ms~3–6× heartbeat so a live leader isn't falsely replaced
Disk flush (fsync) per node~1 msSSD; an entry isn't durable until flushed
Intra-datacenter RTT~0.5 msleader ↔ follower on the same network

Why a majority, and why an odd N. Every decision requires a majority to agree. This one rule buys the whole thing, because any two majorities of the same cluster must share at least one node — for N=5, 3 + 3 = 6 > 5, so by the pigeonhole principle two groups of 3 overlap in ≥1 node (Lesson 11's quorum overlap, exactly). That shared node is what makes disagreement impossible, as we'll see. Fault tolerance follows: to keep making decisions you need a majority alive, so five nodes survive losing 5 − 3 = 2. And this is why clusters are odd: six nodes still need a majority of 4, so six also tolerate only 2 failures — the sixth node adds cost and zero extra safety (Lesson 10's "even N buys nothing," now the same math for data).

What one committed decision costs. A write isn't done when the leader has it — it's done when a majority has it durably. So every commit pays two unavoidable costs: one disk flush (the entry must survive a crash → ~1 ms fsync) and one round trip to enough followers to reach a majority. With 5 nodes the leader needs 2 follower acks (leader + 2 = 3); it waits for the second-fastest follower. Intra-datacenter that's roughly max(leader fsync, RTT + follower fsync) ≈ 0.5 + 1 ≈ ~2 ms per commit. That ~2 ms is the price of certainty, and no faster CPU removes it — it's a network round trip plus a physical disk flush, on a majority, by definition of "safe."

The throughput ceiling, and the one lever. A single leader flushing once per commit is fsync-bound: 1 commit / 1 ms ≈ 1,000 commits/s — modest. The lever is batching (group commit): while one fsync is in flight, entries pile up; flush them all together, and one ~1 ms disk write commits, say, 100 entries → ~100,000 entries/s before the leader's network or CPU becomes the wall (the same amortize-the-flush trick as Lesson 47's storage engines and Lesson 33's outbox relay). Batching cuts the cost per entry; it cannot remove the majority round trip that each batch still pays. And across regions the round trip dominates: five nodes ~30 ms apart make the leader wait for a ~30 ms RTT to its second-nearest follower → ~30 ms per commit, ~15× the intra-DC cost. That is Lesson 11/23's latency-vs-consistency tax, now with a number on it.

Name the trade-off — correctness vs the latency of agreement. Consensus gives you a single, crash-proof, agreed-upon order of events. You pay for it in latency (a majority round trip + a durable flush on every decision) and in a throughput ceiling (one leader, serialized). Every design move below is about paying that toll less often — batch many entries per flush, keep the cluster small and nearby, and put only the data that truly needs agreement inside it — never about avoiding the toll, because the toll is what makes the answer correct.

Move 2 — Model: Raft's three pieces

Raft deliberately splits the problem so you can understand one part at a time: elect a leader, replicate the log through it, and guarantee safety so nothing committed is ever lost. A strong single leader is the simplification — all writes flow through one node, which imposes the order, so there's no arguing about ordering in the common case.

Piece 1 — Leader election (terms + one vote + majority)

Time is divided into terms, each a numbered era with at most one leader. A follower that hears no heartbeat within its election timeout becomes a candidate: it increments the term, votes for itself, and sends RequestVote to everyone. A node grants its vote at most once per term, first-come. A candidate that collects a majority becomes leader and starts sending heartbeats; the others revert to followers. Two candidates can't both win the same term, because each needs 3 votes out of 5 and the two majorities would have to share a node — and that node only votes once (Lesson 11 overlap → at most one leader per term). The term is also a fencing epoch (Lesson 10/22): any message stamped with an older term is rejected, so a slow or revived old leader can do no damage.

Piece 2 — Log replication (leader appends, majority commits)

The leader takes each client command, appends it to its own log as (index, term, command), and sends AppendEntries to the followers. When a majority has stored the entry durably, the leader marks it committed, applies it to its state machine, and answers the client; it then tells followers the new commit index on the next heartbeat so they apply it too. AppendEntries also carries the previous entry's index and term, and a follower rejects the message if that doesn't match its own log — this log-matching check forces the follower to backfill any gap before accepting new entries, which is how a follower that fell behind gets repaired automatically. Result: all logs converge to be identical prefixes of the leader's log.

Piece 3 — Safety (the election restriction)

Replication alone isn't enough — you must also guarantee that a new leader can never erase something the old leader already committed. Raft's rule: a node refuses to vote for any candidate whose log is less up-to-date than its own (more entries, or a higher last term, wins). Now chain two facts: a committed entry is, by definition, on a majority; and any election requires a majority. Those two majorities overlap in at least one node (Lesson 11 again), and that node has the committed entry — so it will only vote for a candidate that also has it. Therefore every new leader already contains every committed entry (Raft calls this Leader Completeness). Committed means permanent, no matter who leads next.

The model in one line: one leader per term imposes an order; entries commit when a majority stores them durably; and the majority-overlap between "committed" and "elected" guarantees a new leader always holds everything committed — so the log only ever grows forward, never contradicts itself, and every node applying it stays identical. Raft is just these three pieces, kept deliberately simple; Paxos reaches the same guarantees by a different (harder to follow) route.

Move 3 — Trace the paths

Run three scenarios: a clean commit, a leader crash, and the one case that decides the whole design.

Path A — a normal commit (the happy path, ~2 ms)

  Client: SET lock:billing = node1  (to the leader, node 3, term 4)

    t=0.0ms  leader appends (idx 7, term 4, "SET lock...") to its log,
             starts its own fsync AND sends AppendEntries to all 4 followers
    t~1.0ms  leader's entry is durable on disk
    t~1.5ms  followers B and C have received, fsynced, and ACKed
             -> leader now has itself + B + C = 3 of 5 = MAJORITY
             -> entry 7 is COMMITTED
    t~1.5ms  leader applies "SET lock..." to its state machine,
             replies SUCCESS to the client
    next HB  leader tells all followers "commitIndex = 7";
             they apply entry 7 too -> all copies identical

  Followers D and E ack a moment later -- but the commit did NOT
  wait for them. A majority is enough; the two slowest (or dead)
  nodes never gate the write. That's the whole point of "majority."

Path B — the leader crashes (election, ~150–300 ms)

  Leader (node 3, term 4) dies. Heartbeats stop.

    followers wait out their RANDOMIZED election timeouts (150-300ms).
    node 1's timer fires first (say at 170ms):
       -> becomes candidate, term = 5, votes for itself,
          sends RequestVote(term 5, "my log ends at idx 7, term 4")
    nodes 2,4,5 each: "term 5 > my term, and candidate's log is at
       least as up-to-date as mine" -> GRANT vote
    node 1 has 1 (self) + 3 grants = 4 >= majority -> LEADER, term 5
       -> starts heartbeats; the cluster keeps serving.

  Why randomize the timeout? If all four followers timed out at the
  SAME instant, they'd all become candidates, split the vote (no one
  gets 3), and retry -- forever (a split-vote storm, L10's flap /
  L26's thundering herd). Random timers make one fire first and win.
  Failover cost ~= one election timeout + a vote round trip.

Path C — the case that decides everything: committed survives, uncommitted may not

  Two sub-cases at the instant a leader crashes.

  (1) Entry 7 reached a MAJORITY before the crash  (COMMITTED,
      client was told SUCCESS):
        the next election needs 3 votes; those 3 overlap the 3 that
        hold entry 7 in >=1 node; that node won't vote for anyone
        missing entry 7 -> the new leader HAS entry 7 -> it stays.
        A promise kept: what we acked is never lost.

  (2) Entry 8 reached only a MINORITY before the crash  (NOT
      committed, client was NEVER told SUCCESS -- its request
      timed out into "unknown", L13):
        a new leader may lack entry 8 and OVERWRITE it when it
        forces its own log onto followers.
        This is CORRECT: we never promised entry 8. The client,
        seeing a timeout, must retry with the same idempotency key
        (L13) -- so a safe overwrite here can't double-apply there.

  The line between (1) and (2) -- "did a majority store it durably
  BEFORE we answered the client?" -- is the entire definition of a
  correct distributed write. Consensus is the machine that draws
  that line and never smudges it.

Path A shows the toll from Move 1 made concrete: a commit is one fsync plus one majority round trip (~2 ms in a datacenter), and it deliberately does not wait for the two slowest nodes — that's why a majority, not all, is the bar. Path B shows leadership recovering on its own in a few hundred milliseconds, with randomized timeouts breaking the split-vote symmetry that would otherwise loop forever (the same jitter fix as Lesson 26's reconnect storm and the same flap risk as Lesson 10). Path C is the crux the whole algorithm exists to guarantee: anything you acknowledged to a client was on a majority, and majority-overlap means the next leader inherits it — while anything you never acknowledged is fair game to discard, which is safe precisely because the client saw a timeout and will retry idempotently (Lesson 13). Committed vs uncommitted is not a technicality; it is the exact boundary of what a distributed system may promise.

Move 4 — Find the first bottleneck: agreement is a toll you pay per decision

Consensus is correct and it is expensive on purpose. The walls all come from the same place — every decision needs a durable majority — and the fixes are all "pay the toll less often," never "skip it."

First wall — the single leader is a serialization point, and every commit pays a majority round trip + fsync. One leader ordering all writes is what makes Raft simple, and also what caps it (Lesson 03's single counter, Lesson 22's serial gate, in a new costume). You attack the cost per entry, not the toll: batch many entries into one fsync and one AppendEntries (group commit → ~100× throughput), and pipeline so the next batch ships before the last one's acks return. When one group still isn't enough, you cannot speed up a single log — its whole value is one total order — so you shard into many independent Raft groups (one per key range: "multi-Raft"), each with its own leader and its own order, running in parallel (Lesson 03's sharding, and the capstone of Lesson 63). The trade you just made: cross-shard operations lose the single global order you were paying for — throughput bought with the loss of one universal timeline.

Second wall — consensus is the most expensive storage you own, so put almost nothing in it. Because every write costs a majority round trip and a flush, a Raft cluster is for the little bit of state that must be agreed: who holds the lock, who is leader, the current config, cluster membership — kilobytes, changing rarely. It is emphatically not where your 100 PB of blobs (Lesson 20), your feed (Lesson 15), or your bulk records live. This is the metadata/data split again (Lesson 20's metadata plane, Lesson 30's KMS holding only keys, Lesson 26's connection registry): route the truth that needs agreement into the small, slow, correct core, and keep the mountain of data in cheap, fast, eventually-consistent storage around it.

Third wall — a majority must be alive and connected, and the nodes must be honest. Lose a majority (3 of 5 down, or a partition that strands the leader with only a minority) and the cluster stops accepting writes — it chooses consistency over availability (Lesson 10/11's CP), because continuing would risk two leaders committing different histories. That's a feature: a config store that returns a stale leader is worse than one that briefly returns an error (Lesson 34 drew the opposite choice for the routing layer, which prefers stale-but-available — different job, different pick). And note the assumption baked in: Raft and Paxos handle crash-stop faults (a node dies or is slow), not Byzantine ones (a node that lies) — surviving liars needs a different, costlier class of algorithm (BFT), which is why blockchains, not your config store, pay for it.

So the honest design for our five-node config store is: elect one leader per term by majority vote, fenced by the term so no stale leader can act; replicate every command through it, committing an entry only when a majority holds it durably; guarantee safety by letting only an up-to-date node win an election, so majority-overlap carries every committed entry into every future leader; and then use it sparingly — batch to survive the fsync toll, shard into many groups to survive the leader ceiling, and store only the agreement-critical scraps inside it. Every choice names its price: a majority round trip buys certainty; batching buys throughput at a little latency; sharding buys throughput at the loss of one global order; refusing writes under partition buys correctness at the cost of availability.

The deepest point: consensus is the one place in a distributed system where "it probably worked" is not allowed. Everywhere else we embraced approximation — eventual consistency (L06), sketches (L21), best-effort delivery (L09), stale caches (L02) — because it was cheaper and good enough. Consensus is what you build when good-enough isn't: when two nodes disagreeing about who holds the lock or who is leader corrupts everything downstream. You pay a round trip and a disk flush on a majority for every single decision, and in return you get a fact that every node will agree on forever. That is why you route the whole system's small, load-bearing truths through this small, slow, expensive core — and keep everything else out of it. The standing tension: correctness & understandability vs the latency of agreement.

The four traps

  • Trap 1 — treating "the leader has it" as done. An entry is safe only when a majority has it durably. Ack the client on the leader's local write and a crash before replication loses an acknowledged write. Commit is a majority event, not a local one.
  • Trap 2 — a fixed (non-randomized) election timeout. If followers time out in lockstep they all become candidates, split the vote, and loop — a split-vote storm (Lesson 10's flap, Lesson 26's herd). Randomize the timeout so one node reliably goes first.
  • Trap 3 — putting bulk data in the consensus cluster. Every write costs a majority round trip and a flush; that price is worth it for kilobytes of load-bearing metadata and ruinous for your actual dataset. Keep data out; store only what must be agreed (Lesson 20/30's split).
  • Trap 4 — expecting availability during a partition. A correct consensus cluster stranded without a majority stops (CP, Lesson 11). That's the design working. If you need the thing to stay available under partition, you wanted a different (AP) system for that layer, not a "more available Raft."

Where we landed

We opened the black box every earlier lesson leaned on. The problem: five servers must agree on one ordered log despite crashes and an unreliable network, so that every copy stays identical (a replicated state machine). Estimate showed why a majority is the magic number — any two majorities of 5 overlap in ≥1 node (3+3>5), which makes two leaders per term impossible and makes a committed entry impossible to lose — and priced a commit at one fsync plus one majority round trip (~2 ms in a DC, ~30 ms across regions), ceiling ~1,000/s per leader lifted ~100× by batching. Model built Raft's three pieces: leader election (terms, one vote, majority; the term also a fencing epoch), log replication (append → majority → commit → apply, with log-matching repairing stragglers), and safety (only an up-to-date node can win, so majority-overlap carries every committed entry into every future leader). Tracing ran a clean ~2 ms commit that never waits for the two slowest nodes, a leader crash that self-heals in a few hundred ms with randomized timeouts breaking the split vote, and the decisive case: a committed entry (on a majority, client acked) always survives a leader change, while an uncommitted one (minority only, client saw a timeout) may be safely discarded — because the client will retry idempotently (Lesson 13). Committed vs uncommitted is the exact boundary of what a distributed system may promise. The first bottleneck is agreement's own price — a durable majority per decision — so you pay it less often (batch, pipeline), shard into many Raft groups when one leader isn't enough (trading the single global order), and store only agreement-critical metadata inside, keeping the mountain of data in cheaper storage around it. The standing tension: correctness & understandability vs the latency of agreement.
