Real-Time Delivery: Telling 10 Million Phones "You Got Paid" the Instant It Happens

Lesson 25 settled the money — Alice's $50 moved to Bob as two immutable ledger entries that can never be lost or doubled. But Bob's phone still doesn't know. The old way to find out is to ask over and over ("any change? any change?"); we want the opposite — the server tells Bob the instant his balance moves, in about 100 ms, without him asking. That means holding a live connection open to every phone at once: 10 million of them, sitting idle almost all the time, each ready to receive the one message that matters to it. We'll estimate the cost of holding that many open sockets (and why polling instead would drown us), model the pieces (the WebSocket, the gateway that holds it, the registry that routes to it, presence), trace three paths — Bob connects, Alice's payment finds Bob's socket, and Bob is offline — and then hit the wall that defines this whole domain: a gateway holding 250,000 live connections dies, and all 250,000 phones try to reconnect at the same instant. The trade shifts from Lesson 25's correctness-vs-throughput to a new one: statefulness vs elastic scale.

The one system we'll design

A real-time delivery layer for the wallet from Lesson 25. Users keep the app open; the moment their balance changes — a payment arrives, a transfer clears — their screen updates on its own, no refresh, no tap. Concretely we serve about 10 million users with the app open at once (concurrent connections), and the single event we trace all lesson is: Alice pays Bob $50, and Bob's phone must show "You got paid $50" within ~100 ms.

The naive design is polling: every phone asks the server "anything new for me?" every few seconds. It's simple and it works for ten users. At ten million it's a firehose of requests that almost always answer "no" — we'll price that in a moment. The alternative flips who speaks first: the phone opens one long-lived connection and then stays quiet, and the server speaks the instant there's news. Here is the whole shape in one picture.

A real-time system doesn't make messages travel faster — it removes the asking. Instead of ten million phones repeatedly asking "anything for me?", the server keeps a connection open to each one and speaks only when there's something to say. The whole design is about affording to hold those connections and knowing which one to speak into.

Words we'll earn before we lean on them

  • Polling — the client repeatedly asks the server for updates on a timer. Simple; wasteful when updates are rare.
  • WebSocket — one long-lived TCP connection, upgraded from an ordinary HTTP request, that stays open and lets either side send a message at any time (full-duplex). The default tool for real-time.
  • Persistent / long-lived connection — a socket that stays open for minutes or hours, not one request then closed. Holding millions of these is the core cost.
  • Server-Sent Events (SSE) — a simpler cousin: the server can push to the client over HTTP, but the client can't push back on the same channel (one-way). Good when only the server has news.
  • Gateway (a.k.a. edge / connection server) — the server whose whole job is to hold the live sockets and shovel messages down them. Stateful by nature: a socket lives on exactly one gateway.
  • Connection registry — the lookup table user → which gateway holds their socket. Without it, an event has no idea where to go.
  • Presence — who is online right now, derived from which connections are alive.
  • Heartbeat (ping/pong) — a tiny message sent every N seconds to prove the connection is still alive, because a dead phone doesn't announce itself.
  • Fan-out — delivering one event to many connections (Lesson 15, now to live sockets instead of stored inboxes).
  • Sticky routing — pinning a client's traffic to one specific server. A live socket is inherently sticky; the skill is making that stickiness disposable.
  • Backoff + jitter — retry after a growing, randomized delay (Lesson 07) so a crowd doesn't retry in lockstep.
  • Mobile push (APNs / FCM) — the phone-OS notification channel that reaches a device even when your app is closed. The fallback when there's no live connection.

Move 1 — Estimate: what it costs to hold 10 million open sockets (and why polling is worse)

Two numbers decide the architecture: how much a fleet of open connections costs, and how much polling would cost instead. The second number is why we bother with the first.

Worked: the cost of holding the connections. Say 10,000,000 users have the app open at once. An idle WebSocket costs memory on both the kernel side (socket buffers) and the app side (who is this, what do they subscribe to) — call it ~20 KB per connection all-in.

• fleet memory = 10,000,000 × 20 KB = 200,000,000 KB ≈ 200 GB — spread across many boxes, unremarkable.

• how many gateways? A tuned connection server comfortably holds ~250,000 idle sockets (the limit is memory and file descriptors, not CPU — idle connections do nothing). So 10,000,000 ÷ 250,000 = 40 gateways, each using 250,000 × 20 KB = 5 GB of RAM for connections. Idle connections are cheap in CPU and modest in RAM — the cost of real-time is not holding the sockets, it's the storms when they all move at once (Move 4).

Worked: why polling is the expensive design. Drop WebSockets and let each phone poll "anything new?" every 5 seconds:

• request rate = 10,000,000 ÷ 5 s = 2,000,000 requests/sec, forever, just to learn "nothing changed."

• How many are useful? From Lesson 25 the wallet does 10M transfers/day = ~116/sec, each notifying 2 people → ~232 real events/sec. So out of 2,000,000 polls/sec, about 232 carry news — 2,000,000 ÷ 232 ≈ 8,600× more requests than there is news to deliver.

And it's still up to 5 seconds stale. To make polling feel instant (~100 ms) you'd poll 50× harder → 100M requests/sec. Polling pays for every possible update whether or not it happened; push pays only for updates that actually happened. When events are rare relative to clients, push wins by orders of magnitude. That ~8,600× gap is the entire reason to hold the connections.

Name the trade-off — hold state vs stay stateless. Polling is beautifully stateless: each request stands alone, any server answers it, scaling is trivial (Lesson 18's REST). Push is stateful: the server must keep a live socket per user and remember who is connected where. We take on that statefulness precisely to kill the 8,600× waste — and the rest of the lesson is the bill for statefulness: routing to the right socket, detecting dead ones, and surviving the moment a stateful server dies.

Move 2 — Model: the gateway, the registry, and presence

Split the job in two. The gateway layer holds sockets and nothing durable — it is deliberately dumb and disposable. The durable truth (who is connected where, what's undelivered) lives off the gateway, in a connection registry. That split is the whole trick to scaling something stateful: keep the expensive-to-lose state somewhere a gateway dying can't destroy.

  THE PIECES, AND WHO KNOWS WHAT

  phone ── WebSocket ──> GATEWAY G7            REGISTRY (durable, off-gateway)
                         holds the raw socket  +--------------+-----------+--------+
                         for Bob               | user         | gateway   | expires|
                         (state that dies      +--------------+-----------+--------+
                          with G7 — on purpose)| Bob          | G7        | +60 s  |
                                               | Alice        | G0        | +60 s  |
   ledger event "Bob +$50"                     +--------------+-----------+--------+
        |                                         ^  heartbeat renews the TTL;
        v                                         |  no heartbeat -> entry expires
   DISPATCHER: look up Bob in registry -> "G7" ---+  -> Bob is now "offline"
        |
        v  forward "Bob +$50" to G7 (internal RPC / pub-sub, L09)
   G7 writes ONE WebSocket frame down Bob's existing socket  -> phone shows it

  PRESENCE = "is there a live registry entry for this user?"  (online = yes)

Why keep the registry separate from the gateway that holds the socket? Because the socket and the routing fact have different lifetimes. The socket is fragile — it dies the instant G7 crashes or the phone loses signal. The routing fact ("Bob is reachable, currently via G7") is what every event needs, and it must survive one gateway dying. So the socket lives on the gateway; the fact lives in a shared, replicated store (Redis-style, keyed by user) with a short TTL that the connection's heartbeat keeps renewing. When G7 dies, its entries stop being renewed and expire within ~60 s — the system self-heals to "Bob is offline" without anyone cleaning up.

Presence falls out for free. "Is Bob online?" is just "does a live registry entry for Bob exist?" No separate system — presence is a view of the connection registry. The heartbeat that keeps a socket alive is the same signal that keeps presence honest: miss two pings and the entry expires, and Bob flips to offline whether he closed the app or drove into a tunnel.

Name the trade-off — where does the connection state live? Put the routing table on the gateway and lookups are a local, zero-latency read — but a dead gateway takes the only copy of "who was connected here" with it, and no event can find those users until they reconnect and re-announce. Put it in a shared registry and every event pays a small network lookup, but any gateway can die without losing the map. We choose the shared registry: the socket is allowed to be disposable only because the fact of the connection is stored somewhere the socket's death can't reach.

Move 3 — Trace the paths

Three journeys. Bob connecting, Alice's payment reaching Bob's live socket, and the same payment when Bob is offline. Watch the same rule hold: the gateway carries no truth of its own — every durable fact lives in the registry or the event source.

Path A — Bob opens the app (the connection is born)

  1. Bob's phone sends an ordinary HTTPS request with:  Upgrade: websocket
  2. A load balancer routes it to some gateway — say G7 (any gateway will do).
  3. G7 authenticates Bob (his token), then completes the WebSocket handshake:
        the HTTP request "upgrades" into a persistent full-duplex socket.
  4. G7 writes the routing fact to the registry:   Bob -> G7, expires in 60 s
  5. The socket goes idle. Every 30 s: phone <--ping/pong--> G7, which also
     renews  Bob -> G7  in the registry (heartbeat = liveness AND presence).

The connection starts life as a normal HTTPS request and is upgraded in place — that's why WebSockets sail through the same ports and proxies as web traffic. The load balancer picks any gateway; there's no "Bob's gateway," which is exactly what lets us add or drain gateways freely. The one durable side effect is line 4: the registry now knows where to find Bob. Everything else about this connection is disposable.

Path B — Alice pays Bob, and the event finds Bob's socket

  Ledger (L25) commits "Alice -$50 / Bob +$50" and emits an event: {to: Bob, ...}

  dispatcher:
    lookup registry[Bob]  ->  "G7"        (the routing table earns its keep here)
    forward event to G7    (internal pub-sub / RPC, L09)
  G7:
    find Bob's live socket in local memory
    write ONE frame: {"type":"credit","amount":5000,"from":"Alice"}
  Bob's phone: renders "You got paid $50"      total time ~100 ms

  If Bob has the app open on 2 devices -> registry[Bob] = {G7, G12}
    -> fan out the event to BOTH gateways (L15 fan-out, now to live sockets)

The event never guesses. It asks the registry where Bob is, forwards to that one gateway, and the gateway does the only thing it's good at: write bytes down an open socket. Note the clean division — the ledger decided the money moved (the truth, Lesson 25), the registry decided where Bob is (the routing), and the gateway just delivered. Multiple devices are the fan-out from Lesson 15 applied to sockets: the registry holds a set of gateways for Bob, and the event is copied to each. Delivery is a lookup plus a write; all the intelligence is in keeping the lookup correct.

Path C — Bob is offline (degrade to store-and-forward push)

  dispatcher: lookup registry[Bob]  ->  (nothing; entry expired — Bob's app is closed)

  Real-time delivery is impossible: there is no socket. So DON'T drop the event.
    -> hand it to mobile push (APNs / FCM): "You got paid $50"
       which stores-and-forwards to Bob's device even with the app closed.
    -> also persist it to Bob's inbox (L15) so it's there when he reopens.

  Bob reopens the app later -> Path A (reconnect) -> app pulls the inbox to catch up.

A live connection is a best-effort accelerator, never the system of record. When it's absent, the message must not vanish — it falls back to the phone-OS push channel (store-and-forward, reaches a closed app) and to a durable inbox (Lesson 15) that the app drains on reconnect. This is the same discipline as Lesson 25's snapshot: the fast path (live socket) is disposable; the durable path (inbox + push) is the truth. Real-time is a latency optimization layered on top of reliable delivery — if you skip the durable fallback, every dropped connection is a lost message.

Name the trade-off — instant-but-fragile vs durable-but-slower. The WebSocket gives ~100 ms delivery but only while it's up. Mobile push and the stored inbox are seconds-slower and clunkier, but they survive a closed app, a dead gateway, and a lost signal. Serious systems run both: push over the socket when it exists, fall back to store-and-forward when it doesn't. You don't pick one; you layer the fast path over the reliable one.

Move 4 — Find the first bottleneck: a gateway dies and 250,000 phones reconnect at once

The steady state is calm — millions of idle sockets sipping heartbeats. The danger is correlated motion: an event that makes a huge number of connections move in the same instant. The worst one is a gateway failing. G7 holds 250,000 live sockets; it crashes (or you deploy new code and restart it). Every one of those 250,000 phones notices the drop within a second or two and does the obvious thing: reconnect immediately. That's the thundering herd from Lessons 02 and 07, now made of connections.

Worked: the reconnect storm. Baseline new-connection rate across the fleet is gentle — say ~5,000/sec, or 5,000 ÷ 40 ≈ 125/sec per gateway. Now G7 dies and its 250,000 clients all retry within ~1 second, landing on the surviving 39 gateways:

• burst per gateway = 250,000 ÷ 39 ≈ 6,410 new connections/sec — about 6,410 ÷ 125 ≈ 51× the normal rate, in a spike.

• each reconnect is expensive: a full TLS handshake (~3 ms of CPU), re-auth, and a registry write. At 6,410/s × 3 ms = 19.2 CPU-seconds of handshake work per wall-second — you'd need ~20 cores per box doing nothing but handshakes. The registry takes a 250,000-write spike at the same moment.

Worse, if every client uses the same fixed 1-second retry, they reconnect in lockstep — connect, overload a gateway, get dropped, all retry together one second later: a synchronized wave that never settles. That's the metastable failure from Lesson 07, now a self-sustaining reconnect storm that can topple the surviving gateways one by one (the cascade).

The fixes are the ones we've earned, applied to connections:

  • Backoff + jitter on reconnect (Lesson 07). Instead of retrying at a fixed 1 s, each client waits a random delay that grows on repeated failure — spread over, say, 30 s. Then 250,000 ÷ 30 ≈ 8,300/sec across the fleet, 8,300 ÷ 39 ≈ 213/sec per gateway — only ~1.7× baseline instead of 51×, and handshake CPU drops to 213 × 3 ms ≈ 0.64 CPU-s/s. The jitter is what breaks the lockstep so waves never form.
  • Capacity headroom (Lessons 07 & 23). The remaining 39 gateways must hold the dead one's 250,000 sockets too. If every gateway already ran at 100%, one death has nowhere to go. Run gateways below capacity so N boxes can absorb the load of N−1 — the price of surviving a failure at all.
  • Sticky, but disposable, routing. A socket is sticky by nature — it lives on one gateway and can't be moved. But because the durable state is in the registry (Move 2), a reconnecting client can land on any gateway and simply re-announce itself. Stickiness that lasts only until the next reconnect is what lets a stateful layer scale and heal like a stateless one.

Two more walls hide behind the storm. First, the slow consumer: a phone on a weak network can't read as fast as events arrive, so the gateway's per-connection send buffer fills. Unbounded, that buffer is a memory leak that kills the gateway (Lesson 07's unbounded queue). Bound it, and when it's full either drop the socket (let the client reconnect and pull the inbox) or shed — backpressure on a single connection. Second, the registry itself is now a hot dependency every event and every reconnect hits; it needs the sharding and replication of Lessons 04 and 06, or it becomes the single point the whole real-time layer waits on.

Name the core trade-off — statefulness vs elastic scale. A gateway holding a live socket is irreducibly stateful: that connection exists on exactly one box and can't be load-balanced away mid-flight. Yet elastic scaling, rolling deploys, and failure recovery all want servers to be disposable. We resolve the tension not by removing the state but by making it cheap to lose: the durable truth (registry, inbox, the ledger itself) lives off the gateway, so any gateway can be killed at any moment and its clients just reconnect elsewhere — with backoff and jitter so the killing doesn't start a storm. You can't make a connection stateless, but you can make it disposable — hold the socket on the gateway and the truth everywhere else, so losing a gateway costs a reconnect, not a message.

Where we landed

We told 10 million phones about their money the instant it moved, without any of them asking. Estimate sized the fleet (10M idle sockets ≈ 200 GB across ~40 gateways at 250k each — cheap to hold) and priced the alternative: polling every 5 s is 2,000,000 req/s to carry only ~232 real events/s, an ~8,600× waste that's still 5 s stale — the entire reason to hold live connections. Model split the job: a dumb, disposable gateway holds the raw socket, while the durable truth — user → gateway — lives in a shared connection registry with a heartbeat-renewed TTL, and presence falls out as "is there a live entry?" for free. Tracing proved the division of labor: Bob's connection is an HTTP request upgraded in place (line 4, the registry write, its only durable effect); Alice's payment reaches Bob by registry lookup → forward to that gateway → one frame down the open socket (~100 ms), fanned out to all his devices (Lesson 15); and when Bob is offline the event does not vanish — it degrades to store-and-forward mobile push plus a durable inbox, because the live socket is a best-effort accelerator, never the system of record. The first bottleneck was correlated motion: a gateway dies, its 250,000 clients reconnect in ~1 s (~6,410/s per surviving gateway, 51× baseline, ~20 cores of handshake CPU, a lockstep metastable storm) → fixed with backoff + jitter (Lesson 07, spreads it to ~1.7× baseline and breaks the lockstep), capacity headroom so N−1 gateways absorb the load, and sticky-but-disposable routing that lets a reconnect land anywhere. The real lesson: real-time delivery isn't faster messages — it's the server holding a connection so it can speak first, and then engineering around the fact that the connection is stateful. Hold the socket on the gateway and every durable truth everywhere else, so a dead gateway costs a reconnect, not a message. The trade is statefulness vs elastic scale.
