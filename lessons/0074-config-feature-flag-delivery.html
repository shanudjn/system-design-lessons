Config & Feature-Flag Delivery: Flip a Switch on 40,000 Servers in Seconds

Lesson 31 taught the trick that a feature flag decouples deploy (code running) from release (behavior reaching users): dark-launch code turned off, flip it on for 1% of users, and roll back with a flag flip instead of a redeploy. That lesson waved a hand at "flip the flag." This lesson opens that hand. You have 40,000 servers (Lesson 27's fleet). A knob lives in a config value — a rollout percentage, a rate limit, a timeout, a kill-switch for a flaky dependency — and you want to change it and have every one of the 40,000 servers act on the new value within seconds, without shipping code and without a restart. We'll estimate why the obvious answer (have each server poll a config service) is a load-vs-freshness trap that carries hundreds of millions of pointless requests per real change; model the config plane — a versioned store, long-poll vs push delivery, deltas not blobs, and a local fail-static cache so a config read is a memory lookup and never a network hop; trace a staged rollout, an instant kill-switch, and a config-plane outage; and find the first bottleneck: "everyone is on the same flag" is never exactly true across a fleet that is always partly stale — the flip is not atomic, so you must make the mixed-version window safe rather than pretend it doesn't exist, and reckon with the fact that a bad value now propagates as fast as a good one. The trade under all of it: change speed & safety vs a new always-on dependency.

The one system we'll build

One flag, one fleet. The flag is checkout_v2 — a new checkout flow, deployed to every server but turned off, currently released to 1% of users. We want to (a) ramp it 1% → 5% → 25% → 100% over the day, watching error rates at each step, and (b) if it misbehaves, kill it instantly — back to 0% across all 40,000 servers in seconds, no deploy. The value lives in a config plane: a small service whose whole job is to hold the current config and deliver changes to the fleet fast and safely. A config value is tiny (a number, a boolean, a short rule); what makes this hard is not the data, it's that changing it changes the running behavior of 40,000 machines at once.

The one idea the whole lesson turns on: the config plane must never be on the request hot path. A server does not phone the config service to answer a user request — it reads a value from its own memory that a background process keeps fresh. Delivery (getting a change from the plane to 40,000 local caches) is a separate, asynchronous problem from evaluation (reading the cached value, which is instant and always available). Get that split right and the config plane can be slow, or briefly down, without taking the fleet with it. Get it wrong — read the config service per request — and you've built a 40,000-way dependency on a single point that fails the whole fleet at once.

Words we'll earn before we lean on them

  • Config / feature flag — a value that changes a running system's behavior without changing its code. A flag is a config value that's usually a rollout rule ("on for X% of users").
  • Control plane vs data plane — the control plane decides and distributes config (here, the config service); the data plane is the 40,000 servers doing the actual work and reading the config.
  • Config plane — the control-plane service that stores the config, versions it, and delivers changes to the fleet.
  • Version — a monotonically increasing number stamped on the whole config every time anything changes (v1200 → v1201). Lets a client ask "anything newer than mine?" and lets you roll back to an exact prior state.
  • Short poll — client asks "changed?" every P seconds. Simple; stale up to P; load grows as fleet/P.
  • Long poll (hanging GET) — client asks and the server holds the request open until the config changes (or a timeout ~30 s), then replies. Near-instant delivery with a fraction of the request load.
  • Push / streaming — the config plane keeps an open connection and sends the change the instant it happens (Lesson 26's live socket). Lowest latency, but the plane holds 40,000 stateful connections.
  • Delta — send only what changed (the one flag + new version), not the whole config blob.
  • ETag / If-None-Match — a version tag the client sends back; the server answers 304 Not Modified (tiny) when nothing changed, so a "check" costs almost nothing.
  • Fail-static — when the config plane is unreachable, keep serving the last-known-good cached config instead of failing or blanking (Lesson 34's AP choice for routing, here for config).
  • Percentage rollout / bucketing — evaluate "on for 25% of users" by hashing a stable id into a bucket [0,10000) and comparing to the threshold — deterministic, so the same user is always in or out.
  • Kill-switch — a flag whose sole purpose is to instantly disable a feature or dependency fleet-wide.
  • Mixed-version window — the brief span during propagation when some servers are on the old version and some on the new. The flip is never truly atomic.

Move 1 — Estimate: why naïve polling is a load-vs-freshness trap

The instinct is: each server asks the config service "what's the current value?" on a timer. Put numbers on it and the timer becomes the whole problem — it's the same polling-waste shape as Lesson 26, now on 40,000 machines reading a value that almost never changes.

The polling-waste wall. Config changes are rare: say 10 changes/day across the whole fleet's config = 10 / 86,400 s ≈ 1.16×10⁻⁴ changes per second. But to keep the fleet fresh, every server polls on a timer.

  • Poll every 1 s: 40,000 servers × 1/s = 40,000 req/s on the config plane, and a change is still up to 1 s stale.
  • Want 100 ms freshness? Poll 10×/s: 40,000 × 10 = 400,000 req/s — to carry ~0.0001 real changes/s.
  • The fleet does 40,000 × 86,400 = 3.456 billion polls/day to deliver 10 real changes: ≈ 346 million pointless polls per actual change.

Polling makes you choose between load and freshness, and both are bad. Slow polling is cheap but stale (a kill-switch that takes 30 s is not a kill-switch); fast polling is fresh but is a self-inflicted 400k req/s DDoS against your own most-critical service.

And the payload is worse than the request count. A full config blob (thousands of flags across the org) is easily ~100 KB. If every poll re-downloads it: 100 KB × 40,000 = 4 GB per round — at 1/s that's 4 GB/s ≈ 32 Gbps of config traffic to move bytes that didn't change. Two fixes stack:

  • ETag / 304: the client sends its version; unchanged → a ~200-byte "nothing new." A check now costs 200 B × 40,000 = 8 MB/s, not 4 GB/s — a 500× cut. But it's still 40k req/s of checks.
  • Delta on change: when something does change, send only the changed key. One flag ≈ 100 bytes → 100 B × 40,000 = 4 MB, once, instead of 4 GB.

So the bytes are solvable. The remaining problem is the 40,000 req/s of "are we there yet?" checks that exist only because the client doesn't know when to ask. That's the exact problem long-poll and push were invented to kill.

Long-poll collapses the check load. Instead of asking every second, the server asks once and the config plane holds the request open until either the config changes or a 30 s timeout fires, then answers. On a quiet fleet each server just re-connects every 30 s: 40,000 / 30 ≈ 1,333 req/s — versus 400,000 req/s for 100 ms short-polling, a ~300× reduction — and delivery is now near-instant instead of up-to-100 ms stale. Long-poll gives you better freshness AND less load at the same time — it removes the guesswork of "when to ask" by letting the server answer the moment there's something to say.

Why "read it per request" is the tempting disaster: the simplest-looking design is to skip caching and just have each server ask the config plane while handling a user request. That makes config perfectly fresh — and puts the config plane on the hot path of all 40k req/s of real traffic, turning it into a latency tax on every request and a single dependency whose hiccup stalls the entire fleet (Lesson 34's "a health check probing a shared dep fails everyone"). The whole design below exists to keep config fresh enough while keeping the read local and instant — freshness of delivery is decoupled from availability of evaluation.

Move 2 — Model: the config plane

Machine 1 — a versioned store: the source of truth

The config plane holds {flag → value} and stamps the whole config with a monotonic version that bumps on every change (v1200 → v1201). Two properties fall out of versioning, both borrowed from the ledger instinct (Lesson 25/38): a client can ask "anything newer than v1200?" in a single integer compare, and you can roll back to an exact prior state by re-pointing to v1200 — the old versions are kept, immutable, so "undo" is not a re-typed value that might be fat-fingered again, it's a known-good snapshot. Because writes are rare and reads are enormous, this store is read-optimized and heavily cached/replicated (Lesson 2/48): it's a tiny database with an outsized blast radius, so it must be the most boring, most available thing you own.

Machine 2 — delivery: pull-with-long-poll vs push

Three ways to get a change from the plane to 40,000 local caches, on a latency-vs-statefulness dial:

  • Short poll — ask every P seconds. Dead simple, stateless, firewall-friendly; stale up to P; load = fleet/P (the Move-1 trap).
  • Long poll (hanging GET) — ask once, the plane holds it open until change-or-timeout. Near-instant, still client-initiated (so it works through NAT/firewalls like any HTTP request), load = fleet/timeout. The default: ~all the benefit of push with the simplicity of pull.
  • Push / streaming — the plane keeps a live connection per server (Lesson 26's WebSocket) and sends the delta the instant it changes. Lowest latency, but now the plane is stateful: it holds 40,000 connections, must track who's connected, and inherits Lesson 26's reconnect-storm and slow-consumer problems. Worth it when you need sub-second and are already running a push tier; otherwise long-poll is the cheaper 95%.

The trade named: latency vs statefulness. Push is fastest but makes the config plane hold connection state for the whole fleet; long-poll keeps the plane nearly stateless (a held request is cheap) at the cost of a small reconnect cadence. Either way you send a delta, not the 100 KB blob.

Machine 3 — the local cache + fail-static: make the read instant and always-available

Every server keeps the last config it received in memory (for instant reads) and on local disk (to survive a restart). Evaluating a flag is a map lookup — no network, microseconds. The delivery loop updates this cache in the background. The safety rule is fail-static (Lesson 34's AP choice, applied to config): if the config plane is unreachable, or returns something that fails validation, keep serving the last-known-good value — never block, never blank the config, never crash. A stale flag is almost always fine; an empty config is a fleet-wide outage. Bake a sane default snapshot into the image too, so a server that boots during a config-plane outage still has values to serve.

Machine 4 — targeting & bucketing: "25% of users" without server state

A flag is rarely a global boolean; it's a targeting rule: "on for 25% of users," "on in the EU," "on for internal accounts." The percentage is evaluated client-side on each server by hashing a stable id into a bucket and comparing to the threshold — no per-user state anywhere:

   bucket = hash(user_id) mod 10000        // uniform in [0, 10000)
   on     = bucket < rollout_pct * 100      // 25% -> bucket < 2500

   user "alice" -> hash -> 1873  -> 1873 < 2500 -> ON  (always, every server)
   user "bob"   -> hash -> 7401  -> 7401 < 2500 -> OFF (always, every server)

Because the bucket is a pure function of the user id, the decision is deterministic and consistent: the same user is on (or off) on every server, and — crucially — raising 25%→50% only ever adds users (buckets 2500–4999), never flips someone off then on (no flicker). This is Lesson 4's consistent-hashing instinct reused: a stable hash gives you sticky, stateless assignment. Ramping is Lesson 31's canary, but for behavior instead of code: 1% → 5% → 25% → 100%, each step a checkpoint you can watch and hold.

Move 3 — Trace the paths

Follow the one flag through a staged rollout, an emergency kill, and a config-plane outage.

Path A — staged rollout: 1% → 25%

   operator: set checkout_v2 = 25%   (was 1%)

   [1] STORE   config plane validates the value, writes v1201
               {checkout_v2: 25%}, keeps v1200 immutable.
   [2] DELIVER every server is holding a long-poll open. The write
               wakes them: the plane returns the DELTA {checkout_v2:25%, v1201}.
               ~1,333 idle reconnects/s become ~40,000 delta responses,
               fanned out over ~1-2 s.
   [3] SWAP    each server validates, atomically swaps its in-memory
               config v1200 -> v1201, writes local disk, re-opens long-poll.
   [4] EVAL    next user request: bucket = hash(uid) mod 10000;
               ON if bucket < 2500. 25% of users now see checkout_v2.
               No deploy. No restart. Elapsed: ~2 seconds.

Path B — the kill-switch: 25% → 0% in seconds

   checkout_v2 is throwing errors at 25%. Undo it NOW.

   operator: set checkout_v2 = 0%   ->  v1202
   -> same delivery path: long-polls wake, delta {checkout_v2:0%, v1202},
      servers swap, next request buckets everyone to OFF.
   -> feature gone from the whole fleet in ~2 s. No redeploy.

   Compare Lesson 31's rollback = ship the old build = MINUTES + a
   capacity dip. A flag flip is the same undo at ~100x the speed,
   because the code was already there -- we only changed a VALUE.

Path C — the config plane goes down

   The config service is unreachable (deploy gone wrong, network blip).

   long-poll fails -> server does NOT block, does NOT blank config.
   -> keeps serving the last-known-good cache (v1201, checkout_v2:25%).
   -> retries with backoff + jitter (L7) until the plane returns.

   a server that BOOTS during the outage:
   -> reads the baked-in default snapshot from its image, serves that,
      catches up when the plane is back.

   The fleet keeps running on slightly-stale config. FAIL-STATIC:
   the config plane is a delivery channel, never a hot-path dependency.

Path A is the everyday win: a behavior change reaches 40,000 servers in seconds through connections that were already held open, costing one small delta each — no deploy, no restart, watched at each ramp step. Path B is why flags exist at all: the kill-switch is the same delivery path in the "off" direction, and it's the fastest undo you own precisely because the code already shipped and only a value moved (Lesson 31's decouple-deploy-from-release, now with the delivery mechanism that makes "instant" real across a fleet). Path C is the safety net that makes the whole thing acceptable: because reads are local and fail-static, the config plane can be slow or briefly dead without the fleet noticing. The first three moves make config delivery look like a solved pipe. Move 4 is where the speed turns into the danger.

Move 4 — Find the first bottleneck: "everyone on the same flag" is never exactly true

The whole design delivers a change fast. But fast is not instant, and instant is not atomic. Across 40,000 servers there is always a moment when some have the new value and some have the old — and the same speed that makes the kill-switch great makes a mistake catastrophic.

The first bottleneck — the mixed-version window: the flip isn't atomic. During Path A's ~2 s propagation, the fleet is split: some servers are on v1200 (1%), some on v1201 (25%). Delivery is eventually consistent (Lesson 6/11), not a global switch. So one user's two requests, load-balanced to two different servers mid-window, can hit off on one and on on the other — a flickering UI, or worse, a workflow that half-sees a new feature. You cannot make the flip atomic across 40,000 machines; you make the mixed state safe. Two tools: (1) evaluate the flag once per user session at the edge and pin the result for the session's life (sticky decision, so a user doesn't oscillate); (2) keep every feature backward/forward compatible so a fleet running two versions at once is fine — the exact same rule as Lesson 24/31's expand→contract, because a config change is a rolling deploy of behavior and old+new must coexist. The window is unavoidable; design it to be harmless.

The second wall — a bad value propagates as fast as a good one. The kill-switch's speed cuts both ways. A fat-fingered 100% where you meant 10%, or a malformed value that crashes every server on parse, reaches all 40,000 machines in ~2 s — faster than any human can react. The config plane is a channel that changes running behavior fleet-wide in seconds, which is precisely the blast radius Lesson 31 built canaries to contain — only now even faster, because there's no build to slow it down. Fixes, all Lesson 31 applied to config: schema-validate every value before the plane accepts it (reject a string where a percent belongs, a percent > 100); fail-static on the client so a garbage delta is dropped, not applied (a bad config should never be able to empty a good cache); and — the big one — stage the config change itself: canary the new value to 1% of servers, watch error rate/p99 (Lesson 17), then fan out. A config push deserves the same guardrails as a deploy, because that's what it is.

The third wall — the config plane is a new always-on dependency (a correlated SPOF). Every one of the 40,000 servers now depends on this one service. A single bad or empty config it serves doesn't fail one server — it fails all of them at once, a correlated outage worse than any single-machine failure (Lesson 7/34). This is the price the trade names: you bought change-speed and paid in a shared dependency. You pay it down, not away: fail-static makes an unreachable plane a non-event (Path C); the store must be HA + replicated — strongly-consistent for the source-of-truth write (Lesson 10/62 consensus, so there's one agreed version), but the read/delivery path served from an AP cache/CDN tier (Lesson 14/48: config is the same bytes for everyone, so it's trivially cacheable and should be read from a fan-out tier, never all 40k hitting the primary). The plane can be strongly consistent about what the config is and still deliver it eventually-consistently to the edge — the write is CP, the delivery is AP.

The fourth wall — the publish thundering herd. A change wakes all 40,000 held long-polls at once, and they all re-fetch and re-connect in the same instant (Lesson 2/26's herd). Even a 100-byte delta × 40,000 simultaneous is a spike, and the reconnect storm hammers the plane just when it's doing real work. Fixes are the herd playbook: jitter the notify and the reconnect so the 40k spread over a window; serve the delta from a cache/CDN tier so the primary isn't the thing being stampeded (config is identical for everyone — a perfect cache hit); and for very large fleets, fan out through a tree of relays (the plane pushes to ~100 relays, each pushes to ~400 servers) so no single node holds 40,000 connections — the same fan-out shape as Lesson 15's feed and Lesson 26's gateways.

So the honest picture of config & flag delivery: you can't poll your way to freshness (40k servers × fast polling = 400k req/s of "are we there yet?" carrying ~346 million pointless checks per real change), so a config plane holds a versioned source of truth and delivers deltas via long-poll (near-instant at ~1,333 req/s, ~300× cheaper than 100 ms short-polling) or push (faster, but a stateful plane holding 40k connections); every server keeps a local fail-static cache so a flag read is a microsecond memory lookup that survives the plane being down, and bucketing (hash(uid) mod 10000 < pct×100) makes "25% of users" a deterministic, stateless, flicker-free decision you can ramp like a canary. The first bottleneck is that the flip is never atomic — a mixed-version window is unavoidable, so you make it safe (sticky per-session evaluation + backward/forward-compatible features, Lesson 24/31); around it, a bad value propagates as fast as a good one (→ validate, fail-static, canary the config change itself), the plane is a correlated SPOF (→ fail-static + CP source-of-truth with AP cached delivery, Lesson 10/14/34), and a publish is a thundering herd (→ jitter + CDN the delta + relay-tree fan-out). Every choice names its price: long-poll is cheap but holds connections; push is instant but stateful; a local cache is fast and available but as stale as the last delivery; instant delivery is a superpower and a loaded gun.

The deepest point: a config plane is a tiny, extreme database whose writes change the behavior of every other system in seconds — so it must be the most boring component you own. Lesson 31 said flags decouple deploy from release. Delivering them at scale reveals that "release" is now its own distributed system, with all the problems you've spent 73 lessons on — versioning (L25), eventual consistency and a mixed window (L6/11), blast radius and staged rollout (L31), fail-static availability (L34), thundering herds (L2/26), stateless assignment by hash (L4) — just compressed into seconds. The engineering isn't the store (it's trivial) or the delivery (long-poll is old); it's respecting that the speed you built is the risk you took on. A deploy is slow enough to catch a mistake; a config push isn't, so every guardrail a deploy has — validation, canary, instant revert to an immutable prior version, an audit log of who changed what — has to be rebuilt around the value. The standing tension: change speed & safety vs a new always-on dependency.

The four traps

  • Trap 1 — reading the config plane per request. Perfectly fresh, and a 40,000-way hot-path dependency whose hiccup stalls the fleet. Read from a local fail-static cache a background loop keeps fresh; delivery ≠ evaluation.
  • Trap 2 — treating a config push as safer than a deploy. It's faster and unguarded, so it's more dangerous. Give it the deploy's guardrails: schema validation, a canary to 1% of servers, instant revert to an immutable prior version, an audit log.
  • Trap 3 — assuming the flip is atomic. There's always a mixed-version window; pretending otherwise ships flicker and half-applied workflows. Evaluate sticky per session and keep features backward/forward compatible so a two-version fleet is safe.
  • Trap 4 — ignoring the herd and the SPOF. A publish wakes all 40k at once, and one bad config fails them all. Jitter + CDN the delta, fan out through relays, and fail-static so an unreachable or garbage config is a non-event.

Where we landed

We took Lesson 31's hand-wave — "just flip the flag" — and built the machine that makes it real on 40,000 servers. Estimate killed the obvious answer: polling for freshness is a load-vs-staleness trap (100 ms freshness = 400,000 req/s; the fleet does 3.46 billion polls/day to carry 10 changes ≈ 346 million pointless polls per change), and re-downloading a 100 KB blob is 4 GB/s — so long-poll delivers near-instant at ~1,333 req/s (~300× cheaper than 100 ms short-poll) and you ship a delta, not the blob. Model gave the config plane: a versioned source of truth (exact rollback), long-poll vs push delivery (latency vs a stateful plane), a local fail-static cache so a flag read is a microsecond memory lookup that survives the plane being down, and bucketing (hash(uid) mod 10000 < pct×100) that makes "25% of users" deterministic, stateless, and flicker-free. Tracing ramped 1%→25% in ~2 s with no deploy, killed a bad feature 25%→0% in ~2 s (Lesson 31's rollback at ~100× the speed), and kept the fleet running on last-known-good through a config-plane outage. The first bottleneck: the flip is never atomic — a mixed-version window is unavoidable (eventual consistency, Lesson 6/11), so you make it safe (sticky per-session evaluation + backward/forward-compatible features, Lesson 24/31); around it, a bad value spreads as fast as a good one (→ validate + fail-static + canary the config change, Lesson 17/31), the plane is a correlated SPOF (→ CP source-of-truth + AP cached delivery, Lesson 10/14/34), and a publish is a thundering herd (→ jitter + CDN the delta + relay-tree fan-out, Lesson 2/15/26). The deepest point: a config plane is a tiny extreme database whose writes change every other system's behavior in seconds, so "release" becomes its own distributed system — and the speed you built is the risk you took on. The standing tension: change speed & safety vs a new always-on dependency.

Next up — we've made behavior changeable in seconds. Now make the RECORD of what changed impossible to forge.

• Append-only audit logs & tamper evidence (Lesson 75): an immutable, verifiable record of "who did what when" (Lesson 38/56) — including who flipped which flag. Hash-chain each entry to the last (a mini-blockchain) so altering any past entry breaks every hash after it; Merkle proofs that a single entry is present and unaltered without re-reading the whole log; and write-once storage. Trade: verifiability & compliance vs write cost and the impossibility of edits.
