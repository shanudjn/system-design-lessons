Webhooks & Outbound Delivery: Telling Ten Thousand Strangers' Servers, Reliably

Every delivery lesson so far pushed a message to a server we own — Lesson 9's queue, Lesson 26's phone, Lesson 33's outbox feeding our own search and warehouse. This lesson pushes it to a server we don't own and can't fix: a merchant's endpoint, a partner's integration, some developer's laptop tunnel. A webhook is an HTTP callback — when something happens on our platform (order.shipped, payment.succeeded), we POST a small JSON event to a URL the customer registered, so their system learns about it without polling us. That single reversal — we call them — changes every rule. Their endpoint can be slow, flaky, down for six hours, or an impostor's. We'll estimate why delivering these calls inline from our own pipeline hands our availability to strangers, and how one dead endpoint ties up thousands of threads. We'll model the async delivery system every webhook provider (Stripe, GitHub, Shopify) builds: a durable outbound queue, workers, signatures so the receiver can trust the call, idempotency keys so they can dedup our retries, and exponential backoff so we don't hammer a broken server. We'll trace a clean delivery, a retried one, and the ambiguous timeout that makes duplicates unavoidable. And we'll hit the bottleneck that defines the whole design: a single slow or dead endpoint that, left unisolated, starves delivery for everyone else. The trade underneath: delivery reliability vs the burden we push onto the receiver.

The one system we'll design

Our platform is the e-commerce backend from Lessons 12/24/25/33. Merchants build their own tools on top of us, and they don't want to poll GET /orders?updated_since=… every few seconds (Lesson 26 already priced polling as mostly waste). Instead each merchant registers a webhook: "when an order of mine ships, POST the event to https://merchant.example/hooks." Concretely: 50,000 registered endpoints, and Lesson 33's outbox already emits 5,000 domain events/second. Each event matches, on average, 2 subscriptions (the merchant plus a fulfillment partner) → 10,000 delivery attempts/second we owe to servers scattered across the internet. Two facts define everything, and both are the opposite of Lesson 9's internal queue: the receiver is outside our control (any latency, any downtime, no SLA we can enforce), and the receiver needs the event (it's their only signal that the order shipped — dropping it silently is a bug they can't detect). So we can neither block on them nor give up on them. We'll build the system that squares that circle.

  ONE WEBHOOK SYSTEM:  5,000 events/s -> ~10,000 outbound POSTs/s to 50,000
  endpoints we neither control nor trust.

  OUR SIDE (durable, fast)                    |  THEIR SIDE (slow, flaky, untrusted)
  --------------------------------------------|-------------------------------------
  event happens (order.shipped)               |
     |                                        |
     v                                        |
  [1] OUTBOX / event log (L33) --- durable, the source of truth
     |
     v   fan-out: match event -> subscriptions
  [2] DELIVERY QUEUE  (one attempt = one job: event_id, sub_id, url, payload)
     |
     v
  [3] DELIVERY WORKERS  ----sign + POST (30s timeout)---->  merchant.example/hooks
     |    ^                                                     |
     |    |  2xx? mark DELIVERED                                v
     |    |  else: schedule RETRY (backoff + jitter)      verify signature,
     |    |                                                dedup on event_id,
     v    |                                                return 2xx fast
  [4] give up after ~24h -> DEAD-LETTER QUEUE + merchant dashboard "replay"

  We can't BLOCK on them (their downtime would become ours) and we can't
  DROP (they need every event) -> retry until 2xx. Retries -> duplicates ->
  the receiver must dedup. At-least-once on OUR side buys idempotency work
  on THEIRS. That hand-off is the whole trade.

A webhook is an HTTP request our system makes to a URL the customer registered, to notify them of an event as it happens — a server-to-server callback that replaces polling. Two words we'll lean on: a subscription is one registered (endpoint URL, which event types, a shared secret); a delivery is one attempt to POST one event to one subscription's URL. An event may cause many deliveries; a delivery may take many attempts.

Words we'll earn before we lean on them

  • Webhook / callback — an HTTP request we send outbound to the customer's server when an event occurs (the inverse of them calling our API).
  • Subscription — a registered endpoint URL + the event types it wants + a per-endpoint shared secret.
  • Delivery attempt — one POST of one event to one endpoint; it succeeds only on a 2xx response.
  • At-least-once delivery — we keep retrying until we see a 2xx, so an event is never lost — but may arrive more than once (Lesson 9).
  • Idempotency key — a stable unique id on the event (we use event_id) the receiver stores, so a repeat delivery is recognized and ignored (Lesson 13).
  • HMAC signature — a keyed hash of the request body using the shared secret, sent in a header, so the receiver can prove the request really came from us and wasn't tampered with (Lesson 30).
  • Exponential backoff + jitter — wait longer after each failure (1s, 2s, 4s, …), with a random spread, so a broken endpoint isn't hammered and a fleet of them doesn't retry in lockstep (Lesson 7).
  • Dead-letter queue (DLQ) — where a delivery lands after retries are exhausted, so it's parked for inspection/replay instead of lost (Lesson 9).
  • Circuit breaker — after an endpoint fails repeatedly, stop calling it for a while and fail fast, so a dead endpoint stops consuming workers (Lesson 7).

Move 1 — Estimate: why delivering inline hands your uptime to strangers

The naive design writes itself: when an order ships, in the very same code path that finalizes the shipment, look up the subscriptions and POST to each. No queue, no workers — just call them. Let's price it, because the cost is not CPU or storage this time. It's a coupling you didn't mean to buy.

Internal calls are fast; third-party endpoints are not. An internal service (Lesson 27) answers in ~40 ms at p99. A stranger's webhook endpoint has no such budget: it might be a healthy 100 ms, a struggling 3 s, or a dead one that accepts your TCP connection and then never responds until your 30-second timeout fires (Lesson 7's partial failure — the connection opens, so you can't fail fast). You are now as slow as the slowest server you don't own.

Little's Law turns their downtime into your thread exhaustion (Lesson 13). Suppose our event pipeline processes 5,000 events/s, and each ships ~2 inline POSTs. Even when everyone is healthy at 300 ms/call, the pipeline holds L = λW = 10,000/s × 0.3 s = 3,000 in-flight calls at all times — 3,000 threads doing nothing but waiting on the network. Now let just 1% of endpoints go dark. That's 100/s deliveries hitting the 30 s timeout: L = 100/s × 30 s = 3,000 threads frozen on dead endpoints alone — and they don't drain, they accumulate, because new dead calls arrive as fast as old ones time out. The pool fills, healthy events queue behind zombie calls, and a checkout pipeline goes down because a merchant we've never met forgot to renew a TLS certificate.

The fix is the oldest one in the course: decouple with a queue (Lessons 5/9). The event pipeline does one fast, durable thing — commit the event and enqueue a delivery job — and returns in microseconds. A separate fleet of delivery workers drains the queue and makes the slow, flaky outbound calls, fully isolated from the pipeline that produced the event. Their downtime is now the workers' problem, and the workers are built to absorb it.

Name the trade-off — synchronous coupling vs asynchronous decoupling. Delivering inline is simpler and gives an instant "did it arrive?" answer — but it welds your availability to the availability of every endpoint you call (Lesson 7's cascade). Delivering async costs you a queue, workers, and a delivery-status system to track what actually landed — but it draws a hard wall between "the event happened" (durable, ours, fast) and "the notification arrived" (best-effort, theirs, eventually). A webhook is fundamentally an asynchronous promise, so build it asynchronously; the moment you make it synchronous you've imported 50,000 strangers' uptime into your own.

Move 2 — Model: a durable outbound pipe with trust, dedup, and patience built in

The queue decoupled us. Now give the delivery path the four properties a stranger on the other end forces on us.

At-least-once, because the receiver can't afford a lost event

Internally we sometimes tolerate a dropped message. Here we can't: the webhook is the merchant's only signal the order shipped, and a silent drop is invisible to them until a customer complains. So a delivery is done only when the endpoint returns a 2xx; any timeout, 5xx, or connection error means retry. That is at-least-once delivery (Lesson 9), and it has an unavoidable consequence: because a timeout is ambiguous (the receiver may have processed it and only the response was lost — Lesson 7), our retry can deliver the same event twice. We cannot fix that on the wire (there is no exactly-once, Lesson 9). We can only make the duplicate harmless — on the receiver's side.

Idempotency key, so our retries don't double-charge the receiver

Every event carries a stable event_id, sent in a header (e.g. Webhook-Id: evt_9f3…) and unchanged across every retry of that event. The contract we publish to integrators is Lesson 13 verbatim, pointed outward: store the id you've processed; if you see it again, acknowledge with a 2xx and do nothing. This is the first piece of the burden we push onto the receiver — and it's why the event_id must be identical on retries (a fresh id per attempt would defeat their dedup and re-run their side effect).

Signature, so the receiver can trust the call is really from us

Our POST arrives at a public URL. From the receiver's side it is indistinguishable from an attacker's POST forging {"event":"payment.succeeded","amount":9999} — unless we prove it's us. We do it with an HMAC signature (Lesson 30): each subscription has a shared secret, and we send a keyed hash of the exact body.

Worked signature. For subscription secret whsec_K, timestamp t, and raw body B:

signature = HMAC‑SHA256( key = whsec_K, message = t + "." + B )

and we send a header Webhook-Signature: t=1690000000, v1=<hex>. The receiver recomputes the same HMAC with their copy of the secret and compares it in constant time (a byte-by-byte early-exit compare leaks the answer via timing). Two properties fall out: authenticity — only someone holding the secret could produce a matching hash, so a forged body fails — and integrity — flip one byte of B and the recomputed hash won't match (Lesson 30's AEAD idea, applied to a request). Signing the timestamp too lets the receiver reject anything older than, say, 5 minutes, so a captured request can't be replayed later.

Why HMAC and not "just put an API key in a header"? A static bearer token proves nothing about the body — anyone who ever saw it can forge any payload. The HMAC binds the sender's secret to this exact message, and the secret never travels on the wire.

Backoff + jitter + a deadline, so we're patient without being a hammer

A failed delivery retries — but not immediately and not forever. We use exponential backoff (Lesson 7): wait 1 s, then 2 s, 4 s, 8 s… doubling, capped at 1 hour, and we keep trying for a 24-hour window before we give up. And we add jitter — multiply each delay by a random factor around 0.5–1.5 — for a reason Lesson 26 already taught: if a popular cloud region blips and 5,000 endpoints fail in the same second, un-jittered backoff has all 5,000 retry at exactly 1 s, then 2 s, then 4 s — a synchronized thundering herd that hammers those endpoints (and our own workers) in lockstep the instant they recover.

The retry schedule, counted out. Doubling from 1 s until the 1-hour cap: 1 + 2 + 4 + 8 + … + 2048 = 4095 s ≈ 68 minutes across the first ~12 attempts. After that the delay is pinned at 1 hour, so the remaining ~23 hours of the window add ~23 more attempts — roughly 35 attempts over 24 hours. A brief blip is absorbed in seconds; a multi-hour outage still gets many patient chances; and a truly dead endpoint is retried a bounded number of times, not infinitely.

Name the trade-off — persistence vs the load your retries impose. More attempts over a longer window means fewer events lost to a temporary outage — and more wasted requests hammering an endpoint that's genuinely gone, plus a bigger backlog of pending deliveries you must store. Backoff spends the retries where they help (early, when a blip might already be over) and grows sparse where they don't; jitter spreads them so recovery isn't a stampede; the 24-hour deadline caps the waste. Every knob here is set against a server whose behavior you can't see and can't fix, so you tune for the flaky common case, not the dead one.

Move 3 — Trace the paths

One clean delivery, one retried delivery, and the ambiguous timeout that makes idempotency non-optional.

Path A — a clean delivery

  Event:  order.shipped  event_id=evt_9f3a  for merchant M (sub_id=771)

   1. Fan-out: match the event to subscriptions -> one delivery job:
        { event_id: evt_9f3a, sub_id: 771, url: https://M.example/hooks,
          payload: {...}, attempt: 1 }
      enqueue it (durable). The event pipeline is now DONE -- microseconds.
   2. A delivery worker claims the job (visibility timeout, L05 -- if the worker
      dies mid-POST the job reappears for another worker, no delivery lost).
   3. Sign:  sig = HMAC-SHA256(whsec_771, t + "." + body)
      POST https://M.example/hooks
        Webhook-Id: evt_9f3a
        Webhook-Signature: t=1690000000, v1=8a1f...
        body: {"type":"order.shipped","data":{...}}
      with a 30 s timeout.
   4. M verifies the signature, checks it hasn't seen evt_9f3a, does its work,
      records evt_9f3a, returns 200 FAST (it should ACK first, work async -- see
      Path C). Worker marks the delivery DELIVERED. Done in one attempt.

Path B — a failing endpoint, retried then dead-lettered

  Same event, but M.example is returning 503 (overloaded) or timing out.

   attempt 1  -> 503   -> schedule retry in ~1 s   (x jitter)
   attempt 2  -> 503   -> ~2 s
   attempt 3  -> timeout -> ~4 s
   ...doubling... capped at 1 h after ~12 attempts (~68 min in)
   ...hourly for the rest of the 24 h window...
   attempt ~35 -> still failing at t = 24 h
        -> STOP. Move the delivery to the DEAD-LETTER QUEUE.
        -> surface it on M's dashboard: "3,412 deliveries failed, [Replay all]".
           M fixes their endpoint, clicks replay -> we re-enqueue from the DLQ.

  Note what we do NOT do: we never drop it silently, and we never retry
  forever (that's an unbounded backlog + a hammer on a dead server). The DLQ
  is the honest middle -- parked, visible, replayable.

Path C — the ambiguous timeout (why the receiver MUST dedup)

   Worker POSTs evt_9f3a  ---->  M receives it, ships the confirmation email,
                                 records evt_9f3a...  then its response packet
   worker's 30 s timeout fires  X----  is lost / arrives after we gave up.

   Worker saw NO 2xx  ->  it MUST assume failure  ->  retry evt_9f3a.
   M receives evt_9f3a a SECOND time.
        - No dedup:  a SECOND confirmation email. Duplicate side effect.
        - With dedup: "seen evt_9f3a already" -> return 200, do nothing. Safe.

   We cannot tell "lost request" from "lost response" from our side (L07). So
   at-least-once is the best the wire allows, and the idempotency key is what
   converts our unavoidable duplicate into the receiver's harmless no-op (L13).

Path A is the 99% we design around but not for; Path B is the reliability machinery (retry, backoff, DLQ, replay) that earns the word "reliable"; Path C is the one that proves why the signature and the idempotency key aren't optional polish — they're the contract that makes "at-least-once from us" survivable "exactly-once effect on them" (Lesson 13). Every piece works as long as one broken endpoint can't take the delivery fleet down with it. That "as long as" is the wall.

Move 4 — Find the first bottleneck: one dead endpoint starving everyone

The queue isolated delivery from the event pipeline. But now all 10,000 deliveries/s share one delivery queue and one worker fleet — and a shared resource is a shared fate (Lesson 40). Watch what a single dead endpoint does to it.

Size the healthy fleet. At 10,000 deliveries/s and a 300 ms average call, Little's Law says the fleet must sustain L = 10,000 × 0.3 = 3,000 concurrent in-flight calls. Fine — that's the baseline it's built for.

Now one big merchant goes dark. Say that merchant receives 500 deliveries/s, and its endpoint now accepts connections and hangs until the 30 s timeout. With no isolation, those deliveries sit in-flight for the full 30 s each: L = 500/s × 30 s = 15,000 concurrent calls consumed by a single endpoint — 5× the entire healthy baseline. The worker fleet fills with zombie calls to one dead server; deliveries to 49,999 healthy endpoints queue behind them and go late. This is head-of-line blocking (Lesson 9's poison message) and the noisy neighbor (Lesson 40) in one: one broken receiver, hurting everyone, breaking no rule.

Name the trade-off — shared throughput vs isolation. One big queue and one worker pool is the cheapest, highest-throughput design — until any single endpoint's slowness becomes global slowness. The fix is to spend some of that efficiency on walls, exactly as Lessons 7/40 did: put a circuit breaker per endpoint, and bulkhead each endpoint's share of the workers.

How real webhook systems keep one endpoint from sinking the fleet:

• Per-endpoint circuit breaker (Lesson 7). Track consecutive failures per subscription. After a threshold (say 5 in a row), open the breaker: stop calling that endpoint entirely, park its deliveries on its own delayed-retry track, and send just one probe request periodically to see if it's back. A dead endpoint now consumes ~0 in-flight slots instead of 15,000 — the single highest-leverage fix.

• Per-endpoint concurrency cap (bulkhead, Lessons 7/40). Never let one subscription hold more than, say, a few dozen in-flight calls. Its own backlog can grow, but it can't reach past its lane to starve others — the greed is paid by the greedy.

• Separate first-attempt and retry paths. Keep fresh deliveries on a fast queue and route backed-off retries to a delay queue, so a flood of one endpoint's retries never blocks first attempts for everyone else (Lesson 9's partitioning).

The through-line: the delivery fleet is a shared pot, and the internet guarantees some tenant of it is always broken — so wall every endpoint off by default.

The other wall: ordering, which at-least-once quietly breaks

Retries and backoff mean deliveries reorder: if order.placed fails and retries while order.updated for the same order sails through, the receiver sees the update before the create. You could force per-subscription (or per-order) ordering with a single-flight partition (Lesson 9) — but then a stuck delivery blocks every later event for that key, and you've re-created the head-of-line wall on purpose. So most webhook systems don't promise ordering. Instead they make each event self-describing: carry the full current state (or a monotonically increasing version/sequence and a timestamp) so the receiver can ignore a stale event it has already superseded — pushing ordering, like dedup, onto the receiver (Lessons 35/37's "let the reader resolve it").

The four traps

  • Trap 1 — delivering inline / synchronously. Calling the endpoint from the request or event-processing thread welds your availability to theirs: one dead endpoint at a 30 s timeout ties up thousands of threads (Little's Law) and stalls the pipeline that produced the event. Always decouple through a durable queue and a separate worker fleet (Lessons 5/9).
  • Trap 2 — no signature (or a static token instead of an HMAC). A public webhook URL will receive forged POSTs; without an HMAC over the body the receiver can't tell your event from an attacker's, and a bearer token that leaks lets anyone forge any payload. Sign the body (and the timestamp, to stop replay) with a per-subscription secret, compared in constant time (Lesson 30).
  • Trap 3 — assuming exactly-once, or a fresh id per retry. At-least-once plus the ambiguous timeout guarantees the receiver sometimes gets an event twice; if the event_id changes per attempt, their dedup can't work and your retry re-runs their side effect (a second charge, a second email). Send a stable idempotency key and publish "dedup on it" as the contract (Lesson 13).
  • Trap 4 — one shared queue/pool with no per-endpoint isolation. Without a circuit breaker and a concurrency cap per endpoint, a single slow or dead receiver consumes the whole delivery fleet (head-of-line blocking + noisy neighbor) and everyone's webhooks go late. Break the circuit on a dead endpoint and bulkhead each one's share (Lessons 7/9/40).

Where we landed

An outbound webhook system delivering ~10,000 events/second (5,000 domain events, ~2 subscriptions each) to 50,000 endpoints we don't own or trust. Estimate killed the naive inline design: a third-party endpoint has no latency budget, and a dead one hangs to a 30 s timeout, so delivering from the event pipeline itself ties up L = λW thousands of threads on strangers' dead servers (100/s × 30 s = 3,000 frozen on the 1% that are down) and takes your own checkout pipeline down with a merchant's expired certificate — so decouple through a durable queue and a separate worker fleet (Lessons 5/9). Model gave the delivery path the four things a stranger forces on you: at-least-once (retry until 2xx, because the receiver can't detect a silent drop), an idempotency key (a stable event_id so their dedup makes your unavoidable duplicate a no-op — Lesson 13), an HMAC signature over body+timestamp (so they can prove it's you and reject forgeries and replays — Lesson 30), and exponential backoff + jitter over a 24-hour window (~35 patient attempts, spread so a recovering fleet isn't a thundering herd — Lessons 7/26), ending in a dead-letter queue with dashboard replay rather than a silent drop or an infinite hammer. Tracing showed the clean one-attempt delivery, the failing endpoint retried and dead-lettered, and the ambiguous timeout (request lost? response lost? — you can't tell, Lesson 7) that makes the idempotency key non-negotiable. The first bottleneck is the shared delivery fleet: one dead endpoint taking 500 deliveries/s to a 30 s timeout consumes 500 × 30 = 15,000 in-flight slots — 5× the entire healthy baseline — head-of-line blocking (Lesson 9) and the noisy neighbor (Lesson 40) at once, fixed by a per-endpoint circuit breaker (a dead endpoint drops to ~0 slots) and a per-endpoint concurrency bulkhead (Lesson 7), plus giving up on strict ordering in favor of self-describing, versioned events the receiver can order itself. The real lesson: a webhook inverts who calls whom, and that one flip means you can't block on the other side and can't drop their event, so reliability becomes retries, retries become duplicates, and duplicates become a burden — dedup, signature verification, ordering — that you deliberately push onto the receiver. Every reliability guarantee you add on your side is a piece of work the integrator must do on theirs. The standing tension: delivery reliability vs the burden pushed onto the receiver.

Next lesson stays with jobs that must fire reliably — but on a clock, and exactly once across a fleet:

• Distributed job scheduling: run thousands of cron jobs across many servers so each fires once at the right time — a leader or lease to stop two nodes double-firing the same job (Lessons 10/22), sharding the schedule for throughput, missed-fire catch-up after an outage, clock skew across nodes (Lesson 35), and idempotent jobs so a retry is harmless (Lesson 13). The trade shifts to timeliness vs exactly-once execution.
