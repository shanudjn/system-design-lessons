Load Balancing: Steering 40k req/s Across a Churning Fleet

For 41 lessons we've built the fleet — servers that scale out (Lesson 27), register and deregister as they churn (Lesson 34), and roll out new versions without an outage (Lesson 31). But we never asked the question at the very front door: when 40,000 requests a second arrive, which of the 286 servers does each one go to? Getting that wrong wastes the whole fleet — some boxes melt while others sit idle, and one sick server can swallow a slice of your traffic whole. The thing that decides is a load balancer, and it turns out "just spread them evenly" is deceptively hard the moment servers stop being identical. We'll estimate why a naïve round-robin — the fairest-sounding rule there is — collapses the instant one backend slows down. We'll model the two places balancing happens (Layer 4, per-connection; Layer 7, per-request) and the ladder of algorithms — round-robin → least-connections → least-latency → power-of-two-choices → consistent-hash for stickiness (Lesson 4). We'll trace a request through a healthy fleet, a fleet with one slow box, and a fleet being deployed to. And we'll hit the bottleneck hiding in plain sight: the load balancer is the one box every request must pass through, so it is the fattest single point of failure in the system (Lessons 7 & 26). The trade underneath every choice: even load distribution vs stickiness & simplicity.

The one system we'll design

The API tier from Lesson 27: 286 servers, offered 40,000 requests/second at peak. Each request takes about 40 ms of work, each server has 8 cores, so one server can finish at most 8 / 0.04 s = 200 req/s flat out; we run them at ~70% (Lesson 27's utilization knee), so each carries about 140 req/s. In front of the fleet sits a load balancer (LB): a single logical front door that every client connects to, which then forwards each request to one backend server. Its whole job is to answer one question, 40,000 times a second — "which backend?" — and it must keep answering it well while servers are dying, booting, and being deployed to underneath it. That last part is what makes it hard.

  THE FRONT DOOR  (clients -> load balancer -> fleet of 286 servers)

     clients                     LAYER 7 LB                    fleet
   (40,000 req/s)          reads the HTTP request         286 servers
        |                  picks a backend PER request    ~140 req/s each
        |   ==============>   +---------------------+   ==============>  [srv 1 ]
        |                     |  which backend?     |                   [srv 2 ]
        |                     |  - round robin?     |                   [srv 3 ]
        |                     |  - least conn?      |    ...            [ ...  ]
        |                     |  - power of two?    |                   [srv286]
        |                     |  - hash(user)?      |
                              +---------------------+
                                       ^
                    LAYER 4 LB below it: forwards whole CONNECTIONS
                    (never reads the request; one decision per TCP connection)

  Every request in the whole system funnels through this one box. Spread them
  well -> the fleet hums at 70%. Spread them badly -> some boxes melt at 100%
  while others idle at 20%, and the LB's own death is a 100% outage.

A load balancer is the component that receives every incoming request and forwards it to one of many identical backend servers, so no single server is overwhelmed and the fleet's capacity adds up. "Identical" is the assumption we'll spend the whole lesson testing — because a server that's mid-GC-pause, or running a slow disk, or half-drained for a deploy, is not identical to its neighbors, and a balancer that assumes it is will feed traffic straight into the sick one.

Words we'll earn before we lean on them

  • Backend — one of the interchangeable servers behind the balancer that actually does the work. Also called an upstream or a pool member.
  • Layer 4 (L4) — balancing at the transport layer: the LB forwards whole TCP/UDP connections by looking only at IP address and port, never reading the payload. Cheap and protocol-blind.
  • Layer 7 (L7) — balancing at the application layer: the LB reads the HTTP request (path, headers, cookies) and can make a fresh decision for every request. Richer, but it must parse and often terminate TLS.
  • Round-robin — hand requests to backends in fixed rotation: 1, 2, 3, …, 286, 1, 2, … Counts turns, ignores state.
  • Least-connections — send the next request to whichever backend currently has the fewest requests still in flight. Reacts to actual load.
  • Power-of-two-choices (P2C) — pick two backends at random, send to the less-loaded of the two. Nearly as good as scanning all of them, at a fraction of the cost and without the herd effect.
  • Sticky session (session affinity) — routing so a given client (or key) always lands on the same backend, e.g. to keep its local cache warm (Lesson 2) or its session in memory.
  • Health check — a probe (active) or observed failures (passive) the LB uses to decide a backend is unfit and pull it out of the pool (Lesson 34's readiness).
  • Connection draining — when retiring a backend (deploy/scale-in), stop sending it new work but let its in-flight requests finish first (Lessons 31 & 34's graceful shutdown).

Move 1 — Estimate: why the "fairest" rule breaks first

Round-robin sounds unimprovable: give every server an exactly equal number of requests, in strict rotation. On a healthy fleet it is fine — 40,000 / 286 ≈ 140 req/s to each, dead even. The problem is that "equal number of requests" is only "equal load" if every request costs the same on every server. The instant one server slows down, that assumption breaks — and round-robin keeps shoving traffic at the sick box because it counts turns, not trouble.

Set the scene. One server out of 286 hits a stop-the-world GC pause / a degraded disk and its requests now take 400 ms instead of 40 ms — 10× slower. Its real capacity just fell: 8 cores / 0.4 s = 20 req/s, down from 200.

What round-robin does. It has no idea. It keeps sending that server its fair share: 140 req/s. So the sick box takes in 140/s and drains 20/s. The other 120/s pile up in its queue (Lesson 28). In one second the backlog is 120 requests; in ten seconds it's 1,200; the queue grows without bound until every request routed there waits past the client's timeout and fails (Lesson 7's partial failure).

Price it. 1 / 286 ≈ 0.35% of all traffic — about 140 req/s — is routed into the tar pit, and essentially all of it fails or times out. Worse, those are slow-failing requests: they hold a client connection open for the full timeout (Lesson 7), and if clients retry (Lesson 7's retry storm) the sick box gets more load, not less. One degraded server out of 286 became a steady stream of user-visible errors — because the balancer was blind to backend state.

Name the trade-off — round-robin buys simplicity by ignoring information. It needs to track nothing about the backends: just a counter that says whose turn is next. That statelessness is exactly why it's fast, trivially correct, and why every LB offers it as the default. But the price of tracking nothing is reacting to nothing — it can't tell a healthy server from a dying one, so it distributes requests evenly while distributing load catastrophically. Round-robin is optimal when all backends are identical and all requests cost the same; it is worst-case-blind exactly when you most need help — when one backend is sick. Every smarter algorithm that follows buys back that lost information, and pays for it in state the LB must track.

Move 2 — Model: the layer you balance at, and the algorithm ladder

Two independent choices. First, where in the network stack the LB makes its decision (Layer 4 vs Layer 7). Second, which rule it uses to pick a backend (the algorithm). They're orthogonal — you pick one of each.

L4 vs L7: connections vs requests

A Layer 4 balancer works at the transport layer. It sees a TCP connection — a source IP:port and a destination — and forwards the packets, never looking inside. It makes one decision per connection: pick a backend when the connection opens, then pin every byte of that connection to it for its whole life. It's cheap (no parsing, no TLS), fast, and works for any protocol.

A Layer 7 balancer works at the application layer. It terminates the connection, reads each HTTP request, and makes one decision per request. That costs more — it parses every request and usually terminates TLS — but it can route by URL path or header, retry a failed request on another backend (Lesson 7), and split many requests from one connection across many servers.

  ONE HTTP/2 CONNECTION CARRYING 100 REQUESTS  (why the layer matters)

  L4 balancer (per CONNECTION):
     client ==== 1 long-lived connection ====>  picks backend #5 ONCE
                                                 ALL 100 requests -> backend #5
     -> one chatty client pins 100 requests to ONE server. Uneven. And a
        long-lived stream (WebSocket, gRPC, HTTP/2) can't be rebalanced mid-life.

  L7 balancer (per REQUEST):
     client ==== 1 connection, 100 requests ==>  demultiplexes the stream
        req 1 -> backend #5     req 2 -> backend #12    req 3 -> backend #40 ...
     -> the 100 requests spread across the fleet. Even. Costs: parse + TLS per req.

  Modern protocols MULTIPLEX many requests onto one connection, so "balance the
  connection" (L4) and "balance the request" (L7) drift far apart. Per-request
  granularity is why service meshes and API gateways balance at L7.

The algorithm ladder — each rung buys back information round-robin threw away

AlgorithmRuleWhat it fixes / costs
Round-robinstrict rotation 1,2,3,…Even counts. Blind to load — melts behind one slow box (Move 1). State: a counter.
Weighted RRbigger boxes get more turnsHandles unequal servers, still blind to dynamic slowness.
Least-connectionsfewest in-flight winsReacts to load: a slow box's in-flight piles up → it stops receiving. State: a live count per backend.
Least-latency (EWMA)lowest recent response time winsReacts to speed, not just count — catches a box that's slow but not yet backed up. State: a running latency average per backend.

The two rungs worth dwelling on are the two clever ones: power-of-two-choices (how to balance well cheaply) and consistent-hash (how to be sticky without wrecking rebalancing).

Power-of-two-choices: why picking the global best is a trap

The obvious upgrade from round-robin is "always send to the least-loaded server." It sounds ideal and it's a trap for two reasons. First, cost: scanning all 286 backends' loads on every one of 40,000 requests/second is a lot of bookkeeping. Second — and worse — the herd: if several load balancers (you always run more than one; see Move 4) all look at slightly stale load numbers and all pick the same "least-loaded" server, they stampede onto it together, it instantly becomes the most-loaded, and the load oscillates violently — Lesson 2's thundering herd, aimed at whichever box looked idle a moment ago.

Power-of-two-choices dissolves both problems with almost nothing. Pick two backends at random, send the request to whichever of the two has fewer in-flight. That's it. Reading two counters is cheap, and because each LB's two picks are random, they don't correlate into a herd. Yet the balance is astonishingly good: with purely random assignment the busiest server's backlog grows roughly like ln N / ln ln N above average (it keeps drifting worse as the fleet grows), while with two choices that gap collapses to about ln ln N — for any realistic N the imbalance stops growing and stays near-constant. One extra random pick turns "spread that slowly gets lumpier as you scale" into "spread that stays tight at any size."

Consistent-hash: stickiness without the reshuffle

Sometimes you want the same client to hit the same backend every time — to keep that backend's in-memory cache warm (Lesson 2) or its session state local. The naïve way, backend = hash(user) % N, has Lesson 3's fatal flaw: change N by one (a server dies or boots) and almost every user remaps to a different backend, every warm cache goes cold at once, and the origin gets hammered. The fix is Lesson 4's consistent hashing: place backends on a ring, hash each key to a point, walk clockwise to the owning backend. Add or remove one backend and only ~1/N of keys move — the rest stay put, caches stay warm.

Name the trade-off — stickiness vs even load. Affinity and balance pull in opposite directions. Sticky routing pins a key to a backend, so a hot key — a celebrity, a whale tenant (Lessons 3, 15, 40) — pins its whole flood onto one server, recreating the hot shard: perfect cache locality, terrible balance. Stateless per-request balancing (P2C) spreads load beautifully but can't keep a cache warm or a session local. You can't maximize both: the routing that keeps a backend's cache warm is exactly the routing that lets one hot key overwhelm it. The middle ground is bounded-load consistent hashing — hash for stickiness, but cap each backend at (1+ε)× the average and spill overflow to the next backend on the ring — buying most of the affinity while refusing to let any one box melt.

Move 3 — Trace the paths

Three runs on the same fleet: a healthy request, the one-slow-box scenario from Move 1 (now under a load-aware algorithm), and a request arriving mid-deploy.

Path A — healthy fleet, power-of-two-choices

  A request arrives at an L7 LB. Fleet healthy, all ~140 req/s, ~40 ms each.

   1. LB terminates TLS, reads the HTTP request.
   2. Pick 2 backends at random:  #58 (5 in-flight)  vs  #203 (3 in-flight).
   3. Send to #203 (the lighter). Forward the request, stream the response back.
   4. #203's in-flight ticks 3 -> 4, then back to 3 when it responds ~40 ms later.

  40,000 times a second, two random picks each, and the fleet stays within a
  hair of even -- no global scan, no herd, no per-backend hot spot.

Path B — one slow backend, least-connections (or P2C) heals it

Now replay Move 1's degraded server (400 ms/req, real capacity 20 req/s) — but under a load-aware algorithm instead of round-robin.

The self-correction. The sick box's requests don't finish, so its in-flight count climbs: 8 → 20 → 50 → 100 while healthy boxes sit at ~5. Least-connections looks at that count and simply stops choosing it. Power-of-two-choices does the same by accident — any time the sick box is one of the two random picks, it loses the comparison to its healthy rival, so it wins traffic only in the rare case it's picked against another overloaded box. Either way the sick server's arrival rate falls from 140/s toward its true 20/s, the backlog stops growing, and the ~0.35% of traffic that round-robin was killing is now spread over the 285 healthy boxes instead.

Then health checks finish the job. If the box stays bad, the LB's health check (Move 4) marks it unready and ejects it from the pool entirely (Lesson 34), and Lesson 7's retry sends any request that already failed there to a healthy backend. Load-awareness contained the damage in milliseconds; the health check removes the box in seconds.

Path C — a request arrives mid-deploy (connection draining)

  Rolling deploy (Lesson 31): backend #58 is being replaced by a new version.

   WRONG (no drain):  kill #58 now.
      -> its ~5 in-flight requests die mid-flight = 5 user-visible errors,
         plus every client with an open connection to it gets a reset.

   RIGHT (connection draining, Lessons 31/34):
   1. #58 DEREGISTERS from the LB pool first -> LB sends it NO NEW requests.
   2. #58 keeps serving its in-flight requests until they finish (a drain
      timeout, say 30 s, caps the wait).
   3. Only when drained (or timeout) does #58 shut down. New version boots,
      passes its READINESS check, and only THEN joins the pool (Lesson 34:
      register when ready, not when merely alive).

  Deregister-first, drain, then die -- the exact ordering a crash gets wrong
  and a graceful shutdown gets right. Zero dropped requests during a deploy.

Path A is the balancer doing its quiet everyday job; Path B is it absorbing a partial failure the way round-robin couldn't; Path C is it cooperating with deploys and churn so a routine rollout costs zero errors. All three assume the balancer itself is up. What happens when it isn't?

Move 4 — Find the first bottleneck: the balancer is the fattest SPOF in the system

Look back at the diagram. Every one of the 40,000 requests/second passes through the load balancer. It is, by construction, the one component whose failure is a 100% outage — a purer single point of failure than anything in Lessons 7 or 26, because there's no partial version of "the front door is gone." The whole apparatus of health checks, draining, and clever algorithms protects the backends; none of it helps if the thing doing the protecting dies. So the balancer must be made redundant — which immediately creates two new problems.

  MAKING THE FRONT DOOR NOT A SINGLE POINT OF FAILURE

  Problem 1: how do clients reach MANY balancers, and skip a dead one?
     - DNS round-robin: publish N LB IPs; clients pick one. Cheap, but DNS
       caches are stale (Lesson 34) -> a dead LB's IP lingers for the TTL.
     - Virtual IP + failover (VRRP/keepalived): one IP, a standby LB grabs it
       if the active dies. Fast failover, but only 1 active at a time.
     - Anycast: ONE IP announced from many locations via BGP; the network
       routes each client to the nearest healthy LB, reroutes if one drops.
       How large-scale front doors survive an LB (or whole PoP) death.

  Problem 2: each LB sees only ITS OWN connections (no shared global view).
     -> "least-connections" is least-connections-KNOWN-TO-ME, not global.
     -> Several LBs can independently pile onto the same "idle" backend
        (Lesson 2's herd). This is exactly why POWER-OF-TWO-CHOICES wins at
        scale: random picks don't correlate, so N balancers don't stampede
        the same box even with zero coordination.

Name the trade-off — redundancy removes the SPOF but destroys the global view. One balancer can, in principle, know the exact load on every backend and route perfectly. The moment you run several balancers for availability (and you must), each sees only the slice of traffic flowing through it, so no balancer has the truth anymore — and any algorithm that depends on a global "best backend" turns into a herd of balancers stampeding stale guesses. You trade the SPOF for a coordination problem, and the winning move is to pick algorithms that don't need coordination: randomized ones (power-of-two-choices) that stay well-balanced precisely because each balancer's choices are independent. Availability forces you toward algorithms that are good without a global view.

The four traps

  • Trap 1 — round-robin (or any blind algorithm) in front of servers that can slow down. It feeds a degraded box its full share (140 req/s into a 20 req/s box), building an unbounded queue that fails ~0.35% of all traffic. Use a load-aware algorithm (least-connections, least-latency, P2C) so a sick box's rising in-flight count routes traffic away from it automatically.
  • Trap 2 — a health check that probes a shared dependency. If every backend's /healthz pings the same database and that DB blips, every backend fails its check at once and the LB ejects the entire fleet — a correlated total outage (Lesson 34). Health-check what this instance can serve, not a shared resource everyone shares.
  • Trap 3 — L4 balancing in front of multiplexed / long-lived connections. One HTTP/2 or gRPC connection carries hundreds of requests; an L4 LB pins them all to one backend chosen once, so load skews hard and a stream can't be rebalanced mid-life. Balance at L7 (per request) when connections are long-lived or multiplexed.
  • Trap 4 — treating the load balancer as infrastructure that "just works." It's the fattest SPOF you own: every request crosses it. Run several (anycast / VIP failover / DNS), and choose coordination-free algorithms (P2C) so N balancers with no shared view don't herd onto the same backend. And drain connections on deploy (Lesson 31) or every rollout drops in-flight requests.

Where we landed

The front door decides which of 286 servers serves each of 40,000 requests/second, and getting it wrong wastes the fleet or takes it down. Estimate exposed the trap in the fairest-sounding rule: round-robin distributes request counts evenly but is blind to backend state, so one server slowed 10× (400 ms, real capacity 20 req/s) still gets fed its full 140 req/s — an unbounded backlog that fails ~0.35% of all traffic, because the balancer tracks turns, not trouble. Model laid out the two orthogonal choices: the layer (L4 forwards whole connections cheaply but pins multiplexed streams to one box; L7 reads each request, spreads them, and can retry — at the cost of parsing and TLS) and the algorithm ladder, each rung buying back the information round-robin discarded — least-connections and least-latency react to load, power-of-two-choices gets near-perfect balance from two random picks with no global scan and no herd (imbalance shrinks from growing like ln N/ln ln N to a near-constant ln ln N), and consistent-hash buys stickiness for warm caches (Lessons 2, 4) at the price of a hot key pinning to one box. Tracing showed all three working: a healthy P2C request, a sick box that a load-aware algorithm heals in milliseconds and a health check ejects in seconds, and a deploy that drops zero requests because the retiring box deregisters, drains, then dies (Lessons 31, 34). The first bottleneck is the balancer itself: every request crosses it, so it's the purest single point of failure in the system (Lessons 7, 26) — and making it redundant (anycast, VIP failover, DNS round-robin) destroys the global view of load, which is exactly why coordination-free randomized algorithms win at scale. The real lesson: balancing perfectly is easy when servers are identical and the balancer is alone; the entire craft is doing it well when servers are sick or churning and no single balancer can see the whole picture — the standing tension between even load distribution and stickiness & simplicity.
