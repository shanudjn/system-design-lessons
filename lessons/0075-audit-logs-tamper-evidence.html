Append-Only Audit Logs & Tamper Evidence: Prove Nobody Rewrote History

Lesson 74 made behavior changeable in seconds — anyone with the console can flip a flag, and Lesson 25's ledger can move money. So the next question is unavoidable: who did that, and can they cover it up? An audit log is the record of "who did what, when, to what" — every refund, every permission grant, every flag flip, every data deletion. This lesson builds one, and its whole point is a property most storage doesn't have: tamper evidence — you may not be able to stop someone from editing the record, but you can make any edit impossible to hide. We'll estimate and find the surprise: the volume is trivial, so scale is not the enemy — trust is, because the person you most need to catch is often the one holding the database. We'll model the log in layers — append-only storage, then a hash chain that links every entry to the one before it, then a Merkle tree that proves a single entry among billions, then an external anchor that turns "detectable in principle" into "detectable in fact." We'll trace a write, a full verification, a one-entry proof to an auditor, and a rogue admin trying to erase their own refund. And we'll find the first bottleneck: the chain is strictly sequential — each entry needs the previous entry's hash — so a verifiable global order fights write throughput, plus the deeper truths that tamper-evident is not tamper-proof, and that "you can never edit it" collides head-on with the right to be forgotten. The trade under all of it: verifiability & compliance vs write cost and the impossibility of edits.

The one system we'll build

One log for one platform's privileged actions. Every sensitive event is appended: admin_42 issued REFUND $9,400 on order_88f… at 14:02:07 from IP 10.2.…, admin_42 flipped checkout_v2 → 100% at 14:05:01 (Lesson 74), system deleted user U-8842 at 03:00:00 (Lesson 56). Auditors and regulators will later ask two questions, and the system must be able to prove the answers, not just assert them: (1) "show me everything admin_42 did last March" and (2) "prove this specific entry is real and hasn't been altered or deleted." The adversary is not a traffic spike. It's a rogue insider — an admin who does something they shouldn't, or an attacker who has stolen an admin's access — who then wants to edit or delete the log entry that would expose them. The data is tiny; the hardness is that the record must survive being attacked by someone with legitimate power over it.

The one idea the whole lesson turns on: you cannot assume you control the bytes. Whoever holds the disk can flip them. So an audit log's job is not to make editing impossible — that's a promise about storage you can't keep against a privileged attacker — but to make any edit leave a mark you can't erase. Every layer below exists to shrink the attacker's options: append-only makes editing against policy, the hash chain makes a single silent edit break everything after it, and the external anchor makes even a full rewrite detectable — because it commits a fingerprint of the log somewhere the attacker can't reach.

Words we'll earn before we lean on them

  • Audit log — an append-only record of privileged/sensitive actions: who, what, when, to what, from where. The evidence trail for security and compliance.
  • Tamper-evident vs tamper-proof — tamper-proof = editing is impossible (a promise you can't keep against a privileged insider). Tamper-evident = editing is detectable. We build the second and stop pretending we have the first.
  • Append-only / write-once (WORM) — storage that permits inserts but no updates or deletes (Write-Once-Read-Many). A policy, not a proof — an attacker under the policy can still rewrite bytes.
  • Cryptographic hash — a function (e.g. SHA-256) that maps any input to a fixed 32-byte fingerprint; change one bit of input and the output changes unpredictably, and you can't work backward or find two inputs with the same output. Our tamper detector.
  • Hash chain — each entry stores H_n = hash(entry_n ‖ H_{n-1}), folding the previous entry's hash into its own. Links entries into an order where changing one breaks all that follow.
  • Tip / head — the hash of the most recent entry. Because of the chain, the tip is a fingerprint of the entire log so far.
  • Merkle tree — a tree of hashes: leaves are entry hashes, each parent = hash of its two children, up to one root that summarizes everything.
  • Merkle / inclusion proof — the log₂(N) sibling hashes along the path from one leaf to the root, letting anyone verify "this entry is in the log" without seeing the other N−1 entries.
  • Consistency proof — a proof that a newer Merkle root contains everything the older root did (the log only grew, nothing was rewritten). Proves append-only cryptographically.
  • Anchor / notarize — periodically publishing the current tip (or root) somewhere outside your control — a second security domain, an external notary, another org, a public chain — so a fingerprint of the log exists where the attacker can't rewrite it.
  • Crypto-shredding — storing sensitive fields encrypted and "deleting" them by destroying the key (Lesson 30). Lets an immutable log honor a deletion request without breaking the chain.

Move 1 — Estimate: the surprise is that scale is not the problem

Start with the numbers, because they overturn the instinct. This is a big platform: 50 million privileged/audited actions a day, each entry ~500 bytes (who, what, when, target, IP, request id), kept 7 years for compliance.

The volume is trivial.

  • Rate: 50,000,000 / 86,400 s = 579 writes/s — a rounding error next to Lesson 27's 40,000 req/s.
  • Storage: 50M × 500 B = 25 GB/day → × 365 = 9.1 TB/yr → × 7 = ~64 TB for the full retention window. One box, or a cheap object store (Lesson 20).

So the audit log is not a scale problem. 579 writes/s and 64 TB are boring. If scale were the whole story, a single Postgres table with an index on (actor, timestamp) would be the entire design. The reason it isn't is the next paragraph.

The real cost is the cost of forgery. In that plain table, what does it take to erase the evidence of a fraudulent refund? One statement: DELETE FROM audit WHERE id = … or UPDATE audit SET amount = 0 …. It leaves no trace, runs in milliseconds, and the very person you're trying to catch — a rogue admin, or an attacker who owns an admin account — is exactly the person with the access to run it. The log's answer to "who did what" is only as trustworthy as your trust in whoever holds the database, and in an audit context that's the assumption you can't make.

So the design goal is to change the cost of forgery from "one silent statement" to "computationally rewrite everything after the entry and alter every fingerprint you already published to the outside world" — the second half of which the attacker cannot do. We're not optimizing throughput; we're raising the price of a lie until it can't be paid silently.

Why "just lock down the table permissions" isn't enough: tightening who can DELETE is real defense-in-depth and you should do it — but it's prevention, and prevention assumes the controls themselves aren't bypassed. An attacker who reaches the disk, the backups, or a DBA account is under, or around, your permissions. Tamper-evidence is the layer that still works after prevention fails: even if someone does edit the bytes, the edit is detectable. You want both — locks on the door and a seal that shows if the door was forced.

Move 2 — Model: four layers, each raising the price of a lie

Layer 1 — append-only storage: make editing against the rules

First, remove the easy path. The log is append-only: the application role can INSERT but has no UPDATE/DELETE grant; better still, store on WORM media or an object store with an immutability/retention lock (Lesson 20) so even an admin can't overwrite an object until its retention expires. This turns a silent one-statement edit into "go around the storage system." It is necessary and cheap — but it is a policy, not a proof: someone who compromises the storage layer itself is no longer bound by it. Append-only raises the bar; the next layers make crossing the bar visible.

Layer 2 — the hash chain: one silent edit breaks everything after it

When you append entry n, compute and store H_n = SHA-256(entry_n ‖ H_{n-1}) — the entry's content plus the previous entry's hash, folded together. Each entry now carries proof of everything before it. The consequence is the whole trick:

   Attacker edits entry 3 (change $9,400 -> $0):
     H3 = h(entry3 | H2)  ->  entry3 changed  ->  H3 is now DIFFERENT
     H4 = h(entry4 | H3)  ->  H3 changed      ->  H4 is now DIFFERENT
     ... every hash from 4 to the tip changes.  The TIP no longer matches.

A cryptographic hash makes this unavoidable: you can't tweak entry_3 and keep H_3 the same (that would be a hash collision, infeasible for SHA-256). So a single silent edit is impossible — altering any past entry forces you to recompute every hash after it, all the way to the tip. This is the honest limit of the chain, and the reason Layer 4 exists: recomputing that tail is cheap — SHA-256 runs at millions of hashes/second, and the algorithm is public — so an attacker with full write access to the log can rewrite the whole tail into a fresh, internally-consistent chain. The chain converts "edit one entry silently" into "rewrite the entire tail," which is progress but not victory. What it buys on its own: anyone who remembers a later hash can catch the edit, because the rewritten chain won't match the hash they remember.

Layer 3 — the Merkle tree: prove ONE entry among billions

An auditor rarely wants the whole log; they want to verify one entry — "prove this refund record is genuinely in the log and unchanged." Re-reading all entries to check the chain is a full scan. A Merkle tree fixes this: hash the entries into leaves, hash each pair up into parents, to a single root. To prove entry X is included, you hand over only the sibling hashes along its path to the root — log₂(N) of them — and the verifier recomputes the root from X + those siblings and checks it equals the trusted root.

                         ROOT = h(H12 | H34)
                        /                   \
                H12 = h(H1|H2)        H34 = h(H3|H4)
                 /       \              /       \
               H1        H2          H3        H4
              e1        e2          e3       [e4 = the entry to prove]
   Inclusion proof for e4 = { H3, H12 }  (the siblings on the path up).
   Verifier: h(H1..? ) no -> computes h(H3 | h(e4)) = H34, then
             h(H12 | H34) = ROOT.  Matches trusted root -> e4 is genuine.

The number that makes this matter. Over 7 years the log holds 50M × 365 × 7 = 127.75 billion entries (≈ 1.28×10¹¹). A tree over them is ⌈log₂(1.28×10¹¹)⌉ = 37 levels deep. So an inclusion proof is 37 sibling hashes × 32 bytes ≈ 1,184 bytes: you prove that one specific entry, out of 128 billion, is present and unaltered — with about 1.2 KB and 37 hash computations, not by shipping or re-reading terabytes. The chain gives order and completeness; the Merkle tree gives cheap, targeted proof. A consistency proof (also O(log N)) additionally proves a new root is a pure extension of an old one — nothing earlier was rewritten — which is append-only proven with math instead of trusted by policy.

Layer 4 — the external anchor: turn "detectable in principle" into "detectable in fact"

Layer 2 left a hole: an attacker who controls the log can rewrite the whole tail into a clean chain, and no one who only looks at the log can tell. The fix is to make sure the log's fingerprint also lives somewhere the attacker doesn't control. Periodically — every block, or every minute (~1,440 times/day) — publish the current tip / Merkle root to an external anchor: a separate security domain, an independent notary service, a partner org, or a public blockchain. Now the attacker's rewritten tail would produce a different root than the one already anchored, and they can't go back and change the anchor — it's outside their reach, possibly witnessed by thousands of parties.

The anchor is where the trust actually comes from. Append-only is policy; the chain links; the Merkle tree proves membership — but it's the anchor that makes forgery detectable in fact, because it externalizes the fingerprint. The cadence is a dial: anchor more often → a smaller window of entries an attacker could rewrite before the next anchor pins them (they can still rewrite everything since the last anchor); anchor less often → cheaper, but a larger un-pinned tail. This is the same shape as every freshness-vs-cost dial in the course (Lesson 2/14/74), now applied to "how recent is the last fingerprint we can trust."

LayerRaises forgery cost to…Its price
Append-only / WORM"go around the storage system"policy only; no edits/fixes ever, even legit ones
Hash chain"rewrite the whole tail, not one entry"strictly sequential writes (the Move-4 wall)
Merkle tree—proves ONE entry in ~1.2 KB / build+store the tree

Where signatures fit (and don't): you can also digitally sign each entry (Lesson 30) so its author is provable and it can't be forged by a third party. Signatures protect a single entry's content and authorship — but a signature on entry 3 does nothing to stop someone deleting entry 3 entirely, or reordering entries. Signatures protect content; the chain protects order and completeness; the anchor protects against a full rewrite. They compose — use all three — but don't mistake one for another.

Move 3 — Trace the paths

Follow one refund entry through a write, a full verification, a one-entry proof, and an attack.

Path A — append an entry

   admin_42 issues REFUND $9,400 on order_88f..

   [1] BUILD   e = {who, what, when, target, ip, req_id, seq=n}
   [2] CHAIN   read current tip H_{n-1};  H_n = SHA-256(e | H_{n-1})
   [3] APPEND  write (e, H_n) to append-only storage; advance tip to H_n
   [4] TREE    add leaf hash(e) to the Merkle tree; update the root
   [5] ANCHOR  (periodically, e.g. every minute) publish the current
               root/tip to the EXTERNAL anchor.
   Cost: one hash + one append. ~579/s is trivial. Note step 2 needs the
   PREVIOUS tip -> writes are serialized (the Move-4 bottleneck).

Path B — verify the whole log

   Auditor: "prove the log wasn't rewritten."
   -> re-walk from genesis: recompute H_i = h(e_i | H_{i-1}) for every i,
      check each stored H_i matches. Any mismatch = the first tampered entry.
   -> compare the final tip to the LAST EXTERNAL ANCHOR. Match => the whole
      history is intact AND matches an out-of-reach fingerprint.
   Full re-walk of 128B entries is a big scan -> in practice verify only
   SINCE the last trusted anchor + use a Merkle CONSISTENCY proof (O(log N)).

Path C — prove one entry to an auditor

   Auditor: "prove THIS refund entry is in the log, unaltered."
   -> server returns the entry + its Merkle INCLUSION proof:
      37 sibling hashes (~1,184 bytes) on the path leaf -> root.
   -> auditor recomputes the root from the entry + siblings, checks it
      equals the trusted (anchored) root. Match => genuine & present.
   No need to read the other 127,749,999,999 entries.

Path D — the attack: a rogue admin erases their refund

   admin_42 wants entry 3 (their $9,400 refund) GONE.

   Attempt 1: DELETE the row       -> seq gap (2,4 present, 3 missing) AND
                                      H4 = h(e4|H3) no longer verifies. CAUGHT.
   Attempt 2: EDIT amount to $0    -> H3 changes -> H4..tip all break. CAUGHT.
   Attempt 3: rewrite the WHOLE tail 3..tip into a clean new chain
              -> internally consistent, BUT the new tip != the root already
                 ANCHORED externally at 14:03. Can't alter the anchor. CAUGHT.
   The only "success" = tamper entries newer than the last anchor, before the
   next anchor fires -> shrink that window by anchoring more often.

Path A shows the cost is one hash and one append — nothing about tamper-evidence is expensive at 579/s. Path B and C show the two ways to trust the log: re-walk everything against the anchor (thorough, a scan) or prove one entry with a ~1.2 KB Merkle proof (targeted, O(log N)). Path D is the payoff: every silent edit an insider might try is turned into a mismatch that verification catches, and the only edits that escape are the ones newer than your most recent external anchor — which is exactly the window the anchor cadence controls. The mechanism looks airtight. Move 4 is where the honest limits live.

Move 4 — Find the first bottleneck: the chain is sequential, and evidence isn't prevention

The first bottleneck — a hash chain is strictly sequential. Every append needs the previous entry's hash (Path A step 2), so writes can't be parallelized the way a normal sharded table can — they form a single ordered line, each waiting on the one before. At 579/s that's a non-issue. But point this at a firehose — say Lesson 74's 100,000 events/s, or per-request logging — and the single global chain becomes the serializer: every writer, on every machine, must agree on and extend one shared tip. Two fixes, each naming its trade:

  • Batch into blocks. Don't chain single entries; collect N entries into a block, build a Merkle tree over the block (its root in one pass), and chain the block roots. One sequential step per block instead of per entry — the same amortization as a group commit. Cost: an entry isn't provable until its block closes (a small latency, the Lesson 29 batch-window trade).
  • Shard into independent chains. Give each partition (per region, per service) its own chain and its own anchor, exactly like Lesson 3/9's partition-for-throughput. You regain parallel writes but lose a single global total order — you can prove each shard's integrity, but "the exact order of two events on different shards" now needs logical clocks (Lesson 35) or a merge at read. The trade named: a single verifiable global order vs write throughput.

The second wall — tamper-evident is not tamper-proof, and it can't see what was never written. Everything above detects tampering after the fact; none of it prevents the edit, and none of it catches an action that bypassed the logger entirely. If an admin can do something without a log entry ever being created, no chain will show a gap, because there was never a link to break. So the log is only as complete as its choke point: the audited action and its log entry must be written together, atomically — the Lesson 33 outbox / same-transaction pattern — so "it happened but wasn't logged" is impossible, not merely unlikely. Add monotonic sequence numbers so a deletion shows up as a gap even before you check hashes. Detection also depends on someone actually verifying and on the anchor being real: an unwatched tamper-evident log is just a log with extra steps.

The third wall — the anchor is the true root of trust, so it must be genuinely out of reach. If you "anchor" the tip into another table in the same database, you've moved the trust, not removed it — the attacker who owns the DB owns the anchor too. The anchor only works if it lives in a different security domain: a separate account with different credentials, an external notarization/transparency service, a partner who counter-signs, or a public chain witnessed by many. The trade named: the stronger the independence (more parties, further out of reach), the more operational coupling and latency you take on — you now depend on an outside witness being available and honest. Weaker anchors (a second internal account) are cheaper but a determined insider with broad access can still reach them. Choose the anchor's independence to match the adversary you actually fear.

The fourth wall — "you can never edit it" collides with the right to be forgotten. Lesson 56's GDPR erasure says a user can demand you delete their personal data. An append-only, hash-chained log says you can never delete anything — and if you did, you'd break the chain and destroy the very integrity you built. Both are legal/ethical requirements; they look irreconcilable. The escape is crypto-shredding (Lesson 30): store the personal fields of each entry encrypted under a per-subject key, and honor "delete" by destroying the key, not the entry. The entry — and its hash, and the whole chain — stays byte-for-byte intact and still verifies; the sensitive content is now unrecoverable ciphertext. You keep the tamper-evident structure and make the data unreadable. The trade named: immutability vs erasability, reconciled by making the bytes present but meaningless rather than gone.

So the honest picture of a tamper-evident audit log: scale is not the enemy (579 writes/s, 64 TB/7yr — a plain table could hold it), trust is — the attacker is a privileged insider who can edit the very store you'd rely on, and in a plain table erasing evidence costs one silent statement. You raise the price of that lie in layers: append-only/WORM makes editing against the rules (policy, not proof); a hash chain (H_n = h(e_n ‖ H_{n-1})) makes a single silent edit impossible by breaking every hash after it (forcing a full-tail rewrite, which is cheap for the attacker — the chain alone isn't enough); a Merkle tree proves one entry among 128 billion in ~1.2 KB / 37 hashes and proves append-only via consistency proofs; and an external anchor — the real root of trust — makes even a full rewrite detectable by committing the tip somewhere the attacker can't reach. The first bottleneck is that the chain is strictly sequential (→ batch into blocks, or shard into independent chains and give up a single global order for throughput); around it, tamper-evident ≠ tamper-proof and can't see un-logged actions (→ atomic log-with-the-action at a choke point, monotonic sequence numbers, and someone who actually verifies), the anchor must be genuinely out of reach (→ a separate security domain, priced in coupling), and immutability fights erasure (→ crypto-shred: keep the bytes, destroy the key). Every choice names its price.

The deepest point: an audit log inverts the usual goal. Everywhere else in this course we made systems fast, elastic, and easy to change; here we deliberately make one part impossible to change and prove it. The value isn't storing the data — a table does that — it's producing evidence: a record whose integrity a hostile auditor can verify with math instead of trusting your word. And evidence has a cost the rest of the system doesn't pay: strict order (the sequential chain), permanence (no edits, colliding with privacy law), and an external witness you now depend on. Notice the whole thing is built from pieces you already own — hashing, Merkle proofs, an outbox choke point (L33), envelope encryption (L30), partition-for-throughput (L3/9), a freshness-vs-cost dial on the anchor (L2/14/74). The new idea is only the goal: not availability, not latency, but verifiable history. The standing tension: verifiability & compliance vs write cost and the impossibility of edits.

The four traps

  • Trap 1 — thinking append-only storage is enough. WORM and locked-down permissions are policy; a privileged attacker goes around them. Add the chain + external anchor so any edit is detectable, not just against the rules.
  • Trap 2 — a hash chain with no external anchor. An attacker with the data and the (public) hash function can rewrite the entire tail into a clean chain. Without a fingerprint committed somewhere out of reach, no one looking at the log alone can tell. The anchor is the actual root of trust.
  • Trap 3 — logging after the action, off the critical path. If an action can complete without its entry being written, tamper-evidence protects a log with holes. Write the entry atomically with the action (L33 outbox) at a choke point, and use monotonic sequence numbers so gaps show.
  • Trap 4 — assuming immutable means you can ignore privacy law. "Never delete" collides with the right to be forgotten. Don't break the chain to comply and don't ignore the law — crypto-shred: encrypt the personal fields, destroy the key on request, keep the entry and its hash intact.

Where we landed

We built the record that keeps every other system honest: a log of "who did what, when" that a hostile auditor can verify instead of trust. Estimate flipped the usual instinct — the volume is trivial (579 writes/s, ~64 TB over 7 years), so scale isn't the problem; trust is, because in a plain mutable table erasing evidence of a fraudulent refund costs one silent statement run by the very insider you're trying to catch. Model raised the price of that lie in four layers: append-only/WORM (editing against policy), a hash chain H_n = h(e_n ‖ H_{n-1}) (a single silent edit breaks every hash after it, so forgery means rewriting the whole tail — but that's cheap, so the chain alone isn't enough), a Merkle tree (prove one entry out of 128 billion with 37 hashes ≈ 1.2 KB, and prove append-only via consistency proofs), and an external anchor — the true root of trust — that makes even a full rewrite detectable by committing the tip somewhere the attacker can't reach. Tracing showed the write is one hash + one append, verification runs against the anchor (full re-walk or a targeted O(log N) proof), and every attack a rogue admin tries — delete, edit, full-tail rewrite — becomes a caught mismatch, leaving only the window newer than the last anchor. The first bottleneck: the chain is strictly sequential (→ batch into blocks or shard into independent chains, trading a single global order for throughput, L3/9/29); around it, tamper-evident ≠ tamper-proof and can't see un-logged actions (→ atomic log-with-the-action at a choke point + sequence numbers, L33), the anchor must be genuinely out of reach (→ a separate security domain, priced in coupling), and immutability fights the right to be forgotten (→ crypto-shred: keep the bytes, destroy the key, L30/56). The deepest point: an audit log deliberately makes one thing impossible to change and proves it — trading the speed and flexibility we prized everywhere else for verifiable history, and built almost entirely from pieces you already own. The standing tension: verifiability & compliance vs write cost and the impossibility of edits.
