API Gateways & the Edge: One Front Door for Many Backends

Lesson 42 answered which backend serves each request — it balanced load across a fleet. This lesson asks the question that sits one step earlier: what should the single front door in front of all those backends actually do? Once a system is 30 microservices instead of one monolith, a pile of work has no natural home — checking who the caller is, enforcing the rate limit, terminating TLS, deciding which service a URL belongs to, stitching six services' answers into one screen for a phone. Push that work into every service and you write it 30 times, 30 slightly-differently, with 30 chances to leave a hole. Pull it out to a shared front door and you write it once — but now every request in the system crosses one component, and that component is a single point of failure and a place every team's changes collide. We'll take a concrete edge — a mobile app's home screen over 40,000 requests/second to 30 backend services — and estimate what a gateway saves: a 6-call home screen collapsed from ~300 ms to ~106 ms, cross-cutting security written once instead of 30 times, and 20% junk traffic rejected before it touches a backend. We'll model what a gateway is and its seven jobs, and draw the line between the north-south gateway and the east-west service mesh. We'll trace a clean request, the aggregating BFF call, a request rejected at the edge, and a partial failure where one of six services times out. And we'll hit the wall the front door builds into the system: it is the fattest SPOF you own (Lessons 7/26/42) and, if you let it grow fat with business logic, a deploy bottleneck every team must queue behind (Lessons 31/36). The trade underneath: centralized cross-cutting concerns vs a fragile shared choke point.

The one system we'll design

Our backend is no longer one program. It's 30 microservices — a profile service, an orders service (Lessons 12/37), a cart, a recommendations service (Lesson 16), notifications (Lesson 26), promotions, and two dozen more — each owned by a different team, each deployed on its own schedule (Lesson 31), each behind Lesson 42's load balancer. The clients are phones and browsers out on the public internet, generating 40,000 requests/second at peak (Lesson 27's fleet). Every single request needs the same handful of things done to it before any service should touch it: the caller's identity has to be verified, the request has to be checked against a rate limit (Lesson 8), the TLS connection has to be terminated (Lesson 30), and the URL has to be matched to which of the 30 services owns it. And one common screen — the app's home tab — needs data from six of those services at once. The question is where all of that lives. Put it in the 30 services and you have 30 copies of security-critical code. Put it in one front door — an API gateway — and you have one copy, one choke point, one thing that must never go down.

An API gateway is a reverse proxy at the edge of your system that terminates the client's connection and applies the concerns every request shares — identity, rate limiting, TLS, routing, sometimes aggregation and observability — before handing a clean, trusted request to the right internal service. "Cross-cutting" is the load-bearing word: these are jobs that cut across every service, belong to none of them, and are dangerous to implement inconsistently. The gateway is where they get one home.

Words we'll earn before we lean on them

  • API gateway — a reverse proxy at the system's edge that all client traffic passes through, applying cross-cutting concerns and routing each request to a backend service.
  • Cross-cutting concern — a job that every service needs done but that belongs to no single service: authentication, rate limiting, TLS, logging. Centralizing it avoids re-implementing it N times.
  • Reverse proxy — a server that accepts a client's request and forwards it to one of several backends on the client's behalf, hiding the backends from the client (Lesson 42's load balancer is one).
  • North-south traffic — requests between the outside world (clients) and your system. The gateway's domain.
  • East-west traffic — requests between your own services, inside the system. The service mesh's domain (Lesson 34's sidecars), not the gateway's.
  • TLS termination — decrypting the client's encrypted connection at the edge so the request can be inspected and routed (Lesson 30).
  • Authentication (authN) — verifying who the caller is (validating a token). Distinct from authorization (authZ) — deciding what they may do.
  • Request aggregation / BFF (backend-for-frontend) — the gateway fanning one client request out to several services and composing their answers into one response shaped for that client.
  • Trusted-identity header — after the gateway authenticates the external token once, it forwards the verified identity to downstream services as a signed internal header, so they don't each re-validate the external token.
  • SPOF (single point of failure) — a component whose failure takes the whole system down. The gateway is the fattest one you own (Lessons 7/26).
  • Admission control — rejecting unwanted requests (unauthenticated, over-quota, abusive) at the edge before they consume backend work (Lesson 28).

Move 1 — Estimate: what the front door buys, and what it centralizes

Three numbers make the case for a gateway — and each one, flipped over, is also the cost. The gateway saves duplicated security code, saves mobile round trips, and saves backend CPU on junk; in exchange it becomes the one component that sees 100% of traffic.

1. Cross-cutting security, written once vs thirty times. Every request needs its token verified and its rate checked. Do that inside each service and the auth logic lives in 30 codebases. A change every team fears — rotating the signing key, tightening a rate limit, patching a token-parsing bug — becomes 30 deploys across 30 teams on 30 schedules, with 30 chances to drift out of sync. And the failure mode isn't gradual: it takes one service that forgot to add rate limiting to become the unprotected hole the whole system leaks through. Centralize the check at the gateway and it is one implementation, one deploy, one place to get right. The value isn't just less code — it's consistent enforcement: a rule applied in one place can't be forgotten in another.

2. Six mobile round trips collapsed to one. The home screen needs data from six services, and those calls often chain — fetch the profile, then that user's recent orders, then recommendations based on those orders — say 3 dependent hops. From the phone, each hop pays the mobile round-trip time (Lesson 14's speed-of-light tax over cellular), about 100 ms: 3 × 100 ms = 300 ms, plus a TLS handshake per connection and the phone having to know all six service addresses. Move the composition into the gateway (the BFF): the phone makes one request (1 mobile round trip, 100 ms) and the gateway runs those 3 chained hops over the internal LAN at ~2 ms each: 100 + 3 × 2 = 106 ms — a ~2.8× latency cut, and the phone holds 1 connection instead of 6.

3. Junk rejected before it costs anything. Say 20% of edge traffic is unauthenticated or abusive — expired tokens, scrapers, over-quota callers: 20% × 40,000 = 8,000 req/s. The gateway rejects each with a cheap 401/429 after a token check, so it never reaches a backend. Without the gateway that 8,000/s fans out into the 30 services and burns real CPU on work whose answer is "no" — Lesson 28's goodput problem. A front door is also a shield: the cheapest request to serve is the one you reject before it enters.

Name the trade-off — centralized cross-cutting concerns vs a fragile shared choke point. Every saving above comes from the same move: funnel all traffic through one place and do the shared work there. That is exactly what makes the gateway powerful (one place to enforce, compose, and shield) and exactly what makes it dangerous (one place whose failure is everyone's failure, one place every team's change must pass through). The gateway trades N scattered, inconsistent implementations for one consistent implementation that is also one shared dependency. The rest of the lesson is about keeping the first half of that trade while defusing the second.

Move 2 — Model: what a gateway is, and the seven jobs it does

A gateway is a reverse proxy (Lesson 42) with a pipeline of steps that run on every request before it reaches a service. The steps are the cross-cutting concerns, in order.

1. The request pipeline — seven jobs at the door

#JobWhat it doesBuilds on
1TLS terminationdecrypt the client connection once, at the edgeL30
2Authenticationvalidate the token; reject if invalid (401)L30
3Rate limit / quotatoken-bucket per API key; reject if over (429)L08
4Routingmatch path/host to a service; pick an instanceL34/L42
5Aggregation (BFF)fan out to several services, compose one replyL15
6Observabilityassign the trace ID, log, meter latencyL17
7Protocol translationexternal REST/JSON ↔ internal gRPC, etc.L18

Jobs 1–4 and 6 are the thin core every gateway does: terminate, authenticate, limit, route, observe. Jobs 5 and 7 — aggregation and translation — are where a gateway starts carrying logic, and where the "fat gateway" risk begins (Move 4). A crucial modelling choice makes the downstream services simpler: after job 2 authenticates the external token once, the gateway forwards the verified identity as a trusted-identity header (signed, and carried over mutual TLS so a service can trust it), so the 30 services never re-parse the external token. They authorize (what may this identity do?) but don't re-authenticate (who is this?). Authentication is centralized; authorization stays with the service that owns the resource.

2. The line that keeps the gateway from swallowing the mesh: north-south vs east-west

The gateway handles north-south traffic: the untrusted outside world talking to your system. That's why it does authentication, TLS from strangers, and public rate limiting. Traffic between your own services — east-west — is a different problem with a different tool: the service mesh (Lesson 34's sidecars), which handles service-to-service discovery, retries, mTLS, and load balancing inside the trust boundary. Confusing the two produces a gateway that every internal call is forced to detour through — re-creating the choke point on every hop. One front door for the outside; a mesh of side doors for the inside.

3. One gateway, or one per client? The BFF split

A phone and a desktop browser want different shapes of the same data — the phone a small, pre-composed home-screen blob; the browser a richer one. Cramming both into one gateway makes it a tangle where a mobile change risks breaking web. The backend-for-frontend pattern gives each client type its own thin gateway (a mobile BFF, a web BFF, a partner-API gateway), each owned by that client's team, each shaped for its client — all sharing the same downstream services. Aggregation logic (the fat part) lives in the per-client BFF; the shared cross-cutting core (auth, rate limit) can still be one layer in front. This is the main tool for keeping the gateway from becoming one god-object every team edits.

Move 3 — Trace the paths

Follow four requests through the edge: a clean authenticated call, the aggregating home-screen call, a request rejected at the door, and a partial failure inside an aggregation.

Path A — a normal authenticated request

  GET /orders/1234   (from an authenticated phone)

   1. TLS terminate            -- decrypt once at the edge (L30)
   2. authenticate token       -- valid? yes. extract user=alice
   3. rate-limit check         -- alice's bucket has tokens? yes (L08)
   4. route /orders/* -> orders-svc; pick an instance (L34 discovery, L42 LB)
   5. forward with a SIGNED identity header (user=alice), over mTLS
   6. orders-svc AUTHORIZES (may alice read order 1234?) -> yes -> responds
   7. gateway logs + records the trace span (L17), returns the reply

  The service never parsed the external token. authN centralized, authZ local.

Path B — the aggregating home screen (BFF)

  GET /home   (ONE request from the phone, 100 ms mobile RTT away)

  gateway fans out over the fast LAN (~2 ms/hop), chaining where needed:
     profile-svc --> orders-svc --> recommend-svc   (3 dependent hops)
                 \-> cart-svc  \-> notify-svc \-> promo-svc  (parallel)
     compose the six answers into ONE home-screen blob -> return.

   phone cost:  1 mobile round trip           = 100 ms
   gateway:     3 chained LAN hops @ 2 ms      =   6 ms
   ------------------------------------------------------
   total ~= 106 ms   vs   client-side 3x100 = 300 ms  (~2.8x cut)
                          and 1 phone connection instead of 6.

Path C — rejected at the edge (the shield)

  GET /orders/1234   with an EXPIRED token   (or alice is over quota)

   1. TLS terminate
   2. authenticate -> INVALID  ->  return 401  (or, over-limit -> 429, L08)
   -------------------------------------------------------------------
   STOP. No routing, no backend touched. ~8,000 req/s of junk (Move 1)
   die here for the cost of a token check -- admission control (L28).
   The 30 services never spend a cycle on a request whose answer is "no".

Path D — a partial failure in aggregation

  GET /home  -- but recommend-svc is slow/down this second (L07 partial failure)

  NAIVE:  gateway waits on all six -> recommend-svc hangs to a 3 s timeout
          -> the WHOLE home screen fails. One service's fate = all six's.

  BETTER: per-call timeout + graceful DEGRADE (L07):
          return the 5 that answered + a null/placeholder for recommendations.
          The home screen renders; the "for you" row is empty, not a spinner.

  The trade aggregation creates: composing N services into 1 response COUPLES
  their fates unless you explicitly degrade. The gateway must own a timeout
  and a fallback PER downstream call, or it inherits the worst of all six.

Path A is the everyday request and shows the identity trick: authenticate once, pass a signed header, let each service authorize locally. Path B is the aggregation win — but notice it is also the moment the gateway stopped being a dumb proxy and started running application logic. Path C is the gateway earning its keep as a shield, killing junk for the price of a token check. And Path D is the bill for Path B: the instant you compose six services into one answer, one slow service can sink the whole screen unless the gateway holds a per-call timeout and a fallback. Every one of these paths ran through one box. That box is the bottleneck.

Move 4 — Find the first bottleneck: the front door is the fattest SPOF you own

By design, 100% of traffic crosses the gateway. That is its power in Moves 1–3 and its danger here: if the gateway is down, every service behind it is unreachable even though every one of them is healthy — a total outage from a single component (Lessons 7/26/42, the same shape as the load-balancer SPOF). And there is a second, slower failure that has nothing to do with uptime: the gateway becomes the place every team's change must pass through, and a shared component that everyone must edit is a deploy bottleneck with a 100% blast radius (Lesson 36).

The availability SPOF — fix it by making the gateway a disposable herd. A gateway that holds no per-request state is stateless — token-based auth means there's no session to pin to a box (Lesson 26's "make the stateful thing cheap to lose"). So run many gateway instances behind Lesson 42's load balancer (or anycast / a floating VIP), sized with N+1 headroom (Lesson 27) so any one can die and the survivors absorb it. At 40,000 req/s, if one instance handles ~8,000 req/s you run 5 + 1 = 6 for single-fault tolerance. The gateway stops being a point of failure by being many interchangeable ones. Health-check and drain them on deploy exactly like any other service (Lessons 31/34).

The deploy-bottleneck SPOF — fix it by keeping the gateway thin. The tempting move is to keep adding logic to the gateway: response transformation, request validation, business rules, one more team's special case. Each addition makes the gateway fatter, more fragile, and more coupled — and turns it into the 1990s ESB (enterprise service bus), the shared middle everyone waited behind. The discipline: the shared gateway does only cross-cutting concerns (auth, rate limit, routing, TLS, observability); business logic and aggregation move out — into per-client BFFs owned by client teams, and into the services themselves. Route configuration is declarative and owned per team (a service ships its own route/rate-limit config as data), so adding a service isn't a change to the gateway's code. A gateway that carries only concerns nobody owns stays small; a gateway that carries logic everybody owns becomes the bottleneck the microservices were meant to remove.

The four traps

  • Trap 1 — the god gateway (ESB reborn). Piling business logic, response transforms, and every team's special case into the shared gateway makes it fat, fragile, and a deploy bottleneck every team queues behind (Lesson 36's shared-component blast radius). Keep the shared layer to cross-cutting concerns only; push logic and aggregation out to per-client BFFs and the services.
  • Trap 2 — treating the gateway as "infra that just works." It's the one component 100% of traffic crosses — the fattest SPOF you own (Lessons 7/26/42). It needs many stateless instances behind a load balancer, health checks, N+1 headroom, and drain-on-deploy, or its single failure is a total outage.
  • Trap 3 — re-authenticating at every hop, or trusting the internal call blindly. Making all 30 services re-validate the external token defeats the point of centralizing auth; but blindly trusting any internal call lets an attacker who reaches a service directly bypass the gateway (the confused-deputy hole). The fix is both: authenticate once at the edge, pass a signed identity header over mTLS (Lesson 30) so services trust the gateway but nothing else — zero-trust internally.
  • Trap 4 — aggregating without per-call timeouts and fallbacks. Composing six services into one response couples their fates: one slow service hangs the whole screen (Lesson 7). Every downstream call in an aggregation needs its own timeout and a graceful degrade (return the parts that answered), or the gateway inherits the worst latency and lowest availability of everything it fans out to.

Where we landed

Once a system is many services instead of one, a set of jobs — identity, rate limiting, TLS, routing, composition, observability — belongs to every service and to none. This lesson gave them a home: the API gateway, the front door all north-south traffic crosses. Estimate made the case in three numbers, each a saving that is also a cost: cross-cutting security written once instead of across 30 codebases (30 deploys → 1, and no forgotten hole); a 6-call home screen collapsed from 3×100 = 300 ms to 100 + 3×2 = 106 ms by moving composition into a BFF; and 20% × 40,000 = 8,000 req/s of junk rejected at the door for the price of a token check (Lesson 28's shield). Model laid out the gateway's seven jobs and the identity trick that keeps services simple — authenticate once, forward a signed identity header, let each service authorize locally — plus the two lines that keep a gateway from swallowing the system: north-south (gateway) vs east-west (service mesh), and one shared gateway vs per-client BFFs. Tracing walked a clean request, the aggregating home screen, a junk request killed at the edge, and the partial failure that is aggregation's bill — one slow service sinks the screen unless the gateway holds a per-call timeout and fallback (Lesson 7). The first bottleneck is the front door itself, failing two ways: as the fattest SPOF you own (fixed by making it a stateless, disposable herd behind Lesson 42's LB, N+1, drained on deploy) and as a deploy bottleneck (fixed by keeping it thin — cross-cutting concerns only, business logic and aggregation pushed out to BFFs and services, routes as per-team declarative config). A gateway is worth it exactly when the concerns it centralizes are ones no single service should own and every service must get right — and it stays worth it only as long as you keep it thin and redundant, so the one door that lets everyone in never becomes the one door that keeps everyone out. The standing tension: centralized cross-cutting concerns vs a fragile shared choke point.

Next we zoom out one more level — from the front door of one region to routing across many:

• Global traffic management (GeoDNS / anycast / failover): this lesson put a front door in front of one fleet. Lesson 23 ran the system live in more than one region. The next question is how a user in Sydney reaches the nearest healthy region — geo/latency-based DNS or anycast to steer them, health-based failover to drain a dead region, and a DNS TTL that bounds how fast you can pull traffic away from one (Lessons 10/11's split-brain risk, now at the routing layer). The trade shifts to proximity & availability vs routing staleness & complexity.
