API Design & Pagination: Paging a Feed Without Dupes or Slowdowns

Lesson 17 ended on a hint: the re-ranker made 100 round trips where 1 batch would do, and that N+1 lived in the shape of its API. This lesson designs that surface itself. We take one concrete endpoint — GET /feed, the home feed from Lesson 15 — and make it return posts a page at a time to a phone. The obvious design, ?limit=20&offset=40, has two bugs that only show up in production: the same post appears twice, and page 50,000 is 50,000× slower than page 1. We'll estimate why you page at all, model offset vs cursor pagination and see exactly why one breaks, trace a request through REST / RPC / GraphQL and watch the N+1 reappear, then hit the wall every public API hits: you can never change it again without breaking someone. The trade-off underneath: client convenience vs server cost and stability.

The one endpoint we'll design

A mobile app opens and asks the server for the user's home feed — the reverse-chronological stream of posts from people they follow, built back in Lesson 15. The user follows ~200 accounts; their feed holds thousands of posts and grows every second. The phone shows about 10 at a time and loads more as the user scrolls. So the server must hand back the feed in pages, not all at once. The whole tension is on one screen: what does "give me the next page" mean when the feed is changing while you read it?

  THE FEED, paged two ways         (newest on top, page size = 3)

  T0: app fetches page 1                T1: 2 new posts arrive, app fetches page 2
  ┌──────────────┐                      ┌──────────────┐
  │ P10          │ row 0  ┐             │ P12  (NEW)   │ row 0
  │ P9           │ row 1  │ page 1      │ P11  (NEW)   │ row 1
  │ P8           │ row 2  ┘  seen       │ P10          │ row 2
  ├──────────────┤                      │ P9           │ row 3 ┐  OFFSET 3
  │ P7           │ row 3  (page 2       │ P8           │ row 4 │  LIMIT 3
  │ P6           │ row 4   = OFFSET 3)  │ P7           │ row 5 ┘  = P9,P8,P7
  │ P5           │ row 5               │ P6           │ row 6
  └──────────────┘                      │ P5           │ row 7
                                        └──────────────┘
   OFFSET page 2 = P9, P8, P7  ──►  P9 and P8 were ALREADY on page 1.
   The 2 inserts pushed every row down by 2, so "row 3" now points at
   a post the user already saw. Result: duplicates (and after deletes: skips).

   CURSOR fix: page 1 also returns a cursor = "you stopped after P8".
   page 2 asks  WHERE post < P8  →  P7, P6, P5.  The 2 new posts sit
   ABOVE the cursor and never move the window. No dupes. No skips.

Offset counts positions in a list that is shifting under it; a cursor names a place in the list that stays put. That single difference is the whole lesson in one line — everything below earns it with numbers.

Words we'll earn before we lean on them

  • Endpoint — one addressable operation the API offers, e.g. GET /feed. The client's whole view of the server is the set of endpoints and their shapes.
  • Pagination — returning a large result a page at a time instead of all at once, with a way to ask for the next page.
  • Offset pagination — "skip N rows, then give me the next K" (LIMIT K OFFSET N). Pages are numbered positions.
  • Cursor pagination — "give me the K rows after this marker." The marker (the cursor) encodes the sort key of the last row you saw.
  • REST / RPC / GraphQL — three styles for shaping the request surface: resources+verbs, named actions, and a client-chosen field query. Defined when we reach them.
  • Over-fetch / under-fetch — the API returns more fields than the screen needs (wasted bytes) or too few (forcing extra requests).
  • N+1 — fetching a list of N things, then making one more request per thing (N more) instead of one batched request. Lesson 17's slow hop.
  • Versioning — how you change a published API without breaking clients that already depend on its old shape.
  • Backward compatible — a change old clients can survive: they keep working as if nothing changed.

Move 1 — Estimate: why page at all, and how big a page

Before choosing how to page, price not paging, then size a sensible page.

Worked: return the whole feed vs one page.

• A hydrated post (text + author + a couple of thumbnails' worth of metadata) is about 2 KB on the wire.
• A active user's feed backlog is easily 5,000 posts.
• Return it all: 5,000 × 2 KB = 10 MB per feed open. On a phone on cellular at ~2 MB/s that's ~5 seconds before the first post paints, and the user reads maybe 30 of the 5,000.
• Return one page of 20: 20 × 2 KB = 40 KB → paints in ~20 ms, and you only build the next page if they keep scrolling.

Paging turns a 10 MB, 5-second, mostly-wasted transfer into a 40 KB, near-instant one. Page size is the dial: too small (say 3) and a fast scroller makes hundreds of round trips; too large (say 500) and each page is 1 MB and you're back to the wasteful transfer. 20–50 is the usual range — enough to fill a few screens, small enough to stay cheap.

Name the first trade-off — round trips vs payload size. A smaller page means more requests (each with its own latency and overhead); a larger page means fewer requests but more bytes and work per request. The page size is where you balance them, and it's the same "narrow and cheap vs wide and expensive" dial you've now seen in L14 (CDN objects) and L16 (retrieve vs re-rank).

Move 2 — Model: offset vs cursor, and why offset breaks

Both designs return K rows and a way to get the next K. They differ in what "next" means, and that difference decides both correctness and speed.

Model A — offset: skip N, take K

The request is GET /feed?limit=20&offset=40 and the query is literally ORDER BY created_at DESC LIMIT 20 OFFSET 40. Page P is offset = (P−1) × 20. It's dead simple, it lets you jump to any page ("go to page 7"), and it's exactly how a numbered search-results footer works. It has two failure modes, and both come from the same fact: offset is a count of positions in a list that keeps changing.

Bug 1 — duplicates and skips under writes (the diagram at the top). The user fetches page 1 (rows 0–19, the 20 newest). While they read, 5 new posts arrive at the top. They scroll; the app fetches page 2 = OFFSET 20. But every existing post has been pushed down by 5, so the row that was at position 20 is now at position 25 — and OFFSET 20 now lands on what used to be position 15. The 5 posts at positions 15–19, already shown on page 1, appear again on page 2. Symmetrically, if 5 posts are deleted above the window, OFFSET 20 skips 5 unseen posts. The list moved; the offset didn't know.

Bug 2 — deep pages get linearly slower. To serve OFFSET 1,000,000 LIMIT 20, the database can't jump straight to row 1,000,000 — it must walk the index and count past a million rows, discarding every one, before it starts collecting your 20. So:

• Page 1 (OFFSET 0): read ~20 rows.
• Page 50,000 (OFFSET 1,000,000): read ~1,000,020 rows, throw away 1,000,000, return 20.

The work is O(offset + limit) — it grows with how deep you page. Page 50,000 does 1,000,020 / 20 ≈ 50,000× the row-reads of page 1 for the same 20 results. Deep offset pagination is a scan wearing a LIMIT. Every "load more" gets slower the further the user scrolls — the exact opposite of what you want.

Model B — cursor: give me K rows after this marker

The request is GET /feed?limit=20&after=<cursor>. The cursor encodes the sort key of the last row the client saw. If we sort by newest-first, the query becomes a range seek, not a skip:

  SORT KEY = (created_at DESC, id DESC)      ← id breaks ties on equal timestamps

  page 1:  SELECT ... ORDER BY created_at DESC, id DESC
           LIMIT 20;
           last row = (ts=1699.812, id=P8801)   ──►  cursor = base64("1699.812|P8801")

  page 2:  SELECT ...
           WHERE (created_at, id) < (1699.812, P8801)   ← seek straight here
           ORDER BY created_at DESC, id DESC
           LIMIT 20;

  the index is already sorted by (created_at, id), so "< cursor" is a direct
  seek to that leaf, then read the next 20.  Cost = O(20), ANY page depth.

Two things fall out for free. It's stable under writes: new posts have a larger created_at, so they sort above the cursor and never enter the window you're paging down through — no duplicates, no skips (this is the same insight as Lesson 04's ring and Lesson 09's committed offset: name a stable place, don't count shifting positions). It's fast at any depth: because the index is sorted by exactly the cursor's key, WHERE (created_at, id) < cursor is a direct seek to that leaf — page 50,000 reads 20 rows, same as page 1. That's the B-tree seek from Lesson 12 doing the work an offset threw away.

Worked: why the cursor needs two fields. Suppose 3 posts share the exact millisecond ts=1699.812. If the cursor were just the timestamp, WHERE created_at < 1699.812 would skip all three (strictly less) or, with <=, re-serve all three every page — a tie you can't page through. Adding the unique id as a tiebreaker makes the sort key total (no two rows compare equal), so (created_at, id) < (1699.812, P8801) resumes at exactly the right row. A cursor must encode a strictly-ordered key; append a unique id whenever the primary sort can tie.

Name the trade-off — random access vs stability & speed. Offset gives you something cursor can't: jump to an arbitrary page number ("page 7 of 400"). Cursor gives you correctness under a live list and O(limit) cost at any depth, but only lets you go next / previous from where you are — there's no "page 7," because a cursor is a place, not a count. For a numbered report or a static table, offset is fine. For an infinite, changing feed, cursor is the right default. Choose by whether the data moves and whether users jump around.

Move 3 — Trace the request surface: REST vs RPC vs GraphQL (and N+1 returns)

Pagination decides how much comes back per call. The API style decides how the client asks and what shape it gets. Trace the same "load my feed with author names" through three styles.

Path A — REST: resources and verbs

REST models the server as resources (nouns, each with a URL) acted on by standard HTTP verbs. GET /feed?limit=20&after=… reads a page; GET /users/42 reads a user; POST /posts creates one; DELETE /posts/99 removes one. It's predictable and cache-friendly (a GET is safe to cache — Lesson 14), and the verb tells you the effect. The weakness is fit: the feed endpoint returns a fixed shape. If the phone needs author names but the endpoint returns only author_id, the client must make a second call per author — under-fetching. If it returns 30 fields and the screen shows 4, that's over-fetching. One fixed shape can't fit every screen.

Path B — RPC: named actions

RPC (remote procedure call) models the server as functions you call by name: getFeed(userId, limit, cursor), getAuthors(ids). There's no resource/verb ceremony — you expose exactly the operations you want, which fits actions that aren't neatly a noun (transferMoney(a, b, amt) is an awkward REST resource but a natural RPC). The cost is you lose the uniform, cacheable, guessable surface REST gives you: every server invents its own verbs, and a plain GET-style cache can't tell a read from a write. gRPC is the common modern form.

Path C — GraphQL: the client picks the fields — and the N+1 comes home

GraphQL exposes one endpoint and lets the client send a query naming exactly the fields it wants, including nested ones, in a single round trip. It kills over- and under-fetching from the client's side:

  POST /graphql
  { feed(limit: 20, after: "…") {          ← one request, exactly the fields the
      text                                    screen needs, nested authors inlined
      author { name avatarUrl }
  } }

The client is delighted: 20 posts with their authors, no extra round trips, no wasted fields. But look at what the server must now do to resolve author for each of the 20 posts. The naïve resolver runs one query for the 20 posts, then — for each post — one query to fetch its author:

Worked: the N+1, exactly Lesson 17's slow hop, now on the server.

• Naïve: 1 query for the page + 20 author lookups = 21 queries.
• If each query is a ~2 ms round trip to the database: 21 × 2 ms = 42 ms.

The fix — batch (the same fix as L17): collect all 20 author_ids from the page, then run one query: SELECT * FROM users WHERE id IN (…20 ids…).

• Batched: 1 page query + 1 author query = 2 queries = 2 × 2 ms = 4 ms.

That's a 42 / 4 ≈ 10× cut, and it's the identical N+1 the trace exposed in Lesson 17 — 100 serial feature-store calls collapsed into one batch. GraphQL doesn't create the N+1; it moves the temptation from the client to the server resolver. The batching pattern (a "data loader" that gathers ids within a tick and fires one IN query) is how every serious GraphQL server survives.

Name the trade-off — client flexibility vs server complexity. GraphQL hands the client exactly what it asks for (great for many diverse screens), but each flexible query becomes a resolution tree the server must execute efficiently, or it silently fans out into N+1 queries and unbounded, hard-to-cache work. REST's rigid shapes are less convenient but easier to cache, rate-limit (L08), and reason about. There's no free lunch: you move the effort, you don't delete it.

Move 4 — Find the next bottleneck: you shipped it, now you can't change it

The endpoint works. Then a million phones install it — and every one hard-codes the exact shape of your response. The moment the API is public, its shape is a promise. Break the promise and you break apps in the field that you can't force-update.

Wall 1 — additive changes are safe; removals and renames are not

Worked: which changes break a client? An old app reads response.author.name and ignores fields it doesn't recognize.

• Add a new field author.verified → old app ignores it. Safe (backward compatible).
• Rename name → displayName → old app reads author.name, gets null, shows a blank. Breaks.
• Remove avatarUrl, or change its type (string → object) → old parser errors. Breaks.
• Change pagination default from 20 to 50 → old app that assumed 20 mis-lays its list. Subtly breaks.

The rule: add, never remove or rename, in place. Additive change is backward compatible; anything that removes, renames, or re-types a field is not.

Wall 2 — when you must break it: versioning

Sometimes you genuinely must change the shape. Then you run the old and new shapes side by side and let clients move at their own pace. Two common ways to name the version:

Where the version livesLooks likeTrade-off
In the URL pathGET /v2/feedObvious, easy to route and cache separately; but /v1 and /v2 are now two code paths you maintain until /v1 is retired.
In a request headerAccept: application/vnd.app.v2+jsonKeeps one clean URL per resource; but the version is invisible in logs/caches and easy to forget.

Either way the real cost is the same: every version you publish is a contract you must keep serving until the last client on it upgrades — often years for mobile apps you can't force-update. So you version rarely and reluctantly, prefer additive changes that need no new version at all, and when you do cut /v2, you publish a deprecation window for /v1 and measure its traffic before switching it off.

Name the last trade-off — evolvability vs stability. A rigid, versioned contract gives clients stability (their app keeps working) at the cost of your freedom to change (you carry old shapes for years). A loose, always-changing API gives you freedom at the cost of breaking clients. Good API design buys most of the evolvability for free by making changes additive, so you rarely have to spend a version at all.

Where we landed

We designed one endpoint — GET /feed — and made every choice pay for itself. Estimate showed why you page at all: 5,000 × 2 KB = 10 MB and ~5 s of mostly-wasted transfer collapses to a 40 KB page, with page size (20–50) as the round-trips-vs-payload dial. Model pitted offset against cursor: offset counts positions in a shifting list, so it serves duplicates under inserts and reads O(offset) rows — page 50,000 does 50,000× the work of page 1 — while a cursor names a stable place (created_at, id), sits still under writes, and seeks in O(limit) at any depth (the L12 B-tree seek doing the work offset threw away), needing a composite key so ties don't skip or repeat rows. Tracing REST (resources+verbs, cacheable but one fixed shape → over/under-fetch), RPC (named actions, flexible but non-uniform), and GraphQL (client picks fields → but the resolver reintroduces the N+1, 21 → 2 queries, 10×, the very same batch fix from Lesson 17) named client flexibility vs server complexity. The next bottleneck was the API itself once published: additive changes are safe, removals/renames break clients, and when you truly must break the shape you version (URL vs header) and carry the old contract for years — evolvability vs stability. The thread: an API is a promise about shape and cost; page it so it's cheap, cursor it so it's stable, batch it so it's fast, and grow it additively so you rarely have to break the promise.
