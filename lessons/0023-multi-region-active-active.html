Multi-Region Active-Active: Two Continents, One Cart, and the Write That Can't Be Merged

Every lesson so far kept safety by forcing one writer at a time — one leader (Lesson 10), one lock holder (Lesson 22), one shard owner (Lesson 03). Now we break that rule on purpose. To serve shoppers on two continents fast, we put a full copy of the service in Virginia and another in Frankfurt, and let both accept writes locally — active-active. The instant we do, the single writer is gone: a shopper's cart can be edited in Virginia and Frankfurt in the same 90 milliseconds, with no lock to serialize them. So the question stops being "who holds the lock?" and becomes "when two edits happen at once, how do the copies agree afterward?" We'll estimate the cross-region latency that forces this design and the availability it buys, model active-active with async replication and the two ways to resolve a conflict — last-write-wins vs a CRDT — trace concurrent cart edits through both, and hit the wall: some state (a bank balance) has a global invariant that no merge rule can save. The trade underneath everything shifts from Lesson 22's safety-vs-liveness to a new one: local writes vs global order.

The one system we'll design

A global e-commerce site. Shoppers everywhere want their cart to feel instant — every tap that adds or removes an item should return in a few milliseconds, not after a round trip across an ocean. So we run the service in two regions: us-east (Virginia) and eu-central (Frankfurt). Each region has its own database. We route every shopper to their nearest region, and that region serves their reads and their writes locally. Then the two regions copy each other's changes in the background so both hold the whole world's data.

That's active-active: every region is live and accepts writes. It's fast (writes are local) and resilient (if one region dies, the other still serves everyone). The catch is the whole lesson: the same cart can be written in both regions before either has heard about the other. There is no single writer, so there is no natural answer to "what's the correct final value?" We have to build that answer.

  THE HAZARD WE'RE HERE TO KILL   (replication lag ~90 ms one way)

  Shopper's cart starts as { }  in BOTH regions.

  t=0ms   VIRGINIA : add("headphones")   local cart = { headphones }
  t=0ms   FRANKFURT: add("case")         local cart = { case }
             (same shopper, two devices — or a retry that landed in
              the other region; either way, concurrent + independent)

  t=0..90 the two writes are still crossing the Atlantic...

  t=90ms  Virginia hears FR's "add case";  Frankfurt hears VA's "add headphones"

  Now BOTH regions must end up at the SAME cart. What is it?
     union  -> { headphones, case }   (both kept — what the shopper wants)
     LWW    -> { case } OR { headphones }   (one silently DROPPED!)

  The regions did nothing wrong. The design has to DEFINE the merge,
  because for a 90 ms window the two copies legitimately disagreed.

Active-active removes the single writer to gain speed and availability. In exchange, you inherit conflicts — and you, not the database, must decide how a conflict resolves. A wrong choice silently loses data.

Words we'll earn before we lean on them

  • Region — a full, self-sufficient copy of the service (compute + database) in one geographic place. A shopper is routed to the nearest one.
  • Active-active vs active-passive — active-active: every region accepts writes. Active-passive: one region takes all writes, the others are read-only standbys that only take over if the primary dies. Active-active is faster and more available, and the only one with a conflict problem.
  • Replication — copying one region's writes to the others. Synchronous: the write waits for the other region to acknowledge before returning (one cross-ocean round trip per write). Asynchronous: the write returns locally and ships to the other region in the background.
  • Replication lag — how far behind a region's copy is. With async replication across an ocean, ~90 ms in the good case, seconds-to-forever during a network partition.
  • Conflict — two regions concurrently write the same key to different values, neither having seen the other. Only possible because there's no single writer.
  • Last-write-wins (LWW) — the simplest resolution: attach a timestamp to each write; on conflict, keep the one with the larger timestamp, discard the other. Simple, and it silently drops the loser.
  • CRDT (Conflict-free Replicated Data Type) — a data structure whose merge is commutative (order doesn't matter), associative (grouping doesn't matter), and idempotent (applying the same update twice = once). Those three properties guarantee every replica converges to the same value no matter what order updates arrive in, or how many times — no coordination needed.
  • Convergence — all replicas eventually reach the same value. A CRDT guarantees this. It does not guarantee the value obeys your business rules.
  • Version vector / logical clock — a per-region counter (like Lesson 06/10's version, one per actor) carried with each value, used to tell concurrent writes apart from one that genuinely happened after another — without trusting wall clocks.
  • Invariant — a rule the data must always satisfy, globally (e.g. "a balance is never negative"). The concept no merge rule can enforce across regions.

Move 1 — Estimate: what forces two regions, and what it buys

Two numbers justify the whole design: the latency you're escaping, and the availability you're buying. Both are big.

Worked: the cross-region latency tax. Virginia to Frankfurt is about 6,400 km great-circle. Light in fiber travels at c ÷ 1.47 ≈ 204,000 km/s (Lesson 02/14's speed-of-light floor). So the fastest physically possible one-way trip is:

• 6,400 km ÷ 204,000 km/s ≈ 31 ms one way → ~64 ms round trip, and that's a straight line through the Earth's crust. Real fiber routes bend and pass through routers, adding ~40%, so a measured RTT is ~90 ms.

Now compare a write that commits locally (~1 ms) against one that must wait for the other region to acknowledge (synchronous replication, +1 RTT):

• local write ≈ 1 ms  vs  synchronous cross-region write ≈ 1 + 90 = 91 ms → a ~90× tax on every write, paid by every shopper on every tap. No faster database removes it; it's the width of the ocean. This is exactly why we let each region write locally — the alternative is a 90 ms wait on every cart change.

Worked: the availability we buy. Suppose one region is up 99.9% of the time — that's 0.001 × 365 × 24 = 8.76 hours of downtime a year. Put two regions in active-active, each able to serve any shopper, with independent failures. The service is down only if both are down at once:

• 0.001 × 0.001 = 10⁻⁶ → 99.9999% up ("six nines") → 10⁻⁶ × 31,536,000 s ≈ 32 seconds of downtime a year. From 8.76 hours to 32 seconds by adding a second live region (Lesson 07's redundancy, now at continent scale).

Name the trade-off — latency & availability vs a conflict problem you now own. Active-active hands you local-speed writes and six-nines availability. The bill comes due the moment two regions write the same key: there's no single writer to declare the winner, so you must define the merge — and the availability upside is only real for data you can actually merge safely. Everything below is about paying that bill.

Move 2 — Model: two regions, async replication, and how a conflict resolves

We route each shopper to their nearest region, which serves reads and writes locally, then streams its writes to the other region asynchronously (Lesson 09's log/queue, now spanning an ocean). Local writes stay ~1 ms and the site stays up even if the link between regions is cut — that choice is AP from Lesson 11: during a partition we keep availability and accept temporary divergence. The design work is all in the merge. There are two families.

Model A — Last-Write-Wins: pick one, drop the other

Stamp every write with a timestamp. When a region receives a conflicting write for the same key, keep whichever timestamp is larger and throw the other away. It's one comparison, no extra storage, and it always converges (both regions apply "keep the max" and land in the same place).

The problem is the word drop. LWW treats the whole value as one opaque blob, so in our cart example it keeps {case} or {headphones} — never both. A shopper's item silently vanishes. Worse, "last" is measured by a wall clock, and two regions' clocks disagree (Lesson 22's clock skew): a region whose clock runs 50 ms slow can stamp a genuinely newer write with an older time, so the correct write loses. LWW is safe only when losing one of two concurrent writes is acceptable, and even then only as safe as your clocks.

Model B — CRDT: design the value so concurrent writes merge instead of collide

The insight that changes everything: a conflict only exists because we modeled the cart as one blob. Model it instead as a set with per-item operations, and the two writes stop conflicting at all. add("headphones") and add("case") touch different elements; their merge is just the union {headphones, case}. Order doesn't matter (commutative), grouping doesn't matter (associative), and replaying the same add twice changes nothing (idempotent — Lesson 05/09/13's idempotency, now load-bearing for correctness). Those are exactly the CRDT properties, and they guarantee both regions converge with zero coordination — no lock, no leader, no cross-ocean wait.

  TWO WAYS TO MERGE THE SAME TWO WRITES

  VA: add(headphones)          FR: add(case)

  LWW register (whole cart is one value, keep latest timestamp):
     VA stamp 10:00:00.100   FR stamp 10:00:00.090
     merge -> keep VA        ->  { headphones }     <-- "case" LOST

  CRDT set (per-element, merge = union):
     merge -> { headphones } ∪ { case }  ->  { headphones, case }
                                             both kept, both regions agree

CRDTs come in shapes for different data. A set (carts, tags) merges by union. A counter (Lesson 06's like-counter, Lesson 21's mergeable sketches — those are CRDTs!) keeps a separate sub-count per region and merges by summing them, so two concurrent "+1"s both survive. A register (a single scalar like a display name) falls back to LWW or "keep all concurrent values and let the app pick." The skill is choosing a shape whose merge preserves what the user meant.

One subtlety: telling "concurrent" from "after". If Frankfurt's write genuinely happened after it had already seen Virginia's, that's not a conflict — it's an update, and the later one should win. To tell the two apart without trusting wall clocks, each value carries a version vector: a little map {VA: n, FR: m} counting writes seen from each region. If VA's vector is {VA:1, FR:0} and FR's is {VA:0, FR:1}, neither dominates the other → truly concurrent → merge them. If FR's were {VA:1, FR:1}, it has seen VA's write and supersedes it → no conflict. This is Lesson 06/10's version idea and Lesson 22's "trust a monotonic number, not the clock," applied to detect concurrency.

Move 3 — Trace the paths

Four journeys through the two regions: the clean merge, the genuine conflict with no right answer, the LWW clock-skew data-loss, and the counter that CRDTs get right where a register loses.

Path 1 — add / add: the union that just works

  t=0     cart = {} in both regions
  t=0     VA: add(headphones), vv={VA:1,FR:0}   VA cart={headphones}
  t=0     FR: add(case),       vv={VA:0,FR:1}   FR cart={case}
  t=90    each ships its op to the other
  t=90    VA merges FR's op: neither vv dominates -> concurrent -> UNION
  t=90    FR merges VA's op: same -> UNION
  RESULT  both regions = {headphones, case}   ✔ converged, nothing lost

Because the cart is a CRDT set, the "conflict" was never a conflict. Concurrent adds to different elements commute, so the two regions reconcile with no coordination and no data loss. This is the happy path active-active is for.

Path 2 — add / remove the SAME item: a real conflict with a business answer, not a technical one

  t=0     cart = {headphones} in both regions
  t=0     VA: remove(headphones)   FR: add(headphones)   (concurrent!)
  t=90    each hears the other. The ops DON'T commute:
             remove-then-add  -> {headphones}
             add-then-remove  -> {}
          Order changes the answer -> a genuine conflict.

  Resolution is a POLICY, not a fact:
     add-wins    ->  {headphones}   (safer for a cart: keep the item)
     remove-wins ->  {}             (safer for "I unsubscribed")

Here order matters, so there's no merge that's "correct" by logic — the CRDT's job is only to make every replica pick the same policy so they still converge. Which policy is a product decision: for a shopping cart, add-wins (don't lose a sale); for a "leave this group" toggle, remove-wins (respect the opt-out). A CRDT guarantees the replicas agree; it can't tell you what they should agree on. That's yours to choose.

Path 3 — LWW under clock skew: the newer write silently lost

  Cart modeled as an LWW register (whole value, latest timestamp wins).
  Frankfurt's clock runs 50 ms SLOW.

  real 10:00:00.100  VA: set cart={A}   stamped 10:00:00.100
  real 10:00:00.130  FR: set cart={A,B} stamped 10:00:00.080  (skewed!)
                          ^ genuinely later, but its clock lied

  merge: keep larger timestamp -> VA's .100 > FR's .080 -> keep {A}
  RESULT  {A}. The later, correct write {A,B} is DROPPED. Item B gone,
          no error, no log line. The clock decided, and the clock was wrong.

Nothing here is a bug in the code — it's a bug in trusting a wall clock to order events across machines. This is the same disease as Lesson 22's lease-expiry check: any safety or ordering argument that compares timestamps across regions is only as good as the clocks, and clocks skew. The fix is the same shape: order by a logical version, not the wall clock — or, better, don't model the cart as an overwrite-the-whole-thing register at all, and let the set CRDT keep both items.

Path 4 — the counter: a register loses, a CRDT counter doesn't

  Item quantity starts at 1 in both regions. Two "+1" taps, concurrent.

  As an LWW register on the NUMBER:
     VA: 1 -> 2      FR: 1 -> 2      merge keeps one "2"  -> 2   ✗ (lost +1)
        (Lesson 06's lost update, now ACROSS regions)

  As a PN-counter CRDT (per-region sub-counts, merge = sum):
     VA increments -> {VA:1, FR:0}    FR increments -> {VA:0, FR:1}
     merge = element-wise max -> {VA:1, FR:1} -> base 1 + 1 + 1 = 3  ✔

Two shoppers each added one → the right answer is 3. The register model loses an increment exactly as a single-node race did in Lesson 06 — the ocean just widened the gap. The counter CRDT keeps a private tally per region and sums them, so no increment is ever overwritten. Same lesson, one layer up: model the value by the operation (increment), not the result (the number), and concurrency stops destroying data.

Name the trade-off — CRDT convergence vs the metadata to get it. CRDTs buy coordination-free, loss-free merges, but they aren't free: a set that supports removes must keep tombstones (Lesson 15/20's "deleted" markers) so a delete isn't undone by a late-arriving add, and those accumulate; a version vector grows with the number of regions/actors. You trade a little metadata and compaction work for never having to coordinate a write across an ocean. Usually a great trade — until the metadata is the cost, which is the next wall.

Move 4 — Find the first bottleneck: the write that can't be merged

Sets, counters, and last-write-wins cover a huge amount of real state. Then you hit data with a global invariant — a rule that must hold across all regions at once — and every merge rule breaks, because merging preserves convergence, not invariants.

Worked: the balance that goes negative. An account holds $100. The invariant: balance ≥ 0 — never overdraw. Model it as a PN-counter (the CRDT that merged perfectly above) and run two concurrent withdrawals:

• VA: withdraw $80. Local check: 100 − 80 = 20 ≥ 0 ✓, approve.
• FR: withdraw $70, concurrently. Local check: 100 − 70 = 30 ≥ 0 ✓, approve.
• Merge (sum the sub-counters): 100 − 80 − 70 = −$50.

The counter converged flawlessly — both regions agree the balance is −$50. And that agreed value violates the invariant. Each region approved a withdrawal that was locally fine, but the rule was global and no region could see the other's spend in time. A CRDT guarantees all replicas reach the same number. It cannot guarantee that number obeys "≥ 0" — because enforcing a global limit is exactly the coordination active-active removed. This is Lesson 11's scalar-balance dilemma, now named precisely: mergeable ≠ invariant-safe.

So for invariant-bound state you must give something back. Three options, each a different point on the trade:

  • Single-home the key. Route all writes for one account to one region (its "home"), the single writer from Lessons 03/04/10/22. The invariant is enforced by one authority, so it can't be violated — but a shopper far from that home pays the ~90 ms cross-region tax on their account's writes. You've traded local-write speed (for that key) to keep the rule.
  • Synchronous consensus across regions. Make the withdrawal a quorum write agreed by both regions before it returns (Lesson 10/11's CP path). The invariant holds globally, but every write pays the +90 ms RTT, and if the regions can't reach each other, the write blocks (availability given up — the CP choice from Lesson 11).
  • Escrow / reservation. Split the invariant itself: give each region a budget — say $50 to Virginia, $50 to Frankfurt. Each region spends only its own budget with no coordination (fast, available), and only talks cross-region when its escrow runs dry (to borrow from the other). You've partitioned a global limit into local ones — the same "shard the counter" idea from Lessons 06/08, applied to an invariant. The cost: a region can refuse a withdrawal it could have covered if it could see the other's unused budget.

Name the core trade-off — local writes vs global order. Active-active's whole promise is that a write commits locally, fast and always-available, without asking any other region's permission. A global invariant is the one thing that requires asking permission — you cannot both "never coordinate" and "enforce a rule across everyone." So per key you choose: keep it mergeable and coordination-free (carts, counters, tags, presence → CRDTs, local writes win), or accept it needs a global order and pay for it (balances, inventory, unique usernames → single-home / consensus / escrow). The art is sorting your data into those two buckets — and putting as little as possible in the expensive one.

Where we landed

We took one shopping cart and put its service live on two continents at once. Estimate showed why: a synchronous cross-region write costs ~90 ms (the 6,400 km speed-of-light floor is already 64 ms) versus ~1 ms local — a 90× tax — while a second live region drops downtime from 8.76 h/yr to ~32 s/yr (six nines). So each region writes locally and replicates asynchronously (Lesson 11's AP: stay available, tolerate divergence). Model gave two ways to reconcile the divergence: last-write-wins (one timestamp comparison — but it silently drops the loser and trusts a skewable wall clock), and a CRDT — a value whose merge is commutative, associative, and idempotent, so every replica converges with zero coordination. Tracing concurrent edits showed the payoff and the limit: two adds to a set union cleanly (nothing lost); an add-vs-remove of the same item is a genuine conflict whose resolution is a business policy (add-wins for a cart) not a technical fact; LWW under a 50 ms-slow clock drops the newer write; and a counter modeled as a CRDT keeps both concurrent "+1"s (result 3) where a register loses one (Lesson 06's lost update, now across an ocean). The first bottleneck was the write that can't be merged: a $100 balance withdrawn $80 in Virginia and $70 in Frankfurt converges to −$50 — the CRDT agreed perfectly and still broke the ≥ 0 invariant, because merging preserves convergence, not global rules → so invariant-bound keys need single-home ownership, synchronous consensus, or escrow (split the limit), each paying latency or flexibility to buy the rule back. The real lesson: active-active trades the single writer for speed and availability, and the price is that you must sort every piece of state into "mergeable" (CRDT, write anywhere, coordinate never) or "globally ordered" (a balance, an invariant — pay to coordinate), and keep the expensive bucket as small as you can. The trade is local writes vs global order.
