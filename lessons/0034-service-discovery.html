Service Discovery & Health Checking: Finding a Live Instance in a Fleet That Comes and Goes Every Minute

Every lesson so far quietly assumed a step it never justified. Lesson 33's relay "publishes to the broker" and its consumers "call the search service." Lesson 32's orchestrator "calls the hotel service." Lesson 27 then told us the truth about that fleet: it autoscales — instances boot on a morning ramp, die on a scale-in, get replaced wholesale by a Lesson 31 rolling deploy, and crash at random. So the search service isn't at an address. It's at 200 addresses that change every few seconds. When your order service needs to call search, which IP does it dial — and how does it avoid dialing one that died two seconds ago? That question is service discovery, and answering it wrong quietly routes real traffic into black holes. This lesson takes one caller (the order service) trying to reach one callee (the search service) across an elastic fleet. We'll estimate how fast a hardcoded address list rots and what that rot costs in failed requests, model the registry (register on boot, heartbeat to stay listed, expire on death) and the split between liveness and readiness health checks, trace a boot, a crash, and a graceful shutdown through it, and hit the wall that defines the domain: the registry is now the one thing everyone depends on to find everyone else. The trade shifts from Lesson 33's freshness-vs-pipeline-complexity to routing freshness vs lookup cost & staleness.

The one system we'll design

The order service (the caller) needs to call the search service (the callee) — say, to index a new order (Lesson 33). The search service runs 200 instances behind Lesson 27's autoscaler, serving 40,000 requests/second in total, so each instance carries about 40,000 / 200 = 200 req/s. The naive answer is a config file: write down the 200 IP addresses and read from it. The problem is motion. In an elastic fleet those addresses are not stable for even a minute:

  • Scale-out / scale-in (Lesson 27): the autoscaler adds instances on a ramp and kills them when load falls — each is a brand-new address appearing or an old one vanishing.
  • Deploys (Lesson 31): a rolling deploy replaces all 200 instances over ~20 minutes — that's 200 address changes in one deploy, several times a week.
  • Crashes (Lesson 7): an instance dies unannounced; its address is now a black hole that still sits in every stale list.

So the real question isn't "what's the address of search?" It's "who is alive and ready to take my request right now?" — and the answer changes every few seconds. First the picture, then why the config file bleeds.

  SERVICE DISCOVERY: how a caller finds a LIVE, READY instance in a fleet that churns

  order-svc (caller)                 REGISTRY   (service name -> healthy instances)
     |                               +------------------------------------------+
     |  1. "give me search-svc"      |  search-svc:                             |
     |------------------------------>|    10.2.0.7:8080   ttl=8s   READY        |
     |   <- [ .7, .8, .9 ]           |    10.2.0.8:8080   ttl=6s   READY        |
     |      (only READY ones)        |    10.2.0.9:8080   ttl=9s   READY        |
     |                               |    10.2.0.4:8080   EXPIRED (no heartbeat) x
     |  2. pick one, send request    +------------------------------------------+
     |----------------\                       ^              ^
     v                 \                      | register     | heartbeat every 3s
   search .7   search .8   search .9          | on boot      | (renews the TTL)
     \___________ each instance: register on boot, heartbeat to renew its lease,
                  deregister on graceful exit, and vanish (TTL expiry) on crash.

  The registry is the live phone book. Instances keep their own entry warm with a
  heartbeat; miss enough heartbeats and the entry expires -- death detected, no reply needed.

A registry is a lease-based phone book: each instance keeps its own entry alive by heartbeating, and an entry that stops being renewed expires on its own. That's Lesson 26's connection registry (which held user→gateway) and Lesson 10's leader lease, generalized to service→instances. The heartbeat is doing exactly Lesson 10's job: turning "is it dead?" — an unanswerable question over a network — into "has it stopped renewing its lease?", which you can answer locally.

Words we'll earn before we lean on them

  • Caller / callee — the service making the request (order-svc) and the service receiving it (search-svc). Discovery is the caller's problem: find a live callee.
  • Service registry — a store mapping a service name (search-svc) to its current set of live instance addresses plus per-instance health. The live phone book.
  • Register / deregister — an instance adds itself to the registry on boot and removes itself on a graceful shutdown.
  • Heartbeat + TTL lease — the instance periodically pings the registry to renew a short time-to-live on its entry (Lessons 10, 22, 26). Stop pinging and the entry expires — the registry's way of noticing death without being told.
  • Liveness check — "is this process running at all?" A failed liveness check means restart it.
  • Readiness check — "should this process receive traffic right now?" A failed readiness check means take it out of the pool — but do not restart it (it may just be warming up or draining, Lesson 31).
  • Client-side vs server-side discovery — does the caller query the registry and load-balance itself, or does an intermediary (a load balancer, a DNS name, a sidecar proxy) do it for the caller?
  • Service mesh / sidecar — a small proxy deployed next to every instance that handles discovery, load balancing, and health for the app, so the app just calls localhost.
  • Fail-static — when the registry itself is unreachable, keep using the last known good instance list rather than failing all routing (a stale-but-alive list beats an empty one).

Move 1 — Estimate: how fast does a hardcoded list rot, and what does the rot cost?

"The addresses don't change that often" is the intuition that makes people hardcode them. Price the churn and the intuition dies.

Worked: the churn rate. Take just one source of motion — a Lesson 31 rolling deploy that replaces all 200 search instances over 20 minutes (1,200 s). That alone is 200 / 1,200 s ≈ one address change every 6 seconds, and deploys happen several times a week. Layer on autoscaling (Lesson 27's morning ramp adds ~86 instances) and random crashes, and the fleet's membership is changing on the order of once every few seconds, all day. A config file you edited this morning is wrong by lunch.

Worked: the cost of one stale entry. Suppose a caller refreshes its address list every 60 s, and an instance crashes right after a refresh. For up to 60 seconds that dead address stays in the list, and the caller keeps sending it its share of traffic: 200 req/s × 60 s = 12,000 requests fired into a black hole before the next refresh — each one a timeout (Lesson 7), each one needing a retry. One crash, one refresh window, twelve thousand failures. Shrink the detection window to a 9 s registry TTL and it's 200 × 9 = 1,800; add active ejection (the caller drops an address the instant a connection is refused) and it's near zero.

Why the config file loses on both freshness axes. It's stale in both directions: a dead address lingers (black-hole traffic until you notice), and a new, healthy address is invisible until you re-deploy the config (your fresh capacity sits idle during the exact ramp you scaled up for). The only fix is to stop treating membership as static configuration and start treating it as live, self-maintaining state — something that adds itself when it's ready and removes itself when it's gone. That's the registry, and the detection window is the dial we'll keep turning.

Move 2 — Model: the registry, and the two questions health checks answer

The registry is a key-value store keyed by service name, each value a set of instance entries carrying an address, a lease TTL, and a health status. Three verbs keep it honest.

Register, heartbeat, expire — a lease, not a fact

When an instance boots and finishes warming up, it registers: "I'm search-svc at 10.2.0.7:8080." Then it heartbeats — every 3 seconds it pings the registry to renew a short TTL on its entry. On a graceful shutdown it deregisters explicitly. And if it crashes? It simply stops heartbeating; the TTL runs out and the registry drops the entry on its own. Death you were never told about becomes an entry that quietly expired.

  registry state for one instance:   10.2.0.7 : { ready:true, ttl:9s }

  t=0s  heartbeat -> ttl reset to 9s          (instance healthy, renewing)
  t=3s  heartbeat -> ttl reset to 9s
  t=6s  heartbeat -> ttl reset to 9s
        x  <-- instance CRASHES here, heartbeats stop
  t=9s  ttl now 3s ...
  t=12s ttl now 0s -> ENTRY EXPIRES, removed from the pool. Death detected in <= 9s.

  heartbeat 3s, TTL 9s  =  3 missed beats before eviction  (Lesson 10's 3-missed-heartbeat failover)

Name the trade-off — the TTL is a liveness dial, and both ends bite. Too long a TTL (say 60 s) and a dead instance lingers a full minute eating requests — Move 1's 12,000-failure window. Too short a TTL (say 4 s = one missed beat) and a live-but-briefly-slow instance — a GC pause (Lesson 22), a network hiccup — misses a single heartbeat, gets falsely evicted, re-registers a second later, and the pool flaps (Lesson 10's flapping leadership, in the routing layer). Detection speed vs false evictions: exactly Lesson 10's heartbeat-timeout sizing and Lesson 22's lease-length dial, now deciding how fast you notice a dead callee. Three missed beats (9 s) is the usual compromise — long enough to survive a hiccup, short enough to bound the black-hole window.

Liveness vs readiness — one word that prevents an outage

"Healthy" is two different questions, and conflating them is one of the most common ways to turn a small problem into a big one.

Liveness — is the process alive at all? A cheap, shallow check (does it answer /healthz at all?). If it fails, the process is wedged and the right action is restart it.

Readiness — should it get traffic right now? It may be alive but not ready: still warming its caches (Lesson 2), still opening DB pools, or deliberately draining before shutdown (Lesson 31). If it fails, remove it from the pool — but do not restart it.

The registry advertises an instance only while it is ready. The distinction matters because the action on failure is opposite: liveness failure → kill and replace; readiness failure → pause traffic, leave running. Swap them and you get a disaster in either direction — a warming instance that gets killed for "failing" a readiness probe used as liveness will never finish warming (a crash loop), and a not-yet-warm instance treated as ready gets real traffic before it can serve it (errors at every deploy).

The three discovery models — who actually does the lookup? The registry holds the truth; someone has to read it and pick an instance. That "someone" is the design choice.

Name the trade-off — routing freshness vs lookup cost & staleness. DNS is the cheapest to adopt and the stalest (its cache is the whole problem in miniature — the same freshness-vs-cost dial as Lesson 2 and Lesson 14). Client-side is the freshest and the most code to spread everywhere. The sidecar mesh buys freshness and language-independence by paying in operational weight. There is no free lookup: you pay in staleness, in client code, or in proxies.

Move 3 — Trace the paths

Run three lifecycle events through the registry and watch each verb do its job.

Path A — an instance boots (register, but only when ready)

  1. autoscaler starts search .7 (Lesson 27)         -> process alive, but caches cold
  2. .7 fails its READINESS check while warming        -> NOT yet in the pool, gets no traffic
  3. warm-up done: pools open, cache primed            -> readiness passes
  4. .7 registers + starts heartbeating (ttl=9s)       -> now advertised as READY
  5. next caller lookup returns [ ..., .7 ]             -> .7 begins taking its 200 req/s
  -> New capacity appears the moment it can SERVE, not the moment it BOOTS. The config
     file couldn't do this: it would send traffic to a cold instance, or leave it idle.

Path B — an instance crashes (expiry + retry cover the gap)

  1. search .4 crashes at t=6s (Lesson 7), heartbeats stop
  2. callers with a cached list still hold .4 -> some requests hit a black hole
  3. each such request fails fast (connection refused / timeout) -> caller RETRIES another
        instance (Lesson 7 backoff+jitter; safe because indexing is idempotent, Lesson 13)
  4. at t=12s .4's TTL expires -> registry drops it -> new lookups never see .4 again
  -> Death is not instant to detect, but the damage is bounded: <=9s of TTL window, and the
     RETRY papers over the gap so the user rarely sees the failure. Two layers, not one.

Notice discovery does not stand alone: the registry eventually removes the dead instance, and the caller's retry to a different instance (Lesson 7) covers the window before it does. Freshness and retries are partners — the registry shrinks the black-hole window, the retry survives whatever's left of it.

Path C — a graceful shutdown (deregister first, then drain)

  1. deploy retires search .8 (Lesson 31)             -> .8 gets SIGTERM
  2. .8 fails readiness ON PURPOSE + deregisters        -> registry stops advertising it
  3. in-flight requests keep finishing (DRAIN, Lesson 31) -> no request cut off mid-flight
  4. new lookups already exclude .8 -> zero new traffic arrives
  5. drain done -> .8 exits cleanly
  -> The ORDER is the whole point: leave the pool FIRST, then drain, then die. A crash does
     these in the wrong order (dies first) -> that's why Path B loses requests and Path C doesn't.

Path B and Path C differ only in ordering. A crash dies before it leaves the pool, so callers discover the death the hard way (a failed request). A graceful shutdown leaves the pool before it dies, so no caller ever sends it a request it can't answer. The readiness check is the instance's off-ramp: it's how a healthy instance says "route around me" without dying.

Move 4 — Find the first bottleneck: the registry is now everyone's single dependency

We removed the stale config file, but we created a new load-bearing thing: a registry that every caller consults to reach every callee. Its health is now the routability of the whole system — the same shape as Lesson 33's relay, Lesson 26's connection registry, and Lesson 30's KMS. Four pressures land on it.

Pressure 1 — the registry must not fail closed. If the registry is a hard dependency on every request's path and it blips, no one can find anyone — a small registry outage becomes a total outage. The fix is fail-static: callers cache the last known good instance list and keep using it if the registry is unreachable. A stale-but-mostly-alive list routes far better than an empty one. This is a deliberate CAP choice (Lesson 11): discovery prefers availability over consistency — route to a possibly-stale instance rather than fail all routing — the opposite of Lesson 10's leader election, which had to be CP.

Pressure 2 — the registry itself needs to survive failure. A single-node registry is a SPOF for the entire platform. So it's replicated — and because instances registering/expiring is agreement about shared membership, this is exactly Lesson 10's job: a real registry (etcd, Consul, ZooKeeper) is a consensus cluster (Raft/Paxos), an odd number of nodes with a majority quorum. Discovery is built on top of the coordination service Lesson 10 built.

Pressure 3 — heartbeat load scales with the whole platform, not one service. 200 search instances heartbeating every 3 s is a trivial 200 / 3 ≈ 67 renews/s. But every instance of every service heartbeats. Ten thousand instances platform-wide is 10,000 / 3 ≈ 3,333 renews/s hammering the registry forever, and a shorter TTL multiplies it. That's why registries push work to the edges — gossip between instances, or local agents that aggregate heartbeats — rather than making one cluster field every beat (Lesson 26's off-gateway truth, generalized).

Pressure 4 — propagation lag never fully closes. A change in the registry still has to reach every caller's cache, so there is always a window where a caller's view is stale — the same eventual-consistency gap as Lesson 33's relay lag. You don't eliminate it; you bound it (short cache TTL) and survive it (retry to another instance, Lesson 7). Routing freshness vs lookup cost is this window: refresh more often for freshness, less often for load.

The four traps

  • Trap 1 — conflating liveness and readiness. Use a readiness probe as a liveness probe and a warming or draining instance gets killed for not being ready → a crash loop that never lets it warm. Use liveness as readiness and traffic hits an instance before it can serve → errors on every deploy. Two questions, two actions: restart vs remove-from-pool. Keep them separate.
  • Trap 2 — a health check that probes a shared dependency. If every instance's health check calls the same database and the DB blips, all instances fail their check at once → the registry ejects the entire fleet → a minor DB hiccup becomes a total outage (a correlated failure, Lessons 7/26). Keep the liveness check local and shallow — "am I, this process, responsive?" — not "is the whole world healthy?"
  • Trap 3 — a strongly-consistent registry on the hot request path. Insisting the registry be perfectly consistent and consulted live on every call means a registry partition blocks all routing (Lesson 11's CP cost, in the worst place). Cache + fail-static instead: prefer a slightly-stale route over no route. Discovery is a place to choose AP.
  • Trap 4 — a TTL that's mistuned in either direction. Too long and dead instances linger and black-hole traffic (Move 1's 12,000 failures); too short and a single missed heartbeat false-evicts a live instance into a flap (Lesson 10). Size it like a lease: heartbeat interval × a few misses, tuned to your real hiccup duration.

Where we landed

We took one thing every previous lesson silently assumed — a caller reaching a callee — and noticed that in Lesson 27's elastic, Lesson 31-deployed fleet the callee isn't at an address, it's at 200 addresses that change every few seconds. Estimate priced the naive config file: a rolling deploy alone changes an address every 6 seconds, and one crash inside a 60 s refresh window black-holes 200 × 60 = 12,000 requests — stale in both directions, dead addresses lingering while fresh capacity sits invisible. Model gave the fix: a registry that instances keep warm with a heartbeat-renewed TTL lease (Lessons 10/22/26), so a crash is just an entry that expires (death detected in ≤ 3 missed beats), plus the one distinction that prevents an outage — liveness ("is it alive?" → restart) vs readiness ("should it get traffic now?" → remove from pool, don't restart) — and the choice of who does the lookup: DNS (cheap, stale), client-side (fresh, code everywhere), or a sidecar mesh (fresh + uniform, operational weight). Tracing a boot (register only when ready, so new capacity appears when it can serve, not when it boots), a crash (TTL expiry bounds the black-hole window, and a Lesson 7 retry to another instance papers over the gap), and a graceful shutdown (deregister first, then drain, then die — the ordering a crash gets wrong) showed the three verbs at work. The first bottleneck: the registry is now everyone's single dependency, so it must fail-static (cache the last good list, choose AP — Lesson 11 — the opposite of Lesson 10's CP), be a replicated consensus cluster (Lesson 10), shed heartbeat load that scales with the whole platform (3,333 renews/s at 10k instances), and live with a propagation-lag window it bounds and retries past. Four traps guard the build: conflating liveness and readiness, a health check that probes a shared dependency (one DB blip ejects the whole fleet), a strongly-consistent registry on the hot path, and a mistuned TTL. The real lesson: in a fleet that churns every few seconds, membership is not configuration — it's live, self-maintaining state, kept honest by a heartbeat and made safe by choosing a stale-but-alive route over no route at all. Routing freshness vs lookup cost & staleness — and the registry you built to find instances is the same coordination service (Lesson 10) that elects their leaders.

Next lesson closes a gap this one leaned on:

• Logical clocks & causal ordering: the registry's TTL, Lesson 22's lease, and Lesson 23's last-write-wins all quietly trusted a wall clock — but clocks on different machines disagree (Lesson 23's skew), so "which event happened first?" has no trustworthy global answer. We'll build ordering that needs no synchronized clock: Lamport timestamps (a total order that respects causality but can't tell concurrent from causal), vector clocks (which can, at O(N) size — Lesson 23's recap), and hybrid logical clocks (physical time bolted on so a timestamp is both causal and roughly wall-clock). The trade shifts from routing freshness vs lookup cost to ordering precision vs metadata size & coordination.
