Sharding & Resharding Live: Splitting a Hot Shard Without Dropping a Write

Every lesson so far has said "the database" as if it were one box. It isn't. Our orders table has grown to 10 billion rows and takes 40,000 writes/second at peak — more storage and more write traffic than any single machine can hold. Lesson 3 already showed us why (a single disk has a storage ceiling and a single node has a throughput ceiling — two separate walls) and hinted at the fix: sharding, splitting the data across many machines so each holds a slice. But splitting raises three questions Lesson 3 left open, and they are the whole lesson. First, how do you decide which row lives on which shard? — range by key, hash of the key, or a directory that looks it up. Each buys something and costs something. Second, what happens when one shard gets too hot and you must split it again — while it's serving live traffic, without losing a write? That's the online-migration problem of Lesson 24, now moving a whole shard. Third, what does a query that doesn't name the shard key cost? — it becomes a scatter-gather across every shard (Lesson 19), and the bill is the tail. We'll estimate how many shards we need and why % N makes resharding a nightmare. We'll model the three strategies and the shard-key decision. We'll trace a point read, a scatter-gather, and a hot shard being split in two live. And we'll find the first bottleneck: resharding a live shard without dropping a write — and the shard key you can almost never take back. The trade under all of it: even load & locality vs query flexibility.

The one system we'll build

Keep the e-commerce site from Lesson 78. Its orders table (Lessons 12/25/29) now holds 10 billion orders at ~1 KB each — 10 TB — and takes 40,000 writes/second at peak (Black Friday). One machine can't do this: a good OLTP node comfortably holds maybe 2 TB and sustains maybe 5,000 writes/second before it slows. So we shard: split the 10 TB across many nodes, each holding one slice (a shard), and route every read and write to the shard that owns its key. Our job is three decisions: how to assign rows to shards (the sharding strategy), which column to shard on (the shard key — a choice we'll see is nearly irreversible), and how to split a shard that outgrows its node while it keeps serving traffic (resharding, live). The adversary isn't an attacker; it's skew — the reality that traffic is never spread evenly, so one shard always ends up hotter than the rest.

The one idea the whole lesson turns on: sharding trades a global view for a local one. On one box, every row is reachable by every query at the same cost. The moment you split the data, a query is cheap only if it names the shard key (so the router sends it to one shard) and expensive if it doesn't (so it must ask every shard and merge). So the shard key isn't a storage detail — it decides which of your queries are fast and which are scatter-gathers, and because changing it means moving every row, you get to decide that essentially once. Everything below is: which strategy assigns keys to shards, what that does to load and to range queries, and how you split a shard when skew makes one too hot.

Words we'll earn before we lean on them

  • Shard (partition) — one slice of a table, living on its own node, holding a disjoint subset of the rows. All shards together are the whole table.
  • Shard key (partition key) — the column whose value decides which shard a row lives on. The router computes the shard from this value.
  • Router (routing layer) — the component that, given a key, answers "which shard owns this?" It sits between the app and the shards.
  • Range sharding — assign contiguous key ranges to shards (shard 0 = A–D, shard 1 = E–H, …). Keeps neighbours together.
  • Hash sharding — assign a row to hash(key) mod N. Scatters neighbours evenly across shards.
  • Directory-based sharding — a lookup table (the directory) that explicitly maps a key (or key range) to a shard. Placement is arbitrary and changeable.
  • Skew / hotspot — uneven distribution: one shard getting far more data or traffic than its fair share. The thing sharding must survive, not the thing it eliminates.
  • Hot shard — a shard whose load exceeds its node's ceiling because of skew. The trigger for resharding.
  • Resharding — changing the number of shards or the key→shard mapping, usually by splitting a shard in two (or merging two into one), while the system serves live traffic.
  • Scatter-gather (fan-out query) — a query with no shard key: the router sends it to all shards, then merges the partial results (Lesson 19). Cost grows with shard count and is bounded by the slowest shard.
  • Cross-shard query / transaction — one that touches rows on more than one shard. Loses single-node atomicity (Lesson 32) and single-node speed.
  • Consistent hashing — hashing keys and nodes onto a ring so adding a node moves only ~1/N of keys instead of ~all of them (Lesson 4). The fix for hash sharding's resharding pain.

Move 1 — Estimate: how many shards, and why % N is a trap

Two numbers set the shard count, and a third shows why the obvious hash scheme makes resharding almost impossible.

Two separate walls set the shard count (Lesson 3's insight, made concrete). We size the fleet twice — once for storage, once for throughput — and take the larger, then add headroom.

  • Storage wall: 10 TB ÷ 2 TB per node = 5 shards just to hold the data.
  • Throughput wall: 40,000 writes/s ÷ 5,000 writes/s per node = 8 shards just to take the write rate.
  • These are independent ceilings — one is bytes, the other is operations/second — so you take the max (8), not the sum, and add headroom for skew and growth: call it 16 shards. Each shard then holds 10 TB ÷ 16 ≈ 625 GB and takes 40,000 ÷ 16 = 2,500 writes/s — comfortably under both ceilings.

Why headroom, not exactly 8: traffic is never even. If one shard runs 2× its fair share (very common), 8 shards would put it at 5,000 writes/s — right at the wall. Sizing to 16 leaves each shard at 2,500 with room for a hot one to run hot before it needs splitting.

Why hash(key) % N makes resharding a nightmare (recap of Lesson 3, because it's the reason two of our three strategies exist). Say you shard by hash(order_id) % 16. It's perfectly even — but the day you add a 17th shard, the mapping becomes % 17, and almost every key now hashes to a different shard:

  • A key stays put only if hash % 16 == hash % 17, which happens for roughly 1 in 17 keys.
  • So adding one shard moves ~16/17 ≈ 94% of all rows — ~9.4 TB of data shuffled across the network to grow capacity by 6%. During the move, the mapping is ambiguous and reads can miss. This is Lesson 3's headline number, and it's why naive hash sharding is a one-time decision you dread revisiting.
  • The fix is consistent hashing (Lesson 4): put keys and nodes on a ring; adding a node steals only the arc between it and its neighbour — ~1/17 ≈ 6% of keys move, not 94%. Same evenness, resharding you can actually do.

The trade named: plain % N hashing buys dead-simple routing (a modulo, no lookup) at the cost of a catastrophic reshard; consistent hashing buys cheap resharding at the cost of a little more machinery (the ring, virtual nodes).

Move 2 — Model: three ways to assign keys, and the key you can't take back

The three sharding strategies, side by side

Every strategy answers one question — given a key, which shard owns it? — and the answer sets your load balance, your range-query cost, and how hard resharding is.

StrategyHow it maps key→shardBuysCosts
Rangecontiguous ranges (A–D → s0, E–H → s1)range queries & scans are local (neighbours together); easy to split a range in twohotspots: sequential keys (timestamps, auto-increment ids) all land on the newest shard → one hot shard, the rest idle
Hashhash(key) mod N (or on a ring)even load by construction; no hotspot from sequential keysdestroys locality — a range query hits every shard (scatter-gather); plain % N resharding moves ~94% of keys (→ consistent hashing)
Directoryan explicit lookup table: key/range → shardmaximum flexibility: place any range anywhere, split a hot range, pin a big customer to its own sharda lookup on every request (extra hop) and the directory is a hot dependency / SPOF (cache & replicate it, L2/34)

The trade named, in one line: range gives you locality but risks hotspots; hash gives you even load but destroys locality; directory gives you flexibility but adds a lookup and a dependency. Real systems often combine: hash within a directory (the directory maps ranges of a hash space to shards — that's essentially what consistent-hashing systems do), getting even load and movable placement.

Why the range hotspot is so common it deserves its own warning: the most natural shard keys are the most dangerous. Shard orders by order_id (auto-incrementing) or created_at (a timestamp) with range sharding, and every new order has a key larger than every old one — so 100% of new writes go to the single highest shard while the other 15 sit idle. You sharded for 40k writes/s and still have one node taking all of them. This is Lesson 19's hot-cell problem and Lesson 3's hotspot in the orders table: sequential key + range sharding = a write hotspot by design. The fixes are to hash the sequential key (spread writes evenly, lose time-range locality) or shard by a naturally-spread key like customer_id instead.

The shard key: a one-way door

The shard key is the single most consequential — and most permanent — choice here, because changing it means recomputing every row's location and physically moving essentially the whole table (the 94% move, but on purpose and for all the data). So pick it against three criteria at once:

  • High cardinality — many distinct values. Shard by country (≈200 values) and you can never have more than ~200 shards, with a few countries dwarfing the rest. Shard by customer_id (millions of values) and you can split as fine as you like.
  • Even distribution — no single value carries a huge share of the data or traffic. A key where one value is 30% of writes gives you a hot shard no split can fix (that value can't be spread — the wall below).
  • Matches the dominant query — the access pattern you do most often should name the shard key, so it's a single-shard lookup, not a scatter-gather. If your app almost always asks "orders for customer X," shard by customer_id and that query hits one shard.

These pull against each other — the query you want local may not be the key that spreads evenly — and that tension is the lesson's headline trade: even load & locality vs query flexibility. Because you get to choose once, choose for the query you run a thousand times a second, not the one you run in a nightly report (send that to the warehouse, Lesson 29).

Move 3 — Trace the paths

Follow three situations: a point read that names the shard key, a query that doesn't (scatter-gather), and — the hard one — a hot shard being split in two while it serves live traffic.

Path A — a point read by the shard key (the cheap, common case)

   App asks: "get order for customer #8675309" (sharded by customer_id).
   [1] Router hashes/looks up customer_id -> shard 7 owns it.
   [2] Send the query to shard 7 ONLY. It scans its local index (L12).
   [3] One shard answers in ~0.5 ms. Merge nothing. Done.
   This is the WHOLE point of sharding: name the shard key and you
     pay one shard's cost, not sixteen. 16x the capacity, 1x the latency.

Path B — a query with no shard key (the scatter-gather tax)

   App asks: "all orders with status = REFUNDED, newest 20" -- no shard key.
   [1] Router can't narrow it: status isn't the shard key.
   [2] Fan OUT the query to ALL 16 shards in parallel.
   [3] Each returns its top 20 by date; the router GATHERS and merges,
         re-sorts, keeps the global top 20.
   The bill:
     - LATENCY = the SLOWEST of 16 shards (tail amplification, L17).
       If each shard is slow 1% of the time, P(>=1 slow) = 1 - 0.99^16
       = ~15%: a query that hits a slow shard 15% of the time.
     - THROUGHPUT = 16x load: one logical query = 16 physical queries.
   Fixes: shard by the field you filter on (make it Path A), OR keep a
     SECOND copy of the data sharded by status (a secondary index, L12,
     kept in sync via the outbox/CDC of L33), OR send it to the
     warehouse (L29) if it's an analytics question, not a live one.

Path C — splitting a hot shard, live (the online migration)

   Skew: shard 7 (customers P..T) has grown to 1.2 TB and 8,000 w/s --
     3x its fair share, past the node's ceiling. Split it: P..T -> P..R + R..T.
   The naive move (lock shard 7, copy half out, flip) = an outage: the
     copy of ~600 GB @ 100 MB/s takes ~100 min, and writes are BLOCKED
     the whole time (L24's table-lock trap, at shard scale).
   Do it LIVE, as an online migration (L24 shape):
   [1] EXPAND: provision new shard 7b (empty), owner of range R..T.
   [2] DUAL-WRITE: every write to a key in R..T now goes to BOTH
         shard 7 (old) AND 7b. Turn this ON *first* (before backfill).
   [3] BACKFILL: copy existing R..T rows from 7 to 7b in the background --
         batched, cursor-paged (L18), throttled on replica lag (L6).
         ~600 GB / (10k rows/s) ~= a few hours; live traffic unaffected.
   [4] VERIFY + CUTOVER: once 7b has caught up (row counts match, lag ~0),
         flip the router: reads of R..T now go to 7b. Instant, reversible
         (flip back to 7 if 7b misbehaves -- 7 is still current).
   [5] CONTRACT: stop dual-writing R..T to shard 7; delete the moved rows
         from 7. Shard 7 is now P..R only; 7b is R..T. Load halved on each.
   Two ordering rules make it safe (L24): dual-write ON *before* backfill
     (else a write during the copy is lost on 7b), and cut readers over
     only *after* verifying 7b is caught up (keep 7 warm as rollback).

Path A is the reward: name the shard key and 16× the capacity costs 1× the latency. Path B is the tax: a query that doesn't name the shard key fans out to all 16 and pays the slowest one — the scatter-gather, and the reason the shard key must match your dominant query. Path C is the hard part and the reason range/directory sharding earn their keep: a hot shard has to be split while it serves traffic, and that's Lesson 24's expand → dual-write → backfill → cutover → contract, now moving a whole key range instead of a column. Move 4 names the wall Path C circles: doing that split without dropping a single write — and the shard key you chose in Move 2 that you can almost never change.

Move 4 — Find the first bottleneck: resharding live, and the one-way door

The first bottleneck — resharding a live shard without dropping a write. Growth and skew guarantee that some shard will outgrow its node, so splitting a shard while it serves traffic isn't a rare event — it's the operation your sharding scheme lives or dies by. The whole difficulty is the window: between "start copying shard 7's upper half to 7b" and "7b is the owner," writes keep arriving, and a write that lands in that window can be lost on the new shard if you copied its row a moment before the write and never told 7b. Lesson 24's parallel-change discipline is exactly the fix, and the two ordering rules are non-negotiable:

  • Dual-write ON before backfill. Turn on writing R–T to both shards first. Then backfill. Now any write during the copy is already on 7b (via the dual-write), so the backfill can safely skip or overwrite it — no gap. Reverse the order and a write that slips between "backfill copied this row" and "dual-write started" is lost on 7b forever.
  • Cut readers over only after verifying 7b is caught up, and keep shard 7 warm and current as an instant rollback. If 7b is wrong, flip the router back — no data lost, because 7 never stopped being correct until you contract.

The strategy you chose in Move 2 decides how painful this is: range and directory sharding split a range locally (just move R–T), and a directory makes the cutover a one-row change in the lookup table; plain % N hash can't split one shard at all — you'd re-hash everything (the 94% move), which is why real hash-sharded systems use consistent hashing (Lesson 4) so a split moves only the affected arc. The trade named: the split's speed and safety vs the coordination it demands — dual-writes cost double writes and a verify step for the duration, buying you a reshard with zero dropped writes and an instant rollback.

The second wall — a single hot key that no split can fix. Sharding balances ranges of keys across nodes. It does nothing for skew within a single key. If one celebrity seller's customer_id takes 8,000 writes/s by itself (Lesson 15's celebrity, Lesson 19's hot cell), splitting the shard doesn't help — that one key can't be in two places, so whichever shard owns it is still hot. You've hit the limit of "spread the keys": the problem is one key, not the key distribution. The fixes come from earlier lessons: split the key itself into sub-keys the app fans across shards (Lesson 6/21's sharded/approximate counter — write to seller#42:shard{0..9} and sum on read), replicate the hot key to many read replicas (Lesson 6) if it's read-hot, or absorb it in a cache (Lesson 78) if it tolerates staleness. The trade named: a hot range is a sharding problem (split it); a hot key is an application-level problem (decompose it) — and confusing the two makes you reshard forever without ever cooling the key.

The third wall — cross-shard operations lose atomicity and speed. On one box, "move $50 from Alice to Bob" is a single transaction. Shard by customer_id and Alice and Bob may be on different shards, so there's no single-node transaction to wrap both writes — you're back to Lesson 32's world (a saga with compensations, or 2PC's blocking locks). Likewise a query joining two tables sharded on different keys can't be a local join. Two mitigations: co-locate related rows by choosing a shard key that keeps them together (shard orders and line-items by the same customer_id so a customer's order + its items live on one shard — the join stays local), and accept that anything genuinely cross-shard pays the distributed-transaction tax. The trade named: the shard key that co-locates your transactional unit keeps writes atomic and joins local, at the cost of flexibility for every other access pattern — which is, once more, even load & locality vs query flexibility.

The fourth wall — the shard key is a one-way door. Every wall above is really a consequence of one choice: the shard key. Chose order_id and now need "all orders for a customer" fast? That's a scatter-gather you can't cheapen without a second copy. Chose a low-cardinality key and now need more shards than it has values? You're stuck. And fixing it means re-sharding on a new key — moving the entire table, the 94% move for 100% of the data, the most expensive migration there is. That's why the shard key is decided against the dominant query, the cardinality, and the distribution before you shard, and revisited only under duress. The escape hatches soften but don't remove it: a directory lets you move ranges without re-hashing; secondary indexes (a second copy sharded by another key, kept in sync via Lesson 33's outbox/CDC) buy a second fast access path at the cost of storage and write amplification. The trade named: commit to one shard key's fast paths now, or pay to maintain multiple copies sharded different ways — storage and consistency work vs query flexibility.

So the honest picture of a sharded table: reads and writes that name the shard key are gloriously cheap — one shard's cost for the whole fleet's capacity (Path A), which is why we could take 40k writes/s across 16 shards at 2,500 each. But the split into shards traded a global view for a local one, so anything that doesn't name the shard key either scatter-gathers across all 16 and pays the slowest (Path B), or needs a second copy sharded differently. The first bottleneck is resharding a hot shard live — survivable only via Lesson 24's dual-write → backfill → verify → cutover → contract, with dual-write-before-backfill and verify-before-cutover as the two rules that keep a single write from being lost (Path C). Around it: a single hot key no split can cool (→ decompose the key, L6/21), cross-shard transactions and joins lose atomicity and locality (→ co-locate the transactional unit, or pay the saga tax, L32), and the shard key is a one-way door (→ choose for cardinality + distribution + dominant query, soften with a directory or secondary indexes, L33). Every choice names its price.

The deepest point: sharding doesn't make one big database; it makes many small independent ones and asks you to pretend they're one — and the pretense holds only for queries that name the shard key. On a single node, storage layout is invisible to the query: every row costs the same to reach. Split the data and the layout becomes the most important thing about the table — the shard key silently divides your queries into "fast, one shard" and "slow, all shards," divides your transactions into "atomic, one shard" and "distributed, needs a saga," and it does so nearly permanently. Notice the whole lesson is assembled from pieces you already own: the two ceilings and the hotspot (L3), consistent hashing for cheap resharding (L4), the online-migration discipline for splitting live (L24), scatter-gather and hot cells (L19), tail amplification across the fan-out (L17), the hot-key decomposition and hot-row coalescing (L6/21), cross-shard transactions as sagas (L32), and secondary copies kept in sync by the outbox (L33). The new idea is only that "the database" was a comfortable fiction, and the shard key is the line you draw through your data that decides, once, which of your questions stay cheap. The standing tension: even load & locality vs query flexibility.

The four traps

  • Trap 1 — a sequential shard key with range sharding. Sharding by order_id or created_at in ranges sends 100% of new writes to the highest shard while the rest idle — you bought N nodes and load one. Hash the key or shard by a naturally-spread field.
  • Trap 2 — backfilling before dual-writing. Copy a shard's rows first and turn on dual-writes second, and every write that lands between "row copied" and "dual-write on" is lost on the new shard. Dual-write ON before backfill, always (L24).
  • Trap 3 — expecting a split to fix a hot key. Splitting a shard balances key ranges, not a single scorching key. One celebrity key stays hot on whichever shard owns it; you must decompose or replicate the key itself (L6/21), not reshard.
  • Trap 4 — choosing the shard key for the wrong query. Optimizing the shard key for a nightly report makes your thousand-per-second live query a scatter-gather. Shard for the dominant online access pattern; send analytics to the warehouse (L29).

Where we landed

We took "the database" — a single logical box every lesson leaned on — and split it, because 10 TB and 40k writes/s clear no single node. Estimate set the shape: two independent ceilings (storage → 5, throughput → 8) taken as a max plus headroom → 16 shards at 625 GB and 2,500 writes/s each, and the reason two of our three strategies exist — plain hash % N moves ~94% of rows to add one shard, where consistent hashing moves ~1/N. Model gave the three strategies — range (locality, risks hotspots), hash (even load, destroys locality), directory (flexible, adds a lookup) — and the shard key chosen against cardinality, distribution, and the dominant query all at once. Tracing showed a point read hitting one shard, a shard-key-less query fanning out to all 16 and paying the slowest (~15% chance of a slow shard, 16× load), and a hot shard split in two live via expand → dual-write → backfill → verify → cutover → contract. The first bottleneck: resharding without dropping a write (→ dual-write-before-backfill, verify-before-cutover, L24); around it, a hot key no split can cool (→ decompose/replicate, L6/21), cross-shard transactions lose atomicity (→ co-locate or saga, L32), and the shard key is a one-way door (→ choose deliberately, soften with directory/secondary indexes, L33). The deepest point: sharding makes many small databases and asks you to pretend they're one, and the pretense holds only for queries that name the shard key.
