Secrets, Keys & Encryption: Protecting the Data Without the Key Becoming the Single Point of Failure

Lesson 29 just built a warehouse that holds a copy of everything — three years of payments (Lesson 25), every customer record, ~11 TB in one place. That concentration is a gift to an attacker: one stolen disk, one leaked backup, one over-broad credential, and the whole vault spills at once. The obvious defense — "encrypt it" — hides two traps that this lesson exists to defuse. Encrypt all 11 TB under one key and that key becomes a single point of failure with a blast radius of everything; and when you must rotate that key (on schedule, or the instant it might have leaked), re-encrypting 11 TB takes ~12 hours of moving every byte. This lesson takes that one vault and traces how to encrypt it so the key is neither a SPOF nor a performance tax. We'll estimate the cost of the naive one-key design two ways (blast radius and rotation time), model the fix — envelope encryption, a key that encrypts keys, with a KMS as the guarded root — trace a write and a read through the key hierarchy plus where TLS belongs, and hit the wall that defines the domain: the KMS becomes a hot dependency on every read, forcing the DEK-caching trade. The trade shifts from Lesson 29's freshness-vs-cost to security blast-radius vs operational friction.

The one system we'll design

Take Lesson 29's warehouse: ~11 TB of order and payment history, denormalized across roughly 100,000 column-partition files (1,095 day-partitions × 50 columns, plus growth). It must be encrypted at rest (so a stolen disk or leaked backup is useless ciphertext) and reached only encrypted in transit (so a wiretap on the network sees nothing). Two operational facts make this hard: keys must be rotated (replaced periodically, and immediately if one might have leaked), and every read must decrypt, so the key material has to be reachable, fast, by the serving path — without being reachable by an attacker. Here is the shape, and why one key is the wrong answer.

  ENCRYPTING THE VAULT  —  one key vs a hierarchy of keys

  NAIVE: one key encrypts all 11 TB              ENVELOPE: a key that encrypts keys
   +-----------------------------+                ROOT KEY  (in KMS/HSM, NEVER leaves)
   |  11 TB  --[ K ]-->  cipher  |                   |  wraps
   +-----------------------------+                   v
   K leaks -> ALL 11 TB exposed  (blast = all)    KEK  (master key, per app/tenant)
   rotate K -> re-encrypt 11 TB  (~12 hours)         |  wraps each
                                                     v
                                                  DEK  DEK  DEK ... (one per file)
                                                   |    |    |
                                                   v    v    v
                                                  each file's bytes, AES-256-GCM

   one DEK leaks -> ONE file exposed  (blast = 1 file)
   rotate the KEK -> re-wrap ~100,000 tiny DEKs (~10 MB), data NEVER moves (~seconds)

One key over everything makes the key do two jobs that pull in opposite directions: it must be near the data (every read decrypts, so it has to be fast and available) and far from attackers (if it leaks, everything is gone). You cannot win both with a single key. Envelope encryption splits the jobs across a hierarchy: a tiny root key that never leaves a hardened service does the guarding, and cheap, plentiful data keys — one per file — do the bulk encrypting. Now a leaked data key costs you one file, and rotating the guarded key re-encrypts only the small keys, not the terabytes. Same ciphertext strength, a thousand-times-smaller blast radius, and rotation that finishes in seconds instead of hours.

Words we'll earn before we lean on them

  • Plaintext / ciphertext — the readable data vs its scrambled form. Encryption turns plaintext into ciphertext under a key; only someone with the key can reverse it (decrypt).
  • Symmetric key — the same secret key both encrypts and decrypts (fast, used for bulk data; e.g. AES-256 = a 256-bit / 32-byte key). Asymmetric — a public/private key pair (slower, used for handshakes and signatures; the basis of TLS).
  • AES-GCM / AEAD — Authenticated Encryption with Associated Data. It encrypts and stamps a tag that detects any tampering, so decryption fails loudly if a bit was flipped. Confidentiality and integrity in one step. Needs a unique nonce (a number-used-once) per encryption.
  • At rest vs in transit — data sitting on disk/backup (at rest) vs data moving over a network (in transit). Different threats (stolen disk vs wiretap), different tools (disk/field encryption vs TLS).
  • DEK (data encryption key) — the symmetric key that actually encrypts a chunk of data. Cheap, plentiful — one per file/object here.
  • KEK (key encryption key) — a master key whose only job is to encrypt (wrap) DEKs. Guarded, rarely used directly on data.
  • Envelope encryption — encrypt data with a DEK, then encrypt (wrap) the DEK with a KEK, and store the wrapped DEK next to the ciphertext. The data carries its own key in a locked envelope.
  • KMS (key management service) — a hardened service (often backed by an HSM, a tamper-resistant hardware module) that holds KEKs, never releases them in plaintext, and offers only "wrap this DEK" / "unwrap this DEK" operations. The root of trust.
  • Rotation — replacing a key with a fresh one, on a schedule and on suspected compromise. Blast radius — how much is exposed when one key or secret leaks.
  • Secret — any credential the system needs but must not reveal: DB passwords, API tokens, private keys. A secrets manager stores and hands these out (ideally short-lived), instead of baking them into config or code.

Move 1 — Estimate: what one key actually costs

Before designing, price the naive "one key over everything" design on the two axes that matter for keys: how much leaks when it leaks, and how long it takes to replace. Both are brutal, and both are what the hierarchy fixes.

Worked (axis 1): blast radius. One key K encrypts all 100,000 files / 11 TB. If K leaks — a compromised host with the key in memory, an over-broad IAM grant, a key checked into a log — the attacker decrypts 100% of the vault: every payment, every customer, three years deep. Blast radius = everything, from a single point of failure. Contrast envelope encryption: a leaked DEK exposes the one file it wrapped — 1 / 100,000 of the vault — and you re-encrypt just that file. The KEK, which could unlock all DEKs, never leaves the KMS, so it is not sitting on any host to be scraped.

Worked (axis 2): rotation time. Security policy (and Lesson 25's payment-data rules) says rotate keys every 90 days, and immediately on any suspicion of compromise. With one key, "new key" means decrypt-and-re-encrypt every byte:

• bytes moved = 11 TB read + 11 TB written = 22 TB. At Lesson 29's 500 MB/s: 22,000,000 MB ÷ 500 MB/s = 44,000 s ≈ 12.2 hours — and that's the vault degraded or offline while it churns, on every rotation.

• With envelope encryption you rotate the KEK and re-wrap the DEKs — the DEKs themselves (and therefore the data ciphertext) don't change. Wrapped DEKs total 100,000 × ~100 B ≈ 10 MB. Re-wrapping 10 MB is seconds, and not one byte of the 11 TB moves.

• the ratio: 22 TB ÷ 10 MB ≈ 2,200,000× less data touched to rotate. Rotation stops being a 12-hour outage and becomes a background metadata update. Envelope encryption turns key rotation from a data-migration problem into a key-migration problem — and the keys are a million times smaller than the data.

Name the trade-off — where the key lives vs how fast you can decrypt. A key an attacker can never reach is also a key you can't use quickly. One key held only in an HSM is safe but too slow to decrypt every read; one key copied to every server is fast but leaks catastrophically. The hierarchy resolves it by giving each layer one job: the KEK stays locked in the KMS (safe, rarely touched), the DEKs are cheap and local to the data (fast, plentiful, low blast radius each). You don't pick between "safe key" and "fast key" — you use a safe key to protect fast keys.

Move 2 — Model: the key hierarchy and the KMS as root of trust

The estimate says: don't encrypt data under a key you'd have to move terabytes to rotate, and don't put the all-powerful key on any host. Two decisions turn that into a system — the hierarchy of keys, and the service that guards the top of it.

The three-layer hierarchy, and why AEAD (not plain AES)

Bulk data is encrypted with per-file DEKs using AES-256-GCM. GCM matters: it is AEAD, so it produces a ciphertext plus an authentication tag. On decrypt, if a single bit of the ciphertext (or its metadata) was altered, the tag check fails and decryption refuses — you get confidentiality and tamper-detection together. Plain AES in the wrong mode (ECB) leaks patterns; AES without authentication lets an attacker flip bits undetected. Each DEK is then wrapped (encrypted) by a KEK that lives only in the KMS, and the KEK itself is protected by a root key in tamper-resistant hardware (an HSM) that never leaves the module at all.

The KMS is a coordination point — recap Lesson 10

The KMS holds the KEKs and exposes only two operations: wrap(DEK) → wrapped DEK and unwrap(wrapped DEK) → DEK. It never returns the KEK in plaintext, so even a fully compromised application server can decrypt only the DEKs it is currently authorized to unwrap — it can never walk away with the master key. But that makes the KMS a single authority every encrypt and decrypt depends on: exactly Lesson 10's coordination service (etcd/ZooKeeper) wearing a security hat. It must be highly available (an outage means nothing can decrypt), it authorizes each call (so a stolen app credential has a scoped, revocable, audited blast radius), and it logs every use (so you can prove what was touched after an incident). Same properties as any coordinator: it is powerful, so it must be HA, access-controlled, and audited.

  THE KEY HIERARCHY  —  each layer has ONE job

   +-------------------- KMS / HSM (the guarded root of trust) --------------------+
   |  ROOT KEY   never leaves the hardware module                                  |
   |     |  protects                                                               |
   |  KEK (master)   used ONLY to wrap/unwrap DEKs; never returned in plaintext    |
   +---------------------------------|--------------------------------------------+
             wrap(DEK) | unwrap(wrapped DEK)   <- the only two calls the app can make
                       v
   APP / WAREHOUSE NODE  (holds a DEK in memory only briefly, per operation)
        DEK ---- encrypts/decrypts ----> file bytes  (AES-256-GCM, per-file DEK)
        stored on disk next to each file:  [ ciphertext | wrapped DEK | key-id ]

   Leak a DEK -> 1 file.   Leak an app cred -> only what KMS lets it unwrap, and it's
   logged + revocable.   The KEK is never on the app host at all -> nothing to scrape.

Name the trade-off — a powerful root concentrates both safety and risk. Putting all trust in the KMS is what lets a leaked DEK or a compromised app stay small — but it also means the KMS is a single point every operation flows through. That's a deliberate bet, the same one Lesson 10 made for coordination: it is easier to make one hardened, highly-available, heavily-audited service safe than to make every application server safe. You concentrate the crown jewels so you only have to defend one vault well — but then that vault must never be the thing that goes down. (That "must never go down" is exactly the wall in Move 4.)

In transit: TLS, and where to terminate it

At-rest encryption protects the disk; in-transit encryption protects the wire. Every hop that carries plaintext data or secrets uses TLS (an asymmetric handshake to agree a fresh symmetric session key, then fast symmetric encryption for the bytes). The design decision is where TLS terminates — where the encrypted tunnel is decrypted back to plaintext. Terminate at the edge load balancer and the client→edge hop is protected, but everything inside the datacenter travels in the clear; an attacker who gets a foothold on any internal hop (or a curious operator) reads it all. The stronger posture re-encrypts internally, service-to-service, with mTLS (mutual TLS — both sides present certificates, so services also authenticate each other), so there is no plaintext hop even inside the trust boundary. The trade is the familiar one: terminate-at-edge is simpler and cheaper; terminate-everywhere (zero-trust) is safer but adds certificate management and CPU on every hop.

Move 3 — Trace the paths

Follow one file into the vault (write), then back out (read), and see the DEK appear and vanish.

Path A — writing an encrypted file

  1. GENERATE   node makes a fresh random DEK (256-bit)         [in memory only]
  2. ENCRYPT    cipher = AES-256-GCM(file bytes, DEK, nonce)    -> ciphertext + tag
  3. WRAP       call KMS: wrapped_DEK = KMS.wrap(DEK, key-id=KEK)   (KEK never leaves KMS)
  4. STORE      write to disk:  [ ciphertext | tag | nonce | wrapped_DEK | key-id ]
  5. WIPE       zero the plaintext DEK out of memory             <- it's gone
  -> the file now carries its own key, locked in an envelope only the KMS can open

Notice the plaintext DEK exists on the node for only steps 1–4, then is wiped. What persists on disk is the ciphertext and the wrapped DEK — useless without the KMS. A stolen disk yields both, and neither can be opened without a live, authorizing, logging KMS call. The key-id records which KEK wrapped it, which is what makes rotation possible: a re-wrap updates the wrapped DEK and the key-id, and nothing else.

Path B — reading it back (and where the wall appears)

  1. FETCH      read from disk:  [ ciphertext | tag | nonce | wrapped_DEK | key-id ]
  2. UNWRAP     call KMS: DEK = KMS.unwrap(wrapped_DEK, key-id)   <- a network round trip
  3. DECRYPT    plaintext = AES-256-GCM-decrypt(ciphertext, DEK, nonce)
                  -> tag mismatch? REFUSE (tampered/corrupt); else return plaintext
  4. WIPE       drop the plaintext DEK when done
  -> every read pays one KMS round trip in step 2  ... 40,000 reads/s = 40,000 KMS calls/s

Step 2 is the whole point and the whole problem. The unwrap has to go to the KMS because that is what keeps the KEK off the node — but it also means every single read makes a network call to one shared service. At the serving tier's Lesson 27 rate of 40,000 req/s, that is 40,000 KMS unwraps per second, each adding a round trip's latency (~10–50 ms) to a query that was supposed to take milliseconds. The very indirection that shrinks the blast radius puts a hot, shared, latency-adding dependency in the path of every read. That is Move 4.

Move 4 — Find the first bottleneck: the KMS on every read, and four traps

Path B named the wall: unwrapping per read makes the KMS a hot dependency — a throughput throttle (KMS services are rate-limited, often to a few thousand ops/s), a latency tax (a round trip on every query), and a Lesson 10/26 single point of failure (KMS down → nothing decrypts). You cannot fix this by removing the KMS (that would put the KEK back on the host). You fix it by not calling the KMS on every operation.

Worked: DEK caching collapses the KMS traffic. Unwrap a DEK once, then cache the plaintext DEK in the node's memory for a bounded time and reuse it for every read of that data. Say a partition-level DEK serves the reads that hit its partition, and you cache it for 5 minutes (300 s). If 40,000 reads/s spread across, say, 2,000 hot DEKs, then in a 300 s window you make at most 2,000 unwrap calls instead of 40,000 × 300 = 12,000,000 — a 6,000× cut — and after the first hit each read decrypts locally with a cached DEK, paying zero KMS latency. Caching the unwrapped DEK turns "one KMS call per read" into "one KMS call per DEK per TTL."

Name the core trade-off — the DEK-cache TTL is blast-radius-in-time. A cached plaintext DEK is exactly what the whole design worked to avoid: usable key material sitting in a node's memory. The longer the TTL, the fewer KMS calls (cheaper, faster) — but the longer a memory-scraping attacker's window to steal a live DEK, and the longer after you revoke access at the KMS before that cached DEK actually stops working. A short TTL keeps the exposure window and the revocation lag small but pushes KMS traffic back up. The cache TTL is a dial between operational friction (KMS load, latency) and security blast-radius (how long a stolen DEK stays valid, how fast a revocation takes effect) — the same performance-vs-safety dial as every cache in this course (L02), but here the cached thing is a key.

The four traps

  • Trap 1 — rolling your own crypto (and the nonce-reuse landmine). Never write the primitive yourself; use a vetted library and a standard mode (AES-256-GCM). The sharpest edge is the nonce: GCM requires a unique nonce per encryption under a given key, and reusing a nonce is catastrophic — it leaks the authentication key and can reveal plaintext relationships. Generate a fresh random nonce every time (or a strict counter), and rotate the DEK long before you could ever exhaust its nonce space. "Encrypted" with a reused nonce or ECB mode is barely encrypted at all.
  • Trap 2 — encrypting without authenticating. Confidentiality alone lets an attacker who can reach the ciphertext flip bits to corrupt or subtly alter data (change a ledger amount, Lesson 25). AEAD (the GCM tag) makes tampering fail the decrypt loudly. At-rest encryption must include integrity, not just secrecy — otherwise a stolen-and-modified backup restores as valid-looking, silently wrong data.
  • Trap 3 — secrets in code, config, or logs (and "secret zero"). The vault also needs DB passwords, API tokens, and the credential that lets a node call the KMS in the first place. Baking these into a Git repo, an environment variable dumped to logs, or a plaintext config file is the most common real-world breach — it's a secret with no envelope at all. Use a secrets manager that hands out short-lived, revocable, audited credentials instead of long-lived static ones. This bottoms out in the secret-zero / bootstrapping problem: something must hold the first credential to authenticate to the KMS/secrets manager — solved by binding identity to the platform (instance/workload identity, an attested hardware root) rather than a copied-around password, so there is no static secret to leak.
  • Trap 4 — terminating TLS too early. Decrypting the TLS tunnel at the edge and then shipping plaintext across the internal network trusts every internal hop and operator. One compromised service or sniffed internal link then reads everything at-rest encryption was protecting. Re-encrypt service-to-service (mTLS), or at minimum keep the sensitive hops inside a genuinely isolated boundary. "Encrypted in transit" has to mean the whole transit, not just the first mile.

Where we landed

We took one vault — Lesson 29's ~11 TB of payments and customer records, ~100,000 files — and traced how to encrypt it so the key is neither a single point of failure nor a tax on every read. Estimate priced the naive one-key design twice and both were fatal: a leaked key exposes 100% of the vault, and rotating it means moving 22 TB → ~12 hours. Model gave the fix: envelope encryption — bulk data under cheap per-file DEKs (AES-256-GCM, so confidentiality and tamper-detection), each DEK wrapped by a KEK that lives only inside a KMS and never touches a host, rooted in an HSM. That shrinks a leaked-DEK blast radius to one file (1/100,000) and turns rotation into re-wrapping ~10 MB of DEKs while the terabytes never move (~2,000,000× less data touched). The KMS is Lesson 10's coordination point in a security hat — powerful, so it must be HA, access-controlled, and audited — and TLS (ideally mTLS, terminated everywhere, not just the edge) protects the wire. Tracing a write (generate → encrypt → wrap → store the envelope → wipe the DEK) and a read (fetch → unwrap → decrypt-or-refuse-on-tamper → wipe) exposed the first bottleneck: the unwrap is a KMS round trip on every read — a hot, rate-limited, latency-adding SPOF — fixed by caching the unwrapped DEK for a bounded TTL (a 6,000× KMS-traffic cut), where the TTL is a dial between KMS load and how long a stolen or un-revoked DEK stays live. Four traps guard the build: rolling your own crypto / reusing a GCM nonce, encrypting without authenticating, secrets in code/config/logs (down to the secret-zero bootstrap), and terminating TLS too early. The real lesson: you don't choose between a safe key and a fast key — you use a safe, guarded key to protect a fleet of cheap, fast keys, and every remaining decision (cache TTL, TLS termination, rotation cadence) is the same dial between security blast-radius and operational friction.
