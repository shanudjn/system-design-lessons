Multi-Cloud & Vendor Portability: Why "Deploy It Twice" Is the Easy Half

Lesson 57 reprocessed billions of rows on one busy database. This lesson asks what happens when leadership says the words "we should be multi-cloud" — run the same system across two providers so a provider-wide outage can't take us down, and so we have negotiating leverage on price. The naive engineer hears "it's just containers, deploy the same images to the second cloud and put a load balancer in front" — and that half really is easy. The trap is that the easy half is the stateless half. Compute is light and portable; data is heavy and stays put. This lesson takes one concrete system — the orders platform (Lessons 12/24/25/57), all on Cloud A today, ~500 TB of data, 40k req/s — and traces what it actually takes to run it on Cloud A and Cloud B. We'll estimate the two walls that make this far harder than "deploy it twice": data gravity (moving 500 TB is slow and the egress bill is brutal, Lesson 14) and the fact that every byte crossing the provider boundary is metered forever. We'll model the real choice — lowest-common-denominator services you can run anywhere vs managed services that do the work but lock you in — and where a control plane can span clouds vs where it simply can't. We'll trace the portable stateless path, the stubborn stateful path, and the outage that reveals whether your "resilience" was real or theater. The trade underneath: portability & resilience vs complexity & cost.

The one decision we'll design

Our orders platform runs entirely on Cloud A: stateless app servers (Lesson 27's fleet), a managed relational database holding ~500 TB of orders and ledger data (Lessons 12/25), a managed object store for receipts and exports (Lesson 20), a managed queue (Lesson 09), and a managed data warehouse (Lesson 29). It serves 40,000 req/s. Leadership wants two things from going multi-cloud:

  • Resilience. "If Cloud A has a provider-wide or account-level failure, we don't want to be down with it." (A single provider can and does fail across all its regions at once — a global control-plane bug, an account lockout, a billing dispute.)
  • Leverage. "If we can credibly move to Cloud B, we can negotiate Cloud A's bill down."

The junior engineer's plan is one sentence: "Our app is containers behind a load balancer. I'll build the same images, deploy them to Cloud B, and point global DNS at both." That sentence is correct about the compute and silent about the data — and the data is the entire problem. Here's the shape of the system and where the sentence runs out:

  "Deploy it twice" — the easy half is drawn solid, the hard half dashed.

  | app servers   |   | app servers   |   <- STATELESS: same container runs
  | (stateless)   |   | (stateless)   |      anywhere. Portable. Cheap to move.
  |     |         |   |     |         |      THIS is the easy half.
  |     v         |   |     :         |
  | [ 500 TB DB ] |   | [   ??????  ] |   <- STATEFUL: heavy, metered to cross
  | [ object store]|  | [   ??????  ] |      the boundary, proprietary APIs.

                one way, forever. Data checks in free, checks out expensive.

Multi-cloud is not "run the servers in two places." Running stateless servers in two places is a solved, cheap problem. Multi-cloud is "keep the data correct, available, and affordable across a boundary that charges you per byte and adds latency." The compute is the tip; the data is the lesson.

Words we'll earn before we lean on them

  • Multi-cloud — intentionally running a system across two or more cloud providers (e.g. AWS + GCP), as opposed to multi-region (Lesson 23), which is one provider in many places.
  • Vendor lock-in — the cost, in time and rewrite effort, of leaving a provider. High when you depend on that provider's proprietary services; low when you depend only on open standards.
  • Portability — how easily a workload can be moved to run somewhere else. It is a property you build and pay for continuously, not one you have by default.
  • Data gravity — the tendency of large data to pull compute toward it and resist being moved: the bigger the dataset, the slower and more expensive it is to relocate, so it stays where it is and everything else orbits it.
  • Egress — data leaving a provider's network. Almost always metered (~$0.09/GB), while ingress (data coming in) is free — a deliberate asymmetry that makes leaving expensive (Lesson 14).
  • Managed service — a proprietary service the provider operates for you (their hosted database, queue, serverless runtime). You trade a proprietary API for not having to run it yourself.
  • Lowest-common-denominator (LCD) — building only on capabilities that exist on every provider (raw VMs, containers/Kubernetes, an S3-compatible object API, open-source Postgres you run yourself). Portable, but you operate it.
  • Control plane — the part of a system that decides and coordinates (who's the leader, what the config is, where traffic goes), as opposed to the data plane that carries the actual work (Lessons 10/34/50).

Move 1 — Estimate: the two walls, in numbers

Two quantities decide whether multi-cloud is a weekend of YAML or a multi-year program: how hard it is to move the data once, and how much it costs to keep the data synced or served across the boundary forever. Both come from the same brutal fact — egress is metered and data is big.

1. Data gravity — moving 500 TB once is slow AND expensive. To seed Cloud B with a copy of the database, you must pull 500 TB = 500,000 GB out of Cloud A. Two costs land at once:

• The bill. Egress at $0.09/GB (Lesson 14) → 500,000 GB × $0.09 = $45,000 for a single copy. Ingress into Cloud B is free, but the door out of A has a turnstile on it.

• The clock. Even over a fat 10 Gbps link (10 Gbps ÷ 8 = 1.25 GB/s), the transfer takes 500,000 GB ÷ 1.25 GB/s = 400,000 s ≈ 4.6 days of continuous, uninterrupted streaming — and real throughput is lower. Half a terabyte per second of writes never stops arriving while you copy, so the copy chases a moving target (Lesson 57). This is data gravity made concrete: the data is so heavy that moving it is a project, not a command.

2. The boundary tax — keeping data synced or served across clouds costs forever. A one-time copy isn't multi-cloud; you need the two sides to stay useful. Both ways of doing that meter every byte:

• Continuous replication. The database takes 5,000 writes/s × ~1 KB = 5 MB/s. Replicating those to Cloud B is 5 MB/s × 2,592,000 s/month ≈ 13 TB/month → 13,000 GB × $0.09 = ~$1,170/month. Modest for the DB alone — but multiply by object store, warehouse, and backups and it climbs.

• Serving across the boundary. Far worse: if you put compute in Cloud B but leave the data in Cloud A, every read crosses the line. 20,000 reads/s × 2 KB = 40 MB/s → 104 TB/month → 104,000 GB × $0.09 = ~$9,300/month ≈ $112,000/year — a permanent tax for the privilege of running your servers away from your data. The numbers force one rule: keep compute next to its data. A hot path that crosses the provider boundary bleeds money every second it runs.

Name the trade-off — portability & resilience vs complexity & cost. Everything above is one dial. Push toward real multi-cloud (two live copies of the data, kept in sync) and you buy resilience and leverage — paid in a continuous egress bill, a second operations burden, and the hardest distributed-systems problem there is (keeping state consistent across a boundary you don't control). Push toward simple (data single-homed in Cloud A, Cloud B idle or empty) and you save the money and complexity — but the resilience you were buying quietly evaporates, because a compute shell with no data can't serve anyone. There is no setting that is portable, resilient, and cheap.

Move 2 — Model: what's portable, what's sticky, where the line falls

The system splits cleanly into three layers by how hard each is to run on a second cloud. Naming the split is the model, because it tells you exactly where the work is.

Layer 1 — Stateless compute: genuinely portable

App servers hold no durable truth (Lesson 26 taught us to push state off the disposable box). A container image runs the same on any provider's VMs or Kubernetes. Moving this layer is a build-and-deploy, not a migration. This is the half the naive plan gets right — and the half that's least of the work. If your whole system were stateless, multi-cloud would be trivial. It never is.

Layer 2 — Stateful data: the sticky core

The database, object store, and warehouse hold the truth, and they resist moving for two independent reasons that stack:

Weight (data gravity). As Move 1 showed, 500 TB is slow and expensive to move and to keep synced. The bigger it grows, the more it anchors you.

Shape (API lock-in). A managed database isn't just rows — it's a proprietary API and set of guarantees. Cloud A's managed store might offer specific transaction semantics, a specific query dialect, specific auto-scaling behavior. Cloud B's nearest equivalent behaves differently. Moving isn't cp; it's a rewrite and re-test of everything that touches the data. Weight makes the bytes hard to move; shape makes the code hard to move. You pay both.

Layer 3 — The control plane: sometimes spans, sometimes can't

Coordination is a mixed bag — some of it is naturally above any single cloud, some of it fundamentally can't straddle two:

Spans cleanly (it lives above the clouds). Global DNS / traffic management (Lesson 50) is designed to point at addresses in any provider — it's the natural front door for multi-cloud. CI/CD pipelines and infrastructure-as-code (Terraform) describe both clouds from one place. These are portable by nature.

Can't span cheaply (it needs tight, low-latency agreement). A strongly-consistent database or a leader election (Lessons 10/23) needs a quorum that agrees quickly. Stretch that quorum across two providers and every decision pays the cross-cloud round trip (~80–150 ms, higher than cross-region because there's no shared backbone) and egress on every coordination message. You can put the traffic director above both clouds, but you cannot put a single strongly-consistent source of truth in both clouds without re-importing every latency and cost wall from Lesson 23 — now made worse by a boundary that meters bytes.

The core choice: managed leverage vs lowest-common-denominator portability

This is the decision that quietly determines your lock-in years before anyone says "multi-cloud." Every service you build on sits on a spectrum:

Managed (do it for me → locked in). Use Cloud A's hosted database, serverless functions, and queue. The provider operates, scales, patches, and backs them up — enormous operational leverage, the actual reason to be on a cloud. The price is a proprietary API: leaving means a rewrite.

Lowest-common-denominator (I run it → portable). Use only what exists everywhere — raw VMs, Kubernetes, self-hosted Postgres, an S3-compatible object API. The same stack runs on any provider, so you're portable. The price is that you're back to operating the database yourself (Lessons 10/34/47), giving up the managed magic you came to the cloud for.

Portability is insurance with a continuous premium. You pay it in engineering effort and forgone managed features whether or not you ever "cash it in" by actually switching. The question is never "portable or not" — it's "how much premium is this specific insurance worth, given how likely we are to claim it?"

The three layers, each with its own verdict: stateless compute is portable and cheap to duplicate (do it); stateful data is heavy (data gravity) and proprietary (API shape), so it anchors you to one provider and is the whole cost; the control plane splits — the traffic director spans both clouds for free, but a single strongly-consistent truth can't span them without re-paying Lesson 23's latency and this lesson's egress. The lock-in you'll feel later is set by today's managed-vs-LCD choices, made one service at a time.

Move 3 — Trace the paths

Follow three journeys: the portable stateless path (easy), the stubborn stateful path (hard), and the outage that tells you whether your resilience was real.

Path A — the stateless request (the half that just works)

  user -> global DNS/traffic mgr (L50) -> picks nearest healthy cloud
                                          |
              +---------------------------+---------------------------+
              v                                                       v
        CLOUD A app server                                      CLOUD B app server
        (same container image)                                 (same container image)
              |                                                       |
              v  reads/writes the DATA that lives in... where?  <-----+  <- the catch

  The compute layer is symmetric and portable: identical images, DNS steers
  by proximity/health, either cloud can serve the stateless work. If the app
  held no state, we'd be DONE here. The arrow "reads/writes the data" is where
  the easy story ends and Path B begins.

Path B — the stateful path: two honest options, each with a bill

  OPTION 1 — SINGLE-HOME the data in Cloud A; Cloud B compute reaches across.
     Cloud B app --- read/write over the boundary ---> Cloud A DB
     Cost: every hot-path byte is EGRESS (~$9,300/mo for 20k reads/s, Move 1)
           + ~80-150 ms cross-cloud latency on every query (L23 x boundary).
     Verdict: cheap to BUILD, ruinous to RUN, and slow. Compute is not next
              to its data. Fine for a tiny B footprint, fatal at scale.

  OPTION 2 — REPLICATE the data so each cloud has a local copy.
     Cloud A DB  <===== async replication (~$1,170/mo + forever) =====>  Cloud B DB
     Now each cloud's compute reads LOCALLY (fast, no per-read egress). But
     two live writable copies = L23's conflict problem, now ACROSS PROVIDERS:
       - active/passive: B is read-only standby, promoted on failover (simpler,
         B's capacity mostly idle, a promotion window).
       - active/active: both take writes -> conflicts -> LWW/CRDT (L23), and a
         scalar invariant (a balance, L25) still can't be split across the ocean.
     Verdict: real resilience, real cost, the hardest distributed-systems work.

  There is no third option where the data is both everywhere AND free AND
  strongly consistent. Pick which two you're buying.

Path C — Cloud A has a provider-wide outage (the moment of truth)

  The whole reason we did this. Does Cloud B actually take over?

  IF we chose Option 1 (data single-homed in A):
     Cloud A is down -> the DB is down -> Cloud B app servers are a COMPUTE
     SHELL with nothing to read or write -> total outage anyway.
     We paid for two clouds and got the availability of one. RESILIENCE THEATER.

  IF we chose Option 2, active/passive (B holds a live replica):
     DNS/traffic mgr (L50) health-checks A -> fails -> steers users to B ->
     B's replica is promoted to primary -> service continues. Costs paid:
     the replication bill, the promotion window (seconds-to-minutes), and any
     writes in A not yet replicated at the instant it died (L06/L23 lag = data
     loss window). THIS is resilience you can actually collect.

  The test of a multi-cloud design is not "is there a second cloud?" It is
  "when the first cloud dies, can the second one serve the DATA?" If the data
  isn't really there, the second cloud is decoration.

Path A is the half everyone demos. Path B is the fork the demo skips: you either pay egress + latency on every cross-boundary request (Option 1) or you pay continuous replication + the full weight of cross-provider consistency (Option 2) — there is no free version. Path C is the audit: resilience is only real if the failing-over cloud can reach the data, which means Option 1's tidy single-homed design buys you exactly zero of the availability you were paying two clouds for.

Move 4 — Find the first bottleneck: data gravity anchors the whole thing

You can make the compute perfectly portable and still be firmly locked to one provider, because the wall isn't the servers — it's the data underneath them. Compute is light: a container is a few hundred megabytes and runs anywhere. Data is heavy: 500 TB is slow to move, metered to cross, and shaped by a proprietary API. So the data decides where the system lives, and everything else orbits it. That single fact has sharp consequences.

1. The leverage argument is mostly a bluff — unless you keep paying to make it real. "We'll move to Cloud B to negotiate A's price down" only works if you actually could move. But data gravity means moving 500 TB is a 4.6-day, $45,000, multi-quarter rewrite of everything built on A's managed services. A vendor knows this. The threat to leave is only credible if you've spent continuously on portability (LCD services, abstraction layers, a warm second copy) — and if you've spent that much, you've already paid most of the cost the threat was supposed to save. Leverage isn't free; it's pre-paid.

2. The real escape is to shrink what must cross the boundary. You can't make 500 TB weightless, but you can arrange for very little of it to travel. Keep each cloud's compute next to its own local copy of the data (Option 2), so the only thing crossing the boundary is the replication stream (small, ~$1,170/mo) — never the read traffic (huge, ~$112k/yr). This is the same move as Lesson 57's "move the heavy scan off the primary" and Lesson 14's "put a copy near the user": don't fight data gravity, respect it — put a local copy where the compute is, and let only the thin delta cross the expensive line.

Two more walls sit behind those. Consistency can't span providers for free. A strongly-consistent value — an account balance, a "seat sold" flag (Lessons 11/23/25) — cannot live authoritatively in both clouds without a quorum stretched across the boundary, paying ~80–150 ms and egress on every write. So the honest multi-cloud pattern is usually active/passive (one cloud owns the writes, the other is a warm replica ready to be promoted) rather than true active/active, or it single-homes each strongly-consistent key to one cloud (Lesson 23's "single-home the invariant") and accepts that the other cloud reaches across for those specific operations. And a second cloud doubles your operational surface: two sets of IAM, two networking models, two monitoring stacks, two on-call runbooks, two bills to reconcile (Lesson 59's problem). The complexity isn't additive, it's multiplicative — every incident now asks "which cloud, and did the boundary between them play a role?"

The deepest point: multi-cloud is not a compute problem, it's a data-placement problem. Stateless servers were always portable; the cloud never locked you in with CPUs. It locked you in with gravity — the 500 TB that's slow to move, metered to cross, and shaped by a proprietary API — and with the managed services you adopted one convenient decision at a time. So "should we be multi-cloud?" is really "how much are we willing to pay, forever, to keep our data in two places and our code free of any one provider's API?" For most teams the honest answer is a warm second copy for disaster recovery, not symmetric active/active — resilience you can actually collect, at a premium you can actually afford. The standing tension: portability & resilience vs complexity & cost.

The four traps

  • Trap 1 — "multi-cloud = deploy it twice." Duplicating stateless servers is the easy, cheap half; it says nothing about the data. The entire difficulty is keeping the stateful core correct, available, and affordable across a metered boundary. If your plan doesn't have a data story, it isn't a multi-cloud plan.
  • Trap 2 — single-homed data behind a "resilient" second cloud. If Cloud A holds the only copy of the truth and A goes down, Cloud B is a compute shell with nothing to serve — you paid for two clouds and got the availability of one. Resilience requires the failing-over cloud to actually reach the data.
  • Trap 3 — LCD-everything "to stay portable." Refusing every managed service to avoid lock-in throws away the operational leverage that is the reason to be on a cloud, and makes you run databases and queues yourself. Portability is insurance with a real premium; pay it only where a claim is likely, not reflexively everywhere.
  • Trap 4 — believing the leverage bluff. "We'll just move" is empty if data gravity means you actually can't in any reasonable time or budget. The threat is only credible if you've already spent continuously on portability — at which point you've pre-paid most of what the threat was meant to save.

Where we landed

Multi-cloud is a data-placement problem wearing a compute problem's clothes. Estimate sized the two walls: moving 500 TB once is ~4.6 days and $45,000 of egress (data gravity), and keeping the two sides useful is a permanent tax — ~$1,170/mo to replicate the write stream, but ~$112k/yr to serve reads across the boundary, which forces the rule keep compute next to its data. Model split the system into three layers: stateless compute (portable, do it), stateful data (heavy by gravity + sticky by proprietary API — the whole cost), and the control plane (the traffic director spans both clouds for free, but a single strongly-consistent truth can't span them without re-paying Lesson 23's latency), with the quiet lock-in decision being managed leverage vs lowest-common-denominator portability, made one service at a time. Tracing walked the stateless request that just works, the stateful fork where you pay either per-read egress (single-home) or continuous replication + cross-provider consistency (replicate), and the outage that reveals single-homed data as resilience theater. The first bottleneck is data gravity itself: compute is light and was always portable; the cloud locked you in with the heavy, metered, proprietary-shaped data — so the data decides where the system lives, the leverage argument is a pre-paid bluff, and the real escape is to shrink what crosses the boundary to a thin replication delta, never the read traffic. Bounded further by the fact that strong consistency can't span providers cheaply (hence active/passive over active/active) and by a doubled, multiplicative operational surface. For most teams the honest answer is a warm second copy for disaster recovery — resilience you can actually collect — not symmetric active/active. The standing tension: portability & resilience vs complexity & cost.
