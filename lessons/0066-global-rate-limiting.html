Global Rate Limiting & Quota: One Shared Limit Across a Fleet

Lesson 8 built a rate limiter on one machine: a token bucket that says "this API key gets 60 requests per minute," and enforces it perfectly because one process sees every request. But a real API platform isn't one machine — it's 30 servers across 3 regions, and a single API key's requests scatter across all of them. Now the limit "60 requests per minute per key" is a promise no single server can keep, because no single server sees all 60. This lesson builds the limiter that holds a shared limit across a whole fleet: one budget, many enforcers, and a network in between. The instant you make the counter shared, a tension opens that Lesson 8 never had to face: check one central counter on every request and you bolt a network round trip — sometimes a cross-region one — onto every call; let each server count on its own and the global limit silently leaks by the number of servers. We'll estimate that cost and see a coordination round trip dwarf the actual work of a request; model the three designs (central counter, static division, and the local-bucket-plus-reconcile that wins) and name the idea that rescues us — rate limiting tolerates being approximately right (Lesson 21); trace a well-behaved key served with zero coordination, an abusive key and exactly how far it overshoots, and a network partition that forces a CAP choice (Lesson 11); and find the first bottleneck, which is not CPU or storage but that a shared limit is a single logical counter every request wants to touch — and you cannot make it globally exact, cheap, and partition-proof at once. The trade under every knob: limit accuracy vs coordination latency & cost.

The one system we'll build

An API platform. Clients call it with an API key, and each key has a limit: the free tier is 60 requests per minute per key. We run 30 API servers, 10 in each of 3 regions (us-east, eu-west, ap-south), behind the load balancers of Lesson 42, taking 40,000 requests/second in total. A single popular key's traffic does not politely land on one server — the load balancer spreads it, and a client in Europe hits the eu-west servers while the same account's mobile app hits ap-south. We must enforce "60/min for this key" as one global number, honored no matter which of the 30 servers each request happens to reach. That single requirement — one shared limit across many independent enforcers — is the whole problem, and it is a problem Lesson 8 never had, because on one machine the counter and the enforcer were the same thing.

Rate limiting is the first problem in this course where being slightly wrong is not just acceptable but the whole point. If we admit 63 requests against a 60/min limit, nobody is harmed — the client barely notices, and the abuse we care about (someone sending 10,000/min) is still crushed. That tolerance is the lever. It means we do not need the exact, expensive coordination a bank balance would demand (Lesson 11's account balance had to be exact); we need a limit that is approximately right and cheap. Everything below is the art of spending as little coordination as possible while keeping the error bounded.

Words we'll earn before we lean on them

  • Rate limit — a cap on requests per unit time (e.g. 60/minute). Enforced with a token bucket (Lesson 8): the bucket refills at the limit rate, each request spends one token, an empty bucket means "rejected — try later" (HTTP 429).
  • Quota — a cap over a long window on a consumable resource: "1,000,000 API calls per month," "$500 of spend per day." Same machinery as a rate limit, but the window is hours or days, not seconds, and overshooting can cost real money.
  • Local counting — each server keeps its own count of a key's usage, seen only by itself. Fast (no network) but blind to what the other 29 servers are doing.
  • Central counter — one shared store (e.g. a Redis) that holds the authoritative global count; every server reads/writes it. Exact but adds a network round trip and concentrates load on one key.
  • Coordination — any network talk between servers (or to a shared store) to agree on the shared count. Coordination buys accuracy and costs latency.
  • Reconciliation — periodically (every T seconds) syncing each server's local count to a coordinator that sums them and redistributes the remaining budget. The middle path between "coordinate on every request" and "never coordinate."
  • Overshoot — how many requests slip through above the limit before the distributed system notices and clamps down. The error we bound instead of eliminate.
  • Fail-open / fail-closed — when the coordinator is unreachable (a partition, Lesson 11), do we keep serving (fail-open, risk leaking the limit) or start rejecting (fail-closed, risk blocking good traffic)? A CAP choice.

Move 1 — Estimate: what coordination actually costs

The whole design is decided by one comparison: the cost of the work a request does versus the cost of coordinating to count it. If coordination is cheap relative to the work, just coordinate on every request. Let's price it.

PieceValueWhere it comes from
Fleet30 servers10 in each of 3 regions
Total traffic40,000 req/sthe platform's front door (L27/49)
Free-tier limit60 / min per key= 1 request/second per key
Same-region round trip~0.5 msserver → counter store in the same DC
Cross-region round trip~70 mseu-west → a counter in us-east
Work of a typical request~5 msthe actual API call it protects
A viral key's rate~10,000 req/sone key, one logical counter

The number that kills "just check a central counter on every request": the coordination can cost more than the request. If every server consults one shared counter before admitting a request, a call landing in eu-west while the counter lives in us-east pays a ~70 ms round trip to count a request whose real work is ~5 ms. You would spend 70 ms of network latency to protect 5 ms of work — a 14× tax, paid on every single request, before the request even runs. Same-region it's only ~0.5 ms, tolerable — but a global fleet has no "same region" for everyone; someone always pays the cross-region trip. And there is a second wall: the counter for one popular key is a single hot key. A viral key doing 10,000 req/s means 10,000 increments per second aimed at one counter entry, which hashing cannot spread (Lesson 3/48's hot-key problem — every request wants the exact same key). Exact global counting runs straight into both walls at once.

Now price the opposite extreme — never coordinate. Give each of the 30 servers its own local bucket and split the limit: 60 ÷ 30 = 2 requests/min per server. Zero network, zero latency tax. But traffic is never evenly spread. Suppose a client sits in Europe, so ~90% of the key's requests hit the 10 eu-west servers and the rest scatter. Even spread across those 10, the key can use at most 10 × 2 = 20/min before being throttled — the paying client is cut off at 1/3 of the 60 they were promised, while 40 of their 60 requests/min of budget sit unused on idle servers in other regions. The obvious "fix" — give every server the full 60 — is worse: 30 servers each independently allowing 60 means the true global limit becomes 30 × 60 = 1,800/min, 30× too loose, which is no limit at all. Static division forces you to choose between strangling honest clients and leaking the limit by a factor of N.

Move 2 — Model: count locally, reconcile globally, and stay approximately right

The three designs on one axis

Every global-limit design is a point on a single axis: how often do the enforcers talk? At one end, talk on every request (exact, expensive). At the other, never talk (cheap, wrong under skew). The winner sits in the middle and leans on rate limiting's tolerance for small error.

Design C — local buckets + periodic reconciliation. Each server keeps a local token bucket for the key and admits requests against it with zero network cost. Every T seconds (say T = 1 s), each server that has served the key reports its recent usage to a coordinator (one shared service, or a designated owner per key). The coordinator sums the reports — that's the true global count — and hands each server a fresh share of the remaining budget, giving more to busy servers and less to idle ones. Busy eu-west servers borrow the idle ap-south servers' unused budget, so the key can use its full 60/min even under total geographic skew — the thing static division couldn't do — while the coordination cost is a handful of small messages per second, not one per request. The catch, and it's the honest one: between syncs, servers act on a slightly stale picture, so the limit can overshoot. We don't eliminate that error; we bound it (Move 3) and turn T into a dial.

Why coordination is cheap here even for a hot key: reconciliation cost is per active server per interval — with the key live on, say, 6 servers and T = 1 s, that's ~6 sync messages/second — regardless of the request rate. For a viral key doing 10,000 req/s, 6 messages/s of coordination is a rounding error; for a cold key hit once a minute, servers back off and barely sync at all. Coordination stays flat while traffic scales — the opposite of the central counter, whose cost grew one-for-one with requests.

The idea that makes it safe: bounded approximation (Lesson 21)

Lesson 21 counted a billion events approximately because exact was too expensive and close enough was all anyone needed. A rate limit is the same bargain. The purpose of "60/min" is to stop abuse and protect capacity, not to be a precise meter — nobody's SLA says "exactly 60, never 61." So we deliberately accept a small, bounded overshoot in exchange for dropping per-request coordination. The design's honesty is in the word bounded: we will show the worst case is at most (the key's arrival rate) × (the sync interval), a number we can make as small as we like by syncing more often — and we pick the point where the overshoot is invisible and the coordination is cheap. Exactness is a cost we choose not to pay because the problem doesn't require it.

One warning: rate limits forgive overshoot; hard quotas may not

The reconcile design admits a little over the limit and corrects afterward. For a rate limit (60 req/min) that's harmless — three extra requests cost nothing. But for a hard quota that maps to money or a finite resource — "$500 of spend per day," "1,000 seats" — overshooting means billing a customer past their cap or overselling something you can't deliver. There the tolerance flips, and you switch machinery: instead of count locally, reconcile after (which can overshoot), you pre-authorize — a server must pull a lease of budget from the coordinator before spending it, so the coordinator, as the sole issuer, can never hand out more than the cap. That trades the overshoot away for a little latency and some "trapped" budget (tokens leased to a server that goes idle sit unused until returned). Name the fork: rate limits lean toward count-and-reconcile (cheap, may overshoot); hard money/resource quotas lean toward pull-a-lease (never overshoots, costs coordination up front). Both are the same axis; the acceptable direction of error decides which end you pick — and per-tenant quotas (Lesson 40) are exactly where this bites.

The model in one line: keep a local token bucket on every server for zero-latency admission; every T seconds reconcile local counts to a coordinator that reallocates the unused budget from idle servers to busy ones; accept a bounded overshoot of at most arrival-rate × T because rate limiting tolerates approximation (Lesson 21); and for hard quotas that can't overshoot, switch to pre-authorized leases so the coordinator never over-issues.

Move 3 — Trace the paths

Three scenarios: a well-behaved key served with no coordination at all, an abusive key and exactly how far it slips past the limit, and a network partition that forces the CAP choice.

Path A — a well-behaved key: zero coordination on the hot path

  Key K, limit 60/min. The client sends ~1 request/second,
  right at its budget, landing mostly on 2 eu-west servers.

    request arrives at eu-west server #3
      -> check LOCAL bucket for K: has tokens?  YES
      -> spend 1 token, admit the request        (~0 ms added)
      -> run the API call                         (~5 ms)
    ...repeat, all served from the local bucket...

    every T = 1 s, in the BACKGROUND (off the request path):
      server #3 reports "served 4 of K's requests" to coordinator
      coordinator sums all servers: 58/60 used this minute
      -> reallocates: busy eu servers keep their share,
         idle ap-south share is lent to eu-west
      -> servers get refreshed local budgets

    Result: the limit is honored, and NOT ONE request paid a
    coordination round trip. Coordination happened off to the
    side, a few messages per second, never in the client's wait.

Path B — an abusive key: how far does it overshoot?

  Key K, limit 60/min. A misbehaving client blasts A = 10 req/s
  (600/min, 10x over). Servers admit against their last-known
  global count, refreshed every T = 1 s (so up to 1 s stale).

    true global count crosses 60 at some instant t0.
    but every server's CACHED count still reads < 60 for up to
    T = 1 s after t0 -- they haven't synced yet.
    during that lag they keep admitting at the arrival rate A.

    worst-case overshoot  =  A x T
                          =  10 req/s  x  1 s
                          =  10 requests

    -> client gets ~70 through before the clamp engages,
       then is hard-blocked (429) until the window resets.
       ~70 on a 60 budget = ~17% over, for ONE second, then 0.

  The dial: halve the staleness to T = 0.5 s
       -> overshoot <= 10 x 0.5 = 5 requests (~8% over),
          at the cost of 2x the sync messages.
  Sync on EVERY request (T -> 0) -> overshoot -> 0, but you are
  back to the central-counter latency tax of Move 1.

Path C — a partition: the CAP choice, made explicit

  eu-west loses its link to the coordinator (in us-east).
  The 10 eu-west servers can no longer sync K's count.
  What do they do with the next request for K?

  FAIL-OPEN  (choose Availability, Lesson 11's AP):
    keep admitting on the last-known local share.
    good traffic flows -- but with no global view, every
    partitioned region can leak up to its share of the limit;
    combined overshoot can reach ~N_regions x share.

  FAIL-CLOSED (choose Consistency/accuracy, Lesson 11's CP):
    stop admitting K (or drop to near-zero) until sync returns.
    the limit can't leak -- but you 429 paying customers over
    an outage that is YOUR fault, not theirs.

  GRACEFUL MIDDLE (the usual default):
    each isolated region falls back to a STATIC local share
    (its pre-assigned slice of 60). Worst case leak is bounded
    to about the original limit per region, service continues,
    and full global optimization resumes when the link heals.

  There is no free answer -- this is CAP (Lesson 11) wearing a
  rate-limiter costume. You pick which way to be wrong.

Path A is the payoff: the common case — a client at or under its limit — pays no coordination at all, because the local bucket admits instantly and the syncing happens in the background. Path B makes the approximation honest and measurable: the overshoot is not "some unknown fuzz," it is at most arrival-rate × sync-interval, a number you dial down by syncing more often and pay for in message chatter — the trade drawn as arithmetic. Path C is the one to remember: a shared counter under a partition is Lesson 11's CAP theorem in a new suit — you cannot have an accurate global limit and keep serving and tolerate the partition, so you choose your failure, and the sane default is to degrade to a safe static share rather than either leak wildly or reject good traffic.

Move 4 — Find the first bottleneck: a shared limit is one logical counter everyone contends on

CPU isn't the wall — admitting a request against a local bucket is nearly free. Storage isn't the wall — a count is a few bytes. The wall is structural: a global limit is, by definition, a single logical number that every one of the key's requests must consult and update. That is a point of contention, and every design is just a different way to spread the contention out in space and time.

The bottleneck — you cannot make the shared counter globally exact, cheap, and partition-proof at the same time. Push for exact and you must coordinate on every request → the round-trip tax and the hot key of Move 1. Push for cheap and you coordinate rarely → overshoot grows with the sync interval (Path B). Push for partition-proof and you must decide, with no global view, whether to leak or to reject (Path C). These three pull against each other exactly the way recall, latency, and memory did last lesson — pick your point, name what you gave up. The master dial is the reconciliation interval T: small T buys accuracy (tiny overshoot) at the cost of coordination chatter and latency sensitivity; large T buys cheapness at the cost of a looser limit. There is no T that is best at everything, and the honest engineering move is to pick the overshoot you can tolerate (for a rate limit, generously — 10–20% for a moment is nothing) and set T just fine enough to hit it.

The second wall — skew and the hot key don't go away, they move. Consistent hashing (Lesson 4) can spread a million keys across the fleet, but it cannot split one key: a single viral key is one logical counter, and all its traffic contends on that one counter no matter how you shard (Lesson 4's own warning — hashing balances many keys, never one hot key). Reconciliation helps because the contention becomes "a few sync messages per second on the coordinator" instead of "10,000 increments per second on one store entry," but the coordinator for that key is now a hot spot of its own. The usual answers echo earlier lessons: shard the coordinator by key so different hot keys land on different owners (Lesson 3's write sharding), and for a single monstrously hot key, let its servers hold larger local shares and sync less often — trading a little more overshoot for far less coordination on exactly the key that would otherwise melt the coordinator.

The third wall — the window itself, and quotas that span days. "60 per minute" needs a notion of "this minute." A naive fixed window (reset the count at the top of each minute) allows a nasty burst at the boundary: 60 in the last second of 12:00 and 60 in the first second of 12:01 is 120 requests in ~2 seconds while never breaking "60/min." The classic fixes are the sliding window (count the trailing 60 seconds, not the calendar minute) and the token bucket's smooth refill (Lesson 8), and they cost a little more state per key. Stretch the window to a quota — "$500/day," "1M calls/month" — and two things change: coordination gets easier (a day-long budget has enormous slack, so you can sync lazily and still be accurate to the cent by day's end), but the tolerance for overshoot vanishes (billing past a hard cap is a real defect), which is exactly why quotas lean to the pre-authorized-lease model from Move 2. The longer and more valuable the budget, the more you favor never-overshoot leasing over cheap-but-loose reconciliation.

So the honest design for our global limiter is: give every server a local token bucket so the common, well-behaved request pays zero coordination (Path A); reconcile usage to a per-key coordinator every T seconds, reallocating idle servers' budget to busy ones so a skewed key still gets its full 60 (the thing static division couldn't do); accept a bounded overshoot of at most arrival-rate × T and set T to make it invisibly small (Path B), because rate limiting tolerates approximation (Lesson 21); shard the coordinator by key and let a monstrously hot key hold a bigger local share so no single counter melts (Lesson 3/4); use a sliding window or token bucket so the minute boundary can't be gamed (Lesson 8); under a partition, degrade each isolated region to a safe static share rather than leak wildly or reject good traffic — the CAP choice, made on purpose (Lesson 11); and for hard quotas that must never overshoot, switch to pre-authorized leases so the coordinator, as sole issuer, can never exceed the cap (Lesson 40). Every choice names its price: coordinating on every request buys exactness at the cost of a round-trip tax and a hot key; a smaller T buys accuracy at the cost of chatter; a bigger local share buys cheapness on a hot key at the cost of overshoot; and fail-open vs fail-closed is availability vs accuracy, chosen with eyes open.

The deepest point: a global limit is a distributed agreement about a single number, and Lesson 11 already told us the truth about that — you cannot have consistency, availability, and partition-tolerance all at once. Lesson 8's single-node limiter got exactness for free because there was nothing to agree with; the moment the counter is shared across a fleet, exactness costs coordination, coordination costs latency, and a partition costs a choice. The escape is that rate limiting, unlike a bank balance, doesn't need consistency — a bounded approximation is not a compromise, it's the correct spec — which is what lets the local-bucket-plus-reconcile design keep the hot path free of the network entirely and pay coordination only in a trickle off to the side. The standing tension, from Lesson 8's perfect single counter to here: limit accuracy vs coordination latency & cost.

The four traps

  • Trap 1 — checking a central counter on every request. It's exact, but it bolts a network round trip (cross-region, ~70 ms) onto every call and turns a popular key into one hot counter doing thousands of increments/second. Rate limiting tolerates approximation, so paying for exactness is paying for something you don't need.
  • Trap 2 — statically dividing the limit by the number of servers. Traffic is never evenly spread; a skewed key gets throttled far below its real budget while idle servers hoard unused allowance. Giving each server the full limit instead makes the global limit N× too loose. Reallocate dynamically via reconciliation.
  • Trap 3 — treating the overshoot as unknowable fuzz. It isn't — it's bounded by arrival-rate × sync-interval. If you can't state your worst-case overshoot, you haven't designed the limiter; you've hoped. Pick the tolerance, then set T.
  • Trap 4 — ignoring the partition case. When the coordinator is unreachable, doing nothing means either leaking the limit (if you kept last state and drifted) or rejecting good traffic (if you fail closed by accident). Decide fail-open vs fail-closed on purpose; the safe default is a static per-region share.

Where we landed

We took Lesson 8's single-node token bucket and made its limit hold across 30 servers in 3 regions — one shared "60/minute per key," honored no matter which server each request reaches. Estimate exposed the tension: coordinate on every request and a cross-region round trip (~70 ms) dwarfs the request's own work (~5 ms) while a popular key becomes one hot counter; coordinate never and a skewed key is throttled to 1/3 of its budget, or the limit leaks 30×. Model found the middle — local buckets + periodic reconciliation that lends idle servers' budget to busy ones — and named the idea that makes it safe: rate limiting tolerates bounded approximation (Lesson 21), so we spend almost no coordination and keep the error small; hard quotas that can't overshoot switch to pre-authorized leases instead. Tracing showed a well-behaved key served with zero coordination on the hot path, an abusive key overshooting by at most arrival-rate × sync-interval (10 requests, then hard-blocked), and a partition forcing the CAP choice with a safe static-share default. The first bottleneck was structural: a shared limit is one logical counter every request contends on, and you cannot make it exact, cheap, and partition-proof at once — the reconciliation interval T is the master dial, and the partition is Lesson 11's CAP theorem in disguise. Every dial named its trade. The standing tension, straight from Lesson 8: limit accuracy vs coordination latency & cost.
