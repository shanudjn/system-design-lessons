Consistent Hashing: Add a Shard Without the Storm

Lesson 03 ended on a cliff: our 16 shards are full, we add a 17th, and hash % N stampedes 94% of 6 billion rows across the network. This lesson fixes exactly that — same system, same four moves — so that adding (or losing) a shard moves only about 1/N of the keys. The trick is a circle.

Where Lesson 03 left us

We shard the shortener with shard = hash(short_code) % N. It spreads the 6 billion rows evenly across N=16 machines, and reads and writes both recompute the shard from the code — nothing stores "which shard." That all works until N changes. The instant we go from 16 to 17 shards, almost every code routes somewhere new, because the destination is glued to the divisor N. Here is the whole problem and the whole fix on one screen.

  NAIVE  hash % N                          CONSISTENT HASHING (the ring)

   place keys by  hash % N                  place keys AND nodes on a circle
   add a node  → N changes →                a key belongs to the first node
   the divisor changes for EVERY key →       found walking CLOCKWISE from it
   ~94% remap → mass migration              add a node → it splits ONE arc →
                                            only that arc's keys move (~1/N)

        0 1 2 ... 15   (16 boxes)                  ╭───── 0 ─────╮
        add box 16 →  % 16 becomes % 17        850·A           B·370
        almost every key lands elsewhere          │   key@410   │
                                                  D·            ·C
                                                   ╰──── 610 ───╯
                                            key@410 → walk CW → first node = C

The flaw in Lesson 03 was never the hash function — it was binding the hash to N. Consistent hashing keeps the hash but removes that binding: keys and nodes share one fixed address space (a circle), and a key is owned by whichever node it bumps into going clockwise. Move a node and only its immediate neighborhood is affected.

Move 1 — Estimate: how much data actually moves?

Before designing, price the migration both ways. One row ≈ 200 bytes (Lesson 03), and we have 6 billion of them = 1.2 TB. We add a 17th shard. The question is: how many bytes cross the network, and how long is the system in a half-migrated, ambiguous state?

Naive % N, 16 → 17. A key keeps its shard only if hash % 16 == hash % 17, which happens for about 1/17 ≈ 5.9% of keys. So 94.1% move.

Bytes moved = 0.941 × 1.2 TB ≈ 1.13 TB. At a realistic ~1 GB/s of usable migration bandwidth that's 1,130 GB ÷ 1 GB/s ≈ 1,130 s ≈ 19 minutes of the whole fleet shuffling — during which a code might be on the old shard or the new one. resharding storm

Consistent hashing, 16 → 17. The new shard inserts at one place on the circle and takes over just the arc between itself and the node behind it — about 1/17 ≈ 5.9% of keys.

Keys moved = 6,000,000,000 ÷ 17 ≈ 353 million rows = ~71 GB. At 1 GB/s that's ~71 seconds. Same hardware change, ~16× less data and ~16× less time in the ambiguous state.

Name the trade-off up front: consistent hashing doesn't make routing free — you now keep a small sorted structure (the ring) and do a binary search per lookup instead of one modulo. You spend a little memory and lookup complexity to buy a ~16× smaller migration every time membership changes. And membership always changes: you add capacity, a node dies, you replace a box. The cheaper that event is, the more freely you can do it.

Move 2 — Model: keys and nodes on one circle

A hash ring is the integer range 0 … 2³²−1 bent into a circle, so the largest value wraps back to 0. We hash two different things into that same range:

  • Each node (shard) — hash its name, e.g. hash("shard-C") → a point on the circle.
  • Each key (short code) — hash it the same way → another point on the circle.

The ownership rule is one sentence: a key belongs to the first node you meet walking clockwise from the key's point. That's it. The node "covers" the arc from the previous node up to itself.

We'll use a toy ring of 0…999 so the numbers fit in your head (real rings use 2³²). Place four shards and one key:

  RING 0..999  (wraps: 999 → 0)        owner = first node CLOCKWISE from the key

         pos 0 ───────────────► clockwise
       ┌──────────────────────────────────────┐
   A @ 120 ──covers (850→0→120]                │   key "8tWk"  hash = 410
   B @ 370 ──covers (120 → 370]                │   walk CW from 410:
   C @ 610 ──covers (370 → 610]   ◄── 410 lands │     next node ≥ 410 is  C @ 610
   D @ 850 ──covers (610 → 850]    here, in C's │   ⇒ "8tWk" lives on shard C
       └──────────────────────────────────────┘
   a key at 880 → walk CW past 999, wrap to 0, first node A @120 ⇒ shard A

Worked lookup. hash("8tWk") = 410. The shard points sorted are 120, 370, 610, 850. Find the smallest one ≥ 410 → that's 610 = shard C. If the key were 880, nothing is ≥ 880, so we wrap to the smallest point 120 = shard A. The lookup is a binary search over four numbers — O(log n), not a scan.

Now add a shard — and watch how little moves

Data grew; we add shard E and it hashes to 500. Before, the arc (370 → 610] all belonged to C (it was the first node clockwise for everything in that span). E now sits inside that arc and splits it:

  BEFORE add E:        (370 ──────────────► 610]  all  C
  AFTER  add E@500:    (370 ──► 500]  E      (500 ──► 610]  C

  Effect on our key "8tWk" @ 410:   410 is in (370,500]  → moves  C ⟶ E
  Everything outside (370,500]:     UNCHANGED  (A, B, D, and C's tail keep their keys)

Adding E touched exactly one arc. Only keys between B (370) and the new node E (500) moved, and they all came from a single donor, C. No other shard sent or received a byte. That is the entire point: a membership change is local to the new node's neighborhood, not global like % N.

In our toy the moved arc is (370,500] = 130/1000 = 13% — lumpy, because four random points don't cut the circle into equal slices. With 16 well-spread nodes the moved arc is ~1/17. That lumpiness is the next problem to solve.

Move 3 — Trace the paths: the lumpiness bug, and virtual nodes

One node = one point on the ring has two ugly failure modes. Trace them.

Bug 1 — uneven load

Random points split the circle into unequal arcs. By bad luck shard C might own a 200-wide arc while D owns a 90-wide arc — C then holds ~2× the data and traffic of D. No hotspot protection at all.

Bug 2 — failure dumps on one neighbor

If C dies, all of C's keys flow to the very next node clockwise (D). D instantly inherits C's entire load on top of its own — it can double and tip over. The failure spreads to one unlucky machine.

The fix is virtual nodes (vnodes): instead of placing each physical shard at one point, place it at many points by hashing "shard-C#1", "shard-C#2", … "shard-C#150". Each physical shard now owns ~150 tiny arcs scattered all around the ring.

  1 point per node                    150 points per node (virtual nodes)

   A───────B─────C────D                a-c-b-d-a-b-d-c-a-d-b-c-a-c-...
   big arcs, very uneven                hundreds of tiny arcs, interleaved
   C dies → ALL of C → D                C dies → C's 150 arcs each merge into
   (one neighbor doubles)               a DIFFERENT neighbor → load spreads

How smooth, exactly? The spread of load across nodes shrinks roughly like 1/√V, where V is vnodes per node. So:

V=1 → loads can differ ~100% (2×).   V=100 → busiest vs quietest within ~10%.   V=256 → within ~6%. Most real systems use ~100–256 vnodes per node.

Failure spreads, too. With vnodes, a dead shard's 150 arcs each have a different clockwise neighbor. Its 1/16 share is handed out across the surviving 15 nodes: each gains only (1/16) ÷ 15 ≈ 0.42%, moving from 6.25% to ~6.67% load. No single neighbor doubles. The same math runs in reverse when you add a node: it pulls a thin slice from many donors at once, so the rebalance is spread and fast.

Name the trade-off: more vnodes = smoother load and gentler failures, but the ring now holds N × V entries (16 × 150 = 2,400 points) costing more memory and slightly slower lookups, plus more bookkeeping during a move. You're spending memory and per-lookup work to buy balance and graceful failure. V around 100–256 is the usual sweet spot — past that you pay memory for balance you can't measure.

Move 4 — Find the next bottleneck

The ring scales membership changes beautifully. Two honest things it still does not solve:

(a) Consistent hashing balances key count, not key heat. It spreads 6 billion codes evenly, but if one short link goes viral, every request for that code hashes to the same single shard. The ring can't split one key. That's a hot key, and it's handled higher up — by the cache from Lesson 02, or by replicating that one key to several nodes. Even load on average ≠ even load per request.

(b) Rebalancing is itself heavy background work. Even at ~71 GB, moving a new shard's keys is a long job that must run without blocking live reads and writes. You don't do a 71 GB copy inside a user's request — you hand it to background workers that stream keys over while traffic keeps flowing. And the original villain from Lesson 03, the enterprise bulk API minting millions of links, has the same shape: don't do bulk work on the request path.

The transferable idea: consistent hashing is the standard answer anywhere a set of items must be spread over a changing set of machines — database shards, cache servers (the original 1997 use case was web caches), and partitioned queues. Whenever you hear "we added a cache node and the hit rate cratered," the cause is % N remapping everything, and the fix is a ring. The moment a change becomes cheap, you stop fearing it.

Where we landed

We took Lesson 03's cliffhanger — adding one shard remaps 94% of 6 billion rows — and made it cost ~1/N instead. Estimate priced the two migrations: 1.13 TB / ~19 min naive vs ~71 GB / ~71 s with a ring. Model put keys and nodes on one 2³² circle and owned each key by the first node clockwise, so adding a node splits only one arc. Tracing exposed lumpy arcs and one-neighbor failure dumps, fixed by virtual nodes (~100–256 per node, balance improving like 1/√V). The next bottlenecks — a single hot key the ring can't split, and rebalancing as heavy background work — point straight at queues and replication. Same four moves; membership changes are now cheap.
