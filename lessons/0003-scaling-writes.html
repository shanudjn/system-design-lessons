Scaling Writes: One Counter, Many Shards

Lessons 01–02 were about reads — the shortener was read-heavy, so we cached. But the system has one piece every write still squeezes through: the single counter that hands out IDs. And all 6 billion rows still live on one disk. When writes spike, both crack. We fix them with the same four moves.

Where Lessons 01–02 left us

From Lesson 01, every new link does two things on the write path: INCR counter to get the next number, then Base62-encode it into a short code (e.g. counter 1,000,000 → "4c92") and INSERT the row. From Lesson 02 we know there are ~6 billion links on a single database. Writes were tiny — at a 100-to-1 read/write ratio, the ~3,800 reads/sec implied only ~38 writes/sec. A single database laughs at 38 writes/sec.

Then the product landed an enterprise bulk API: customers generate links by the millions during ad campaigns. Peak write rate is now projected at 40,000 new links/sec. Two things that were fine at 38/sec are now on fire. Here they are on one screen.

(1) One counter is a single row every writer must serialize through — a coordination ceiling and a single point of failure. (2) 6 billion rows don't fit or write fast enough on one machine — we must split the data across shards. (3) The naive way to pick a shard makes adding one shard reshuffle almost everything. We take them in order.

Move 1 — Estimate: where exactly are the ceilings?

Before redesigning anything, measure the two walls we're about to hit: a throughput wall (IDs per second) and a storage wall (bytes on one disk).

Throughput wall — the single counter. Every write must do INCR counter on one row. The database serializes those updates so two writers never get the same number. A single primary doing durable, serialized increments tops out around ~10,000/sec in practice (disk fsync + lock contention on that one row).

Demand at peak = 40,000 writes/sec.  →  40,000 ÷ 10,000 = 4× over the ceiling. counter is the bottleneck

Storage wall — one disk. One row ≈ short_code (7 B) + long_url (100 B) + created_at + owner + index overhead ≈ ~200 bytes/row.

Total = 6,000,000,000 × 200 B = 1.2 TB today. With 10× growth ahead → 12 TB — past what one node comfortably holds and writes to.

Why both walls matter even though writes used to be trivial: the counter is a problem of coordination (everyone needs the same source of truth for "the next number"), and storage is a problem of volume (bytes outgrow one box). They're separate, and they need separate fixes: distributed ID generation for the counter, sharding for the storage. Confusing the two is a classic mistake — a bigger disk doesn't fix the counter, and a faster counter doesn't fix the disk.

Move 2a — Model the IDs: who hands out "the next number"?

The single counter is simple and gives short, dense, perfectly-ordered codes — counter 41 is just "j", counter 1,000,000 is "4c92". The price is that every writer on Earth must touch that one row. To remove the bottleneck we must let many machines mint IDs without all asking the same row each time. Three honest ways:

ID blocks (ticket server) ✅

Keep one counter, but hand out IDs in blocks. An app server asks once for a block of 1,000 IDs (say 5,000,000–5,000,999), then serves 1,000 links locally before asking again.

Coordination drops 1,000×. Codes stay short and roughly ordered. The counter row is touched 40 times/sec, not 40,000.

Snowflake ID

No shared counter at all. Each machine builds a 64-bit ID from time + machine-id + a per-millisecond sequence. Unique by construction, sortable by time.

Zero coordination, but IDs are big (≈ 11-char codes) and depend on synced clocks + unique machine IDs.

The Snowflake walk-through (worked, because the bit-budget is the whole idea)

A Snowflake ID is a single 64-bit integer whose bits are divided into fields. One common split:

  64-bit Snowflake ID  =   [ 1 ] [    41 bits    ] [ 10 bits ] [  12 bits  ]
                            unused   timestamp (ms)  machine id   sequence
                            (sign)   since an epoch  (which box)  (Nth id this ms)

How long do 41 timestamp bits last? 241 = 2,199,023,255,552 ms. ÷ 1000 ÷ 86,400 ÷ 365 ≈ 69.7 years of unique millisecond stamps. Plenty.

How many machines? 210 = 1,024 distinct machine IDs.

How many IDs per machine per millisecond? 212 = 4,096. So per machine per second = 4,096 × 1,000 = 4,096,000 IDs/sec.

Capacity check: we need 40,000/sec. One Snowflake machine already does ~4.1M/sec — so a single generator is 100× over our peak, with zero cross-machine coordination. Across all 1,024 machines the ceiling is ~4.2 billion IDs/sec.

Name the trade-off (the part that decides it for a shortener): Snowflake removes coordination but its 64-bit numbers Base62-encode to ~11 characters instead of 7 — log62(263) ≈ 10.6. Longer codes partly defeat the point of a shortener. ID blocks keep codes short and remove the hot single row. So for this system we pick ID blocks; Snowflake is the right call when you care less about code length and more about generating IDs anywhere with no server to ask (e.g. tweets, events, log records).

ID-blocks math: at 40,000 writes/sec with a block size of 1,000, the central counter sees 40,000 ÷ 1,000 = 40 requests/sec — a 1,000× cut, far under its ~10,000/sec ceiling. We can also make the counter a highly-available pair so it isn't a single point of failure. Cost: if a server crashes mid-block, the unused IDs in that block are lost forever — you trade a few wasted IDs for 1,000× less coordination. For a shortener with billions of codes to spare, that's a trivial price.

Move 2b — Model the storage: split 6B rows into shards

IDs are solved, but the rows still live on one disk. Sharding means splitting one logical table across many physical databases (shards), each holding a slice of the rows. The only real question: given a short code, which shard owns it? Two honest schemes.

Hash partitioning ✅

Shard number = hash(short_code) % N. The hash scatters codes evenly, so each of N shards gets ~1/N of the rows and ~1/N of the writes.

Even load by design. No single shard becomes a hotspot just because it holds the newest links.

Range partitioning

Shard by ranges of the code/time: codes aaaa–ffff on shard 0, etc. Great for "list everything between X and Y."

But the newest range is a hotspot — every fresh write lands on whichever shard owns the latest range, so one shard takes all the write heat.

Name the trade-off: hash partitioning spreads writes perfectly but destroys range scans — "give me all links created Tuesday" now means asking every shard and merging (a scatter-gather). Range partitioning keeps scans cheap but concentrates writes on the newest shard. A URL shortener looks up one code at a time and almost never range-scans, so we choose hash and happily give up scans we don't need.

Sharding math, N = 16:

Writes per shard = 40,000 ÷ 16 = 2,500 writes/sec — comfortably under one node's limit.

Storage per shard = 1.2 TB ÷ 16 = ~75 GB each — small and fast.

Reads from Lesson 02 (the ~152/sec that miss the cache) also split 16 ways → ~10/sec per shard. Sharding scales reads and writes; the cache and the shards stack.

Move 3 — Trace the paths: a write and a read, end to end

Creating a link (the write)

1. POST /shorten {long_url}
2. App server takes the next id from its LOCAL block  (no network trip if block has IDs left)
3. Base62-encode the id  →  short_code = "8tWk"
4. shard = hash("8tWk") % 16  →  shard 5
5. INSERT (short_code, long_url, created_at) INTO shard 5
6. Return https://sho.rt/8tWk

Notice steps 2 and 4 are independent: the ID block answers "what number," the hash answers "which shard." The code does not encode its shard — we recompute the shard from the code on every read.

Resolving a link (the read, revisited)

1. GET /8tWk
2. shard = hash("8tWk") % 16  →  shard 5      (same function, so same answer)
3. Check cache (Lesson 02). Hit? return. Miss?
4. SELECT long_url FROM shard 5 WHERE short_code='8tWk'
5. Backfill cache, return 301/302

The routing function must be deterministic: the same short_code must always hash to the same shard, on writes and reads alike, forever. That one rule is what lets us find a row again without storing "which shard" anywhere. It's also exactly what makes adding a shard painful — change the function and old codes route to the wrong place.

Move 4 — Find the next bottleneck: resharding

Everything works at N = 16. Now the data grows and we need a 17th shard. Watch what % N does the instant N changes from 16 to 17.

A code stays put only if hash % 16 equals hash % 17 — which is rare. The fraction of keys that keep their shard is about 1/17 ≈ 6%.

So adding one shard forces ~94% of 6 billion rows to move between machines. During that migration, routing is ambiguous (is the row on the old shard or the new one yet?), and the network melts. resharding storm

  NAIVE  hash % N                          BETTER  (next lesson)
  add shard 17 → N changes → almost         spread keys on a RING so adding a node
  every key remaps → mass migration         only moves the keys near it (~1/17 of them)

   % 16:  k → shard 5                        ring:  k → next node clockwise
   % 17:  k → shard 12   (moved!)            add node → only neighbours' keys move
   ...94% of keys move...                    ...~6% of keys move...

The transferable lesson: % N is a fine router until N changes — and N always changes (you add capacity, a node dies). The flaw isn't the hash; it's that the hash is tied to the current node count. The fix, consistent hashing, breaks that tie so a membership change moves only a small slice of keys. That's the whole of Lesson 04. We've now hit it honestly instead of asserting it.

Where we landed

We took the write path that "didn't matter" and pushed it to 40,000/sec. Estimate found two separate walls: a throughput ceiling on the single counter (~10k/sec) and a storage ceiling on one disk (1.2 TB → 12 TB). Model fixed them separately — ID blocks to mint IDs with 1,000× less coordination (Snowflake when you can spare longer codes), and hash sharding to spread 6B rows over 16 machines at ~75 GB and 2,500 writes each. Tracing showed the shard is recomputed from the code, never stored. The next bottleneck is what happens when you add a shard — % N remaps ~94% of keys — which is exactly the door into consistent hashing. Same four moves; the write side now scales.
