Autoscaling & Capacity Planning: Sizing a Fleet Before the Spike Hits

Lesson 26 leaned on a word without earning it: headroom. We said "run the gateways below capacity so N−1 boxes can absorb a death" — but how far below, and how do you add servers before the storm instead of scrambling during it? This lesson answers both for the API tier behind those gateways: 40,000 requests per second at peak, each request needing about 40 ms of CPU. We'll estimate the fleet size two ways that must agree (Little's Law from Lesson 13 returns), find the utilization knee near ~70% where latency stops being linear and shoots to the moon, model the autoscaler as a feedback loop (measure → decide → provision → warm), trace three loads — a gentle morning ramp, a sudden 2× spike, and a known scheduled surge — and then hit the wall that defines this whole domain: a server takes ~3 minutes to boot and warm up, so a reactive autoscaler can never catch a spike that rises faster than that. The trade shifts from Lesson 26's statefulness-vs-scale to the one every capacity decision comes down to: cost vs headroom for spikes.

The one system we'll design

An API fleet — plain stateless request/response servers (Lesson 18's REST), the tier that does the actual work behind the connection gateways of Lesson 26. Every server is identical and interchangeable; a load balancer sprays requests across them. Our job is to decide how many servers to run, moment to moment, as load rises and falls — enough to keep responses fast, not so many that we burn money on idle boxes. Concretely: peak load ≈ 40,000 requests/second, each request costs about 40 ms of CPU time (one core, one request, 40 ms — call this the service time), and each server has 8 cores.

The naive plan is "watch CPU, add a server when it's busy, remove one when it's idle." That instinct is right and also the source of every autoscaling disaster, because a server you ask for now doesn't exist for another few minutes. Here is the whole shape in one picture — the control loop, and the curve that makes it dangerous.

Autoscaling is a control loop with a delay built into it. The autoscaler measures load, decides how many servers it wants, and asks for them — but the servers take minutes to arrive. So capacity planning is really two questions: what is the right number of servers for a given load (the knee), and how do you have them running before the load that needs them shows up (the lag). Everything in this lesson is one of those two.

Words we'll earn before we lean on them

  • Service time (S) — how long one request occupies one core of work. Here 40 ms. Not the same as response time (which includes waiting).
  • Throughput / capacity (C) — how many requests a server can finish per second at full tilt. One core at 40 ms/req does 1 ÷ 0.04 = 25 req/s; 8 cores → 200 req/s per server.
  • Utilization (ρ, "rho") — the fraction of capacity in use: ρ = load ÷ capacity. A server taking 140 req/s of its 200 possible is at 70%.
  • Response time (T) — service time plus time spent waiting in the queue for a free core. This is what the user feels.
  • Little's Law (Lesson 13) — in any stable system, items in flight = arrival rate × time each spends inside: L = λ × W. It ties fleet size to load and latency.
  • The utilization knee — the point (~70–80%) where the response-time curve bends sharply upward. Below it, more load costs a little latency; above it, a little more load costs a lot.
  • Autoscaler — the controller that watches a metric and adds/removes servers to keep it near a target. Target tracking = "keep utilization at 70%."
  • Scale-out / scale-in — add servers / remove servers (horizontal). Distinct from scale-up (bigger servers, vertical).
  • Cold start / warm-up lag — the minutes between "launch a server" and "that server can safely take traffic": boot, app start, JIT/cache warm, health checks.
  • Reactive vs predictive scaling — respond to load you're already seeing, vs provision ahead of load you expect (a schedule, a forecast).
  • Warm pool — pre-booted standby servers kept ready so they can take traffic in seconds instead of minutes. You pay for idle to buy speed.
  • Cooldown / flapping — a wait after each scaling action so the fleet doesn't thrash (add-remove-add) around the threshold (Lesson 10's leadership flap, now for capacity).
  • Scale-to-zero — run no servers when idle; the first request pays a full cold start. The extreme end of the cost-vs-latency dial.

Move 1 — Estimate: how many servers, two ways that must agree

We size the fleet twice — once from raw work, once from the latency we're willing to tolerate — and the two answers have to line up. The gap between them is the headroom decision.

Worked (way 1): the floor, from Little's Law. At peak, λ = 40,000 req/s arrive, each needing S = 40 ms = 0.04 s of core time. Little's Law says the number of cores kept busy at once is:

• busy cores = λ × S = 40,000 × 0.04 = 1,600 cores working every second, flat out.

• at 8 cores/server that's 1,600 ÷ 8 = 200 servers — but only if every core runs at 100%. This is the absolute floor: fewer than 200 servers physically cannot finish 40,000 req/s, no matter the latency. Little's Law gives you the wall you can't go below; it does not give you a number you'd actually run at.

Worked (way 2): the target, from the knee. Nobody runs at 100% — that's the right edge of the curve where latency is seconds. Model one server as a queue: response time T = S ÷ (1 − ρ). Watch what utilization does to a 40 ms request:

• ρ=0.5 → 40 ÷ 0.5 = 80 ms ·  ρ=0.7 → 40 ÷ 0.3 = 133 ms ·  ρ=0.8 → 200 ms ·  ρ=0.9 → 400 ms ·  ρ=0.95 → 800 ms ·  ρ=0.99 → 4,000 ms.

The curve is flat then vertical — that bend is the knee. Pick ρ* = 70% as the operating point (133 ms, still on the flat part, with room to rise before disaster). Each server then safely carries 200 × 0.70 = 140 req/s, so:

• fleet = 40,000 ÷ 140 = 285.7 → 286 servers. (Cross-check via cores: 1,600 ÷ 0.70 = 2,286 cores ÷ 8 = 286. The two ways agree.)

So the honest fleet is 286 servers, not 200. Those extra 86 servers (43% more) buy nothing but distance from the knee — they exist so that when load twitches upward, latency rises from 133 ms toward 200 ms instead of from 4 s toward a timeout. At ~$0.50/server-hour that headroom costs 86 × $0.50 × 24 × 365 ≈ $377,000/year. That is the price, in dollars, of the word "headroom."

Name the trade-off — latency vs cost, decided at the knee. Run closer to 100% and you spend less on servers but sit on the vertical part of the curve, where any small surge (or one dead box, Lesson 26) tips you into multi-second latency and timeouts. Run at 50% and latency is rock-steady but you're paying for nearly double the fleet. The knee (~70%) is the defensible middle: the last utilization where the curve is still flat enough that a normal wobble doesn't hurt. Capacity planning is choosing where on the T = S/(1−ρ) curve to live — and the knee exists because queueing latency is not linear in load.

Move 2 — Model: the autoscaler as a feedback loop

We don't run 286 servers all day — peak is 40,000 req/s but 3 a.m. might be 4,000. Running peak-sized around the clock wastes ~90% of the fleet at night. So the number of servers must track the load. That tracking is a control loop: measure a signal, compare it to a target, change the fleet, wait, repeat.

  THE CONTROL LOOP  (target tracking on utilization)

   every ~30-60 s:
     1. MEASURE   average utilization across the fleet    ->  ρ = 0.85  (85%, too hot)
     2. COMPARE   to target                               ->  ρ* = 0.70
     3. DECIDE    desired = ceil( current × ρ / ρ* )      ->  286 × 0.85/0.70 = 348
                  (equivalently: desired = ceil( load ÷ (C × ρ*) ) = 40k/... )
     4. ACT       launch (348 − 286) = 62 new servers
     5. COOLDOWN  wait before the next change, so the fleet doesn't thrash
                                                             |
     ...but each of those 62 servers isn't usable for ~3 min ---+  <-- the lag (Move 4)

  Scaling metric options (what to put in step 1):
     utilization  — direct, but lags a sudden spike a little
     req/s per server — proportional to load, predictable
     queue depth / p99 latency — reacts fastest, but noisy

The decision in step 3 is just algebra: if you're at 85% and want 70%, you need 0.85 ÷ 0.70 = 1.21× the current servers. Feed it load instead and it's the Move 1 formula living on a timer: desired = load ÷ (capacity/server × ρ*). Nothing clever — the whole art is in the parts the formula hides: which metric you steer on, how often you look, and how long you wait between moves.

Two design choices matter most. First, scale-out fast, scale-in slow. Adding servers late is an outage; removing them late is a few dollars. So react quickly when hot and dawdle when cold — a long cooldown on scale-in. Second, don't thrash. If you add at 71% and remove at 69%, a fleet hovering near 70% will add-remove-add forever, and since each add costs a 3-minute warm-up, the thrash is pure waste. Widen the band (add above 75%, remove below 55%) and enforce a cooldown — the same flapping failure as Lesson 10's leader election, now measured in servers instead of votes.

Name the trade-off — responsiveness vs stability. Steer on a twitchy signal (p99 latency, queue depth) with a short window and the autoscaler reacts to spikes fast — but it also jumps at every random blip and flaps. Steer on a smooth signal (average utilization) with a long window and cooldown and the fleet is calm and cheap — but slow to notice a real surge. You can't have instant and stable from one reactive loop; you tune where on that dial to sit, and (Move 4) you add a second, non-reactive mechanism for the surges the loop can't catch in time.

Move 3 — Trace the paths

Three loads through the same loop. Watch one thing: whether the load rises slower or faster than a server can boot. That single comparison decides whether reactive scaling works or fails.

Path A — the morning ramp (reactive scaling works)

  07:00  load 8,000 req/s   -> fleet 57,  ρ ~70%,  calm
  09:00  load rising ~ +5% every 5 min (a slow, smooth climb toward the 40k peak)

  loop each minute:  ρ drifts to 75% -> desired = 57 × 75/70 -> add a few servers
                     new servers ready in ~3 min, but load only moved a few % in 3 min
                     -> capacity stays a step ahead of demand the whole ramp
  11:00  load 40,000 req/s  -> fleet 286,  ρ ~70%,  still calm

A gentle ramp is the easy case: demand rises slowly enough that the 3-minute warm-up doesn't matter — by the time you need the servers, the ones you asked for three minutes ago have arrived. Reactive target-tracking handles the daily up-and-down of most services beautifully, which is exactly why it's the default. Reactive scaling works whenever load changes slower than servers boot.

Path B — the sudden spike (reactive scaling fails)

  12:00:00  load 40,000 req/s, fleet 286, ρ=70%   (marketing push fires / L26 gateway dies)
  12:00:30  load has DOUBLED to 80,000 req/s in 30 s

  reactive loop:
    +30 s   metric window notices ρ pinned at ~140%  (80k on a 40k fleet)
    decide  desired = 40k→80k  ->  need 572 servers (add 286)
    launch  286 servers ... ready at +3 min

  MEANWHILE, from 12:00:30 to ~12:03:30, the fleet is 286 vs a load of 80,000:
     ρ = 80,000 ÷ (286 × 200) = 1.40   -> 140%, past 100%, the queue grows without bound
     response time leaves the knee entirely -> seconds -> timeouts -> retries (L07)
     -> retries add load -> metastable collapse risk while you WAIT for boots

Same loop, opposite outcome. The load doubled in 30 seconds; the servers to serve it don't exist for 3 minutes. For those ~3 minutes the fleet is running at 140% — which isn't "slow," it's a queue that grows every second, response times in the seconds, timeouts, and the retry storm of Lesson 07 piling on more load precisely when you have none to give. A reactive autoscaler cannot catch a spike that rises faster than a server boots — by definition it's chasing a number that's already wrong. This is the wall; Move 4 is how you don't hit it.

Path C — the scheduled surge (predict, don't react)

  Known event: the 8:30 AM daily push (index.html says so!) sends every user a link.
  Reactive would discover the surge at 8:30:30 and be 3 min late = a 3-min brownout.

  Predictive / scheduled scaling:
    08:20  autoscaler PRE-SCALES to 572 servers on a schedule (10 min early)
    08:30  the surge lands on a fleet that is ALREADY warm  -> ρ jumps 35% -> 70%, calm
    08:45  surge passes -> scale back in slowly (long cooldown)

When a spike is predictable — a daily cron, a product launch, a Super Bowl ad, market open — you don't have to lose the race against boot time, because you can start before the gun. Scheduled scaling (or a forecast-driven predictive autoscaler) provisions the fleet ahead of the known load, so the servers are warm when it arrives. The reactive loop still runs underneath to catch the surprises; prediction just removes the surprises you already know about. The cure for boot-time lag is to start booting before you need the capacity — which you can only do for load you saw coming.

Name the trade-off — react vs predict. Reactive scaling needs no forecast and follows any shape of load, but it's always one warm-up behind, so it's helpless against a step change. Predictive/scheduled scaling is early enough to beat the step, but only for load you can foresee, and it wastes money (or under-provisions) whenever the forecast is wrong. Real systems run both: predict the known surges, react to everything else — and keep enough headroom that "everything else" never fully outruns the boot.

Move 4 — Find the first bottleneck: the cold-start lag (a control loop with dead time)

Path B named the wall; here's why it's fundamental and how you engineer around it. Every feedback loop has dead time — the delay between acting and the action taking effect. In autoscaling the dead time is the warm-up, and it's brutal because it's minutes long while spikes are seconds long. Let's break down where the ~3 minutes goes and then reduce its damage — because you can't reduce the boot time to zero.

Worked: where the 3 minutes goes, and why the fleet drowns. Ask for a new server at t=0:

• ~30 s provision the machine (VM/instance boot, kernel, network) · ~30 s pull & start the app image · ~60 s JIT/connection-pool/cache warm-up (a cold app is slow and would itself fall over) · ~30 s pass health checks before the load balancer trusts it. Plus the autoscaler's own ~30 s metric window to even notice. Total ≈ 180 s from spike to safe traffic.

• During that window in Path B, load is 80,000 on a fleet built for 40,000: ρ = 80,000 ÷ 57,200 = 1.40. Above 100% the queue has no steady state — backlog grows at 80,000 − 57,200 = 22,800 requests/second. Over ~180 s that's ~4.1 million requests queued or dropped before help arrives. The bottleneck isn't a lack of servers — it's the time-to-server. Capacity you can't have for 3 minutes is capacity you don't have during a 30-second spike.

You cannot delete the boot time, so you attack the gap it opens — four levers, each a familiar tool aimed at the lag:

  • Headroom as a spike buffer (revisit Move 1). Run at 60% instead of 70% and the fleet is 40,000 ÷ (200 × 0.60) = 333 servers (47 more, ~$206k/yr). Now the empty 40% absorbs a bump instantly: load can rise to 333 × 200 × 0.70 = 46,620 req/s (+16%) before you even reach the knee — buying one whole boot-window of slack with zero new servers. Headroom converts money into reaction time you'd otherwise have to wait for.
  • Warm pools (pay idle to buy speed). Keep some servers pre-booted and warm on standby; when the spike hits they take traffic in seconds, not minutes, while the real boots happen behind them. A pool of, say, 60 warm boxes covers the first slice of a doubling instantly. You pay for idle capacity to shrink the dead time — the direct cost-for-latency trade.
  • Predictive / scheduled pre-scaling (Path C). For any surge you can foresee, start booting before it lands so the lag happens on your clock, not the spike's.
  • Faster warm-up (shrink the lag itself). Smaller images, pre-baked machine images, lazy-loading less at startup, snapshot/restore of a warm process — every second shaved off the 180 s is a second less drowning. This is why "cold start" is a first-class metric, not a footnote.

And at the far end of the same dial sits scale-to-zero: for a spiky, low-traffic service (an internal tool, a rarely-hit endpoint) you can run no servers when idle and eat a full cold start on the first request — trading user-facing latency for near-zero cost. For a user-facing tier like ours that's unacceptable; you keep a warm floor. Same knob, opposite ends: how much idle capacity you pre-pay is exactly how much cold-start latency you refuse to expose.

Name the core trade-off — cost vs headroom for spikes. Every lever above is the same purchase in a different currency: extra headroom, warm pools, scale-to-zero avoidance, and generous cooldowns all cost money for idle-ish capacity, and what they buy is the ability to absorb a spike faster than you can boot for it. Run lean and you save cash but stand naked in front of the next 30-second surge; run padded and you're safe but paying for servers doing nothing most of the time. There is no setting that is both cheapest and spike-proof — the autoscaler doesn't remove that choice, it just lets you re-make it every minute. Autoscaling doesn't beat the cost-vs-headroom trade; it turns a once-a-quarter capacity meeting into a continuous one, and the boot-time lag is why you can never set headroom all the way to zero.

Where we landed

We sized and steered the API fleet behind Lesson 26's gateways. Estimate gave the fleet two ways that had to agree: Little's Law fixed the floor (40,000 × 0.04 s = 1,600 busy cores = 200 servers at an impossible 100%), and the utilization knee (T = S/(1−ρ): 133 ms at 70%, but 4,000 ms at 99%) set the real target at 286 servers — the extra 86 (43%, ~$377k/yr) buying nothing but distance from the vertical part of the curve. Model made the autoscaler a feedback loop — measure utilization, compare to a 70% target, set desired = load ÷ (C × ρ*), act, cool down — with the design living in the parts the formula hides: scale-out fast / scale-in slow, and a wide band + cooldown so the fleet doesn't flap (Lesson 10, now in servers). Tracing three loads exposed the one comparison that matters — does load rise slower or faster than a server boots: a gentle morning ramp reactive scaling handles for free; a sudden 2× spike it cannot catch (the fleet runs at 140% for ~3 minutes, ~4.1M requests backed up while boots complete); and a known 8:30 surge you beat only by pre-scaling ahead of it. The first bottleneck was that ~3-minute cold-start lag — a control loop's dead time, minutes long against seconds-long spikes — attacked not by deleting boot time (you can't) but by shrinking the gap it opens: spike-buffer headroom (run 60%, absorb +16% instantly), warm pools (pay idle, take traffic in seconds), predictive/scheduled pre-scaling for foreseeable surges, and faster warm-up itself — with scale-to-zero as the opposite extreme of the same dial. The real lesson: an autoscaler doesn't give you infinite instant capacity — it gives you a feedback loop with a minutes-long delay steering against a latency curve that goes vertical near 100%. You can't set headroom to zero, because the boot-time lag means the capacity you order now isn't the capacity you have now. The trade is cost vs headroom for spikes.
