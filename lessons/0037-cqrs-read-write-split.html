Read/Write Splitting & CQRS: Two Shapes of the Same Data

Several lessons already built a second copy of the data beside the first and never named the pattern. Lesson 2 put a cache in front of the database. Lesson 15 precomputed every follower's feed so the read was a single lookup. Lesson 16 fed a search inverted index, Lesson 29 fed a columnar warehouse, and Lesson 33's outbox/CDC pipeline shipped every change out to all of them. Each time we quietly admitted the same thing: the shape that is good for writing the data is not the shape that is good for reading it. This lesson makes that admission a design. CQRS — Command Query Responsibility Segregation — says: keep one write model optimized for correct, consistent writes (Lessons 6/25), and build as many read models as you have read shapes, each purpose-built and each fed from the write model's change stream (Lesson 33). We'll take one concrete system — the orders service from Lessons 12/24/25/33 (5,000 writes/s, 50,000 reads/s) — and watch a single normalized table that's perfect for placing an order fail four different reads at once, then split it. We'll estimate why reads and writes pull in opposite directions (it's shape, not just volume); model the write side, the read sides, and the projection that connects them; trace a command and a query through the split; and hit the wall the split creates — a read is always a little behind the write (eventual consistency) — which is also the line where CQRS stops being clever and starts being accidental complexity. The trade shifts from Lesson 36's blast-radius isolation to read/write optimization vs the consistency gap between the two sides.

The one system we'll design

The orders service we've grown across the course: 100M orders (Lesson 12), money that must never be lost or doubled (Lesson 25's ledger), a live schema (Lesson 24), and a change pipeline already shipping every write out to search, cache, and the warehouse (Lesson 33). Traffic: 5,000 writes/s (place order, cancel, update address) and 50,000 reads/s — a 10:1 read-heavy load. But the reads aren't one query; they're four wildly different ones, and each wants the data in a different shape:

   COMMANDS (writes, ~5k/s)                     QUERIES (reads, ~50k/s)
   place / cancel / change address              detail page / search / dashboard / status
        |                                          ^          ^         ^          ^
        v                                          |          |         |          |
  +-------------------+                    +----------+ +--------+ +--------+ +---------+
  |   WRITE MODEL     |                    | doc view | | search | |  OLAP  | |  cache  |
  | normalized SQL    |   change events    | (detail) | | index  | | warehse| | (status)|
  | ACID -- the TRUTH |==(L33 outbox/CDC)=>|   L15    | |  L16   | |  L29   | |   L02   |
  +-------------------+     one log,        +----------+ +--------+ +--------+ +---------+
   correctness-first        many readers          READ MODELS (derived, purpose-built,
   (L06/25)                                        each EVENTUALLY CONSISTENT with truth)

   ONE side optimized for correct WRITES.  MANY sides optimized for fast READS.
   They are different SHAPES of the same data, kept in sync by a stream --
   so a read model always trails the write by the projection delay.

CQRS splits one model into a write model and one-or-more read models, connected by a projection. "Command" = a request that changes state (place an order). "Query" = a request that only reads state (show me the order). The ordinary design uses one model for both. CQRS says the two jobs have different needs, so give them different models — and pay for it in the gap between the moment a write lands and the moment every read model reflects it.

Words we'll earn before we lean on them

  • Command — a request that changes state (a write): place order, cancel order. Judged by correctness.
  • Query — a request that returns state and changes nothing (a read): show order 42. Judged by speed and shape.
  • Write model — the single source of truth, shaped so a command is correct and cheap: normalized, constrained, transactional (Lessons 6/25).
  • Read model — a derived copy shaped so one query is fast: a denormalized document, a search index, a columnar table, a cache. Not the truth — a projection of it.
  • Projection — the process that turns the write model's change events into a read-model update. The wire between the two sides (Lesson 33's stream).
  • Read replica — the mild split: a byte-for-byte copy of the write model for read scaling (Lesson 6). Same shape, more capacity — the step before full CQRS.
  • Eventual consistency gap — the delay between a committed write and the read model reflecting it. The cost CQRS introduces.

Move 1 — Estimate: reads and writes pull in opposite directions

Two forces push toward a split. The obvious one is volume: 50,000 reads vs 5,000 writes, so reads deserve their own capacity you can scale independently. But volume alone is solved by a plain read replica (Lesson 6) — same shape, just more copies. The force that actually demands CQRS is shape: the layout that makes a write correct is the layout that makes a read slow, and vice-versa. Price it on the busiest read — the order-detail page.

Worked: the detail page on the write model. A normalized order is scattered across tables so nothing is duplicated: orders + order_items + products (for names) + customers + addresses. Rendering one detail page is a 6-way JOIN — roughly six index seeks at Lesson 12's ~0.4 ms each = ~2.4 ms of database work per page. Say order-detail is 20,000 of the 50,000 reads/s. Cost = 20,000 × 2.4 ms = 48,000 ms/s = 48 CPU-cores spent re-assembling the same joins over and over.

Worked: the detail page on a read model. Precompute the join once (Lesson 15's push): store the whole page as a single denormalized document, order_id → {order, items, product names, customer, address}. Now a read is one key lookup ≈ 0.4 ms. Cost = 20,000 × 0.4 ms = 8,000 ms/s = 8 cores — a 6× cut, and simpler code (no join to plan). Same data, a different shape, one-sixth the work.

Why one table can't win both. To make that read cheap you denormalized — you copied the product name into every order document. But a denormalized copy is exactly what makes a write dangerous: change one product's name and you must now update it in every order document that mentions it (Lessons 15/24's fan-out), and any missed copy is a lost-update anomaly (Lesson 6). The write model stays normalized precisely so a name lives in one row and a change touches one place. Normalized is optimal for writing; denormalized is optimal for reading; no single table is both.

Name the trade-off — one shape can't serve opposite jobs. And the detail page is only one read. Search ("my orders containing 'shoes'") wants an inverted index (Lesson 16), not a table scan. The seller dashboard ("units sold per product per day") wants a columnar warehouse (Lesson 29), not row storage. The live status widget wants a tiny, blazing-hot cache (Lesson 2). A relational write model can be none of these well at once — "normal form is a bet on your write:read ratio" (Lesson 29), and with four different reads you have four different bets. So stop trying to make one model win four arguments: give each read the shape it wants, and keep the writes on the one shape that keeps them correct.

Move 2 — Model: one write side, many read sides, one wire between them

CQRS is three parts: a write model that owns the truth, read models that are cheap derivations of it, and a projection that keeps the derivations current.

The write model — correctness-first. Normalized relational tables, ACID transactions, foreign-key and balance constraints (Lesson 25's ledger, Lesson 6's atomic updates, Lesson 32's invariants). A command validates against it and commits in one transaction. It is the single source of truth; every read model is downstream of it. Optimized for one thing: a write that is correct and cheap because each fact lives in exactly one place.

The read models — one per read shape. Detail page → a denormalized document (Lesson 15). Text search → an inverted index (Lesson 16). Dashboards → a columnar warehouse (Lesson 29). Live status → a cache (Lesson 2). Each is derived, disposable, and eventually consistent — never the truth, always rebuildable.

The result: writes and each read scale, deploy, and fail independently — a heavy dashboard scan can't evict the write model's buffer or trip its knee (Lesson 29's "never share one DB", Lesson 36's blast radius), because it runs on a different store entirely.

What connects them is the piece we already built in Lesson 33. The write model, in the same transaction that commits a command, writes an event to an outbox (or the change is tailed from its commit log by CDC). A projection consumes that stream and applies each change to its read model. This is the load-bearing detail:

  THE PROJECTION -- the only correct way to keep a read model in sync.

   command --> [ WRITE MODEL ]  --commit order + event IN ONE TXN--> outbox
                                                                       |
                              (L33 relay / CDC tails the durable log)  |
                                                                       v
                                             +------- change event stream (at-least-once) -------+
                                             |                |                |                  |
                                             v                v                v                  v
                                        projection A     projection B     projection C      projection D
                                        -> doc view      -> search idx     -> warehouse      -> status cache
                                        (idempotent,     (idempotent,      (idempotent,      (idempotent,
                                         keyed by         L13)              L13)              L13)
                                         event id, L13)

  Rules that make it safe:
    * Project from the DURABLE STREAM, never dual-write from the app to each store
      (writing to write-DB and search-index directly = L33's dual-write trap: they
      diverge on a crash, with no shared transaction to save you).
    * Projections are IDEMPOTENT (L13): at-least-once delivery means an event can
      arrive twice; applying it twice must equal applying it once.
    * A read model is DERIVED, so it is REBUILDABLE: replay the log from the start
      to construct a brand-new read model (L09/L29 kappa) -- add a fifth read shape
      next year with zero write-side change.

Name the trade-off — CQRS vs a read replica. A read replica (Lesson 6) copies the write model byte for byte: it scales read volume but keeps the same shape, so it can serve more detail-page joins but can never become an inverted index or a columnar table. CQRS changes the shape, which is what buys the 6× (and the search, and the aggregates) — but a replica lags by milliseconds of physical replication, while a CQRS projection lags by an application step you built, and it can drift or need rebuilding. Replica = same shape, cheap, tight. CQRS = any shape, powerful, looser. Reach for a replica when you need more of the same read; reach for a read model when you need a different read.

Move 3 — Trace the paths

Two runs — a command down the write side, a query up a read side — and then the gap between them.

Path A — a command (place order)

  POST /orders  (Alice buys 2 items, $120)

   1. Validate against the WRITE MODEL: item in stock? balance ok? (L25/L32 invariant)
   2. ONE transaction: insert order + order_items  AND  insert an outbox event
        {type:"OrderPlaced", order_id:42, ...}          (L33: two writes, one commit)
   3. ACK Alice -- the command is durably done the instant the write model commits.
        (nothing downstream has run yet)
   -- async, off the commit path --
   4. Relay/CDC publishes event 42 to the stream (L33).
   5. Each projection applies it idempotently (L13):
        doc view: assemble & store the detail document for order 42
        search  : tokenize product names, add to the inverted index (L16)
        warehse : append a fact row for tonight's aggregates (L29)
        cache   : set status=PLACED for the live widget (L02)
   -> Order 42 appears in each read model after THAT projection's own delay.

Path B — a query (four different reads, four different models)

  GET  /orders/42            -> doc view    : 1 key lookup, no JOIN (~0.4 ms)   [was 2.4 ms]
  GET  /orders?q=shoes       -> search idx  : postings intersect (L16), not a scan
  GET  /seller/dashboard     -> warehouse   : columnar aggregate (L29), not row reads
  GET  /orders/42/status     -> cache       : hot in-RAM read (L02), ~30k/s of these

  The WRITE MODEL serves NONE of these -- it is never touched by a read.
  A dashboard scan can't evict the status cache or slow a checkout: different stores.

Path A shows the discipline: the command commits to one place (the write model, plus its outbox row in the same transaction), and everything else is a consequence carried by the stream. Path B shows the payoff: each read is served by a store shaped exactly for it, and reads and writes can't starve each other because they don't share a database. But look again at step 3 versus step 5 — Alice is told "order placed" at step 3, and the read models only catch up at step 5. That gap is the wall.

Path C — read-your-writes, and the gap

  t=0 ms    Alice places order 42 -> write model commits -> ACK "Order placed!"
  t=1 ms    Alice's browser loads "My Orders" -> reads the DOC VIEW read model
  t=1 ms    ...but projection A hasn't applied event 42 yet (it lands at, say, t=120 ms)
  -> "My Orders" does NOT show order 42.  Alice thinks her order vanished.

  The write SUCCEEDED. The read model is just BEHIND by the projection delay.

Move 4 — Find the first bottleneck: the eventual-consistency gap

The command is acknowledged from the write model, but every read model trails it by the projection delay: relay/CDC poll + queue + apply. Estimate it — typically tens to a few hundred milliseconds, and seconds when the stream is backed up (Lesson 6's replication lag, Lesson 9's consumer lag). For most reads (a dashboard, a search) that lag is invisible and fine. For the one read that immediately follows its own write — read-your-writes — it looks like data loss. This is the tax CQRS charges, and you pay it per query, deliberately:

1. Read-your-writes from the write side (Lesson 15's trick). For the short window after a user's own write, serve that user's affected data from the write model (or from the command's own result) instead of the lagging read model. Costs a little read load on the write side, buys correctness exactly where it's noticed.

2. Return the result in the command's response. The command already holds the new order — hand it straight back so the client can render it optimistically, no read model consulted at all.

3. Wait-for-version (monotonic reads). The write returns a version/offset; the client passes it on the next read, and the read model serves only once it has applied up to that version. Costs a small wait, guarantees the user never sees older than what they wrote.

4. Just accept the lag where staleness is harmless — the seller dashboard being 200 ms behind changes nothing. Decide per query where the gap matters; don't pay to close it everywhere.

Name the trade-off — and when this whole pattern is a mistake. The eventual-consistency gap is the price of CQRS: you traded a single always-consistent model for many fast, purpose-built, lagging ones. That trade only pays when the read shapes genuinely diverge (you truly need search + aggregates + documents) or a read is starving the write DB. If your reads and writes share a shape and fit one database, CQRS is accidental complexity: you've added two models, a projection pipeline, and a consistency gap you now have to paper over — for no read benefit. Start with one model. Add a read replica when read volume is the problem. Reach for a separate read model only when the read shape is the problem. Don't skip to the end of the ladder.

  THE LADDER -- climb only as far as the read forces you.

   one model  ->  read replica  ->  materialized view / cache  ->  full CQRS
   (same DB)      (L6: same          (L2/L15: one derived           (many divergent
    reads &        shape, more        shape, one projection)         read models, N
    writes         copies -- fixes                                   projections +
    share)         VOLUME, not shape)                               the gap)

   cost paid:  none  ->  replication lag  ->  one invalidation/projection  ->  N gaps
   buy:        --    ->  read capacity    ->  one fast read shape          ->  any read shape

   Each rung pays MORE sync cost for MORE read freedom. Stop at the rung your
   reads actually need; every rung past that is complexity you maintain for free.

The four traps

  • Trap 1 — dual-writing instead of projecting. Having the app write to the order DB and the search index and the cache directly is Lesson 33's dual-write in disguise: no shared transaction, so a crash between the writes leaves them diverged with nothing to reconcile them. Always drive read models from the durable event stream (outbox/CDC), never with side-by-side writes from application code.
  • Trap 2 — a non-idempotent projection. The stream is at-least-once (Lesson 9), so every event can arrive twice. A projection that does count += 1 double-counts on a redelivery. Make every projection idempotent (Lesson 13): key it on the event id or the entity version so applying an event twice equals applying it once.
  • Trap 3 — treating a read model as the truth. A read model is a derived cache; if a command trusts a read model's value to enforce an invariant ("is this seat still free?"), a stale read model lets two commands both win (Lesson 6's lost update, Lesson 32's dirty read). Validate invariants against the write model only; a read model can be wrong and is fixed by replaying the log to rebuild it (Lesson 29's kappa).
  • Trap 4 — hiding the gap from the UX. Promising instant read-your-writes on every query is expensive and often needless. Decide, per read, whether staleness is acceptable — close the gap on the user's own just-changed data, and let the dashboard lag. Pretending the gap doesn't exist is how "my order vanished" bugs ship.

Where we landed

We took the copy-beside-the-data instinct that Lessons 2, 15, 16, 29, and 33 kept reaching for and made it an explicit design. The orders service runs 10:1 read-heavy, but the real driver isn't volume — it's shape: estimate showed one normalized table costs ~2.4 ms (six index seeks) per detail page = 48 cores at 20,000/s, while a denormalized read model does it in one 0.4 ms lookup = 8 cores, a 6× cut — yet the very denormalization that makes the read cheap is what would make a write dangerous, so no single table wins both. Model gave the three parts: a write model that owns the truth (normalized, ACID, correctness-first — Lessons 6/25), many read models each shaped for one query (document/search/columnar/cache — Lessons 15/16/29/2), and the projection that connects them by consuming Lesson 33's durable event stream idempotently (Lesson 13) — and the distinction from a plain read replica, which scales the same shape where CQRS changes the shape. Tracing a command showed it commit to exactly one place (write model + outbox in one transaction) with every read model updated as an async consequence; tracing the queries showed four reads each served by its own optimized store, unable to starve one another. The first bottleneck is the gap between them: a write is acknowledged before any read model reflects it (typically tens to hundreds of ms, seconds under lag), so read-your-writes looks like data loss until you special-case it — serve the user's own fresh data from the write side, return it in the command, wait-for-version, or simply accept the lag where it's harmless. And that same gap marks the line where CQRS becomes accidental complexity: if reads share the write's shape and fit one DB, you've bought two models, a pipeline, and a consistency gap for nothing. The real lesson: a command and a query are two different jobs on the same facts, so give them two different shapes — one write model kept correct, many read models kept fast, a durable stream between them — and pay for it, deliberately and per query, in the eventual-consistency gap. Next lesson takes the write side to its logical extreme:

• Event sourcing: today the write model stored current state and emitted events as a side effect. What if the stream of events IS the source of truth, and current state is just a fold over it (Lesson 25's ledger, generalized)? Then history is free, any read model is a replay away (Lessons 9/33/this lesson's rebuild), and audit is total — paid for in snapshotting to avoid re-folding millions of events, evolving old event schemas, and the "how do I query current state?" problem that CQRS answers. The trade shifts from read/write optimization to perfect auditability & replayability vs query complexity and storage.
