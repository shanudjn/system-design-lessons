Global Traffic Management: Steering Every User to the Nearest Healthy Region

Lesson 49 put one front door in front of one fleet, in one place. Lesson 23 ran the system live in more than one region — Virginia and Frankfurt at once — for latency and survival. This lesson connects the two and asks the question that sits above the load balancer: before a user's request can reach any fleet, their device has to be handed an IP address to connect to — so which region's address does a shopper in Sydney get, and what happens to that answer the instant that region catches fire? A single fixed address fails twice over: it drags everyone to one far-away region (the speed-of-light tax of Lesson 14, now measured in whole continents), and when that region dies it takes down users who could have been served perfectly from somewhere else. We'll take one concrete system — a service live in three regions (Virginia, Frankfurt, Singapore) with a shopper in Sydney — and estimate what steering to the near region buys (~300 ms off a cold page load) and what a fixed address costs when a region fails. We'll model the two families of answer — DNS-based steering (GeoDNS / latency routing) versus anycast (one IP announced from many places) — and the health-based failover that gates both. We'll trace the steady state, a region death, an anycast reroute, and the false failover that is really a split-brain in disguise. And we'll hit the wall the whole scheme is built on: DNS caching — a failover is only as fast as a TTL and a pile of caches you do not control. The trade underneath: proximity & availability vs routing staleness & complexity.

The one system we'll design

The service from Lesson 23 now runs in three regions, each a complete copy of Lesson 49's stack (gateway, fleet, data): us-east in Virginia, eu-central in Frankfurt, and ap-southeast in Singapore. Each region has its own public IP address (or a small set of them, behind Lesson 42's regional load balancer). Users are spread across the planet. Our test user is a shopper in Sydney. When her phone wants to load the app, it must first turn our name — shop.example.com — into an IP address it can open a connection to. That translation is DNS, the internet's phone book. The whole game of this lesson happens in that one step: which of the three region IPs does shop.example.com resolve to, for this user, right now — and how fast can that answer change when a region goes down? Get it right and Sydney talks to Singapore in ~95 ms and never notices Virginia burning. Get it wrong and she's either dragged across the Pacific on every request or stranded pointing at a dead region.

Global traffic management is the layer that decides which region each user's request is sent to — before it reaches any regional load balancer — steering by proximity and steering away from regions that are unhealthy. Lesson 42 balanced load within a region ("which server?"). This is the level above it ("which region?"). The two nest: global traffic management picks the region, then that region's Lesson 42 load balancer picks the server.

Words we'll earn before we lean on them

  • DNS (Domain Name System) — the system that turns a name (shop.example.com) into an IP address a device can connect to. The first step of every request to a named service.
  • Authoritative DNS server — the server that holds the real answer for a domain and decides what IP to return. This is where we put our steering logic.
  • Resolver (recursive resolver) — the DNS server your device or ISP asks; it queries the authoritative server on your behalf and caches the answer. Your device rarely talks to the authoritative server directly.
  • TTL (time to live) — how many seconds a DNS answer may be cached before it must be looked up again. The dial that bounds how fast a DNS change (like a failover) can take effect.
  • GeoDNS / latency-based routing — an authoritative DNS server that returns a different IP depending on where the query came from (or which region is lowest-latency for it). Steering at name-resolution time.
  • EDNS Client Subnet (ECS) — a DNS extension that passes a truncated form of the user's IP to the authoritative server, so it steers by the user's location, not the resolver's.
  • Anycast — announcing the same IP address from multiple regions at once, so the internet's routing delivers each packet to the topologically nearest one. Steering in the network, per packet, no DNS choice involved.
  • BGP (Border Gateway Protocol) — how networks announce "reach this IP range through me"; anycast works by announcing one range from many places and letting BGP pick the nearest.
  • Unicast — the normal case: one IP address lives in exactly one place. (Anycast is the exception.)
  • Health check — a probe that decides whether a region is fit to receive traffic; a failing region is pulled from the answer set (Lesson 34's readiness, at region scale).
  • Failover — moving traffic off a failed region onto a healthy one.
  • Drain — the act of pulling traffic away from a region; how fast you can drain is the number this lesson is about.
  • Split-brain — two regions both believing they are in charge (e.g. both primary) at once, usually because a network partition made each think the other is dead (Lessons 10/11).

Move 1 — Estimate: what steering buys, and what a fixed address costs

Two numbers make the case, and they are the same two words as Lesson 23: proximity (latency) and availability (survival). A single fixed IP loses both; steering wins both back.

1. Proximity — the ocean, priced in milliseconds. Distance is latency, and at continent scale the numbers are brutal (Lesson 14's speed-of-light tax). Light in fiber travels about 200,000 km/s (two-thirds of light in vacuum). Sydney to Singapore is ~6,300 km: one way 6,300 ÷ 200,000 = 31.5 ms, so a round trip is 2 × 31.5 ≈ 63 ms at the physical floor (~95 ms in the real, non-straight-line internet). Sydney to Virginia is ~16,000 km: one way 16,000 ÷ 200,000 = 80 ms, round trip 2 × 80 = 160 ms at the floor (~230 ms real). The difference is 160 − 63 ≈ 97 ms per round trip — and a cold HTTPS request is not one round trip: it's a DNS lookup, a TCP handshake, a TLS handshake, then the request itself — call it ~3 round trips before a byte of content comes back (Lesson 14). 3 × 97 ≈ ~290 ms shaved off a cold page load, for free, just by handing Sydney the Singapore address instead of the Virginia one. A fixed IP anchored in Virginia makes every Sydney request pay that ocean, on every round trip, forever.

2. Availability — the second region is only real if you can route to it. Lesson 23 paid for a second (and third) live region to cut downtime: one region at 99.9% is down ~8.76 h/yr, but users who can be steered to a healthy region don't experience that outage. That saving is entirely conditional on the steering layer. Pin one fixed IP to Virginia and when Virginia fails, 100% of users are down — including Sydney, who was being served from Singapore's healthy stack and had no reason to care about Virginia at all. Multi-region redundancy that the front door can't steer around is money spent on a spare you can't reach. The job of global traffic management is to make Lesson 23's spare regions actually usable: detect the dead region and stop sending anyone to it.

Name the trade-off — proximity & availability vs routing staleness & complexity. Steering buys latency and survival, but it buys them by making the answer to "what IP?" change per-user and over time — and a changing answer that is cached (which every DNS answer is) is an answer that can be stale. The entire difficulty of this lesson is that the mechanism that lets you route around a dead region is the same mechanism whose caching makes "route around it" take time you can't fully control. Powerful steering and instant, trustworthy change pull against each other.

Move 2 — Model: two ways to steer, and the health check that gates both

There are exactly two places you can decide which region a user reaches: when the name is resolved to an IP (DNS-based steering), or in the network, once the packet is already addressed (anycast). They have opposite strengths, and real systems often combine them. Both are useless without a health check deciding which regions are even eligible.

1. DNS-based steering — GeoDNS and latency routing

Here the authoritative DNS server is the brain. When a resolver asks "what is shop.example.com?", the server looks at where the question came from — the resolver's IP, or, better, the user's own subnet via EDNS Client Subnet — and returns the IP of the nearest or lowest-latency healthy region. Sydney's resolver gets Singapore's IP; a Berlin resolver gets Frankfurt's. Steering happens at name-resolution time, so it is rich: you can route by geography, by measured latency, by weight (send 5% to a new region as a canary, Lesson 31), and — the point of this lesson — you can remove a region's IP from the answer set the moment its health check fails. The catch is baked into DNS itself: every answer is cached for its TTL, at the resolver, the OS, and often the browser — so a change you make now reaches users only as their caches expire. DNS steering also natively sees the resolver's location, not the user's, so a user on a distant public resolver can be mis-placed unless ECS carries their real subnet.

2. Anycast — one IP, announced from everywhere

Here the network is the brain. The same IP address is announced via BGP from all three regions at once. To the internet, that address exists in three places, and each router forwards a packet toward the topologically nearest announcement. Sydney's packets land in Singapore not because DNS said so, but because that's the closest place the address is being announced from. Steering happens per packet, in the routing fabric, with no DNS decision at all. Two consequences fall out. Failover is fast and automatic: withdraw a dead region's BGP announcement and the internet reconverges in seconds, pulling traffic to the next-nearest announcement — no DNS cache to wait out. But control is coarse: you get "nearest by network topology," which is not the same as lowest latency or a weighted split, and a mid-session re-route can land a live TCP connection in a different region and break it. That's why anycast is the default for stateless, connectionless traffic (DNS itself, and increasingly QUIC/HTTP-3) and used carefully for long-lived TCP.

They compose well: a very common design is anycast the DNS servers themselves (so the lookup is fast and DDoS-resistant) while using GeoDNS logic in those servers to hand out region IPs — or anycast a thin edge (Lesson 14's CDN / Lesson 49's gateway) that then forwards to a health-checked region. You rarely pick one; you layer them.

3. The health check — the part that makes it "route to the nearest healthy"

Neither mechanism means anything without a health check deciding which regions are eligible. A checker probes each region's endpoint on an interval; after a region fails a threshold of consecutive checks it is declared unhealthy and pulled — its IP dropped from the GeoDNS answer set, or its BGP announcement withdrawn. This is exactly Lesson 34's readiness check and Lesson 42's health check, lifted to the region as the unit. And it inherits Lesson 34's two dials: probe too slowly and a dead region keeps taking traffic; probe too aggressively (or from a single vantage point) and a momentary blip false-fails a healthy region — the region-scale version of Lesson 10/34's flap. The tuning knob is the same shape: detection time ≈ interval × failure-threshold.

Move 3 — Trace the paths

Follow four scenarios: the steady state, a clean region death under GeoDNS, the same death under anycast, and the false failover that is really a split-brain.

Path A — steady state (Sydney, all regions healthy)

  Sydney phone wants shop.example.com

   1. asks its resolver -> resolver asks our AUTHORITATIVE DNS
   2. authoritative sees the query is near AU (ECS subnet) + all healthy
   3. returns ap-southeast (Singapore) IP, with TTL = 60 s
   4. phone opens TLS to Singapore -> ~95 ms RTT -> served (L23/L42/L49 stack)
   5. resolver caches "shop.example.com = SG" for 60 s (next lookups are free)

  vs a fixed IP in Virginia: every request pays ~230 ms RTT (L14 ocean tax),
  ~290 ms extra on the cold load. Steering earned that back.

Path B — region death under GeoDNS (the failover window)

  Singapore region goes DOWN.

   t=0    SG stops answering health probes.
   t~30s  health checker: 3 failed probes x 10 s -> declares SG UNHEALTHY,
          pulls SG's IP from the answer set. New lookups now get FR (next-nearest).
   BUT    Sydney phones whose resolver cached "SG" at t=-5s keep sending to the
          DEAD IP until that cache entry expires (TTL 60 s).
   worst  errors for already-cached users up to  detect + TTL = 30 + 60 = ~90 s,
          then they re-resolve -> Frankfurt (~250 ms, worse latency but ALIVE).

  Failover is NOT instant. It is bounded below by:
     health-check DETECTION  +  DNS TTL (+ caches you don't control).
  New users after t~30s are fine; the cost is the cached tail.

Path C — the same death under anycast

  Same IP announced from VA + FR + SG. Singapore dies.

   t=0    SG withdraws its BGP announcement (or the router yanks it on health fail).
   t~few  the internet RECONVERGES: Sydney's packets, addressed to the SAME IP,
    sec   now flow to the next-nearest announcement -> Frankfurt. No DNS involved,
          no TTL to wait out.
   cost   any in-flight TCP connections pinned to SG may RESET (land in FR mid-flow);
          the client reconnects. Fine for stateless/QUIC, a hiccup for long TCP.

  Faster than DNS failover (seconds vs tens of seconds), but coarser control
  and a risk to live connections. That's the trade between the two mechanisms.

Path D — the false failover (a split-brain in disguise)

  Singapore is UP and serving Sydney fine -- but the health checker (running in
  Virginia) is on the far side of a NETWORK PARTITION and can't reach SG.

  NAIVE:  checker sees SG "down" -> pulls it -> Sydney yanked to Frankfurt for
          NO reason (a false failover, +155 ms latency, and a needless reconnect).

  WORSE (stateful): if failover also PROMOTES a new primary in FR while SG is
          alive and still taking writes -> TWO regions act primary at once =
          SPLIT-BRAIN (L10/L11). Both accept writes -> divergence, lost updates.

  The root cause: a health check CANNOT tell "region is DEAD" from "region is
  UNREACHABLE FROM ME" -- that's CAP at the routing layer (L11). Fixes:
    - check from MULTIPLE vantage points, agree by quorum (L10) before draining.
    - keep ROUTING (AP: send users to whoever's up) SEPARATE from PROMOTION
      (CP: who may accept writes needs consensus + fencing, L10/L11/L23).
  A stale route costs a retry; a wrongly-promoted primary corrupts data.

Path A is the everyday win — near region, low latency, cache the answer and move on. Path B shows the honest cost of DNS failover: it is not instant, and the floor is set by detection time plus a TTL you partly don't control. Path C shows anycast trading that cached tail for network-speed reconvergence, at the price of coarser control and connection resets. And Path D is the one that turns a routing feature into a data-corruption bug: the health check is a guess made from one place, and a partition can make a live region look dead — so failover for stateless routing is safe to do eagerly (worst case: a needless reroute), but failover that promotes a writer must go through consensus, or you've built Lesson 11's split-brain at global scale.

Move 4 — Find the first bottleneck: DNS caching bounds how fast you can drain

Every path above ran into the same wall from a different side: you do not control the caches. When you change a DNS answer to drain a dead region, that change propagates only as fast as the TTL — and even the TTL is a request, not a command. Browsers pin a resolved IP for the life of a tab. Some OS and ISP resolvers round small TTLs up to a minimum of their own. A resolver that's offline when your change lands serves the stale answer until it comes back. DNS failover is therefore fundamentally a "tens of seconds," best-effort mechanism — never an instant, guaranteed one.

The TTL dial, priced both ways. Suppose 40,000 active clients and a TTL of 60 s. Steady-state DNS load is 40,000 ÷ 60 ≈ 667 lookups/s, and a region death costs cached users up to detect (30 s) + TTL (60 s) = ~90 s of errors. Want faster failover? Drop the TTL to 20 s: the failover tail shrinks to 30 + 20 = ~50 s, but DNS load rises to 40,000 ÷ 20 = 2,000 lookups/s — 3× the query volume (more cost, more load on the authoritative servers, less benefit from caching). Push TTL toward a few seconds and the failover window keeps shrinking while DNS QPS keeps climbing — and past a point the client caches that ignore you make further cuts buy nothing. TTL is the same freshness-vs-load dial as Lesson 2's cache TTL and Lesson 14's CDN TTL — the cached thing here is a routing decision, and its staleness is measured in whose traffic keeps hitting a dead region.

The two-layer escape. You don't beat the DNS floor by lowering TTL forever; you beat it by not relying on DNS for the fast part. Layer the mechanisms: put an anycast edge (or anycast DNS) in front so the network reroutes in seconds for the common region-down case, and use health-gated GeoDNS for the rich region selection and weighting. Inside each region, Lesson 42's load balancer and Lesson 34's health checks handle server-level failure so a single sick box never needs a region-level DNS change at all. The result: fast failover from anycast, rich control from DNS, and DNS changes reserved for the coarse, rare "drain a whole region" move where a tens-of-seconds tail is acceptable.

The four traps

  • Trap 1 — a fixed, un-steered address in front of multi-region. Paying for Lesson 23's second and third regions and then pinning one static IP means far users pay the ocean on every request and, when that region dies, everyone is down — including users a healthy region could serve. The redundancy is only real if the front door can steer to it.
  • Trap 2 — treating DNS failover as instant. A DNS change propagates only as caches expire — the TTL is a request, not a command, and browsers/resolvers routinely hold or round it. Size your failover expectation as detection + TTL + slack (tens of seconds), and if you need seconds, put anycast (or an anycast edge) in front rather than chasing an ever-lower TTL.
  • Trap 3 — health-checking a region from one place. A single-vantage-point checker can't tell "region dead" from "region unreachable from me," so a partition triggers a false failover — or, if failover promotes a writer, a split-brain (Lessons 10/11). Check from several locations and agree by quorum before draining; keep write-promotion behind consensus.
  • Trap 4 — letting routing decide correctness. Steering users to whoever's up is an AP decision (a stale route just costs a retry, Lesson 11). Deciding who may accept writes is a CP decision that needs consensus and fencing (Lessons 10/23). Conflate them and a routing hiccup becomes two primaries and lost data. Route eagerly; promote carefully.

Where we landed

Above every regional load balancer sits one more decision: before a request can reach any fleet, the user's device must be handed an IP to connect to — and that answer has to be near and alive for this user, right now. Estimate made the case in Lesson 23's two words: proximity (Sydney to Singapore ~63 ms floor vs to Virginia ~160 ms — 3 × 97 ≈ ~290 ms off a cold load) and availability (a fixed IP means a region death is a 100% outage, wasting the spare regions you paid for). Model laid out the two places you can steer — DNS-based (GeoDNS/latency: rich control, but bounded by a cached TTL) and anycast (one IP announced by BGP from many places: seconds-fast failover, but coarse and rough on live TCP) — gated by a health check that is Lesson 34's readiness at region scale. Tracing walked the steady state, a GeoDNS region death (failover bounded by detection + TTL ≈ ~90 s), the same death under anycast (network reconverges in seconds, at the cost of connection resets), and the false failover where a partition makes a live region look dead — a routing hiccup at worst, a split-brain at worst-worst. The first bottleneck is DNS caching: a drain is only as fast as a TTL and a pile of caches you don't control, so you buy speed with a lower TTL (paying DNS QPS) up to the point client caches ignore you — then you stop fighting DNS and layer anycast for the fast path while reserving DNS changes for the coarse, rare region drain. Global traffic management is worth it exactly when you run in more than one region and need each user routed to the nearest healthy one — and its hard edge is that the steering answer is cached, so "route around the dead region" is fast but never instant, and "who may write" must never be decided by a route. The standing tension: proximity & availability vs routing staleness & complexity.

We've now designed the system all the way up from a single URL to global routing. The last move is to prove the failure designs actually hold:

• Chaos engineering & fault injection: we've spent fifty lessons building defenses — timeouts and circuit breakers (Lesson 7), health checks and failover (Lessons 34/50), cells (Lesson 36), quorums (Lesson 10). But a defense you've never triggered is a hypothesis, not a fact. The next lesson deliberately breaks things — kills a node, adds latency, drops a region, partitions the network — to verify the failure designs behave as drawn, with blast-radius control and a steady-state hypothesis so the experiment itself is safe. The trade shifts to confidence in resilience vs the risk of the experiment.
