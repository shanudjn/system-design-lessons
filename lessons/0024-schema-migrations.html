Schema Changes at Scale: Renaming a Column on a Live 100-Million-Row Table Without Downtime

Every lesson so far changed the data — where it lives (Lesson 03/04), how it's copied (Lesson 06), how two continents agree on it (Lesson 23). Now we change its shape. Product wants the orders table's total column — a plain integer count of cents — split into amount_cents plus a currency, because the old column silently assumed every order was in US dollars. The table has 100 million rows, takes 50,000 reads/sec and 5,000 writes/sec, and must not go down for a second. The naive move — one ALTER TABLE ... RENAME — is a trap: it can lock the table, and the instant you rename, every running copy of the old code breaks because it still asks for total. The skill is that a schema change and a code change are two different deploys that can't be simultaneous across a fleet, so you must make the database understand both shapes at once and cross the gap in small, reversible steps. We'll estimate what a blocking migration costs, model the expand/contract dance (add → dual-write → backfill → cut readers over → contract), trace a read and a write at every stage, and hit the wall: the backfill that fights the live write traffic. The trade underneath shifts from Lesson 23's local-writes-vs-global-order to a new one: migration safety vs deploy velocity.

The one system we'll design

A payments service backed by one big SQL table, orders. It has 100 million rows and grows by a few million a week. Live traffic is 50,000 reads/sec (order-history pages, receipts) and 5,000 writes/sec (new orders, status updates). Dozens of application servers run the same code and talk to this table. We must change the column total (an integer, cents, always assumed USD) into two columns, amount_cents and currency, so an order can be €40 or ¥5000 instead of "40, and we hope it's dollars."

The naive plan is one command: ALTER TABLE orders CHANGE total amount_cents ... then ship code that reads the new name. That plan has two independent ways to cause an outage, and understanding both is the whole lesson: the ALTER itself can freeze the table, and even a free rename breaks every app server still running the old code. So instead of one big switch we take a sequence of small steps where, at every moment, both the old code and the new code work against the database as it currently is.

  THE TRAP WE'RE HERE TO AVOID   (schema deploy ≠ code deploy)

  You cannot flip the schema and all the code at the same instant.
  A fleet deploy is gradual: for minutes, OLD and NEW code run together.

     t0   50 app servers, ALL running OLD code  ->  read/write column "total"
     t1   you run: ALTER ... RENAME total -> amount_cents   (schema flips NOW)
     t2   every OLD server's query "SELECT total" -> ERROR: no such column
          ...outage... while the code deploy crawls across 50 servers
     t3   deploy finally finishes, NEW code reads "amount_cents"  -> healthy

  Between t1 and t3 the DB shape and the code disagree. That gap is the outage.

  FIX: never let them disagree. Make the DB understand BOTH shapes
       (old "total" AND new "amount_cents") for the whole transition,
       and remove the old shape only after ALL code stopped using it.

A schema change and the code that uses it are two separate deploys that are never simultaneous across a fleet. So you migrate in steps where old code and new code both work — never a step that only one of them survives.

Words we'll earn before we lean on them

  • Schema — the shape of the table: which columns exist, their types, their constraints. Changing it is a DDL statement (ALTER, CREATE); changing rows is DML (INSERT, UPDATE).
  • Migration — a versioned change to the schema (or to the data's shape), run as an ordered, repeatable step so every environment reaches the same state.
  • Online vs offline — an online migration runs while the table keeps serving reads and writes; an offline one needs the table (or the app) stopped. We want online.
  • Lock — while some ALTERs run, the database blocks other queries on that table (Lesson 22's lock, now held by the schema change itself). A long lock on a hot table = an outage.
  • Backfill — copying/computing values for the existing 100M rows to populate a newly added column. New rows get it going forward; old rows need a sweep.
  • Dual-write — for a transition period, the app writes both the old and the new column on every write, so the two are kept in sync no matter which the reader trusts.
  • Expand/contract (a.k.a. parallel change) — the pattern: first expand the schema so old and new shapes coexist, migrate readers and writers across, then contract by removing the old shape. Each step is small and reversible.
  • Backward-compatible change — a schema change that doesn't break code already running. Adding a nullable column is backward-compatible; renaming or dropping one is not.
  • Cutover — the moment readers switch from trusting the old column to the new one. In expand/contract it's a plain code deploy, not a schema change — so it's instant and reversible.

Move 1 — Estimate: what a blocking migration actually costs

Two numbers decide whether the naive one-shot plan is survivable: how long the operation holds the table, and how much work backs up behind it while it does. Both are large.

Worked: the lock that becomes an outage. Suppose the naive ALTER rewrites the whole table (many engines do, for a type change or some renames) and the table is 20 GB on disk. The server rewrites at, say, 100 MB/s once you account for indexes and WAL:

• rewrite time ≈ 20 GB ÷ 100 MB/s = 20,000 MB ÷ 100 MB/s = 200 s ≈ 3.3 minutes.

If that ALTER holds a write lock (or worse, a full lock) for those 200 s, every write queues behind it. At 5,000 writes/sec the backlog is:

• 5,000 writes/sec × 200 s = 1,000,000 queued writes — a million requests stuck, connection pools exhausted, and (Lesson 07) timeouts cascading into the app tier. A 3-minute lock on a table doing 5k writes/sec isn't a slow migration; it's a million-request outage. That's why "just run the ALTER" is off the table, and why every step below is designed to take a lock only for a fraction of a second, if at all.

Worked: the backfill is the expensive part, not the ALTER. Even with an online tool, filling in amount_cents for 100M existing rows is real work. If you update in batches and sustain 10,000 rows/sec (kept deliberately low so it doesn't starve live traffic — the Move-4 wall):

• backfill time ≈ 100,000,000 rows ÷ 10,000 rows/sec = 10,000 s ≈ 2.8 hours.

So the migration is not a moment — it's a 2.8-hour window during which old rows already have the value and old rows don't yet. Any reader that trusts the new column before the backfill finishes will see NULL for un-migrated rows. This is why readers cut over last, after the backfill is verified complete — the sequence isn't bureaucracy, it's the only order that never exposes a half-filled column.

Name the trade-off — migration safety vs deploy velocity. You could change the column in one command and one deploy in thirty seconds — and gamble on a lock and a code/schema gap. Or you spend hours-to-days moving through small reversible steps that never break a running server. Expand/contract chooses safety: more steps, more elapsed time, more discipline, in exchange for zero downtime and a working rollback at every stage. The rest of the lesson is that sequence.

Move 2 — Model: the expand/contract dance

The core idea is a parallel change: instead of transforming the old shape into the new one, you stand the new shape up beside the old, keep both in sync, move consumers across one at a time, then tear the old one down. Because both shapes exist through the whole middle, there is never a moment where a running server asks for something the database can't give. Five steps, each independently deployable and reversible:

  EXPAND / CONTRACT  —  5 steps, old code keeps working the whole time

  START   column: total (int, cents)      code: reads+writes total

  1 EXPAND SCHEMA (backward-compatible DDL, sub-second)
      ADD COLUMN amount_cents INT NULL,  ADD COLUMN currency CHAR(3) NULL
      -> old code ignores the new nullable columns. Nothing breaks.

  2 DUAL-WRITE (code deploy)
      new writes set BOTH:  total = X  AND  amount_cents = X, currency='USD'
      -> from now on, every NEW row is correct in both shapes.
         reads still trust "total".

  3 BACKFILL (background job, batched, ~2.8 h)
      for old rows where amount_cents IS NULL:
          amount_cents = total, currency = 'USD'   (in small batches)
      -> after this, ALL rows have both shapes. Verify counts match.

  4 CUTOVER READS (code deploy — the flip)
      readers now SELECT amount_cents, currency  (not total)
      -> still dual-writing, so "total" stays correct as a safety net.
         If wrong: redeploy readers back to "total". Instant rollback.

  5 CONTRACT (stop dual-write, then drop, each a separate deploy)
      stop writing "total"  ->  bake time  ->  DROP COLUMN total
      -> old shape gone. Migration complete.

Notice the shape of it: step 1 and step 5 are schema changes but each is backward-compatible on its own (adding a nullable column breaks nobody; dropping a column nobody reads anymore breaks nobody). Steps 2 and 4 are ordinary code deploys. Step 3 is a data job that touches no schema. At no single step do the schema and the deployed code disagree — that's the invariant the whole dance protects.

Name the trade-off — one column of storage vs a safe transition. For the whole middle of the migration you carry both columns and write both on every request — extra storage (100M × ~4 bytes ≈ 400 MB for the duplicate integer) and a little extra write cost (Lesson 12's write amplification, in miniature). You're paying redundant storage and writes to buy a migration where every step is reversible. Cheap insurance, and you reclaim it in step 5.

Move 3 — Trace the paths

Follow one read and one write through each stage. The point is to prove the invariant: at every stage, both old code and new code get a correct answer.

Stage A — after EXPAND, before DUAL-WRITE (columns added, still writing only total)

  row 42: { total: 4000, amount_cents: NULL, currency: NULL }

  WRITE (old code): UPDATE orders SET total=4500 WHERE id=42
     -> total=4500, amount_cents still NULL     (fine: no one reads it yet)
  READ  (old code): SELECT total ...            -> 4500   ✔

The new columns are dead weight so far — nullable, unread, unwritten. The only thing that happened is the schema got wider, which no running server noticed. This is the safe beachhead the rest of the dance stands on.

Stage B — during DUAL-WRITE + BACKFILL (both written; old rows filling in)

  NEW row 90,000,001 (written by new code):
     { total: 4000, amount_cents: 4000, currency: 'USD' }   both correct

  OLD row 42, not yet backfilled:
     { total: 4500, amount_cents: NULL, currency: NULL }

  READ (still trusts total): SELECT total -> 4500  ✔  (correct for BOTH rows)

  WRITE (new code, dual-write): UPDATE SET total=X, amount_cents=X, currency='USD'
     -> if it touches row 42, that row is now consistent too.

  Meanwhile backfill sweeps old rows in batches:
     UPDATE orders SET amount_cents=total, currency='USD'
       WHERE amount_cents IS NULL LIMIT 5000;   (repeat ~20,000 times)

This is the delicate stage and the reason for the exact ordering. Dual-write is turned on before the backfill starts. Why: if you backfilled first and enabled dual-write second, any row written in the gap between them could be updated with total only, leaving amount_cents stale — and the backfill, which only touches NULL rows, would skip it. Turning dual-write on first guarantees every new write is consistent, so the backfill just has to mop up the old rows once. Readers still trust total, which is correct for every row throughout, so the half-filled new column is never exposed.

Stage C — after CUTOVER (readers trust amount_cents; still dual-writing)

  Precondition to flip: backfill DONE and verified —
     SELECT COUNT(*) FROM orders WHERE amount_cents IS NULL;  -> must be 0

  READ (new code): SELECT amount_cents, currency -> 4500,'USD'  ✔
  WRITE (still dual): SET total=X, amount_cents=X, currency=...

  total is now a WARM STANDBY: still written, no longer read.
  If the new read path is wrong, redeploy readers back to "total" -> instant,
  no data lost, because total was never allowed to go stale.

The cutover is a code deploy, not a schema change — that's what makes it instant and reversible. You verified the backfill left zero NULLs before flipping, so the new column is complete. And because dual-write is still on, total remains a correct fallback: rolling back the reader is a one-line redeploy, not a data-recovery project. The order — verify-then-flip, and keep the old column warm — is what turns "rename a column" from a scary one-way door into a reversible step.

Stage D — CONTRACT (retire the old column, in two separate deploys)

  D1  deploy: STOP writing total (drop it from the write path)
       -> total is now frozen but still present. Bake for a day:
          if a hidden reader still needs it, you find out while it's
          still there to roll back to.
  D2  after bake, schema: ALTER TABLE orders DROP COLUMN total
       -> backward-compatible: no deployed code reads or writes it.
          Migration complete. Reclaim the ~400 MB.

Contract is expand run backwards, and it's split into two deploys on purpose. First stop writing the old column (code deploy) and let it bake — this is your last chance to discover a forgotten consumer while the column still holds good data. Only then drop it (schema change). Dropping a column that no live code touches is backward-compatible, so it breaks nobody, and it takes only a metadata lock in modern engines — sub-second, not the 200 s rewrite from Move 1.

Name the trade-off — reversibility vs elapsed time. Every arrow above is a separate, independently-deployable step with a working rollback. That's the safety. The cost is that a change one ALTER could attempt in 30 seconds now spans hours (backfill) and days (bake times), across five deploys. You trade calendar time and process for the guarantee that no single step can take the site down and every step can be undone.

Move 4 — Find the first bottleneck: the backfill vs the live table

The schema steps are sub-second and the code deploys are routine. The one part that runs for hours against the hot table is the backfill, and done carelessly it becomes its own outage — the exact thing the whole dance was avoiding.

Worked: the one big UPDATE that locks the table. The tempting backfill is a single statement:

UPDATE orders SET amount_cents = total, currency = 'USD' WHERE amount_cents IS NULL;

That touches 100 million rows in one transaction. Consequences, all bad: it holds locks on a huge row set for minutes (Lesson 22's lock, now blocking 5,000 writes/sec of live traffic); it inflates the undo/redo log to tens of GB and can run the disk out of space; and if it fails at row 90 million, the whole thing rolls back — 90 million rows of work undone, zero progress. This is the Move-1 lock outage wearing a different hat.

The fix — batch it. Walk the table in small chunks, each its own transaction, with a pause between:

UPDATE orders SET amount_cents=total, currency='USD' WHERE amount_cents IS NULL ORDER BY id LIMIT 5000; → commit → sleep 50 ms → repeat.

• batches = 100,000,000 ÷ 5,000 = 20,000 batches. Each locks only 5,000 rows for a few ms and commits, so live writes slip between batches; a failure loses only the last 5,000-row batch, not 90M; and the log stays small. At ~10,000 rows/sec effective (batch + pause) that's the 2.8 hours from Move 1 — slower on purpose, because the goal is to be invisible to live traffic, not fast.

Two more sharp edges the batched backfill still has to respect:

  • Throttle against replication lag (Lesson 06). Every batch you write must also travel to the read replicas that serve those 50,000 reads/sec. Push batches too fast and the replicas fall behind — read-your-writes breaks and stale reads spread. So the backfill watches replica lag and slows down when it climbs: the backfill's speed is governed by the slowest replica, not the primary's capacity.
  • Seek, don't offset (Lesson 18). Page the batches by WHERE id > :last_id ORDER BY id LIMIT 5000 (a cursor), not OFFSET n. Offset re-scans all the rows it already skipped, so batch 20,000 would read ~100M rows to find its 5,000 — the migration would slow to a crawl exactly as page 50,000 did in Lesson 18. The cursor seek stays O(batch) at any depth.

Name the core trade-off — migration safety vs deploy velocity. The fastest change is one ALTER and one deploy; it is also the one that locks a hot table and opens a code/schema gap. Everything in expand/contract — the extra column, dual-writing, the batched throttled backfill, the verify-before-flip, the bake before drop — spends velocity to buy safety: no lock long enough to notice, no moment where deployed code and schema disagree, and a working rollback at every step. On a table nobody depends on, skip the dance. On a 100M-row table taking 5,000 writes/sec, the dance is the design.

Where we landed

We changed the shape of a live 100M-row table — splitting an ambiguous total into amount_cents + currency — with zero downtime. Estimate showed why the naive path is an outage: a table-rewriting ALTER on 20 GB at 100 MB/s holds a lock for ~200 s, and at 5,000 writes/sec that queues ~1,000,000 writes; separately, backfilling 100M rows at a deliberately gentle 10,000 rows/sec is a ~2.8-hour window where old rows have the value and older ones don't. So the change can't be one command — a schema deploy and a code deploy are never simultaneous across a fleet, and the gap between them is the outage. Model gave the expand/contract dance: expand the schema with backward-compatible nullable columns, dual-write both shapes, backfill the old rows in the background, cut readers over with a plain code deploy, then contract by stopping the dual-write and dropping the old column — five small, independently-deployable, reversible steps where old and new code both always work. Tracing a read and a write through each stage proved the invariant and pinned down the two ordering rules that make it safe: dual-write turns on before the backfill (so no write slips through with a stale new column), and readers cut over only after the backfill is verified zero-NULL, keeping the old column warm as an instant-rollback fallback. The first bottleneck was the backfill fighting live traffic: one 100M-row UPDATE locks the table and rolls back all-or-nothing → batch it into 20,000 small committed chunks (5,000 rows each), throttle on replica lag (Lesson 06) so stale reads don't spread, and page by cursor not offset (Lesson 18) so batch 20,000 doesn't re-scan 100M rows. The real lesson: a schema change on a live table is not an event, it's a sequence — you make the database understand both the old and new shape at once, move every reader and writer across in small reversible steps, and remove the old shape only after nothing uses it. The trade is migration safety vs deploy velocity.

The trade shifts from migration safety vs deploy velocity to correctness/auditability vs throughput.
