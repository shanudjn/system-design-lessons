Idempotency: How to Retry a Payment Without Charging Twice

Lesson 07 told you to retry a timed-out call, and Lessons 05 and 09 told you a queue redelivers anything it isn't sure was handled. Both create the same danger: the same write happens twice. This lesson takes the most unforgiving version of that danger — a payments API charging a card $50 — and traces it end to end. We'll watch a single retry turn $50 into $100, then build the one mechanism that makes a repeated write a safe no-op: the idempotency key. We'll size the bug with real money, walk the dedup store that fixes it, trace the nasty concurrent-retry race, and find the bottleneck that catches everyone — the gap where the charge succeeds but the record of it doesn't.

The one system we'll trace

A payments service with one endpoint: POST /charge. The client sends "charge customer 5567 $50"; the server calls the card network, moves the money, and replies 200 OK. 10 million charges a day. The whole trouble starts with one fact from Lesson 07: a timeout is not an answer. When the client's request times out, the charge may have already happened — the reply just got lost on the way back. The client can't tell "never charged" from "charged, reply lost." So it retries. Here is the whole problem and its fix on one screen.

  ONE CHARGE, RETRIED — WHY $50 BECOMES $100, AND THE FIX

  WITHOUT a key                                WITH an idempotency key  (key = "ik_9f3a")
  ─────────────                                ────────────────────────────────────────
  client ─POST /charge $50─▶ [server]          client ─POST /charge $50  key=ik_9f3a─▶ [server]
      ✗ timeout (reply lost)    charges $50         ✗ timeout (reply lost)    charges $50, SAVES key→result
  client ─retry───────────▶ [server]           client ─retry  key=ik_9f3a─────────▶ [server]
                                charges $50 AGAIN                              sees key → REPLAYS saved result
                                                                              (does NOT charge again)
  ┌───────────────────────────────┐            ┌───────────────────────────────┐
  │  result: $100   ✗  DOUBLE      │            │  result: $50    ✓  EXACTLY ONCE │
  └───────────────────────────────┘            └───────────────────────────────┘

An operation is idempotent when doing it twice has the same effect as doing it once. "Set the light switch to ON" is idempotent — flip it twice, still on. "Charge $50" is not — do it twice, you're out $100. The whole lesson is about taking a non-idempotent operation and wrapping it so the second attempt safely does nothing.

Words we'll earn before we lean on them

  • Idempotent — an operation where N ≥ 1 identical applications give the same result as exactly one. Retrying it is free.
  • Idempotency key — a unique id the client picks for one logical operation and sends with every attempt (including retries), so the server can recognize "this is the same request again."
  • Dedup store — the server's table mapping key → (status, saved response). The memory that lets a retry be recognized.
  • At-least-once delivery — the network/queue guarantee from Lessons 05/09: a message arrives one or more times, never zero. Duplicates are normal, not a bug.
  • Exactly-once effect — the goal: no matter how many times a request is delivered, the money moves once. Built from at-least-once delivery + idempotent processing.
  • In-flight window — the span while the first attempt is still running. A retry that arrives inside it races the original (Lesson 06's concurrency, now over the network).
  • Atomic commit — two changes that both happen or neither does. We'll need the charge and its key-record to commit together.
  • TTL — time-to-live: how long the dedup store remembers a key before forgetting it.

Move 1 — Estimate: what the bug costs, and how often it fires

Before building the fix, price the problem. Two numbers matter: how often a duplicate actually arrives, and what each duplicate costs.

Worked: the daily cost of doing nothing.

• Volume: 10,000,000 charges/day — about 10,000,000 ÷ 86,400 ≈ 116 charges/second.
• Retry rate: timeouts, dropped replies, user double-clicks, and queue redeliveries mean a small slice of requests arrive twice. Say a conservative 2%.
• Duplicate attempts: 10,000,000 × 2% = 200,000 duplicate charges/day.
• Average charge: $50.

200,000 × $50 = $10,000,000 of erroneous double-charges every day. That is the bug, in dollars. It isn't a rare edge case you can patch later — at this scale it fires 200,000 times a day, and every one is a refund, a chargeback, and a furious customer. Idempotency isn't a nicety here; it's the difference between a working payments system and a non-working one.

Worked: how many retries collide with a still-running original. A retry is only dangerous in a new way if it arrives while the first attempt is still in flight (a finished-and-recorded charge is easy to recognize; an in-progress one is the hard case). Use Little's Law — the average number in flight is arrival rate × time each takes: L = λ × W. With λ = 116/s and a p99 charge latency of W ≈ 0.8 s (Lesson 07's "set the timeout from p99"), L = 116 × 0.8 ≈ 93 charges in flight at any instant. So at any moment ~93 operations are mid-charge, and a retry of any of them lands in a live race. That ~0.8 s in-flight window is exactly the case Move 3 has to get right.

Name the trade-off up front: you cannot fix this by making delivery perfect. Exactly-once delivery over a network is impossible — the sender can never be sure its message (or its acknowledgement) arrived, so it must either risk losing it or risk sending it again. Every real system therefore chooses at-least-once delivery (duplicates) and then kills the duplicates at the receiver. Idempotency is how you buy an exactly-once effect on top of an at-least-once wire — you trade "no duplicates ever arrive" (unachievable) for "duplicates arrive but cost nothing" (achievable).

Move 2 — Model: the idempotency key and the dedup store

The fix has two halves. First, the client names the operation. Second, the server remembers the name.

Half 1 — the client picks a key

Before its first attempt, the client generates a unique idempotency key — a random UUID like ik_9f3a... — for this one logical charge. It sends that key with the request (an Idempotency-Key header) and reuses the same key on every retry. The key says: "all of these requests are the same operation; perform it at most once." The key must come from the client, because only the client knows that its retry is a retry — to the server, two requests with two different keys are simply two different charges.

Half 2 — the server remembers

The server keeps a dedup store: a table keyed by the idempotency key. Each row records the request's status and, once finished, the saved response.

idempotency_keystatussaved_responsecreated_at
ik_9f3aCOMPLETED{charge_id: 88, amount: 50}10:00:01
ik_7b21IN PROGRESS(none yet)10:00:02

The rule the server follows on every request: look up the key first.

  ON EVERY REQUEST, BEFORE TOUCHING THE CARD NETWORK:

  key seen before?
    ├─ no  ──▶ claim it (INSERT key, status=IN PROGRESS) ─▶ do the charge ─▶ save response, status=COMPLETED ─▶ reply
    ├─ COMPLETED ──▶ skip the charge, REPLAY the saved response ───────────────────────────────────────────▶ reply
    └─ IN PROGRESS ─▶ a retry caught the original mid-flight ─▶ wait, or reply 409 "in progress, retry shortly"

Worked: sizing the dedup store. One row ≈ the key (16 B) + status + a saved response blob (~1 KB for a charge result). At 10M charges/day that's 10M × ~1 KB ≈ 10 GB/day of new rows. You don't keep them forever — you set a TTL. With a 24-hour TTL the store holds ~one day of keys ≈ 10 GB steady; a 7-day TTL holds ~70 GB. Tiny next to the actual ledger, and easily a fast key-value store (Lesson 02's cache shape, but here it must be durable — losing it re-opens the double-charge). The TTL length is a real decision we'll pay for in Move 4.

Name the trade-off: the dedup store buys safety with a write and a lookup on the hot path of every request, plus a durable store you must run and pay for. Idempotency is correctness bought with one extra round-trip to a store you must never lose. That's why you apply it to operations that must not repeat (charges, transfers, "send the email") and skip it for operations that are already safe to repeat (a plain read, or a write that's naturally idempotent — Move 4).

Move 3 — Trace the paths

Path A — first attempt (the happy path)

Key ik_9f3a has never been seen. The server claims it (insert row, IN PROGRESS), calls the card network, the $50 moves, the server writes the result and flips the row to COMPLETED, and replies 200 OK. One charge. Exactly what we want.

Path B — retry after success (the easy duplicate)

The reply to Path A got lost, so the client retries with the same ik_9f3a. The server looks it up, finds COMPLETED, and — without touching the card network — replays the saved response: same 200 OK, same charge_id: 88. The client can't tell it from the original, which is the point. Money moved once; the client got its answer. Notice the bonus: replaying the saved response means the retry even returns the same charge id, so anything the client built on that id still lines up.

Path C — retry during the first attempt (the race)

This is the one that catches people. The first attempt is still mid-charge (we computed ~93 of these in flight at once) when the retry arrives. Now two requests with the same key are running at the same time. A naïve "check if seen, else charge" has a gap between the check and the write — both check "not seen," both charge. That's Lesson 06's lost-update race, except instead of losing an update we duplicate one.

  THE CHECK-THEN-ACT GAP (same idempotency key, two concurrent requests):

  req 1:  check key → "not seen"  ┐
  req 2:  check key → "not seen"  ┘  ← both passed the check in the gap
  req 1:  charge $50
  req 2:  charge $50              ← DOUBLE CHARGE, even though we "checked"

  THE FIX — make CLAIMING the key atomic (one winner):
  req 1:  INSERT key  ✓ wins the unique constraint → proceeds to charge
  req 2:  INSERT key  ✗ violates unique constraint → it's a duplicate → wait / return 409

Worked: why a unique constraint, not a check. Make the idempotency key a unique primary key in the dedup store and have each request try to insert it as the very first step. The database guarantees exactly one insert of a given key succeeds — the second gets a duplicate-key error. So the winner charges; the loser, seeing the key already exists, knows a twin is handling it and either waits for the result or returns 409 In Progress so the client retries in a moment. The atomic claim is what closes the check-then-act gap — the same move as Lesson 06's atomic increment and Lesson 10's "only one leader," here applied to "only one charge per key."

Path D — the crash in the middle (atomicity)

The hardest path: the server charges the $50, then crashes before it writes COMPLETED. The money moved, but the dedup store still says IN PROGRESS (or nothing). The retry can't see that the charge happened, so it charges again. The whole mechanism just failed at the one moment it existed for. The cause is that "move the money" and "record that we moved it" were two separate steps, and we died between them.

There are two honest fixes, and which you can use is itself the trade-off:

  • If the effect lives in your own database (e.g. "debit this account row"), put the effect and the key-record update in one atomic transaction. They commit together or not at all — there is no "between." A crash leaves both undone; the retry redoes both cleanly.
  • If the effect lives in another system (the card network — you can't share a transaction with it), you can't make it atomic with your store. So you push idempotency down: send your idempotency key to the card network too, and let it dedupe. Now even if you retry the downstream call, the card network charges once. Idempotency composes — each hop must be individually idempotent for the whole chain to be exactly-once.

Name the trade-off: exactly-once effect demands that the action and the memory-of-the-action commit together. When you control both, use one transaction; when you don't, every downstream hop must carry the key and dedupe on its own. The failure mode to fear isn't the duplicate you catch — it's the gap between doing and recording, where a crash turns "remembered" into "forgotten."

Move 4 — Find the next bottleneck

The key + store + atomic claim make a single charge exactly-once. Now the walls.

The TTL trap (forgetting too soon vs storing forever)

Worked: how short is too short. The dedup store forgets a key after its TTL. If a retry arrives after the key is forgotten, it looks brand-new — and you double-charge. So the TTL must be at least as long as the longest possible retry horizon. How long is that? A timed-out client retries in seconds. But a stuck queue message (Lesson 05's visibility timeout) can redeliver hours later, and a human re-submitting a saved form can come back days later. Set the TTL to 24 hours and a 30-hour-late redelivery double-charges; set it to 30 days and the store is 30× bigger (~300 GB here). Trade-off: a short TTL risks correctness (a late retry slips through); a long TTL costs storage. Size it to the slowest realistic retry, not the fastest.

Natural idempotency (the key you don't need)

An idempotency key is the general tool, and it isn't free — a store, a lookup, a TTL to tune. Sometimes you can dodge it by designing the operation to be idempotent by nature, so repeating it is harmless with no bookkeeping at all.

OperationIdempotent by nature?Why
GET /balanceYesa read changes nothing — repeat freely
PUT status = "shipped"Yessets an absolute value; twice = once
DELETE order 88Yessecond delete finds it already gone
balance += 50 (a delta)Noeach apply adds again — Lesson 06's non-idempotent increment
POST /charge $50Nocreates a new effect each time → needs a key

The pattern: absolute "set to X" is idempotent; relative "change by X" is not. Where you can express the operation as a PUT of a final state or a conditional write ("set to shipped only if currently packed" — Lesson 06's compare-and-set), you get idempotency for free and skip the dedup store entirely. Where the operation genuinely creates something new each time — a charge, a "send money," an "append a row" — there is no natural version, and the idempotency key is the only tool.

Name the trade-off: natural idempotency is free but only available for some operations (absolute writes, deletes, conditional updates); the idempotency key is universal but costs a durable store, a hot-path lookup, and a TTL you must tune. Reach for natural idempotency first; fall back to the key when the operation has no idempotent shape.

Where we landed

We took one POST /charge $50 and made a retry safe. Estimate priced the bug: at 10M charges/day and a 2% duplicate rate, doing nothing is 200,000 double-charges = $10M/day, and Little's Law put ~93 charges in flight at once, so retries routinely race a live original. Model built the fix: a client-chosen idempotency key sent on every attempt, plus a durable dedup store (key → status, saved response, ~10 GB/day at a 24 h TTL) that the server checks before touching the card network. Tracing the paths walked the happy first attempt, the easy retry-after-success (replay the saved response, no second charge), the dangerous concurrent retry (closed with an atomic claim — a unique-key insert, so exactly one winner, Lesson 06's race solved again), and the crash-in-the-middle (fixed by committing effect + record in one transaction, or pushing the key downstream when you can't). The next bottleneck was the TTL trap (forget too soon → a late redelivery double-charges; remember too long → storage bloats) and the escape hatch of natural idempotency (absolute PUT/delete/conditional writes need no key at all). The thread of the whole lesson: you can't stop duplicates from arriving, so make the second one a no-op — exactly-once effect on top of at-least-once delivery.
