Serialization Formats & the Wire: The Same Message in JSON and Protobuf, Byte for Byte

For seventy-nine lessons we've shipped bytes everywhere — a scatter-gather merges 16 partial results (L79), the outbox fans one order event out to search, cache, the warehouse, and notifications (L33), a request touches 20 services on its way to a page (L17). Every one of those arrows carries a message, and a message is a structure in memory (an object with fields) that has to become a flat sequence of bytes to travel down a socket, then become a structure again on the other side. That turning-into-bytes is serialization; the reverse is deserialization. We've never once asked what those bytes look like — we just said "send the message." This lesson asks the question nobody estimates: what format are the bytes in, and what does the wrong choice cost? We'll take one concrete order event and write it out byte for byte in JSON (text, self-describing) and in Protobuf (binary, schema-driven), measure the size and CPU gap, and — the part that actually bites — trace what happens when you need to add or remove a field six months later without breaking the services that haven't redeployed yet (Lesson 18's contract, Lesson 24's expand/contract). We'll estimate the bytes and cycles at 40k req/s, model the four formats and how each survives change, trace an add, a remove, and a rename across a fleet mid-rollout, and find the first bottleneck: the schema is a distributed contract, and the compactness is paid for in the discipline of never breaking it. The trade under all of it: human-readability & flexibility vs size, speed & schema discipline.

The one system we'll build

Keep the e-commerce orders platform. When an order is placed, the service (L33's outbox) emits one OrderPlaced event that gets shipped to every downstream — search (L16), cache (L02), the warehouse (L29), and the notification path (L26) — and internal RPCs pass the same shape between services (L34). Here is the one message we'll trace, as an object in memory:

  OrderPlaced {
     order_id     = 1234567890123   (a 64-bit integer)
     customer_id  = 8675309         (a 64-bit integer)
     amount_cents = 4999            (a 32-bit integer)
     currency     = "USD"           (a 3-char string)
     status       = PLACED          (one of a few known values)
     created_at   = 1725500000      (a unix timestamp, 64-bit)
  }

Our job: turn that object into bytes for the wire, and back. Two honest options sit at opposite ends. JSON writes it as human-readable text with the field names spelled out. Protobuf writes it as compact binary against a schema both sides agreed on ahead of time. We'll write out both, byte for byte, count them, count the CPU to parse them, and then — because a real system runs for years — change the message and watch which format survives the change. The adversary here isn't skew or an attacker; it's time: the message shape you ship today is not the shape you'll ship next year, and half your fleet will be running the old code when you change it.

  JSON (text, self-describing):        Protobuf (binary, schema-driven):
  {"order_id":1234567890123,           08 CB 89 EC 8F F7 23   <- field 1 (order_id)
   "customer_id":8675309,              10 ED BF 91 04         <- field 2 (customer_id)

  message ("amount_cents" = 12 bytes)  live in the schema, sent ZERO times

The one idea the whole lesson turns on: a serialization format is a bet about where the schema lives. JSON carries the schema inside every message — the field names are right there in the bytes, repeated on all 40,000 messages per second — so it needs no prior agreement and anyone can read it, but it's fat and slow and nothing checks that the fields mean what you think. Protobuf/Avro move the schema out of the message into a definition both sides hold ahead of time, so the wire carries only tiny field numbers and raw values — far smaller and faster — but now producer and consumer share a contract that must be evolved carefully and never broken. Everything below is that one trade made concrete: the bytes you save, the CPU you save, and the coordination you take on in return.

Words we'll earn before we lean on them

  • Serialization (marshalling) — turning an in-memory structure (an object with fields) into a flat sequence of bytes that can travel over a network or be written to disk. Deserialization is the reverse.
  • Wire format — the exact byte layout a serialized message takes on the network ("the wire"). What this lesson is about.
  • Schema — the declared shape of a message: its fields, their names, their types. It exists whether or not you write it down; the question is where it lives.
  • Self-describing format — one where the bytes carry their own field names/structure, so a reader needs no prior schema (JSON, XML). Flexible, verbose.
  • Schema-driven (binary) format — one where the bytes carry only values + tiny field tags, and the field names/types live in a separate schema both sides hold (Protobuf, Avro, Thrift). Compact, fast, needs the schema.
  • Varint — Protobuf's variable-length integer encoding: small numbers take 1 byte, big ones take more (7 value-bits per byte + 1 continuation bit). Why a binary int isn't always 8 bytes.
  • Field tag / field number — in Protobuf, the small integer that identifies a field on the wire (not its name). The number, not the name, is the contract.
  • Wire type — 3 bits in each Protobuf tag saying how to read the value that follows (varint, 64-bit, length-delimited, 32-bit). Lets a reader skip a field it doesn't recognize.
  • Schema evolution — changing a message's shape over time (add/remove/rename fields) without breaking readers running the old or new version. The heart of the lesson.
  • Backward compatible — a new reader can read old data. Forward compatible — an old reader can read new data (it tolerates fields it doesn't know). You usually need both during a rollout (L31).
  • Schema registry — a central service holding versioned schemas (Avro's model), so a message can carry a tiny schema id instead of the whole schema.
  • Columnar / zero-copy format — a layout (Parquet on disk, Arrow in memory) that stores values column-by-column and can be read without parsing rows, for analytics (L29). The opposite optimization from a row message.

Move 1 — Estimate: the bytes and the cycles

Two costs ride on the format choice — how many bytes cross the wire and how much CPU it takes to produce and parse them. Let's compute both for our one message, exactly.

JSON, byte for byte (compact, no whitespace). Text encoding: every character is a byte, and every field name is spelled out in full.

PieceBytes
"order_id":123456789012310 (name+quotes) + 1 (:) + 13 (digits) = 24
"customer_id":867530913 + 1 + 7 = 21
"amount_cents":499914 + 1 + 4 = 19
"currency":"USD"10 + 1 + 5 = 16
"status":"PLACED"8 + 1 + 8 = 17
"created_at":172550000012 + 1 + 10 = 23
5 commas + 2 braces7
Total127 bytes

Where the bytes go: of 127 bytes, the field names alone are 8+11+12+8+6+10 = 55 bytes — 43% of the message is the same field names repeated on every single message. The numbers are stored as their decimal text (1234567890123 = 13 bytes) rather than as raw integers.

Protobuf, byte for byte. Each field = a 1-byte tag (field number + wire type) then the value. Integers use varints: 7 value-bits per byte, so bytes = ceil(bit-length / 7). No field names anywhere — the schema holds those.

Field (number, type)TagValueBytes
order_id (1, varint)11,234,567,890,123 → 41 bits → ceil(41/7)=67
customer_id (2, varint)18,675,309 → 24 bits → 45
amount_cents (3, varint)14,999 → 13 bits → 23
currency (4, length-delimited)11 (length=3) + 3 ("USD")5
status (5, enum→varint)1PLACED = 1 → 12
created_at (6, varint)11,725,500,000 → 31 bits → 56
Total28 bytes

Worked byte dump for amount_cents = 4999: tag = (3<<3)|0 = 0x18; varint of 4999 = 4999 = 39×128 + 7 → low byte 0x87 (7, continuation set) then 0x27 (39) → wire bytes 18 87 27. Three bytes, and the string "amount_cents" appears nowhere — versus JSON's 19 bytes for the same field, 14 of them the name.

The size verdict: 127 bytes ÷ 28 bytes ≈ 4.5× smaller. The win comes from two places, both structural, not clever compression: (1) field names replaced by 1-byte numbers (the schema holds the names, sent zero times), and (2) numbers stored as raw varints instead of decimal text. At 40,000 messages/second: JSON = 127 × 40,000 ≈ 5.1 MB/s ≈ 440 GB/day; Protobuf = 28 × 40,000 ≈ 1.1 MB/s ≈ 97 GB/day — ~343 GB/day less on this one event stream, before you multiply by the fan-out (L33 ships each event to ~4 consumers; L17 crosses ~20 hops).

The CPU cost — the one people forget. Bytes are cheap; the cycles to make and read them are not. Parsing JSON means scanning every byte, matching field-name strings, allocating objects, and converting "1234567890123" (text) into a 64-bit integer — all branchy, allocation-heavy work. Protobuf reads a tag, knows the type, and copies the value; no text scanning, far fewer allocations. In microbenchmarks a small message like this round-trips (serialize + parse) on the order of ~3 µs in JSON vs ~0.4 µs in Protobuf — roughly 7× less CPU (order-of-magnitude; exact numbers depend on library and language, but the ratio is robust). Put it on the request path of L17's 20 hops, where the message is serialized and parsed at each hop:

  • JSON: 20 hops × 3 µs = 60 µs of pure marshalling CPU per request. At 40k req/s: 40,000 × 60 µs = 2.4 s of CPU per second ≈ 2.4 cores doing nothing but turning objects into text and back.
  • Protobuf: 20 × 0.4 µs = 8 µs per request → 40,000 × 8 µs = 0.32 cores.
  • Difference: ~2 cores reclaimed on this path alone (L59's cost lens), and — because marshalling sits on the hot path — lower tail latency (L17): fewer allocations means fewer GC pauses spiking p99.

The trade named: JSON spends bytes and cycles to buy the ability for any human or tool to read the message with no schema; Protobuf spends a shared schema to buy back the bytes and cycles. Neither is "faster" in the abstract — the question is whether you're paying for readability you actually use.

Move 2 — Model: four formats, and how each survives a change

The four formats, side by side

Every format answers two questions: where does the schema live? and how does a message change over time without breaking readers?

FormatSchema lives…BuysCosts
JSON (text)in every message (field names on the wire)human-readable, no prior agreement, any tool can parse it, flexiblelargest & slowest; no type checking; the contract is implicit & unenforced
Protobuf (binary)a shared .proto file compiled into both sidescompact, fast, typed; field numbers make add/skip safeopaque bytes (need the schema to read); must never reuse/retype a field number

The trade named, in one line: JSON puts the schema in the message (readable, fat); Protobuf/Thrift put it in a shared file (compact, needs both sides to compile it); Avro puts it in a registry (smallest records, needs the registry). Text formats optimize for the human and the unknown reader; binary formats optimize for the machine and the known reader.

How a binary format skips what it doesn't know — the forward-compat trick

The reason you can add a field without breaking old readers lives in Protobuf's wire type. Every field on the wire is tag (field-number + 3-bit wire type) → value. The wire type tells a reader how to measure the value's length even if it has never heard of that field:

Wire typeMeaningHow the reader skips it
0 varintint32/64, bool, enumread bytes until one has the continuation bit clear
1 64-bitdouble, fixed64skip exactly 8 bytes
2 length-delimitedstring, bytes, sub-messageread the length varint, skip that many bytes
5 32-bitfloat, fixed32skip exactly 4 bytes

So an old reader that hits unknown field 7 reads the tag, sees "wire type 2, length 40," skips 40 bytes, and carries on — unknown fields don't break parsing. That is forward compatibility built into the byte layout. JSON gets the same property a cruder way: an unknown key is just skipped by the parser. Both tolerate new fields; the difference is Protobuf does it in 1 tag byte while JSON does it by carrying the full name.

Why "schemaless" is a myth, and a dangerous one: people reach for JSON because it has "no schema" and feels flexible. But the schema didn't disappear — it moved into every reader's code. When service B does order.amount_cents, it is asserting a schema; it's just un-written, un-versioned, and un-checked. Rename the field in the producer and nothing complains at build time — B simply reads undefined at 3 a.m. in production. Protobuf's schema is the same contract made explicit, versioned, and checked by the compiler (L18's published contract, enforced instead of hoped for). The choice isn't "schema vs no schema"; it's "schema you can see and evolve deliberately vs schema scattered implicitly across a dozen codebases."

Move 3 — Trace the paths: adding, removing, and renaming a field

A message that never changes is easy in any format. Real messages change for years while a fleet of services runs mixed old and new code mid-rollout (L31). Trace the three changes that matter.

Path A — adding a field (the safe, common case)

   Six months in, we add "coupon_code" to OrderPlaced.
   PROTOBUF: give it a NEW field number (7). Old readers hit tag 7,
     read the wire type, SKIP its bytes, ignore it. New readers get
     the value, or a default if an old producer didn't send it.
     -> backward AND forward compatible. Safe. This is the ONLY
        routine evolution move: add optional fields with new numbers.
   JSON: producers start emitting "coupon_code":"SAVE10". Old readers
     ignore the unknown key; new readers use it. Also safe.
   VERDICT: both survive an ADD. Additive change = safe (L18/24).

Path B — removing / renaming a field (where it goes wrong)

   We decide "status" (string "PLACED") should become an enum, and we
     want to drop the old text field.
   PROTOBUF done RIGHT: stop writing the old field, but RESERVE its
     number and name so no future field ever reuses them:
        reserved 5; reserved "status";
     Old readers still expecting field 5 get its default (empty) --
     they don't crash, and no new field can silently inherit tag 5.
   PROTOBUF done WRONG: reuse number 5 for the new enum. Now an OLD
     message's bytes at tag 5 (a length-delimited STRING) are read by
     a NEW reader as a VARINT enum -> garbage, or a parse error. The
     field NUMBER is the contract; changing what it means corrupts
     every in-flight old message. NEVER reuse a field number.
   RENAME in .proto (status -> order_status) but KEEP number 5: FREE.
     The name isn't on the wire; only the number is. Nothing breaks.
   JSON: rename "status" -> "order_status". The name IS the wire key,
     so every old reader doing order["status"] now reads undefined,
     silently, in production. A rename is a BREAKING change in JSON.

Path C — the change rolls out across a live fleet (why both directions matter)

   A deploy is gradual (L31): for ~10 min, HALF the fleet runs new
     code, half runs old, all reading each other's messages.
   So a change must be compatible in BOTH directions at once:
     - new reader must read OLD messages   (backward compatible)
     - old reader must read NEW messages   (forward compatible)
   ADD a field  -> both hold (old skips it, new defaults it). Ship it.
   REMOVE/RENAME/RETYPE -> forward-compat BREAKS. So you can't just
     "change it." You do L24's expand/contract on the WIRE:
       1. EXPAND: add the new field alongside the old (both on the wire)
       2. dual-populate: producers write BOTH old and new
       3. migrate readers to the new field, deploy, bake
       4. CONTRACT: once no reader reads the old field, reserve+drop it
   The schema change is a MIGRATION (L24), not an edit -- because the
     readers you don't control are mid-rollout when you flip.

Path A is the reward and the rule: adding an optional field with a fresh number is safe in every format — that's why systems accrete fields and rarely remove them. Path B is the knife: a rename is free in Protobuf (names aren't on the wire) but breaking in JSON (names are the wire), while reusing or retyping a field number is the cardinal Protobuf sin — it silently reinterprets old bytes. Path C is why this is a lesson and not a footnote: because a fleet deploys gradually (L31), a message-shape change is only safe if it's compatible in both directions during the overlap, so a remove/rename/retype must be run as Lesson 24's expand → dual-write → migrate → contract — on the wire this time. Move 4 names the wall all three circle: the schema is a contract shared across services you deploy independently, and the format's compactness is exactly the discipline of never breaking that contract.

Move 4 — Find the first bottleneck: the schema is a distributed contract

The first bottleneck — schema coordination across independently-deployed services. The bytes and the cycles from Move 1 are real, but they are not the thing that wakes you at night. The real cost of a binary format is that producer and consumer now share a contract they must evolve without ever meeting. Get it wrong and the failure is silent and data-shaped, not loud and crash-shaped: reuse field number 5 and a new reader reads an old string's bytes as an integer, producing a plausible-looking wrong number that flows into the ledger (L25) or the warehouse (L29) undetected. The discipline that prevents it is small and absolute:

  • Only ever add optional fields with new numbers. This is the one always-safe move (Path A).
  • Never reuse a field number, never change a field's type or number. reserved the number and name of anything you remove so it can't come back (Path B).
  • Run any breaking change as a migration (expand → dual-populate → migrate readers → contract, L24), because the fleet is always mid-rollout (Path C, L31).

JSON doesn't escape this — it just hides it. There's no schema file to coordinate, so the contract feels free; but it still exists in every reader's code, un-versioned, and it breaks at runtime (a 3 a.m. undefined) instead of at compile time or in the registry. Avro makes the coordination explicit and central: a schema registry holds every version and can reject an incompatible schema at publish time — turning the silent runtime break into a loud deploy-time error. The trade named: a binary schema gives you compactness and speed and enforceable evolution, paid for with a shared artifact you must version and a registry/build step you must run; JSON gives you freedom from all that machinery, paid for with a contract nobody can see until it breaks.

The second wall — row messages are the wrong shape for analytics. Everything above serializes one row (one order) at a time — perfect for an RPC or an event, because you want the whole record. But send a billion of these to the warehouse (L29) and ask "sum of amount_cents by day," and a row format forces you to parse every field of every record just to read one column. That's L29's row-store problem reborn on the wire. The fix is a different kind of format: columnar (Parquet on disk, Arrow in memory) stores all the amount_cents values together, so the reader touches only the column asked for (projection, L29) and the values compress hard (a column is a billion similar numbers). Arrow goes further — it's zero-copy: the in-memory layout is the wire layout, so there's no deserialization step at all; you point at the bytes and read. The trade named: a row format (JSON/Protobuf/Avro) optimizes shipping one whole record; a columnar format optimizes scanning one field across many records — same "turn structure into bytes" problem, opposite access pattern, so opposite layout (L79's "the layout is the design," applied to the wire).

The third wall — the debuggability tax. The moment you go binary, you lose the thing JSON gave you for free: a human (or curl, or a log grep, or a new engineer) can no longer read the message. 08 CB 89 EC 8F F7 23 means nothing without the .proto. This is a real operational cost — every debugging session now needs the schema and a decoder, and a message logged without its schema version is a mystery. Mitigations: log a decoded (text) copy at the edge for humans while the wire stays binary; keep schemas versioned and discoverable; use gRPC reflection or Avro's registry so tools can decode on the fly. The trade named: binary buys size and speed at the cost of transparency — the same bytes that are cheap for the machine are opaque to the human, so you pay it back in tooling.

The fourth wall — don't pay for discipline you don't need. Binary isn't automatically the answer. A public API consumed by third parties you'll never coordinate a schema rollout with (L18) wants JSON precisely because it's self-describing and universal — the readability and zero-setup are the product. A config file a human edits wants text. A message sent once a minute doesn't justify a schema registry to save 100 bytes. Protobuf/Avro earn their keep on high-volume, internal, service-to-service traffic where you control both ends, the bytes and cycles multiply by 40k/s and 20 hops, and you can run the schema discipline. The trade named: the format follows the reader — a known, high-volume, coordinated reader wants compact binary; an unknown, low-volume, or human reader wants self-describing text. Choosing binary for a public API buys speed nobody needed and pays in adoption friction; choosing JSON for a 40k/s internal fan-out burns the cores from Move 1 for readability nobody uses.

So the honest picture of a wire format: the same object is 127 bytes and ~3 µs in JSON, or 28 bytes and ~0.4 µs in Protobuf — ~4.5× the bytes, ~7× the CPU — and at 40k req/s across L17's 20 hops that's ~343 GB/day and ~2 cores of difference on one event stream (Move 1). But the bytes and cycles are the visible cost; the one that governs the design is the schema as a contract shared across services you deploy independently (Move 4). Adding a field is safe in every format; removing, renaming, or retyping one is a migration (L24) because the fleet is always mid-rollout (L31), and the compactness of a binary format is bought with the discipline of never reusing a field number and running every breaking change through expand/contract. Around that: analytics wants a columnar/zero-copy layout, not a row message (L29); binary costs you debuggability (pay it back in tooling); and the right format follows the reader — compact binary for known high-volume internal traffic, self-describing text for public or human-read messages. Every choice names its price.

The deepest point: a serialization format is a decision about where the schema lives, and that decision sets who has to agree with whom before a message can change. Put the schema in the message (JSON) and no one has to agree — any reader can parse any message — but you pay in bytes on every message and the real contract hides, un-versioned, in a dozen codebases until it breaks at runtime. Move the schema out of the message (Protobuf/Avro) and the wire gets tiny and fast, but now every producer and consumer shares a versioned artifact they must evolve in lockstep-without-a-meeting, which is exactly why field numbers (not names) are the contract and why you may never reuse one. Notice the whole lesson is assembled from pieces you already own: L18's published contract (additive-safe, removes break), L24's expand/contract run on the wire instead of a table, L31's gradual rollout that forces both-directions compatibility, L17's 20 hops that multiply the CPU, L29's row-vs-columnar layout choice, L33's fan-out that multiplies the bytes, and L59's cost lens on the cores you reclaim. The new idea is only that "send the message" was hiding a real engineering choice, and that choice trades human-readability & flexibility vs size, speed & schema discipline.

The four traps

  • Trap 1 — reusing a Protobuf field number. Drop field 5 and hand its number to a new field of a different type, and old messages' bytes at tag 5 are silently reinterpreted → plausible garbage in the ledger/warehouse. Always reserved a removed number and name; never reuse.
  • Trap 2 — treating a rename/remove as an edit. The fleet is always mid-rollout (L31), so a breaking change must be a migration (expand → dual-populate → migrate readers → contract, L24). "Just rename it" breaks every not-yet-deployed reader — instantly in JSON (name is the wire key), and on removal in Protobuf.
  • Trap 3 — using a row format for analytics. Shipping a billion Protobuf/JSON rows to answer "sum by day" forces a full parse of every record to read one column (L29's row-store trap on the wire). Use a columnar format (Parquet/Arrow) so the reader touches only the column.
  • Trap 4 — choosing the format against the reader. Binary on a public third-party API buys speed nobody needed and pays in adoption friction and lost debuggability; JSON on a 40k/s internal fan-out burns cores and bytes for readability nobody reads. The format follows the reader: text for unknown/human, compact binary for known/high-volume.
