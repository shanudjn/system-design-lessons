Backpressure & Flow Control: Saying No Gracefully When Scaling Can't Keep Up

Lesson 27 ended on a hard fact: a sudden 2× spike outruns the 3-minute boot time, so for those ~3 minutes the fleet is offered 80,000 requests/second while it can only finish 40,000. Something has to give. The tempting answer — "just queue the extra work until servers arrive" — is the exact move that turns a slowdown into a total outage. This lesson takes that mismatch (a fast producer, a slow consumer, across a whole call graph) and traces what actually happens: we'll estimate how fast an unbounded buffer fills memory (~144 GB in 3 minutes → crash) and how goodput collapses to zero even while throughput stays high, model the one fix that matters — a bounded queue sized from the client timeout — plus the two ways it can say no (block upstream, or drop), trace three responses to the same overload, and hit the wall that names the whole domain: where in the chain you put the "no." The trade shifts from Lesson 27's cost-vs-headroom to the one every overloaded system is really deciding: throughput vs tail latency & stability.

The one system we'll design

Take the request path from the last few lessons. Phones hit an edge (a load balancer / API gateway, Lesson 26), which forwards to the API tier (the stateless servers of Lesson 27), which calls a downstream service that does the slow, expensive part — say the ledger writer of Lesson 25, bound by a database that can durably commit only so many writes per second. During the 2× spike, the edge is offered 80,000 req/s but the downstream can sustain only 40,000 req/s. That gap — 40,000 req/s of work with nowhere to go — is the whole problem. Here is the shape, and the two numbers that decide whether the system bends or breaks.

  BACKPRESSURE  —  a fast producer, a slow consumer, and where you put the "no"

     offered                                                 40,000 req/s
        |                                                          |

   | (LB /   |      | (stateless|      |  [ | | | ]|      | (ledger DB writer)|
   |  gateway)|     |  workers) |      |           |      |   40,000 req/s    |

  Two questions decide everything:
    1. Is that queue BOUNDED?   unbounded -> fills memory -> crash (total outage)
    2. WHERE does the "no" go?  at the slow end (wasted work) or at the EDGE (cheap)?

Backpressure is the signal a slow consumer sends back up the chain that says "stop handing me work faster than I can finish it." Flow control is the machinery that carries and obeys that signal. The failure this lesson is about is what happens when there is no such signal: the producer keeps pushing, the work piles up somewhere, and the pile itself becomes the outage. You cannot make the consumer faster in the moment (Lesson 27 proved that), so the only honest move is to make the producer slower — or to refuse work you can't do. Everything here is one of those two.

Words we'll earn before we lean on them

  • Producer / consumer — whatever hands off work, and whatever does it. The edge produces requests; the downstream consumes them. Any two adjacent hops are a producer/consumer pair.
  • Backpressure — the "slow down" signal flowing against the direction of work, from the overloaded consumer back toward the producer.
  • Flow control — the mechanism that produces, carries, and enforces that signal so the producer's rate is capped at the consumer's rate.
  • Bounded vs unbounded queue — a buffer with a hard maximum length vs one that grows until memory runs out. The single most important choice in this whole lesson.
  • Throughput — responses produced per second. Goodput — useful responses per second: ones that arrive before the client gave up. Under overload these two diverge, and goodput is the one that matters.
  • Load shedding — deliberately dropping work you can't do in time, returning a fast, honest rejection (an HTTP 429 Too Many Requests, Lesson 07) instead of a slow timeout.
  • Admission control — deciding at the entrance whether to accept a request at all, before it consumes any downstream work.
  • Credit-based flow control — the consumer advertises how much it can take (a number of free slots, a "credit" or "window"); the producer sends only up to that credit and blocks at zero. TCP's receive window, HTTP/2 flow-control windows, and Reactive Streams' request(n) all work this way.
  • Block vs drop — the two ways a full bounded queue can say no: block the producer (push-back — only works if you control the producer) or drop the request (shed — the only option when the producer is the public internet).
  • Head-of-line blocking — one stuck item at the front of a queue holding up everything behind it, even work that could proceed.

Move 1 — Estimate: doing nothing is worse than doing less

Before designing a fix, price the naive plan — "buffer the overflow until Lesson 27's new servers boot." Two independent numbers say that plan doesn't just degrade, it detonates.

Worked (way 1): the unbounded buffer eats memory. Overflow piles up at 80,000 − 40,000 = 40,000 requests/second. Each in-flight request holds real memory — parsed body, response buffer, connection and TLS state — call it a modest ~20 KB. We're waiting out the ~180 s boot window from Lesson 27:

• backlog after 3 min = 40,000 × 180 = 7,200,000 requests queued.

• memory = 7,200,000 × 20 KB = 144 GB — far past any server's RAM. Long before that, the box hits swap or the OOM killer and dies. An unbounded queue doesn't buy you time — it converts a latency problem into a crash, and a crash sheds 100% of load, including the requests you could have served.

Worked (way 2): goodput collapses to zero while throughput looks fine. Suppose clients wait 1 s then give up (Lesson 07's timeout). With an unbounded queue in front of a 40,000/s consumer, the wait time is W = queue_length ÷ 40,000 (Little's Law again, Lesson 13). The queue crosses 40,000 items after just 40,000 ÷ 40,000/s = 1 second of overload — and from that instant every request waits more than 1 s, so every client is already gone by the time its answer is ready.

• throughput stays a healthy-looking 40,000 responses/s — the CPU is pegged, producing answers.

• goodput = ~0 — every one of those answers arrives after its client timed out. The server is at 100% utilization doing work nobody is waiting for anymore, while fresh requests rot behind them. This is the goodput cliff: past capacity, an uncontrolled system's useful output doesn't plateau, it falls toward zero — because it spends its capacity finishing requests that have already been abandoned.

So the two "do nothing" outcomes are a crash (way 1) and a system that's busy but useless (way 2). Both are worse than simply refusing the 40,000 req/s you can't serve. That refusal, done well, is this entire lesson.

Name the trade-off — throughput vs goodput under overload. Chasing maximum throughput ("accept everything, keep every core busy") is exactly what destroys goodput once you're past capacity, because the busywork is stale-on-arrival and it starves the requests that could still be served in time. The counter-intuitive move is to accept less so that what you accept actually completes before its deadline. Under overload, the goal is not to do the most work — it's to do the most work that still matters.

Move 2 — Model: bound the queue, then choose how it says no

The fix has two parts. First, every queue in the path gets a hard maximum length. Second, when a bounded queue is full, it must do something — and there are exactly two somethings: push back on the producer (block) or throw the request away (drop). Which one depends on whether you control the producer.

Sizing the bound: derive it from the timeout

A bounded queue is only useful if the wait it allows is shorter than the client's patience. Max wait = depth ÷ service_rate. We want that under the 1 s timeout at a 40,000/s consumer, so:

• depth < 1 s × 40,000/s = 40,000. Pick depth = 20,000 for margin → max wait 20,000 ÷ 40,000 = 0.5 s, comfortably under the timeout.

• memory is now fixed: 20,000 × 20 KB = 400 MB, not 144 GB. And every served response is ≤ 0.5 s old, so it beats the timeout — goodput returns to the full 40,000/s. The other 40,000/s gets a fast 429 instead of a slow death. A bounded queue turns "how much do I buffer?" into "how much latency am I willing to add before I say no?" — and you answer it with the client's deadline, not with available RAM.

The two ways to say no when full

  A FULL BOUNDED QUEUE HAS TWO MOVES

  (a) BLOCK  — push back on the producer          (b) DROP — shed the request
      producer must wait for a free slot               queue is full -> reject now
      the "slow down" travels UPSTREAM                 return 429 instantly (honest no)

      use when you CONTROL the producer:               use when you DON'T control it:
        one internal service calling another             the public internet, users, UDP
        a worker reading a Kafka partition (L09)         (you can't make strangers wait)
        a thread pulling from an in-process queue

  CREDIT-BASED FLOW CONTROL = block, made explicit and continuous:
      consumer advertises free slots ...... credit = 12,000
      producer sends at most 12,000, then STOPS until credit refreshes
      credit shrinking toward 0  ==  backpressure, expressed as a number
      (this is TCP's receive window / HTTP-2's flow window / Reactive Streams request(n))

Blocking is the cleaner tool when you own both ends: the consumer simply stops accepting, the producer's send() stalls, and — if every hop back to the edge is also bounded — that stall propagates all the way up until the edge itself is the thing that's blocked, at which point it must convert the block into a drop, because it cannot block a stranger on the internet. That's the key structural rule: backpressure propagates inward as blocking and terminates at the edge as shedding. Credit-based flow control is just blocking made into an explicit, continuously-updated number so the producer never even sends the byte that would be dropped — cheaper than send-then-reject, because the "no" arrives before the work does.

Name the trade-off — block vs drop is "who can wait?" Blocking preserves every request (nothing is lost) but only works when the producer is something you can legitimately stall; stall the wrong producer and the block travels upstream until it freezes a user-facing thread pool (Lesson 07's exhaustion) — you've moved the outage, not fixed it. Dropping loses requests but is the only truthful answer to a producer you can't slow down, and a fast 429 lets the client back off (Lesson 07) instead of hanging. Block inside the graph where you control both ends; shed at the boundary where you don't.

Move 3 — Trace the paths

Three responses to the same 80,000-vs-40,000 overload. Watch one thing: how much wasted work each request costs before the system says no.

Path A — unbounded buffer (the naive "queue everything")

  t=0     overload begins, queue unbounded
  t=1 s   queue = 40,000 -> wait crosses the 1 s timeout -> goodput starts dying
  t~10 s  clients time out AND retry (L07) -> offered load climbs above 80,000
          server still finishing abandoned requests at 40,000/s -> goodput ~ 0
  t~60 s  queue in the millions, memory climbing toward 144 GB
  t~??    OOM / swap death -> the box falls over -> 100% of load shed the ugly way

No bound, no signal, no survivors. The queue absorbs the overflow exactly long enough to guarantee a crash, and the retry storm (Lesson 07) piles on more load while goodput is already zero — the textbook metastable failure: even after the spike passes, the retry backlog can keep the system down. "Buffer it and hope" is not flow control; it's a delayed, worse outage.

Path B — bounded queue, but shed at the slow end

  edge --> API tier --> [bounded queue @ downstream, depth 20,000] --> ledger DB
     accept 80,000 ......... all 80,000 traverse edge + API tier (auth, parse, TLS) ...
        |                                                                    |
        v                                                                    v
   downstream queue full at 20,000 -> DROP the excess 40,000/s here (429)   40,000/s served

  survives (no OOM, goodput = 40,000/s) BUT:
     the 40,000/s it drops already PAID for edge + API-tier CPU before being rejected
     -> that wasted work is capacity stolen from requests that could have completed

Bounding the queue stops the crash and restores goodput to the full 40,000/s — a huge win over Path A. But the rejection happens at the far end, so every one of the 40,000 dropped requests/second first consumed the edge and the API tier: connection setup, TLS, auth, JSON parsing, a hop across the network. That work produces a 429 and nothing else. Worse, it competes for the same CPU the survivors need. Better than a crash, but leaky: a request you were always going to reject should be rejected before you spend anything on it.

Path C — bounded queue + backpressure propagated to admission control at the edge

  downstream queue depth -> credit signal -> API tier -> credit signal -> EDGE
     "I have room for 40,000/s"  ..... travels upstream as shrinking credit .....
        |                                                                    |
        v                                                                    v
   EDGE admits only ~40,000/s (admission control), 429s the other 40,000/s INSTANTLY
     rejected requests cost ~nothing: no auth, no parse, no downstream hop
        |
        v
   API tier + downstream run at a healthy ~70% (L27's knee), every admitted request completes

Same bounded queue, but now its fullness is reported upstream as a credit/health signal, and the edge acts on it: it admits only what the chain can finish and returns an immediate 429 to the rest — before spending a cent of downstream work on them. The rejected requests are cheap, the admitted requests all complete within the deadline, and the whole graph runs at a healthy utilization instead of thrashing. This is the same "honest 429" from Lesson 07, now placed where it's cheapest. The best place to say no is the first place that can — the entrance.

Name the trade-off — where you shed is goodput vs simplicity. Shedding deep (Path B) is trivial to add — one bounded queue in front of the bottleneck — but every drop wastes the upstream work already spent, so your usable goodput sags under heavy overload. Shedding at the edge (Path C) preserves nearly all goodput because rejects are cheap, but it needs the downstream's health to travel upstream — a real signal to build and trust. Cheap-but-leaky vs efficient-but-wired-up: the deeper you can afford to push the "no" toward the door, the more of your capacity survives the overload.

Move 4 — Find the first bottleneck: where the "no" goes, and the traps around it

Path C names the principle — reject at the edge, informed by the whole chain. But "put admission control at the door" hides three traps that turn a good idea into a new outage. Here they are, each a familiar tool aimed at the flow.

Worked: wasted work is stolen capacity. Say the edge + API tier cost 5 ms of CPU per request before the downstream is even called. Under Path B, the 40,000 req/s you reject still burn 40,000 × 5 ms = 200 core-seconds/second = 200 cores doing nothing but producing 429s — CPU that the 40,000 survivors now have to fight for. Push the reject to the edge (Path C) and those 200 cores come back to real work. Every unit of work spent on a request you will reject is subtracted twice: once wasted, once stolen from a request you could have served.

  • Trap 1 — an unbounded queue hiding anywhere in the graph. Bounding the front door is worthless if some internal hop (a thread pool's task queue, a client library's send buffer, a Kafka producer's in-memory batch) is still unbounded — the pile just moves there and OOMs there instead. The rule is total: every queue, at every hop, gets a bound. Backpressure only propagates if there's an unbroken chain of bounded buffers from the bottleneck back to the edge; one unbounded link in the middle silently swallows the signal.
  • Trap 2 — blocking the wrong thing (head-of-line blocking & thread-pool freeze). Blocking is the right push-back inside the graph, but if the block lands on a shared, user-facing thread pool, one slow downstream can freeze threads that were serving unrelated fast requests — Lesson 07's exhaustion, now triggered on purpose by your own backpressure. Keep the bounded queue's "full" behavior non-blocking at the edge (drop, don't hang), and isolate pools (a bulkhead) so backpressure from one dependency can't stall the rest.
  • Trap 3 — shedding blindly (all requests are not equal). When you must drop, which 40,000/s you drop is a design choice with big goodput consequences. Shed the cheapest to lose and the least valuable first: drop retries before first-tries (a retry means the original may still complete), drop low tier before paying customers, and never shed health checks (killing those makes the load balancer think the box is dead — the shed becomes an outage). A neat overload trick: switch the queue from FIFO to LIFO so you serve the freshest requests (whose clients are most likely still waiting) and drop the stale head that's already near its timeout — raising goodput without adding a single server.

Name the core trade-off — throughput vs tail latency & stability. Every lever here spends potential throughput to buy a bounded tail and a system that stays up. A bounded queue refuses work it could nominally have queued (lower peak throughput) so that admitted work completes within the deadline (bounded p99) and memory stays flat (stability). Admission control rejects requests a greedier system would accept, trading raw acceptance for the guarantee that acceptance means completion. Backpressure is the system choosing a smaller amount of work it can actually finish over a larger amount it can only pretend to — and the whole skill is placing the "no" where it costs the least and protects the most: bound every queue, block where you own both ends, shed at the edge, and when you shed, shed the least valuable first.

Where we landed

We took Lesson 27's unwinnable spike — 80,000 req/s offered, 40,000 servable, for the ~3 minutes before new servers boot — and made it survivable. Estimate killed the naive "buffer it" plan twice: an unbounded queue fills ~144 GB in 3 minutes (40,000/s × 180 s × 20 KB) and crashes, and even before that goodput collapses to ~0 while throughput stays a deceptive 40,000/s — the server pegged, finishing requests whose clients already timed out. Model gave the one fix that matters: bound every queue, sized from the timeout (depth < timeout × rate = 40,000 → pick 20,000 → max wait 0.5 s, memory a fixed 400 MB, goodput back to 40,000/s), and when a bounded queue is full, choose its "no" — block the producer (credit-based flow control: TCP window, HTTP/2, request(n)) when you control it, or drop (an honest 429, Lesson 07) when you don't. Tracing three responses to the same overload showed the axis that matters — how much work you waste before saying no: the unbounded buffer (crash + retry-storm metastability), the bounded-but-shed-deep queue (survives, but every reject already burned edge + API-tier CPU — ~200 stolen cores), and bounded-plus-edge-admission (the downstream's fullness travels upstream as a credit signal, the edge 429s the excess for near-free, goodput preserved and the graph runs at Lesson 27's healthy knee). The first bottleneck was where the "no" goes, guarded by three traps: one unbounded queue hiding at any hop reopens the OOM; blocking a shared user-facing pool re-creates Lesson 07's thread-pool freeze (bulkhead + non-blocking edge); and blind shedding wastes goodput (drop retries, low tier, and the stale head — FIFO→LIFO — first, never health checks). The real lesson: you cannot make a slow consumer fast in the moment, so the only honest options are to slow the producer or refuse the work — and a system that gracefully does less it can finish beats one that greedily accepts more it can only crash trying to do. The trade is throughput vs tail latency & stability.
