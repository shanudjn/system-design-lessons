Consistency & Replication: A Like-Counter Under Concurrent Writes

We add a like button to our short links. A celebrity posts one and it goes viral: 50,000 likes/second, half a million people watching the number tick. Two problems crash into each other. First, when two likes land at the same instant, the count goes up by one, not two — a lost update. Second, when one database can't serve the reads we copy it, and now the copies disagree. Same four moves, and we name every trade-off: atomic vs lock, strong vs eventual, sync vs async, exact vs fast.

The one number we'll trace

A short link xZ9 has a like counter: one row, likes(link_id, count). Liking it should add 1. Reading the page should show the total. That's it — and it is one of the hardest things in distributed systems, because "add 1" is secretly three steps, and "show the total" is secretly a question about which copy you ask. Here is both bugs on one screen.

  THE WRITE BUG (lost update)                 THE READ BUG (stale replica)
  ───────────────────────────                 ─────────────────────────────

  count = 100                                  Alice ──like──► LEADER (count 100→101)
  Worker A: read 100 ─┐                                          │ async copy (lag)
  Worker B: read 100 ─┤ both saw 100                             ▼
  Worker A: write 101 │                        Alice ──refresh──► REPLICA (still 100)
  Worker B: write 101 ┘ second overwrites      "I just liked it... why does it say 100?"
  TWO likes, count = 101  (one vanished)       read-your-own-write broken

A "counter" is the simplest piece of shared mutable state — which is exactly why it exposes every consistency problem at once. Get the like-counter right and you understand bank balances, inventory, vote tallies, and seat reservations. They are all the same shape: many writers, many readers, one truth that must not drift.

Words we'll earn before we lean on them

  • Read-modify-write — the three hidden steps of "+1": read the value, add one, write it back.
  • Race condition — two operations interleave so the result depends on timing, not logic.
  • Replication — keeping copies of the data on more than one machine.
  • Leader / replica — the one copy that takes writes (leader) and the read-only copies (replicas, aka followers) that trail behind it.
  • Consistency — a promise about which value a read is allowed to return.

Move 1 — Estimate: how hot is this counter, and how many readers?

Price the load before designing. A viral link draws 50,000 likes/second at peak. Reads dwarf writes — every viewer's page renders the count — call it 10×, so 500,000 reads/second. Both hit the same one row.

The hot-row ceiling. An atomic increment must briefly lock the row so two writers can't clobber each other. Say a locked write-and-release takes ~0.5 ms. Writes to one row serialize, so that single row caps at 1 ÷ 0.0005 = 2,000 increments/second. We need 50,000. The hot row is 25× too slow — not because the database is weak, but because one row is a single point of serialization.

The read ceiling. One database node serves maybe 10,000 reads/second of this kind. We need 500,000. That's 50× — so we'll replicate the data across read-only copies (and cache the count, per Lesson 02). Replication is the only way to scale reads past one machine, and it is the move that introduces disagreement between copies.

Name the tension up front: the two fixes pull in opposite directions. To survive the writes we want the count in one authoritative place (easy to keep correct, but a throughput wall). To survive the reads we want the count in many places (scales reads, but now copies can disagree). Every consistency decision in this lesson is a point on the line between "one true copy" and "many fast copies."

Move 2 — Model: what "+1" really is, and why it races

Spell out the naive like handler. It looks like one line; it's three.

  def like(link_id):
      n = db.read(link_id).count     # step 1: READ   (e.g. 100)
      n = n + 1                       # step 2: MODIFY (101, in app memory)
      db.write(link_id, n)           # step 3: WRITE  (store 101)

Between step 1 and step 3 there is a gap. If a second request reads the same 100 during that gap, both compute 101, and the second write overwrites the first. One like is gone. This is a race condition: correctness now depends on timing. Trace it on a clock.

Worked: two likes, one survivor. Count starts at 100.

t=0.0 ms — Request A reads 100.
t=0.1 ms — Request B reads 100 (A hasn't written yet).
t=0.2 ms — A writes 101.
t=0.3 ms — B writes 101 (it still thinks the base was 100).

Two users liked. The count is 101, not 102. A like vanished. At 50,000 likes/second these gaps overlap constantly — you would silently lose a large fraction of every viral spike. The bug isn't rare; under load it is the common case.

Move 3 — Trace the paths: fixing the write, then the read

Path A — kill the lost update (atomic increment)

The read-modify-write loses data because the "read" and the "write" are separate trips with a gap between them. The fix is to make the increment atomic — one indivisible operation the database does for you, with no gap for anyone to slip into:

  LOST-UPDATE (read then write):            ATOMIC (one statement):
    n = read(count)      # 100                UPDATE likes
    write(count, n+1)    # 101                  SET count = count + 1
    -> two of these race -> lost like           WHERE link_id = 'xZ9';
                                              -> DB serializes per row; nothing lost

Now the database itself does read+add+write as one step while holding the row lock, so two concurrent + 1s run one-after-the-other and the count rises by exactly two. The race is gone because the gap is gone. (The same idea appears as compare-and-set / optimistic locking: write only if the value is still what you read, else retry. Atomic increment is the lock-free special case for counters.)

Name the trade-off: atomic increment trades flexibility for safety. You can no longer compute the new value in your own code (apply a discount, cap at a max) — the database owns the arithmetic. For a plain counter that's a perfect fit. For richer logic you fall back to compare-and-set with a retry loop, paying retries under contention instead.

Path B — the stale read (replication lag)

Atomic increment fixes the write but the row still caps at ~2,000/s and one node still can't serve 500,000 reads. So we replicate: one leader takes all writes, and several replicas copy the leader's changes and serve reads. The leader streams its changes to the replicas — but that copy takes time. That delay is replication lag.

   WRITES                         READS (fan out across replicas)
   ──────                         ──────────────────────────────
   all likes ─► LEADER ──┬── stream ──► REPLICA 1 ─► readers
                count    ├── stream ──► REPLICA 2 ─► readers
                = truth  └── stream ──► REPLICA 3 ─► readers
                              (lag: replicas trail the leader by tens of ms)

Now Alice likes the link (write → leader, count 100→101), then refreshes (read → a replica that's 40 ms behind and still says 100). She sees her own like disappear. This breaks read-your-writes: the weak but vital promise that you at least see your own changes. Everyone else seeing 100 for 40 ms is harmless; the author seeing it is alarming.

Worked: how stale, exactly? Suppose average replication lag is 40 ms. In those 40 ms the leader took 50,000 × 0.040 = 2,000 more likes. So a replica read can be up to ~2,000 behind the true count during a viral spike. For a like badge, being 2,000 behind for 40 ms is completely fine — nobody can tell 1,048,000 from 1,050,000. For a bank balance or "seats left: 1," it is not. The acceptable staleness is a property of the data, not the database.

The named choice: strong vs eventual consistency

You get to choose what a read promises. The two anchors:

ModelPromiseCostRight for
Strongevery read sees the latest writereads must hit the leader or a quorum → slower, less scalablebalances, inventory, "seats left"
Eventualreads may be stale but copies converge if writes stopcan show old data brieflylike counts, view counts, feeds

Two cheap middles fix Alice without going fully strong: read-your-writes (for a few seconds after you write, route your reads to the leader, so you see your own like; everyone else reads replicas), or simply increment the number in her browser optimistically. Both keep eventual consistency's cheap reads for the 499,999 other viewers.

How "strong" is actually built: quorums (W + R > N)

When you do need strong reads from replicas, the tool is a quorum. Keep N copies. Require a write to be acknowledged by W of them before it's "done," and a read to gather answers from R of them and take the newest. The magic rule: if W + R > N, the write set and the read set must overlap in at least one node — and that node has the latest value.

Worked: N = 3 copies. Pick W = 2 and R = 2. Then W + R = 4 > 3.

A write lands on copies {1, 2}. A later read asks copies {2, 3}. The sets share copy 2 — which saw the write — so the read returns the fresh value. Because 2 + 2 = 4 > 3, any write-pair and any read-pair must share a node (pigeonhole: 4 picks among 3 boxes forces a collision). Overlap is guaranteed → the read can't miss the latest write.

Counter-example: W = 1, R = 1. W + R = 2, not > 3. Write hits {1}; read hits {3}; no overlap → the read returns stale data. Fast (one node each) but not strong. That's the dial: raise W and R for consistency, lower them for speed and availability.

Name the trade-off (this is CAP in miniature): sync replication / high quorums buy strong consistency but cost latency (you wait for more nodes) and availability (if too few nodes are reachable, you must refuse the operation rather than serve stale data). Async replication / low quorums buy speed and stay up during partial failures, but let reads go stale. There is no setting that is fast, always-available, AND always-fresh during a network split — you pick two. We give CAP its own lesson; the like-counter is your first feel for it.

Move 4 — Find the next bottleneck: the hot row is still one row

Atomic increment removed the correctness bug, but not the throughput wall: one row still serializes at ~2,000 writes/second and we need 50,000. The standard fix is the sharded (approximate) counter: split one logical counter into K physical sub-counters on different rows/nodes. Each like increments a random shard; the displayed total is the sum of all shards.

  ONE HOT ROW (serializes)            SHARDED COUNTER (K = 50 sub-rows)
  ────────────────────────           ─────────────────────────────────
  like ─► [ xZ9 : count ]            like ─► pick random k in 0..49
          ~2,000 writes/s max                 ─► [ xZ9#k : +1 ]   (50 rows)
          50,000 needed = JAM        read  ─► SUM(all 50 rows)
                                     each row: 50,000/50 = 1,000 w/s  (under the 2,000 cap)

Worked: size K. Per-row ceiling ≈ 2,000 writes/s; target 50,000 writes/s. K ≥ 50,000 ÷ 2,000 = 25. Use K = 50 for headroom → each shard takes ~1,000 writes/s, comfortably under the cap. Writes now scale linearly with K. The read pays for it: instead of reading 1 row you must SUM 50 — so cache that sum (Lesson 02) and recompute it every second or so, since a like badge tolerates ~1 s of staleness.

Name the trade-off: sharding the counter trades a cheap exact read for a cheap scalable write. One row gave you the instant true total but choked on writes; K rows swallow the writes but make the read a fan-in sum that's best served slightly stale from cache. That's the right trade for likes (write-heavy, staleness-tolerant) and the wrong trade for a bank balance (read-heavy, must be exact) — which would keep the single strongly-consistent row and shard by account instead. Match the consistency to what the number means.

Where we landed

We took one counter and met every consistency problem at once. Estimate exposed two ceilings: a hot row that serializes at ~2,000 writes/s (vs 50,000 needed) and a single node that can't serve 500,000 reads. Model revealed that "+1" is a read-modify-write with a gap, which races into lost updates. Tracing the paths fixed the write with an atomic increment (close the gap), then scaled reads with replication — which introduced lag and the choice between strong and eventual consistency, built concretely from quorums (W + R > N guarantees overlap). The next bottleneck — the still-hot single row — pushed us to a sharded counter, trading an exact read for a scalable write. The thread through all of it: pick how fresh a read must be based on what the number means, then pay only for that much consistency.
