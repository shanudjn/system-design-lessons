Multi-Region Data Placement & Residency: Where a Row Is Legally Allowed to Live

Every lesson so far has treated a row as something you can put anywhere that's fast — cache it (L02), replicate it across an ocean (L23), shard it by a hash (L79). This lesson adds a constraint that isn't about speed at all: some rows aren't allowed to leave a country. A privacy law can make copying one German user's profile to a US server a violation that costs millions — not a slow query, a fine. So placement stops being purely a performance choice and becomes a legal one. We take one concrete row — Alice's profile, a resident of Germany — and one concrete query — "total revenue by product last month, worldwide" — and watch the query try, and fail, to gather rows that legally cannot move. We'll estimate the two forces in tension: the ~90 ms speed-of-light tax on crossing the Atlantic, and the compliance wall (a 4% fine that dwarfs any latency cost). We'll model the fix: partition data by the user's home region, a key that is now a legal attribute, with a small global directory that says which region owns each user. We'll trace three paths — Alice at home (fast, compliant), Alice traveling abroad (the roaming tax), and the global analytics join that hits the wall. And we'll find the first bottleneck: the cross-region query — a "global" join can't pull rows that can't leave home, so you push the computation to the data instead of the data to the computation. The trade under all of it: local latency & compliance vs global query simplicity.

The one system we'll build

A global marketplace: 300 million users spread across three regions — EU (served from Frankfurt), US (Virginia), and India (Mumbai). Each user has a profile (name, email, address — personal data) and a stream of orders. A privacy law covering the EU says the personal data of EU residents must be stored and processed inside the EU. One row and one query travel through this lesson:

  • One row: Alice, a resident of Germany. Her profile is EU personal data — by law it may live only in the EU region. We'll follow it as she uses the app at home and abroad.
  • One query: the finance team asks for "revenue by product, worldwide, last month." It wants to join orders against users across all three regions — and it is about to discover it cannot legally pull Alice's region's rows into a US warehouse.

Here is the whole tension on one page. Two things pull placement in opposite directions — the network wants a copy near every user, the law forbids Alice's copy from leaving the EU — and a global query sits on top wanting to read everything at once:

        EU region (Frankfurt)      US region (Virginia)      India (Mumbai)
        ┌──────────────────┐      ┌──────────────────┐      ┌──────────────┐
        │ EU users' data   │      │ US users' data   │      │ IN users'    │
        │  Alice (DE) ◀────┼──┐   │  Bob (TX)        │      │  data        │
        │  ...120M rows    │  │   │  ...130M rows    │      │  ...50M rows │
        └──────────────────┘  │   └──────────────────┘      └──────────────┘
                              │            ▲
        Alice's PII may NEVER │            │  "give me every user + order
        leave the EU box  ────┘            │   row so I can join them here"
                                           │              ✗  ILLEGAL
                              ┌────────────┴─────────────┐
                              │  GLOBAL analytics query   │  wants to gather
                              │  revenue by product, WW   │  rows that can't move
                              └───────────────────────────┘

        GLOBAL DIRECTORY (tiny, replicated everywhere):  user_id -> home_region
          Alice -> EU     Bob -> US     ...      (says WHERE each row lives)

The one idea the whole lesson turns on: once a law pins a row to a place, the row's location becomes a property of the row, not a free optimization. You can't cache Alice in Virginia for speed, you can't replicate her to survive an EU outage by copying her to the US, and you can't pull her into a global join. So you flip the whole design: instead of moving data to wherever the computation is, you keep each user's data in its legal home and move the computation (and only non-personal results) to the data. Every technique below — home-region partitioning, the directory, per-region joins that ship aggregates — is that one inversion.

Words we'll earn before we lean on them

  • Region — a geographic cluster of datacenters (Frankfurt, Virginia, Mumbai). Crossing between regions costs real time and, sometimes, crosses a legal border.
  • Personal data (PII) — data that identifies a person: name, email, home address, precise location. This is what privacy law protects. An anonymous product count is not personal data.
  • Data residency / data localization — a legal requirement that certain data be stored (and sometimes processed) within a specific country or region.
  • Data sovereignty — the idea that data is subject to the laws of the place it physically sits. Put a row in Virginia and US law can reach it — which is itself a reason a law may forbid the move.
  • Home region — the one region a user's personal data is bound to, usually their country of residence. It is the partition key (L79) for placement — but a legal one.
  • Geo-partitioning — sharding by home region so each region's cluster holds only its own residents' rows.
  • Directory (placement map) — a small, globally replicated lookup: user_id → home_region. It tells any server which region owns a given user without moving the user's data.
  • Pseudonymization / tokenization — replace PII with a meaningless token (L30). The token can travel; the mapping token → real PII stays home.
  • Follow-the-sun — a user roams; requests land near wherever they physically are, even though their data stays in its home region.
  • Cross-region join — a query that needs rows from more than one region at once. The central problem of this lesson.
  • Aggregate — a summary number (revenue, count) with the personal detail stripped out. Aggregates can usually cross borders where raw rows cannot.

Move 1 — Estimate: the latency tax, and the compliance wall that dwarfs it

Two forces set every decision here, and they are measured in different units. One is milliseconds; the other is money. Sizing both is what shows why compliance wins.

Force 1 — the speed-of-light tax on crossing the ocean. Frankfurt to Virginia is about 6,500 km. Light in fiber travels at ~200,000 km/s (about two-thirds of light in vacuum, L14). That sets a floor no faster server can beat:

  one-way   6,500 km / 200,000 km/s = 0.0325 s = 32.5 ms
  round trip                          = ~65 ms
  + routing/queueing overhead         ≈ ~90 ms   (matches L23)

  local read inside one region        ≈ ~1 ms

  crossing the Atlantic per request   ≈ 90× a local read

Serving a user from their own region is ~90× faster than reaching across the ocean. This is the force that wants a copy of every user near every user — the same instinct as a CDN (L14) or a second live region (L23). Left alone, it says "replicate Alice everywhere." The next number is why you can't.

Force 2 — the compliance wall, priced as a fine, not a delay. A privacy law like the GDPR can fine a company up to 4% of global annual turnover, or €20M, whichever is higher. Put a number on it:

  company turnover        €500,000,000 / yr
  max fine = 4%           €20,000,000            (per violation category)

  cost of a slow request  ~90 ms  -> a worse experience, measurable, PAYABLE
  cost of an illegal copy  a €20M fine + a headline -> categorical, NOT payable

  A latency cost is a number you can trade against other numbers.
  A compliance violation is a WALL: no amount of speed buys the right
  to cross it.

This is the difference that reorders the whole design. Every earlier lesson traded one cost against another — freshness vs speed, storage vs latency. Residency is not a cost on that scale; it is a constraint. You do not "spend €20M of compliance budget to save 90 ms." You treat the border as impassable for personal data and optimize latency within what the law allows. Trade named for the first time: local latency & compliance vs global query simplicity — and compliance is the term that can't be negotiated.

How big is the data, and how big is the thing that can move? Sizing both tells you the shape of the fix before we design it.

  users        300,000,000  (EU 120M, US 130M, India 50M)
  profile row  ~2 KB each   -> 300M × 2 KB = ~600 GB of personal data
     ... which must stay split across its 3 legal homes, never pooled.

  the DIRECTORY that says where each row lives:
     user_id (8 B) + region (1 B) = 9 B/user
     300M × 9 B = ~2.7 GB   -> tiny, holds NO personal data,
                               safe to replicate to ALL regions.

The personal data is heavy and stuck; the map of where it lives is tiny and free to travel. That split — 600 GB pinned in place, 2.7 GB copied everywhere — is the seed of the design. You never move the 600 GB across a border. You replicate the 2.7 GB directory so any server, anywhere, can find out which region owns a user and route to it (the same shape as L34's service directory, but for data instead of services).

Why the whole design inverts the usual instinct: for 84 lessons the reflex has been "move the data closer to the work" — cache it, replicate it, precompute it. Residency forbids that move for personal data. So the reflex flips to "move the work to the data, and let only non-personal results come back." A €20M wall can't be optimized away; it can only be designed around, and the way you design around it is to stop trying to gather rows in one place and instead compute where they already sit.

Move 2 — Model: home-region partitioning and the directory

The placement key is a column now — a legal one

Give every user a home_region — normally their country of residence, resolved at signup. It looks like an ordinary sharding key (L79), but it is chosen by law, not by hash, and it decides which regional cluster physically stores the row:

  users table (conceptually — physically split per region):
     user_id | home_region | name  | email        | address ...
     Alice   |   EU         | ...   | ...          | ...   -> stored in EU
     Bob     |   US         | ...   | ...          | ...   -> stored in US
     Priya   |   IN         | ...   | ...          | ...   -> stored in IN

  placement rule:  a user's PII lives ONLY in its home_region cluster.
  Alice's row exists in the EU database and NOWHERE else. No cache in
  Virginia, no read-replica in Mumbai. The column IS the law applied.

Sharding by a hash (L79) balances load; sharding by home region satisfies a statute. The difference matters: a hash key you can change for performance, but you cannot rehash Alice into Virginia to balance load, because the key encodes a legal boundary. The trade this locks in: you give up the freedom to place a row wherever it's fastest, in exchange for never having to prove a copy didn't leak across a border.

The directory: find the region without moving the row

Any server, anywhere, needs to answer "which region owns Alice?" before it can serve or route her request — without reading her personal data. That's the directory's whole job (L34's registry idea, pointed at data):

   DIRECTORY:  user_id -> home_region     (2.7 GB, no PII, replicated to
                                            all 3 regions, read-mostly)

   request for Alice lands anywhere
     -> look up "Alice" in the LOCAL directory replica  (~1 ms, no border)
     -> answer: EU
     -> route the request (or the data call) to the EU cluster

The directory is small, personal-data-free, and globally replicated — the opposite of the user rows it points to. It's safe to copy everywhere precisely because it carries no protected content: a mapping from an opaque id to a region name identifies no one. Because every region has a local copy, the "where does this row live?" lookup never itself crosses a border. Trade: the directory must be highly available everywhere (a stale or missing directory can't route anyone), so it's an AP, fail-static dependency (L34/L11) — better to serve a slightly stale region map than to block; region assignments change rarely, so staleness is cheap.

Split data by sensitivity, not just by region

Not all of a user's data is equally protected. The design that makes global features possible at all is to separate the personal from the non-personal, so the non-personal part is free to travel:

   PINNED to home region (personal data):
     name, email, address, phone, precise location, payment details
       -> Alice's identity. Never leaves the EU.

   FREE to replicate globally (non-personal / pseudonymized):
     product catalog (no person in it)          -> copy to every region
     order FACTS keyed by a TOKEN, not a name    -> token travels, PII home
     aggregates: "product P sold 40,000 units"   -> a number, identifies no one

   the bridge: tokenization (L30)
     Alice's PII  <->  token "u_9f3a"  (mapping stays in the EU)
     the rest of the world sees only "u_9f3a bought product P"

A token can cross the border; the person cannot. Pseudonymization (L30) lets an order fact travel the world as "u_9f3a bought product P" while the map from u_9f3a back to Alice stays locked in the EU. Trade: you gain global features (analytics, recommendations) on the pseudonymized stream, at the cost of an extra hop — to turn a token back into a name you must ask the home region, which re-crosses the border. So you design features that never need the name: they operate on tokens and aggregates and only re-identify inside the home region when strictly necessary.

Move 3 — Trace the paths: home, roaming, and the global join

Path A — Alice at home in Frankfurt (fast and compliant)

   Alice opens the app in Berlin
     │
     ▼
   request lands at the EU edge (nearest region)
     │
     ▼
   directory lookup (local EU replica): Alice -> EU        (~1 ms, no border)
     │
     ▼
   read/write Alice's profile in the EU cluster            (~1 ms, local)
     │
     ▼
   respond  ->  total ~a few ms, and her PII never left the EU

The common case is the easy case: a user in their home region reads and writes locally, fast, and the law is satisfied for free because nothing crossed a border. This is the payoff of geo-partitioning — most requests are local because most users are home.

Path B — Alice travels to New York (the roaming tax)

   Alice (home_region = EU) opens the app in New York
     │
     ▼
   request lands at the US edge (nearest to her body)
     │
     ▼
   directory lookup (local US replica): Alice -> EU
     │      the US region has NO copy of Alice's data — by law it can't.
     ▼
   two legal choices:
     (1) PROXY the data call back to the EU cluster     (+~90 ms round trip)
     (2) ROUTE the whole session to the EU region       (all reads ~90 ms)
     │
     ▼
   Alice sees her data, ~90 ms slower — the data did NOT follow her.

Follow-the-sun means the request follows the user, never the personal data. When Alice roams, you do not spin up a copy of her profile in Virginia — that copy would be the violation. Instead the nearby edge either proxies to her home region or hands the session back to it, and she pays the ~90 ms Atlantic tax for as long as she's abroad. Trade named: a traveling user gets slower reads (a latency cost you can pay) so that you never duplicate PII outside its legal home (a wall you can't cross). The rare traveler pays; the common home user doesn't.

Path C — the global analytics join (hits the wall)

   Finance: "revenue by product, worldwide, last month."
   NAIVE plan: pull every region's orders + user rows into a US
               warehouse and JOIN them there.
     EU orders + EU users --ship to US-->  ✗  moves EU PII to the US.
                                              ILLEGAL. Do not do this.

   LEGAL plan: push the computation to the data; ship only aggregates.
     in EACH region, locally join orders×products and SUM:
        EU:    product P -> €40,000
        US:    product P -> €55,000
        IN:    product P -> €12,000
        (each row is (product_id, revenue) — NO person in it)
     ship the small per-region aggregates to a central warehouse:
        3 regions × ~100k products × ~20 B  ≈ ~6 MB total
     MERGE (sum the partials, L21/L29):
        product P worldwide = 40,000 + 55,000 + 12,000 = €107,000

The naive join moves 300M personal rows across a border; the legal join moves ~6 MB of anonymous numbers. Compare the two: shipping raw rows would be ~30M orders × ~200 B ≈ 6 GB of personal data across the ocean — illegal and a thousand times bigger than the ~6 MB of aggregates. Computing the sum in each region and shipping only (product, revenue) pairs is smaller, faster, and compliant, because a revenue total identifies no one. This is L29's partition-prune-aggregate-merge and L21's mergeable sums, now with a legal reason to prefer them: the person never crosses the border; only the anonymous total does.

Move 4 — Find the first bottleneck: the cross-region query, and the walls around it

The first bottleneck — the "global" query that wants rows which can't move. Any feature that needs to see users from more than one region at once runs into the wall: you cannot gather the rows in one place. The fix is the inversion from Move 1, made concrete:

  DON'T: move data to the computation
     gather all regions' rows into one warehouse -> illegal + huge.
  DO:    move computation to the data
     run the query IN each region on local rows -> emit only
     non-personal aggregates -> ship those -> merge centrally.

Push the computation down; let only anonymous results come up. A global count, sum, or top-K becomes a per-region local query plus a central merge of small aggregates (L21/L29). The personal rows stay home; the answer is assembled from summaries. Trade: global queries get more complex (you write a scatter-gather-and-merge instead of one big join) and can't do arbitrary row-level analysis across regions — but they become both legal and cheaper. Global query simplicity is exactly what you spend to buy compliance.

The second wall — a join that genuinely needs two people from two regions. Some queries aren't aggregates: a message from Alice (EU) to Bob (US), a shared document, a friendship (L84) that spans regions. You cannot co-locate both people — each is pinned to their own home. Two moves:

   STORE PER-ENDPOINT: keep a copy of the interaction in EACH
     participant's home region, holding only THAT participant's data
     + a TOKEN for the other side.
       EU copy: Alice's message body + "to: token(Bob)"
       US copy: Bob's inbox entry   + "from: token(Alice)"
     -> each region holds only its own resident's PII; the counterparty
        is a token, re-identified only in ITS home region if needed.

   or KEEP ONLY PSEUDONYMOUS REFERENCES across the edge (L30), so the
     cross-region link carries tokens, never names.

You don't join two people in one place — you store each person's slice in their own place and link by token. The relationship exists as two half-rows, one per home region, joined only by opaque ids. Trade: you duplicate the interaction (once per participant) and accept that showing the counterparty's name means a call to their home region — more storage and an extra hop, in exchange for never pooling two jurisdictions' PII in one row.

The third wall — a user permanently relocates. Alice moves from Germany to Texas for good. Her home_region must change EU→US, which means physically moving her personal data across the border (now legal because she is a US resident) and updating the directory. This is a live migration (L24) of one user:

   1. copy Alice's EU rows to the US cluster        (expand, L24)
   2. verify the copy, then flip the directory       Alice -> US (cutover)
   3. new requests route to US; drain in-flight EU reads
   4. DELETE the EU copy after bake                  (contract, L24 + L56)
   the directory flip is the atomic switch; the delete is the
   irreversible step, so it comes last, after verification.

Relocation is expand→cutover→contract (L24) applied to one row's legal home, with the directory flip as the cutover. The order is the safety: copy first, flip the pointer, drain, then delete — because the delete (L56) is the one step you can't undo. Trade: relocations are rare but must be exact; you accept a careful multi-step migration per moving user rather than risk either two live copies (a residency violation) or a lost row.

The fourth wall — the directory is everyone's dependency. Every request, in every region, hits the directory to find a user's home. If it's slow or down, nothing routes. So it inherits L34's rules exactly: replicate it to every region, make it fail-static (serve the last-known map rather than block), and choose AP over CP (L11) — a slightly stale "Alice → EU" is cheap to be wrong about (region assignments change only on relocation), whereas blocking every request on a strongly-consistent global lookup would re-import the ~90 ms tax onto the common path. Trade: the directory trades perfect freshness for always-available local reads — the right call because the thing it stores barely ever changes.

So the honest picture: residency turns placement from an optimization into a constraint. Estimate sized the two forces — the ~90 ms Atlantic tax (which wants a copy near every user) and the €20M compliance wall (which forbids the copy for personal data) — and showed they live in different units, so the wall wins and reorders everything. Model made home_region the placement key (a legal column, not a hash), added a tiny globally-replicated directory that finds a row's region without moving it, and split data by sensitivity so tokens and aggregates can travel while PII stays home. Tracing Alice at home (fast, compliant), Alice roaming (the request follows her, the data doesn't — ~90 ms tax), and the global join (naive = illegal 6 GB move; legal = ~6 MB of aggregates merged centrally) showed the inversion in action. The first bottleneck — the cross-region query that can't gather immovable rows — is solved by pushing computation to the data and merging anonymous results; around it, cross-region interactions store per-endpoint linked by token, relocations run as expand→cutover→contract migrations (L24), and the directory is an AP fail-static dependency (L34). The standing tension: local latency & compliance vs global query simplicity.

The deepest point: once a law pins a row to a place, location becomes part of the data model, not a knob you turn for speed. For every prior lesson the reflex was "move the data closer to the work." Residency inverts it: keep the data in its legal home and move the work to it, letting only tokens and aggregates cross the border. That single flip explains the whole design — home-region partitioning is the row staying put, the directory is how you find it without moving it, per-region joins that ship aggregates are the work coming to the data, and tokenization is the one safe thing that's allowed to travel. The genuinely new idea is small and sharp: a compliance boundary is a wall, not a cost — you cannot pay to cross it, you can only design so you never need to. The trade to carry: local latency & compliance vs global query simplicity.

The four traps

  • Trap 1 — treating residency as a latency cost. "We'll cache EU users in the US to speed them up" isn't a slow-but-fine trade; it's a violation with a fine attached. A compliance boundary is a wall, not a number on the same axis as milliseconds — you design so you never cross it, you don't "spend" against it.
  • Trap 2 — pooling everything into one global warehouse to make analytics easy. The convenient "just copy all regions' rows to one place and join" moves personal data across borders. Push the computation to each region and merge only anonymous aggregates; the person never crosses, only the total does.
  • Trap 3 — forgetting the directory is a single global dependency. If the "which region owns this user" lookup is slow, strongly-consistent, or centralized, every request pays for it and an outage blocks everyone. Replicate it, make it fail-static, choose AP (L11/L34) — it stores something that barely changes, so stale-but-available is right.
  • Trap 4 — copying a row during relocation and never deleting the old one. Moving a user's home region leaves two live copies unless the old one is deleted — and two copies in two jurisdictions is itself the violation. Relocation is expand→cutover→contract with the delete (L56) as the deliberate, verified, irreversible last step.

Where we landed

We asked a question no prior lesson allowed itself to ask: not "where is a row fastest?" but "where is a row legally allowed to live?" Estimate weighed the ~90 ms Atlantic tax against a €20M compliance fine and found they aren't on the same axis — latency is a cost you can pay, residency is a wall you can't — so the wall reorders the design. Model made home_region a legal placement key (L79), added a tiny personal-data-free directory replicated everywhere to find a row's region without moving it (L34), and split data by sensitivity so tokens and aggregates travel while PII stays pinned (L30). Tracing Alice at home (local, compliant), Alice abroad (the request follows her, the data stays — a ~90 ms roaming tax), and the finance team's worldwide join (naive = an illegal 6 GB cross-border move; legal = ~6 MB of per-region aggregates merged centrally, L21/L29) showed the core inversion: move the computation to the data, not the data to the computation. The first bottleneck — the cross-region query over rows that can't move — is solved by that inversion; around it, cross-region interactions store per-endpoint linked by token, relocations run as expand→cutover→contract (L24/L56), and the directory is an AP fail-static dependency (L11/L34). The deepest point: a compliance boundary is part of the data model, and you design so you never need to cross it. The standing tension: local latency & compliance vs global query simplicity.
