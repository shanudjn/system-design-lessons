Event Sourcing: When the Log of Changes IS the Truth

Two lessons already flirted with this idea and then stopped short. Lesson 25 rejected a mutable balance column and stored an immutable, append-only stream of ledger entries, computing the balance as their SUM — the truth was the history, and the number was derived. Lesson 33 committed a change to the write model and an event to an outbox in one transaction, then shipped that event out to everyone downstream. Lesson 37 used those events to feed read models. In every one of those, the current state was the truth and the events were a side effect — a derived echo of the real thing. Event sourcing turns that around. It says: store the stream of events as the one source of truth, and treat current state as the side effect — something you compute by folding the events back up, exactly the way Lesson 25 folded entries into a balance, but now for every aggregate, not just money. The outbox becomes the database. We'll take one concrete system — the digital wallet from Lesson 25, re-built event-sourced — and watch. We'll estimate the two storage walls it creates (a log that never shrinks, and a fold whose cost grows with an account's history); model the four moving parts (events, the aggregate, the fold, and the append with a version check); trace a command, a query, and a full replay; and hit the first wall — folding a long-lived account on every read — whose fix (snapshots) is Lesson 25's snapshot generalized to "a cached fold." The trade shifts from Lesson 37's read/write shapes to perfect auditability & replayability vs query complexity and unbounded storage.

The one system we'll design

Lesson 25's digital wallet: money that must never be lost, doubled, or un-audited. Back then we stored immutable ledger entries and derived each balance as their sum. Event sourcing takes that instinct and makes it the whole system's storage model, for any kind of state — not just dollars. Instead of a table row that says account 7: balance $100 and gets overwritten on every change, we keep the ordered list of facts that happened to that account and never overwrite anything. The current balance is not stored at all; it's replayed on demand.

  TWO WAYS TO STORE THE SAME ACCOUNT

  (a) STATE-STORED  (the ordinary DB, L37's write model, L33: state is truth)
      account 7:  balance = $100        <- one row, OVERWRITTEN on each change
      history?  gone. how did it reach $100?  unknown. audit?  a separate log you hope is right.

  (b) EVENT-SOURCED  (the log is truth; state is DERIVED by folding)
      account 7's event stream (append-only, immutable, ordered by version):
        v1  AccountOpened     {}
        v2  MoneyDeposited    {amt: 100}
        v3  TransferSent      {amt:  30}
        v4  TransferReceived  {amt:  50}
        v5  MoneyWithdrawn    {amt:  20}
      balance = fold(apply, $0, [v1..v5]) = $100     <- COMPUTED, stored nowhere
      history?  every fact, forever.  audit?  the log IS the audit.

  L33/L37: state is the truth, events are a derived side effect.
  EVENT SOURCING inverts it: events are the truth, state is the derived side effect.

Event sourcing stores the ordered stream of events as the source of truth and derives current state by folding them. "Fold" is just Lesson 25's SUM, generalized: start from an empty state, apply each event in order, and the final value is the current state. Nothing is ever updated in place — the only write is appending a new event to the end. That single constraint is where every property (and every cost) comes from.

Words we'll earn before we lean on them

  • Event — an immutable record of something that already happened, named in the past tense: MoneyDeposited, OrderShipped. A fact, not a command. It is never edited or deleted.
  • Aggregate — the unit you fold events within and enforce a rule across: one account, one order. Its events share an id and are ordered by a version. It's also the consistency boundary (Lessons 6/32).
  • Apply / fold — the pure function apply(state, event) → state, run left-to-right over an aggregate's events to compute its current state: state = events.reduce(apply, empty).
  • Append — the only write: add a new event at the aggregate's next version. Guarded by an expected version so two concurrent writers can't both win (Lesson 6's compare-and-set).
  • Snapshot — a cached fold: the state as of version N, stored so a read folds only the events after N instead of from the start. Derived, disposable, rebuildable (Lesson 25's snapshot).
  • Projection / read model — Lesson 37's read side: consume the event stream to build a query-shaped view (a table, an index). How you answer "current state?" without folding.
  • Replay — re-reading the log from the start to rebuild any state or read model (Lessons 9/29/33's kappa). The superpower event sourcing hands you for free.

Move 1 — Estimate: two walls, both about storage

State-stored databases have one copy per entity, so their size tracks the number of entities and is roughly flat. An event-sourced store keeps every change forever, so its size tracks the number of changes — and it only ever grows. Two numbers matter: how fast the log grows, and how expensive the fold gets.

Worked: the log that never shrinks. The orders/wallet service runs at Lesson 37's 5,000 writes/s, and in event sourcing every write is one appended event. Say an event is ~300 B (type + aggregate id + a small JSON payload + metadata). Growth = 5,000 × 300 B = 1.5 MB/s = ~130 GB/day ≈ 47 TB/year, and because events are immutable it never shrinks — you don't overwrite, you accumulate. Contrast the state-stored write model: ~100M orders × ~1 KB = ~100 GB, roughly constant. Event sourcing trades near-constant state storage for an ever-growing log. That's the price of total history — and it's usually affordable (disk is cheap), but it's real and it's forever.

Worked: the fold that grows with history. The other wall isn't total size — it's one aggregate's size. A quiet account has 5 events; folding it is instant. But Lesson 25's hot merchant account accumulates one event per transaction and reaches 100M events. To answer "what's your balance?" you fold all of them. At an in-memory apply rate of ~5M events/s (~200 ns each), that's 100,000,000 ÷ 5,000,000 = 20 seconds to load the account — per read. A state-stored DB answered the same question with one 0.4 ms row read (Lesson 12). Deriving state is cheap only while an aggregate's history is short. This is the wall Move 4 knocks down.

Name the trade-off — storing events vs storing state. State-stored keeps one current value: tiny, instantly readable, but it has thrown the history away — you cannot ask "how did we get here?", "what was the balance last Tuesday?", or "replay this to build a new view", because the only facts you kept are the latest ones. Event sourcing keeps every value that ever was: perfect audit, free time-travel, any view rebuildable by replay — paid for in a log that grows without bound and a "current state" that costs a fold. You are choosing total history at the cost of storage and derivation, versus a cheap current value at the cost of amnesia. Most systems don't need the history and should stay state-stored; the ones that do — money, compliance, anything where "why?" is a real question — are exactly where event sourcing earns its keep.

Move 2 — Model: events, an aggregate, a fold, and a guarded append

Four parts. The events are the truth; the aggregate is where you fold them and enforce a rule; the fold turns events into state; the append is the one write, guarded so concurrency can't corrupt the rule.

Events — immutable facts, past tense. AccountOpened, MoneyDeposited{amt}, MoneyWithdrawn{amt}. Each is something that already happened, so it is never changed or deleted — a wrong event is corrected by appending a new one (a compensating event, Lesson 25's refund / Lesson 32's compensation), never by editing the past. Editing an event would rewrite history and silently break every snapshot and read model derived from it.

The aggregate — the fold boundary and the rule boundary. One account's events share its id and are ordered by version (1, 2, 3…). The aggregate is both the thing you fold into a state and the boundary an invariant is enforced across (balance ≥ 0). Draw it at the true invariant — small enough that a fold is cheap and one writer owns it, large enough to hold the rule (Lessons 6/32).

The fold and the guarded append. To make a decision you fold the aggregate to its current state, check the rule, and append the resulting event at the next version — but only if no one else has appended in the meantime. That version check is Lesson 6's compare-and-set: two concurrent withdrawals both read version 5, both try to write version 6, and the store lets exactly one through. The other retries against the new truth. No lock (Lesson 22), just an atomic append-if-version-matches.

Here is the fold made completely concrete — the Base62-style walk-through, but for state instead of ids:

  FOLDING account 7's events into a balance (apply left-to-right from $0):

    start                                     state = $0
    v1  AccountOpened     {}       apply -->  state = $0
    v2  MoneyDeposited    {amt:100} apply -->  state = $0 + 100 = $100
    v3  TransferSent      {amt: 30} apply -->  state = $100 - 30 =  $70
    v4  TransferReceived  {amt: 50} apply -->  state =  $70 + 50 = $120
    v5  MoneyWithdrawn    {amt: 20} apply -->  state = $120 - 20 = $100

    current balance = $100   -- COMPUTED, stored nowhere; the events are the truth.

  A SNAPSHOT is just a cached fold you can start from:

    snapshot @ v4 = {version:4, balance:$120}   (derived, rebuildable -- NOT the truth)
    balance = snapshot($120) then fold only [v5]:  $120 - 20 = $100
            -> folded 1 event instead of 5, and got the identical answer.

Name the trade-off — event sourcing vs the outbox (Lesson 33), and vs CQRS (Lesson 37). Lesson 33's outbox stored current state as the truth and wrote an event as a derived side effect in the same transaction. Event sourcing inverts that: the event is the truth and state is the derived side effect — "the outbox becomes the database." And note what event sourcing is not: it is not CQRS. CQRS (Lesson 37) is about having many read shapes; event sourcing is about how the write side stores truth. You can do either without the other. But they marry perfectly — an event-sourced write side emits exactly the event stream CQRS's projections want to consume — which is why they're so often seen together and so often confused. Event sourcing decides what the truth is (the log); CQRS decides how you read it (many projected shapes).

Move 3 — Trace the paths

Three runs: a command that must enforce a rule, a query that must not fold, and a replay that rebuilds a view from nothing.

Path A — a command (withdraw $20, balance must never go negative)

  POST /accounts/7/withdraw {amt: 20}

   1. LOAD: read snapshot (v4, $120) + fold events since it ([v5]) -> state {balance:$100, version:5}
        (the fold happens on the COMMAND side, only to make a correct decision)
   2. DECIDE against the invariant: $100 - $20 = $80 >= 0  -> allowed.
        produce event  MoneyWithdrawn{amt:20}
   3. APPEND with expectedVersion=5:  store does an atomic check --
        if account 7 is still at v5, write this as v6;  else CONFLICT -> reload & retry.
        (L06 compare-and-set: two concurrent withdrawals can't BOTH become v6.
         One wins v6, the other reloads at v6, re-checks the rule, retries.)
   4. The appended event is the ONLY write. Downstream, projections (L37) update
        the read models and, every N events, a new snapshot is written -- all async.

Notice the invariant was enforced with no lock (Lesson 22): fold to decide, append-if-version-unchanged to commit. Two people racing to overdraw the account can't both succeed, because only one append can land at version 6.

Path B — a query (what's the balance? who's overdrawn?) — do NOT fold

  GET /accounts/7/balance        -> read a PROJECTION (L37): a plain {account -> balance}
                                    table kept current by consuming the event stream. ~0.4 ms.
  GET /reports/overdrawn         -> read a PROJECTION: an index of accounts where balance < 0.
                                    The event LOG cannot answer this -- you can't
                                    "SELECT ... FROM a stream of facts".

  Folding is for the COMMAND side (decide + append). Queries are served by read
  models projected from the events -- this is why event sourcing needs CQRS (L37)
  to answer "current state?" at all.

Path C — a replay (build a brand-new read model, or time-travel)

  New requirement: "monthly-spend per account." No migration, no backfill script --
   just a new projection that reads the log FROM v1 and folds spend as it goes (L09/29/33 kappa).

  Audit / time-travel (free, because every fact was kept):
   "balance on 2026-01-01?"  ->  fold events with timestamp <= that date. A state-stored
   DB threw those facts away and simply cannot answer this. Event sourcing replays them.

Path A shows the discipline (fold to decide, guarded append to commit); Path B shows the catch (you can't query a log, so you must project — event sourcing needs CQRS to be usable); Path C shows the payoff (any new view is a replay away, and history is queryable across time). But look back at Path A step 1: for the hot account, "fold events since the snapshot" is cheap — but only because of the snapshot. Without it, step 1 was the 20-second fold from Move 1. That's the wall.

Move 4 — Find the first bottleneck: folding a long-lived aggregate

The command side must fold an aggregate to its current state before every decision. For a short-lived aggregate (an order with 8 events) that's free. For a long-lived one (Lesson 25's hot account at 100M events) it's the 20-second load from Move 1 — and it happens on every single command. The fix is Lesson 25's snapshot, now stated generally: a snapshot is a cached fold. Periodically store the folded state at version N; then a load reads that snapshot and folds only the events after it.

Worked: the snapshot's payoff. Hot account, 100M events. Fold-from-zero = 100M ÷ 5M/s = 20 s. Snapshot every 1,000 events: a load reads the latest snapshot (at, say, v99,999,000) and folds at most 1,000 events = 1,000 × 200 ns = 0.2 ms. That's a 20 s → 0.2 ms = ~100,000× cut, back to state-stored read speeds. The snapshot interval is the dial: snapshot more often → smaller folds but more snapshot storage/writes; less often → cheaper storage but longer tails.

Why it's safe. A snapshot is derived, never the truth (Lesson 25's rule, and Lesson 37's read model). If a snapshot is wrong, corrupt, or you change the apply logic, you throw it away and rebuild it by replaying the events — the log is still the sole source of truth. The snapshot is a cache in front of a fold, exactly as Lesson 2's cache sat in front of a database.

Name the trade-off — derivation speed vs a cache that can go stale. The snapshot buys read/decision speed with storage and a small correctness burden: it's another derived thing you must keep current and be willing to discard. That's the same shape as every accelerator in this course (Lesson 2's cache, Lesson 15's precomputed feed, Lesson 25's balance snapshot) — speed by keeping a derived copy, correctness by remembering the copy is never the truth and can always be rebuilt from the log.

Past the fold, three more walls define whether event sourcing is a good fit here:

  THE THREE WALLS AFTER THE FOLD

  1. "How do I query current state?"  You can't SELECT over a log.
        -> PROJECT to read models (L37 CQRS). Event sourcing without CQRS is nearly unusable
           for queries. This is THE reason the two patterns travel together.

  2. Event schemas are FOREVER.  A 3-year-old MoneyDeposited event must still deserialize
        after you refactor the code that wrote it.
        -> VERSION events and UPCAST old shapes on read (add v2 with a currency field;
           an upcaster turns a stored v1 into a v2 in memory). Events are a forever contract
           (L18 additive-only, L24 expand/contract, L33 don't couple consumers to raw schema).

  3. The log grows without bound (Move 1: 47 TB/yr, never shrinks).
        -> For streams that must be trimmed, snapshot + ARCHIVE cold events to object storage
           (L20), or (where allowed) fold-and-drop a closed aggregate. But dropping events
           forfeits the audit/replay you adopted event sourcing FOR -- trim reluctantly.

The four traps

  • Trap 1 — mutating or deleting an event to "fix" a mistake. An event is a fact that happened; editing it rewrites history and silently corrupts every snapshot and read model folded from it. Correct a mistake the way a ledger does — append a compensating event (Lesson 25's refund, Lesson 32's compensation). The wrong fact and its correction both stay in the log, which is what keeps the audit honest.
  • Trap 2 — folding the whole log on every read (no snapshot). This turns an O(1) read into O(history) and makes a hot aggregate a 20-second load (Move 1). Snapshot the command side, and serve queries from projected read models (Lesson 37), never from a live fold of the entire stream.
  • Trap 3 — an aggregate drawn too big. One giant "Bank" aggregate that every transaction appends to serializes all writes through one version counter — Lesson 6's contention, Lesson 22's serial gate. Draw the aggregate at the real invariant boundary (one account), keep it small so folds are cheap and one writer owns it, and make cross-aggregate consistency a saga (Lesson 32), not a bigger aggregate.
  • Trap 4 — events coupled to your current code. Storing events as raw serialized objects that change with the code means old events won't deserialize after a refactor — you've made an immutable, forever record depend on a moving schema. Treat the event as a versioned, additive-only contract and upcast old shapes on read (Lessons 18/24/33). Future-you must be able to read past-you's events for as long as the log exists.

Where we landed

We took the instinct Lesson 25 showed with its ledger — keep the immutable history, derive the number — and made it a general storage model. The digital wallet, event-sourced, stores the ordered stream of events as its one source of truth and computes current state by folding them, inverting Lessons 33/37 where state was the truth and events a side effect ("the outbox becomes the database"). Estimate named two storage walls: a log that grows ~130 GB/day ≈ 47 TB/year and never shrinks (vs a state DB's flat ~100 GB), and a fold whose cost grows with one aggregate's history — 20 seconds to load Lesson 25's 100M-event hot account. Model gave four parts: immutable past-tense events (corrected by appending, never editing), the aggregate as both fold boundary and invariant boundary, the fold (state = events.reduce(apply, empty), walked through $0→$100), and the guarded append that enforces a rule with Lesson 6's compare-and-set instead of a lock. Tracing showed a command fold-to-decide then append-if-version-matches (no lock, no double-spend), a query served from a projected read model because you cannot query a log (which is why event sourcing needs CQRS), and a replay that builds any new view — or answers "the balance last Tuesday" — for free because every fact was kept. The first bottleneck, folding a long-lived aggregate on every command, falls to a snapshot — Lesson 25's snapshot generalized to "a cached fold," a 100,000× cut that stays safe because a snapshot is derived and rebuildable, never the truth. Past it: you must project to answer queries (CQRS), version-and-upcast events because their schema is forever, and accept an unbounded log as the price of total history. The real lesson: choose whether your truth is the latest value or the whole history — event sourcing keeps the history and derives the value, buying perfect audit, time-travel, and replay-any-view at the cost of unbounded storage and a "current state" that must be folded and projected. Perfect auditability & replayability vs query complexity and storage.

Next lesson follows the log where it inevitably leads — the data grows forever, so not all of it can live on fast disk:

• Tiered storage & data lifecycle: the event log (this lesson), the object pile (Lesson 20), and the warehouse (Lesson 29) all grow without bound, but a 3-year-old event is read a thousand times less often than yesterday's (Lesson 2's access skew, again). Move data hot → warm → cold → archive (RAM → SSD → HDD → object store → glacier) by age and access frequency, governed by TTL/retention policies — and meet the retrieval-latency cliff of the cold tiers, where reading an archived byte can take minutes. The trade shifts from auditability to storage cost vs retrieval latency and operational policy.
