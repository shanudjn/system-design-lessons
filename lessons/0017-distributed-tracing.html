Distributed Tracing: Finding the Slow Hop in a 20-Service Request

Lesson 16 ended with a search request that now fans out across a parser, a retrieval service, a re-ranker, and a feature store. Here is the problem that creates: the search box's average response is a healthy 44 ms, but 1 shopper in 100 waits almost a full second — and no single service's dashboard shows anything wrong. Each of the 20 services it touches looks fast. So which hop ate the time? You can't answer that from per-service metrics, because none of them can see the request as one connected thing. This lesson takes that one slow request and traces it end to end: estimate why you can't just log everything, model the request as a tree of timed spans stitched by one trace ID, trace the waterfall to spot the culprit, and hit the bottleneck that forces every large system to choose which traces to keep. The trade-off underneath: observability cost vs coverage.

The one system we'll trace

The search backend from Lesson 16, in production. One user query — red running shoes — enters an API gateway and fans out: auth check, query parser, retrieval (the inverted index), re-ranker (the ML model), and a feature store the re-ranker reads from. About 20 service calls in all. Most requests come back in ~40 ms. A few come back in ~950 ms, and the user who waited has no idea why — neither do you, from the outside. Here is the whole idea on one screen.

  time ──────────────────────────────────────────────────────────▶  (ms)
  [ api-gateway ============================================= ] 950   ← root span
    [ auth = ]                                                    4
    [ parser == ]                                                 6
    [ retrieval ==== ]                                           45
    [ re-ranker ======================================= ]       890   ← where did it go?

        [ feature-store call  #2  = ]  8ms   ...100 calls, one       │ 800 ms

                                                                 └────────────┘
                                                                 the SLOW HOP

  A span = one unit of work: {trace_id, span_id, parent_id, name, start, duration}
  A trace = all spans sharing one trace_id, linked parent→child into a tree.
  The picture above is that tree drawn on a time axis = a "waterfall."

A metric tells you the system is slow; a trace tells you where. The re-ranker's own work (model-scoring) is only 90 ms. The other 800 ms is spent making 100 separate calls to the feature store, one after another — a fan-out hidden inside one service. No per-service dashboard reveals this, because from the feature store's point of view each of those 100 calls was a fast, healthy 8 ms. Only by stitching them into one request — one trace — does the 800 ms of serial waiting become visible. That stitching is what distributed tracing does.

Words we'll earn before we lean on them

  • Span — one timed unit of work: a service handling a request, or one outbound call. It records a name, a start time, a duration, and who its parent was.
  • Trace — all the spans for one request, sharing one trace ID, linked into a tree by parent pointers. The request's whole story.
  • Trace context propagation — passing the trace ID + current span ID across every service boundary (usually as request headers) so the next hop can attach its span to the right parent.
  • Waterfall — the trace drawn on a time axis: each span a horizontal bar. Gaps and long bars are where the time went.
  • Sampling — keeping only some traces, because keeping all of them costs too much. Head-based decides at the start; tail-based decides after seeing the whole trace.
  • Percentile (p50 / p99) — p99 = the latency that 99% of requests beat. The number that describes the tail the average hides.
  • The three pillars — metrics (cheap aggregate numbers), logs (per-event text), traces (per-request causal structure). Different jobs.

Move 1 — Estimate: why you can't just keep everything

The naïve fix is "record every span of every request forever, then search it when something's slow." Let's price that against the search service's real traffic.

Worked: the raw firehose of spans.

• Search handles 50,000 requests/second at peak.
• Each request fans out to ~20 spans (gateway, auth, parser, retrieval, re-ranker, 100 feature-store calls collapsed here to a typical 20 on the average request).
• So: 50,000 × 20 = 1,000,000 spans/second.
• A span with its name, timings, and a few tags is ~500 bytes.
• 1,000,000 × 500 B = 500 MB/second = 43.2 TB/day.

Storing and indexing 43 terabytes a day, forever, to occasionally debug one slow request, is absurd — it would cost more than the search service itself. So you sample: keep 1 trace in 100. 43.2 TB/day × 1% = 432 GB/day — large but sane. This is the core tension of observability: you cannot afford to see everything, so you must choose what to keep — coverage vs cost.

Name the first trade-off — observability cost vs coverage. The more you record, the more you can debug, and the more you pay to store, index, and query it. Sampling buys affordability by throwing away most traces. But that raises the question that will become our final bottleneck: if you keep a random 1%, and the slow requests are a rare 1%, you'll usually throw the interesting one away. Hold that thought.

Why metrics alone can't do this job

Couldn't we skip traces and just watch metrics — a latency number per service? Metrics are cheap because they're aggregates: "the feature store served 8 ms at p50 this second" is one number for millions of calls. That's their strength and their blindness. An aggregate has no per-request identity — it can't tell you that these particular 100 feature-store calls all belonged to one slow search. Metrics tell you that something is slow and roughly where; only a trace, which keeps each request as a connected object, tells you the causal chain. That's why you need all three pillars, not one.

Move 2 — Model: a request is a tree of spans

To see a request as one thing, every hop must agree on an id and record its slice of time. Two pieces of machinery make that work.

Piece 1 — the span, and the trace ID that binds them

When the request enters the gateway, it gets one trace ID — a random 128-bit number, say 7f3a…. The gateway opens the root span. Every unit of work below it opens a child span that records four things: the same trace ID, its own new span ID, its parent's span ID, and {name, start, duration}. Because each span points at its parent, the flat list of spans reassembles into the exact tree — no service needs to know the whole shape, only its own parent.

  span records (flat list, arriving from 5 different machines):

   {trace:7f3a, span:01, parent:  —, name:api-gateway, start:0,   dur:950}
   {trace:7f3a, span:02, parent:01, name:auth,         start:1,   dur:4}
   {trace:7f3a, span:03, parent:01, name:parser,       start:6,   dur:6}
   {trace:7f3a, span:04, parent:01, name:retrieval,    start:13,  dur:45}
   {trace:7f3a, span:05, parent:01, name:re-ranker,    start:59,  dur:890}
   {trace:7f3a, span:06, parent:05, name:feature-get,  start:60,  dur:8}   ← ×100
   ...
              │  group by trace, link parent→child  │
              ▼
   the waterfall tree at the top of this page — rebuilt from parent pointers

Piece 2 — propagation: the id must cross the wire

Here is the part that makes it "distributed." When the re-ranker calls the feature store, the feature store is a different process on a different machine — it has no idea it's part of trace 7f3a unless someone tells it. So the re-ranker attaches the trace ID and its own span ID to the outbound call, as headers (the open standard is traceparent, e.g. 00-7f3a…-0000005-01). The feature store reads those headers, opens its span with parent = 05, and passes its own context onward. Trace context propagation is the whole trick: one id, carried across every boundary, is what lets 20 independent services describe a single shared request. Miss the propagation on one hop and the trace breaks — the spans past that point become orphans with no parent, and your waterfall has a hole exactly where you most need it.

Name the trade-off: instrumentation cost vs visibility. Propagating context and emitting spans adds a little code to every service and a few bytes to every call. Skip it on the hot path and that service becomes a blind spot — a bar you can't draw. The discipline is that tracing is only as complete as its least instrumented hop, so it's an all-or-nothing investment across a request path.

Move 3 — Trace the paths

Path A — the mean lies; the tail is the story

Start with why the dashboard looked fine. Suppose 99 of every 100 searches take 35 ms and 1 takes 950 ms. The average is:

Worked: what the mean hides.

mean = (99 × 35 ms + 1 × 950 ms) / 100 = (3,465 + 950) / 100 = 44.15 ms

The average barely twitches — 44 ms looks great — yet 1% of your users wait almost a full second. The mean is dominated by the many fast requests and drowns the few slow ones. That's why you watch percentiles: p50 = 35 ms (the typical request) but p99 = 950 ms (the tail). The gap between p50 and p99 is the pain your average is hiding. You alarm on p99, not the mean — the mean tells you the common case is fine while a real slice of users suffers.

Path B — reading the waterfall to find the culprit

Now take one of those p99 traces and open its waterfall (the picture at the top). Read it top-down: gateway 950 ms total, auth 4, parser 6, retrieval 45 — all healthy. The re-ranker bar is 890 ms and swallows nearly the whole request. Expand it: model-scoring is only 90 ms, but underneath sit 100 feature-store spans of 8 ms each, laid end to end. 100 × 8 ms = 800 ms of pure serial waiting. That's the N+1 pattern: the re-ranker fetches features one document at a time in a loop instead of asking once for all 100. The trace didn't just say "the re-ranker is slow" — it showed the shape of the slowness (many small serial calls), which points straight at the fix.

Worked: the fix the trace suggests. Replace 100 serial single-key reads with one batched call for all 100 keys. A batch fetch of 100 keys costs, say, 8 ms once (not 800 ms).

• Before: gateway 5 + auth 4 + parser 6 + retrieval 45 + (800 serial + 90 model) = 950 ms
• After:  5 + 4 + 6 + 45 + (8 batched + 90 model) = 158 ms

A ~6× cut to the p99, from one insight the waterfall handed you — and one you could never have gotten from the feature store's own dashboard, where all 100 calls looked like healthy 8 ms hits. This is the payoff of per-request causal structure.

Path C — why fan-out makes the tail everyone's problem

Here's the deeper reason the tail matters so much when a request touches many services. Suppose each of the 20 services is individually great: only 1% of its calls are slow. What fraction of whole requests hit at least one slow hop?

Worked: tail amplification under fan-out.

A whole request is fast only if every hop is fast: P(all 20 fast) = 0.99²⁰.
0.99²⁰ ≈ 0.818, so P(≥1 slow hop) = 1 − 0.818 = 0.182 ≈ 18%.

Even though every single service is "99% fast," nearly 1 request in 5 is slow — because it only takes one of the 20 hops to stall. Fan-out multiplies your exposure to rare slowness: the more services a request touches, the fatter its tail. This is why p99 of the whole request is far worse than p99 of any one service — and why you can't debug it without a trace that spans all 20.

Move 4 — Find the next bottleneck: sampling drops the trace you needed

Return to the thread from Move 1. We keep 1 trace in 100 to afford it. But watch what that does to debugging.

Wall 1 — head-based sampling is blind to what's interesting

Worked: the coin flip happens too early. Head-based sampling decides at the start of the request — flip a weighted coin at the gateway, keep this trace with probability 1%, and that decision rides along in the propagated context so every hop agrees. Cheap and simple. But the decision is made before anyone knows whether the request will be slow or error. The slow requests are ~1% of traffic; your sample is a random 1%. So the chance a given slow request is also sampled is 1% × 1% = 0.01% — you keep roughly 1 in 10,000 of exactly the traces you'd want to look at. When the on-call engineer goes hunting for a p99 trace, it's almost never there.

Trade-off: head sampling is cheap because it decides early, but deciding early means deciding blind — you can't keep the slow/error traces because you don't know yet which they are.

Wall 2 — tail-based sampling keeps the right ones, at a price

The fix is to decide late. Tail-based sampling buffers all the spans of a trace until the request finishes, then applies a rule: keep it if it was slow (> 500 ms) or errored; otherwise keep only 1% of the boring fast ones. Now every slow request is retained and the on-call always has a trace to open. The cost is real, and it's the trade-off: you must hold every trace in memory long enough to see its outcome, and gather all of a trace's spans — which arrive from 20 different machines — in one place to judge it. That's a heavier, stateful collector. Trade-off named: head sampling is cheap but blind; tail sampling is smart but must buffer and centralize every trace before choosing — you pay memory and coordination to stop throwing away the traces that matter.

Wall 3 — the metric side has its own cliff: cardinality

One more trap, on the metrics pillar. It's tempting to tag every metric with rich labels — user_id, query_text, product_id — so you can slice finely. But a metric's cost scales with its number of unique label combinations (its cardinality): one time-series is stored per combination. Tag latency by user_id across 50 million users and you've created 50 million time-series for one metric — a memory explosion that can take down your monitoring system. Trade-off: metric granularity vs cardinality cost — high-cardinality identifiers (user, request, id) belong on traces (kept per-request, sampled), never on metrics (kept per-label-combo, forever). This is the clean division of labor between the three pillars: metrics for cheap aggregate trends, traces for expensive per-request detail.

Where we landed

We took one slow request — 950 ms at p99 while the mean sat at a healthy 44 ms — and found the hop that ate the time. Estimate showed why you can't keep everything: 50k req/s × 20 spans × 500 B = 43 TB/day, so you sample, and named the tension — observability cost vs coverage. Model built the request as a tree of spans bound by one trace ID, reassembled from parent pointers, and stressed the trick that makes it distributed: trace-context propagation across every boundary, whose weakest hop is a blind spot. Tracing the paths showed the mean lies (99×35 + 950 → 44 ms hides a 950 ms tail), read the waterfall to expose an N+1 of 100 serial 8 ms feature-store calls (800 ms → one 8 ms batch = a 6× cut), and proved with 1 − 0.99²⁰ ≈ 18% why fan-out fattens the tail until it's everyone's problem. The next bottleneck was sampling itself: head-based sampling decides early and blind, keeping the slow trace only 1 in 10,000 times, so large systems move to tail-based sampling — buffer the whole trace, then keep the slow and errored ones — paying memory and coordination to stop discarding the traces that matter; and on the metrics side, keep high-cardinality ids off labels. The thread: metrics say something is wrong, traces say where, and every observability decision is some version of "you can't afford to see everything, so choose what to keep — and choose it late enough to be the right thing."
