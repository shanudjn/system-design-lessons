Multi-Level Caching: One Write Down Three Layers

Lesson 2 taught us one cache in front of the database. Real systems stack several: a tiny in-process cache living inside each app server (nanoseconds away), a shared Redis tier every server can reach (half a millisecond away), the database that is the actual truth (ten milliseconds away), and a CDN at the edge for anything public (Lesson 14). Reads are easy — you fall down the layers until something answers, and the picture from Lesson 2 mostly holds. The hard question is the one nobody asks until it bites: when a value changes, what does a write do? Push it all the way down to the database before you say "done" (write-through: safe, slow)? Acknowledge instantly and flush to the database later (write-back: fast, loses data on a crash)? Or skip the cache entirely on writes (write-around)? We open on the number that makes this real: a "viewers watching now" counter ticking 2,000 times a second on one hot product — write it through and you've just aimed 2,000 writes/sec at a single database row (Lesson 6's hot-row wall); write it back and it's one write per second, 2,000× fewer, at the price of losing up to a second of counts if the box dies. We'll estimate the latency of the layered read and the cost of each write policy. We'll model the hierarchy and the three write policies as one decision. We'll trace a price change, a hot counter, a crash, and a bulk import through the stack. And we'll find the first bottleneck: coherence — two hundred app servers each holding their own copy, and a write that updates the database but leaves 199 of them serving yesterday's price. The trade under all of it: read/write latency vs durability & coherence.

The one system we'll build

An e-commerce site. 50 million products, a fleet of 200 app servers (Lesson 27) serving 40,000 page-reads/second. Two kinds of data flow through the same product page and behave nothing alike. A price is read constantly and written rarely, and it must be correct — showing a customer the wrong price is a real problem. A "viewers watching now" counter is written furiously — thousands of increments a second on a hot item — and if we lose a few of those counts nobody is harmed. Our job: put a cache hierarchy in front of the database so reads are fast, and decide, for each kind of write, how far down the stack the write must travel before we call it done — because that one choice sets the write's latency, its durability if a machine crashes, and whether every server agrees on the current value. The adversary here isn't an attacker; it's staleness — a copy of the truth that quietly stopped being true.

The one idea the whole lesson turns on: a cache is a copy of the truth, and every copy can be wrong. Reads only ever read copies, so a stale copy costs you a wrong answer. But a write changes the truth, and now every copy of the old value is a lie waiting to be served. So the entire design is: how many copies do we keep, and what does a write do to all of them? Write-through, write-back, and write-around are three answers to "how far down does the write go before we say done" — and the coherence machinery (TTLs, invalidation) is the answer to "how do the other copies find out." Everything below is those two questions, made concrete.

Words we'll earn before we lean on them

  • Cache tier / level (L1, L2) — one layer of cache. L1 = the fastest, smallest, closest (here, in-process). L2 = larger, slightly slower, shared (here, Redis). The names come from CPU caches, where the same idea was invented.
  • In-process cache — a cache living inside the app server's own memory (a hash map). Nanoseconds to read, but each server has its own — so 200 servers = 200 independent copies.
  • Backing store / origin / source of truth — the layer a cache sits in front of and defers to. Here the database. The one copy that is, by definition, correct.
  • Hit ratio — fraction of reads a tier answers itself (Lesson 2). A tier's job is to raise its own hit ratio so the slower tier below is rarely touched.
  • Write-through — a write updates the cache and the backing store synchronously; you don't acknowledge until the truth is updated. Safe, but you pay the slow tier's latency on every write.
  • Write-back (write-behind) — a write updates only the cache, marks the entry dirty, acknowledges immediately, and flushes to the backing store later (batched/async). Fast, and it coalesces repeat writes — but un-flushed data dies with the cache.
  • Write-around — a write goes straight to the backing store and skips the cache (the stale entry is invalidated). Avoids filling the cache with data that won't be read soon.
  • Dirty entry — a cached value that has been changed but not yet written to the backing store. Only exists under write-back. It's the data you lose in a crash.
  • Flush — writing dirty entries down to the backing store, on a timer or a threshold.
  • RPO (recovery point objective) — how much recent data you're willing to lose in a crash, measured in time. Write-back's flush interval is your RPO.
  • Cache coherence — all copies of a value agreeing. Broken the instant one copy changes and the others don't hear about it.
  • Invalidation — telling a cache "this entry is stale, drop it" so the next read re-fetches the truth (Lesson 2/48). Pub/sub invalidation = broadcasting that message to every server's L1.
  • TTL (time-to-live) — an expiry stamped on a cache entry; after it, the entry is discarded and re-fetched. A crude, automatic coherence knob.
  • Inclusive vs exclusive — whether an item in L1 is also kept in L2 (inclusive: simple, duplicated) or lives in exactly one tier (exclusive: more total capacity, more complex).

Move 1 — Estimate: the layered read, and the price of each write

Three numbers set everything: how fast the layered read is, how much slower write-through is than write-back, and how many writes write-back can swallow before touching the database.

The read: falling down the layers. Rough per-tier latencies in one datacenter: L1 ≈ 100 ns = 0.0001 ms, Redis ≈ 0.5 ms, DB ≈ 10 ms. Suppose L1 answers 90% of reads, Redis answers 90% of the rest, and the database catches the last sliver. The average read latency is each tier's latency weighted by how often you reach it:

  • 0.90 × 0.0001 = 0.00009 ms  (L1 hits)
  • 0.09 × 0.5    = 0.045 ms  (fall to Redis)
  • 0.01 × 10     = 0.100 ms  (fall to the DB)
  • Total ≈ 0.145 ms per read, versus 10 ms if every read hit the database raw — a ~69× speed-up, and the database sees only 1% of the read traffic (400 reads/s instead of 40,000).

Notice where the time goes: the 1% of reads that reach the database contribute 0.100 ms — more than two-thirds of the average, from one-in-a-hundred reads. That's the tail (Lesson 17): each tier exists to shrink how often you pay the tier below it.

The write: how far down decides the latency. The same tier latencies, but now a write must reach some depth before we acknowledge:

PolicyWrite reaches…Ack latencyOn crash
Write-throughRedis + DB, synchronously0.5 + 10 ≈ 10.5 msnothing lost — DB is current
Write-backRedis only; DB flushed later≈ 0.5 ms (21× faster)un-flushed writes lost
Write-aroundDB only; cache skipped≈ 10 msnothing lost; next read misses

Write-back is ~21× faster to acknowledge than write-through, and that gap is the entire reason it exists — but the speed is borrowed against durability, and the loan comes due in a crash.

The coalescing win: 2,000 writes become 1. Take the "viewers watching now" counter on one hot product during a flash sale — 2,000 increments/second. Under write-through, that's 2,000 writes/second hammering a single database row — exactly Lesson 6's hot-row wall, and no amount of caching in front helps because you insisted every write reach the bottom. Under write-back, the increments accumulate in Redis and we flush the current value once per second: the database sees 1 write/second for that row — 2,000× fewer writes — and the value it stores is just as correct one second later. Write-back didn't only make writes faster; it collapsed 2,000 writes into 1 because a counter written twice before a flush only needs its final value persisted. The trade named: we traded up to one second of durability (a crash loses that second's un-flushed increments) for surviving a write rate the database physically could not.

Move 2 — Model: the hierarchy, and three answers to "how far down?"

Why more than one cache tier at all?

Each tier fixes a weakness of the one below and inherits a weakness of its own:

  • L1 (in-process) is the fastest — a memory read, no network, ~100 ns — and it takes load off Redis. Its weakness is the whole lesson: it is per-server and not shared, so 200 servers hold 200 independent copies that can disagree. It's also small (you can't fit 50M products in each server's heap), so it holds only the hottest keys.
  • L2 (Redis) is shared — one logical copy every server reads, so it's the tier where "the cached value" is unambiguous — and big enough for a broad working set. Its weakness is a network hop (~0.5 ms) and being a hot dependency of its own (shard/replicate it, Lesson 4/6).
  • DB is the truth: durable, correct, and slow. Its weakness is that it can't take 40,000 reads/second cheaply — which is why the tiers above exist.
  • CDN (Lesson 14) sits in front of everything for public, identical-for-everyone responses (a product image, a cacheable page fragment), absorbing reads before they ever reach your datacenter.

The trade named: each tier you add buys latency and offload but adds one more copy to keep coherent. More tiers = faster reads and less load below, paid for in more places the truth can go stale.

The three write policies, as one decision

Reads (from Lesson 2) come in two flavours — cache-aside (the app checks the cache, and on a miss loads from the DB and fills the cache) and read-through (the cache loads on a miss itself). Both just populate copies. The interesting choice is on the write, and it's a single question — how far down must the write travel before we acknowledge, and does the cache get the new value or just lose the old one?

PolicyWhat it doesBuysCostsUse when
Write-throughupdate cache + DB together, ack after the DBthe truth is always current; no data loss; cache stays warm & correctevery write pays the DB's latency; can't absorb write bursts on a hot rowcorrectness-critical, read-soon data: prices, profiles, balances
Write-backupdate cache only, mark dirty, ack now, flush to DB latertiny write latency; coalesces repeat writes (2,000→1); absorbs burstsa crash loses un-flushed writes (RPO = flush interval); coherence is harder (truth is only in the cache)high-frequency, loss-tolerant, reconstructable: counters, metrics, "last seen"
Write-aroundwrite straight to the DB, skip/invalidate the cachedoesn't pollute the cache with data that won't be read; the DB is currentthe just-written value is a guaranteed cache miss on its first readwrite-once-read-rarely, or bulk writes: imports, logs, archival records

These aren't global settings — you pick per kind of data. Our one product page uses write-through for the price and write-back for the counter, in the same request. The through-line: write-through spends latency to buy durability; write-back spends durability to buy latency; write-around spends a first-read miss to buy a clean cache.

Why write-back is dangerous in a way write-through never is: under write-through the database is always at least as fresh as the cache, so the cache is a pure accelerator — lose it entirely and you've lost nothing but speed (Lesson 26's "make the fast path disposable"). Under write-back the cache briefly holds the only copy of the newest truth. It has stopped being an accelerator and become, for those dirty entries, the source of truth — an un-replicated, in-memory source of truth. That is why write-back is right for a view counter (lose a second of counts, shrug) and catastrophic for a bank balance (lose a deposit). The trade named: write latency vs durability — and the currency you spend is "how much recent truth am I willing to have existed only in volatile memory."

Inclusive or exclusive: is an L1 entry also in L2?

One more structural choice. When L1 caches a product, does L2 also keep it (inclusive), or does an item live in exactly one tier (exclusive)?

  • Inclusive — everything in L1 is also in L2. Simple: L2 is a superset, so evicting from L2 also means invalidating L1, and coherence logic has one clear place to hook. The cost is duplication — the hottest keys sit in both tiers, so your total distinct cached set is smaller than the raw capacity suggests.
  • Exclusive — an item is in L1 or L2, never both. The two tiers' capacities add up to more distinct keys cached, which matters when memory is scarce. The cost is complexity: promoting/demoting items between tiers, and coherence has to reason about "which tier is it in right now."

The trade named: effective cache capacity vs coherence simplicity. At our scale L1 is tiny (a few thousand hot keys per server) and L2 is huge, so the duplication is negligible and inclusive wins — we take the simpler coherence story. When the tiers are comparable in size (classic CPU L1/L2/L3), exclusivity's capacity gain is worth its complexity.

Move 3 — Trace the paths

Follow four situations down the stack: a price change (write-through), a hot counter (write-back), a crash mid-flush, and a bulk import (write-around).

Path A — a price change, write-through

   Merchant drops product #42 from $80 -> $60.
   [1] App WRITES the DB (10 ms): truth is now $60. Durable.
   [2] App WRITES Redis ($60): shared tier now current.
   [3] ACK the merchant (~10.5 ms total). Slow, but the truth
         and the shared copy agree, and NOTHING can be lost.
   ...but 200 app servers still hold $80 in their L1 caches. (!)
   [4] Publish "invalidate product:42" on Redis pub/sub ->
         every server drops its L1 entry -> next read re-fetches $60.
   Latency paid on the write; correctness bought. The price is
     never allowed to exist only in volatile memory.

Path B — the "viewers now" counter, write-back

   Flash sale: product #42's counter ticks 2,000x/second.
   [1] Each increment updates Redis ONLY (INCR, ~0.5 ms), acks now.
         The Redis entry is "dirty": ahead of the DB.
   [2] A flusher writes the CURRENT value to the DB once/second.
         DB sees 1 write/s for this row, not 2,000 (L6 hot row dodged).
   [3] Reads serve the live Redis value; the DB is up to ~1 s behind,
         which for a "watching now" number is invisible.
   RPO = 1 s: if Redis loses this key before a flush, up to a
     second of increments vanish -- and nobody is harmed.

Path C — a crash mid-flush (the write-back bill comes due)

   A Redis node holding dirty counters dies at t = 0.7 s,
     0.7 s after the last flush.
     - Counters: ~0.7 s of increments across the dirty keys are
       GONE. Correct call: these are reconstructable / loss-OK,
       so we shrug. RPO honored.
     - Had we (wrongly) put PRICES on write-back: a price change
       in that 0.7 s window would VANISH -- DB still shows $80,
       merchant thinks it's $60. That is why prices are write-through.
   Shrink the blast radius WITHOUT going full write-through:
     - replicate the cache (a hot standby has the dirty data), and/or
     - append dirty writes to a small durable log before ack, and/or
     - flush more often (smaller RPO) at the cost of more DB writes.
   The dial: how much recent truth may live only in memory.

Path D — a nightly catalog import, write-around

   An overnight job rewrites 5,000,000 product descriptions.
   Write-through here would be a disaster: it'd shove 5M rarely-read
     descriptions into the cache, EVICTING the hot prices/counters
     real traffic needs (cache pollution).
   Write-AROUND: the job writes only the DB and INVALIDATES each
     touched key (drop any stale copy). The cache is left holding
     what's actually hot.
   First read of an updated description = a miss -> load from DB ->
     cache it. Fine: it's read rarely, so one miss is cheap, and
     the hot working set was never disturbed.

Path A shows write-through buying correctness with latency — and hints at the wall: updating the DB and Redis still leaves 200 L1 copies stale. Path B is the coalescing headline: write-back turns an impossible write rate into a trivial one. Path C is the bill: write-back's speed was a loan against durability, and a crash calls it — survivable for counters, ruinous for prices, which is why the policy is chosen per data type. Path D shows write-around protecting the hot set from a bulk write that would otherwise evict it. Move 4 names the wall Path A exposed: keeping 200 private copies coherent.

Move 4 — Find the first bottleneck: coherence across per-server caches

The first bottleneck — the L1 caches don't agree. This is the wall the whole design bends around. Redis is one shared copy, so updating it is clean. But each of the 200 app servers has its own in-process L1, and a write that updates the DB and Redis does not touch those 200 private copies. Product #42 drops to $60; server #137's L1 still says $80 and will keep serving $80 to every customer who lands on it — until something tells it otherwise. Quantify the exposure: with a lazy 10-second TTL as the only coherence mechanism, that stale price can be served for up to 10 seconds after the change, and at 40,000 reads/second a meaningful slice of traffic sees the wrong price in that window. Three ways to fix it, each a different point on one dial:

  • Short TTL — stamp L1 entries with, say, a 1–5 s expiry. Dead simple, no messaging, self-healing. But it's a blunt clock: it serves stale data for up to the TTL and re-fetches perfectly good entries the moment they expire (wasted loads). Freshness bounded by the TTL; you're always a little stale on purpose.
  • Pub/sub invalidation — on every write, publish "key #42 changed" on a Redis channel; all 200 servers subscribe and evict their L1 entry within milliseconds (Lesson 26's push). Near-instant coherence, at the cost of a fan-out message per write and a new failure mode: a dropped invalidation leaves one server stale indefinitely (so you keep a modest TTL as a backstop — belt and suspenders).
  • Versioned keys — never mutate product:42; write product:42:v7 and bump a tiny version pointer. Readers that learn v7 can't be served a cached v6 (Lesson 14's immutable-URL trick). No invalidation race, but you must distribute the version and the old entries linger until evicted.

The trade named: freshness vs invalidation traffic & complexity. A pure TTL sends zero messages and is always a little stale; pub/sub is fresh but chatty and drop-sensitive; versioning sidesteps the race but adds a version to propagate. Most real stacks run pub/sub for speed with a short TTL as a safety net — the message makes you fresh, the TTL saves you when the message is lost.

The second wall — write-back's dirty data is un-replicated truth. The moment you choose write-back, the newest value of a dirty key lives only in the cache's memory until the next flush, and a crash in that window loses it (Path C). The flush interval is your RPO. You don't fix this by abandoning write-back — you'd lose the 2,000×-write coalescing that made the hot counter possible. You shrink the blast radius: replicate the cache so a standby holds the dirty entries; append dirty writes to a small durable log before acking (a write-ahead log, so a restart replays them); or simply flush more often to trade a smaller RPO for more DB writes. And you reserve write-back for data whose loss is survivable or reconstructable — counters, metrics, session "last seen" — never money. The trade named: write latency & throughput vs the amount of recent truth you allow to exist only in volatile memory.

The third wall — a hot key expiring across tiers triggers a stampede. Suppose a very hot product's entry expires (TTL) in Redis at the same instant across the board. Every one of the 200 servers misses L1, misses L2, and stampedes the database for the same key at once — Lesson 2's thundering herd and Lesson 48's invalidation race, now amplified by having two cache tiers that can miss together. One expensive DB read becomes a synchronized spike of hundreds. The fixes are the ones you already own: single-flight / request coalescing (only one loader fetches the key; the rest wait and share the result), staggered/jittered TTLs so keys don't expire in lockstep (Lesson 2), and serve-stale-while-revalidate (hand back the old value and refresh in the background rather than blocking). The trade named: a tiny window of staleness (serve-stale) or a little coordination (single-flight) vs a correlated load spike on the tier below.

The fourth wall — every tier you add is another copy to keep coherent, including the CDN. The hierarchy's speed comes from multiplying copies, and coherence cost grows with them. The CDN (Lesson 14) is the farthest, least controllable copy: you can't reliably reach into every edge PoP to mutate a value, so a price change that must show immediately can't live behind a long-TTL CDN entry. This is exactly Lesson 14's choice — purge (tell the CDN to drop the key: direct but eventually-consistent and stampede-prone) versus versioned/immutable URLs (change the URL so there's nothing to invalidate; the default for anything renameable). The general rule the whole lesson has been circling: cache close and long-lived only what tolerates being stale; keep the volatile, must-be-exact values in fewer, nearer-to-truth tiers (or version them). The trade named: read latency & offload (more tiers, longer TTLs) vs coherence effort and staleness risk (more copies to chase when the truth moves).

So the honest picture of a layered cache: reads are gloriously cheap — ~0.145 ms average, the database touched on just 1% of reads — because you stacked a per-server L1, a shared Redis L2, and a CDN in front of the truth. But every one of those copies is a lie the instant the truth changes, so the real design work is on the write. Write-through pays the database's ~10.5 ms on every write to keep the truth durable and current — the right call for a price. Write-back acks in ~0.5 ms and collapses 2,000 hot-row writes into 1, at the price of losing up to a flush-interval of un-replicated truth in a crash — the right call for a counter, ruinous for money. Write-around skips the cache so a 5M-row import can't evict the hot working set. The first bottleneck is coherence — 200 private L1 copies a write doesn't touch (→ short TTL, pub/sub invalidation, or versioned keys, most stacks running pub/sub with a TTL backstop); around it, write-back's dirty data is un-replicated truth (→ replicate/log/flush-often, and never for money), a synchronized cross-tier expiry stampedes the DB (→ single-flight + jittered TTL + serve-stale, Lesson 2/48), and the CDN is the farthest copy to keep coherent (→ purge vs versioned URLs, Lesson 14). Every choice names its price.

The deepest point: a cache is a bet that the truth won't change before you read the copy again — and the whole craft of caching is managing what happens when that bet loses. Reads are the easy half because a stale read costs one wrong answer; the write is the hard half because a write invalidates every copy at once and you must decide, for each kind of data, how urgently and how durably that change must propagate. Write-through, write-back, and write-around are three answers to "how far down does the write go before I'm done"; TTL, invalidation, and versioning are three answers to "how do the other copies find out." Notice the whole thing is assembled from pieces you already own: a single cache and its read policies (L2), invalidation and immutable URLs (L14/48), the hot-row write wall that forces coalescing (L6), the thundering herd and single-flight (L2), the disposable-fast-path idea that write-through embodies and write-back deliberately breaks (L26), and RPO/durability thinking (L7). The new idea is only the stacking: with more than one copy, "update the cache" stops being one action and becomes "decide how far the write travels, and how the copies you didn't touch will learn the truth moved." The standing tension: read/write latency vs durability & coherence.

The four traps

  • Trap 1 — write-back for data you can't afford to lose. Un-flushed dirty entries live only in volatile memory; a crash erases them. Fine for a view counter, catastrophic for a price or a balance. Money and other must-not-vanish writes go write-through (or write-back with a durable log + replication).
  • Trap 2 — forgetting the per-server L1 copies exist. Updating the DB and Redis feels complete, but 200 in-process caches still serve the old value until their TTL. Invalidate them (pub/sub) or bound them (short TTL) — ideally both.
  • Trap 3 — write-through on a hot row. Insisting every increment reach the database turns a hot counter into 2,000 writes/s on one row (L6's wall). High-frequency, loss-tolerant writes want write-back's coalescing.
  • Trap 4 — polluting the cache with bulk or write-once data. Write-through on a 5M-row import evicts the hot working set real traffic needs. Use write-around so rarely-read writes never displace the hot set.

Where we landed

We put a cache hierarchy in front of one database and made every write decide how far down it must travel. Estimate set the stakes: stacking a per-server L1 (~100 ns), a shared Redis L2 (~0.5 ms), and the DB (~10 ms) drops the average read to ~0.145 ms and leaves the database only 1% of read traffic; on the write side, write-through acks in ~10.5 ms versus write-back's ~0.5 ms — a 21× gap — and write-back collapses a 2,000 writes/s hot counter into 1 write/s. Model gave the structure: a hierarchy where each tier trades a weakness of the one below for one more copy to keep coherent, and three write policies as a single decision — write-through (spend latency, buy durability; for prices), write-back (spend durability, buy latency & coalescing; for counters), write-around (spend a first-read miss, buy a clean cache; for imports) — plus the inclusive-vs-exclusive structural choice. Tracing showed a price change kept correct and durable, a hot counter surviving an impossible write rate, a crash that's a shrug for counters and would be ruin for prices, and a bulk import that leaves the hot set untouched. The first bottleneck: coherence across 200 private L1 copies (→ pub/sub invalidation with a short-TTL backstop, L26/48); around it, write-back's dirty data is un-replicated truth (→ replicate/log/flush-often, never for money, L7), a synchronized cross-tier expiry stampedes the DB (→ single-flight + jitter + serve-stale, L2/48), and the CDN is the farthest copy to keep coherent (→ purge vs versioned URLs, L14). The deepest point: a cache is a bet the truth won't change before you read the copy again, and caching is the craft of handling the moment that bet loses. The standing tension: read/write latency vs durability & coherence.
