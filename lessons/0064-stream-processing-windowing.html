Stream Processing & Windowing: Correct Answers From a Moving Firehose

Lesson 29 built a warehouse that answers "revenue by region by day" in half a second — but the answer was stale, only as fresh as the last batch load. It waved at a "speed layer" and moved on. This lesson opens that box: how do you compute a continuously-updating aggregate — "revenue in the last minute, per product, refreshed every second" — over a never-ending stream of events, and get an answer that is both fast and correct? The concrete job: a live sales leaderboard over a 100,000-events/sec purchase stream, end-to-end lag under a few seconds. We'll estimate the stream and the state it forces; model the three window shapes and the one idea — event time vs processing time — that decides whether the numbers are even right; trace a late event, a firing window, and a worker crash; and find the first bottleneck, which for a stateful processor is not throughput but the state itself — recovering it after a crash and moving it when you rescale. The trade underneath every knob: latency & correctness of windowed results vs state size & recovery cost.

The one system we'll build

A live sales leaderboard. A stream of purchase events flows in — one event per checkout, {product_id, price_cents, event_time, user_id} — and a dashboard must show, updated every second, the total revenue for each product in the last minute. The batch warehouse of Lesson 29 can't do this: it re-scans history on a schedule, so its freshest answer is minutes-to-hours old. We want an answer that is at most a few seconds behind reality and never wrong — a number that stays correct even though events arrive out of order, workers crash, and traffic doubles at noon. That "never wrong" requirement is the seed of the whole design: a stream processor's hard part is not moving the bytes fast — it's keeping a correct running answer in the face of late data and failure.

  A stateful stream processor: standing query over a moving log.

    purchase events (100k/s), each stamped with its EVENT TIME
        |
        v
   [ SOURCE ]  reads the log (L09), keeps an OFFSET per partition
        |   partition-by product_id  (L09 keyed routing)
        v
   [ KEYED WINDOW OPERATOR ]  <- the stateful heart
        |
        |  bucket each event by its EVENT TIME, not arrival time
        |  keep one running SUM per (product, window) in STATE
        |
        |     window [10:00:00 , 10:01:00)   product P-7:  $ 4,120
        |     window [10:00:00 , 10:01:00)   product P-9:  $ 2,300
        |     window [10:01:00 , 10:02:00)   product P-7:  $   80  ...
        |
        |  a WATERMARK ("I've now seen everything up to time t")
        |  decides WHEN a window is complete enough to FIRE
        v
   [ SINK ]  emit the finished window's totals to the dashboard

    running quietly underneath, forever:
      * STATE lives on each worker (in RAM + a local LSM store, L47)
      * CHECKPOINTS snapshot {all state + source offsets} together
        so a crashed worker restores exactly where it left off

A stream processor is a database query turned inside out. A database stores data and runs a query when you ask. A stream processor stores the query — the standing aggregation — and runs it forever as data flows past, keeping the answer materialized in state. Everything hard about it comes from that inversion: the input never ends (so "when is a window done?"), the input arrives out of order (so "which window does this event belong to?"), and the state is precious and large (so "what happens when the worker holding it dies?").

Words we'll earn before we lean on them

  • Stream / unbounded input — an input with no end: events keep arriving forever. A batch job reads a finite file and stops; a stream job runs indefinitely, so it can never "wait for all the data" before answering.
  • Event time vs processing time — event time is when the thing actually happened (stamped on the event at its source: a phone at checkout). Processing time is when your processor happens to see it (arrival). Network delay, retries (Lesson 7), and offline buffering make the two differ — often by seconds.
  • Window — a finite slice of the endless stream that you aggregate over: "the last minute," "9:00–9:01." Windowing is how you get a finite answer out of an infinite input.
  • Tumbling / sliding / session window — the three shapes. Tumbling: fixed, non-overlapping buckets (each event in exactly one). Sliding: fixed-length but overlapping (each event in several). Session: gap-defined, grows with activity and closes after a period of silence.
  • Watermark — the processor's moving assertion "I believe I have now seen every event with event time ≤ t." When the watermark passes a window's end, the window is declared complete and fires (emits its result). It is the dial between answering early and answering completely.
  • Keyed state — the per-key running aggregates the operator holds (here: one revenue sum per product per open window). It is partitioned by key across workers, exactly like Lesson 9's partition-by-key.
  • Checkpoint — a periodic, consistent snapshot of all operator state together with the source offsets it corresponds to, saved to durable storage, so a crashed job can restore state and rewind the input to the matching position.
  • Exactly-once state — the guarantee that each event affects the stored aggregates exactly once even though events may be re-read after a crash. It is about the effect on state, not about delivery on the wire (Lessons 9/13 — there is still no exactly-once delivery).

Move 1 — Estimate: the stream, and the state it forces

Two sizings decide everything: how fast do bytes arrive, and — the number that actually shapes the system — how much state must the processor hold?

PieceValueWhere it comes from
Event rate100,000/sone per checkout, peak (reuse L09's firehose scale)
Event size~200 Bproduct id, price, timestamps, user id
Ingest bandwidth20 MB/s100,000 × 200 B
Events per 1-min window6,000,00060 s × 100,000/s
Active products / min~1,000,000distinct keys that get a sale in the minute
Per-window keyed state~24 MB1M keys × ~24 B (sum + counters)
Target end-to-end lag< a few secondsvs L29 batch = minutes-to-hours stale

The number that matters: state scales with KEYS and WINDOWS, not with the event rate. Notice we do not store the 6,000,000 events in a window — we store one running sum per product. So the state is ~1M keys × 24 B ≈ 24 MB per in-flight window, and because we hold a couple of windows open at once (the current one plus one waiting for stragglers), the live keyed state is tens of megabytes, not the ~1.2 GB/min the raw events would be. This is the whole reason streaming aggregation is cheap where the raw firehose is not: an aggregate collapses many events into one number per key (Lesson 21's sketches, again — trade exact-events-kept for a compact running summary). But it flips the cost model: the expensive, fragile thing to manage is no longer throughput — it's this state. Lose it in a crash and the running answer is gone; grow the key count without bound and the worker runs out of memory.

Why not just re-run the batch query more often? Lesson 29 already priced this: the batch cost is proportional to history scanned × frequency. To refresh "last minute" every second by re-scanning, you'd re-read a rolling 60 s of events (6M rows) every second — 60× the work of reading each event once, and it still can't get below the batch interval in freshness. A stream processor reads each event once, folds it into a running sum, and is done — cost proportional to new data, not to history re-scanned. That is the streaming payoff, and the reason the "speed layer" of Lesson 29's lambda architecture exists at all.

Move 2 — Model: three window shapes, and the one idea that makes them correct

The three window shapes

Tumbling — fixed, non-overlapping buckets. A 1-minute tumbling window puts the event at 10:00:05 into exactly one bucket, [10:00:00, 10:01:00). Each event contributes to one window, so state and compute are minimal. This is our leaderboard's default: "revenue per clock-minute."

Sliding — fixed length, but stepped so windows overlap: "revenue over the last 60 s, recomputed every 10 s." Each event now belongs to 60 ÷ 10 = 6 windows at once, so it costs up to 6× the state and 6× the aggregate updates of a tumbling window. You buy a smoother, more responsive curve and pay in multiplied state — name that trade before you reach for a slide.

Session — no fixed clock; group an entity's events until a gap of inactivity (say 30 min) closes the window. A user's browsing session has no predetermined length — it's "however long they kept clicking." Session state is per-active-entity and lives until the gap elapses, so an unbounded number of never-idle sessions is an unbounded-state hazard (cap the max session length so a bot that never stops can't hold state forever).

The idea the whole lesson turns on: event time, not processing time

Here is the trap that quietly makes every dashboard wrong. An event happens at event time 10:00:59 — a checkout on a phone with a flaky connection. It reaches your processor at 10:01:04, five seconds later, because of network delay, a broker retry (Lesson 7), or the phone buffering while offline. If you bucket by processing time (when it arrived), this sale lands in the [10:01, 10:02) window — but it belongs to [10:00, 10:01). The 10:00 window under-counts and the 10:01 window over-counts. Worse, the error is non-deterministic: replay the same events on a faster network and they'd bucket differently, so you can't even reproduce the number. The fix is to bucket by the event's own event time stamp — an event's window is a property of the event, fixed forever, independent of when or how fast it arrives.

But event time creates a new problem: when is a window "done"? If a window's membership is decided by event time, and events can arrive late, then at 10:01:00 processing time you can't safely close the [10:00, 10:01) window — a straggler stamped 10:00:59 might still be in flight. Wait forever and you never emit an answer; close immediately and you drop stragglers. This is what a watermark resolves. A watermark is a promise the source emits, riding in the stream: "as of here, I've seen every event with event time ≤ t." It's computed as watermark = (max event time seen so far) − (allowed lateness). When the watermark reaches a window's end, the window fires.

  Watermark with allowed lateness = 5 s. Window W = [10:00:00, 10:01:00).

    events seen (by event time): ... 10:00:58, 10:00:59, 10:01:03 ...
    max event time seen                         = 10:01:05
    watermark = max_seen - 5 s                   = 10:01:00
        watermark has now reached W's END (10:01:00)
        -> W FIRES: emit each product's minute revenue

    a straggler stamped 10:00:57 that arrives AFTER W fired is LATE:
        watermark (10:01:00) is already past it
        -> drop it, OR route to a side output, OR emit a correction

  Latency to fire W  ~=  allowed lateness (5 s) + pipeline delay.
  Bigger allowed lateness -> fire later (more lag) but catch more
  stragglers. Smaller -> fire sooner but drop more late events.

The watermark's allowed-lateness bound is the exact dial between latency and completeness — the same freshness-vs-completeness tension as Lesson 17's tail (a slow span you either wait for or give up on) and Lesson 29's watermark for late-arriving batch data. Set it from the real tail of your arrival delay: if 99.9% of events arrive within 5 s, a 5 s bound catches almost everything and costs 5 s of dashboard lag.

Where the state lives, and how it survives a crash

The keyed sums live on the worker that owns each key's partition — in RAM for speed, backed by a local LSM store (Lesson 47's RocksDB-style engine: fast writes, spills to disk when state outgrows memory). That state is the whole answer, so losing it is catastrophic. A crashed worker must come back with its sums intact and reprocess no event twice into them. The mechanism is the checkpoint: periodically, the processor snapshots all operator state together with the source offsets (Lesson 9) that produced it, atomically, to durable storage. The offset-and-state pairing is the trick — a checkpoint records "these sums correspond to having consumed the log up to exactly these offsets." On recovery: restore the sums from the last checkpoint, rewind the source to the offsets in that same checkpoint, and resume. Every event after that offset is reprocessed, but since the state was rolled back to before those events too, each one folds into the sums exactly once.

This is "exactly-once state," not "exactly-once delivery." Records after the last checkpoint are re-read and re-processed on recovery (Lessons 9/13: no exactly-once on the wire). What's exactly-once is the effect on the stored state — because state and offset roll back together, the reprocessing lands the same sums, not doubled ones. Pushing that guarantee out to the dashboard (the sink) needs one more thing: either an idempotent write keyed by (window, product) so a replayed emit overwrites rather than adds (Lesson 13), or a transactional sink that commits its output together with the checkpoint (Lesson 33's outbox flavor). Skip that and recovery double-counts downstream even though the internal state was perfect.

The model in one line: bucket each event by its own event time into tumbling / sliding / session windows; hold one running aggregate per key in keyed state on an LSM-backed worker; let a watermark decide when a window has waited long enough for stragglers to fire; and checkpoint state-plus-offsets together so a crash costs a rewind, not a wrong answer.

Move 3 — Trace the paths

Three scenarios: a late event finding its correct window, a window firing, and a worker crash — the case the checkpoint machinery exists for.

Path A — a late event lands in the right window

  A phone checks out at event_time 10:00:59 ($40, product P-7),
  but buffers offline and the event ARRIVES at 10:01:04.

    t=10:01:04  source reads the event; reads its EVENT TIME = 10:00:59
                -> its window is [10:00:00, 10:01:00), decided by the
                   stamp, NOT by the 10:01:04 arrival time
    t=10:01:04  is W=[10:00,10:01) still open? watermark so far
                = max_seen(10:01:03) - 5 s = 10:00:58  < 10:01:00
                -> W has NOT fired yet -> add $40 to P-7's sum in W
    t=10:01:05  an event stamped 10:01:05 arrives; max_seen=10:01:05
                watermark = 10:01:00 -> reaches W's end -> W FIRES
                with the late $40 correctly included.

  Had we bucketed by ARRIVAL (10:01:04), the $40 would have wrongly
  landed in [10:01,10:02) and both minutes would be off. Event time
  + a 5 s watermark caught the straggler and kept the numbers right.

Path B — a sliding window vs a tumbling window on the same event

  One $40 sale of P-7 at event_time 10:00:59.

  TUMBLING (1 min):   belongs to exactly ONE window
       [10:00:00, 10:01:00)   +$40      (1 state update)

  SLIDING (len 60 s, step 10 s): belongs to 60/10 = 6 windows
       [10:00:00,10:01:00) +$40
       [10:00:10,10:01:10) +$40
       [10:00:20,10:01:20) +$40
       [10:00:30,10:01:30) +$40
       [10:00:40,10:01:40) +$40
       [10:00:50,10:01:50) +$40      (6 state updates, 6x the state)

  Same event, 6x the work + memory for a smoother refresh curve.
  That multiplier IS the trade: responsiveness vs state size.

Path C — a worker crashes mid-window (why checkpoints exist)

  Checkpoint interval = 10 s. Last good checkpoint C5 saved:
     { P-7 sum in W = $3,200, ... }  AT source offset = 5,000,000

    t=+7 s after C5   worker has since folded 700,000 more events;
                      P-7's live sum is now $4,120 (in RAM)
    t=+7 s            *** worker crashes *** -> the $4,120 (and all
                      un-checkpointed state) is GONE from that box

    RECOVERY:
      1. a standby worker restores state from C5  -> P-7 sum = $3,200
      2. rewind the source to C5's offset          -> 5,000,000
      3. replay the ~700,000 events since C5 (10 s x 100k = <=1M)
         -> each folds in ONCE (state rolled back with the offset)
         -> P-7 sum climbs back to exactly $4,120. No double-count.

    Recovery cost = restore state (tens of MB) + replay <= 1 interval
    of events. Checkpoint OFTEN -> short replay, steady overhead.
    Checkpoint RARELY -> cheap steady state, long replay on crash.

Path A is the payoff of event time: an event's window is a fact fixed at its source, so a straggler still counts where it belongs — and the watermark held the window open exactly long enough (5 s) to receive it. Path B makes the window-shape trade concrete: the same event costs 1 update tumbling and 6 sliding, so a sliding window's smoothness is paid for in a state multiplier you should name out loud. Path C is why the whole checkpoint apparatus exists: by snapshotting state and offset together, a crash becomes a bounded rewind — reprocess at most one checkpoint interval of events — rather than a lost or doubled answer. Exactly-once state, paid for by re-reading (never exactly-once delivery, Lessons 9/13).

Move 4 — Find the first bottleneck: the state, when you must recover or rescale it

A stateless service scales by adding boxes and shrinks by removing them — nothing moves. A stateful processor can't: the running sums are pinned to the workers that own their keys, so both recovery and scaling become exercises in moving state. That is the wall.

The bottleneck — rescaling means relocating state, and the naive key mapping reshuffles almost all of it. Traffic doubles at noon; you want to go from 20 workers to 40. Each key's state must live on the worker that will now receive that key's events — so the keyed state has to move to match the new assignment. If you assign keys by hash(key) % N, changing N from 20 to 40 remaps almost every key (Lesson 3's exact result: % N resharding moves ~94% of keys) — so ~94% of your state has to be shipped across the network before the job can resume. On tens of GB of state that's minutes of downtime on every scale change. The cost of rescaling a stateful processor is proportional to state size, not to throughput — the opposite of a stateless tier.

The fix — key groups (consistent hashing, applied to state). Pre-split the keyspace into a fixed, large number of key groups (say 1,024), assigned once at job start. Each worker owns a contiguous range of key groups; a key belongs to hash(key) mod 1024, and that mapping never changes. Rescaling reassigns whole key groups to workers — moving only the groups that changed hands (~1/N of them), not reshuffling every key. This is exactly Lesson 3/4's move: put a fixed indirection layer between keys and machines so adding a machine relocates a small slice, not the whole world. Key groups make the reassignment cheap; the state transfer is still real, but bounded to ~1/N. The same snapshot format that a checkpoint uses is what makes a group portable — you restore a savepoint into a differently-sized job (Lessons 31/38's redeploy-by-replay).

The second wall — the checkpoint interval is a two-sided dial. Checkpointing is not free: snapshotting tens of MB (or GB) of state to durable storage steals I/O and briefly stalls processing. Checkpoint too often and steady-state throughput drops under the overhead; checkpoint too rarely and a crash forces a long replay (recovery reprocesses up to one full interval of events — at 100k/s, a 60 s interval means replaying 6M events). The interval trades steady-state cost against recovery time, the same shape as Lesson 24's backfill-batch size and Lesson 2's cache TTL. For large state, incremental checkpoints (snapshot only the LSM segments changed since last time, Lesson 47) cut the steady cost so you can checkpoint often and keep recovery short.

The third wall — unbounded state. Keyed state is only cheap because windows close and release their memory. Break that and state grows without limit: a session window on a bot that never goes idle stays open forever; a "count distinct users ever" with no window keeps every key for all time; a watermark that never advances (one dead source partition stops emitting, so max_seen freezes) leaves every window open, holding state indefinitely. Every piece of state needs a reason it will eventually be released — a window that fires, a session gap, a state TTL (Lessons 20/39's lifecycle). A processor whose state only grows is a slow-motion out-of-memory crash.

So the honest design for our live leaderboard is: read the purchase log partitioned by product (Lesson 9); bucket each event by its event time into 1-minute tumbling windows (slide only where the smoother curve is worth 6× the state); hold one revenue sum per product per window in keyed state on an LSM-backed worker; let a watermark with a 5 s allowed-lateness bound decide when each window has waited long enough to fire (dropping or side-outputting anything later); checkpoint state-and-offsets together often enough that a crash costs a short replay; write results to the dashboard idempotently keyed by (window, product) so recovery can't double-count downstream; and partition state into fixed key groups so noon's scale-out moves ~1/N of the state, not ~94% of it. Every choice names its price: event time buys correctness at the cost of waiting on a watermark; a bigger watermark buys completeness at the cost of latency; frequent checkpoints buy fast recovery at the cost of steady overhead; key groups buy cheap rescaling at the cost of an indirection layer.

The deepest point: a stream processor is a materialized query kept correct against three enemies at once — the input never ends, it arrives out of order, and the machine holding the answer can die. Windows tame the endlessness, event-time-plus-watermarks tame the disorder, and checkpoints-plus-key-groups tame the fragility of state. Get those three right and "give me a correct, live, always-fresh aggregate over a firehose" stops being magic and becomes a set of dials you can point at your own latency and correctness budget. The standing tension, from Lesson 29's stale-but-cheap batch to here: latency & correctness of windowed results vs state size & recovery cost.

The four traps

  • Trap 1 — bucketing by processing time. Using arrival time to assign windows makes every out-of-order or delayed event land in the wrong bucket, and makes the result non-deterministic (a replay gives different numbers). Bucket by the event's own event-time stamp; use a watermark to decide completeness.
  • Trap 2 — confusing exactly-once state with exactly-once delivery. After a crash, events since the last checkpoint are reprocessed. The internal sums stay correct because state and offset roll back together — but the sink double-counts unless the write is idempotent or transactional (Lessons 13/33). There is still no exactly-once on the wire (Lesson 9).
  • Trap 3 — rescaling by hash(key) % N. Changing worker count remaps ~94% of keys (Lesson 3), so ~94% of state must ship before the job resumes — minutes of downtime per scale change. Use fixed key groups so only ~1/N of state moves (Lessons 3/4).
  • Trap 4 — unbounded state. A session that never idles, a global aggregate with no window, or a stalled watermark (one dead partition freezes max_seen) keeps state growing until the worker OOMs. Give every window a reason it will close — a fire, a gap, or a TTL (Lessons 20/39).

Where we landed

We built a live sales leaderboard — a correct, always-fresh aggregate over a 100,000-events/sec purchase stream — the thing Lesson 29's stale batch warehouse couldn't do. Estimate showed the shape-defining number: state scales with keys and windows (~24 MB of running sums), not with the 20 MB/s firehose, because an aggregate collapses many events into one number per key — which is why streaming is cheap on throughput but expensive on state. Model laid out the three window shapes (tumbling cheap, sliding = a state multiplier, session = an unbounded-state hazard) and the idea the whole lesson turns on: bucket by event time not processing time, and let a watermark (with an allowed-lateness bound that dials latency against completeness) decide when a window has waited long enough to fire; state lives on LSM-backed workers and survives crashes via checkpoints that snapshot state and offsets together — exactly-once state, not delivery. Tracing ran a 5-second-late event into its correct window, showed the same sale costing 1 update tumbling and 6 sliding, and rewound a crashed worker from its last checkpoint with no double-count. The first bottleneck was the state itself: rescaling relocates it, and the naive % N mapping reshuffles ~94% of it → fixed key groups (Lesson 3/4 again) move only ~1/N; the checkpoint interval trades steady overhead against replay time; and unbounded windows OOM the worker. Every dial named its trade. The standing tension, straight from Lesson 29: latency & correctness of windowed results vs state size & recovery cost.
