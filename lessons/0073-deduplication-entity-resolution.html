Deduplication & Entity Resolution: Are These Two Records the Same Person?

Every large dataset hides the same rot: the same real-world thing stored more than once, spelled a little differently each time. One customer signs up on the web as "Jonathan Q Smith", again on mobile as "Jon Smith", and a support agent types a third row as "J. Smith" — three rows, one human. This lesson takes 500 million customer records and answers one question at scale: are these two records the same person? The obvious method — compare every record to every other — is N², and we'll estimate why that's ~1.25×10¹⁷ comparisons (a job measured in millennia, not hours). We'll model the four machines that make it possible — blocking keys that only compare records that could plausibly match, a similarity score (Jaccard, edit distance, field weights) that turns "close" into a number, MinHash + LSH that finds near-duplicates without the N², and a clustering + survivorship step that turns matched pairs into one golden record — trace two records through the whole funnel, and find the first bottleneck: this is a recall-vs-precision problem where the two errors are not symmetric — a blocking key that's too tight misses true dupes, a threshold that's too loose merges two different people into one (a corruption far worse and far harder to undo than leaving them split), and "same-as" is not transitive, so naïve clustering chains unrelated records into one giant blob. The trade under all of it: match recall vs precision & compute cost.

The one system we'll build

A company has grown by acquisitions and years of sloppy sign-up forms, and now holds 500 million customer records across one big table. Nobody enforced "one row per person," so the same human appears many times with small differences: a nickname, a typo, an old address, a missing phone. We want to build a deduplication pipeline (also called entity resolution or record linkage): find every group of rows that refer to the same real person, and collapse each group into one clean golden record. The hard part is that there is no shared id to join on — if there were, this would be a GROUP BY, not a lesson. We have to decide sameness from fuzzy, dirty fields. Three example rows we'll follow the whole way:

  Three rows. One human? We have to DECIDE.

   id     name              email               phone       address
   ------ ----------------- ------------------- ----------- ------------------
   R1     Jonathan Q Smith  jsmith@gmail.com    555-0142    12 Oak Street
   R2     Jon Smith         jsmith@gmail.com    (blank)     12 Oak St
   R3     J. Smith          jon.s@work.com      555-0142    88 Pine Ave

   No shared id. Every field disagrees a little. Are R1=R2? R1=R3? R2=R3?

  THE FUNNEL: 500M records down to clean golden records.

   500,000,000 records
        |
        v   [1] BLOCKING  -- never compare records that can't match.
        |                    group by a cheap key (e.g. name-prefix+zip).
   ~ candidate pairs only WITHIN each block  (N^2  ->  N*b/2)

The one idea the whole lesson turns on: you cannot afford to ask "same person?" about most pairs, so the entire design is about not asking. Blocking throws away the ~99.9999% of pairs that obviously can't match (different name, different city) so the expensive fuzzy comparison only ever runs on a tiny plausible shortlist. Everything else — the scoring, the S-curve of LSH, the clustering — is machinery around that one move: compare few, compare well.

Words we'll earn before we lean on them

  • Entity resolution / record linkage / deduplication — deciding which records refer to the same real-world entity (here, a person) and collapsing them.
  • Golden record / master record — the single clean row that survives after a group of duplicates is merged.
  • Pairwise comparison — one "are these two the same?" check. The unit of work, and the thing we must ration.
  • Blocking / blocking key — a cheap key computed per record so we only compare records that share it (same block). Turns N² into "N² within small blocks."
  • Similarity score — a number (usually 0–1) for how alike two records are. 1 = identical, 0 = nothing in common.
  • Jaccard similarity — for two sets, |A∩B| / |A∪B|: the fraction of all distinct items that both share.
  • Edit distance (Levenshtein) — the number of single-character insert/delete/substitute edits to turn one string into another (Jon→Jan = 1).
  • Shingle / token set — a string broken into pieces (words, or overlapping character n-grams) so it becomes a set we can take a Jaccard of.
  • MinHash — a small fixed-size signature of a set such that the chance two signatures agree in a slot equals the sets' Jaccard. Estimates Jaccard cheaply (Lesson 21's sketch idea).
  • LSH (locality-sensitive hashing) — hashing so that similar items land in the same bucket with high probability and dissimilar ones almost never do — blocking done by similarity, not by an exact key.
  • Precision / recall — of the pairs we called "match," what fraction really match (precision); of all real matches, what fraction we found (recall).
  • Transitivity — the property "if A=B and B=C then A=C." Sameness is transitive; a similarity score is not — the source of the giant-blob trap.
  • Survivorship rule — how you pick the winning value for each field when merging (newest, most complete, most trusted source).
  • False merge vs false split — merging two different people into one row (a corruption) vs failing to merge one person's two rows (a nuisance). The lesson's core asymmetry.

Move 1 — Estimate: why N² is a wall, and blocking is the only way through

The naïve algorithm is one nested loop: for every record, compare it to every other record. Put the real number on it and the method dies on contact.

The N² wall. With N = 500,000,000, the number of distinct pairs is N·(N−1)/2 ≈ N²/2:

(5×10⁸)² / 2 = 2.5×10¹⁷ / 2 ≈ 1.25×10¹⁷ pairwise comparisons.

  • A fuzzy record comparison (parse two names, run an edit-distance, weight the fields) is at best ~1 µs. On one core: 1.25×10¹⁷ × 1 µs = 1.25×10¹¹ s ≈ 3,960 years.
  • Throw a big cluster at it — 1,000 cores at 1M comparisons/sec each = 10⁹/s: 1.25×10¹⁷ / 10⁹ = 1.25×10⁸ s ≈ 4 years — for one run of a job you need to run nightly.

N² isn't slow, it's impossible. Doubling the customer base quadruples the work. No faster comparison saves you — 10× faster still leaves centuries. The only fix is to stop doing most of the comparisons.

Blocking collapses the wall. Almost every pair is a trivially-obvious non-match: "Jon Smith in Ohio" versus "Wei Chen in Osaka" share nothing. So compute a cheap blocking key per record — say (first 3 letters of last name + zip code) — and only compare records that land in the same block. If a key spreads 500M records into blocks that average b = 100 records each, the comparisons are the pairs within blocks:

(N/b) blocks × (b²/2 pairs each) = N·b/2 = 5×10⁸ × 100 / 2 = 2.5×10¹⁰ comparisons.

That is a reduction of (N²/2) / (N·b/2) = N/b = 5×10⁸ / 100 = 5,000,000×. The same job that was 3,960 years on one core is now 2.5×10¹⁰ × 1 µs ≈ 6.9 hours on one core — and ~25 seconds across the 1,000-core cluster. One cheap key turned an impossible job into a coffee break.

Why blocking is a bet, not a free lunch: the 5-million× cut comes entirely from refusing to compare records whose blocking key differs. That is a wager that "same person ⇒ same key." It is often wrong — the same person with a mistyped zip, or a maiden vs married name, lands in a different block and is never compared, so never matched. Blocking trades recall (did we find all the real dupes?) for compute (how many pairs did we score?). Turn the key tighter and you compare fewer pairs but miss more true matches; looser, and you find more but pay more. This dial is the first bottleneck (Move 4); for now, just hold that the cut and the misses are the same knob.

Move 2 — Model: the four machines

Machine 1 — blocking keys: compare only the plausible

A blocking key is any cheap, deterministic function of a record that equal records tend to share. Good keys: zip + last-name-prefix, Soundex(last_name) + birth_year (Soundex maps Smith and Smyth to the same code — a phonetic key survives spelling), the email domain, the first 4 digits of a phone. You sort or hash by the key so same-key records sit together, then run the expensive pairwise scoring only inside each block (Lesson 3's sharding-by-key, reused: a block is a shard of the comparison work). The key's job is to be cheap, and to almost never separate two records that are truly the same. "Almost never" is doing a lot of work — see Move 4.

Machine 2 — the similarity score: turn "close" into a number

Within a block we still must decide sameness from fuzzy fields. Two building blocks:

  • Edit distance for short strings: Jon → Jonathan is a few edits; Smith vs Smyth is one substitution. Cheap for names.
  • Jaccard similarity for "bag of pieces" fields. Break each string into a token set, then Jaccard = |A∩B| / |A∪B|. Worked example on our R1 vs R2 addresses+names, tokenised:
   A = { jon,        smith, 12, oak, street }     (from R1)
   B = { jonathan,   smith, 12, oak, st     }     (from R2)

   A ∩ B = { smith, 12, oak }            -> 3 shared
   A ∪ B = { jon, jonathan, smith, 12, oak, street, st }  -> 7 total

   Jaccard = 3 / 7 = 0.43

A single 0-to-1 number isn't enough, because fields carry different weight as evidence. Two people sharing a rare value (the exact same email, the same phone) is strong evidence they're the same; sharing a common value ("lives in New York," first name "John") is weak. So the record score is a weighted blend: score = w₁·sim(name) + w₂·sim(email) + w₃·sim(phone) + w₄·sim(address), with big weights on high-discriminating fields (this is Lesson 16's IDF instinct — rare tokens carry more information — applied to whole fields). For R1 vs R2: emails match exactly (strong), names are close, addresses are the same street abbreviated — the blend lands high. For R1 vs R3: name close, but different email and different address, shared phone only — the blend lands in the murky middle.

Machine 3 — MinHash + LSH: near-duplicate blocking without the N²

Exact-key blocking has a hole: it only groups records that share the key exactly. We want to block by similarity itself — put records together when their token sets are Jaccard-close, typo or not. Computing Jaccard for all pairs is back to N². MinHash (Lesson 21's sketch family) fixes it: hash a set through k hash functions, keep the minimum under each — a k-slot signature. The magic property: the probability two signatures agree in any given slot equals the Jaccard of the original sets. So comparing two k=100 signatures estimates Jaccard to about 1/√k = ±10% error (Lesson 21's "small chosen error for constant memory"), from tiny fixed-size signatures instead of the full sets.

LSH turns that into blocking. Split each 100-slot signature into b = 20 bands of r = 5 rows. Two records become candidates if they match in all 5 rows of at least one band. The chance of colliding as a function of true similarity s is 1 − (1 − sʳ)ᵇ — an S-curve with a threshold near (1/b)^(1/r) ≈ 0.55:

   LSH collision probability   (k=100, b=20 bands, r=5 rows/band)

    similarity s   P(become a candidate pair)
    -----------    --------------------------
       0.80          0.9996     <- true dupes: almost always caught
       0.55          0.64       <- the threshold "knee"
       0.43          0.26
       0.30          0.047      <- distinct people: almost always skipped

   Sharp S-curve: high-similarity pairs pass, low-similarity pairs are
   filtered out -- WITHOUT ever computing an all-pairs Jaccard.

LSH is blocking by similarity: tune b and r to move the knee — more bands (higher b) lowers the threshold and catches looser matches (higher recall, more candidates to score); fewer bands raises it (higher precision, fewer candidates). It's the same recall-vs-compute dial as exact blocking, but the "key" is now fuzzy nearness, which plugs the typo hole.

Machine 4 — decide, cluster, and choose a survivor

Each candidate pair gets a score, and two thresholds split the outcomes into three, not two: score ≥ 0.85 → auto-match; score ≤ 0.45 → no-match; in between → a review band queued for a human (the middle is where automation is dangerous — Move 4). Matched pairs are edges in a graph; you take connected components (union-find) to turn pairwise "R1=R2, R2=R7" into whole clusters that are one person. Finally, survivorship collapses each cluster to one golden record by field-level rules: newest non-null address, most-complete name, most-trusted source for email, union of all phone numbers — and you keep every original row's id as provenance so a bad merge can be traced and undone.

Move 3 — Trace the paths

Follow our three rows through the funnel, then watch LSH generate a candidate a typo would have hidden.

Path A — R1 and R2 resolve into one person

   R1 Jonathan Q Smith / jsmith@gmail.com / 555-0142 / 12 Oak Street
   R2 Jon Smith        / jsmith@gmail.com / (blank)  / 12 Oak St

   [1] BLOCK   key = zip(same) + lastname-prefix "smi"
               -> R1 and R2 land in the SAME block. They get compared.
   [2] SCORE   email  : EXACT match  (rare value -> strong)   sim=1.0 w=.45
               name   : Jon~Jonathan, Smith=Smith             sim=0.7 w=.20
               address: "12 Oak Street" ~ "12 Oak St"         sim=0.9 w=.25
               phone  : one blank -> no evidence, not penalty  --   w=.10
               blend  -> ~0.90
   [3] DECIDE  0.90 >= 0.85  ->  AUTO-MATCH  (edge R1--R2)
   [4] MERGE   golden: name "Jonathan Q Smith" (most complete),
               phone "555-0142" (only non-null), address newest,
               keep {R1,R2} ids as provenance.

Path B — R3 is the hard one: the review band earns its keep

   R1 Jonathan Q Smith / jsmith@gmail.com / 555-0142 / 12 Oak Street
   R3 J. Smith         / jon.s@work.com   / 555-0142 / 88 Pine Ave

   [2] SCORE   phone  : EXACT 555-0142 (rare -> strong)       sim=1.0 w=.10
               name   : J. Smith ~ Jonathan .. Smith          sim=0.6 w=.20
               email  : gmail vs work.com -> DIFFERENT         sim=0.0 w=.45
               address: Oak St vs Pine Ave -> DIFFERENT        sim=0.0 w=.25
               blend  -> ~0.22 ... but the shared phone nags.
   [3] DECIDE  0.22 is below no-match? A shared RARE phone +
               same last name is real evidence. Landing this as a
               hard "no" risks a false split; as "yes" risks a false
               merge (a work email + different address may be a
               spouse/roommate sharing a landline).
               ->  REVIEW BAND. A human (or a stronger model) decides.

   The point: the MIDDLE is exactly where a naive threshold is most
   likely to be catastrophically wrong. Don't guess -- defer.

Path C — LSH catches a match that exact blocking would have missed

   R2 "12 Oak St, Springfield"      R4 "12 Oak St, Sprinfield"  (typo!)

   Exact block key = city -> "Springfield" != "Sprinfield"
       -> DIFFERENT blocks -> never compared -> MISSED. (recall hole)

   LSH on token-shingles:
       token sets overlap heavily (12, oak, st, spring... )
       true Jaccard ~ 0.80
       P(candidate) at s=0.80  =  0.9996   ->  they collide in a band
       -> become a CANDIDATE PAIR -> scored -> matched.

   LSH blocks by NEARNESS, so a single typo no longer hides a duplicate.

Path A is the easy win the whole pipeline exists to automate: a shared rare value (the exact email) plus corroborating fields sails past the high threshold and merges cleanly, with provenance kept. Path B is the honest one — a shared rare phone but conflicting email and address is genuinely ambiguous, and the design's job there is not to guess but to defer to the review band, because both wrong answers are costly and one of them is very hard to undo. Path C shows why exact blocking alone isn't enough and LSH exists: a one-character city typo puts a true duplicate in a different block forever, and only similarity-based blocking recovers it. The first three moves make dedup look like a solved funnel. Move 4 is where its two errors turn out to be dangerously unequal.

Move 4 — Find the first bottleneck: recall vs precision, and two errors that aren't equal

Every knob in the pipeline is really one knob — how aggressively do you declare "same?" — and it trades the two ways you can be wrong. The trap is treating them as symmetric. They are not.

The first bottleneck — the two errors are asymmetric, and the expensive one is silent. A false split (leaving one person as two rows) is a nuisance: a duplicate mailer, a slightly inflated user count — annoying, easily fixed later by a looser pass. A false merge (fusing two different people into one golden record) is a corruption: person A now sees person B's orders, addresses, maybe payment info (Lesson 30/56 — a privacy incident), and because you deleted the distinction, it is brutal to detect and unwind. A false split is reversible; a false merge destroys the very information you'd need to reverse it. So the whole system must be biased toward NOT merging when unsure: high auto-match threshold, a wide review band for the murky middle, keep every source id as provenance so a merge is reversible, and never auto-merge on weak evidence alone. Precision (don't merge wrongly) is bought at some cost to recall (leave a few dupes) — and here that's the right trade.

The second wall — blocking recall: the match you never compared. Blocking's 5-million× speed-up is built on skipping pairs, so any true duplicate whose blocking-key field is dirty (mistyped zip, maiden vs married name, "Bob" vs "Robert") lands in a different block and is never scored — a miss you can't see, because the pipeline never produced the pair to reject it. A single blocking pass caps your maximum recall no matter how good the scorer. Fix = multi-pass blocking: block several times on different keys (once by zip+name, once by phone, once by email domain, once by LSH on the address), and take the union of candidate pairs. A record has to be dirty in every key at once to escape all passes — far less likely. The cost is more candidate pairs to score (more compute), which is exactly the recall-vs-compute dial from Move 1, now turned deliberately.

The third wall — "same-as" is not transitive: the giant-blob trap. Sameness should be transitive (if R1=R2 and R2=R3 then R1=R3), but a similarity score is not: R1 can be 0.86-similar to R2, and R2 0.86-similar to R3, while R1 and R3 are only 0.4-similar (Smith→Smyth→Smithe, each step tiny, the ends far apart). Take connected components naïvely and these near-matches chain: one over-eager edge welds two clusters, then a third, and a "John Smith" super-cluster swallows a thousand unrelated Smiths into one monstrous golden record (a false merge at industrial scale). Transitive closure amplifies a single bad edge into a catastrophe. Fixes: require clusters to be dense (near-cliques, not chains), cap cluster size and quarantine anything implausibly large for review, use cannot-link constraints (two rows with different verified government IDs may never be merged, no matter the score), and correlation-cluster rather than blindly closing transitively.

The fourth wall — dedup is never "done": incremental resolution. The 6.9-hour batch is a snapshot; meanwhile new records arrive every second, and re-running the full N²-avoiding batch on all 500M for each new signup is absurd. So the live path inverts the batch: when a record arrives, compute its blocking keys, fetch only the candidates in those blocks (a handful, not 500M), score, and attach it to an existing cluster or start a new one — an incremental, Lesson-19-style "query the neighbourhood, not the world." The periodic full batch still runs to catch drift and re-cluster (rules and models change; a merge good last year may be wrong now). And because merges must stay reversible, the golden record is a derived view over immutable source rows (Lesson 25/38 — the ledger/event-sourcing instinct: never destroy the originals; the merge is a computed projection you can recompute or roll back).

So the honest picture of deduplication: you cannot compare all N² ≈ 1.25×10¹⁷ pairs (millennia), so blocking compares only records sharing a cheap key (N·b/2, a ~5-million× cut) and MinHash + LSH extends that to blocking-by-similarity so a typo can't hide a duplicate; within the shortlist a weighted similarity score (Jaccard on token sets, edit distance, rare fields weighted like Lesson 16's IDF) turns "close" into a number, two thresholds split it into auto-match / review band / no-match, and connected components + survivorship collapse matched pairs into one golden record with provenance kept. The first bottleneck is that the two errors are not equal — a false merge corrupts and is near-irreversible while a false split is a cheap nuisance — so the whole system leans away from merging: high threshold, wide review band, reversible merges over immutable sources. Around it sit three more walls: blocking silently caps recall (fix: multi-pass blocking on several keys, union the candidates), similarity is not transitive so naïve clustering chains unrelated records into a giant blob (fix: dense clusters, size caps, cannot-link constraints), and the job is never done (fix: incremental resolution per new record + periodic full re-cluster). Every choice names its price: a tighter block is faster but misses more; a higher threshold is safer but splits more; LSH is cheap but approximate; automation is scalable but the murky middle belongs to a human.

The deepest point: entity resolution is a decision under uncertainty, not a computation. There is no ground-truth join key — you are inferring an identity the data never recorded, from evidence that always partly conflicts. That reframes the whole design: the goal isn't a clever similarity formula, it's an error budget deliberately spent on the cheaper mistake. You will be wrong about some pairs no matter what; the engineering is choosing to be wrong in the direction you can afford and undo (leave a dupe) rather than the direction that corrupts and can't be undone (merge two people). Blocking, LSH, thresholds, the review band, provenance, cannot-link — every mechanism is a way to push your unavoidable errors toward the survivable side of that line. The standing tension: match recall vs precision & compute cost.

The four traps

  • Trap 1 — treating the two errors as equal. A false merge fuses two real people (privacy breach, near-irreversible); a false split is a cheap, fixable dupe. Bias the whole system away from merging: high auto-match threshold, wide review band, reversible merges. Never auto-merge on weak evidence.
  • Trap 2 — one blocking key. A single key silently caps recall — any dupe dirty in that field is never compared. Block in multiple passes on different keys (and LSH) and union the candidates; a record must be dirty in every key to escape.
  • Trap 3 — naïve transitive closure. Similarity isn't transitive, so blindly taking connected components chains near-matches into a giant blob that swallows unrelated records. Require dense clusters, cap size, and honor cannot-link constraints (verified different IDs).
  • Trap 4 — destroying the originals on merge. Overwriting the source rows with a golden record makes a bad merge unrecoverable. Keep every source id as provenance and treat the golden record as a derived, recomputable view (L25/38).

Where we landed

We took the rot in every large dataset — the same real person stored many times, spelled differently — and built a pipeline to resolve 500M records. Estimate priced the wall: comparing every pair is N²/2 ≈ 1.25×10¹⁷ comparisons ≈ 3,960 years on a core (≈4 years even on 1,000), so blocking — only comparing records that share a cheap key — cuts it to N·b/2 ≈ 2.5×10¹⁰, a ~5,000,000× reduction (≈6.9 hours on one core, ~25 s on the cluster), at the cost of missing matches whose key field is dirty. Model gave four machines: blocking keys (compare only the plausible), a weighted similarity score (Jaccard on token sets — 3/7 = 0.43 worked out — plus edit distance, with rare fields weighted like Lesson 16's IDF), MinHash + LSH (block by similarity so a typo can't hide a dupe; k=100, b=20, r=5 gives a sharp S-curve — 99.96% of 0.80-similar pairs caught, 4.7% of 0.30-similar pairs), and clustering + survivorship (union-find matched pairs into one golden record). Tracing merged R1/R2 on a shared rare email, sent the genuinely-ambiguous R3 to the review band, and watched LSH recover a duplicate a one-character city typo had hidden from exact blocking. The first bottleneck: the two errors are asymmetric — a false merge corrupts two people's data near-irreversibly while a false split is a cheap nuisance — so the system must lean away from merging (high threshold, wide review band, reversible merges); around it, single-key blocking silently caps recall (→ multi-pass + union), similarity is not transitive so naïve clustering chains into a giant blob (→ dense clusters, caps, cannot-link), and the job never ends (→ incremental resolution + periodic re-batch). The deepest point: entity resolution is a decision under uncertainty — you infer an identity the data never stored — so the real engineering is spending your unavoidable error budget on the mistake you can afford and undo.
