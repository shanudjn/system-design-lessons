Data Modeling: Normalization vs Denormalization: One Order-and-Customer Schema, Laid Out Both Ways

For eighty-one lessons we've said "the orders table" as if the shape of it were obvious. It isn't. The very first decision you make about any dataset — before sharding it (L79), indexing it (L12), or backing it up (L81) — is how to split the facts into tables, and that one choice quietly sets the cost of every read and every write forever after. This lesson takes one concrete schema — customers and their orders — and lays it out both ways: fully normalized (each fact stored exactly once, tables joined at read time) and denormalized (facts copied together so a read is a single fetch). We'll estimate what a join costs versus a pre-joined read, put a real read:write ratio on it, and price the storage. We'll model what "normalized" actually means (functional dependencies, third normal form) and why copying a fact creates the update anomaly. We'll trace three operations — reading an order history, placing an order, and renaming a product — through both layouts, watching one get cheap exactly where the other gets expensive. And we'll find the first bottleneck: the update-anomaly tax, and the resolution that lets you stop choosing — keep the normalized truth, derive a denormalized read copy. The trade under all of it: write correctness & storage vs read latency.

The one system we'll build

Keep the orders platform from L79: 10 billion orders, placed by 100 million customers, each order holding a few line items (a product, a quantity, a price). The page everyone hits is the order-history page: "show me my 50 most recent orders, with each item's product name, category, and price." It's read constantly. Orders are placed at 40,000 writes/second at peak (L79); the history and product pages are read at roughly 500,000 reads/second. Hold onto that ratio — it decides everything.

Here is the same information, drawn two ways. Look at where the facts live:

  NORMALIZED (3NF) — each fact stored ONCE, tables joined at read time
  ┌──────────────┐      ┌──────────────┐      ┌──────────────────┐
  │  customers   │      │    orders    │      │   order_items    │
  ├──────────────┤      ├──────────────┤      ├──────────────────┤
  │ customer_id ◄├──┐   │ order_id     │   ┌─►│ order_id  (FK)   │
  │ name         │  └───┤ customer_id ─┼───┘  │ product_id (FK) ─┼──┐
  │ email        │      │ created_at   │      │ qty              │  │
  │ tier         │      │ status       │      └──────────────────┘  │
  └──────────────┘      └──────────────┘      ┌──────────────────┐  │
                                              │    products      │◄─┘
   "Blue Runner" is stored in exactly ONE     ├──────────────────┤
   place: products.name. Everything else      │ product_id       │
   POINTS to it with a foreign key (FK).       │ name  "Blue Runner"
                                              │ category         │
                                              │ price_cents      │
                                              └──────────────────┘

  DENORMALIZED — facts COPIED together so a read is one fetch
  ┌──────────────────────────────────────────────────────────────┐
  │  order_history  (one wide row per order line)                 │
  ├──────────────────────────────────────────────────────────────┤
  │ order_id │ customer_id │ customer_name │ product_name │ ...    │
  │  9001    │   42        │  "Ada Lovelace"│ "Blue Runner"│ 12900 │
  │  9001    │   42        │  "Ada Lovelace"│ "Red Racer"  │  8900 │
  │  9002    │   42        │  "Ada Lovelace"│ "Blue Runner"│ 12900 │  <- "Blue Runner"
  └──────────────────────────────────────────────────────────────┘     and "Ada Lovelace"
                                                                        copied on EVERY row

The one idea the whole lesson turns on: normalization stores every fact in exactly one place and reconstructs the wide view with a join at read time; denormalization copies facts together so the wide view is already assembled. The first makes writes correct and cheap (change a fact in one row) but makes reads expensive (re-join every time). The second makes reads cheap (one fetch) but makes writes expensive and dangerous (a fact now lives in a million rows that can disagree). Every data-modeling decision is choosing which of those two pains to pay, and where.

Words we'll earn before we lean on them

  • Schema — the shape of your data: what tables exist, what columns they have, and how they relate.
  • Primary key (PK) — the column that uniquely identifies a row (e.g. customer_id). One per row, never repeated.
  • Foreign key (FK) — a column that holds another table's primary key, so a row can point to a row elsewhere instead of copying it.
  • Join — the read-time operation that follows foreign keys to stitch rows from several tables back into one wide result.
  • Functional dependency — "A determines B": if knowing A always fixes B, then B depends on A. Knowing customer_id fixes the name. Written customer_id → name.
  • Normalization — organizing tables so each fact is stored once, in the table whose key it depends on. Removes duplicated data.
  • Third normal form (3NF) — the common target: every non-key column depends on the key, the whole key, and nothing but the key. In plain words: no column is a copy of a fact that really belongs to some other table.
  • Denormalization — deliberately copying facts together (violating 3NF on purpose) so a read doesn't have to join.
  • Update anomaly — the bug denormalization invites: a fact stored in many rows, so changing it means updating every copy, and any copy you miss is now wrong.
  • Read:write ratio — how many reads you serve per write. The single number that decides which pain is worth paying.
  • Materialized view / read model — a denormalized, pre-joined copy that the database (or your code) keeps in sync with the normalized truth. The copy is derived, never the source.
  • Source of truth — the one authoritative place a fact lives. Everything else is a copy you can rebuild.
  • Embedding vs referencing — the document-store version of the same choice: nest child data inside the parent document (embed) or store an id that points to it (reference).

Move 1 — Estimate: what a join costs, and how often you pay it

Two numbers decide this whole lesson: how expensive is the join we're avoiding, and how lopsided is the read:write ratio that tells us whether avoiding it is worth it.

The read: normalized order history is a 4-way join. To render one customer's 50-order page, each order carrying ~3 line items (150 items total), the normalized schema must:

  1. find the 50 orders    — one index range on orders(customer_id, created_at)
                             (L18 cursor seek) ........... ~0.5 ms
  2. find their items      — 150 rows via order_id index .. ~0.5 ms
  3. look up each product  — 150 B-tree seeks into products
                             (L12: ~0.4 ms each) = 150 × 0.4 = 60 ms   <-- dominates
  4. look up the customer  — 1 seek ...................... ~0.4 ms
                                                          ---------
                             total ................... ~61 ms

The killer is step 3: a nested-loop join does one index seek per item, so the cost scales with how many rows you're stitching. Now the denormalized read of the same page:

  order_history is already keyed by (customer_id, created_at) with the
  product name/category/price COPIED into each row:
     one index range scan returns all 50 orders' lines ...... ~0.5 ms

~61 ms vs ~0.5 ms ≈ 120× faster. That's the read prize denormalization buys: the join was precomputed once at write time (L15's precompute-the-read) instead of re-run on every page view. The trade named: we traded write-time work and duplicated storage for a 120× cheaper read.

How often do we pay it? The read:write ratio. Reads run at ~500,000/s; order-placing writes at ~40,000/s; and the facts we'd be copying — a product's name or category, a customer's name — change far more rarely still (a product is renamed maybe once in its life, read millions of times).

  reads : order-writes      = 500,000 : 40,000   ≈ 12 : 1
  reads : product-renames   ≈ 500,000/s : ~0.01/s ≈ 50,000,000 : 1

  A product read is served ~50 million times between renames.
  Paying a little MORE on the rename to make each of those 50M
  reads 120× cheaper is an overwhelmingly good trade.

This ratio is the deciding bet. When reads vastly outnumber the writes that would change a copied fact, denormalize: pay the rare expensive write to make the constant read cheap. When writes are frequent or the data churns, normalize: don't create copies you'll spend all day keeping in sync. Data modeling is a bet on your read:write ratio — and if you don't know the ratio, you can't make the schema decision honestly.

The storage price of copying. A customer's name is ~20 bytes. Stored once per customer (normalized) vs copied into every order (denormalized):

  normalized:   100,000,000 customers × 20 B = 2 GB      (once each)
  denormalized: 10,000,000,000 orders   × 20 B = 200 GB   (copied per order)
                                                 -------
                        100× more storage for that ONE field

Multiply across every copied column (name, category, price...) and denormalized tables balloon. Storage is cheap, so the bytes aren't the real cost — but every one of those duplicated copies is a fact that can now drift out of sync, and that is the real bill, which Move 2 makes precise.

Why the read and the write pull in opposite directions: a join is work you do at read time; a copy is work (and risk) you take on at write time. You cannot make both cheap with one physical layout, because the wide, pre-joined shape that a read wants is exactly the duplicated shape a write hates. So the schema question is never "which is better" — it's "which side of this system do I want to pay on, given how often each side runs." Name the ratio, then name the price.

Move 2 — Model: what "normalized" means, and the anomaly copying creates

Normalization is one rule: each fact depends on its key, and lives with that key

Start with the messy "one big table" everyone reaches for first, and watch what's wrong with it:

  order_id │ customer_id │ customer_email      │ product_id │ product_name │ price
  ─────────┼─────────────┼─────────────────────┼────────────┼──────────────┼──────
   9001    │   42        │ ada@example.com     │  7         │ Blue Runner  │ 12900
   9002    │   42        │ ada@example.com     │  7         │ Blue Runner  │ 12900
   9003    │   42        │ ada@example.com     │  9         │ Red Racer    │  8900

Look at the functional dependencies — which column determines which:

  • customer_id → customer_email (id 42 always means ada@example.com)
  • product_id → product_name, price (product 7 is always "Blue Runner" at 12900)

Neither of those facts depends on order_id, the table's key — yet they're stored in this orders table, repeated on every row. Third normal form is the rule that fixes it: every non-key column must depend on the key, the whole key, and nothing but the key. customer_email depends on customer_id, not on the order — so it belongs in a customers table keyed by customer_id. product_name depends on product_id — so it belongs in a products table. Move each fact to the table whose key it actually depends on, and leave behind only a foreign key that points to it. That's the normalized schema from the top of the page. Each fact now lives in exactly one place.

Why "one place" matters: the update anomaly

Store a fact in one place and changing it is one write. Copy it into a million rows and you've created the update anomaly: to change the fact you must find and rewrite every copy, and the instant you've done some but not all, your data is lying.

  Product 7 is renamed "Blue Runner" -> "Blue Runner v2".

  NORMALIZED:  UPDATE products SET name='Blue Runner v2' WHERE product_id=7;
               -> ONE row changed. Every order that points to product 7
                  now reads the new name automatically. Impossible to
                  be half-done: there's only one copy.

  DENORMALIZED: product 7 appears in, say, 2,000,000 order_history rows.
               UPDATE order_history SET product_name='Blue Runner v2'
                 WHERE product_id=7;
               -> 2,000,000 rows to rewrite. At 10,000 rows/s that's
                  ~200 seconds, DURING WHICH some rows say "Blue Runner"
                  and some say "Blue Runner v2" — the same product, two
                  names, at the same time. If the job crashes at row
                  1,000,000, it stays that way.

The update-anomaly tax, stated as a number: one logical change costs 1 write normalized and 2,000,000 writes denormalized — and worse than the cost is the window of inconsistency while the fan-out runs, plus the permanent corruption if it fails partway. (Its cousins: the insertion anomaly — you can't record a new product until someone orders it, because products only exist inside order rows — and the deletion anomaly — delete the last order for a product and the product's very existence vanishes. Both are the same disease: a fact with no home of its own.)

The same choice in a document store: embed vs reference

Document databases dress this decision in different clothes but it's identical. An order document can embed its line items (nest them inside) or reference them (store ids):

  EMBED (denormalize):  { order_id: 9001, customer: "Ada",
                          items: [ {name:"Blue Runner", price:12900}, ... ] }
     one read gets the whole order — but "Blue Runner" is copied into
     every order that bought it, and the document grows with the array.

  REFERENCE (normalize): { order_id: 9001, customer_id: 42,
                           item_ids: [7, 9] }   // look products up separately
     no duplication, but rendering the order needs a second lookup (a join
     by another name).

The rule of thumb: embed what is read together, owned by the parent, and bounded; reference what is shared, independently updated, or unbounded. Line items are read with their order, owned by it, and few → embed. A product's canonical name is shared across millions of orders and updated on its own → reference. The wall on embedding is the same update anomaly plus a hard one: an unbounded array (embed every comment under a post, forever) eventually blows the document size limit and rewrites the whole document on every append. Bounded-and-owned embeds; shared-or-unbounded references.

Move 3 — Trace the paths: one read, one write, one rename

Path A — read the order-history page (denormalized wins)

   NORMALIZED:   4-way join, 150 nested-loop product seeks -> ~61 ms
   DENORMALIZED: one index range scan of pre-joined rows   -> ~0.5 ms

   This page runs ~500,000 times/second. The 120× gap is paid
   half a million times a second -> denormalization is the whole
   difference between a snappy page and a melted database.

This is the case denormalization exists for: a read-heavy path where the join is re-run constantly on data that rarely changes. Precompute the join once (L15), store it wide, and every read is a single seek.

Path B — place a new order (normalized wins, mildly)

   NORMALIZED:   INSERT 1 order row + 3 order_item rows (FKs to
                 existing customer & products) = 4 small inserts.
                 The customer's name and each product's name are
                 NOT written — they already exist, once.

   DENORMALIZED: INSERT 3 order_history rows, each carrying a COPY
                 of the customer name + product name/category/price.
                 More bytes per write, and you must first FETCH those
                 facts to copy them in. Slightly heavier, but bounded
                 (a handful of rows) — placing an order is fine either way.

Placing an order touches only a few rows in both layouts, so the write difference here is small. The write pain of denormalization doesn't show up when you add a row — it shows up when you change a copied fact, which is Path C.

Path C — a product is renamed (the denormalized layout's nightmare)

   NORMALIZED:   UPDATE products SET name=... WHERE product_id=7;
                 -> 1 row. Atomic. Every reader sees the new name at once.

   DENORMALIZED: UPDATE order_history SET product_name=... WHERE product_id=7;
                 -> ~2,000,000 rows. Slow (~200 s), and INCONSISTENT
                    for the whole 200 s (two names live at once). Crash
                    mid-way -> permanently split-brained product name.

The two layouts are photographic negatives of each other. Exactly where the denormalized layout is 120× faster (the read, Path A), the normalized layout is 2,000,000× cheaper (the rename, Path B/C). Neither is "better." The read:write ratio from Move 1 tells you which path runs more and matters more — and for order history (read 500k/s, product renamed ~never) the read wins decisively. But notice we've been forced to give up something real on whichever side we don't pick. The next move refuses that dilemma.

Move 4 — Find the first bottleneck: the update-anomaly tax, and how to stop choosing

The first bottleneck — the update-anomaly tax. A pure denormalized schema makes the common read fast but turns every change to a shared fact into a mass rewrite with a window of inconsistency (Move 2, Path C). A pure normalized schema keeps every write correct and cheap but makes the common read a costly multi-way join (Path A). Chosen globally, each is wrong for half your workload. The resolution is to stop treating it as one global choice:

   Keep the NORMALIZED tables as the SOURCE OF TRUTH.
     - 3NF: each fact once, writes correct, rename = 1 row (Path C stays cheap)
     - this is where an order is placed and a product is renamed

   DERIVE a DENORMALIZED read model from it, kept in sync ASYNC.
     - a materialized view / read table: pre-joined, wide, fast (Path A)
     - the rename updates 1 truth row, then a background job (L15/L33
       CDC/outbox) re-fans the new name into the read model
     - readers hit the read model; writers hit the truth

   The copy is DERIVED, never authoritative. If it drifts or is lost,
   REBUILD it from the truth. The update anomaly stops being CORRUPTION
   (a lie with no correct source) and becomes LAG (a copy that's briefly
   stale but will converge) — a far cheaper problem.

This is the deepest point of the lesson. The reason a pure-denormalized schema is dangerous isn't the duplication itself — it's that the duplicated copy is the data, so a missed update is permanent corruption with no correct version to fall back to. Make the copy derived from a single normalized source of truth and the same duplication becomes safe: the worst case is a few seconds of staleness (L06 eventual consistency), and you can always rebuild the read model by re-running the join. You get the 120× read and the 1-row rename — paid for with eventual consistency and the machinery to keep the copy in sync. That machinery is exactly CQRS (L37), materialized views, and the precompute-the-read pattern (L15), fed by CDC/outbox events (L33).

The second wall — over-normalization has its own tax. Normalization taken to a purist extreme (split every attribute into its own table) makes writes pristine but turns a simple read into a 10-way join, and every join is a chance for the query planner to pick a bad plan (L12's selectivity trap). A read that needs eight joins to show one screen is a design smell in the other direction. The trade named: normalize until each fact has one clear home, but don't shatter data that's always read together across so many tables that every read pays a join tax with no write benefit to show for it. 3NF is the target, not "as many tables as possible."

The third wall — some denormalization can't be derived cheaply and must be chosen up front. The order-history read model is easy to derive because the join is simple. But some access patterns (a feed, a leaderboard, a per-user timeline, L15) are expensive to compute on the fly and expensive to keep as a derived view, so you bake the denormalized shape into the primary write path — this is the norm in wide-column and document stores (Cassandra, DynamoDB), where you model the table around the query, not the entities. There you accept the update anomaly deliberately and manage it with application-level fan-out and idempotent updates (L13). The trade named: the more your store lacks cheap joins, the more you must denormalize at write time and own the consistency work yourself.

The fourth wall — the read:write ratio changes, and so must the schema. The deciding bet (Move 1) is made against today's ratio. A write-light, read-heavy table that denormalized happily can flip — a new feature makes the "copied" fact change hourly, and suddenly your rename tax is a daily fire. Schemas are not permanent; they migrate (L24 expand/contract, L79 resharding). The trade named: a denormalized schema is a bet that the copied facts stay stable; when that bet stops holding, the fix is a migration back toward normalization (or toward a derived read model), and the earlier you priced the ratio the earlier you see the bet turning.

So the honest picture: normalization stores each fact once, keeping writes correct and cheap (a product rename is one row) but making the read-heavy order-history page a ~61 ms four-way join. Denormalization copies facts together, making that page a ~0.5 ms single fetch (120× faster, paid half a million times a second) but turning a product rename into a ~2,000,000-row rewrite with a window of inconsistency and a corruption risk if it fails partway — the update-anomaly tax. Estimate priced both sides and named the read:write ratio (~12:1 for orders, ~50,000,000:1 for renamed facts) as the deciding bet. Model defined normalization as "each fact depends on and lives with its key" (3NF), showed the anomaly copying creates, and mapped it onto embed-vs-reference in document stores. Tracing showed the two layouts as photographic negatives — one cheap exactly where the other is dear. The first bottleneck — the update-anomaly tax — dissolves once you stop choosing globally: keep a normalized source of truth and derive a denormalized read model kept in sync asynchronously (L15/L37/L33), turning corruption into mere lag. Around it: don't over-normalize into a join tax, some denormalization must be chosen up front in join-less stores, and re-price the bet when the read:write ratio shifts. Every choice names its price.

The deepest point: a normalized fact has a single source of truth, and a denormalized fact is a cache of that truth — so denormalization is safe exactly when the copy is derived and rebuildable, and dangerous exactly when the copy is the only copy. That reframes the whole lesson: "normalize vs denormalize" is really "where is the truth, and what is merely a fast copy of it?" Store the truth normalized so a fact changes in one place; serve reads from denormalized copies so the common path is a single fetch; and keep the copies honest with the sync machinery you already know — precompute-the-read (L15), materialized views / CQRS (L37), CDC/outbox propagation (L33), all under eventual consistency (L06). Notice everything here is assembled from pieces you own: L12's B-tree seek is what a join costs, L15's precompute-the-read is the denormalized read model, L18's cursor indexes the history page, L33's outbox keeps the copy in sync, L79's sharding and L24's migration are how a schema changes when the bet turns. The new idea is only that the shape of the data is itself a design decision — the first one — and it is a bet on your read:write ratio. The standing tension: write correctness & storage vs read latency.

The four traps

  • Trap 1 — denormalizing without a source of truth. Copying a fact into many rows where the copy is the data means a missed update is permanent corruption with nothing to fall back to. Always keep one normalized authoritative copy and derive the rest, so drift is lag you can rebuild, not corruption you can't.
  • Trap 2 — choosing the layout without knowing the read:write ratio. Normalize vs denormalize is a bet on how often you read versus how often the copied facts change. Guessing the ratio is guessing the schema. Measure it first, and revisit when the workload shifts.
  • Trap 3 — over-normalizing into a join tax. "More tables = more correct" is false past 3NF: shattering read-together data across ten tables makes every read an expensive multi-join with no write benefit. Normalize until each fact has one home, then stop.
  • Trap 4 — embedding unbounded or shared data. Nesting a growing array (all comments under a post, forever) or a shared fact (a product's canonical name) inside a document rebuilds the whole document on every change and duplicates the shared fact. Embed only what is bounded and owned; reference the rest.

Where we landed

We took the one decision eighty-one lessons assumed away — the shape of the orders table — and laid it out both ways. Estimate made the trade concrete: the normalized order-history read is a ~61 ms four-way join (150 nested-loop product seeks, L12), the denormalized read is a ~0.5 ms single fetch (~120× faster, L15's precompute), and the read:write ratio (~12:1 for orders, effectively ~50,000,000:1 for the facts we'd copy) is the deciding bet. Model defined normalization as functional dependencies obeyed — each fact stored with the key it depends on (3NF) — and showed the update anomaly that copying invites: one logical rename costs 1 write normalized and ~2,000,000 denormalized, with a window of inconsistency and a corruption risk if it fails partway; the same choice reappears as embed-vs-reference in document stores. Tracing a read, a write, and a rename showed the two layouts as photographic negatives — each cheap exactly where the other is dear. The first bottleneck, the update-anomaly tax, dissolves once you keep a normalized source of truth and derive a denormalized read model kept in sync asynchronously (CQRS L37, materialized views, CDC/outbox L33) — turning corruption into mere lag (L06). Around it: don't over-normalize into a join tax, denormalize up front in join-less stores and own the consistency (L13), and re-price the bet when the ratio shifts (L24/L79). The deepest point: a normalized fact is the truth and a denormalized fact is a cache of it, so the real question is always where does the truth live, and what is merely a fast copy? The standing tension: write correctness & storage vs read latency.
