Rendering & Delivery at Scale: Server, Client, or Edge — and the Personalization Line

Lesson 59 made the whole cloud bill a design constraint and ended pointing at one hot, user-facing slice of it: getting the page itself onto the screen. This lesson zooms all the way in to the last hop — turning your data into HTML and getting that HTML painted on a phone, fast and cheap, for millions of users. It sounds like a front-end detail; it is a distributed-systems problem in disguise, because the same page can be built in four different places (at build time, on the origin, at the edge, or on the phone itself), and every choice trades time-to-first-byte and server cost against freshness and personalization. We'll take one concrete page — a product page on the orders platform (Lessons 27/49/59): 40k req/s, served to a phone on a mid-tier mobile connection — and get it onto the screen. We'll estimate the timeline of a page load down to the millisecond and find that the round trips, the JavaScript bundle, and the phone's CPU each cost more than people expect. We'll model the four rendering strategies (server / client / static / edge), plus streaming and hydration, as points on two dials: where the HTML is built and who pays to make it interactive. We'll trace the same page rendered four ways and watch the numbers move. The first bottleneck is the one that governs the whole design: you cannot make one page both fully cacheable and fully personalized — the line between the shared shell and the per-user slice is the architecture. The trade underneath: time-to-first-byte & offload vs freshness & compute.

The one problem we'll design

A user taps a link to a product page. Somewhere, your data — the product's name, price, photo, reviews, plus this user's cart and recommendations — has to become HTML the browser can paint, and that HTML has to travel to their phone. The page serves 40,000 req/s at peak (Lesson 27's fleet), and the users are on phones far from your Virginia origin (Lesson 14/55: ~100 ms round trip to the origin, ~15 ms to a nearby edge PoP) on connections around 12 Mbps (~1.5 MB/s). The naive instinct is "rendering is a front-end concern — pick a framework and move on." But where that rendering happens decides your time-to-first-byte, your server bill (Lesson 59), whether the page can be cached (Lesson 14), and whether it can say "Hi Alice, your cart has 3 items." Those are system-design decisions, and they conflict.

  And the page is NOT one thing -- it is a SHELL + SLICES:

     |  reviews / description / price          |     everyone  -> CACHE it (L14)
     |- - - - - - - - - - - - - - - - - - - - -|
     |  "Hi Alice"   cart (3)   your recs      |  <- PER-USER: unique  ->
     +-----------------------------------------+     can't cache -> render/fetch per user

  The design decision IS the line between the shell and the slice.

Rendering is not one thing that happens in one place. The same page can be assembled at build time (once, for everyone), on the origin (per request), at the edge (near the user), or on the phone (offloaded to the client) — and it is really a shared shell plus a thin per-user slice. The whole lesson is deciding where each part is built and how the two are stitched together.

Words we'll earn before we lean on them

  • Rendering — turning your data plus a template into the HTML string a browser can paint. The question is only where that happens.
  • SSR (server-side rendering) — the server runs the render per request and sends finished HTML with content already in it.
  • CSR (client-side rendering) — the server sends a nearly empty HTML shell plus a JavaScript bundle; the browser downloads the bundle, runs it, fetches data, and builds the HTML itself.
  • SSG / static rendering — the render runs once at build time, producing a static HTML file cached and served to everyone (a CDN cache hit, Lesson 14).
  • Edge rendering — SSR run at the PoP nearest the user instead of the distant origin (Lesson 55), so the round trip is ~15 ms not ~100 ms.
  • Streaming / progressive rendering — the server flushes the HTML in chunks: send the fast shared shell immediately, stream the slow per-user parts as they finish, so the slow part doesn't hold up the fast part.
  • Hydration — a server-rendered page is static HTML until the JavaScript bundle downloads and runs to attach event handlers ("hydrate" the markup). Until it finishes, the page looks ready but taps do nothing.
  • TTFB (time to first byte) — how long until the first byte of the response arrives. A blank shell can have a great TTFB and show nothing.
  • FCP (first contentful paint) — when the user first sees real content on screen.
  • TTI (time to interactive) — when the page actually responds to taps. Often much later than FCP — the gap is hydration.
  • Shell vs slice (personalization boundary) — the shared part of the page (same for all → cacheable) versus the per-user part (unique → not cacheable). Where you draw this line is the core design choice.
  • Island / partial hydration — hydrate only the interactive pieces of the page (a "Buy" button, a cart widget) instead of the whole tree, so you ship and run far less JavaScript.

Move 1 — Estimate: time the page load

Before choosing a strategy, put real numbers on the pieces. A page load is a sequence of round trips, downloads, and CPU work, and each one is bigger than intuition suggests. Here are the constants we'll reuse:

PieceValueWhere it comes from
Round trip to origin~100 msdistant user → Virginia (Lesson 14/55 speed-of-light)
Round trip to nearest edge PoP~15 msa copy nearby (Lesson 14/55)
Mobile bandwidth~1.5 MB/s~12 Mbps mid-tier connection
JavaScript bundle300 KB gzippeda typical single-page-app framework + code
Full HTML page~40 KBrendered markup with content
Server render (per request)~30 ms CPUrun the template tree to a string
Data fetch (server-side)~20 msfrom cache / feature store (Lessons 48/53)
Phone parse + execute JS~1 ms per KBa median phone's main thread; 300 KB ≈ 300 ms

Two costs dominate and both are easy to miss. First, round trips, not bytes: at ~100 ms each, three dependent requests in a row (get HTML → get bundle → get data) is ~300 ms of nothing-but-waiting before a pixel appears — the Lesson 14 speed-of-light tax, paid once per hop in the chain. Second, the phone's CPU: downloading a 300 KB bundle is only 300 ÷ 1500 = 0.2 s, but parsing and executing it on a median phone is another ~300 ms of main-thread work — and JavaScript execution, unlike download, doesn't get faster with a better network. The expensive parts of a page load are the serial round trips and the JavaScript the phone has to run — not the size of the HTML.

Now the server side, priced the Lesson 59 way. A server render is ~30 ms of CPU. If every request renders on the origin, that's 0.030 s × 40,000 req/s = 1,200 core-seconds every second = 1,200 CPU cores — about 150 servers (at 8 cores each) doing nothing but turning data into HTML. A cached static page renders once at build time and then costs a CDN cache hit: ~0 origin cores. The difference between rendering per-request and rendering once is ~150 servers — the same "cache hit vs miss" gap Lesson 59 priced, now measured in render CPU. Where you render is a line item on the bill.

Name the trade-off — time-to-first-byte & offload vs freshness & compute. Everything below is one dial. Push work off the request path (render once at build, cache at the edge, or offload to the phone) and TTFB drops and the server bill shrinks — paid for in staleness or in a slow, JavaScript-heavy client. Push work onto the request path (render fresh per user on the server) and the page is current and personal — paid for in latency and ~150 cores of render compute. No single point on the dial is right for the whole page, which is exactly why we'll end up splitting it.

Move 2 — Model: two dials, four strategies

Every rendering strategy is a choice on two independent dials: where the HTML is built (build time → origin → edge → client) and who makes it interactive (how much JavaScript the phone must run to hydrate). Let's place the four named strategies on those dials.

The four strategies

CSR — client-side rendering. Server sends a ~3 KB empty shell plus a <script> tag. The phone downloads the 300 KB bundle, runs it, calls your API for data, and builds the HTML itself. Server compute ≈ 0 (it just served a static shell and an API call); the phone does all the work. Great offload, but the user stares at a blank screen through a waterfall of dependent round trips, and search engines / link previews see an empty page.

SSR — server-side rendering. Server fetches data and runs the render per request, sending full HTML. Content is in the first response, so FCP is fast — but the server pays ~30 ms of CPU per request (~150 cores at peak), and the page still isn't interactive until the bundle hydrates it.

SSG / static. Render once at build time; serve the resulting file as a CDN cache hit (Lesson 14). Fastest TTFB (~15 ms from a nearby PoP) and near-zero origin compute — but it's the same HTML for everyone (no personalization) and stale until the next rebuild/purge.

Edge rendering (Lesson 55). Run the SSR render at the PoP near the user. Cuts the round trip from ~100 ms to ~15 ms and keeps per-request freshness — but the edge can only reach data that's local or eventually-consistent (Lesson 55's rule: the edge runs the decision, the origin owns the truth), so a render needing the authoritative database still forwards home.

Streaming — don't let the slow part block the fast part

Naive SSR waits for all the data before sending any HTML, so the whole page runs at the speed of its slowest piece — and the slowest piece is usually the personalized recommendation section that needs a ~200 ms ML call (Lesson 53). Streaming SSR fixes this: flush the shared shell and above-the-fold content the instant they're ready (~20 ms of data fetch), keep the connection open, and stream the slow recommendation block in when it finishes. TTFB and first content stay fast, and the slow per-user slice fills in progressively instead of holding the whole page hostage — the same "don't let a slow dependency block a fast one" idea as Lesson 28's backpressure and Lesson 49's BFF graceful-degrade, applied to HTML.

Hydration — the second dial, and the hidden tax

SSR and SSG both send finished HTML, so the page appears quickly. But that HTML is inert: a "Buy" button drawn in HTML doesn't do anything until JavaScript attaches a click handler. Hydration is the client downloading the bundle and re-running the component tree to wire up the static markup. Its cost is the whole bundle: ~200 ms download + ~300 ms execute ≈ 500 ms on our phone. During that gap the page looks ready and taps do nothing — the "uncanny valley" between FCP and TTI. Hydration cost scales with how much JavaScript you ship, which is why the fix is to ship less: hydrate only the interactive islands (partial hydration), not the whole page. The trade sharpens here: interactivity vs bytes shipped — sending HTML is cheap, sending interactivity is expensive.

The model in one line: pick where the HTML is built (build time is cheapest/stalest, origin is freshest/most expensive, edge is a nearby middle, client offloads to the phone) and how much of it must hydrate (all of it → long TTI gap; just the islands → cheap). Streaming lets a page be fast and personal by sending the shared part now and the per-user part as it arrives. Every named framework is a preset on these two dials.

  Static is fastest AND cheapest -- so personalize it, right?

  This is Lesson 14's stray-tracking-param bug in a new hat:
  anything that makes a response unique per request kills the

  The fix is NOT "pick fast-but-generic OR slow-but-personal".
  It is to SPLIT the page along the personalization line:

        -> render once, cache at edge (99% hit, ~15ms, ~0 cores)
     SLICE ("Hi Alice", cart, recs)        -> per user

           OR stream it in last, OR personalize at the edge (L55)

  Big shared expensive-to-build part: cached once.
  Small per-user part: pays the per-request price.

Path C — streaming the slow slice

  The recommendation block needs a 200ms ML call (L53).
  The rest of the page is ready in 20ms.

  NAIVE SSR (wait for everything):
     data fetch 20ms ... but recs take 200ms ...
     server holds the whole response 200ms -> TTFB 300ms
     the fast 95% of the page waited on the slow 5%.

  STREAMING SSR:
     flush shell + product + reviews at 20ms  -> TTFB ~120ms
        (browser starts downloading the bundle in parallel)
     recs stream in when the ML call returns   -> +200ms, appears

  The slow personalized slice no longer holds the fast shared
  shell hostage. TTFB and first content stay fast; the expensive
  part fills in progressively or degrades. (L28/L49 on the page.)

Path A shows the raw trade: static is fastest to content and cheapest but generic; SSR is fast-to-content and personal but costs ~150 render cores; CSR offloads the server but pays with a blank screen and a round-trip waterfall. Path B is the collision that decides the design: personalizing a cacheable page makes every response unique, which drops the CDN hit ratio to ~0 and puts all ~150 render cores back — Lesson 14's stray-param cache-killer, now caused by personalization itself. Path C shows the escape: split the page and stream, so the shared shell is a cache hit for everyone and only the thin per-user slice pays the per-request price.

Move 4 — Find the first bottleneck: the personalization line, and the hydration tax

Two walls decide every rendering design, and they map onto the two dials.

First wall — you cannot make one page both fully cacheable and fully personalized. A CDN cache hit (Lesson 14) is the fastest and cheapest way to deliver a page: ~15 ms from a nearby PoP, ~0 origin compute, one copy served to millions. But a cache works only when the response is the same for many requests — and personalization is, by definition, a response unique to one user. The two pull in exactly opposite directions, and no clever framework dissolves the conflict. The resolution is not to choose one; it is to draw the personalization line through the page. The big, shared, expensive-to-build part (product info, reviews, the layout) is rendered once and cached at the edge for everyone. The small per-user slice ("Hi Alice", the cart badge, recommendations) is rendered or fetched per request — as a client-side island, a streamed-in chunk, or an edge personalization (Lesson 55). The dial is the fraction of the page that's per-user: push it toward all-shared and you get a fast, cheap, generic page; push it toward all-personal and you get a slow, expensive origin render every time. Drawing that line well — cache the 95% that's shared, personalize the 5% that isn't — is the entire craft.

Second wall — HTML is cheap to send, interactivity is expensive. Server and static rendering get content on screen fast, but the page is inert until the JavaScript bundle downloads and hydrates it — ~500 ms on our phone, during which the page looks ready and taps do nothing (the FCP-to-TTI gap). That cost scales with how much JavaScript you ship, and shipping a whole single-page-app framework to hydrate a mostly-static page is paying full price for a little interactivity. The fix is to ship less: hydrate only the interactive islands (the "Buy" button, the cart widget) instead of the entire tree (partial hydration), or send components that are HTML-only with no client JavaScript at all. Sending markup is nearly free; sending the code to make markup interactive is the real weight. This is the second dial — interactivity vs bytes shipped — and it is why "just server-render everything" isn't automatically the answer: SSR fixes FCP but leaves the hydration tax untouched unless you also cut the bundle.

So the honest delivery design for our product page is not one strategy but a composition: render the shared shell once and cache it at the edge (Lesson 14/55 — fast TTFB, ~0 compute, generic-on-purpose), stream or island-hydrate the thin per-user slice (personal without killing the cache), and ship only the JavaScript the interactive islands need (short TTI gap). Each decision is made knowing what it costs: a cache hit trades freshness for speed and dollars; a per-request render trades ~150 cores for personalization; every kilobyte of bundle trades phone CPU for interactivity.

The deepest point: "rendering" looks like a front-end checkbox and is actually a placement decision identical to the ones this whole course has been making. Where do you build the HTML — at build time (cache it, Lesson 14), on the origin (fresh but expensive, Lesson 59), at the edge (near the user, Lesson 55), or on the client (offloaded)? It's the same question as where to put a cache, where to run a computation, and where the truth lives — answered for the last hop to the screen. And it carries the same unavoidable tension: the fastest, cheapest page is a static cache hit shared by everyone, and the moment you make it personal you give that up, so the art is splitting the page so that the shared part stays cacheable and only the personal part pays. The four traps

  • Trap 1 — personalizing an otherwise-cacheable page. Sprinkle "Hi Alice" and a cart badge into the shared HTML and every response becomes unique, the CDN hit ratio collapses to ~0, and every request is a full origin render (~150 cores) — Lesson 14's stray-tracking-param cache-killer, caused by personalization. Split the page: cache the shared shell, render only the per-user slice.
  • Trap 2 — hydrating the whole page. Shipping a full framework bundle to make a mostly-static page interactive creates a long FCP-to-TTI gap where the page looks ready but taps do nothing. Hydration cost is the bundle size — hydrate only the interactive islands (partial hydration), or send HTML-only components.
  • Trap 3 — pure CSR for content-first pages. Offloading all rendering to the phone gives a blank screen and a waterfall of dependent round trips (~770 ms to content in our trace), plus an empty page for search engines and link previews. Render content on the server or edge; save CSR for app-like screens behind a login where SEO and first paint don't matter.
  • Trap 4 — letting the slow slice block the fast shell. Naive SSR waits for the slowest piece (a 200 ms recommendation call, Lesson 53) before sending any HTML, so the whole page runs at the speed of its slowest dependency. Stream the fast shared part immediately and let the slow personalized part fill in — degrading to a placeholder if it times out (Lesson 49).

Where we landed

Getting HTML to the screen is a placement problem, not a front-end detail. Estimate timed the page load and found the costs hide in the serial round trips (~100 ms each, and dependent requests chain them) and the phone's CPU (a 300 KB bundle is ~200 ms to download but another ~300 ms to execute), while on the server a per-request render is ~30 ms × 40k/s ≈ 150 cores versus ~0 for a cached static page. Model placed four strategies on two dials — where the HTML is built (build time / origin / edge / client) and how much must hydrate — with streaming letting the fast shared shell go out before the slow per-user slice, and hydration as the hidden tax that makes a page look ready before it works. Tracing rendered the same page four ways (static fastest+cheapest but generic; SSR fast+personal but ~150 cores; CSR offloaded but blank-then-waterfall), watched personalization collapse the cache to ~0 (Lesson 14's stray-param bug reborn), and streamed the slow recommendation slice so it stopped holding the page hostage. The first bottleneck is twofold: you cannot make one page both fully cacheable and fully personalized, so the personalization line — cache the shared shell, render only the per-user slice — is the design; and HTML is cheap to send while interactivity (hydration) is expensive, so ship only the JavaScript the islands need. The deepest point: where you build the HTML is the same placement question as where a cache, a computation, or the truth lives — answered for the last hop to the screen. The standing tension: time-to-first-byte & offload vs freshness & compute.

We've now delivered the page to the user as fast and cheap as the shared/personal split allows. But every one of those 40k req/s assumed a real human on the other end. The next lesson asks the question the edge has to answer before it renders anything:
