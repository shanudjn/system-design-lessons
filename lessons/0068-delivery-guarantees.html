Delivery Guarantees & the Dead-Letter Lifecycle: Making a Whole Pipeline Reliable End to End

We have been building reliability one hop at a time. Lesson 9 gave a message log that never loses an event but may hand it over more than once. Lesson 13 made a single POST /charge safe to retry. Lesson 33 got a database write and a published event to agree. Each was one link in a chain. This lesson threads them into one pipeline — an order event flowing through four services — and asks the question a real system lives or dies by: what does it actually mean for that message to be "delivered," across the whole chain, when any hop can crash, retry, or choke on a bad message? We'll meet the three delivery semantics — at-most-once, at-least-once, exactly-once — and the hard truth that exactly-once delivery is a myth while exactly-once effect is routine. We'll estimate how many duplicates a busy pipeline actually produces (spoiler: tens of thousands of double-charges a day if you do nothing); model the fix — at-least-once transport plus idempotent consumers, with a clear answer to where deduplication lives; trace a happy message, a duplicate that gets absorbed, a poison message that fails forever and must be quarantined, and its dead-letter triage-and-replay; and find the first bottleneck, which is that "never lose it" has a storage bill — the in-flight state (dedup keys, the DLQ, the un-acked backlog) is the price of certainty. The trade under every choice: delivery certainty & operability vs pipeline latency & the storage of in-flight state.

The one system we'll build

One order.placed event, born when a shopper taps "Buy," must travel through a pipeline of four services, each a separate process on a separate machine that can fail on its own: ingest (write the order down), payment (charge the card), fulfillment (reserve stock, tell the warehouse), and notify (email the receipt). Between each pair sits a durable log (Lesson 9's append-only, partitioned message queue). The pipeline runs at 2,000 orders/sec on an average day and peaks near 10,000/sec; each event is about 1 KB. Our job is to define — and then guarantee — what "this order was processed" means from end to end, so the shopper is charged once, shipped once, and emailed once, even though somewhere in those four hops something is always failing.

  ONE order event, FOUR hops. Each hop can crash / retry / choke.

   producer                                                consumer
   (checkout)                                              (warehouse+inbox)

      v      [log 1]        [log 2]        [log 3]      [log 4]  |
   +--------+  =>  +---------+  =>  +-------------+  =>  +--------+
   | INGEST |      | PAYMENT |      | FULFILLMENT |      | NOTIFY |
   +--------+      +---------+      +-------------+      +--------+

    ack|   \ (dup!)    |   \ (dup!)      |   \ (dup!)       |ack

   "have I seen msg-id X?  yes -> skip effect, just ack."

   Some messages NEVER succeed (malformed / deleted entity):
       retried N times -> QUARANTINE -> [ DEAD-LETTER QUEUE ]

   Guarantee to build:  at-least-once transport (never lose)
                      +  idempotent consumers (never double-count)
                      =  EFFECTIVELY-ONCE effect, end to end.

The one idea the whole lesson turns on: you cannot stop a duplicate from arriving — the network guarantees that (see Move 1). So you stop it from counting. Ship every message with a stable idempotency key (Lesson 13), and make every consumer check "have I already done this key?" before it acts. At-least-once delivery says the message is never lost; idempotent processing says it's never applied twice. Bolt them together and you get the only "exactly-once" that is real: the effect happens once, even though the message may show up many times. Everything else in this lesson — poison messages, dead-letter queues, replay — is about the messages that don't fit that clean story.

Words we'll earn before we lean on them

  • Delivery semantics — the promise a transport makes about how many times a message is handed to the consumer: at-most-once, at-least-once, or exactly-once.
  • At-most-once — send and forget; no retry. A message is delivered zero or one time. Never duplicates, but can lose data on any failure.
  • At-least-once — retry until the consumer acknowledges (acks). A message is delivered one or more times. Never loses, but can duplicate.
  • Exactly-once — delivered exactly one time. As a pure transport promise across an unreliable network it is impossible (Move 1). As an observable effect it is achievable — we call that effectively-once.
  • Ack — the consumer's signal "I've durably handled this; stop redelivering." No ack (crash, timeout) ⇒ the broker redelivers.
  • Idempotency key — a stable ID the producer stamps on the message (Lesson 13) so every retry carries the same key, letting a consumer recognize a repeat.
  • Deduplication (dedup) — a consumer remembering which keys it has already applied, so a repeat is skipped (acked without re-doing the effect).
  • Effectively-once — at-least-once delivery + idempotent consumers. Duplicates arrive but change nothing; the net effect is one-time.
  • Poison message — a message that fails every time it's processed (malformed, or references a row that no longer exists). Retrying it forever is pointless and, in an ordered partition, harmful.
  • Head-of-line blocking — in an ordered partition (Lesson 9), a stuck message at the front holds up every message behind it.
  • Dead-letter queue (DLQ) — a side channel where a message is parked after it exhausts its retries, so the main pipeline can move on. It is quarantine, not a trash can.
  • Replay — re-injecting a DLQ'd (or historical) message back into the pipeline after the cause is fixed.
  • In-flight state — everything the pipeline must remember to keep its promise: dedup keys, un-acked messages, and the DLQ's contents.

Move 1 — Estimate: exactly-once is a myth, and duplicates are not rare

Two facts decide the whole design. First: why can't the transport just deliver each message once? Second: if we accept duplicates, how many actually happen — is this a real problem or a rounding error?

Why exactly-once delivery is impossible (the two generals, in one paragraph). A consumer finishes the work and must tell the broker "done" so it stops redelivering. That ack travels the network — and the network can lose it. Now the broker faces a choice with no safe answer. If it redelivers when an ack is missing, a consumer that did the work but whose ack was lost gets the message again → a duplicate (that's at-least-once). If it doesn't redeliver, a consumer that crashed before doing the work never gets a second chance → a loss (that's at-most-once). No amount of extra messages closes the gap: whatever the last message is, it too can be lost, so someone must act without knowing it arrived. You must pick which failure you can tolerate — lose, or duplicate. There is no third door at the transport layer. (This is Lesson 7's "a timeout tells you nothing" made formal.)

The number that forces dedup: without it, ~86,400 double-charges a day at the payment hop alone. A duplicate happens whenever a consumer does the work and then dies before its ack lands (or the ack is lost). Put that at a modest 0.05% of deliveries. At the payment hop's 2,000/s, that's 2,000 × 0.0005 = 1 duplicate delivery per second — 1 × 86,400 = 86,400 duplicate charge attempts every day at just one hop. Across all four hops it's ~4 duplicate deliveries/second ≈ 345,600/day of double-fulfilled, double-emailed, double-charged effects. That is not a rounding error; it is a customer-trust catastrophe. Exactly-once delivery being impossible, our only move is to make the effect immune to the duplicate: dedup on the idempotency key. The scan itself was never the danger — duplicates at scale are.

Why at-most-once is off the table here: we could avoid every duplicate by never retrying — send once, and if the ack is missing, shrug. But at 0.05% loss that's the same ~1 lost order/second per hop: orders that vanish silently, money the shopper spent with nothing shipped. For an order pipeline, losing is far worse than duplicating, because a duplicate can be neutralized (dedup) but a loss is gone. So we choose at-least-once and pay for it with dedup. (For a fire-hose of low-value telemetry, the opposite choice — at-most-once, drop on failure — is often right. Name the trade: tolerable loss vs tolerable duplication.)

Move 2 — Model: at-least-once + idempotency = effectively-once, and where dedup lives

The recipe, and the one subtle part everyone gets wrong

The shape is simple: the transport promises at-least-once (retry until acked), and each consumer is idempotent (skip a key it has already applied). Duplicates still arrive; they just do nothing. The subtle part is making the skip reliable — and it's the same trap as Lesson 33's dual write.

The dedup check and the effect must commit together, or you've fixed nothing. Naïvely: "check the dedup store; if new, do the effect; then record the key; then ack." But look at the gaps. If you record the key before the effect and crash between them, the retry sees "already done" and skips a charge that never happened — a silent loss. If you do the effect before recording the key and crash between them, the retry re-does the effect — the very duplicate we're trying to kill. The fix: the effect and the "I did this key" record must land in one atomic commit. For a database effect, write the row and the dedup key in the same transaction (Lesson 33's outbox move: the marker rides with the work). For a truly external effect (charge a card), delegate the atomicity to the downstream by passing your idempotency key through to it (Lesson 13), so the payment provider itself dedups. Ack only after that commit. Now a crash at any point is safe: either the whole thing happened (retry skips) or none of it did (retry re-does).

Where does dedup live? At every hop, keyed by that hop's input. A tempting wrong answer is "dedup once, at the front door." But each of the four hops retries independently — a lost ack between fulfillment and its log has nothing to do with the front door — so a duplicate can be born at any hop, not just ingest. Dedup must therefore sit at the boundary of every consumer, each remembering the keys it has applied. The idempotency key is stamped once by the original producer and carried unchanged through all four hops (it rides in the message, alongside the trace ID of Lesson 17), so each hop dedups the same logical order even as the message is transformed along the way. Dedup is a property of the consumer, not of the channel.

Poison messages: retrying forever is a bug, not a virtue

At-least-once says "retry until success." But some messages never succeed: a malformed event that fails to parse, or one that references an order row a bug already deleted. Retry it and it fails again, identically, forever — burning CPU and, worse, if the log is ordered (Lesson 9 keeps a partition in order), the poison message sits at the head and blocks every good message behind it. Estimate the damage: a partition doing 500 msg/s, retried 5 times with exponential backoff (1+2+4+8+16 = 31 s) before giving up, delays 500 × 31 ≈ 15,500 perfectly good orders stuck behind one bad one. The fix is quarantine: after a bounded number of attempts, move the poison message out of the main flow into a dead-letter queue and let the partition proceed. We trade the strict ordering promise for that one message (it's now handled out of band) in exchange for the throughput of every message behind it — usually a trade worth making, and one you must make consciously.

The DLQ is quarantine, not a landfill. A message lands in the DLQ carrying why it failed (the exception, the stack, the hop, the attempt count, the trace ID). That turns a silent black hole into an operable queue: engineers triage it (is this a bad message, or a bug in our code that failed a good message?), fix the cause (patch the parser, restore the row, deploy), and then replay — re-inject the DLQ'd messages back into the pipeline. Because every consumer is idempotent, replay is safe: any message that had partially succeeded before dying is skipped on the way through. The DLQ is where "never lose it" and "don't block on it" are reconciled — the message is neither dropped nor blocking; it's parked, visible, and recoverable.

The trade you are buying into

Certainty is not free; it is state you must store and manage. At-most-once is cheap and simple — no retries, no dedup store, no DLQ — and it loses data. Effectively-once buys correctness with three standing costs: a dedup store at every hop (remembering keys), an un-acked backlog (messages held until acked, so a slow consumer grows the queue — Lesson 28's backpressure), and a DLQ (quarantined messages plus tooling to triage and replay them). Every one of those is in-flight state — memory of work not yet provably finished — and it costs storage, adds a lookup to the hot path (latency), and needs its own lifecycle (TTLs, expiry, monitoring). Name the trade plainly: delivery certainty & operability vs pipeline latency & the storage of in-flight state. You are paying, in bytes and milliseconds, for the guarantee that nothing is lost and nothing counts twice.

The model in one line: choose at-least-once transport (never lose) and make every consumer idempotent by committing its effect and its dedup key in one atomic step keyed by a producer-stamped idempotency key carried through all hops (never double-count) — that is effectively-once; quarantine poison messages to a dead-letter queue after bounded retries so one bad message can't block a partition; and triage + replay the DLQ (safe because consumers are idempotent) — paying for all of it in the storage of in-flight state.

Move 3 — Trace the paths

Four scenarios: a clean message, a duplicate that gets absorbed, a poison message that gets quarantined, and a DLQ message that gets replayed.

Path A — the happy path: delivered once, effect once

  Order O-77 placed. Producer stamps idempotency key = O-77.

    ingest:   see O-77 (new) -> write order row + key O-77  (ONE txn)
              -> ack log-1. Publish to log-2 with key O-77.
    payment:  see O-77 (new) -> charge card, passing key O-77 to provider
              -> record key O-77 with the charge (ONE txn) -> ack.
    fulfill:  see O-77 (new) -> reserve stock + key O-77 (ONE txn) -> ack.
    notify:   see O-77 (new) -> send email + key O-77 -> ack.

    Result: charged once, shipped once, emailed once. Key O-77 now
    recorded at all four hops. Any later re-arrival is a no-op.

Path B — a duplicate: absorbed, not applied

  At the payment hop, the charge succeeds but the consumer crashes
  BEFORE its ack reaches log-2. (0.05% of deliveries -> ~1/s here.)

    broker: no ack for O-77 -> REDELIVER O-77  (this is at-least-once)
    payment (on restart): see O-77
        -> dedup check: key O-77 already recorded WITH the charge?  YES
        -> skip the charge entirely, just ack.            (idempotent)

    The card is charged ONCE. The duplicate delivery changed nothing.
    Why it's safe: the charge and the key were ONE atomic commit, so
    "key present" is proof the effect already happened. (L13/L33)

Path C — a poison message: quarantined so it can't block

  O-99's payload references a deleted product row. It fails EVERY time.

    attempt 1 fail -> backoff 1s -> attempt 2 fail -> 2s -> ... -> attempt 5 fail
        (meanwhile, if the partition is ordered, ~500 msg/s pile up behind it:
         500 x (1+2+4+8+16 = 31s) ~= 15,500 good orders delayed.)

    attempts exhausted -> MOVE O-99 to the DEAD-LETTER QUEUE with:
        { key: O-99, hop: fulfillment, error: "product 4412 not found",
          stack, attempts: 5, trace-id: ... }
    -> the partition advances. Good orders behind O-99 flow again.

    Trade made consciously: O-99 loses its in-order place (handled out of
    band) so the 15,500 behind it aren't held hostage. (L09 ordering vs L28 flow)

Path D — replay: fix the cause, re-inject, dedup protects you

  Triage the DLQ: O-99 failed because a bug deleted product 4412.
  Root cause is a BUG in us, not a bad message -> the order is valid.

    1. fix: restore product 4412, deploy the patched fulfillment code.
    2. replay: re-inject O-99 (and its DLQ cohort) into log-3.
    3. fulfillment sees O-99: dedup check -> key O-99 NOT yet recorded
       (it never succeeded) -> reserve stock + key O-99 (ONE txn) -> ack.
       downstream notify sees O-99 (new) -> emails the receipt.

    If O-99 had PARTIALLY succeeded before dying, the recorded key would
    make the replay a no-op at that hop. Idempotency makes replay SAFE
    to run even in bulk, even more than once.

Path A is the boring 99.9% we design around. Path B is the payoff of idempotency: the duplicate that at-least-once guarantees will happen is turned into a harmless no-op, because the effect and its key committed together. Path C is the payoff of quarantine: one unfixable message is pulled aside instead of poisoning a whole partition — the conscious trade of one message's ordering for thousands of messages' throughput. Path D is the payoff of the whole design: because every hop is idempotent, recovery is not a delicate hand-surgery of "which files are corrupt" — it's "fix the cause, replay the queue, let dedup sort out what already happened." Losing is impossible, double-counting is impossible, and stuck is temporary.

Move 4 — Find the first bottleneck: certainty is stored state, and it has a bill

The guarantee works. What it costs is memory — of every key seen, every message not yet acked, every message quarantined — and each of those piles up.

The first bottleneck — the dedup store grows without bound unless you bound the window. Every hop must remember every key it has applied, or a late duplicate slips through. Count it: 2,000/s × 4 hops × 86,400 s = 691.2 million keys applied per day; at ~50 bytes each that's ~35 GB/day of dedup state, and it grows every day forever. You cannot remember every key for all time, so you remember them for a window — a TTL long enough to outlive the longest possible retry. If a duplicate can only re-arrive within, say, 24 hours (the broker's max redelivery horizon plus a safety margin), keep keys 24 h and expire the rest → the store holds a rolling ~35 GB instead of an ever-growing mountain. The dial is exactly Lesson 8/48's cache-window tension reborn: a longer dedup window catches later duplicates but costs more storage; a shorter one is cheaper but risks a very-late duplicate sneaking past. (When even that is too much, a bounded-memory approximate filter — Lesson 21's Bloom filter — trades a tiny false-positive rate for constant memory: it may occasionally skip a new message it wrongly thinks it saw, so you use it only where a rare miss is acceptable.)

The second wall — the dedup check is a lookup on the hot path, and the un-acked backlog is backpressure. Every message now pays for a dedup lookup before it can act — a read against the key store on the critical path of every hop (Lesson 48's "a cache check in front of every request"). Keep that store fast (in-memory / co-located) or the guarantee taxes latency. Meanwhile, at-least-once means a message stays un-acked — held, redeliverable — until the consumer provably finishes, so a slow or stuck consumer doesn't drop messages; it accumulates them. That backlog is Lesson 28's backpressure with a new name: the queue depth is the visible measure of "work promised but not yet provably done." It's a feature (nothing is lost while you're behind) and a hazard (unbounded backlog eventually exhausts the broker), so it needs the same watching, autoscaling (Lesson 27), and flow control as any queue.

The third wall — "prove it was handled," and the effectively-once boundary. The pipeline's real promise is auditable: for any order, can you prove it was charged once and shipped once? That proof is the in-flight state — the recorded idempotency keys and the DLQ are the ledger of what happened and what didn't (pair them with Lesson 17's trace IDs to follow one order across all four hops). But be honest about the boundary of "exactly-once": it holds only for effects you can make idempotent. A database write, yes (dedup key in the same transaction). A charge through a provider that honors your idempotency key, yes. But a non-idempotent side effect with no dedup hook — firing a physical relay, sending an SMS through a gateway that ignores keys — can still happen twice, because there's no atomic "effect + key" to lean on. The rule the whole lesson rests on has an edge: effectively-once reaches exactly as far as your effects can be made to dedup, and no further. Push dedup as close to the irreversible action as you can, and where you can't, prefer an effect that's safe to repeat (send the same receipt email twice ≈ annoying; charge twice ≈ a refund).

So the honest design for our pipeline is: choose at-least-once transport on every hop (Lesson 9's durable log) so nothing is ever lost; make every consumer idempotent by committing its effect and a producer-stamped idempotency key in one atomic step (Lesson 13/33), so the duplicates at-least-once guarantees are absorbed and the net effect is effectively-once; carry that key (and a trace ID, Lesson 17) unchanged through all four hops so each dedups the same logical order; quarantine poison messages to a dead-letter queue after bounded retries so one bad message can't head-of-line-block a partition (Lesson 9 ordering traded for Lesson 28 throughput), and give the DLQ real triage + replay tooling (safe because consumers are idempotent); bound the dedup window with a TTL so the key store is rolling, not infinite (Lesson 8/48's window dial, Lesson 21's filter when memory is tight); watch the un-acked backlog as backpressure (Lesson 28) and autoscale consumers (Lesson 27); and remember the effectively-once boundary — it holds only as far as your effects can be made to dedup. Every choice names its price: never-lose costs retries and backlog; never-double costs a dedup store and a hot-path lookup; never-block costs a DLQ and lost strict ordering for the quarantined few; prove-it-was-handled costs the storage of the whole ledger.

The deepest point: "exactly-once" was never a property of the wire — it's a property of the effect. The transport can only ever promise at-most-once (may lose) or at-least-once (may duplicate); the network's two-generals problem forbids more. Everything reliable is built by picking at-least-once and then designing the duplicate out of the effect — a stable key, an atomic effect-plus-key commit, and dedup at every consumer. The dead-letter lifecycle is the same philosophy applied to the messages that don't fit: don't drop them (that would lose), don't retry them forever (that would block), park them where they're visible and replayable. The standing tension, from Lesson 9's log to here: delivery certainty & operability vs pipeline latency & the storage of in-flight state.

The four traps

  • Trap 1 — chasing exactly-once delivery. The network's two-generals problem forbids it: you must tolerate either loss (at-most-once) or duplication (at-least-once). Stop trying to prevent duplicates on the wire; prevent them in the effect, with idempotency. Exactly-once is a property of what you do, not of how it arrives.
  • Trap 2 — dedup that isn't atomic with the effect. Recording the key before the effect can silently lose a charge on a crash; doing the effect before recording the key re-does it. The check, the effect, and the key must land in one commit (L13/33), or you've built the illusion of idempotency without the substance.
  • Trap 3 — retrying a poison message forever. A message that fails every time will fail every retry, burning CPU and — in an ordered partition — blocking thousands of good messages behind it (~15,500 in our estimate). Bound the retries and quarantine to a DLQ so the pipeline flows; retrying harder never fixes a bad message.
  • Trap 4 — a DLQ with no tooling (a black hole). A dead-letter queue nobody triages or replays is just silent data loss with extra steps. It must carry the failure reason, be monitored/alerted on, and have a safe replay path (safe precisely because consumers are idempotent). Quarantine without recovery isn't reliability.

Where we landed

We took the reliability tricks we'd built one hop at a time — the durable log (Lesson 9), the retry-safe charge (Lesson 13), the transactional outbox (Lesson 33) — and threaded them into one four-hop order pipeline, then defined and guaranteed what "delivered" means end to end. Estimate proved exactly-once delivery is impossible (the two-generals gap: you must tolerate loss or duplication) and that duplicates are not rare — at 0.05% crash-before-ack, a busy pipeline manufactures ~86,400 double-charges/day at one hop if you do nothing. Model chose the only real answer: at-least-once transport + idempotent consumers = effectively-once, with dedup living at every hop keyed by a producer-stamped idempotency key, and the effect committed atomically with its dedup key so a crash can neither lose nor double it. Tracing showed a clean order, a duplicate absorbed into a no-op, a poison message quarantined to a dead-letter queue before it could head-of-line-block ~15,500 good orders, and a DLQ message safely replayed after the cause was fixed. The first bottleneck was that certainty is stored state: the dedup store grows ~35 GB/day and needs a bounded TTL window (Lesson 8/48/21); the dedup lookup taxes the hot path and the un-acked backlog is backpressure (Lesson 27/28); and "exactly-once" reaches only as far as your effects can be made idempotent. Every dial named its trade. The standing tension, straight from Lesson 9's log: delivery certainty & operability vs pipeline latency & the storage of in-flight state.
