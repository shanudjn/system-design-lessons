Bulk & Batch APIs: Collapsing 200 Round Trips Into Two

Lesson 18 paged one GET /feed down to a phone and mentioned, in passing, that a client fetching each item's details separately re-creates an N+1 — a pattern that "batching fixes." This lesson makes that concrete. One screen: a social app's home feed shows 200 posts, and each post is written by an author whose name and avatar the screen must display. The feed call returns 200 posts, each carrying an author_id. The naïve client now fires one request per author — 200 more calls to paint one screen. We'll estimate why that is the silent latency killer even when every individual call is fast (the cost is the round-trip count, not the work), model the three fixes that collapse it — a batch endpoint, server-side request coalescing / DataLoader, and field selection — and the over-fetch vs under-fetch tension underneath them, trace the N+1 happening, a batch endpoint erasing it, and a GraphQL-style query that looks like one call but fans out to N+1 inside the resolver until a DataLoader coalesces it, and find the first bottleneck: a batch is a new unit of failure, latency, and load — one unbounded batch becomes a slow all-or-nothing query, a partial failure that sinks 200 good items, or a scatter-gather that just moved the N+1 onto the server; and collapsing cacheable GETs into one uncacheable POST throws away the edge cache. The trade under all of it: fewer round trips & payload control vs API, caching & failure-handling complexity.

The one system we'll build

A mobile app's home feed. The client calls GET /feed?limit=200 (Lesson 18's paged endpoint) and gets back 200 posts. Each post has text, a timestamp, and an author_id — but not the author's name or avatar, because the feed table stores the id, not a copy of the profile (Lesson 12/24: don't denormalize a mutable name into every post). To render the screen, the client needs, for each of the 200 posts, the author's display name and avatar URL. The naïve approach — the one every framework makes easy — is a loop: for each post, call GET /users/{author_id}. That's the N+1: 1 call to get the list, then N = 200 calls to get each item's related data. It works in the demo with 3 posts on office Wi-Fi. It falls apart at 200 posts on a train. The whole lesson is about turning that 1 + N into a small constant number of calls without giving up on always having the freshest name.

  THE N+1: one screen, 200 posts, each needs its author's name+avatar.

    client                         server / DB
      |  GET /feed?limit=200  ----> [200 posts, each w/ author_id]
      |  <----------------------
      |
      |  GET /users/17   -------->  [user 17]     \
      |  GET /users/4    -------->  [user 4]       |  200 SEPARATE
      |  GET /users/17   -------->  [user 17 again]|  round trips,
      |  GET /users/88   -------->  [user 88]      |  many duplicates
      |     ... 196 more ...                       /
      |
   1 list call + N item calls  =  1 + 200  =  201 round trips

   Each call is FAST on its own (~3 ms of server work).
   The killer is the COUNT x the network round-trip time, not the work.

The one idea the whole lesson turns on: a network round trip has a fixed floor — the time for a request to reach the server and the response to come back — that has nothing to do with how little work the server does. On a phone that floor is ~100 ms whether the handler takes 1 ms or 50 ms. So the cost of a screen isn't the work, it's the number of round trips × that floor. The fix is never "make each call faster." It's "make fewer calls" — bundle the N item fetches into one request. Everything else (coalescing, field selection, batch caps) is machinery around that one move.

Words we'll earn before we lean on them

  • Round trip / RTT — one request out and its response back. Its time is dominated by network latency (~100 ms on mobile), not server work.
  • N+1 problem — 1 query/request to fetch a list, then N more to fetch each item's related data; the classic hidden performance bug (Lesson 18 in GraphQL, Lesson 17's N+1 of feature-store calls).
  • Batch endpoint / multiget — one endpoint that takes many keys and returns many results in a single request (e.g. POST /users:batchGet {ids:[...]}), backed by one set query (WHERE id IN (...)).
  • Request coalescing / DataLoader — a server-side collector that gathers all the per-item lookups issued within one request (or one tick), de-duplicates the keys, and fires a single batched query for them.
  • Field selection — the client naming exactly which fields it wants (a sparse fieldset / field mask, or a GraphQL query) so the response carries no more than needed.
  • Over-fetch — the endpoint returns more than the client needs (the whole 2 KB user when 40 B of name+avatar would do).
  • Under-fetch — the endpoint returns too little, forcing the client to make another call for the rest — re-creating round trips.
  • Chatty vs chunky — a chatty interface makes many small calls; a chunky one makes few big calls. The dial this lesson turns.
  • Scatter-gather — one request the server must fan out to many backends/shards and reassemble (Lesson 3/19).
  • Partial failure — some items in a batch succeed and some fail; the response must report per-item status, not one all-or-nothing code.

Move 1 — Estimate: why round trips, not work, are the killer

The instinct "each GET /users/{id} is tiny, 200 of them can't be that bad" is exactly the trap. Put real numbers on it and the round-trip count dominates everything.

Force 1 — network: the round-trip floor times the count. A mobile round trip is ~100 ms (cellular RTT; office Wi-Fi hides this, which is why the bug ships). The screen needs 201 requests (1 feed + 200 authors).

  • Sequential (a naïve for loop, awaiting each): 201 × 100 ms = 20,100 ms ≈ 20 s. The user has closed the app.
  • Parallel, 6 at a time (HTTP/1.1 caps ~6 connections per host): ⌈200/6⌉ = 34 rounds + the feed = ~35 rounds → 35 × 100 ms = 3.5 s. Better, still ~7× over the ~500 ms "feels instant" bar, and it pins the radio and drains battery.
  • HTTP/2, all 200 in flight on one connection: the transport collapses to ~1–2 RTT, but the server now handles 201 requests, each paying its fixed overhead — TLS/framing, auth check, logging, a DB round trip. Even at ~3.5 ms each that's 200 × 3.5 ms = 700 ms of CPU, and 200 concurrent handler invocations hammer the connection/thread pool (Lesson 28 backpressure) for data one query returns in ~5 ms.

There is no transport trick that fixes this, because the problem isn't the pipe — it's that you asked 200 separate questions. Multiplexing hides the network cost; it does nothing about 200× the server overhead and pool pressure. The only real fix is to ask fewer, bigger questions.

Force 2 — payload: over-fetching multiplies the bytes. A full user object is ~2 KB (bio, settings, follower counts, preferences). The screen needs only name + avatar URL ≈ 40 B. Fetch 200 full users and you move 200 × 2 KB = 400 KB to use 200 × 40 B = 8 KB — 50× wasted bytes over a metered, high-latency mobile link. Over-fetching turns a fast call into a slow one and a cheap screen into an expensive one.

The naïve fix (a skinnier endpoint like /users/{id}/name) over-corrects into under-fetching: now the avatar needs a second call, and you're back to multiplying round trips. The two errors point in opposite directions, which is why field selection (Move 2) exists — let the client name the 40 B it wants, in one shape that serves every screen.

The target. Replace the 200 author calls with one batch call over just the ids the feed returned, asking for just the two fields:

POST /users:batchGet  { ids:[17,4,88,...], fields:["name","avatar"] }

Server runs one SELECT id,name,avatar FROM users WHERE id IN (<deduped ids>) — ~200 primary-key index seeks ≈ ~2 ms (Lesson 12's B-tree), payload 8 KB. Screen load becomes feed + batch = 2 round trips ≈ 200 ms, versus 201 trips and ~3.5–20 s. ~100× fewer round trips, ~50× fewer bytes, from one endpoint shape.

Why "just parallelize the 200 calls" is the seductive wrong answer: firing all 200 at once feels like the fix — it drops 20 s to 3.5 s — but it treats a design problem as a concurrency problem. You still pay 200× the per-request server overhead (700 ms of CPU, 200 pool slots), you still can't cache or reason about it as one unit, and you've made the client hammer the server with a burst it must now defend against (Lesson 8 rate limiting, Lesson 28 shedding). Parallelism moves the wait around; batching removes the calls. The right instinct is never "make the N calls faster or more concurrent." It's "there should not be N calls."

Move 2 — Model: three ways to collapse the N+1

Fix 1 — the batch endpoint (multiget): change the API shape

Add an endpoint that takes many keys and returns many results: POST /users:batchGet {ids:[...]}, or a cache-friendly GET /users?ids=4,17,88. The client collects all 200 author_ids from the feed, de-duplicates them (a feed of 200 posts might have only ~60 distinct authors — dedup alone can cut the work 3×), and sends one request. The server answers with one set query (WHERE id IN (...)) instead of a loop of point reads. The N+1 becomes 1 + 1.

The cost is API surface: every "list of ids → list of objects" relationship wants a batch variant, and the response is now a map (id → object or "not found") the client must re-join to its posts. The batch also needs a size cap and partial-failure semantics (the bottleneck, Move 4) — a single object endpoint needed neither.

Fix 2 — request coalescing / DataLoader: batch without changing the client

Sometimes you can't change the caller — a page's components each independently ask for "the author of post X," or a GraphQL resolver is defined per-item and naturally fires one lookup per post. A DataLoader (request-coalescing loader) sits between that code and the database: instead of running each load(id) immediately, it collects the ids requested within one tick (or one request), de-duplicates them, and fires a single batched query for the whole set, then hands each caller its result. The code still reads as "fetch one author per post," but underneath, 200 load() calls become one WHERE id IN (...). It usually also holds a per-request cache so the same id asked twice is fetched once. This is the server-side twin of the batch endpoint — same collapse, but the batching is invisible to the calling code.

Fix 3 — field selection: send only the bytes needed

Let the client name the fields: ?fields=name,avatar (a sparse fieldset / field mask) or a GraphQL query that lists exactly the fields the screen renders. The response carries 40 B, not 2 KB — killing the over-fetch — and the same endpoint serves a screen that wants five fields and one that wants two, killing the under-fetch (no need for a zoo of skinny endpoints). Field selection controls the payload; batching controls the round trips — they're orthogonal, and you usually want both. The catch: GraphQL's field selection makes it trivial to write a query that walks posts → author → name, and the per-post author resolver quietly re-creates the N+1 on the server — which is exactly why GraphQL servers lean on Fix 2 (DataLoader) to survive (Lesson 18's "resolver reintroduces the N+1").

Why the two problems are separate. "Too many round trips" and "each response too fat" feel like one problem — "the API is slow" — but they have different fixes and you can have either without the other. A single fat GET /users/{id} over-fetches (2 KB) with no N+1. A perfectly slim /users/{id}/name under-fetches and creates round trips. Batching fixes the count; field selection fixes the size. Fixing one and not the other leaves half the tax on the table — a batch of 200 full users is one round trip but still 400 KB. Do both: one call, exact fields.

Move 3 — Trace the paths

Three renders of the same 200-post screen: the N+1 as it actually happens, a batch endpoint erasing it, and a GraphQL query that hides an N+1 until a DataLoader coalesces it.

Path A — the N+1 as it really unfolds

  Client renders 200 posts, each needs author name+avatar.

    GET /feed?limit=200      -> 200 posts [{id, text, author_id}, ...]
    for each post:
       GET /users/{author_id}   (fires 200 times; ~60 distinct ids,
                                  so ~140 are DUPLICATE fetches)
    total: 1 + 200 = 201 round trips
    wall clock: 20 s sequential / 3.5 s at 6-way parallel
    server: 201 handler runs, ~700 ms CPU, 200 pool slots burned

  Works with 3 posts on Wi-Fi. Dies with 200 on cellular.

Path B — a batch endpoint erases it

  Same screen, one extra endpoint.

    GET /feed?limit=200      -> 200 posts, collect author_ids
    client dedups ids        -> [17,4,88,...]  (~60 distinct)
    POST /users:batchGet { ids:[...], fields:["name","avatar"] }
       server: SELECT id,name,avatar FROM users WHERE id IN (...)
               ~60 PK index seeks ~= 2 ms, payload ~2.4 KB
       -> { "17":{name,avatar}, "4":{...}, ... , "999":null }  (map)
    client joins the map back onto its 200 posts

    total: 2 round trips (feed + batch)  ~= 200 ms
    round-trip cut ~100x, byte cut ~50x, one DB query not 200.
    NOTE the "999":null -- a missing/deleted user is a per-item
    result, not a failed batch (Move 4).

Path C — GraphQL hides an N+1 until DataLoader coalesces it

  ONE query goes out; the N+1 hides on the SERVER.

    query { feed(limit:200){ text author { name avatar } } }
      |
      v  server resolves:
      feed resolver     -> 200 posts
      author resolver   -> called ONCE PER POST = 200 times !!
                           (N+1 moved server-side; client sees 1 call)

    Fix: wrap the author load in a DataLoader.
      author resolver calls loader.load(author_id)   x200
      loader collects the tick's ids, dedups -> ~60
      fires ONE  SELECT ... WHERE id IN (...)  -> hands each its row

    client: 1 round trip.  server: 1 feed query + 1 batched user query.
    Field selection gave payload control; DataLoader gave round-trip
    (query) control. You needed BOTH.

Path A is the tax in full: 201 trips, most of them duplicate fetches of the same ~60 authors, ~700 ms of pointless server CPU. Path B is the client-side cure: one batch call, one IN query, a map re-joined on the client — and it already shows the bottleneck's edge (a deleted user comes back as null, a per-item outcome, not a batch-wide failure). Path C is the subtle one: field selection can make the round-trip count look solved while the N+1 lives on inside the resolver, and only a coalescing loader actually collapses the server work. The first three moves make batching look like a free win. Move 4 is where the batch's own costs — failure, latency, load, cacheability — come due.

Move 4 — Find the first bottleneck: a batch is a new unit of failure, latency & load

Collapsing 200 calls into 1 doesn't delete the work — it fuses it into a single request that now succeeds, fails, waits, and loads as one thing. That fusion is the source of every problem below.

The first bottleneck — the unbounded batch. If the endpoint accepts any number of ids, a client (buggy or hostile) sends ids:[...100,000...]. Now one request is a 100k-key IN query (a slow, planner-punishing scan), a response of 100,000 × 2 KB = ~200 MB (a memory spike that can OOM the handler, Lesson 28), and a single unit of work big enough to be a denial-of-service all by itself. A batch endpoint without a size cap is a DoS you built yourself. The fix is a hard cap (say 100–1,000 ids/batch) plus pagination of the batch itself (Lesson 18): the client sends the 200 ids as, e.g., two calls of 100. You've re-introduced a round trip — but 2 or 3, not 200. The cap size is the dial: bigger = fewer trips but fatter, slower, riskier requests; smaller = safer but chattier.

The second wall — partial failure and tail latency. One call for 200 items is one status code and one latency — and that's the problem. If id 999 was deleted, does the whole batch 500 and sink 199 good rows? It must not: a batch response is a list of per-item results ({"17":{...}, "999":{"error":"not_found"}}), so one bad key can't fail the other 199 (Lesson 32's "some steps commit, some don't"). And the batch's latency is the slowest item's latency — if 199 users are cached and one is on a cold, slow shard, the whole response waits for it (Lesson 17's tail latency, now fused into one request). A single-item call could fail or lag alone; a batch shares one fate across all its items unless you deliberately design per-item outcomes.

The third wall — batching the wire is not batching the work. The client now makes 1 call, but if the server implements batchGet as a for id in ids: db.get(id) loop, the N+1 didn't die — it moved server-side, and it's now 200 sequential DB round trips inside one slow handler (often worse, because there's no client parallelism left). The batch must become one set operation: a single WHERE id IN (...), or — if users are sharded by id across, say, 16 nodes (Lesson 3/4) — a scatter-gather that groups the ids per shard, fires one multiget per shard in parallel, and merges (Lesson 19/21's "local compute, central union"). Batch the work, not just the wire; otherwise you paid for a new endpoint and kept the N+1.

The fourth wall — batching burns the cache. Two hundred individual GET /users/{id} calls are each independently cacheable — at the CDN/edge (Lesson 14) and in the client (Lesson 2) — so the same author seen on the next screen is a free hit, and a popular author is served from the edge to everyone. One POST /users:batchGet is uncacheable (a POST body, and a near-unique id set no two screens share). Batching trades edge-cacheability for round-trip count. The middle path: a cache-friendly batch — GET /users?ids=4,17,88 with the ids sorted so the URL is stable and cacheable — or coalesce client-side while still hitting per-id caches underneath. The dial is Lesson 2/14's freshness-and-reuse against this lesson's round-trip count: chatty & cacheable vs chunky & uncacheable.

So the honest picture of bulk APIs: a screen that needs N related records must not make N calls, because a screen's cost is round trips × the ~100 ms RTT floor, not the trivial per-call work (Lesson 18/17's N+1). You collapse the N+1 three ways — a batch endpoint (client bundles the ids, server runs one set query), request coalescing / DataLoader (the same collapse made invisible to the calling code, the fix GraphQL's per-item resolvers require), and field selection (name the exact fields, killing over- and under-fetch) — and batching (round trips) and field selection (payload) are orthogonal so you want both. You pay for it by accepting that a batch is a new unit: cap its size and paginate it or it's a self-inflicted DoS; give it per-item results or one bad id sinks the batch and one slow id sets the whole latency (Lesson 17/32); implement it as one set/scatter-gather query or the N+1 just moved to the server; and know it can't be edge-cached the way the individual GETs could (Lesson 2/14). Every choice names its price: batching costs API surface, cacheability, and failure-handling; field selection costs cache-key explosion; a bigger batch costs tail latency and blast radius.

The deepest point: the N+1 is not a database bug or a client bug — it's a boundary-crossing bug. Every one of those 200 author fetches is cheap; what's expensive is crossing the network boundary 200 times, because a boundary crossing has a fixed floor that dwarfs the work on either side. So the cure is always the same shape — move the fan-out to the side of the boundary where it's cheap: do the 200 lookups as one set operation inside the datacenter (one IN query, one scatter-gather), and cross the expensive client↔server boundary once. Batching, DataLoader, GraphQL-with-a-loader are three spellings of that one idea. The standing tension, unchanged since Lesson 18 first paged a feed: fewer round trips & payload control vs API, caching & failure-handling complexity.

The four traps

  • Trap 1 — an unbounded batch. No size cap means a client can request 100,000 ids → a slow mega-query, a ~200 MB response, an OOM, a self-built DoS. Always cap batch size and paginate the batch (L18/28); the cap is a dial (bigger = fewer trips but fatter/riskier requests).
  • Trap 2 — one status for the whole batch. Returning a single 500 when one of 200 ids is missing sinks 199 good results, and a single latency means one slow item drags the whole response (L17). A batch response must be a list of per-item results (L32), not all-or-nothing.
  • Trap 3 — batching the wire but looping on the server. A batchGet implemented as a per-id loop just relocated the N+1 into the handler, often serialized and slower. Express it as one set query (WHERE id IN) or a per-shard scatter-gather (L3/19) — batch the work.
  • Trap 4 — collapsing cacheable GETs into one uncacheable POST. 200 individual GETs are each edge- and client-cacheable (L2/14); one POST batch is not. Weigh the round-trip win against the lost cache; reach for a cache-friendly GET-with-sorted-ids or client-side coalescing when reuse is high.

Where we landed

We took Lesson 18's throwaway line — "fetch each item separately and you've re-created the N+1" — and made it a whole system. Estimate priced the round-trip tax: a 200-post screen that fetches each author separately is 201 round trips ≈ 20 s sequential (3.5 s even 6-way parallel, ~700 ms of pointless server CPU), and fetching full 2 KB users for 40 B of name+avatar wastes 50× the bytes — the killer is the round-trip count × the ~100 ms RTT floor, not the trivial per-call work, so no transport trick can save it. Model gave three collapses: a batch endpoint (bundle the ids, one WHERE id IN set query → 1 + 1), request coalescing / DataLoader (the same collapse made invisible to per-item code, the fix GraphQL resolvers require), and field selection (name the exact fields, killing over- and under-fetch) — batching for round trips and field selection for payload, orthogonal, both wanted. Tracing watched the N+1 unfold (201 trips, mostly duplicates), a batch erase it (2 trips, one query, ~100× fewer round trips), and a GraphQL query hide an N+1 inside its resolver until a DataLoader coalesced it. The first bottleneck was the batch's own nature as a fused unit: cap its size and paginate it or it's a self-inflicted DoS; give it per-item results or one bad/slow id sinks or stalls the rest (L17/32); make it one set/scatter-gather query or the N+1 just moved server-side (L3/19); and accept it can't be edge-cached like the individual GETs (L2/14). The deepest point: the N+1 is a boundary-crossing bug — move the fan-out to the cheap side of the network boundary and cross the expensive one once. The standing tension, unchanged since we first paged a feed: fewer round trips & payload control vs API, caching & failure-handling complexity.

Next up — we've made reads cheap to gather. Now face a data-quality problem hiding in every large dataset: the same real thing stored twice.

• Deduplication & entity resolution at scale (Lesson 73): across 500M customer rows, "are these two records the same person?" Comparing every pair is N² ≈ 1.25×10¹⁷ comparisons — impossible — so blocking keys group plausible matches to shrink the candidate set, similarity scoring ranks them, MinHash / LSH (Lesson 65's nearest-neighbours) finds near-duplicates without the N², and a survivorship rule decides which record wins the merge. Trade: match recall vs precision & compute cost.
