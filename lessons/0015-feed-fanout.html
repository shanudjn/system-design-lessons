Feed Fan-out: Delivering One Post to a Million Timelines

Lesson 14 asked "do the work before the request or during it?" for bytes, and answered before — precompute a copy near the reader. This lesson asks the exact same question for timelines. We take one concrete system — a social app where you post short updates and see a home feed of recent posts from the people you follow — and trace what happens when you tap Post. There are two honest ways to build the feed: do the work when someone writes a post (copy it into every follower's inbox), or do the work when someone reads their feed (gather posts from everyone they follow, on the spot). We'll estimate which is cheaper, model both, trace the post-path and the read-path, and then hit the wall that breaks the simple answer: the celebrity with 50 million followers.

The one system we'll trace

A social app. Every user has a home feed: a reverse-chronological list of recent posts from the accounts they follow. When Ada taps Post, her update must eventually appear in the feed of each of her followers. When Ben opens the app, he must see a fresh feed built from the ~200 accounts he follows. The whole design turns on one choice: at post time, do we push Ada's post into each follower's inbox, or do we leave it in one place and pull it together at read time? Here is both approaches on one screen.

  ONE POST → MANY FEEDS — PUSH (fan-out on write) vs PULL (fan-out on read)

  PUSH: work happens when Ada POSTS            PULL: work happens when Ben READS
  ─────────────────────────────────           ──────────────────────────────────
   Ada taps Post                                Ada taps Post
       │                                            │
       ▼  copy into every follower's inbox          ▼  just store the post once
   ┌───────────────────────────────┐           [ POSTS table ]  (one row)
   │ inbox[f1] += post              │
   │ inbox[f2] += post   (N writes) │           Ben opens app
   │  ...                           │               │  gather from the 200
   │ inbox[fN] += post              │               ▼  accounts Ben follows
   └───────────────────────────────┘           SELECT ... WHERE author IN (…200…)
       Ben opens app                                ORDER BY time  (fan-IN read)
       │  read own inbox (ONE lookup)                  merge + sort on the spot
       ▼
   [ inbox[Ben] ]  already built → fast read     read is heavy, write was cheap

Two names for the same fork. Fan-out on write = push: spraying one post out to N inboxes at post time. Fan-out on read = pull: gathering ("fanning in") from N sources at read time. Push makes the write expensive and the read trivial; pull makes the write trivial and the read expensive. The entire lesson is deciding which cost you'd rather pay — and, at the end, refusing to pick just one.

Words we'll earn before we lean on them

  • Post — one update Ada writes. Stored once in a posts table, keyed by a time-sortable id (Lesson 03's Snowflake id gives you "newest first" for free).
  • Home feed / timeline — the list Ben sees: recent posts from accounts he follows, newest first.
  • Follow graph — who follows whom. "Ada has N followers" (they see her posts); "Ben follows M followees" (he sees theirs). The two counts are different numbers for the same person.
  • Inbox / timeline cache — a per-user precomputed list of post ids, one per user. Push writes into it; a push read just reads it.
  • Fan-out on write (push) — at post time, copy the post id into every follower's inbox.
  • Fan-out on read (pull) — at read time, query every followee's recent posts and merge them.
  • Fan-out worker — a background job (fed by a queue, Lessons 05 & 09) that does the N inbox writes, so the person posting doesn't wait for them.
  • Read:write ratio — how many feed opens happen per post. This number decides which side to precompute.

Move 1 — Estimate: which side is cheaper to precompute?

The rule from Lesson 02 and 14: precompute the side that's read far more often than it changes. So the first question isn't "push or pull," it's "how lopsided is read vs write?" Let's put real numbers on our app.

Worked: the app's traffic shape.

• 100 million daily active users.
• Each user follows ~200 accounts (so, on average, each account has ~200 followers).
• Each user posts 2×/day → 200 million posts/day.
• Each user opens the feed 5×/day → 500 million feed reads/day.

Read:write ratio at the app level = 500M reads : 200M posts ≈ 2.5 : 1. Reads win — so our instinct should be to precompute the read, i.e. push. But "which is cheaper" isn't about the app-level counts; it's about the total work each strategy generates. Let's price both.

Worked: total work, push vs pull.

Push (fan-out on write). Every post is copied to each follower's inbox:
• Inbox writes = 200M posts × 200 followers = 40,000,000,000 = 40 B writes/day.
• Per second: 40 B ÷ 86,400 ≈ 463,000 inbox writes/sec — but each is a tiny append (add one id to a list).
• Reads: 500M/day ≈ 5,800/sec, and each is one lookup of an already-built inbox. Cheap and O(1).

Pull (fan-out on read). A post is stored once; the read gathers from all followees:
• Writes: 200M/day ≈ 2,300/sec — almost free.
• Read work = 500M reads × 200 followees = 100,000,000,000 = 100 B post-fetches/day ≈ 1,160,000/sec of scatter-gather, each read doing a 200-way query + merge + sort.

Push generates 40 B heavy ops; pull generates 100 B. Push does ~2.5× less total work and makes the common operation (the read) a single fast lookup. That matches the 2.5:1 read-heaviness exactly — the same posts get read many times, so paying once at write time and amortizing across reads is the better deal. For the average user, push wins.

Worked: does the inbox storage even fit? Keep the last 800 post ids per inbox; each entry is a post id + author id ≈ 16 bytes. Per inbox: 800 × 16 = 12,800 B ≈ 12.5 KB. Across 100M users: 12.5 KB × 100M ≈ 1.25 TB of timeline cache — a modest sharded key-value / Redis footprint, and it stores ids, not the posts themselves (the post bodies live once in the posts table and are hydrated at read). So push's storage cost is real but small. Its problem is elsewhere.

Name the trade-off up front: push vs pull is write-time work vs read-time work — the same "precompute vs compute-on-demand" dial as the CDN (Lesson 14) and the covering index (Lesson 12). Push pays a lot at write time to make reads instant; pull pays nothing at write time but makes every read expensive. You precompute the side that is read more than it changes — and you keep watching for the case where "write once" secretly means "write ten million times."

Move 2 — Model: the inbox, and fan-out as async work

Push needs two pieces: a per-user inbox and a fan-out worker. The inbox is a list of post ids per user (our 1.25 TB cache). The worker is what actually performs the N writes — and it must run in the background, because Ada should not wait for her post to reach 200 inboxes before her screen says "Posted."

  THE POST PATH (push), done asynchronously so the poster never waits:

  Ada taps Post
      │
      ▼
  1. INSERT into posts table            (durable: the one true copy)
      │  return "Posted ✓" to Ada now   (she's done in ~50 ms)
      ▼
  2. enqueue fan-out job {post_id, author=Ada}   (Lesson 05/09 queue)
      │
      ▼
  3. FAN-OUT WORKER pulls the job:
        look up Ada's followers  ──▶  for each follower f:  inbox[f] += post_id
        (N appends, spread across timeline-cache shards; retried on failure)

Storing the post (step 1) is synchronous and fast — one row. The expensive part (step 3, the N inbox appends) happens after Ada is told "Posted," driven by the queue. This is Lesson 05's whole point: the slow part of a request should not block the fast part. If the worker crashes mid-fan-out, the queue's visibility timeout redelivers the job (Lesson 05/09) and the appends must be idempotent — "add post_id to inbox if not present" — so a retried job doesn't double-list the post (Lesson 13).

Name the trade-off: doing fan-out async buys Ada a fast post but costs you eventual consistency on the feed. For a few seconds after Ada posts, some followers' inboxes have the post and some don't — the fan-out is still draining. For a social feed that's completely fine (nobody notices a 3-second delay). For something where the writer must see their own change immediately — "read-your-writes," Lesson 06 — you special-case it: show Ada her own post from the posts table right away rather than waiting for it to appear in her own inbox.

Move 3 — Trace the paths

Path A — the read, under push (the common case)

Ben opens the app. The server reads one key: inbox[Ben] — a ready-made list of ~800 recent post ids, already merged and time-sorted because the fan-out worker appended them in order. It takes the top ~50, hydrates them (fetch the post bodies for those 50 ids, a batched lookup often served from cache — Lesson 02), and returns the feed. Total: two round trips (inbox read, then a 50-id batch fetch), no per-followee queries, no sort over hundreds of rows. This is why push exists: 500M times a day, the read is trivial.

Path B — the read, under pull (for contrast)

The same read without precomputation: fetch Ben's 200 followees, query each one's recent posts (or one big WHERE author IN (…200…) ORDER BY time LIMIT 50), merge and sort potentially thousands of candidate rows, keep the top 50, hydrate. Every feed open pays this. It's correct and it needs almost no write-time work — but it's the 100 B-ops/day monster from Move 1, and its latency grows with how many people you follow.

Path C — the post, when the author is a celebrity

Now the crack. Push assumed ~200 followers per post. But follower counts are not uniform — they follow a power law. A handful of accounts have millions of followers. Watch what one of them does to the push model.

Worked: the celebrity fan-out storm. Suppose there are 1,000 celebrity accounts, each with an average of 5 million followers, each posting 5×/day.
• Inbox writes from celebrities alone = 1,000 × 5 posts × 5,000,000 followers = 25,000,000,000 = 25 B writes/day.
• That's 25 B out of our 40 B total push writes — ~60% of all fan-out work — generated by 5,000 posts, which is 0.0025% of the 200M daily posts.

Worse, it arrives as a spike: one celebrity post = 5 million inbox appends that all want to happen at once (a distributed thundering herd, Lesson 02/14). And most of it is wasted: if only 20% of those 5M followers open the app today, then 4 million of the 5 million appends land in inboxes nobody will read before the entries age out. Push does its most work exactly where it pays off least — spraying a post to millions of mostly-inactive followers.

Name the trade-off: push trades read speed for write amplification, and for a high-follower account the amplification is unbounded — one action becomes millions of writes. The average said "push wins." The distribution says "push is catastrophic at the tail." Averages hide tails; system design lives in the tail (Lesson 12's selectivity trap and Lesson 07's p99 were the same lesson).

Move 4 — Find the next bottleneck: the hybrid, and what still bites

The fix is not to pick a side but to route by follower count. Push for the many normal accounts (cheap fan-out, fast reads); pull for the few celebrities (skip the write storm, gather their posts at read time). The read merges the two.

  HYBRID: push the normal accounts, pull the celebrities, merge at read

  POST time:
    author's follower count < THRESHOLD  ──▶  fan-out on write (push to inboxes)
    author's follower count ≥ THRESHOLD  ──▶  do NOTHING extra (just store the post)

  READ time (Ben opens app):
    A = inbox[Ben]                       (pushed posts from his normal followees)
    B = for each CELEBRITY Ben follows:  fetch their recent posts
                                         (cached once per celebrity — shared by all fans)
    feed = merge_sort(A, B), top 50, hydrate

Worked: why the hybrid read stays cheap. Ben follows 200 accounts; say 5 of them are celebrities. His read is now 1 inbox lookup + 5 celebrity fetches. And those 5 fetches are the same "recent posts of celebrity X" that every one of X's fans needs — so they're cached once and served from memory (Lesson 02's hot key done right, because now the hot key is a feature not an accident). So the read went from "1 lookup" to "1 lookup + a handful of cache hits" — still tiny — while the write side shed the 25 B celebrity writes entirely. The 40 B/day push cost drops toward 15 B, the spikes vanish, and no work is wasted on inactive followers of celebrities.

Name the trade-off — the threshold is the dial. Set the celebrity threshold too low and too many accounts get pulled → reads fan in to many sources and slow down (drifting toward pure pull). Set it too high and a few huge accounts still trigger million-write storms (drifting toward pure push). Real systems put it in the tens of thousands to ~1M followers, and can even decide per-read (pull an account only if it's both high-follower and posted recently). The threshold trades read fan-in against write amplification — the whole push/pull tension, now a tunable number instead of a fixed choice.

The other walls this opens

  • Ranking vs chronological. If the feed is ranked by a relevance score (not just newest-first), the precomputed inbox can't just be a sorted list of ids — the score depends on Ben and changes over time. The common shape: push builds the candidate set (what's eligible), and a ranking pass scores it at read time. You precompute membership, compute order on demand — a push/pull split within one feed.
  • Deletes and edits. Ada deletes a post that push already copied into millions of inboxes. You either fan-out the delete too (another N writes) or — cheaper — leave a tombstone and filter at read: when hydrating the 50 ids, drop any whose post row is gone. Storage vs read-time work, again.
  • The inactive-user tax. Even for normal accounts, pushing to followers who never log in is wasted. A refinement: only fan out to recently-active followers, and lazily backfill a dormant user's inbox by pulling on their next login. Push for the live audience, pull to rehydrate the rest.
  • New follow / cold start. When Ben follows someone new, their past posts aren't in his inbox. You backfill by pulling that followee's recent posts once and merging — the same read-path pull, used to patch the write-path gap.

Where we landed

We took one post and asked how it reaches every follower's feed. Estimate showed the app is read-heavy (2.5 reads per post) and that push generates ~40 B ops/day versus pull's ~100 B, so precomputing the read (push) wins for the average user — while the inbox cache fits in ~1.25 TB because it stores ids, not bodies. Model built push as a durable post write plus an async fan-out worker (a queue job, idempotent appends), buying a fast post at the price of a few seconds' eventual consistency. Tracing the paths walked the cheap push read (one inbox lookup + a batched hydrate), the expensive pull read (200-way scatter-gather), and the post path that breaks when the author is a celebrity: 1,000 accounts generate 60% of all fan-out writes from 0.0025% of posts, in spikes, mostly wasted on inactive followers. The next bottleneck was that tail, fixed by a hybrid — push normal accounts, pull celebrities (cached once per celebrity), merge at read — with the follower threshold as the dial between read fan-in and write amplification, plus the follow-on walls of ranking, deletes, inactive users, and cold-start backfill. The thread of the whole lesson: a feed is a bet about where to spend work — at write time or read time — and the winning design refuses a single bet, routing each post to the cheaper side.
