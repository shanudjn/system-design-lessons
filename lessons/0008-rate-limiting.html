Rate Limiting: Token Bucket, Leaky Bucket & Distributed Counters

Our URL-shortener API offers a free tier: 60 requests per minute per API key. One morning a single key — a runaway script — starts firing as fast as it can. Last lesson's backpressure decided when the system says "no" to protect itself. Rate limiting answers the next question: who gets to say how much, and how we enforce it fairly the instant a request arrives — before it touches a database, a queue, or a leader. This lesson takes ONE noisy key and traces every decision: how big the limit is, which counting algorithm we use (and the boundary bug that lets a sloppy one leak 2× the traffic), and why a limiter that works on one server quietly breaks across ten. We name the trade-off behind each.

The one request we'll trace

A client holding API key k_42 sends POST /shorten. Before we do any real work, one gate must answer a yes/no question in well under a millisecond: has this key used up its allowance for the current slice of time? If yes, we reject it immediately with HTTP 429 Too Many Requests and never spend a database call on it. Here is the whole job on one screen.

  THE RATE-LIMIT GATE (decided before any real work)

  k_42 ──POST /shorten──►  ┌──────────────────────┐
                           │   RATE LIMITER        │   counter for k_42
                           │   "tokens left > 0?"  │   ────────────────
                           └──────────┬───────────┘   allowance: 60 / min
                              yes ◄───┴───► no
                               │             │
                               ▼             ▼
                         do the work     429 Too Many Requests
                        (db, queue…)      Retry-After: 30s   ← cheap, instant

  The gate protects everything DOWNSTREAM by spending almost nothing itself.

A rate limiter is a cheap gate that caps how often one caller can act, so no single caller can starve the rest or topple shared infrastructure. It is the front-door cousin of last lesson's load shedding: load shedding sheds anyone when the system is overloaded; rate limiting caps each named caller all the time, fairly, whether or not the system is busy.

Words we'll earn before we lean on them

  • Rate limit — the maximum number of requests one caller may make per unit of time (e.g. 60/min).
  • Throttle — to reject or delay a request because the caller is over its limit (the 429).
  • Burst — a clump of requests arriving close together, faster than the sustained rate.
  • Token bucket — an allowance modeled as tokens that refill over time; each request spends one.
  • Leaky bucket — a queue that drains (does work) at a fixed steady rate, smoothing bursts out.

Move 1 — Estimate: how big is the limit, and what does breaking it cost?

A limit has two numbers, not one: a sustained rate (how fast you may go forever) and a burst (how much you may clump up momentarily). Pick them from what the protected resource can take and what a legitimate client actually needs.

Worked: sizing the free tier. The downstream write path (leader + queue) safely handles 20,000 requests/second across all callers (that was the ceiling we found in Lesson 07). We have ~100,000 free-tier keys. If we let each key sustain 1 req/s (= our 60/min), worst case all keys go flat-out: 100,000 × 1 = 100,000 req/s — 5× over the 20,000 ceiling. So the per-key limit alone isn't enough; it must be paired with a global cap. But for the typical case, a real client makes maybe a handful of calls then pauses, so 60/min with room to burst ~60 at once covers honest use while the runaway script slams into the wall on request 61.

And the cost of getting it wrong cuts both ways. Set the limit too low and you 429 paying customers doing nothing wrong — lost trust, support tickets. Set it too high (or enforce it loosely) and one runaway key consumes the capacity meant for thousands of others — the very starvation the gate exists to prevent.

Name the trade-off: the limit is a dial between false throttling and resource starvation. The honest client and the abusive one are separated only by where you set the number and how tightly you count — so the counting algorithm in Move 2 matters as much as the number itself.

Move 2 — Model: counting requests (and the boundary bug)

The simplest counter is a fixed window: keep one integer per key for the current 60-second clock window; increment on each request; reset to zero when the window rolls over. It's one counter and one comparison — beautifully cheap. It also has a famous bug.

Worked: the fixed-window double burst. Limit = 60 per 60-second window. A client sends 60 requests at 12:00:59 (all inside window [12:00:00–12:01:00), all allowed) then 60 more at 12:01:00 (the counter just reset for window [12:01:00–12:02:00), all allowed). That's 120 requests in about 2 seconds straddling the boundary — 2× the rate we promised to enforce. The counter was never "wrong" inside either window; the windows simply don't see across their own edge.

  FIXED WINDOW — bursts hide at the seam

  window A [12:00:00 ───────────── 12:01:00) window B [12:01:00 ──────────
                                  60 reqs │ 60 reqs
                                  @ :59   │ @ :00
                              ────────────┼────────────
                                          ▲
                                 120 reqs in ~2s — each window counted 60,
                                 neither saw the other → promised 60, got 120

Two well-known fixes, then the one we'll actually trace:

  • Sliding-window log — store the timestamp of every request and count how many fall in the last 60 s on each call. Exact, but you store and scan one entry per request — costly memory for a busy key.
  • Sliding-window counter — keep the current and previous window counts and blend them by how far into the current window you are. Cheap and smooth; a good production default.
  • Token bucket — model the allowance as a refilling reserve. It handles bursts by design and is what most APIs (and our trace) use, so we'll walk it in full.

Move 3 — Trace the paths: token bucket vs leaky bucket

Path A — the token bucket (allow bursts, cap the average)

Picture a bucket that holds at most B tokens and refills at r tokens per second. Each request must take one token to proceed; if the bucket is empty, the request is throttled. Two numbers, two jobs: the capacity B sets the biggest burst; the refill rate r sets the sustained average. For our free tier: B = 60 tokens, r = 1 token/second (= 60/min). The bucket starts full.

Worked: the runaway script meets the bucket.

t = 0.0 s — bucket full at 60. The script fires 60 requests instantly. Each takes a token → all 60 allowed, bucket now 0. (The burst is honored — that's the point.)
t = 0.1 s — request 61 arrives. Bucket holds 0 (only 0.1 s × 1/s = 0.1 token refilled, not a whole one) → throttled, 429.
t = 10 s — 10 seconds have refilled 10 × 1 = 10 tokens. The script's next 10 requests pass; the 11th is throttled again.

Over a long minute the script can spend at most the 60 it started with plus 60 refilled = 120 in the first 60 s, then a steady 60/min forever after. Burst up to B once, then clamped to the refill rate r. Honest clients who never burst never even notice the bucket.

  TOKEN BUCKET  (B = 60 capacity, r = 1 token/sec)

        refill 1 token/sec
              │  drip
              ▼
        ┌───────────┐   take 1 token per request
        │ ● ● ● ●    │   ─────────────────────────►  allowed
        │ ● ● ●      │   bucket empty? ───────────►  429 throttled
        └───────────┘
   capacity B = biggest burst   ·   rate r = sustained average

The implementation is lazy and O(1): you don't run a timer adding tokens. You store (tokens, last_refill_time) and, on each request, add (now − last_refill) × r tokens (capped at B) before checking for one. Cheap enough for the hot path.

Path B — the leaky bucket (smooth everything to a steady drip)

A leaky bucket flips the picture: requests pour into a queue of fixed size and are let out — actually processed — at a constant rate, like water leaking from a hole. A burst fills the queue but the output stays a perfectly even stream; overflow past the queue size is dropped.

  TOKEN BUCKET                         LEAKY BUCKET
  ─────────────                        ─────────────
  burst of 60 → all 60 pass NOW        burst of 60 → queue fills, output
  then clamp to r afterward            drips out at a fixed 1/s, smooth
  spiky output, bursty-friendly        even output, burst latency added
  good for APIs (let clients clump)    good for protecting a fragile
                                        downstream that hates spikes

Name the trade-off: token bucket trades smoothness for burst tolerance — it lets a client clump requests (great for interactive APIs) but passes that spike straight downstream. Leaky bucket trades burst tolerance for smoothness — it guarantees a steady output rate (kind to a fragile dependency) but adds latency to bursts and drops the overflow. Choose by what you're protecting: token bucket when callers are bursty and downstream can absorb it; leaky bucket when downstream must never see a spike.

Move 4 — Find the next bottleneck: one limiter, ten servers

Everything above assumed one counter. In production our API runs on a fleet of servers behind a load balancer. If each server keeps its own local bucket for k_42, the limit silently multiplies.

Worked: the per-server leak. We run M = 10 API servers; the load balancer spreads k_42's requests round-robin. Each server keeps a local 60/min bucket. The client sends 600/min; each server sees only 60 → each thinks the client is exactly at its limit → all 600 are allowed. The promised 60/min became 60 × 10 = 600/min — the limit is 10× too loose, and it scales looser every time autoscaling adds a server.

Two ways to fix it, each with a cost:

  • Divide the budget — give each server 60 ÷ 10 = 6/min. Simple, no shared state. But traffic is never perfectly even: if the balancer sends a client mostly to 3 servers, it gets throttled at 18/min while 42/min of its budget sits unused on idle servers. And M changes under autoscaling, so the per-server share keeps shifting.
  • Centralize the counter — put one shared store (e.g. Redis) in front; every server does an atomic token-bucket update against the same key. Now all 10 servers see one true count for k_42. This is the accurate choice — and it must be atomic, or two servers read "1 token left" at once and both spend it (the exact lost-update race from Lesson 06; here a Lua script or atomic INCR makes the read-modify-write a single indivisible step).
  CENTRALIZED LIMITER (one true counter, atomic updates)

  server 1 ─┐
  server 2 ─┤   atomic "take a token for k_42"
   …        ├────────────────►  ┌──────────────┐
  server 10 ┘                   │  REDIS        │  k_42 → tokens, ts
                                └──────────────┘  one source of truth
            every server sees the SAME count → limit holds at exactly 60/min

But the centralized store is now on the hot path of every request — and that's the next wall.

Worked: the limiter store becomes the bottleneck. The whole fleet handles 200,000 req/s, and every request must consult the limiter first. A single Redis node tops out near ~100,000 simple ops/s — so one central node is already 2× over capacity before doing any real work. Two escapes, both old friends: (1) shard the limiter by key across many nodes (consistent hashing from Lesson 04) so the 200k spreads out — but a single celebrity key doing 50k/s still pins one shard. (2) go approximate: let each server keep a local bucket holding a slice of the global budget and reconcile with the central count every second. That trades a small, bounded overshoot at the edges for a limiter that scales — the same exact-vs-scalable bargain we struck with the sharded counter in Lesson 06.

Name the trade-off: distributed rate limiting is a dial between accuracy and scalability. A single shared counter is exact but a throughput bottleneck and a single point of failure; per-server or approximate counters scale freely but let the real limit drift a little. As everywhere in this course, there is no "correct" — only the overshoot you can tolerate versus the scale you must reach.

Where we landed

We took one noisy API key and built a fair gate in front of everything. Estimate sized the limit from two numbers — a sustained rate (1 req/s) and a burst (~60) — chosen against the downstream ceiling, and named the dial: false throttling vs starvation. Model showed the cheap fixed-window counter and its boundary bug — 120 requests across a seam where we promised 60 — and the sliding-window and token-bucket fixes. Tracing the paths walked the token bucket (capacity = burst, refill = average; burst once then clamp to r) against the leaky bucket (smooth output, burst latency) and named the smoothness-vs-burst trade. The next bottleneck — one limiter across ten servers — exposed the 10× per-server leak, fixed by a centralized atomic counter (beware the lost-update race), which itself became a throughput wall solved by sharding or approximation. The thread through all of it: a rate limiter is a cheap gate that makes one caller's appetite everyone else's problem no longer — and counting it correctly at scale is its own small distributed-systems problem.
