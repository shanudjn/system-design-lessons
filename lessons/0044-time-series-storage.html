Time-Series & Metrics Storage: A Million Points a Second, Kept for Years

Lesson 17 built the dashboards that tell you something is slow — the p99 that spiked, the error rate that climbed. But every one of those charts is drawn from numbers that had to be stored first, and the fleet emits them by the million per second, forever. This lesson designs the database underneath the graphs: a time-series database. It looks like it should be easy — the data is just (what, when, value) triples, and they only ever get appended, never updated. That very shape is what makes it both wonderfully compressible and treacherous in one specific way. We'll estimate why the naive "one row per reading" costs half a petabyte a year and how a purpose-built encoding squeezes each reading to under 2 bytes. We'll model the two halves every metrics store splits — the series (the label soup that names a metric) from the samples (the timestamp+value stream) — plus the delta-of-delta and XOR tricks that do the squeezing, time-partitioning, and rollups. We'll trace a write landing and a range query reading back "p99 latency for search, last 6 hours." And we'll hit the bottleneck that surprises everyone: the thing that kills a time-series DB is almost never the volume of points — that's bounded and compresses beautifully — it's the cardinality of series, which multiplies, and one careless label can multiply it into the trillions. The trade underneath: resolution & retention vs storage cost.

The one system we'll design

The observability backend for a platform of 10,000 hosts running Lesson 27's fleet, Lesson 26's gateways, Lesson 25's ledger — every service exporting metrics. A metric is a number that changes over time: CPU percent, requests per second, p99 latency, queue depth. Each host exports thousands of them, and a scraper pulls every metric from every host on a fixed interval. Concretely: 10 million active time series, each sampled every 10 seconds. That's 10,000,000 ÷ 10 = 1,000,000 data points per second, flowing in and never stopping, and dashboards want to read arbitrary time ranges out of it fast — "the last 5 minutes" for an alert, "the last 90 days" for a capacity trend. Two facts define everything: writes are append-only and in time order (a point for "now" never changes an old point), and reads are always by a time range over a chosen set of series. A general database (Lesson 12's B-tree, tuned for random point reads and updates) is the wrong shape for both. We'll build the right one.

A time-series database stores numeric measurements stamped with a time, optimized for append-only writes in time order and for reading back ranges of time. The two words that will do all the work: a series is one uniquely-labelled metric (e.g. http_requests_total{service="search",status="200"} — the metric name plus a specific set of label key-values); a sample (or data point) is one (timestamp, value) reading of that series. A series is created once and lives a long time; samples pour in forever.

Words we'll earn before we lean on them

  • Series (time series) — a metric name plus a specific set of labels. cpu{host="h7"} and cpu{host="h8"} are two different series.
  • Sample / data point — one (timestamp, value) reading belonging to a series.
  • Label (dimension / tag) — a key=value pair on a series (host, region, status) you filter and group by.
  • Cardinality — how many distinct series exist. It is the product of every label's number of possible values.
  • Scrape / sample interval — how often each series is measured (we use 10 s). It fixes the point rate.
  • Chunk / time partition — samples grouped by a time window (e.g. 2 hours). Once its window passes, a chunk is immutable — never written again.
  • Delta-of-delta — store not the timestamp, nor even its gap from the last, but the change in the gap. For a regular stream that change is zero, and zero packs into one bit.
  • XOR encoding — store a value as its bitwise difference from the previous value; slow-moving numbers differ in only a few bits, so most of each value is zeros you don't store.
  • Downsampling / rollup — replace many fine-grained points with one coarse point holding an aggregate (min/max/sum/count), trading resolution for size.
  • Retention — how long data of a given resolution is kept before it's dropped.

Move 1 — Estimate: why one row per reading is a half-petabyte-a-year mistake

The obvious design is a table: (series_labels, timestamp, value), one row per reading, in the relational store from Lesson 12. Let's price it before we build anything else, because the numbers decide the whole architecture.

The naive row. Store the full label string on every reading: a realistic label set like http_requests_total{service="search",region="us-east",status="200",endpoint="/q"} is ~200 bytes, plus a timestamp (8 B) and a value (8 B). At 1,000,000 points/s that's 1,000,000 × 216 B ≈ 216 MB/s ≈ 18.7 TB/day. That's not a database, that's a landfill — and it's mostly the same label string written a million times a second.

First fix — split the "what" from the "when" (Lesson 20's plane split). A series' labels never change. Store them once in a series index that maps the label set to a small integer series_id, and let each sample carry only (series_id, timestamp, value). Now a raw sample is timestamp (8 B) + value (8 B) = 16 B (the tiny series_id is implied by which stream you're appending to). Cost drops to 1,000,000 × 16 B = 16 MB/s = 1.38 TB/day ≈ 505 TB/year. Better by 13×, but still half a petabyte a year for one platform's metrics.

Second fix — compress the samples for what they actually are. Here's the gift in the data: samples arrive at a regular interval and values move slowly. A purpose-built encoding (below) squeezes each 16 B point to under 2 bytes. At ~1.5 B/point: 1,000,000 × 1.5 B = 1.5 MB/s = 130 GB/day ≈ 47 TB/year — an ~11× cut on top of the split, and the number that makes the whole thing affordable.

Why a general-purpose database can't do this. A B-tree (Lesson 12) is built for random reads and in-place updates: it scatters rows, leaves gaps for inserts, and stores each value independently. Metrics never update and always append at "now," so all that machinery is dead weight — and storing each value independently forfeits the 11× compression that only exists because consecutive points are nearly identical. The time-series shape (append-only, time-ordered, slow-moving) is exactly the shape a normal database is built to not assume — which is why metrics get their own storage engine.

The compression, worked out by hand

Two independent tricks, one for the timestamp column and one for the value column — the same "store columns, not rows, and encode each column for its pattern" idea as Lesson 29's warehouse, aimed at a stream.

Timestamps → delta-of-delta. Our stream ticks every 10,000 ms. Watch what's left to store:

t0 = 1,600,000,000,000 → store in full (64 bits, once per chunk).
t1 = t0 + 10,000 → the delta is 10,000 (store ~14 bits, once).
t2 = t1 + 10,000 → delta is again 10,000, so the delta-of-delta is 10,000 − 10,000 = 0 → store a single 0 bit.
t3, t4, … → still perfectly regular → each is one more 0 bit.

Across a 20-minute chunk of 120 points, the timestamps cost 64 + 14 + 118×1 ≈ 196 bits ≈ 25 bytes for 120 timestamps ≈ 0.2 B each — versus 8 B each stored plainly, a 40× shrink. A scrape that runs a little early or late just makes one non-zero delta-of-delta; regularity is the common case and it's nearly free.

Values → XOR with the previous value. A CPU gauge reads 40.0, 40.0, 40.25, 40.25. Store v0 in full (64 bits), then each next value as vₙ XOR vₙ₋₁: identical values XOR to all zeros → one bit ("same as before"); a small change flips only a few bits in the middle of the float, and you store just that window, skipping the run of leading and trailing zero bits. Slow-moving gauges land around ~1.3 bytes per value.

Together: ~0.2 B timestamp + ~1.3 B value ≈ ~1.5 B/point. (Facebook's Gorilla, the design this comes from, reports ~1.37 bytes per point averaged over real production metrics — a ~12× cut over the 16 B raw pair.)

Name the trade-off — compression leans on regularity. Both tricks pay off in proportion to how boring the data is: a perfectly regular interval and a slow-moving value compress to a bit or two; a jittery interval or a wildly noisy value stores closer to the full 16 B. You don't choose this per point — you choose it by what you measure and how often. The encoding is free money for smooth operational metrics and buys almost nothing for random data — which is another reason high-entropy identifiers do not belong in this store.

Move 2 — Model: series on one side, a compressed time-partitioned stream on the other

The estimate already forced the core split. Now give each half its real structure.

The series index — the "what" (an inverted index on labels)

Every unique label set gets one series_id. To answer "give me every series where service="search"," you need to go from a label to the set of series that carry it — which is exactly Lesson 12/16's inverted index: a posting list per label=value naming the matching series ids. A query with several label matchers intersects the posting lists (Lesson 16's AND), yielding the handful of series to actually read. This index is small if cardinality is sane (10M series × ~a few hundred bytes ≈ a few GB) — and it is the exact thing that explodes in Move 4.

The sample store — the "when" (chunks by time, immutable once past)

Samples for a series are appended, in time order, into the current time chunk (say a 2-hour window). Two properties fall out and both matter enormously:

  • Append-only + time-ordered means the delta-of-delta / XOR encoders work: each point only needs the one before it. The newest chunk lives partly in memory (the encoder's working buffer per active series), then is flushed to disk compressed.
  • Once its window passes, a chunk is immutable — no metric ever rewrites 3 pm's data at 5 pm. Immutable chunks can be compressed hard, copied to cheaper tiers (Lesson 39), rolled up, and — the payoff — deleted whole when they age out. Retention isn't a DELETE WHERE timestamp < … scanning a billion rows; it's dropping a partition file, an O(1) operation (Lesson 24's partition-and-drop).

Because reads are always a time range, chunking by time is the same partition pruning as Lesson 29: a "last 6 hours" query touches ~3 two-hour chunks and skips every older one without reading it.

Rollups — trading resolution for size as data ages

Nobody inspects last March at 10-second granularity; they want the trend. So downsample: replace each window of raw points with one rollup point holding aggregates (min, max, sum, count — enough to recompute avg and to draw a band). A rollup runs as a background job over immutable chunks.

Price the win. A 1-hour rollup replaces 3600 / 10 = 360 raw points with one point. Even storing 4 aggregates (so ~4× the bytes of a single point), that's 360 / 4 = 90× smaller per unit of time. So instead of 47 TB/year of raw:

ResolutionKept forRough sizeAnswers
raw 10 s7 days~0.9 TBthis morning's 2-min latency spike
1-min rollup30 days~2 TBlast week's daily pattern
1-hour rollup2 years~1 TBthis quarter vs last year's growth

Keeping everything at 10 s for 2 years would be ~95 TB; the tiered scheme above is ~4 TB — a ~24× cut — and you still answer every real question, because the questions you ask about old data are coarse.

Name the trade-off — resolution & retention vs storage cost. Three knobs set the bill: how often you sample (interval), how fine you keep it (rollup granularity), and how long you keep each grain (retention). Turn any up and you see more, pay more. The one you can never undo is resolution lost to a rollup: a 1-hour rollup that stored an average has permanently erased the 2-minute p99 spike inside that hour — Lesson 17's whole point (the tail hides in the mean) reappears as a storage decision. That's why you keep raw data at full resolution for a short recent window (where you debug incidents) and only roll up the old data (where you study trends) — matching each age of data to the questions actually asked of it.

Move 3 — Trace the paths

One write in, one range query out.

Path A — a sample lands

  Scraper reports:  http_requests_total{service="search",status="200"} = 84213  @ t=1600000000

   1. Resolve the SERIES. Look up the label set in the series index.
        seen before?  -> reuse series_id 5591
        new label set? -> mint a new series_id, add posting-list entries for
                          service="search" and status="200"  (this is the
                          cardinality cost -- a NEW series is the expensive event,
                          a new SAMPLE of an existing series is nearly free)
   2. Append the SAMPLE to series 5591's current in-memory chunk:
        timestamp -> delta-of-delta vs the last point  (regular -> ~1 bit)
        value     -> XOR vs the last value             (slow move -> ~1.3 B)
   3. Also append to a write-ahead log so an unflushed in-memory chunk survives a
      crash (durability, L38's log). When the 2-hour window closes, the chunk is
      compressed, flushed to disk, and marked IMMUTABLE.

  Cost of a sample for an EXISTING series: a couple of bytes + a couple of bits.
  Cost of a sample that CREATES a series: an index insert + a fresh in-RAM buffer.

Path B — "p99 latency for search over the last 6 hours"

  Query:  quantile(0.99, http_request_duration{service="search"}[now-6h : now])

   1. SELECT SERIES (series index, L12/L16 inverted index):
        posting list for service="search"  ->  intersect with the metric name
        ->  say 40 series (one per endpoint/instance).  NOT a scan of 10M series.

   2. PRUNE BY TIME (partition pruning, L29):
        6 hours -> the last ~3 two-hour chunks per series.  Every older chunk on
        disk is skipped without being read.  ~120 chunks touched, not the year.

   3. SCAN + DECODE + AGGREGATE:
        decompress those chunks (delta-of-delta + XOR reverse), walk the points in
        the range, feed them to the p99 estimator.  Reading FEWER BYTES is the whole
        game (L29): compressed 6 h of 40 series is a few MB, not the 47 TB pile.

   4. If the range were "last 90 days", step 3 reads the 1-min / 1-hour ROLLUPS
      instead of raw -- coarser points, far fewer of them, same query shape.

Path A shows why creating a series is the costly event and sampling an existing one is nearly free; Path B shows the read is "narrow to the right series, prune to the right time window, decode only those bytes" — the label index picks the what, time-partitioning picks the when, and rollups pick the grain. Every one of those steps is cheap as long as the series count stays sane. That "as long as" is the whole ballgame.

Move 4 — Find the first bottleneck: cardinality, not volume

Everything so far made the volume of points cheap: it's bounded (series × 1/interval), it compresses 11×, and it rolls up and drops on a schedule. So the thing that takes these systems down is almost never "too many points." It's too many series — and series count behaves completely differently, because it's a product.

A sane metric. http_requests_total{service, region, status, endpoint} with service=50, region=5, status=15, endpoint=200 possible values → 50 × 5 × 15 × 200 = 750,000 series. Fine. The point rate is capped by the scrape interval no matter how busy those endpoints get.

One innocent label. A developer adds user_id to "see per-user request rates." There are 10 million users. Cardinality is a product, so:

750,000 × 10,000,000 = 7,500,000,000,000 — 7.5 trillion series.

Now recall what a series costs, from Path A. Each one needs (a) an entry in the series index and posting lists — call it ~100 B → 7.5×10¹² × 100 B = 750 TB just to index the series, and (b) its own in-RAM encoder buffer for the active chunk — even at a few hundred bytes each, 7.5 trillion of them is impossibly beyond any machine's memory. The samples were never the problem; the series index and per-series memory are, and both scale with cardinality — which one high-cardinality label multiplied into the trillions.

Name the trade-off — dimensions vs cardinality. Every label you add lets you slice the data a new way — and multiplies the series count by that label's number of values. A low-cardinality label (status: ~15 values) is a bargain; an unbounded one (user_id, request_id, trace_id, an email, a full URL with query params) is a bomb, because its value count grows without limit and multiplies everything beside it. This is Lesson 17's rule made physical: identifiers go on traces and logs, never on metric labels. A metric answers "how many / how fast, sliced by a few bounded dimensions"; the moment you need "which specific user/request," that's a trace or a log query, not a metric — and mixing them melts the metrics store.

How real systems keep cardinality bounded:

• Keep unbounded identifiers out of labels. Aggregate them away at emit time (count requests per service, not per user). If you need to jump from a metric to an example request, attach an exemplar — a single trace ID hung off the metric — instead of making the ID a label (Lesson 17's traces).

• Enforce limits at ingest. Cap series per metric, allowlist which labels may exist, and drop or alert on a metric whose cardinality suddenly explodes (usually a bug — a UUID or a raw path accidentally used as a label).

• Pre-aggregate the dimensions you actually query. If you only ever look at request rate by service, record it that way and never carry endpoint at all.

The discipline is the same as Lesson 40's noisy-neighbor: the shared resource here is the series index and the ingesters' memory, and one careless tenant (a bad label) can exhaust it for everyone.

The four traps

  • Trap 1 — a high-cardinality label. Putting user_id, request_id, trace_id, a session token, an email, or a full URL into a metric label. Cardinality is a product, so one unbounded label multiplies the whole series count into the billions or trillions, blowing up the index and the ingesters' memory — while the sample volume looks perfectly fine. Identifiers belong on traces/logs (Lesson 17), linked by an exemplar if you need the jump.
  • Trap 2 — storing metrics in a general-purpose (row) database. A B-tree is built for updates and random reads and stores each value independently, forfeiting the 11× delta-of-delta/XOR compression that only exists because consecutive points are nearly identical — and turning retention into a billion-row DELETE instead of dropping an immutable partition. Use a storage engine that assumes append-only, time-ordered, slow-moving data.
  • Trap 3 — one resolution and retention for everything. Keeping raw 10-second data for two years is ~24× the cost of a tiered scheme and answers no question you actually ask of old data; keeping only hourly rollups means the 2-minute incident spike you need to debug this morning was already averaged away. Match each age of data to its real questions: raw recent, rolled-up old.
  • Trap 4 — rolling up before you know the questions. A rollup is lossy and irreversible — if you only stored the average, you can never recover the max or the p99 for that window. Store the aggregates you'll need (min/max/sum/count, and quantile sketches if you query percentiles) before the raw data ages out, because once it's gone the resolution is gone (Lesson 21's "a sketch tells you how many, never which," applied to time).

Where we landed

A metrics backend ingesting 1,000,000 data points/second (10M series × a 10-second interval) and keeping them for years. Estimate killed the naive design twice: one row per reading with inline labels is ~216 MB/s ≈ 18.7 TB/day (the same label string written a million times a second), so first split the series from the samples — store each label set once, and a sample becomes a bare (timestamp, value) = 16 B → 1.38 TB/day — then compress the samples for what they are: delta-of-delta timestamps (a regular interval → ~1 bit each) and XOR values (slow-moving → ~1.3 B each) crush 16 B to ~1.5 B/point (Gorilla's ~1.37), landing at 130 GB/day ≈ 47 TB/year, an ~11× cut. Model gave each half its shape: the series live in an inverted label index (Lesson 12/16) that intersects posting lists to pick which series a query touches, and the samples live in time-ordered chunks that go immutable once their window passes — which is what lets old chunks compress hard, roll up (raw 10 s → 1 min → 1 hour, a ~90× shrink per rollup level), and get dropped whole at retention (O(1), not a billion-row delete). Tracing showed a sample landing (creating a series is the costly event; sampling an existing one is a couple of bytes and bits) and a range query narrowing by label index, pruning by time partition (Lesson 29), and decoding only those few MB. The first bottleneck is the counter-intuitive heart of the lesson: the volume of points is bounded and cheap, but the cardinality of series is a product of label values, so one unbounded label (user_id over 10M users) explodes 750k series into 7.5 trillion — ~750 TB of index and unbounded RAM — while the sample rate still looks fine. The real lesson: a time-series database is easy in the dimension everyone worries about (write volume, solved by splitting and compressing) and fragile in the one they don't (series cardinality, a multiplicative wall) — so keep identifiers off labels, keep raw data only as long as you debug it and rollups as long as you study trends, and remember every rollup permanently trades resolution for cost. The standing tension: resolution & retention vs storage cost.
