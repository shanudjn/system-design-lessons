Scaling Reads: Eviction, CDNs, and the Stampede

Last lesson we put a cache in front of the URL shortener and the read problem looked solved. It isn't — not yet. A real cache can't hold everything, it lives near one data centre, and when a hot key disappears it can take the database down with it. We fix all three, reusing the same four moves.

Where Lesson 01 left us

The shortener does ~3,800 reads/sec against ~6 billion stored links, and we added a cache (an in-memory key→value store, think Redis) in front of the database. The mapping short_code → long_url is immutable — written once, never changed — so a cached value is never stale. That was the easy part. Now three cracks show up the moment traffic is real. Three cracks: (1) the cache is too small to hold everything, so something must be thrown out — eviction. (2) one cache sits in one place, but users are global — CDNs. (3) when a hot key leaves the cache, a herd of requests stampedes the database at once. We take them in order.

Move 1 — Estimate: how much can the cache actually hold?

Before choosing an eviction rule, find out how tight the squeeze is. Caching is only interesting because memory is small and expensive compared to disk. So: how many of our 6 billion links fit in RAM?

Size of one cache entry: the key short_code (~7 bytes) + the value long_url (~100 bytes average) + per-entry bookkeeping (pointers, expiry, hashtable slot ~ 90 bytes). Round to ~200 bytes/entry.

One cache box with 16 GB RAM. Reserve ~25% for the process itself → ~12 GB usable.

Entries that fit = 12 GB ÷ 200 bytes = 12,000,000,000 ÷ 200 = 60,000,000 entries.

Coverage = 60M ÷ 6,000M = 1% of all links fit in the cache.  99% live only on disk

Why this matters: 1% sounds hopeless, but remember from Lesson 01 that access is skewed — a few links go viral while most are clicked almost never (this is the 80/20, or Zipfian, pattern). If the hottest 1% absorbs, say, 96% of clicks, then the cache catches 96% of reads and the database only sees the other 4%. A 1% cache can carry a 96% hit rate — but only because traffic is skewed. If traffic were uniform, this cache would be nearly useless. The skew is the whole reason caching works.

Payoff at a 96% hit rate:

Reads the database must serve = (1 − 0.96) × 3,800/sec = 0.04 × 3,800 = ~152 reads/sec.

From 3,800/sec hammering disk down to 152/sec. That's the cache earning its keep. 25× less DB load

Move 2 — Model the cache entry: what does "throw one out" mean?

The cache holds 60M entries. Click number 60,000,001 needs a slot and there are none. The cache must evict — pick an existing entry and delete it to make room. Which one you pick is the entire game. Two honest rules:

LRU — Least Recently Used ✅

Track when each entry was last read. When full, evict the one untouched for the longest time. The bet: what you haven't used lately, you won't use soon.

Fits skewed traffic perfectly. Viral links get read constantly, so they're always "recent" and never evicted. Cold links go quiet and fall out. LRU naturally keeps the hot 1%.

TTL — Time To Live

Stamp each entry with an expiry (say 1 hour). After that it's dropped no matter how hot it is. Bounds how long any data lingers.

But our mapping is immutable — a cached value is never wrong, so we don't need TTL for staleness. We use a long TTL only to recycle memory and to eventually notice the rare deleted link. TTL here is a safety net, not the main rule.

Name the trade-off: LRU optimizes for the access pattern (keep what's hot); TTL optimizes for freshness and memory hygiene (drop what's old). They're not rivals — real systems run LRU for eviction + a long TTL as a backstop. The skill is knowing why each is there: LRU because traffic is skewed, TTL because even "immutable" data can be deleted and memory must be reclaimed.

One subtlety: LRU vs LFU

There's a cousin, LFU — Least Frequently Used — which evicts by total count, not recency. LFU protects an all-time-popular link better, but it's slower to forget yesterday's fad: a link that was huge last week but is dead today keeps its high count and clogs the cache. LRU adapts faster to changing trends; LFU remembers longer. For a shortener, where virality is bursty, LRU's quick forgetting usually wins.

Move 3 — Trace the paths: the cache hit, the miss, and the dangerous one

Cache hit (96% of the time)

1. GET /15FTGg
2. App checks cache → key "15FTGg" present
3. Return long_url straight from memory   (~0.5 ms, no disk touched)

Cache miss (4% of the time) — read-through

1. GET /15FTGg
2. App checks cache → MISS
3. App reads DB:  SELECT long_url WHERE short_code='15FTGg'   (~20 ms)
4. App writes the value back into the cache   (so the NEXT read hits)
5. Return long_url

This "miss → fetch → backfill" loop is called read-through (or cache-aside). The first reader of a cold link pays the slow ~20 ms; everyone after pays the fast ~0.5 ms until it's evicted.

The dangerous path: a hot key vanishes → the stampede

Now the failure that's special to caches. A link goes viral — 2,000 requests/second for one code. It's a guaranteed cache hit, so the database never sees it. Life is good. Then its cache entry disappears — maybe the TTL expired, maybe the cache box restarted. For a brief window, that hot key is a miss. What happens?

A database read takes ~20 ms (= 0.02 s). During that 20 ms window, new requests keep arriving for the same key — and they all miss, because nobody has backfilled yet.

Requests piling on in 20 ms = 2,000/sec × 0.02 s = 40 simultaneous identical DB queries for one key.

Now imagine thousands of warm keys whose TTLs were all set at the same startup instant and expire together: tens of thousands of misses fire in the same second.

This is the cache stampede, also called the thundering herd or dogpile: the moment a popular key leaves the cache, the herd that the cache was shielding slams into the database all at once. The database, sized for 152 reads/sec, suddenly gets thousands — and falls over. Ironically, the cache made the database weaker by hiding the true load, so the database was never provisioned to survive a cache gap. This is crack #3, and it's the one that takes systems down.

Three fixes, each with a named trade-off

FixHow it worksTrade-off
Single-flight
(request coalescing)		On a miss, the first request grabs a lock and does the one DB read; the other 39 wait and then read its backfill.The 39 waiters see slightly higher latency — but the DB does 1 query instead of 40. Trade a little latency for survival.
TTL jitterDon't expire entries on a round number. Add a random ±10% to each TTL so expiries spread out instead of firing in the same second.Costs nothing; just prevents synchronized expiry. The fix for the "10,000 keys die at once" version.
Stale-while-revalidateKeep serving the old value past expiry while one background task refreshes it.Readers briefly get slightly-stale data — fine here, since the value is immutable anyway. No reader ever waits on the DB.

The transferable lesson: a cache doesn't remove load, it hides load. Always ask "what happens the instant this cache is empty?" — on a cold start, a restart, or a hot-key expiry. If the answer is "the database dies," you haven't finished. Protect the gap, not just the steady state.

Move 4 — Find the next bottleneck: distance

Eviction and stampede are solved, but the cache and database still sit in one data centre — say Virginia. A user in Tokyo is ~10,000 km away. Light in fibre travels ~200,000 km/s, so the round trip is physically ~100 ms before any work happens. A 0.5 ms cache hit is meaningless if the packet spends 100 ms crossing the Pacific. The new bottleneck isn't compute — it's the speed of light.

Fix: a CDN — Content Delivery Network. A CDN is a fleet of caches (called edge servers, or PoPs — Points of Presence) spread across the globe. The Tokyo user hits a Tokyo edge ~5 ms away instead of Virginia 100 ms away.

Latency for the Tokyo user:

Without CDN: ~100 ms round trip to Virginia + 0.5 ms cache = ~100 ms.

With CDN edge in Tokyo: ~5 ms round trip + edge lookup = ~5 ms. 20× faster

For a URL shortener the CDN can cache the redirect itself — the response that says "go to long_url." The edge answers the redirect without ever reaching your origin. But look closely at the trade-off, because it's the exact one from Lesson 01:

Name the trade-off: if the edge serves the redirect, clicks never reach your server — so you can't count them. That's the 301-vs-302 dilemma again, one layer out. You choose per use case: cache the redirect at the edge for raw speed and cheap traffic, or let clicks flow to origin so you keep per-click analytics. You can also split it — cache aggressively for links where you don't need counts, and bypass the CDN for links you're tracking. Speed vs. visibility; there's no free version.

Where we landed

We took the "solved" cache from Lesson 01 and stress-tested it. Estimate showed only 1% of links fit in RAM — fine, because skew gives a 96% hit rate. Model gave us eviction: LRU to keep the hot set, TTL as a backstop. Tracing the paths exposed the stampede when a hot key vanishes, fixed with single-flight, jitter, and stale-while-revalidate. The next bottleneck was physical distance, answered by a CDN — which handed us the analytics trade-off all over again. Same four moves; deeper system.
