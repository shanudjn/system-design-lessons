Designing for Failure: Timeouts, Retries, Idempotency & Backpressure

Our app server calls the leader to record a like. Usually it answers in 10 ms. One afternoon the leader hiccups and an answer never comes back. Now the hard question: how long do we wait, and then what? Wait too long and threads pile up until the whole app falls over. Retry blindly and we duplicate writes — or worse, we hammer a struggling dependency into a full outage. This lesson takes ONE timed-out call and traces every decision: the timeout, the retry, the idempotency key that makes a retry safe, and the backpressure that stops a slowdown from becoming a meltdown. We name the trade-off behind each.

The one call we'll trace

A user likes link xZ9. Our app server sends one network request to the leader: recordLike(xZ9). The leader normally replies in ~10 ms. Today, after 50 ms, nothing. The reply hasn't come. Here is the whole problem on one screen: a timeout tells you the answer is late — it does not tell you whether the work happened.

  THE PARTIAL FAILURE (one timed-out call, three possible truths)

  app server ──recordLike(xZ9)──►  ??? ──►  LEADER
       │                                       │
       │   ...50 ms... no reply...             │
       ▼                                       ▼
   TIMEOUT fires. What actually happened on the other side?

   (1) request never arrived ............ work NOT done  → retry is safe
   (2) work done, but the ACK was lost ... work DONE     → retry DUPLICATES
   (3) request still running slowly ...... in progress   → retry RACES it

   The app cannot tell (1) from (2) from (3). All it knows: "no reply yet."

Distributed systems fail partially: a call can half-happen, and the caller is left guessing. On one machine a function either runs or doesn't. Across a network the request, the work, and the acknowledgement are three separate things, and any of them can be lost. Every tool in this lesson exists to make a sane decision while genuinely not knowing which of the three truths you're in.

Words we'll earn before we lean on them

  • Timeout — the deadline after which the caller gives up waiting for a reply.
  • Partial failure — a call that may have done its work even though you got no confirmation.
  • Retry — sending the request again after a failure.
  • Idempotent — an operation you can apply more than once and get the same end state as applying it once.
  • Backpressure — pushing "slow down" back to callers (or rejecting them) when you can't keep up.

Move 1 — Estimate: how long is it safe to wait?

Pick the timeout from the dependency's real latency, not a round number. Measure the leader's recordLike response times: p50 = 10 ms, p99 = 50 ms, p99.9 = 200 ms. A healthy call almost never takes longer than 200 ms. So a wait beyond ~200 ms means "this one is genuinely stuck," not "this one is just slow." That — not the framework's lazy 1-second default — is where the deadline belongs.

Why the default 1 s is a trap. The app server serves likes from a pool of 200 worker threads. Each call ties up one thread until it returns. Normal call = 10 ms, so one thread does 1000 ÷ 10 = 100 calls/second; the pool handles 200 × 100 = 20,000 calls/second.

Now the leader stalls and every call hangs until the timeout. With a 1 s timeout each thread does just 1000 ÷ 1000 = 1 call/second; the pool collapses to 200 × 1 = 200 calls/second — a 100× drop. All 200 threads sit blocked on dead calls, new likes queue up, and the app stops responding to everything, not just likes. With a 200 ms timeout the same stall caps each thread at 5 calls/s → 1,000 calls/s, and threads free up 5× faster to fail fast and recover.

Name the trade-off: the timeout is a dial between false failures and thread exhaustion. Too short, and you kill healthy-but-slow calls — wasting completed work and triggering needless retries. Too long, and during a real stall your threads pile up on dead calls until the caller itself dies. The right timeout is "the point where waiting longer is worse than giving up." Set it from the p99/p99.9 of the thing you're calling — every hop gets its own.

Move 2 — Model: a timeout is not an answer

The naive like handler treats a timeout like a clean "no":

  def like(link_id):
      try:
          record_like(link_id)        # call leader, 200 ms timeout
      except Timeout:
          record_like(link_id)        # "it failed, just try again"  ← the bug

But from Move 1's diagram, a timeout could mean the like already landed (truth 2) and we just lost the reply. Retrying then applies the like twice. We are right back in the lost-update's evil twin from Lesson 06 — except now the cause isn't concurrency, it's a retry on an operation that already succeeded. Trace it:

Worked: the duplicate like.

t=0 ms — app sends recordLike(xZ9); leader applies it, count 100 → 101.
t=12 ms — leader's ACK starts back… and is dropped by a flaky switch.
t=200 ms — app's timeout fires. App believes the call failed.
t=201 ms — app retries recordLike(xZ9); leader applies it again, 101 → 102.

One user clicked like once. The count is 102. The retry was the right instinct (the network did fail) but the operation wasn't safe to repeat. Retries are only safe on idempotent operations. So before we retry, we have to make recordLike idempotent.

Move 3 — Trace the paths: retry, but make it safe and gentle

Path A — make the write idempotent (an idempotency key)

An operation is idempotent when doing it twice leaves the same end state as doing it once. A blind counter +1 is not idempotent. We make it so by tagging each logical action with a unique idempotency key — a UUID the client generates once and reuses on every retry of that same action. The server remembers keys it has already applied and ignores repeats:

  NOT idempotent (counts every call)     IDEMPOTENT (counts each key once)
  ──────────────────────────────────     ─────────────────────────────────
  recordLike(xZ9):                        recordLike(xZ9, key=K7):
     count = count + 1                       if K7 in applied:        # seen it
                                                 return stored_result  # no-op
  retry  -> count + 1 AGAIN                    count = count + 1
           (duplicate)                         applied.add(K7)        # remember
                                            retry with SAME K7 -> deduped, no double

Now replay truth 2 from Move 2: the first call applied K7 and bumped the count to 101; the ACK was lost; the retry arrives carrying the same K7; the leader sees K7 is already applied and returns the stored result without touching the count. The count is 101. Retry as many times as you like — the key makes it safe. This is the exact same idempotency-key trick that tamed at-least-once queue delivery in Lesson 05; here it tames at-least-once retries.

Name the trade-off: idempotency buys safe retries at the cost of state — the server must store every applied key for long enough to outlive any retry (say a 24 h TTL), which is memory and a lookup on the hot path. The key must also identify the logical action, not the attempt: generate it once on the client and reuse it, or each retry looks new and the dedup does nothing.

Path B — retry without starting a storm (backoff + jitter + budget)

Safe retries can still be dangerous in aggregate. The leader hiccuped because it was near capacity. If every failed call instantly retries — and retries up to 3 times — we multiply the load on a dependency that is already drowning. That's a retry storm, and it turns a blip into an outage.

Worked: retries amplify load. Normal offered load is 20,000 calls/s; the leader holds up to ~25,000 calls/s (80% utilized). It hiccups and starts failing a slice of calls. With "retry up to 3×," each failure can become 1 + 3 = 4 attempts. As failures spread, offered load climbs toward 20,000 × 4 = 80,000 calls/s against a 25,000 ceiling — 3× over capacity. The leader now fails everything, so everything retries, so it stays dead even after the original hiccup is gone. That self-sustaining death spiral is a metastable failure.

Three controls keep retries from becoming a storm:

  • Exponential backoff — wait longer between each attempt: ~100 ms, then ~200 ms, then ~400 ms. This gives the dependency room to recover instead of a wall of instant retries.
  • Jitter — add a random spread to each wait so retries from thousands of clients don't fire in lockstep. (Same thundering-herd cure as the cache stampede in Lesson 02 — desynchronize the crowd.)
  • Retry budget — cap retries to a small fraction (say 10%) of normal traffic. When the budget is spent, fail fast instead of retrying. This bounds the amplification: worst case 1.1×, never 4×.

Path C — stop calling a corpse (the circuit breaker)

If the leader is hard-down, even backed-off retries waste 200 ms per call hitting a wall. A circuit breaker watches the recent failure rate and, when it crosses a threshold, opens — failing calls instantly for a cooldown instead of waiting on the timeout. After the cooldown it goes half-open, letting one trial call through; success closes it, failure re-opens it.

  CLOSED  ──(failures > 50% of last 20 calls)──►  OPEN
   normal: calls flow                              fail fast, ~0 ms, for 5 s cooldown
     ▲                                               │
     │ trial call succeeds                           │ cooldown elapsed
     └──────────────  HALF-OPEN  ◄───────────────────┘
                       let ONE call through to test the water

Worked: fail fast vs hang. Leader is dead. Without a breaker, each of 20,000 calls/s waits the full 200 ms timeout, holding threads and collapsing the pool to 1,000 calls/s of throughput — the app drags everyone down. With the breaker open, those calls return in ~0 ms with a clean error, threads stay free, and the like feature degrades gracefully (show the last cached count) while the rest of the app keeps serving. Failing fast protects the caller and gives the dependency quiet time to recover.

Name the trade-off: the circuit breaker trades availability for stability. While open it rejects calls that might have succeeded — but in exchange it stops thread exhaustion in the caller and stops piling load on a dependency that needs breathing room. Tune the threshold and cooldown to how fast the dependency actually recovers; too twitchy and you reject healthy traffic, too sluggish and you hang too long.

Move 4 — Find the next bottleneck: backpressure beats an unbounded queue

We've made the caller behave. But if work arrives faster than the leader can drain it, where does the excess go? The tempting answer — "queue it all" — just moves the failure. An unbounded queue fills with requests whose users have already timed out and gone home; you spend capacity replying to nobody while latency climbs without limit. The fix is backpressure: bound the queue, and when it's full, shed load — reject new work immediately with a clear "try later" (an HTTP 429) instead of accepting work you can't finish.

  UNBOUNDED QUEUE (hidden collapse)      BOUNDED QUEUE + LOAD SHEDDING
  ─────────────────────────────────      ───────────────────────────────
  arrivals ─► [ ∞∞∞∞∞∞∞∞… ] ─► leader    arrivals ─► [ ▓▓▓▓ ] (cap 10k) ─► leader
              latency → minutes                       │
              users already gone                      └─ full? → reject NOW (429)
              capacity wasted on the dead             bounded latency, honest "no"

Worked: bound the wait. The leader drains 20,000 calls/s. Cap the queue at 10,000 items. Worst-case wait = 10,000 ÷ 20,000 = 0.5 s — under our 200 ms+backoff budget's tolerance, and never unbounded. Past 10,000 we shed: better to tell 5% of users "retry in a moment" than to give 100% of them a 3-minute hang. A fast, honest rejection is a feature; a slow timeout is the worst outcome for everyone.

Name the trade-off: backpressure trades completeness for survival — you deliberately reject some requests so the system stays up and fast for the rest, instead of accepting everything and melting for all. It's the same wall we hit as consumer lag in Lesson 05; load shedding is just backpressure applied at the front door instead of the queue.

Where we landed

We took one timed-out call and made the whole system fail gracefully. Estimate set the timeout from the dependency's p99/p99.9 (~200 ms), and showed a lazy 1 s default turns one stall into a 100× thread-pool collapse. Model revealed the core truth: a timeout is a partial failure — the work may have happened — so a blind retry duplicates the like. Tracing the paths fixed that with an idempotency key (safe to retry), then kept retries gentle with backoff + jitter + a retry budget (no storm), and cut losses on a dead dependency with a circuit breaker (fail fast). The next bottleneck — work arriving faster than we can drain it — pushed us to backpressure: bound the queue and shed load with an honest 429. The thread through all of it: you can't prevent failure, so design what happens during it — never wait forever, never retry blindly, and always prefer a fast honest "no" to a slow collapse.
