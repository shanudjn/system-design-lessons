LESSON 34
Service Discovery & Health Checking: Finding a Live Instance in a Fleet That Comes and Goes Every Minute
Every lesson so far assumed a step it never justified: a caller "calls the search service." But Lesson 27's fleet autoscales and Lesson 31 rolls deploys through it, so the search service isn't at an address — it's at 200 addresses that change every few seconds. Which IP does the order service dial, and how does it avoid one that died two seconds ago? Price the naive config file: a rolling deploy alone changes an address ~once every 6 s, and one crash inside a 60 s refresh window black-holes 200 req/s × 60 s = 12,000 requests before the caller notices — stale in both directions (dead addresses linger, fresh capacity stays invisible). The fix is to stop treating membership as config and make it live self-maintaining state: a registry where each instance registers on boot and heartbeats every 3 s to renew a 9 s TTL lease (Lessons 10/22/26), so a crash is just an entry that expires — death detected in ≤3 missed beats, no reply needed. Plus the one distinction that prevents an outage: liveness ("is it alive?" → restart) vs readiness ("should it get traffic now?" → remove from pool, don't restart — the drain off-ramp, Lesson 31). Choose who does the lookup — DNS (cheap, stale), client-side (fresh, code everywhere), or a sidecar mesh (fresh + uniform, operational weight). Trace a boot (register only when READY, so capacity appears when it can serve), a crash (TTL expiry bounds the black hole, a Lesson 7 retry papers over the gap), and a graceful shutdown (deregister first, then drain — the ordering a crash gets wrong). First wall: the registry is now everyone's single dependency — it must fail-static (cache the last good list, choose AP — Lesson 11 — opposite of Lesson 10's CP election), run as a replicated consensus cluster (etcd/Consul/ZK), and shed heartbeat load that scales with the whole platform. Four traps: conflating liveness/readiness, a health check that probes a shared DB (one blip ejects the whole fleet), a strongly-consistent registry on the hot path, and a mistuned TTL that flaps. Trade named throughout: routing freshness vs lookup cost & staleness.
LESSON 33
Change Data Capture & the Outbox: Getting Data Out of One Database Into Everyone Else's Without the Dual-Write Lie
Lesson 32 ended on a poisonous "and": each saga step had to "commit locally and emit an event." Committing to your DB is one system; publishing to a broker is another — and there's no shared transaction across two systems. So "write the order row and publish OrderPlaced" is a dual write, and it lies in either order: write-then-publish → a crash leaves a real order nobody was told about (not searchable, not in the warehouse, no confirmation); publish-then-write → a crash announces an order that never saved. There's no safe order — the gap is the bug (Lesson 32's wall, in miniature, under every "when an order is placed, update search/cache/warehouse/notify"). Price it: at 5,000 writes/s even a 99.9% publish rate drips 5/s = 432,000 silently-invisible orders a day, and one 30-second broker blip orphans 150,000 at once — and no retry closes the crash-in-the-gap window. The fix is to stop having two writes: the transactional outbox inserts an event row in the same transaction as the order (Lessons 13/25), so the announcement is a byproduct of the one commit, shipped out-of-band by an at-least-once relay — a crash can only make the event late, never lost. Or change data capture skips the table and tails the DB's own commit log (WAL/binlog), emitting every committed change with no app code and the lowest lag (raw row events vs the outbox's clean domain events — combine them by CDC-tailing the outbox). Trace a clean run, a crash right after the commit (outbox row survives → only late), and a relay that republishes (at-least-once → duplicate → made safe by idempotent consumers keyed on event_id, L13). First wall: everything now flows through one relay — its lag is every downstream system's staleness (L09), it grows the outbox 86 GB/day unless compacted (L20/L24), and ordering at scale needs partition-by-key (L09). Trade named throughout: freshness/consistency vs pipeline complexity.
LESSON 32
Distributed Transactions & Sagas: Making Many Services Commit All-or-Nothing Without a Shared Transaction
Lesson 31 shipped one service safely; now one user action spans four — "book my trip" = reserve flight + hotel + car + charge the card, all-or-nothing. But each lives in its own database, and a transaction stops at the edge of its own database — so the atomicity you got free inside one box you now must build. Price the obvious "hold a lock across all four" (that's two-phase commit): every contended row is held 50/5 = 10× longer than a local commit (a hot flight drops ~200 → ~20 bookings/sec), the commit is only as available as the product of its participants (0.999⁴ ≈ 99.6% ≈ 35 h/yr unbookable), and a coordinator crash between the two phases leaves participants in-doubt — frozen holding locks (Lesson 10's coordinator, darker). The saga is the AP answer: commit each step locally and immediately (no cross-service lock ever held), and on failure walk backward running compensating transactions — ordered so everything before the pivot (the charge) is undoable and everything after is retriable, driven by a central orchestrator or by choreographed events (L09). Trace a clean booking, a sold-out car (compensate the holds, no charge made), and a declined card (why the charge goes last), and the wall appears: a saga has no isolation — its half-done state is really visible, so a second saga can dirty-read a soon-to-be-cancelled hold or double-book the last seat → fixed not by re-adding the lock but by a semantic lock (HELD, not SOLD) + idempotent, retriable compensations (L13). Trade named throughout: atomicity vs availability across service boundaries.
LESSON 31
Deployments & Progressive Rollout: Shipping New Code to a Live Fleet Without Making Every User Your Test Subject
Thirty lessons built a system; now we have to change it — push a new version to Lesson 27's live fleet (286 servers, 40,000 req/s) while users are mid-request. The simplest move, a big-bang deploy, is the release-form of the all-at-once blast radius Lesson 30 just shrank: a bug meets 40,000 × 300 s = 12,000,000 requests — 100% of users — before a ~5-min rollback lands. Ship the same bug as a 1% canary and it meets ~24,000 (a 500× cut) and never reaches the rest. Model the space as two dials — shrink the exposed slice or shrink the time to undo: rolling (cheap, gradual, slow rollback, capacity dip), blue-green (instant flip-back, 2× transient fleet, all-at-once at the flip), canary + health-gated promotion (smallest blast radius, at the cost of metrics + bake time), and the orthogonal feature flag that decouples deploy (code running) from release (behavior reaching users) so rollback is a millisecond flag flip. Trace a healthy ramp (1% → 5% → 25% → 100%, drain before retiring v1) against a poisoned one (spike at 1% → gate fires → auto-rollback, 99% untouched), and the wall appears: old and new run simultaneously over one shared database the load balancer's fast flip can't reverse → so rollback is only as fast as your slowest-to-reverse layer, and safety demands backward/forward compatibility (expand → deploy → bake → contract, L24). Four traps: coupling the migration to the deploy, a thin canary that proves nothing, dropping in-flight work instead of draining (L26), and feature flags left to rot into test debt. Trade named throughout: release velocity vs blast radius.
LESSON 30
Secrets, Keys & Encryption: Protecting the Data Without the Key Becoming the Single Point of Failure
Lesson 29's warehouse concentrated three years of payments and every customer record into one ~11 TB vault — a gift to an attacker. The obvious defense, "encrypt it," hides two traps. Encrypt all 11 TB under one key and a single leak exposes 100% of the vault, while rotating that key means moving 22 TB → ~12 hours of churn. The fix is envelope encryption: bulk data under cheap per-file DEKs (AES-256-GCM, so confidentiality and tamper-detection), each DEK wrapped by a master KEK that lives only inside a KMS and never touches a host. Now a leaked DEK costs one file (1/100,000), and rotating the KEK re-wraps just ~10 MB of DEKs while the terabytes never move (~2,000,000× less data touched). The KMS is Lesson 10's coordination point in a security hat — powerful, so it must be HA, access-controlled, audited — and TLS/mTLS guards the wire (terminate it everywhere, not just the edge). Trace a write (generate → encrypt → wrap → store the envelope → wipe the DEK) and a read (fetch → unwrap → decrypt-or-refuse-on-tamper), and the wall appears: the unwrap is a KMS round trip on every read (40,000/s = a hot, rate-limited SPOF) → fixed by caching the unwrapped DEK for a bounded TTL (a ~6,000× cut), where the TTL is a dial between KMS load and how long a stolen or un-revoked DEK stays live. Four traps: reusing a GCM nonce, encrypting without authenticating, secrets in code/config/logs (down to secret-zero), and terminating TLS too early. Trade named throughout: security blast-radius vs operational friction.
LESSON 29
Data Warehousing & OLAP: Asking One Big Question of the Whole Firehose
For 28 lessons we protected the serving path. Now the opposite question: not "what is order #12345?" but "revenue by region by day for last quarter — across all 11 billion orders (~11 TB)?" Run it on the row-oriented serving DB and it drags whole 1 KB rows to read 2 of 50 columns → 900 GB → ~30 minutes, while also starving live customers (L07/L27). Store the same data by column instead and that query reads only the 2 columns it names, prunes to 90 of 1,095 day-partitions (11 TB → 900 GB), projects (→ 9 GB), and compresses (→ ~2.5 GB) → a 5 s scan, ~0.5 s across 10 nodes — a 360× cut bought purely by reading fewer bytes, not a faster disk. Model the system: a separate columnar warehouse (analytics and serving have opposite shapes and failure modes — never share one DB), partitioned for pruning and denormalized into a star schema (precompute the join, L15 — normalize for writes, denormalize for reads), fed by an ETL/ELT pipeline that makes it a copy, and so stale. Trace the load (an order is queryable in ms but enters analytics only at the next batch) and the scan (prune → project → scan → merge, L21's partial-then-merge). First wall: the warehouse is stale, and "batch more often" loses (cost scales with history × frequency) → the lambda (two layers, duplicated logic) vs kappa (one replayable stream) reconciliation — guarded by three traps: point lookups on a scan engine (L12's selectivity trap reversed), over-partitioning into a small-file swamp (L20), and late events needing a watermark (L17). Trade named throughout: query freshness vs cost & complexity.
LESSON 28
Backpressure & Flow Control: Saying No Gracefully When Scaling Can't Keep Up
Lesson 27 proved a 2× spike outruns the 3-minute boot time, so for those ~3 minutes the fleet is offered 80,000 req/s but can finish only 40,000 — something has to give. The tempting answer, "just queue the overflow," is exactly what turns a slowdown into a total outage: an unbounded queue grows at 40,000/s and hits ~144 GB in 3 minutes (40,000/s × 180 s × 20 KB) → OOM crash, and even before that goodput collapses to ~0 while throughput stays a deceptive 40,000/s — the server pegged, finishing requests whose clients already timed out. The fix is one idea: bound every queue, sized from the client timeout (depth < timeout × rate = 40,000 → pick 20,000 → max wait 0.5 s, memory a fixed 400 MB, goodput back to full). Then choose how a full queue says no — block the producer (credit-based flow control: TCP window, HTTP/2, request(n)) when you control it, or drop (an honest 429, L07) when you don't. Trace three responses and watch the wasted work: unbounded (crash + retry-storm metastability), bounded-but-shed-deep (survives, but every reject already burned edge + API-tier CPU — ~200 stolen cores), and bounded-plus-edge admission control (downstream fullness travels upstream as a credit signal → 429 the excess for near-free → goodput preserved at L27's knee). First wall: where the "no" goes, guarded by three traps — an unbounded queue hiding at any hop, blocking a shared thread pool (L07 freeze), and blind shedding (drop retries/low-tier/stale head first — FIFO→LIFO — never health checks). Trade named throughout: throughput vs tail latency & stability.
LESSON 27
Autoscaling & Capacity Planning: Sizing a Fleet Before the Spike Hits
Lesson 26 leaned on a word without earning it — headroom. Now earn it for the API tier behind those gateways: 40,000 req/s at peak, 40 ms of CPU each, 8 cores per server. Size the fleet two ways that must agree: Little's Law (L13) fixes the floor — 40,000 × 0.04 s = 1,600 busy cores = 200 servers at an impossible 100% — and the utilization knee (T = S/(1−ρ): a 40 ms request is 133 ms at 70% but 4,000 ms at 99%) sets the real target at 286 servers, the extra 43% (~$377k/yr) buying nothing but distance from the cliff. Model the autoscaler as a feedback loop (measure → compare to 70% → desired = load ÷ (C × ρ*) → act → cool down), scale-out fast / scale-in slow so it doesn't flap (L10). Trace three loads and watch the one thing that decides everything — does load rise slower or faster than a server boots: a gentle morning ramp reactive scaling handles for free; a sudden 2× spike it cannot catch (fleet at 140% for ~3 min, ~4.1M requests backed up); a known 8:30 surge you beat only by pre-scaling ahead. Then the wall: the ~3-minute cold-start lag — a control loop's dead time, minutes against seconds — fought not by deleting boot time but by shrinking the gap: spike-buffer headroom, warm pools, predictive pre-scaling, faster warm-up (and scale-to-zero as the opposite extreme). Trade named throughout: cost vs headroom for spikes.
LESSON 26
Real-Time Delivery: Telling 10 Million Phones "You Got Paid" the Instant It Happens
Lesson 25 settled the money; now tell Bob's phone the instant his balance moves — in ~100 ms, without him asking. That means holding a live connection open to every phone at once: 10 million of them, idle almost all the time, each ready for the one message that matters. Polling instead — every phone asking "anything new?" every 5 s — is 2,000,000 requests/sec to carry only ~232 real events/sec (an ~8,600× waste) and it's still 5 s stale. So flip it: the phone opens one WebSocket (an HTTP request upgraded into a persistent full-duplex socket) and stays quiet; the server speaks first. Model the split that makes a stateful layer scalable — a dumb, disposable gateway holds the raw socket (250k per box, ~40 boxes), while the durable truth user → gateway lives in a shared connection registry with a heartbeat-renewed TTL (and presence falls out for free). Trace Bob connecting, Alice's payment reaching his socket by lookup → forward → one frame, and Bob offline degrading to store-and-forward mobile push + a durable inbox (the live socket is an accelerator, never the truth). Then the wall: a gateway dies and its 250,000 phones reconnect in one second (~6,410/s per survivor, 51× baseline, a lockstep metastable storm) → backoff + jitter (L07), capacity headroom (L23's N−1), and sticky-but-disposable routing. Trade named throughout: statefulness vs elastic scale.
LESSON 25
Payments & Ledgers: Moving $50 So It Can Never Be Lost, Doubled, or Un-Audited
Lesson 24 made the orders table safe to reshape. Now make the money in it trustworthy: Alice pays Bob $50, and forever after the $50 must never vanish or double, a retry must move it once, and an auditor must prove every balance to the penny. The tempting UPDATE balance = balance + 50 fails all three — it races (L06's lost update), keeps no history to audit, and one bad write silently corrupts the number with no way to recompute it. The fix is the oldest idea in accounting: the double-entry ledger, where money is never edited, only appended as paired immutable entries that sum to zero — so a balance is a SUM you derive, not a number you store, and the whole ledger always totals zero (money is conserved via a bank system account). Trace a clean transfer (two entries in one atomic commit, or $50 vanishes), a duplicate retry stopped cold by a unique idempotency key before any entry is written (L13's exactly-once effect, now moving dollars), and a refund that appends a reversal instead of deleting — which is what keeps the books auditable. Then the wall: a hot merchant's balance = SUM of 100M entries takes ~3.2 s → snapshot the running balance (100,000× cut) and shard the account (L21), both kept as derived accelerators over an untouched ledger. Trade named throughout: correctness & auditability vs throughput.
LESSON 24
Schema Changes at Scale: Renaming a Column on a Live 100M-Row Table Without Downtime
Lesson 23 kept two continents' data in agreement. Now change its shape: split the orders table's ambiguous total into amount_cents + currency — on 100M rows taking 50k reads/sec and 5k writes/sec — with zero downtime. The naive ALTER ... RENAME is a double trap: a table-rewriting ALTER on 20 GB locks for ~200 s and queues ~1,000,000 writes, and even a free rename breaks every app server still running old code, because a schema deploy and a code deploy are never simultaneous across a fleet. Fix it with the expand/contract dance — add nullable columns, dual-write both shapes, backfill the old rows in the background (~2.8 h), cut readers over with a plain code deploy, then contract — five small reversible steps where old and new code both always work. Trace a read and write at each stage to pin the two ordering rules (dual-write before backfill; cut readers over only after verifying zero-NULL, keeping the old column warm for instant rollback). Then the wall: one 100M-row UPDATE locks the table and rolls back all-or-nothing → batch it into 20,000 chunks, throttle on replica lag (L06), page by cursor not offset (L18). Trade named throughout: migration safety vs deploy velocity.
LESSON 23
Multi-Region Active-Active: Two Continents, One Cart, and the Write That Can't Be Merged
Lesson 22 kept safety with one writer at a time. Now break that on purpose: run the service live in Virginia and Frankfurt and let both accept writes locally — active-active. A synchronous cross-region write costs ~90 ms (the 6,400 km speed-of-light floor alone is 64 ms) vs ~1 ms local, and a second live region cuts downtime from 8.76 h/yr to ~32 s/yr — but the instant there's no single writer, the same cart can be edited on both continents in one 90 ms window and you must define the merge. Last-write-wins is one timestamp compare that silently drops a shopper's item and trusts a skewable clock; a CRDT models the value so concurrent writes merge — a set unions {headphones, case}, a counter sums per-region tallies so two "+1"s make 3 not 2 (Lesson 06's lost update, now across an ocean). Trace the clean union, the add-vs-remove conflict whose answer is a business policy, and the clock-skew data-loss. Then the wall: a $100 balance withdrawn $80 in VA and $70 in FR converges to −$50 — the CRDT agreed perfectly and still broke balance ≥ 0, because merging preserves convergence, not invariants → single-home, consensus, or escrow. Trade named throughout: local writes vs global order.
LESSON 22
Distributed Locks & Leases: Two Workers, One Billing Job, and the Fencing Token
Lesson 21 left a hazard: two workers both believe they hold the lock on the nightly billing job, and both charge the customer $50. Trace it end to end. A lock is a claim to be the only writer, but a process can freeze — a stop-the-world GC pause, a paused VM — for longer than its lease lives: at t=6s worker A freezes, at t=15s its 15s lease expires, at t=16s worker B acquires and charges, and at t=28s A wakes still believing it holds the lock and charges again. Size the lease TTL (heartbeat 5s → TTL 15s → ≤15s failover) and watch a too-short TTL flap a live-but-slow holder. The lease alone can't save you — it caused the overlap. The real fix is a fencing token: a monotonic number (41, 42) the ledger uses to reject any write from a superseded grant — A's token-41 write is fenced out at the resource, no clock needed. Then the wall: one shared lock serializes to 200 ops/s (13.9 h for 10M charges), is a SPOF, and leans on clocks — which is why a distributed lock is a last resort, behind idempotency and single-writer routing. Trade named throughout: safety vs liveness.
LESSON 21
Analytics at Scale: Counting a Billion Uniques in 12 KB
Lesson 20 left a question: across 25 trillion objects, how many unique cars uploaded today? The exact answer is a set of every ID you've seen — 8 GB at a billion cars, per metric, per hour. Answer three dashboard questions in kilobytes instead with three sketches. HyperLogLog counts distinct cars from the leading zeros of hashes across 16,384 registers in a flat 12 KB at ~0.8% error (650,000× smaller). A Bloom filter answers "have we stored this key?" with no false negatives — 9.6 bits/key, ~1.2 GB for a billion keys — so "definitely new" lets ingest skip the index lookup. A Count–Min sketch estimates how often each car uploaded in 76 KB, only ever rounding up. All three merge across shards (max / add / OR). Then the wall every sketch hits: it tells you how many, never which — fixed by pairing Count–Min with a small heap for the heavy hitters. Trade named throughout: a small, chosen error for constant memory.
LESSON 20
Object Storage: Storing 100 PB Durably Without Paying for 300
The fleet's dashcam clips and photos already fill 100 PB, and it must survive dying disks and be fetched by key. A filesystem drowns in a billion-entry tree; the obvious "keep 3 copies" burns 300 PB of raw disk to survive just 2 failures. Fix it with an object store: a flat key→blob namespace, a tiny consistent metadata plane split from the huge durable data plane (1 TB vs 100 PB — a 100,000× gap), chunking, and erasure coding — RS(10,4) survives 4 losses on just 140 PB, where matching that with copies needs 500 PB (~3.5× more), saving ~$38M/year for more durability. Trace the write (chunk → code → scatter 14 fragments → commit metadata last) and the read (fetch any 10 → decode only if needed), then hit the wall every blob store hits: trillions of tiny 4 KB files that blow the 1 TB index up to 25 PB, because those costs are per-object, not per-byte — fixed by packing into containers. Trade named throughout: durability per raw byte vs simple copies.
LESSON 19
Geo & Proximity: Finding the Drivers Near You Without Scanning a Million
A rider taps "find a ride" and the server must return the drivers within 2 km — out of a million moving cars — in a few milliseconds. Checking every driver is 5 × 10¹⁰ distance calls/sec; indexing one coordinate returns a 4 km strip that wraps the planet, because two 1-D indexes don't intersect into a 2-D box. Fix it by folding 2-D into 1-D: a geohash interleaves the bits of lat/lng (our point → 01001 10110 → 9q…) so nearby points share a prefix and a plain B-tree answers "who's near here?". Handle the boundary problem (a car 100 m away in a different cell) with a 3×3 neighbour query + exact haversine — a 1,100× cut. Then quadtrees (cell size follows density) and S2 (a Hilbert curve on a cube), and the wall every grid hits: a stadium empties and one cell holds 50,000 cars. Trade named throughout: a uniform grid vs load that follows the crowd.
LESSON 18
API Design & Pagination: Paging a Feed Without Dupes or Slowdowns
Lesson 17's N+1 slow hop lived in the shape of an API — so here we design that surface. Take GET /feed and hand a phone one page at a time. The obvious ?limit=20&offset=40 has two production-only bugs: the same post shows twice under inserts, and page 50,000 reads ~1,000,020 rows to return 20 — 50,000× page 1. Fix both with a cursor that names a stable place (created_at, id) and seeks in O(limit) at any depth. Then trace the same request through REST (cacheable, one fixed shape), RPC (named actions), and GraphQL (client picks fields — but the resolver reintroduces the N+1, 21→2 queries, ~10×). End on the wall every public API hits: once shipped you can't change it — additive is safe, removals/renames break clients, versioning is the last resort. Trade named throughout: client convenience vs server cost and stability.

LESSON 13
Idempotency: How to Retry a Payment Without Charging Twice

One timed-out call, traced end to end. A timeout isn't an answer (partial failure), so set it from p99 not a lazy 1 s default, make the retry safe with an idempotency key, gentle with backoff + jitter + a retry budget, and cut losses with a circuit breaker — then backpressure and load shedding instead of an unbounded queue.
